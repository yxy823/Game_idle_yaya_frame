# 项目说明

本游戏只面向 Windows PC，只支持鼠标和键盘操作，不支持手柄、触屏和其他平台。开发环境使用 Windows 11、PowerShell 7、Godot 4.7、GDScript 和 gdUnit4。工具的实际路径写在 `docs/methodology-config.json`。工具能否使用以实际检查结果为准，不根据模板推断已安装了哪些工具。

回复格式（表达方式、提问格式、完成汇报与排查结论的小标题、状态词）按使用者的个人沟通规则，本文件不另写一份：Claude Code 读 `~/.claude/CLAUDE.md`，Codex 读 `~/.codex/AGENTS.md`。

## 使用说明的可读性

编写、更新或整理项目文档时，使用本地 [technical-documentation-writing-godot](.agents/skills/technical-documentation-writing-godot/SKILL.md)，按本次文档类型读取其中的参考。适用于 README、使用说明及需求、设计、知识和报告中的自然语言文字。回复和文档中要避免的写法见[措辞检查](.agents/skills/technical-documentation-writing-godot/references/writing-guide.md#措辞检查)。

所属规范继续决定字段、固定路径、文档语言、流程、授权、验收与完成条件；写作 Skill 不替代这些契约，也不改变机器可读结构。持久项目文档使用 `docs/methodology-config.json` 中的 `document_language`。

## 工作流程与授权

项目由一位使用者与 Agent 配合开发。工作流程不涉及多人协作，也不追踪每处改动由谁完成。

- 支持在同一目录内暂停、切换和续接任务，包括换到新对话后续接。
- 只有当前任务的范围和授权需要时才使用 worktree，并遵循 [Git 与提交](#git-与提交)。任务默认不在 worktree 中开始。
- 限定范围的调研和独立审核使用各自的角色，入口见任务路由表。
- 沿用具体授权，Agent 能完成的工作继续完成；缺少关键信息、决定或实际人工验收时请用户介入，优先提出最关键的问题。可能造成重要数据损失且现有授权未覆盖的操作，执行前确认；已明确批准的同一动作不重复询问。

选择工作流程或下一个允许的动作时，读 [任务路由表](yaya/methodology/00-overview.md#任务路由表)；各工作流程文件分别负责什么，见同页的[延伸阅读](yaya/methodology/00-overview.md#延伸阅读)。Skill 在 `.agents/skills/`，`.claude/skills/` 是供 Claude Code 读取的相同副本，修改 Skill 时两个目录一起改；角色配置同样有 Codex 的 `.codex/agents/*.toml` 和 Claude Code 的 `.claude/agents/*.md` 两种格式，说明正文相同，修改时一起改；显式命令在 `yaya/tools/`。只读选中的流程及其需要的参考，不加载全部工作流程。Skill 返回后，按 [授权与续接](yaya/methodology/03-execute-loop.md#授权与续接) 继续任务。

### 设计前提与需阅读的来源

游戏设计可以从一个想法开始，使用 `design-gdd`。交付规划、实现、工程工作和可运行的实验，都需要能说清当前范围的实质 GDD 内容；只有占位内容的页面不算。完整规则见 [GDD 前提与职责](yaya/methodology/01-product-doc-structure.md#gdd-前提与职责)。Product 文档负责组织交付，链接到 GDD，不复制其中的设计。

在设计讨论、规划、实现或审核之前，按任务阅读下列内容：

- [设计范围与边界](yaya/methodology/01-product-doc-structure.md#设计范围与边界)、与本任务有关的[开放问题](yaya/methodology/01-product-doc-structure.md#开放问题)，以及覆盖该主题的 GDD 页面。
- `docs/terminology.md` 中与本任务有关的定义。
- 与本任务有关的 Product 和专业来源，以及已接受的架构决定。
- `docs/project-rules.md` 中约束本任务的工程规则。Product、Feature 或 ADR 不能悄悄豁免这些规则。

只说明目录用途或待定状态的起始页面，不算已确认的需求或定义。设计讨论不必等待所有后续细节，也不必等待详细的 Product 文档。

## 任务范围

本节适用于每个会修改项目文件的任务。批准、验收和完成条件由所属流程决定，Feature 见 [Stage 0–8 `feature-execute` 执行循环](yaya/methodology/03-execute-loop.md)。

### 修改前先定位

- 读当前实现，以及实际调用它的代码或使用该资源的消费方，找到真正负责这项行为的代码或数据。不按文件名、症状或复制来的示例推断修改位置。
- 新写函数、常量、计算规则或数据转换之前，先在项目中搜索同用途的已有实现；能满足需要就调用它，不另写一份。不能复用时，在动手前的说明中写明原因。把已有的几份重复实现合并成一份属于重构，按下面的「范围判断」单独汇报。
- 确认受影响的契约、模块、数据和验证路径。只追踪必要的依赖。
- 动手前默认用几句话说明改法、实质影响和需要的验证。已批准且仍有效的方案直接复用。这段说明不是审批关卡，也不需要单独的方案文件。

### 范围判断

- 做能完整实现所要求行为的最小修改。“最小”指影响最小，不是文件数最少。
- 修改分为三类：
  - **请求的修改**：用户或所属流程要求的内容。
  - **必要的连带修改**：为保证正确性必须做、因果关系清楚的迁移。它属于任务范围，验证范围随之扩大。
  - **顺带发现的问题**：默认不改。只在它阻塞任务、立即带来正确性或安全风险，或用户扩大范围时才改；有用时单独汇报。
- 已经改到某个文件，不是扩大范围的理由。不做无关的重命名、格式化、目录调整、警告清理、死代码清理、API 现代化、场景规范化或重构。
- 保留已有的公共 API、依赖和局部代码风格。修改共享契约时，迁移全部已知的消费方，并在汇报中说明。
- 现有技术栈够用时不增加依赖。不为假想的未来消费方预先搭建通用框架。结构拆分的依据见[GDScript 结构与依赖](yaya/agent-rules/10-gdscript/structure-and-dependencies.md)。

### 删除与派生产物

- 删除一个产物前，确认它的所属方、引用方（包括动态引用和登记表，字符串引用的来源见[场景引用](yaya/agent-rules/00-core/godot-resource-references.md#场景引用)）、它与源文件或生成器的关系，以及对存档和数据兼容的影响。
- `unused`、`unreferenced` 一类检查结果只说明它是删除候选，不授予删除权限。
- 权威来源变化、且项目规定派生产物要提交时，用正式流程重新生成，并检查结果是确定的、没有过期。
- 工具产生无关的序列化或格式差异时，先检查这些差异，可行时回退无关部分，不整体接受；不能用 Git 回退时（例如派活方禁止 Git 写操作），列出这些差异交给主 Agent，不手工改写。例外：项目自己的记录工具把 Feature 记录 JSON 写回标准格式（见 `yaya/methodology/02-feature-list-schema.md` 的 **文件结构**）造成的差异随本次提交，不手工回退。

### 收尾时核对受影响的文档

任务改变了游戏行为、代码或场景的职责、配置、数值或文件路径时，在最终验证和提交之前，核对描述这些内容的文档是否仍与实际一致。Feature、Feature 之外的实验和 Bug 修复、调试台采纳的收尾都要做这一步；只读任务和只改文档措辞的任务不需要。

1. 在 `docs/`、`dev/` 和项目 README 中搜索本次改动涉及的文件名、类名、函数名、配置键和资源路径，找出提到它们的段落。
2. 对照实际实现，检查这次工作是否：
   - 修改了已接受的游戏设计或交付范围；
   - 新增、重命名、退役或澄清了项目术语；
   - 修改了 Feature 设计稿、当前架构或已记录的导航；
   - 产生了重要的技术决定；
   - 暴露出值得修改的项目规则。
3. 只在所属位置更新有用且已授权的内容。需要新决定或超出本次授权的修改，写进完成汇报的待确认。没有变化时，不要创建文档或空报告。
4. 移动、重命名文档或修改标题后，用 [`check-markdown-links.py`](yaya/tools/README.md#check-markdown-linkspy) 校验链接和锚点。

写过或改过文档的任务（包括只改措辞的），收尾时还要对本次改过的文档运行[check-terminology.py](yaya/tools/README.md#check-terminologypy)，把报出的不用说法改为正式名称；不顺手改本次没碰过的文档。改过的文档可以用 `git status --short -- "*.md"` 列出，直接写在命令后面（也支持 `.json`，只查字符串值）：

```powershell
python -B yaya/tools/checks/check-terminology.py <改过的文档> <另一个文档>
```

提交时，[提交钩子](yaya/tools/README.md#提交钩子)还会对暂存的文档运行术语检查、措辞检查、链接检查和链接文字检查。

Feature 中各类内容的动作与权限见 [3D. 最终验证前的文档检查点](yaya/methodology/03-execute-loop.md#3d-最终验证前的文档检查点)。

## Git 与提交

每个会修改文件的任务都按本节使用 Git，环境准备任务也一样。写入项目需要 Git 仓库。

### 开始修改前

- 在任务指定的工作目录中工作，运行一次 `git status`，记下工作区是否干净。
- 存在 `dev/debug/adoption-log.md` 时，其中列出的改动是用户在调试台中的采纳。这是“保留已有改动、不替用户提交”的例外：先用 `in-game-tuning` 收尾并提交，再开始本次任务。之后是否需要源同步，按 [完成后再调值](yaya/methodology/13-debug-console-and-validation.md#完成后再调值) 判断。
  - **只暂存采纳涉及的路径**：采纳写入的游戏文件、移动的候选，以及收尾时 Agent 修改的 `slot.gd`、`dev/debug/README.md` 与设计文档的资源条目；插槽预设与组合的提交见[收尾步骤](dev/debug/_shared/README.md#收尾步骤)。
  - **用户或派活的主 Agent 要求不提交时**：按其范围执行，只完成收尾的文件修改并报告；被派的子智能体交回主 Agent 提交收尾，再开始本次任务。
  - **收尾受阻时**（例如编辑器不关、测试失败）：报告受阻的步骤，只停下依赖收尾结果的工作。
  - **只读任务**：只报告存在未收尾的采纳，不收尾。
- 只在当前范围和授权需要时使用 worktree，不默认创建。另开工作目录不会隔离工具进程、缓存或 `user://` 等运行时数据；在已有 worktree 中运行编辑器、导入、测试等会写入的工具前，读 [在独立检出目录中准备 Godot](.agents/skills/worktree-create/references/godot-worktree-runtime.md)。
- 存在未完成的合并或变基，或者 HEAD、分支出现本任务无法解释的变化时，保留现场并汇报。弄清之前，不做依赖该状态的写入或提交，也不自动中止、重置或清理。
- 续接时（包括换到新对话），依据工作目录、Feature 与 Progress、当前 HEAD 和实际差异。同一任务留下的改动，核实范围后可以继续完成、验证和提交。

### 暂存

- **开始时工作区干净**：之后出现的改动通常属于本任务，可以用 `git add -A` 暂存。提交前看一眼 `git status`，排除混入的运行产物或缓存，这类文件还没有被忽略时补充 `.gitignore`；也排除明显不是本任务产生的改动，例如编辑器插件写入的本机数据、用户在编辑器里另做的修改，这些保留在工作区，不替用户提交。
- **开始时已有改动**：保留它们及其暂存状态，来源不明的改动也是要保留的工作。只按明确的路径或检查过的差异块暂存本任务的改动，不用 `git add -A`、`git add .` 或 `git commit -a`。无法分离出连贯的提交时，只停下受影响的部分并说明重叠位置；不为方便提交而 stash、restore、删除或覆盖已有改动。
- 提交不另设审核关卡。复用仍然覆盖当前修改的验证结果，出现新的修改、失败或证据失效时才重新检查。

### 提交

- 已授权任务中的完整逻辑修改自动提交，不再次确认；在 `main` 或 `master` 上不要求切换分支。用户或派活的主 Agent 明确要求不提交或规定了提交条件时照办，这些设置跨 Skill、换对话后仍然有效。被派的子智能体被禁止 Git 写操作、又要连续做多个 Feature 时，每个 Feature 做到可以提交时停下，交回主 Agent 提交，再继续下一个。
- 实现授权、人工验收结果和提交许可是三件不同的事，互不代替。任务同时要求人工验收和明确的提交许可时，两者都满足后才提交；已经给出的许可直接复用。
- 一个提交是一个能独立理解的逻辑修改，带上必要的实现、测试、引用和文档。相互独立的 Feature、Bug 和重构分开提交；一个 Feature 可以有多个提交。按连贯的行为和验证划分，不按时间、文件数或“代码”“测试”“文档”划分。
- 主题使用 `<type>(<scope>): <摘要>`。`type` 用 `feat`、`fix`、`refactor`、`test`、`perf`、`build`、`docs`、`chore` 等英文类型；`scope` 选最窄且稳定的范围，执行 Feature 时用 Feature ID；摘要使用 `docs/methodology-config.json` 的 `document_language`（默认中文），写实际的行为变化，不写“修复问题”“更新代码”这类笼统的话。
- 非简单修改写简短正文：改了什么、为什么、关键取舍和实际运行过的主要验证，不罗列文件。剩余工作记在 Feature 与 Progress 中，不把部分交付写成整个 Feature 已完成。
- Feature 或工程 Feature 的每个提交，正文都包含 `Feature: <docs/feature-list.json 中的 title>` 和恰好一行 `Work item: docs/features/F0XX.json`。没有单一 Feature 负责时省略这两行，不编造。
- 本地提交不代表任务完成或人工验收；Feature 的完成由 [Stage 0–8 `feature-execute` 执行循环](yaya/methodology/03-execute-loop.md) 的 Stage 7 确立。已提交的内容需要修正时，新建修正提交。
- [提交钩子](yaya/tools/README.md#提交钩子)报出术语、措辞、链接、链接文字、资源格式或 Skill 目录不一致问题时，按输出改正本次改过的文件，重新暂存后再提交；报出的位置不在本次改动内时，按下一条保留工作并汇报。
- 仓库状态、权限、身份、签名或钩子阻止提交时，保留工作，汇报实际原因和未提交的范围；不为让提交成功而初始化仓库、修改 Git 配置或绕过检查。

示例：

```text
feat(F012): 增加背包容量检查并拒绝超量入库

Feature: 增加背包物品管理

入库前检查剩余容量，超量时返回失败并保持原有物品数量。
验证：容量边界与失败后数量不变的测试通过；解析和 lint 通过。

Work item: docs/features/F012.json
```

### 禁止的操作

- 不自动执行 push、tag、amend、rebase、reset，不修改远程配置，不用 `--no-verify`，不强制改写历史，不使用破坏性的 checkout 或 clean。
- 不在当前任务的具体授权之外创建、切换、合并或删除分支。使用 worktree 不授权修改另一个工作目录，也不授权移除已有工作。

## 验证与完成汇报

以下验证规则适用于各规则模块。测试范围（Required、affected、full）和测试运行的失败条件见 [08 · 测试追溯与证据](yaya/methodology/08-test-traceability-and-evidence.md)；各模块需要的验证写在模块 README 末尾的验证节。

### 选择与组合

- 每个改动的产物都要满足所有适用模块的验证要求，这些要求相互叠加。
- 派活时，主 Agent 按本次修改确定验证要求，并把所属入口交给实施者：测试范围按 08 号规范的[测试影响评估](yaya/methodology/08-test-traceability-and-evidence.md#测试影响评估)，lint 结果按 lint 约定的[lint 的退出码](yaya/methodology/contracts/gdscript-lint.md#lint-的退出码)，gdUnit 的运行方式按 [gdUnit4 运行器与诊断](yaya/agent-rules/70-tests/gdunit4-profile.md)。不用统一的“结束时跑全量”“只看新增 Critical”或“一律无头运行”代替这些规定。
- 运行适用于这次修改的验证，不运行所有能想到的昂贵检查。影响范围不确定时，把可能受影响的相关模块也纳入验证，不声称一个缺乏依据的最小范围。
- 使用项目已配置的入口：`yaya/tools/` 下的命令，以及 [GDScript lint 的约定与证据](yaya/methodology/contracts/gdscript-lint.md) 中的解析和 lint 命令。不编造不受支持的检查器，不为填满清单安装新的工具链。
- 一类验证不代替另一类，除非项目规则明确规定它们对受影响的契约等价。上层检查通过不抵消下层的失败。
- 只有实际执行并成功结束的检查才算通过。按工具的退出码或结构化结果判断，不根据控制台文字猜测。包装脚本不能用退出码 0 掩盖底层检查的失败。lint 的退出码 1 只有 Warning，不算失败，见 lint 约定的[解读结果](yaya/methodology/contracts/gdscript-lint.md#解读结果)。

### 失败处理

- 不通过放宽 lint 阈值、扩大忽略范围、跳过失败的测试、关闭错误监控、降低 schema 严重级别、移除检查或改写规则来换取通过。
- 验证失败是需要归类的证据。不能仅因为检查阻碍了完成，就认定检查出错。
- 修复失败后，重新运行失败的检查，以及这次修复牵连的检查。

### 证据的适用范围

- 证据只证明它实际运行到的环境。规则要求新进程、新导入、新导出或目标运行时的证据时，已有编辑器或会话的结果不能代替。
- 人工验收和自动验证是不同的证据，不把其中一种汇报成另一种。
- 日志、JUnit 报告和临时导出等验证产物按[临时、备份与草稿文件](yaya/agent-rules/00-core/third-party-generated-and-temporary-files.md#临时备份与草稿文件)处理，不变成正式源文件。命令辅助脚本放在哪里、何时提出保存为项目脚本，见[保存常用脚本](yaya/methodology/09-records-reports-and-handoff.md#保存常用脚本)。

### 汇报验证结果

- 写实际执行过的检查及其结果。只有实际执行了完全相同的范围，才能说“所有测试通过”“已完整验证”或同等的话。
- 必需的检查没有执行或被阻塞时，写明原因和具体的剩余风险，不假定通过。
- 清楚列出仍然存在的失败和阻塞，不把部分失败的运行概括为成功。
- 不声称未经测量的性能、平台兼容性、无泄漏、视觉质量或其他没有实际评估过的性质。
- 结果与版本有关时，写明确切的 Godot 或工具版本。
- 概括日志，只在解释失败需要时引用片段。

### 完成汇报

任务何时算完成，由所属流程的完成检查决定。存在未解决的完成阻塞时，不把任务标为完成。已验证的逻辑修改仍可以按 [Git 与提交](#git-与提交) 提交，并如实汇报剩余工作和人工验收情况。

汇报写结果和证据，不复述 Agent 的内部过程，按使用者个人沟通规则中完成汇报的小标题组织（见[项目说明](#项目说明)开头）。按任务规模包含：

- 结论：行为、架构或配置上的实质变化，包括重要的连带迁移；
- 改动：关键的改动文件或文件组，以及为什么需要这些修改。不罗列全部文件，也不复述差异；
- 验证：按[汇报验证结果](#汇报验证结果)写；
- 提交：本任务的提交哈希或已核实的提交范围，以及本任务仍未提交的改动；
- 待确认：视觉修改中仍需人工验收的方面，见[视觉验证边界](yaya/agent-rules/70-tests/test-levels.md#视觉验证边界)；有用的顺带发现，与本任务的失败分开写，避免被误认为本任务造成的回归；
- 下一步：来源包括任务记录中的剩余工作和人工验收。需要完整判断项目接下来做什么时，使用 [next-step-advisor](.agents/skills/next-step-advisor/SKILL.md)。

只汇报当前状态，不把尚未执行的后续工作写成会自动发生的事。只在存在具体的未验证条件、限制或推迟处理的问题时写剩余风险。不为标注“不适用”而逐一列出无关的验证类别。

## 项目知识与规则反馈

在规划、调查、实现、调试或审核中选择做法之前，先按项目知识的[先查找相关知识](docs/knowledge/README.md#先查找相关知识)查阅相关条目。主题为空不阻塞工作。知识不能推翻已接受的决定或规则。

在已获授权的任务文档工作中，按项目知识的[在已获授权的工作中维护](docs/knowledge/README.md#在已获授权的工作中维护)记录有用的做法和失败教训：

- 只读任务保持其写入边界。
- 没有有用的新经验时，不需要写条目。
- 在 Stage 7 提交之前定稿 Feature 笔记和知识条目；Stage 8 链接它们。
- Agent 自己的流程失误按[Lessons](yaya/methodology/09-records-reports-and-handoff.md#lessons)记次数，同样在 Stage 7 提交前定稿。

项目规则、知识条目或其他项目文档中的做法被证明错误时，删除错误的建议，不保留原文，也不加“已取代”“已废弃”之类的标记；同时检查引用它的依据、索引和摘要里有没有同样的说法。只有它容易让人再犯时，才在原处改写成一两句陷阱提示：不要做什么、为什么会出错、怎么做。

工作中发现 `yaya/agent-rules/` 或 `docs/project-rules.md` 尚未覆盖、可复用的规定性指导时，按 [规则的增量维护](yaya/methodology/04-project-rules.md#规则的增量维护) 规定的时机和自查方式提出。没有获得该批准，不修改规则。

规则、Skill、工作流程和命令都不是定死的。执行中发现某条不适用、互相冲突或明显拖慢工作时，写出具体条款、实际情况和影响，提出修改建议，不暗中绕开或自行豁免。用户同意后再改：规则按上一段的规则的增量维护；Skill、工作流程和命令按[工程变更流程](yaya/methodology/07-engineering-change.md)执行。需要改框架本身时，把建议交回框架维护任务，不跨仓库写入。

## 领域规则路由

`yaya/methodology/` 规定工作流程和可追溯性，任务范围、Git、验证与完成汇报写在本文件；`yaya/agent-rules/` 规定具体的引擎与语言规则。

做修改或与修改有关的工程决定时，先读 [`yaya/agent-rules/README.md`](yaya/agent-rules/README.md)：它列出各领域的规则入口和常见任务的阅读组合。只读匹配的文件和小节；一处修改可能同时适用几个模块；规则冲突按[规则冲突的处理流程](yaya/agent-rules/00-core/rule-precedence-and-routing.md#规则冲突的处理流程)解决。
