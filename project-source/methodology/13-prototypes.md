# 13 · 演示台与技术验证

`prototype-godot` 构建有边界的 Godot 场景，用来在正式实现之前回答一个具体问题。按要回答的问题分为三类：

- [画面演示台](#画面演示台)：假逻辑、真画面。确定界面布局和可读性，或比较画面、音效、交互动效等观感候选。
- [逻辑演示台](#逻辑演示台)：真实的一小块规则、占位画面。比较会改变游戏结果的规则候选，或试验一个玩法提议。
- [技术验证](#技术验证)：既定做法能否在真实引擎中实现。

这些工作在已规划的 Feature 或已获授权的实验中运行，入口由[任务路由](00-overview.md#任务路由表)选择。观察结果和暂定参数不是已批准的 GDD 设计，也不是 Feature 的验收。不超出约定的实验预算；超出预算需要用户指示。

## 按要回答的问题选择

| 要回答的问题 | 去处 |
| --- | --- |
| 新界面或明显的布局变化在运行中是否成立：布局、裁切、可读、可点击 | 画面演示台，单方案验证 |
| 观感怎么选：画面、音效、交互动效，以及它们的多组参数 | 画面演示台，比较候选 |
| 规则怎么选：会改变游戏结果的参数或分支，例如输入是否被接受、跳跃高度 | 逻辑演示台，比较候选 |
| 一个玩法提议好不好玩 | 逻辑演示台，候选为“现状”和“这个提议” |
| 既定做法能否在真实引擎中实现：信号、输入、生命周期、存档集成、性能是否达标 | 技术验证 |

用户看描述就能决定的候选，不必做成场景；但这不能免除已有的验证义务，例如新界面的视觉基础检查。判断一个参数属于画面还是逻辑，看它是否改变游戏结果：只影响观感和节奏的放画面演示台，决定操作是否被接受、结果是否成立的放逻辑演示台。

## 共同约定

- **位置**：画面演示台放在 `dev/showcase/visual/<主题>/`，逻辑演示台放在 `dev/showcase/logic/<主题>/`，主题名使用小写连字符。`dev/` 在导出时整体排除，正式场景和代码不能引用其中的文件。
- **候选可以保留**：演示台中的候选是比较材料，可以长期保留，不是正式实现的第二份权威。正式实现单独采纳和维护；不维护两套相互竞争的正式实现。
- **授权与记录**：入口、问题、过程观察和文件处置记录在当前 Feature 的 notes 中，独立实验记录在 Progress 中。每条观察写明是实际运行看到的，还是推断的；推断的标为待核实。候选和采用结果写进对应的来源文档，不另建演示台状态记录文件。
- **验证**：临时候选不强制建立自动验收测试；需要保留的演示台驱动或规则副本按实际风险验证。所属 Feature 已有的验证义务照常执行。静态检查和截图辅助评估，但不能代替实际操作和人的判断；缺少运行或人工反馈时，明确标为未验证。

## 画面演示台

画面演示台不运行正式的游戏规则代码，用本地示例状态或假数据模拟情境，例如“这三颗棋子被消除”“余额从 100 变为 80”。它不连接正式的持久化或实时数据流；如果项目的 Autoload 会运行这些流程，把演示台入口与它们的副作用隔离开。

### 单方案验证（视觉基础）

新界面，或界面布局、资源的较大改动，在实现依赖该界面的逻辑之前，需要先有经过验证的视觉基础。

- 已验证的布局覆盖当前范围时，直接复用。
- 文字或数值的修改、非视觉逻辑和不受影响的模块，不需要做。
- 在周围的画面环境中处理当前界面或模块。不必等全部游戏美术或所有未来画面就绪。

按以下顺序进行：

1. 确定界面的用途和主要状态。
2. 收集有代表性的资源，写出初始规格。
3. 在画面演示台中构建这个界面。
4. 验证并调整布局和尺寸。
5. 实现依赖它的正式逻辑。
6. 细化视觉效果。

资源规格和布局可以一起迭代。Agent 在规划和 Stage 1 资源预检时识别是否需要视觉基础，或者由用户直接要求。这是任务中的判断，不是后台触发。只讨论的工作只提出下一步建议，不写文件，也不构建场景。实现授权覆盖范围内的准备和构建，但永远不能代替用户的视觉验收。

### 比较候选

画面、音效或交互动效有多个候选时，每个候选是演示台目录内的独立场景或资源，可以并存、切换和重放；一组参数也是一个候选，可以有多组、多个参数一起变化。单一维度、静态的比较（例如两套配色）放一个能切换的场景即可。候选可以有自己的素材，素材放在演示台目录内。

改版已经上线的画面时，先把正式版本复制进演示台作为“当前方案”，再和新候选比较。复制按 `yaya/agent-rules/60-assets/naming-paths-and-moves.md` 处理文件身份，复制后的候选只加载 `dev/` 下的脚本和通用依赖，不加载正式规则代码。

### 范围与资源

构建之前，先确定：

- 要回答的问题；
- 目标视口或窗口，以及相关的缩放条件；项目还没有确定显示基线时，先按[视口、窗口与拉伸](../agent-rules/40-project-config/subsystem-settings.md#视口窗口与拉伸)定下来；
- 核心元素和状态；
- 现有资源和剩余缺口。

这些输入由[专业工作与来源](11-specialist-workflows.md)中的 UI、表现和资源规格 Skill 规定。文字草图或 HTML 探索不能验证 Godot 中的结果。需要先准备或提供资源时，按[资源需求与交接](11-specialist-workflows.md#资源需求与交接)处理。

界面需要时，使用有代表性的真实图像、字体、视频、音乐和音效：

- 选择能暴露实际宽高比、细节、文字长度和内容密度的样本。不需要每种媒体类型，也不需要完整素材库。
- 区分源像素尺寸、屏幕上的显示尺寸，以及去掉透明留边后的可见主体尺寸。
- 音频要确定对体验有影响的时长、循环和反馈时机。
- 遵循项目的资源来源记录和导入规则。
- 缺少样本时，对应的检查保持未验证。说明缺口，并找到合适的样本或用户接受的替代品。文字、静音或占位文件名不能证明检查通过。

在周围布局中放入实际的内容区域、有代表性的物品、按钮和文字。只添加评估所需的交互，例如悬停、按下、选中和禁用反馈，打开面板、滚动或预览播放。原生控件无法表达所需反馈时，一个小的本地脚本就够了。此时最终的背景、装饰和配色是可选的；评估需要可读的对比度和可区分的交互状态。

### 运行检查

在目标项目已确认的 Godot 环境中运行场景。在约定的显示条件下，检查空间关系、资源尺寸与裁切、文字可读性、按钮可用性，以及相关的空状态、密集状态和长文本状态。实际操作这些交互，并试听相关样本。

## 逻辑演示台

逻辑演示台回答规则问题：一个会改变游戏结果的参数或分支应该怎么定，或一个玩法提议好不好玩。画面用占位即可，不在这里比较观感。

构建之前，先确定：

- 问题本身；
- 相关的已确认 GDD 规则；
- 能回答这个问题的观察结果；
- 有边界的实验。

规则的来源：

- 正式代码已经把这个值做成参数（例如导出变量）时，直接使用正式逻辑，通过可测试的公开接口设定起始状态。
- 候选是不同的分支或流程时，在 `dev/showcase/logic/<主题>/` 中写候选规则：复制需要改动的正式文件，它依赖而不需要改动的文件可以只读引用。不在正式代码里为候选加分支。
- 正式逻辑还不存在时，在演示台中只写回答问题需要的那一小块。

每个候选的规则先写成可以实现的描述，例如“连锁期间的点击排队，执行前重新判断是否相邻”。占位画面如果参与流程推进（例如逻辑等待画面播放完成），使用与正式画面相同的推进方式，时长取表现文档中的值，否则手感判断会失真。

优先使用一个小型、可独立运行的场景，只包含问题需要的状态和交互：让相关状态可见，支持重置到已知的起点，并把自由操作和能暴露不确定点的可重复情境结合起来。以制作队列为例，有用的情境可能包括材料不足、暂停，或取消与返还。候选数量没有硬性要求。

未确定的设计选择保持为提议，演示台不会批准新规则。之前的实验仍能回答这个问题时，复用它。只有用户明确要求一个与引擎无关的概念演示时，才可以用 HTML；它不是必经的前置步骤，也不是 Godot 行为的证据。

## 技术验证

技术验证回答“既定的做法能否在真实引擎中实现”，例如信号与生命周期的配合、输入路由、存档集成、某种渲染做法的性能能否达标。已经实现的功能出现卡顿时，用 `diagnostics-performance` 定位，不属于这里。

- 问题涉及实际的信号、输入、生命周期、持久化或其他引擎集成时，在任务权限内运行真实路径，并保护实时数据。模拟的转换不能证明集成可用。
- 结论分为可行、受限（写明限制条件）、不可行、未验证四种，并写明适用的版本和环境。
- 临时探针代码放在 `reports/scratch/<任务>/`。作为后续实现参考需要保留的，移到 `dev/` 下并在 notes 写明用途，其余在授权范围内删除。结论、限制和必要的原始证据保留在 Feature notes、Progress 或报告目录中。

## 验证与采纳

报告每项工作回答了什么、实际的观察结果和剩余的限制。

每项已确认的变化交回它的来源，采纳遵循任务授权和[专业工作与来源](11-specialist-workflows.md#归属与决策)中的来源修改路由：

- 游戏设计通过 `design-gdd`（限定范围的数值设计通过 `design-balance`）写入 GDD，交付边界写入 Product，布局、表现、尺寸、可读性或声音规格写入对应的专业文档。
- 当前 Feature 内已规划的待定参数，在 Stage 3 文档检查点写入；改变已确认的要求时，由负责的 Skill 修改来源，再按 `feature-sync` 同步计划。
- 资源细节保存在使用该资源的设计文档中。节点属性和调参数值留在场景、资源或实现说明中。不维护第二份规格。

视觉基础 Feature 定下的布局、尺寸、色值、时长等参数，在人工验收之前写进专业文档：

- 在 Stage 3 文档检查点、Stage 4 之前，把演示台实际使用的值写进负责它的专业文档对应小节，替换规划时的“待定”说明。这样用户验收的场景和文档属于同一个快照。
- 写法不带验收状态，例如“以下参数由 F001 的画面演示台确定，采纳情况见 F001 的人工验收记录”。不写“试验值，供用户接受或调整”这类验收后会过时的话，也不在验收后回头改成“已采纳”：验收之后修改来源文档会使证据失效，见[最终验证前的文档检查点](03-execute-loop.md#3d-最终验证前的文档检查点)。
- 用户在人工验收中接受这些值就是采纳，不需要再写回一次。用户要求调整时，修改演示台和文档中的值，重做 Stage 4 和 Stage 5。
- Feature 按 AC 填写来源中已列为待定的参数，不触发 `feature-sync`，见[编写与采纳](11-specialist-workflows.md#编写与采纳)的变化路由。

在已规划的交付中，可以单独审查的视觉基础使用普通 Feature；该 Feature 要求人工验收时，依赖它的实现要等人工验收完成。范围很窄的检查可以留在当前 Feature 内，前提是视觉决定在依赖逻辑之前确定。用户明确要求的独立探索，按[任务路由](00-overview.md#任务路由表)中“用户明确要求的演示台或技术验证”一行处理。演示台的验收只覆盖它的视觉或规则范围，永远不覆盖后续的业务行为。

落地到正式实现：

- **画面候选**：把选中的场景、参数和资源依赖复制进正式目录，重建文件身份并改正引用，去掉示例状态的连接；演示台中的原件保留。只有明确退役的候选才移动或删除。
- **规则候选**：由 Feature 按写进 GDD 的规则正式实现；演示台中的规则副本不复制进 `game/`。
- 落地后以正式游戏中的人工验收为准。发现表现差异回画面演示台，规则差异回逻辑演示台，实现问题在 Feature 内修正。

成功的演示台或验证不代表可以投入正式使用，也不代表已有必需的回归测试覆盖或人工验收。不要让没有相关不确定点的工作以演示台或验证为前提。带已登记测试的场景，删除前按[需求变化与过时的测试](08-test-traceability-and-evidence.md#需求变化与过时的测试)退役这些测试。
