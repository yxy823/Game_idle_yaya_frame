# 15 · 任务范围、Git 与完成汇报

本文适用于每个会修改项目文件的任务，规定修改范围、Git 改动的保留与本地提交，以及完成时汇报什么。批准、验收和完成条件由所属流程决定，Feature 见 [03 执行规范](03-execute-loop.md)。验证证据的规则见[验证策略](../agent-rules/00-core/validation-policy.md)。

## 任务范围

### 修改前先定位

- 读当前实现，以及实际调用它的代码或使用该资源的消费方，找到真正负责这项行为的代码或数据。不按文件名、症状或复制来的示例推断修改位置。
- 确认受影响的契约、模块、数据和验证路径。只追踪必要的依赖。
- 建议：动手前用几句话说明改法、实质影响和需要的验证。已批准且仍有效的方案直接复用。这段说明不是审批关卡，也不需要单独的方案文件。

### 范围判断

- 做能完整实现所要求行为的最小修改。“最小”指影响最小，不是文件数最少。
- 修改分为三类：
  - **请求的修改**：用户或所属流程要求的内容。
  - **必要的连带修改**：为保证正确性必须做、因果关系清楚的迁移。它属于任务范围，验证范围随之扩大。
  - **顺带发现的问题**：默认不改。只在它阻塞任务、立即带来正确性或安全风险，或用户扩大范围时才改；有用时单独汇报。
- 已经改到某个文件，不是扩大范围的理由。不做无关的重命名、格式化、目录调整、警告清理、死代码清理、API 现代化、场景规范化或重构。
- 保留已有的公共 API、依赖和局部代码风格。修改共享契约时，迁移全部已知的消费方，并在汇报中说明。
- 现有技术栈够用时不增加依赖。不为假想的未来消费方预先搭建通用框架。结构拆分的依据见[结构与依赖](../agent-rules/10-gdscript/structure-and-dependencies.md)。

### 删除与派生产物

- 删除一个产物前，确认它的所属方、引用方（包括动态引用和登记表）、它与源文件或生成器的关系，以及对存档和数据兼容的影响。
- `unused`、`unreferenced` 一类检查结果只说明它是删除候选，不授予删除权限。
- 权威来源变化、且项目规定派生产物要提交时，用正式流程重新生成，并检查结果是确定的、没有过期。
- 工具产生大量无关的序列化或格式差异时，先检查这些差异，可行时回退无关部分，不整体接受。

## Git 与提交

项目由一位使用者与 Agent 配合开发。本节不建立多人协作下的改动归属机制。写入项目需要 Git 仓库；环境准备任务同样遵循本节。

### 工作目录与已有改动

- 在任务指定的工作目录中工作，先核对它的实际路径和 Git 状态。
- 只在当前范围和授权需要时使用 worktree，不默认创建。另开工作目录不会隔离工具进程、缓存或 `user://` 等运行时数据。
- 开始修改前，查看 Git 状态和相关差异。
- 保留已有的无关改动及其暂存状态。来源不明的改动也是要保留的工作。
- Git 状态非空不阻止已授权的任务。不为了得到干净的目录或方便提交，而 stash、restore、删除、覆盖或纳入无关改动。
- 续接时（包括换到新对话），依据工作目录、Feature 与 Progress、当前 HEAD 和实际差异。仍然有效的决定和授权继续使用。同一任务留下的改动，核实范围后可以继续完成、验证和提交。不建立改动归属记录文件。
- 出现下列情况时，只停止依赖它的那部分修改，并说明重叠的具体位置；其他已授权工作继续：
  - 要求的修改与已有内容冲突；
  - 预期结果有实质歧义；
  - 无法从无关改动中分离出一个连贯、已验证的提交。

  不靠丢弃已有工作来解决冲突。
- 存在未完成的合并或变基，或者 HEAD、分支出现本任务无法解释的变化时，保留现场并汇报。弄清之前，不做依赖该状态的写入或提交，也不自动中止、重置或清理。

### 暂存

- 只暂存属于当前逻辑修改的路径或差异块。使用明确的路径参数，或检查过的差异块选择。
- 不使用 `git add .`、`git add -A`、`git commit -a` 或宽泛的通配符。
- 提交不另设审核关卡。复用仍然覆盖当前修改的验证结果，不为每次提交重读完整的暂存差异。出现新的修改、失败或证据失效时，才重新检查。
- 提交内容需要的依赖一并纳入。

### 本地提交

- 已授权任务中的完整逻辑修改自动提交，不再次确认。分支名是 `main` 或 `master`，本身不要求切换分支。
- 用户明确要求不提交，或规定了提交条件时，在其范围内照办。这些设置跨 Skill 继续有效，续接到新对话后仍然有效。
- 实现授权、人工验收结果和提交许可是三件不同的事，任何一个都不能代替另一个。任务同时要求人工验收和明确的提交许可时，两者都满足后才提交。已经明确给出的许可直接复用，不再询问。
- 本地提交不代表任务完成，也不代表人工验收。Feature 的完成由 [03 执行规范](03-execute-loop.md) 的 Stage 7 确立。
- 已提交的内容需要修正时，修复并验证后新建修正提交，不改写已有提交。
- 仓库状态、权限、身份、签名或钩子阻止提交时，保留工作，汇报实际原因和未提交的范围。不为让提交成功而初始化仓库、修改 Git 配置或绕过检查。

### 提交边界

- 一个提交是一个能独立理解的逻辑修改，带上它必要的实现、测试、引用和文档。
- 相互独立的 Feature、Bug 和重构分开提交。同一根因的修改，只在必须一起实现和验证时放进同一个提交。
- 一个 Feature 可以有多个提交，后面的提交可以依赖前面已提交的工作。
- 按连贯的行为和验证划分边界，不按时间、文件数，或“代码”“测试”“文档”这样的阶段划分。

### 提交说明

- 主题使用 `<type>(<scope>): <摘要>` 格式：
  - `type` 用 `feat`、`fix`、`refactor`、`test`、`perf`、`build`、`docs`、`chore` 等常用类型，保持英文。
  - `scope` 选最窄且稳定的范围。执行 Feature 时用 Feature ID，例如 `F012`。
  - 摘要使用 `docs/methodology-config.json` 中 `document_language` 指定的语言；默认 `zh-CN`，即中文。摘要写本次提交实际的行为或流程变化，不只重复 Feature 标题，也不写“修复问题”“更新代码”“优化逻辑”这类笼统的话。
- 非简单修改写简短正文：改了什么、为什么需要、关键取舍，以及实际运行过的主要验证。不罗列文件。
- 剩余工作记在 Feature 与 Progress 中。正文只在某项限制会影响理解或使用本次修改时提及，不把部分交付写成整个 Feature 已完成。
- Feature 或工程 Feature 的每个提交（包括增量实现和完成记录的提交），正文都包含下面两行：
  - `Feature: <title>`，取 `docs/feature-list.json` 中对应条目的 `title`；
  - 恰好一行 `Work item: <relative-path>`，指向该 Feature 的详情记录，例如 `Work item: docs/features/F012.json`。
- 没有单一 Feature 负责的任务，省略这两行。不编造名称或路径，也不让它们指向实现文件。

示例（名称、修改和验证换成实际情况；除 `Feature:` 和 `Work item:` 外，正文按需要写）：

```text
feat(F012): 增加背包容量检查并拒绝超量入库

Feature: 增加背包物品管理

入库前检查剩余容量，超量时返回失败并保持原有物品数量，避免部分写入后调用方无法判断结果。
验证：容量边界与失败后数量不变的测试通过；解析和 lint 通过。

Work item: docs/features/F012.json
```

### 禁止的操作

- 不自动执行 push、tag、amend、rebase、reset，不修改 Git 远程配置，不用 `--no-verify` 绕过钩子，不强制改写历史，不使用破坏性的 checkout 或 clean。
- 不在当前任务的具体授权之外创建、切换、合并或删除分支。使用 worktree 不授权修改另一个工作目录，也不授权移除已有工作。

## 完成汇报

任务何时算完成，由所属流程的完成检查决定。存在未解决的完成阻塞时，不把任务标为完成。已验证的逻辑修改仍可按本文提交，并如实汇报剩余工作和人工验收情况。

汇报写结果和证据，不复述 Agent 的内部过程。按任务规模包含：

- 行为、架构或配置上的实质变化，包括重要的连带迁移；
- 关键的改动文件或文件组，以及为什么需要这些修改。不罗列全部文件，也不复述差异；
- 验证结果，按[汇报验证结果](../agent-rules/00-core/validation-policy.md#汇报验证结果)写；
- 本任务的提交哈希或已核实的提交范围，以及本任务仍未提交的改动；
- 视觉修改中仍需人工验收的方面，见[视觉验证边界](../agent-rules/70-tests/test-levels.md#视觉验证边界)；
- 有用的顺带发现，与本任务的失败分开写，避免被误认为本任务造成的回归。

只汇报当前状态，不把尚未执行的后续工作写成会自动发生的事。只在存在具体的未验证条件、限制或推迟处理的问题时写剩余风险。不为标注“不适用”而逐一列出无关的验证类别。
