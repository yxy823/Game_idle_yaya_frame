# 13 · 调试台与技术验证

本文规定两件事：在游戏内调试台中比较候选、调参并采纳到游戏，以及用技术验证回答既定做法能否在真实引擎中实现。调试台的工作由 `debug-console-godot` 执行，技术验证由 `technical-validation-godot` 执行，入口由[任务路由](00-overview.md#任务路由表)选择。本文只写原则与流程；调试台的具体机制（`slot.gd` 常量、预设格式、收尾命令）写在[调试台共享代码说明](../../dev/debug/_shared/README.md)，本项目的调试对象与启动命令写在[本项目的调试台](../../dev/debug/README.md)。

## 选择方式

| 要回答的问题 | 去处 |
| --- | --- |
| 新界面或明显的布局变化在运行中是否成立：布局、裁切、可读、可点击 | 先建最小真实骨架，再在调试台做视觉决策，见[界面的开发顺序](#界面的开发顺序) |
| 已有界面或效果的观感怎么选：画面、音效、交互动效，以及它们的参数 | 调试台：在插槽中比较候选、调参，见[调试台](#调试台) |
| 会改变游戏结果的规则怎么选，或一个玩法提议好不好玩，游戏已有对应骨架 | 调试台的[逻辑候选](#逻辑候选) |
| 同上，但游戏还没有对应的骨架 | 先规划并完成骨架 Feature，再做逻辑候选 |
| 纯数值的模型、公式或参数区间 | `design-balance`，不建候选 |
| 已完成 Feature 用到的值，用户想再改 | [完成后再调值](#完成后再调值) |
| 既定做法能否在真实引擎中实现：信号、输入、生命周期、存档集成、性能是否达标 | [技术验证](#技术验证) |

用户看描述就能决定的候选，不必做成可运行的候选；但这不能免除已有的验证义务，例如新界面的视觉决策。判断一个参数属于观感还是规则，看它是否改变游戏结果：只影响观感和节奏的是观感候选，决定操作是否被接受、结果是否成立的是逻辑候选。

调试台和技术验证都在已规划的 Feature 或已获授权的实验中运行。入口、问题、过程观察和文件处置记录在当前 Feature 的 notes 中，独立实验记录在 Progress 中。每条观察写明是实际运行看到的，还是推断的；推断的标为待核实。不超出约定的实验预算；超出预算需要用户指示。

## 调试台

调试台从调试入口启动真实游戏，在独立窗口中修改游戏正在使用的调参资源。候选、参数和固定局面都作用在真实游戏上，不在 `dev/` 中另写假系统或示例状态。

### 入口与依赖方向

- **调试入口**是 `dev/debug/debug_main.tscn`。它先挂上调试窗口，再切到项目的主场景；平时运行主场景，调试时启动调试入口。启动命令只写在[本项目的调试台](../../dev/debug/README.md#启动)，其他文档引用它。
- **项目挂钩** `dev/debug/debug_project.gd` 属于项目自己：按项目的存档系统把调试会话的存档指到只供调试的 `user://` 文件。没有改写时调试会话可能写入真实存档，调试窗口会提示。游戏要为此提供可配置的存档位置，见 [Autoload](../agent-rules/40-project-config/autoloads-and-plugins.md#autoload)。
- **依赖只能从 `dev/` 指向游戏**：`game/`、`main/`、`components/` 和 `project.godot` 不引用 `dev/` 下的路径、UID 或类名；游戏和 `tests/` 不读取预设与组合。调试台不用 Autoload 挂载，因为 Autoload 写在 `project.godot` 中，会让游戏引用 `dev/`。依赖方向由默认登记的不变量测试 `tests/invariants/debug_dependency_test.gd` 检查。
- **正式导出**整体排除 `dev/`，见[导出资源与过滤器](../agent-rules/41-export-config/resources-and-filters.md)。

入口的启动顺序和窗口操作见[入口与项目挂钩](../../dev/debug/_shared/README.md#入口与项目挂钩)。

### 调试对象、插槽与候选

| 层 | 编号例子 | 含义 |
| --- | --- | --- |
| 调试对象 | `shop`、`global` | 游戏里的一个界面，或跨界面共用的 `global`。键名与 `game/<对象>/` 一致，与 UI 规格界面键的对应见[界面规格目录](../../docs/ui/README.md#文件放在哪里) |
| 插槽 | `shop/feedback/sound` | 调试对象中一个可调的部分，对应 `game/<对象>/tuning/` 下的一份调参资源，目录层级即类别 |
| 候选 | `shop/feedback/sound` 下的“明亮” | 插槽的一种实现：场景、脚本、音效或图片。没采纳时放在 `dev/debug/` 中，采纳后移进 `game/` |

- 新增功能等于新增插槽，调试对象的编号不变。每个插槽只属于一个调试对象，避免两处同时修改同一参数。
- 每个插槽最多一个候选字段；有多个可替换部分时拆成多个插槽。候选自带的参数放在调参资源的 `candidate_params` 中，面板只显示当前候选的参数。
- `game/` 为每类插槽定义候选基类，例如特效候选提供 `play(context)`，候选继承它。
- 插槽、候选和试播动作按目录自动发现，不维护登记清单。目录约定与 `slot.gd` 的声明见[调试对象、插槽与候选](../../dev/debug/_shared/README.md#调试对象插槽与候选)。

### 调参资源

调参资源是 `game/<对象>/tuning/**/*.tres` 下的独立资源，保存调试台可以修改的全部取值：参数、选中的候选和候选参数。它是这些取值在游戏中的唯一位置。

- **文档链接资源，不抄数值**：UI 规格、表现文档或 Feature AC 需要某个取值时，链接这份资源文件；Feature 设计稿也不复制调试窗口里看到的数值。规划时尚未确定的参数同样由调参资源承载，来源文档链接它并写明由哪个 Feature 确定。
- **测试不写死调优值**：测试对照参数所在的资源，见[测试层级](../agent-rules/70-tests/test-levels.md)。
- **工程约束**：独立文件、运行时只由调试台修改、setter 发出 `changed`、不复制、一份资源一个插槽，见[调参资源](../agent-rules/21-resources/roles-sharing-and-locality.md#调参资源)。

一次性效果（特效、音效）每次触发时读取参数；持久状态（格子尺寸、主题色、循环中的音乐）由使用方监听资源的 `changed` 后重新应用。所以改动在下一次使用时生效，不需要重启游戏。

### 预设与组合

- **插槽预设**保存一个插槽的一组取值，**组合**按调试对象引用一组插槽预设，空项表示游戏原值。两者都是候选设定，不是游戏的值。
- 预设与组合由调试台在运行中保存，不是游戏资源：不补 UID，资源格式检查跳过它们，修改它们也不改变[内容指纹](08-test-traceability-and-evidence.md#内容指纹)。所以验收期间试调、另存或删除预设，不会让证据失效。
- 字段改名或候选删除后，载入时只让对不上的项回到游戏原值。迁移规则见 [Schema](../agent-rules/21-resources/identity-saving-and-schema.md#schema)，文件格式见[插槽预设与组合](../../dev/debug/_shared/README.md#插槽预设与组合)。

### 对比

对比是“当前改动”和对比对象之间的切换。对比对象默认是**游戏原值**，即游戏文件中保存的值；也可以选一个已保存的组合。比较不需要事先准备一组“当前版本”的副本，也不复制游戏文件进 `dev/`。固定局面播放中切换时，在下一遍开头生效。

### 采纳到游戏

“采纳到游戏”是用户在调试台中把当前设定写进游戏文件的一步操作，用户确认一次即可。

- 候选还在 `dev/` 时，调试台先把它移进 `game/` 再写参数。只有素材的候选当场生效；含脚本、场景或文本资源的候选排到下次启动调试入口时移动。
- 被替换的实现留在 `game/`，之后仍可在调试台选回；发布前由用户决定删除或排除，见[导出资源与过滤器](../agent-rules/41-export-config/resources-and-filters.md)。从未采纳的候选留在 `dev/`，用户要求时 Agent 删除，Git 历史可以找回。
- 每次采纳都记在 `dev/debug/adoption-log.md`。这个文件存在，表示有采纳还没收尾：运行中写的 `.tres` 缺外部资源 UID，移动的文件也还没被编辑器重新扫描。Agent 用 `debug-console-godot` 按[收尾步骤](../../dev/debug/_shared/README.md#收尾步骤)补 UID、检查、测试并提交。对话开始时发现这个文件的处理见 `AGENTS.md` 的[开始修改前](../../AGENTS.md#开始修改前)。
- 采纳到游戏不等于验收通过。验收针对的是采纳后的游戏原值，见[验收](#验收)。

采纳的具体行为、Godot 编辑器开着时的处理见[采纳到游戏与收尾](../../dev/debug/_shared/README.md#采纳到游戏与收尾)。

### 固定局面、试播与测试状态

- **固定局面**是调试对象登记的一个可反复播放的游戏状态，例如“三轮连消”“资源充足、已解锁一半”。它就是一份游戏存档：按游戏自己的存档格式保存，包括随机种子，走游戏自己的读档路径进入，不另设状态注入接口。局面文件放在 `tests/fixtures/` 或 `game/`，测试与调试台共用。
- **试播动作**是插槽登记的“点一下就看到效果”的动作，例如在棋盘中央生成一个火箭并引爆，用于真实游戏里很难等到的效果。
- **测试状态与状态控制**：内容很深的系统（技能、后期关卡）需要直接进入某个进度，或在运行中升级、给物品、刷敌人。测试状态同样用游戏存档格式保存，状态控制只调用游戏的公开功能，不在调试台里直接改游戏状态。共享代码目前只提供固定局面，其余按项目的真实需求在该调试对象中细化。

为了支持固定局面，游戏从一开始就满足以下要求：

- 存档位置可配置，主场景开始时才读档，Autoload 的 `_ready` 不读档、不开自动保存，见 [Autoload](../agent-rules/40-project-config/autoloads-and-plugins.md#autoload)；
- 随机数可设种子，见[随机数](../agent-rules/10-gdscript/state-resources-and-loading.md#随机数)；
- 有“这一遍结束”的信号，供调试台循环播放和锁定参数使用；需要等特效或音频播完时，同时提供尾部反馈是否结束的查询。

`debug_target.gd` 的登记方式见[固定局面与播放](../../dev/debug/_shared/README.md#固定局面与播放)。

### 从编辑器启动

主要方式是命令行启动。需要脚本热重载或远程场景树时，也可以在 Godot 编辑器中打开 `debug_main.tscn` 按 F6 运行，但调参只在调试台里改：编辑器检查器显示的是编辑器自己的资源副本，不是游戏当前值。从编辑器停止（F8）会直接结束游戏，不出现保存提问，未保存的改动丢失，所以停止前先在调试台保存。其余限制见[从编辑器启动](../../dev/debug/_shared/README.md#从编辑器启动)。

## 界面的开发顺序

新界面，或界面布局、资源的较大改动，按三步开发：

1. **骨架**：在游戏中做这个界面最小的真实骨架，范围是“本次固定局面需要的状态和状态转换”，外观用占位；同时建立 `game/<对象>/tuning/` 下的调参资源。不在 `dev/` 中写假系统。骨架用自动测试验证。
2. **视觉决策**：Agent 用 `debug-console-godot` 登记插槽、候选和固定局面；用户在调试台比较、调参并采纳到游戏。外观已经选定时只有一个候选，用户在调试台确认布局、裁切、可读和可点击。
3. **完整逻辑**：补完其余规则。只有读取视觉参数（例如动画时长）的部分等待视觉决策验收，其余部分可以并行。

三步对应三个 Feature，拆法与 AC 写法见[拆分规则](02-feature-list-schema.md#拆分规则)，Stage 中的位置见[资源](03-execute-loop.md#1b-资源)。文字或数值的修改、非视觉逻辑和不受影响的模块，不需要这个顺序；已验证的布局覆盖当前范围时直接复用。

视觉决策开始之前，先确定：

- 要回答的问题和界面的主要状态；
- 目标视口或窗口，以及相关的缩放条件；项目还没有确定显示基线时，先按[视口、窗口与拉伸](../agent-rules/40-project-config/subsystem-settings.md#视口窗口与拉伸)定下来；
- 现有资源和剩余缺口，输入由[专业工作与来源](11-specialist-workflows.md)中的 UI、表现和资源规格 Skill 规定；需要先准备资源时，按[资源需求与交接](11-specialist-workflows.md#资源需求与交接)处理；
- UI 规格中列出的界面任务，写法由 `design-ui-spec` 规定。

候选使用有代表性的真实图像、字体、视频、音乐和音效：

- 选择能暴露实际宽高比、细节、文字长度和内容密度的样本。不需要每种媒体类型，也不需要完整素材库。
- 区分源像素尺寸、屏幕上的显示尺寸，以及去掉透明留边后的可见主体尺寸。
- 音频要确定对体验有影响的时长、循环和反馈时机。
- 缺少样本时，对应的检查保持未验证。说明缺口，并找到合适的样本或用户接受的替代品。文字、静音或占位文件名不能证明检查通过。

文字草图或 HTML 探索不能验证 Godot 中的结果。在约定的显示条件下检查空间关系、资源尺寸与裁切、文字可读性、按钮可用性，以及相关的空状态、密集状态和长文本状态。

## 逻辑候选

逻辑候选回答规则问题：一个会改变游戏结果的分支或流程应该怎么定，或一个玩法提议好不好玩。本节的规则还没有在真实项目中验证过，第一次实际使用时核对并修正。

- **前提**：游戏已有对应的骨架或正式逻辑。还没有时，先规划骨架 Feature，不在 `dev/` 中另写一套核心规则。
- **规则从调参资源取实现**：游戏通过调参资源持有规则实例并调用它，不写死静态调用。某处出现两个以上候选时，就把它改成从调参资源取实现；这是固定规则，不由 Agent 判断“将来会不会变化”。这次改动属于所在的 Feature，按正常流程测试。
- **候选写法**：每个候选是继承游戏中规则基类的脚本，先写成可以实现的描述，例如“连锁期间的点击排队，执行前重新判断是否相邻”。不复制正式文件，也不在正式代码里为候选加分支。
- **占位画面参与流程推进时**（例如逻辑等待动画播完），使用与正式画面相同的推进方式，时长取调参资源中的值，否则手感判断会失真。
- **不是这里的问题**：只涉及数值模型、公式或参数区间时交给 `design-balance`；做法能否实现交给[技术验证](#技术验证)。

未确定的规则保持为提议，调试台不会批准新规则。用户选定一个逻辑候选后，先由 `design-gdd` 把规则写进 GDD，再在已获授权的 Feature 中采纳到游戏并验证。

## 完成后再调值

本节是 Feature 完成后再改调参资源时的唯一路由。用户随时可以在调试台调值并采纳到游戏；采纳本身不需要先通知 Agent。

1. **先收尾提交**：Agent 发现 `dev/debug/adoption-log.md` 时，先用 `debug-console-godot` 按[收尾步骤](../../dev/debug/_shared/README.md#收尾步骤)完成收尾并提交，再做别的任务。这样被写入的资源作为来源已经提交。
2. **查找链接它的文档**：在 `docs/` 下搜索每份被写入的调参资源的路径，查看哪些 GDD、UI 规格、表现文档、Feature 设计稿或 Feature AC 链接了它。
3. **按命中情况处理**：

| 命中情况 | 处理 |
| --- | --- |
| 被已完成 Feature 的文档或 AC 链接 | 报告受影响的 Feature，运行 `feature-sync`。被文档链接的调参资源属于[查找与映射来源](11-specialist-workflows.md#查找与映射来源)中的来源，`feature-sync` 从资源的 Git 差异建立变更；已完成 Feature 的验收记录保持历史，需要重新验收时由新的 Feature 完成。 |
| 只被进行中的 Feature 链接 | 留在该 Feature 内处理：Stage 3 中的采纳是正常工作；人工清单绑定之后的采纳等于拒绝本次验收，见 [Stage 5](03-execute-loop.md#stage-5--明确的人工验收仅-manual-模式)。 |
| 没有被任何文档或 AC 链接 | 收尾提交即完成，不需要源同步。 |

用户也可以直接说“收尾调试台采纳”，从第 1 步开始。

## 技术验证

技术验证回答“既定的做法能否在真实引擎中实现”，例如信号与生命周期的配合、输入路由、存档集成、某种渲染做法的性能能否达标。已经实现的功能出现卡顿时，用 `diagnostics-performance` 定位，不属于这里；纯技术试验（例如轨迹探针）也不进调试台。

- 问题涉及实际的信号、输入、生命周期、持久化或其他引擎集成时，在任务权限内运行真实路径，并保护实时数据。模拟的转换不能证明集成可用。
- 结论分为可行、受限（写明限制条件）、不可行、未验证四种，并写明适用的版本和环境。
- 临时探针代码放在 `reports/scratch/<任务>/`。作为后续实现参考需要保留的，移到 `dev/<主题>/` 并在 notes 写明用途，其余在授权范围内删除。结论、限制和必要的原始证据保留在 Feature notes、Progress 或报告目录中。

## 验收

- **验收针对游戏原值**：人工验收检查的是采纳后游戏文件中的值，不是某个预设或组合。Feature 在 Stage 3 中、人工清单绑定之前完成采纳和收尾，见[最终验证前的文档检查点](03-execute-loop.md#3d-最终验证前的文档检查点)。清单的入口写调试入口和固定局面，见[人工验收文件](contracts/manual-acceptance-files.md)。
- **验收中改值等于拒绝**：用户在验收期间可以随意试调和另存预设，不影响证据；但又采纳了新值，就等于拒绝本次验收，按 [Stage 5](03-execute-loop.md#stage-5--明确的人工验收仅-manual-模式) 回到 Stage 3。
- **作者先试用**：Feature 改动了有界面任务的界面或调试台界面时，Agent 在人工清单之前按界面任务试用，见 [Stage 4](03-execute-loop.md#stage-4--自动验证与人工检查清单)。
- **调试台的观察不是验收**：用户在调试台中满意、Agent 的截图或试用通过，都不代替人工验收；技术验证的结论也不代表已有必需的回归测试覆盖。不要让没有相关不确定点的工作以调试台或技术验证为前提。
- **删除带测试的内容**：删除登记过测试的调试对象、候选或探针前，按[需求变化与过时的测试](08-test-traceability-and-evidence.md#需求变化与过时的测试)退役这些测试。
