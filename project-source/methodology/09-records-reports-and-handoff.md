# 09 · 记录、报告与交接

本文规定报告、调研、项目知识和 Progress 保存在哪里，以及任务怎样交接或在另一个对话中续接。可复用的工具和项目决定留在项目的源目录中；报告只包含实际的执行输出。

## 报告与清理

在产生一次运行或临时工作区之前，先选好输出位置。报告根目录只放固定入口；下列目录只在需要时创建：

| 产物 | 位置与职责 |
| --- | --- |
| 工具或流程规定的报告 | 保持其固定路径，包括 `reports/gdunit-wrapper/<Feature-ID>/run-<id>/`（或同一根目录下的 `focused/run-<id>/`）、`reports/manual-acceptance/` 和 `reports/initialization.md`。读取它们的工具和证据引用依赖这些约定。 |
| 自定义的 Feature 日志、结果和截图 | 使用 `reports/features/<Feature-ID>/`，工程 Feature 也一样。结果跟着各自的 Feature 存放，不散落在根目录，也不把多个 Feature 归进一个 Product 草稿目录。 |
| 不属于 Feature 的自定义报告 | 使用 `reports/maintenance/<task>/`，用能说明维护或调查内容的名称。 |
| 临时文档：草稿、当次方案、交接副本和参考来源摘录 | 使用项目根目录的 `tmp/<task>/`，需要时按主题或尝试建子目录。临时文档不混进正式的源码或文档目录。 |
| 临时项目、探查和命令辅助文件 | 使用 `reports/scratch/<task>/`，需要时按尝试分目录。每个复制的项目及其生成的缓存都留在这个工作区内；只复制检查所需的输入。 |

`tmp/` 中的临时文档只在本地，被 Git 忽略。删除草稿之前，把长期有效的决定整合进它们所属的正式文档；当前任务或交接仍需要的临时材料要保留。

### 保存结果

- 工具支持指定输出路径时，把要保留的结果存进任务报告目录，与临时输入分开。
- 文件名要能说明内容。需要保留多次尝试时加运行子目录，绝不覆盖被引用的原件。
- `final`、`verified`、`delivery` 这类后缀不能说明哪份结果有效；能说明的是 Feature 或 Progress 中的证据链接。
- 证据留在临时项目里时，保留所需的工作区，并链接证据的实际位置。路径在 scratch 下，不代表其中的内容可以丢弃。
- 优先使用工具的原始输出：gdUnit 已经把 `result.json`、`engine.log` 和原始报告放在一起。只有控制台记录包含原件没有的有用信息时，才另存它。
- 自定义报告或截图属于证据。探查和候选输入放在 scratch；提交说明这类临时文档放在 `tmp/<task>/`。可复用的生成器按[保存常用脚本](#保存常用脚本)放在 `dev/tools/`，夹具放在 `tests/`，即使它们的输出只是临时占位。

### 保留临时材料

创建临时材料时，按[临时、备份与草稿文件](../agent-rules/00-core/third-party-generated-and-temporary-files.md#临时备份与草稿文件)处理。临时材料必须在任务结束或交接后继续保留时，在 Feature notes 或 Progress 中记录它的用途和释放条件，例如某项待完成的验收或调查结束时。释放条件写成能判定的事件；完成归档仍引用其中的原件时，写“归档引用，长期保留”。任务正常收尾时，检查任务实际的输出位置和证据链接，指出仍需要的临时材料。Progress 和 Feature 记录是阅读入口；不另建报告索引或保留记录文件。

### 保存常用脚本

命令辅助脚本先按上表放在 `reports/scratch/<task>/`。写这类脚本时，判断这类操作以后是否还会用到，例如导出打包、批量重新生成内容表。以后还会用到、并同时满足下面三条时，提出把它保存为项目脚本：

- 检查有明确的对错，操作有明确的成功条件；
- 输入格式稳定，步骤固定；
- 做错的代价高，或手动执行容易漏步。

保存超出当前任务的范围，先征求用户同意。不在任务中途停下：在完成汇报的待确认中写明脚本做什么、计划放置的路径，以及会同时修改 `dev/tools/README.md`，用户同意后再保存。用户不同意时，脚本留在 scratch；以后同类脚本出现时仍可再提。用户说某类脚本不要再提时，按[规则的增量维护](04-project-rules.md#规则的增量维护)把这个决定写进项目规则。

两种情况不按本节征求同意：

- Feature 本身要交付的生成器或工具，例如内容表生成器，已在任务范围内，直接按下面的要求保存。
- 检查类脚本随规则修改一起提出，按[自检报告](04-project-rules.md#自检报告)中“检查方式”写明的流程授权，不再按本节另问一次。

保存时，无论来自用户同意还是上面两种情况，都做下面几件事；用户同意保存的脚本直接保存，不另建 Feature：

- 脚本放在 [`dev/tools/`](../../dev/tools/README.md)。`dev/` 在正式导出时整体排除，脚本不会进入游戏包。检查优先写成 `tests/invariants/` 下的 gdUnit 不变量测试；测试超时内跑不完的检查才放进 `dev/tools/`。
- 脚本失败时返回非零退出码。
- 在 `dev/tools/README.md` 的脚本列表中加一行，写明用途、示例命令和预期结果。
- 按示例命令实际运行一次，结果与预期一致才算保存完成；不另建回归测试。

### 整理和清理报告

- 保留当前验证、验收、未解决的失败或后续工作需要的报告，包括保留下来的历史和知识条目所链接的证据。从 Feature 或 Progress 记录链接它们的路径。不另设归属记录文件、保留文件或保留状态。
- 整理报告之前，一并核对它们的生成方、读取方和证据链接，包括之前的 Progress 和知识引用。工具管理的运行目录和验收原件保持在固定路径。归类文件和修复引用，不授权删除它们或改写之前的证据。
- 清理是一项明确的维护操作。先检查拟清理的路径、当前引用和内容。只删除理解清楚且获得授权的输出；未知文件和尚未解决的证据留待之后决定。
- 文件的存在时间、目录名或之后的一次成功运行，单独都不能授权删除失败记录。没有任何测试运行器会自动清理旧报告。

## 外部调研

### 决定与委派调研

主 Agent 决定：现有证据是否已经足够，直接查找是否有帮助，或者是否把一项有边界的调查交给 `researcher` 角色。没有任何 Stage、主题或 Feature 强制要求调研。

- **委派时**：传递问题、具体的目标版本、项目约束、已找到的有用证据，以及是否保存报告；保存位置按下文「保存调研」固定。独立的工作照常推进；只有依赖调研结果的决定才等待。
- **直接查找时**：遵循该角色关于来源和版本的指导，不启动子 Agent，也不写完整报告。
- **角色不可用时**：客户端无法选择该角色时，把角色的说明交给一个可用的 Agent，或者直接调研，并说明用了哪种方式。
- **优先使用 `anysearch`**：可用时使用用户安装的 `anysearch` Skill。它是外部工具，不复制进项目；该角色可以自行退回到其他搜索方式。
- **拿到结果后**：主 Agent 判断调研结论是否适用，在当前授权内采纳决定，完成任务的文档和提交，并继续任务。调研结果或搜索失败都不改变这项权限。

### 保存调研

保存下来的外部调研结论放在 `docs/research/<descriptive-topic>.md`，只在保存有用的调研时创建。初始的目录 README 只做导航。

- `researcher` 角色（Codex 为 `.codex/agents/researcher.toml`，Claude Code 为 `.claude/agents/researcher.md`，说明正文相同）规定报告的最低内容和搜索指导。主 Agent 分派报告，并决定采纳什么。
- 通过 Feature 设计、notes 或 Progress 的链接导航。只在报告数量多到需要时，才在目录 README 中添加报告链接。
- 报告是普通的、纳入版本控制的 Markdown。`reports/` 仍是本地执行证据和临时材料的位置。

调研是被引用的参考材料，不是已批准的意图，也不能证明本地的运行时行为。

- 被接受的游戏设计决定更新 GDD。交付边界、专业规范和技术决定更新 Product、专业文档、Feature 设计或 ADR，并引用这份调研。
- 经过项目工作确认的经验可以进入 `docs/knowledge/`，链接调研和实际证据，不复制报告。
- 修订调研时，保留其他文档引用的结论。不另建第二份任务记录文件。

调研 Markdown 不影响测试证据（见[内容指纹](08-test-traceability-and-evidence.md#内容指纹)），所以需求不能只写在那里。脚本、夹具和其他非 Markdown 文件放在正式的源码或报告位置。只要求调研的任务，不授权做实验、实现、修改需求或把 Feature 标为完成。

## 项目知识

`docs/knowledge/` 保存来自项目工作的可复用解释。Feature notes 保存简短的事件经验，并链接到 Feature 设计中的局部决定。事件记录是情境性证据，不是 Product 需求、工程规则或可执行的输入。按知识库 README 中的 [组织条目](../../docs/knowledge/README.md#组织条目) 和 [在已获授权的工作中维护](../../docs/knowledge/README.md#在已获授权的工作中维护) 处理。

知识 Markdown 及其索引不影响测试证据，见[内容指纹](08-test-traceability-and-evidence.md#内容指纹)。可运行的脚本、夹具和数据放在项目的正式目录中。

在任务的正常提交之前，定稿本任务负责的条目和索引修改；交接时报告链接。更新项目知识不授权提升规则，也不授权修改其他项目或框架。

## 教训台账

`docs/lessons.md` 统计 Agent 自己的流程失误出现了几次，次数够了就提出升级。本节是台账的唯一正文。

### 记什么

- **只记行为类失误**：知道规则或事实却没做到，例如漏步骤、没验证、没问用户、用错入口。不限于当前 Feature 才记；只属于本 Feature 的留在 Feature notes。
- **事实类陷阱不进台账**：引擎、语言、工具或环境怎样运作，第一次出现就写知识条目，见知识库的[在已获授权的工作中维护](../../docs/knowledge/README.md#在已获授权的工作中维护)。
- **不为交差而写**：没有新的失误时不写。台账记出了后果的失误，不记 Agent 的动作。

### 条目格式

```text
## <一句话规则：以后该怎么做>
- 触发：<做什么动作时会犯>
- 症状：<看到什么现象>
- 出事：<Feature ID 或提交号>，后果：<…>
- 修复：<提交号>
- 做对的例子：<…>（还没有就省略）
- 出现 N 次（YYYY-MM-DD, YYYY-MM-DD）；严重：是 / 否
```

### 写入与计数

- **何时写**：Stage 7 提交前，和 Feature notes、知识条目一起定稿；用户纠正 Agent 后，在下一次回复前写。
- **先搜再写**：追加前按“触发”和“症状”各搜一次台账，命中就在原条目加一次，不新开条目。
- **怎样算一次**：不同任务或不同日期里再犯算一次；同一任务内的重试不算。“出事”没有 Feature ID 或提交号的不计数。
- **严重**：只算无法恢复的后果，即用户文件或存档丢失、未提交的内容被覆盖、用户必须手动介入才能继续，例如杀进程或恢复文件。

### 升级

- **何时提出**：出现 3 次，或严重的第 1 次。Bug 的 Guardrail 另按 07 号的[Bug 经验的提升](07-engineering-change.md#bug-经验的提升)判断，台账次数只是其中一条。
- **去向**：按 04 号的[经验的归宿与规则提升](04-project-rules.md#经验的归宿与规则提升)选择。
- **只提方案**：Agent 提出改什么、改在哪里，用户批准后由对应负责方执行，规则修改仍按[规则的增量维护](04-project-rules.md#规则的增量维护)。
- **执行后删除条目**：新位置不写经过，历史由 Git 保存。

不设到期删除，因为删掉后计数会从头开始。条目多到影响阅读时，由用户决定删哪些。

## Progress

`docs/progress.md` 包含当前状态、阻塞、待决定事项、下一个允许的动作和历史索引。它链接已批准的计划和证据，不复制其正文。普通的 Markdown 标题就够了；不需要机器标记或规定的解析格式。

当前状态只写仍在进行、正在等待或接下来要做的事，包括当前在交付哪个 Product。Feature 完成并归档后，从当前状态删掉它的条目，只在历史索引保留归档链接；测试数、证据这类完成细节留在归档里。每次更新时，顺带删掉已经不成立的说法，例如已处理掉的文件、已解决的阻塞。

按 [Stage 0 · 选择 Feature 并加载上下文](03-execute-loop.md#stage-0--选择-feature-并加载上下文)中的等待例外同时有多个进行中的 Feature 时，当前状态为每个 Feature 各写一条：所处 Stage、停点、正在等待的对象（例如“等人工验收结果”），以及输入到达后的第一个动作。

初始的 `docs/progress/README.md` 说明这个目录，并链接回当前 Progress；它不是归档，也不是另一份历史索引。

已完成的 Feature、已批准批次或已完成的独立实验，历史由 Agent 一次性归档到 `docs/progress/<key>.md`，并在当前 Progress 文档中保留链接。独立实验没有 Feature 编号，`<key>` 用实验的简称，例如 `mushroom-shed-art`；实验的完成确认和用户的确认结论也记在归档里。保留剩余的阻塞、待决定事项、原始历史和证据链接。不要推断批准，不要覆盖归档，也不要重复之前的历史。新正文用 `document_language` 写；移动历史不需要翻译它。

归档保存执行历史，Progress 保存当前状态。Feature notes 保存任务提醒、回归链接、TODO 和导航。实现设计和局部决定按 [Feature 设计与实现说明](02-feature-list-schema.md#feature-设计与实现说明) 写在 `docs/features/F0XX-design.md`；ADR 和独立技术决定按 10 号规范的[架构决策记录](10-architecture-overview.md#架构决策记录)处理。链接这些记录，不要把同一段叙述贴进 Progress 或 notes。

## 任务交接

根据当前请求、相关文件、实际的 Git 状态和任务记录准备交接。保留原始目标、已确认的决定、仍然有效的授权、实际停下的位置、未完成的义务和下一个允许的动作。如果计划开启下一个对话，写明它的具体目的，而不只是“继续这个项目”。把已完成的工作、针对已观察版本的证据、未经验证的说法、阻塞和待进行的人工验收分开写。

需要在对话结束后保留的信息写进 Progress 和 Feature notes；不属于 Feature 的工作使用 Progress 及其任务文件。链接设计和原始证据，不复制它们。只在授权范围内更新本任务需要的记录。

- 只要求摘要的请求不需要写文件。
- 暂停记录不需要续接提示词。
- 准备交接不要求重跑已完成的检查，也不要求完成被暂停的实现。

按 `AGENTS.md` 的 **Git 与提交** 在任务的工作目录中保留状态，并处理任何获得授权的记录提交。交接不会：

- 确立人工验收或完成；
- 重置 Feature 状态或丢弃进行中的工作；
- 建立第二份交接记录文件，或要求操作系统的临时文件；
- 开启新对话、发送消息或启动建议的动作。

尊重用户明确的暂停或缩小后的当前范围；之前的实现授权不能覆盖它。

`task-handoff-godot` 是这项工作的直接入口。只想了解状态或选择流程的请求，可以改用 `project-next-step-advisor`；它只读，不更新记录。要求提供提示词时，按下面的格式并结合当前的项目事实来写。`project-next-step-advisor` 从它声明的共享 Godot 提示词库中取场景材料；任务交接使用所属任务的来源。

## 续接提示词

每份起草的任务提示词或续接提示词，都按下列顺序用二级标题写出这些字段：

1. 目标
2. 范围
3. 输入与事实来源
4. 决策边界与授权
5. 约束
6. 输出与交付
7. 验证要求
8. 完成条件

标题和提示词的其余部分一样，使用当前对话语言；例如英文对话使用 `Goal`、`Scope`、`Inputs and sources of truth`、`Decision boundaries and authorization`、`Constraints`、`Output and delivery`、`Verification requirements`、`Completion conditions`。无论提示词多短，每个字段都要填写针对该任务的内容。

- 共同要求引用目标任务实际的规则，不复制它们。
- 只在确有需要时，在相关字段旁加上标注清楚的字段，用于背景或入口、冲突处理、环境，或风险与恢复。
- 这个格式只管呈现，不增加流程步骤或审批关卡。

写明目标任务的目的和第一个有用的动作、它真实的当前来源和剩余义务。

- 保留有效的授权和明确的限制。不要虚构 ID、路径、命令可用性、已完成的检查、决定或验收；缺少的事实写明是缺口。
- 把受阻或等待人工的状态与成功完成分开。
- 字段或 Skill 的边界都不会终止更大范围的有效授权，“继续”一词也补不上缺少的授权。

被要求时，产出针对该任务、可直接复制的文字，而不是维护一个模板文件或一套并行的提示词集合。交接和 `project-next-step-advisor` 共用这个格式；它们各自不同的读写职责仍然适用。
