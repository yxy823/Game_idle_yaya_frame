# 游戏职责与项目组织指南

理解游戏功能、判断逻辑与表现的分工、查找设计资料或安排模块位置时，按需要查阅本指南。先明确职责和文档关系，再决定代码、场景与资源如何组织。游戏设计约束沿 GDD 的[设计范围与边界](../yaya/methodology/01-product-doc-structure.md#设计范围与边界)及所属主题读取；开发约束以[项目规则](project-rules.md)及下文链接的工程规则为准。本页提供共同概念、判断方法与示例。

## 游戏逻辑与表现

游戏逻辑负责规则、业务状态和有效结果，游戏表现负责这些内容如何被玩家感知。两者共同构成一次游戏体验，可以在同一个业务模块内协作。

| 职责 | 决定什么 | 例子 |
| --- | --- | --- |
| 游戏逻辑 | 行为是否有效、何时改变哪些游戏状态、产生什么结果 | 是否可以买商品、实际扣费、库存与物品变化；攻击是否命中和实际伤害 |
| 游戏表现 | 怎样向玩家传达状态、结果和可操作信息 | 商品界面、价格显示、图标飞行、血条过渡、声音与镜头反馈 |

影响游戏规则的状态由明确的权威所有者维护，调用者通过其有效 API 请求改变。表现也有自身状态：按钮悬停、提示框展开、正在显示的插值数值和播放进度，不必移交游戏逻辑。例如真实生命值已经是 80，血条可以仍在从 100 过渡到 80；伤害计算读取真实生命值。

### 请求、状态与事件怎样协作

以商店购买为例，点击按钮提出购买请求；逻辑检查金币、库存等条件，给出失败原因或执行购买并返回有效结果；表现再更新价格、余额、物品和反馈。按压反馈可以在请求时立即出现，获得商品的反馈则依据购买成功结果。

- **请求**表达想做什么，可能被拒绝；输入设备采集到的操作不等于规则已经生效。
- **当前状态**说明现在是什么，可用于界面打开、重新连接或载入后的显示恢复。
- **一次性事件或结果**说明刚发生什么，用于本次飘字、音效、闪烁等反馈。读取当前生命值不等于又受了一次伤；需要补播时由具体需求明确约定。

玩家输入只是触发来源之一，AI、计时器和游戏流程也会调用逻辑。选择普通方法、已有 API、Signal 或必要的协调者，取决于实际依赖、结果传递和生命周期；职责模型不要求新增通信机制。双方的创建、连接与退出清理由实际组装所有者负责，具体规则见[依赖与协作](../yaya/agent-rules/10-gdscript/structure-and-dependencies.md)。

### 编排和 Godot 对象按实际职责判断

回合推进、购买事务和攻击有效窗口属于逻辑编排；安排图标、闪光和声音的先后属于表现编排。连接这些对象的场景或协调者说明真实关系，不要求另设一个固定的控制层。

场景可以同时包含碰撞、规则、绘制和输入对象。Node、Resource、AnimationPlayer 或文件后缀本身不决定所属职责，也不要求所有逻辑脱离 Godot。值得独立的公式和条件判断可以单独测试；物理、场景生命周期等仍遵守其真实引擎边界。

动画可提供攻击命中帧等时序输入，但逻辑仍判断当前攻击是否有效、是否已取消和能否结算伤害。若动画结束或图标抵达影响游戏流程，应在对应规则和接入约定中说清条件与中断结果；不能由替换动画意外改变已确认规则。

环境配置、测试、构建、创建器和开发记录是支撑两层的共同工程能力。游戏内的存档行为和应保存哪些业务状态由相应游戏规则负责，具体存取技术按实际工程职责组织。

## 从游戏功能找到文档

先确定游戏目标，再沿规则与表现要求找到负责的正文、实现和验收。总体设计可以同时涉及两层；“表现层”也不等同于一次具体游戏表现的文档目录。

| 要了解什么 | 查阅位置 | 商店购买示例 |
| --- | --- | --- |
| 游戏目标、规则、状态和体验要求 | [GDD](gdd/README.md) | 商品可购买条件、扣费与入包规则、成功和失败要传达的信息 |
| 界面布局、状态与操作方式 | [UI 设计](ui/README.md) | 商品如何排列、价格与按钮状态、购买结果如何呈现在界面 |
| 一次具体表现的过程、备选方案与采用组合 | [游戏表现](presentation/README.md) | 购买成功后的图标飞行、背包入口的到达反馈及采用的组件方案 |
| 共享视觉、声音和语言要求 | [美术](art/art-bible.md)、[声音](audio/sound-bible.md)、[本地化](localization/localization-spec.md) | 共用的图标风格、反馈声音与价格在各语言中的分隔符写法 |
| 实际模块、状态所有者、调用与连接 | [项目架构](architecture.md)及必要的子系统说明 | 谁校验并执行购买、谁管理余额与物品、界面怎样获得结果 |
| 本次交付、局部设计与验证 | [Product](product.md)、[Feature](features/README.md)及其关联记录 | 本次完成哪些购买行为、反馈与检查，实际验收覆盖什么 |

这些例子不代表项目已有商店或已确定设计。记录随实际工作产生，具体来源归属见[专业工作与来源](../yaya/methodology/11-specialist-workflows.md)。一项要求保留一个正文，其他文档引用它；当前实现关系由实施任务同步，验收结果归既有记录。

UI 文档从实际交互位置引用相关表现；角色死亡等非 UI 表现可直接从 GDD 引用。架构或任务设计链接实际接入关系，不把规则、表现规格和实现说明混成同一份清单。

## 用职责选择实现

表现类、逻辑类和跨层类用于解释一个功能涉及的范围。例如修改受击闪烁、修改伤害计算、新增完整护盾功能，分别可能侧重表现、逻辑或两者。它们不新增任务字段、Skill 或执行阶段；一个 Feature 可以交付完整的跨层功能，或继续完善已有表现的一部分。

本模型帮助理解职责、定位资料和作出设计判断。普通实现方式由 Agent 根据已确认需求、现有结构和验证结果选择；默认建议按适用条件使用，不把例子变成每个任务都必须采用的结构。职责清楚不意味着必须拆成特定数量的类、节点或文件。

开发顺序按实际依赖安排，逻辑与表现分工不要求逻辑先行。新界面先做最小的真实骨架，例如商店能发出购买请求、余额会变化、外观用占位；再在调试台中比较和采纳界面的外观与反馈；最后补完其余购买逻辑。调试台修改的是游戏真实使用的调参资源，不另写示例状态。顺序见[界面的开发顺序](../yaya/methodology/13-debug-console-and-validation.md#界面的开发顺序)，三段分别核对规则结果、表现要求和接入行为。

## 先确定内容属于谁

项目使用以下共同骨架：

```text
res://
├── main/                  应用入口与顶层组装
│   └── main.tscn          最小启动场景
├── game/                  当前游戏的功能模块
│   └── <模块>/tuning/     调参资源，调试台中的插槽
├── components/            输入与职责明确的可复用能力
├── assets/                跨模块共享的素材
├── addons/                插件及其所属文件
├── dev/                   只用于开发的场景和脚本
│   └── debug/             调试台：调试入口、共享代码与各调试对象的候选
└── tests/                 按实际需要添加的项目测试
```

文档、工具和明确标记的示例保留各自位置。`dev/` 存放只在开发时使用的场景和脚本，例如 `dev/debug/` 下的调试台；导出时整体排除，`main/`、`game/`、`components/` 和 `project.godot` 不能引用其中的文件，依赖方向见[调试台](../yaya/methodology/13-debug-console-and-validation.md#入口与依赖方向)。`main/main.tscn` 是配置好的启动场景；入口存在不代表环境就绪、已有玩法或已经运行成功。

| 判断问题 | 建议归属 |
| --- | --- |
| 负责启动应用或连接顶层模块吗？ | 放在 `main/`，具体行为仍由所属模块实现。 |
| 实现当前游戏特有的概念或策略吗？ | 放在 `game/` 中有明确名称的模块；设置、存档、全局 UI 也属于当前游戏的功能。 |
| 消费者能否在不引入当前游戏规则、不查找其全局对象的情况下使用它？ | 确实需要独立复用时放在 `components/`，否则先留在当前模块。 |
| 只供一个模块或场景使用吗？ | 场景、专属脚本、美术、声音与配置默认放在所属模块的目录内。 |
| 素材确实跨模块共享吗？ | 放在 `assets/`，或选择更明确的共同归属，例如仅用于 UI 的字体和主题可放在 `game/ui/`。 |
| 来自插件或外部包吗？ | 保留包的边界和命名契约。 |

可复用组件也可以拥有自己的专属素材。只在同一个模块内部共享的 Resource 可以留在该模块；“有多个使用者”不等于必须移入根 `assets/`。

## 有实际内容再展开模块

从当前需要的场景、专属脚本和资源开始。例如，拥有采矿功能的项目可能逐渐形成：

```text
game/mining/
├── mining_panel.tscn
├── mining_panel.gd
├── mining_rules.gd
├── ore_definition.gd
├── ores/
│   ├── copper_ore.tres
│   └── copper_ore.png
└── tuning/
    └── feedback/mine_hit.tres
```

这些文件只用于说明，不是初始项目内容。示例假定矿石只属于采矿；若同一物品定义同时服务背包、商店等功能，可由 `game/items/` 统一拥有并供各模块引用。只有内容增长后更方便查找时，才增加 `art/`、`audio/`、`data/` 或更细的功能目录。

模块名称来自当前游戏：探索游戏可能需要 `world/` 与 `actors/`，放置游戏可能需要 `production/` 与 `upgrades/`。有需求再建立相应目录和实现。功能专属面板跟随功能，菜单等全局 UI 可归入 `game/ui/`。

逻辑分层与目录分层分别判断：优先在所属游戏模块内部明确输入、规则与表现的职责。例如，`mining_rules.gd` 与 `mining_panel.gd` 可以同属 `game/mining/`，规则代码不依赖面板实现。再按内容规模与查找、维护需要细分目录；逻辑分层本身不要求新建根级 `core/`、`presentation/` 等目录。依赖方向沿用[项目架构原则](project-rules.md#22-核心架构原则)。

## 用领域与职责命名

先表达领域概念，需要区分时再补充职责。项目自有 Godot 文件与目录使用英文 `snake_case`，类名与场景节点名使用 `PascalCase`；场景与专属脚本同名，例如 `mining_panel.tscn` 与 `mining_panel.gd`。第三方原名和工具要求的约定名称按其契约保留。具体要求见[资源命名](../yaya/agent-rules/60-assets/naming-paths-and-moves.md#命名与组织)、[GDScript 命名](../yaya/agent-rules/10-gdscript/typing-and-api.md#风格与命名)与[场景结构](../yaya/agent-rules/20-scenes/structure-and-ownership.md)。

以下是可选的职责词，按真实需要采用：

| 职责词 | 适用含义 | 示例 |
| --- | --- | --- |
| `Definition` | 在制作阶段定义的内容身份与属性 | `OreDefinition`、`ore_definition.gd` |
| `Config` | 配置特定功能或服务的参数 | `MiningConfig`、`mining_config.gd` |
| `State` | 有明确所有者与生命周期的可变状态 | `MiningState`、`mining_state.gd` |
| `Rules` | 值得与表现分开的领域判断和约束 | `MiningRules`、`mining_rules.gd` |
| `Panel` | 职责有边界的界面面板 | `MiningPanel`、`mining_panel.tscn` |
| `Calculator` | 输入与结果明确的特定计算 | `ProductionCalculator`、`production_calculator.gd` |
| `Store` | 明确的存储、持久化或数据访问边界 | `SaveStore`、`save_store.gd` |
| `Manager` | 对多个所属对象或共同生命周期的真实协调 | `FeedbackManager`、`feedback_manager.gd` |

小模块可能只需要一个场景和脚本。使用职责词不要求同时增加 `class_name`、继承层、Resource 类型或 Autoload；职责能说清时，用具体名称代替笼统的 `utils.gd`。Resource 的角色与可变性见[资源职责、共享与局部性](../yaya/agent-rules/21-resources/roles-sharing-and-locality.md)。

## 生命周期与文件位置分别判断

Autoload 按真实生命周期选择，文件仍按职责归属。例如，需要跨场景存续的存档服务可以留在 `game/saving/`；场景局部协调者则跟随其所属场景。`Manager` 后缀不表示全局生命周期，放进 `components/` 也不自动证明它已经独立。

需要跨模块协作时，先指出状态归谁、调用哪个 API、由谁连接双方。组装放在相关父级或协调者，不为接线方便把游戏规则引入通用组件。实现细节沿用[依赖规则](../yaya/agent-rules/10-gdscript/structure-and-dependencies.md)与[Autoload 规则](../yaya/agent-rules/40-project-config/autoloads-and-plugins.md#autoload)。

当实际边界需要说明时，按[架构概览](../yaya/methodology/10-architecture-overview.md)维护项目的可选架构文档。新增目录本身不要求创建架构地图、ADR 或额外验证阶段。
