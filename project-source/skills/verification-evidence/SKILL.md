# 维护实际的验证证据

确认请求的证据操作、实际的 Feature 或诊断范围、当前的源文件状态和被引用的原件。复用已有的记录和任务授权；维护证据不新建 Feature、新 Stage，也不另建平行的结果记录文件。

## 分清证据问题

阅读 `yaya/methodology/08-test-traceability-and-evidence.md` 的 **基于原始结果的完成判断与语义时效**，以及 `yaya/tools/README.md` 中 **调用** 或 **结果如何使用** 下匹配的操作。这些路径相对项目根目录；证据身份、覆盖范围、导入和恢复都以这些文件为准。不要照搬它们的结构，也不要手工修改判定结果。

| 实际情况 | 在已有约定内的处理 |
| --- | --- |
| 一次真实完成的运行需要导入，或它的引用路径写错了 | 读取实际原件，检查它当前是否仍适用；用已有的导入工具和有效的引用导入。只修正引用时，不需要重跑仍然有效的证据 |
| 有摘要，但原件缺失或损坏 | 先找到并检查实际原件。原件不能支持该结果时，报告缺口，只安排替换它所需的验证；不要根据文字描述重建通过的证据 |
| 源文件或验证义务发生变化 | 按权威的内容和过期规则判断哪些已失效。复用仍然有效的证据，重新完成受影响的义务；提交时间或熟悉的文件名不能证明证据没有过期 |
| 一次运行被中断、失败，或可能仍在运行 | 在新开运行或执行停止操作之前，先检查它真实的记录、日志和进程状态。保留这次尝试，尊重进程归属和停止授权；按权威的失败和恢复覆盖规则处理，不要用更早或范围更小的成功结果掩盖它 |

按 `yaya/tools/README.md`，显示已保存的记录，与检查它当前能否支持完成，是两种不同的操作。选择任务需要的操作，并报告它实际代表什么。定向结果、基线结果、静态输出和专业测量各自保留证据局限；不要把它们转成最终的 gdUnit 证据，也不要为 `not_required` 编造报告。

## 只补齐缺少的证据

已获授权的恢复需要再做静态检查、运行已有测试或检查场景时，使用 [project-verification](../project-verification/SKILL.md)。按原始失败或当前义务要求的范围选择，不默认全部重跑。诊断或实现上的修改交回已有的负责方，不变成对证据的修改。

需要准备、记录或更新实际的人工结果时，使用 [manual-acceptance](../manual-acceptance/SKILL.md)。自动重跑不能更新人工验收。失败和被引用的原件，按 `yaya/methodology/09-records-reports-and-handoff.md` 的 **报告与清理** 保留；任何清理或重建的产物，都不能掩盖必须报告的失败。

## 返回有依据的结果

报告检查或更新了哪些原件和引用，哪些仍然有效，哪些失败、已过时或仍然缺少。记录成功或证据校验通过，只在其实际覆盖范围内有效，不能证明直接的静态检查、人工验收或整个 Feature 已完成。

长期保存的文字按 `yaya/methodology/05-document-language.md` 书写；任何仓库写入按 `AGENTS.md` 的 **Git 与提交** 执行，包括当前任务的验收和提交条件。范围很窄的证据维护请求，不授权修改业务内容，也不授权转为完成状态。返回调用方；Skill 返回不会结束它所在的已授权任务（methodology 03 的 **授权与续接**）。
