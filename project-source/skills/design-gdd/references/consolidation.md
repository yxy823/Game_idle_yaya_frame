# 整合游戏设计材料

把分散的笔记、GDD 主题、外部提供的文档或已采用的讨论结果，整合成便于维护的设计时，使用本参考。整合仍属于编写工作；只要求列出问题的独立审核使用 `plan-review`。

## 确定每个来源能支持什么

阅读本次涉及的材料和开放问题，确定每个来源的主题、当前状态和实际引用。区分已采用的规则、备选方案、对实现的观察和实测证据。用户指定的权威来源和明确的决定是重要依据；文件的日期、大小或在目录中的位置，不能解决设计冲突。

实现与已采用的设计不一致时，保留这个区别，不要自动改写设计去迎合实现。遇到重要冲突时，写明双方的说法、所在位置、可用的采用证据，以及哪些工作依赖它的解决。未决的选择保持可见，不受影响的整合工作继续进行。

需要时，在对话或受影响的主题中做一个小的对比就够了。不要只为了组织任务就新建来源记录文件，或记录每个文件的元数据。

## 整合时不丢失设计

输出按[设计文档结构与规则归属](design-docs.md)组织；文件命名、导入的 GDD 和迁移按 `yaya/methodology/01-product-doc-structure.md` 的 **GDD 文件名** 处理。移动内容时，更新受影响的文件和标题引用。未解决的设计冲突连同来源和影响整合到开放问题文档中，重复的问题正文改为链接。获准整合的内容涉及整体范围时，迁移这部分内容并更新引用；保留无关的结构。只做局部整合时，单文件的 GDD 不需要另存一份，也不需要整体转换。

每条保留下来的规则都有一个所属位置。即使周围的措辞被压缩，也要保留它的例外、假设、数值含义、决定状态和有用的证据。系统规则和数值模型放在 methodology 01 规定的固定路径；已确认的专业规格放在 methodology 11 规定的所属位置；复杂度和原来的位置都不改变这种分配。通过 `terminology-register`（`yaya/methodology/14-project-terminology.md`），把外部提供的材料中已确认的术语定义、别名和不用的说法收集到 `docs/terminology.md`。已迁移的正文改为引用，同时把任务中受保护的原始输入保留为来源材料。含义尚未确定的内容，先解决再记录为已确认的定义。

材料里的工程约束（例如“平衡参数不与战斗逻辑耦合”）属于项目规则，不写成 GDD 正文。整合授权包括项目规则，或者材料明确要求把它移到 `docs/project-rules.md` 时，按[规则的增量维护](../../../../yaya/methodology/04-project-rules.md#规则的增量维护)写入。授权不覆盖时，在回复的「未做」里列出约束原文和来源位置。不要用项目规则里现有的、条件更宽的条款代替它，例如把“不得耦合”换成“需要不改代码就能修改时，放进配置”，因为这样约束就被悄悄放宽了。

保留足够的“来源到结果”信息，用来核实实质内容是被保留了，还是被有意修改了。来源在项目仓库之外时（例如另一个项目的文档），用文字写明来源路径和版本（如提交号），不写成 Markdown 链接：项目独立于其他目录，外部路径移动后链接会失效，链接检查也查不到。小规模整合有一段简短说明就够了；较大的迁移可能需要在回复或已有的任务记录中给出对照表。这不要求另建产物。

资料里集中写成一份的验收清单，整合时按主题拆到对应规则旁，不另保留一份集中清单。

写完后按原文逐条找去向：每条规则、限制、许可、例外和工程约束，在结果中找到它所在的位置，或者在回复中说明它被有意修改、没有纳入的原因。“逐主题核对原意”不能代替这一步，因为压缩措辞时最容易出下面三类改动，而它们读起来仍然像原意：

- **加了原文没有的限制**：例如原文写“规则可以先实现，参数用可调的占位值”，结果写成“没有选定占位值前不能开始制作”。
- **删了原文的许可，或降低了它的采用状态**：例如把正文里已采用的规则移成未采纳想法，或者删掉原文明确允许的做法。
- **改了整合范围外的已有正文**：例如顺手删掉或改写项目原有专业文档里与本次材料无关的句子。

发现这三类改动时改回原文的意思；确实需要改变时，作为待用户决定的问题列出，不直接写成结果。

保留下来的建议保存在 methodology 01 的 **备选方案与未采纳想法** 选定的位置，不放进推测性的系统主题。检查新建或更新的入口、受影响的链接和锚点（用 `python -B yaya/tools/checks/check-markdown-links.py`，不另写检查脚本），以及各主题之间规则、术语和数字是否一致。只在实际任务的授权范围内替换、归档或删除旧材料。用户明确要求另存一份时，保留输入原样；普通的局部编辑没有另存一份的要求。

## 交付整合后的设计

提供整合后的入口或编辑过的主题，说明重要的结构变化和采用理由，指出仍未解决的冲突及其后果。整合中提出的建议，在被采用之前仍然是建议。如实说明实际覆盖的范围和证据局限，不要声称整理好的文档证明了玩法或实现。
