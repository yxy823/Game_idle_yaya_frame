# 游戏数值设计

为期望的玩家体验建立可解释、可复算的数值方案。

## 输入与权限

明确的体验目标，加上足以写出有用模型的规则草稿，就是有效的输入。早期数值设计不要求 GDD、Product 或 Feature 已经完整，见 `yaya/methodology/01-product-doc-structure.md` 的 **GDD 前提与职责**。GDD 已经存在时，从它的入口找到本次涉及的规则、数值来源和依赖，不要只凭总览建模。

提取实际的目标、约束、变量和可用证据。分清哪些来源描述已采用的规则、候选规则、已观察到的实现或实测结果，并保留它们的范围和假设。只有缺少的决定会实质改变目标或模型时才提问；否则写明有边界的假设并继续。需要澄清时，在本 Skill 的范围内使用[共享提问方法](../project-grill-me/SKILL.md#共享提问方法)。依赖规则草稿的模型仍然是有条件的。

在用户的具体授权范围内，把模型维护在该系统范围和键名对应的固定数值文件中，文件名见 `yaya/methodology/01-product-doc-structure.md` 的 **GDD 文件名**。模型的长短或复杂度不决定存放位置。该章节也说明了组织方式不同的 GDD 怎样处理。获准整合时，把嵌在其他位置的模型迁到对应的数值文件，原处留下引用。需要迁移但超出本次写入范围的，在报告中说明。标题和正文使用 `document_language` 编写（`yaya/methodology/05-document-language.md`）。只要求讨论时，在对话中交付模型。

新推导的结果和调优数值一开始都是候选值。只有用户决定采用，才标为已采用。验证证据分开记录：计算、模拟和实际观察的结果证明的是不同的事。备选数值和暂缓的想法放在 methodology 01 的 **备选方案与未采纳想法** 中；暂缓的未来机制交回 `design-gdd`，不写成推测性的数值文件。不要悄悄替换已采用的数值。保存候选模型不等于采用它；已采用的数值也可能还没有体验证据。

## 推导与检查模型

本次需要的数值关系、时间与资源核算、情景和常见错误，见[数值建模与计算检查](references/numeric-modeling.md)。只处理已采用的机制，或用户要求探索的备选方案。不要凭游戏类型推断出离线奖励、转生、指数增长或无尽成长。

把体验目标转换成要建模的量；仍需人工观察的主观问题保留下来。定义变量、单位、公式、边界、取整方式和更新条件。用能回答问题的最简单模型；如果用恒定速率近似会掩盖重要变化，就分阶段计算。

列出有意义的输入和中间关系，让主要结果可以复算。检查典型情景，以及与本次改动有关的边界，包括玩家可能做出的选择和敏感的假设。需要时使用可用的计算工具，并准确说明实际运行了什么。计划中的模拟不是模拟结果。

诊断时，分清观察到的症状、有依据的结论和原因假设。调优时，对比原值和候选替代值，以及预期效果、取舍和剩余的不确定性。能达成目标时，优先只改少数几个关键数值；不要为了让目标可达而悄悄重新设计游戏。

## 写回并协调后续影响

公式、决定状态和计算假设保存在所属的 GDD 位置。参数取值按[数值放在哪里](../../../yaya/methodology/01-product-doc-structure.md#数值放在哪里)保存，GDD 链接实际来源。阅读并维护 `yaya/methodology/01-product-doc-structure.md` 的 **开放问题** 中受影响的数值问题，保留仍需采用决定或试玩证据的不确定项。直接更新已授权的数值段落和相关链接；不会只因为所属文档是 GDD，就另外需要整体设计的批准。

- 新机制或体验目标的变化属于 [design-gdd](../design-gdd/SKILL.md)。说明冲突或建议的取舍，并把当前授权带到那项工作中；不要把调优请求当成采用另一种游戏设计的许可。
- 数值来源的变化影响已规划或已完成的工作时，按 `yaya/methodology/11-specialist-workflows.md` 的 **编写与采纳** 和 **源同步前先提交来源修改** 处理。在任务授权范围内，受影响的 Product 范围与 `product-author` 协调，已规划的使用方与 `feature-sync` 协调。不要只为了完成一个独立模型就创建 Product 或 Feature 文档。
- 值得长期保存的领域定义，使用 `project-terminology`；文档措辞使用 `technical-documentation-writing-godot`。真实的暂停或阻塞，按 `yaya/methodology/09-records-reports-and-handoff.md` 写入 Progress 或任务记录。这些是按需使用的支持，不是必须依次调用的 Skill 链。
- 公式或目标区间变化影响已有内容数据时，由已授权 Feature 中的 [content-data-authoring](../content-data-authoring/SKILL.md) 重新生成并检查；`balance/` 不复制每行数值。
- 独立的数值审核使用 [review-balance](../review-balance/SKILL.md)。作者自己的计算检查不是正式的独立审核；用户要求正式审核时，按 `yaya/methodology/12-independent-review.md` 使用另一个非作者实例。

数值设计的授权不会自动授权修改运行时代码、数据或资源。已经获准的实现，按所属流程使用规则、状态、反馈和可观察结果都已写明的已采用设计继续进行，并照常承担验证和人工验收义务。设计验证情景不会自动在调试台建逻辑候选。

## 交付结果

提供目标和来源依据、模型和候选值、可复算的计算情景、重要的敏感性或局限，以及评估预期效果需要的证据。说明哪些内容已被采用、实际检查了什么，不要暗示游戏现在已经平衡或好玩。

获准写入时，链接更新后的数值来源，并说明对下游的影响、已完成的源同步和剩余缺口。只提出方案时，指出受影响的来源位置，不要声称已经更新。遵守任务的 Git 规则和完成规则。

返回调用方；Skill 返回不会结束它所在的已授权任务（methodology 03 的 **授权与续接**）。
