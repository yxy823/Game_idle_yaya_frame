# 用 TLA+ 行为模型检查设计

行为模型检查属于代码架构设计：它在写代码之前检查设计本身有没有漏洞。TLC 通过只说明“在模型范围内，设计满足列出的性质”，不说明代码正确；代码由 Stage 3 改写出的 GdUnit4 测试证明。模型检查的结果不进入完成证据。

## 何时使用

`feature-execute` 在 [1C. 设计决定与实现指导](../../../yaya/methodology/03-execute-loop.md#1c-设计决定与实现指导)按其中的适用条件调用本 Skill。用户在 Feature 之外要求检查某个子系统的设计时也可以使用；这时模型放在 `reports/scratch/<task>/models/`，只交付模型和结论，不修改 `docs/architecture/models/` 和 Feature 记录。

模型由主 Agent 建立和运行。委派 `implementation-advisor` 准备实现指导时，顾问只读取模型检查的结果，不写模型、不运行工具。

开始前必须有：

- 当前 Feature 的 AC 和它链接的 GDD 章节；
- 已完成的依赖 Feature 的实际代码接口，例如结算顺序、暂停判断；
- 子系统已有的模型（如果有），位置见下一节。

缺 GDD 章节或 AC 时停下，按 1C 的规定报告，不自己补规则。

## 模型放在哪里

模型描述子系统的当前行为，和 [架构与决定记录在哪里](../../../yaya/methodology/10-architecture-overview.md#架构与决定记录在哪里)中的子系统文档一样随行为变化更新：

- 一个子系统一个模型，正式位置和检查配置以那张表为准。之后改这个子系统的 Feature 更新同一个模型，不另建副本。
- 1C 时设计还没批准，模型草稿写在 `reports/scratch/<Feature ID>/models/`（更新已有模型时先复制过去再改），在那里运行工具。批准后由 Stage 2 保存到正式位置；内容和最后一次运行不一致时才重跑。
- 清单字段和工具的退出码见 [check-behavior-model.py](../../../yaya/tools/README.md#check-behavior-modelpy)。
- Feature 设计稿写明用了哪个模型、哪些性质对应哪条 AC，以及 Stage 2 记录的 `summary.json` 路径；不复制模型正文。

## 步骤

建模方法、写法模式和参数规则见 [references/modeling-guide.md](references/modeling-guide.md)，第一次建模时先读它；[references/SessionPause.tla](references/SessionPause.tla) 和同名的 `.checks.json` 是一个完整的小例子。

1. **定范围和抽象。** 只建模本 Feature 涉及的状态和与它交错的参与者。其他系统抽象成“任意时刻可能发生”的动作，在模型开头写明抽象了什么。
2. **列状态 × 事件对照表。** 写模型之前，把每个状态遇到每个事件的处理逐个列出，写法见指南的[状态 × 事件对照表](references/modeling-guide.md#状态--事件对照表)。表中一个状态和一个事件的组合简称“组合”，每个组合写明来源。写不出来源的组合就是“未确定”，先和用户讨论，定下后再把它写进模型。
   - 每个“未确定”的组合单独成一题；几个组合只能一起定时，在题里写明理由。
   - 有来源的组合不等回答，全部建进模型，照常走完第 3–9 步并跑工具。同一个动作或状态里有“未确定”的组合时，只留出这些组合，不把整个动作或状态留空。
   - 提问的回复里同时给出对照表和已建部分的检查结果，让用户看到每道题对应哪个组合。
3. **写动作。** 依赖 Feature 已有的行为按实际代码语义写；本 Feature 新增的行为按设计稿写。模型开头的注释写明模型和代码的对应。对应包括：每个变量对应的代码字段，每个动作对应的函数或信号，代码里跨了 `await` 的动作。新增行为先写设计稿里的名称，Stage 3 实现后改成实际名称。
4. **写性质。** 每条性质来自一条 AC 或 GDD 规则，在注释里写明来源。性质只写需求，不照抄实现。
5. **配错误版本。** 用常量 `Mutation` 切换，每个错误版本模拟一种合理的实现错误，并在检查配置里写明由哪条性质抓到。关键性质都要有错误版本；工具会列出没有配的性质，逐条判断是否需要。
6. **写可达性检查。** 每条重要的合法路径写一个期望被违反的不变量，证明模型没有把它限制掉，例如“片段能够失败”“宽限期内补入物品后物品挨打”。
7. **选参数。** 参数要让参与者能够错开，见指南的[参数选择](references/modeling-guide.md#参数选择)。
8. **运行工具。** 用 `check-behavior-model.py` 跑完全部检查，退出码的含义见上面链接的工具说明。
9. **分类每个失败。** 按指南的[失败的分类](references/modeling-guide.md#失败的分类)判断是性质写错、模型写错、参数挡住了路径，还是设计漏洞；修正后重跑，直到退出码为 `0`。

## 失败时不能做的事

- 不删除或放宽性质，不删掉没被抓到的错误版本，不缩小参数来求通过。错误版本没被抓到时，先查参数和模型。
- GDD 没写清、但模型必须取一个值的规则，不由 Agent 自定，也不先把各选项建进模型再问：发现时就在回复里列成题和用户讨论，给出选项和推荐；用户回答后，再把选定的规则写进模型。
- 设计漏洞的修正改的是设计稿或 GDD，不是模型里的性质。
- TLC 没有完整结束（超时、内存不足、工具报错）时，不报告通过。

## 交给 1D 批准材料的内容

用文档语言写给用户读，不要求用户读 TLA+：

- 状态 × 事件对照表，其中原来“未确定”的组合写明讨论结论；
- 模型范围：参数、抽象、没有覆盖的部分，以及要由随机序列测试补上的部分（例如浮点边界）；
- 性质清单：每条性质的一句话含义和来源 AC；
- 结果表：正确版本、每个错误版本、每条可达性检查各占一行，写期望和实际结果，以及 `summary.json` 路径；不只给通过数；
- 建模中和用户讨论定下的规则：每条写结论和来源（用户哪次回答），用 `design-gdd` 写回 GDD 的位置；
- 要在 Stage 3 改写成 GdUnit4 测试的路径：逐条列出，每条可达性检查一个测试，每个被抓到的错误版本一个能在代码上复现它的测试，各自对应哪条 AC；不用一句“都会改写成测试”代替。

返回调用方；Skill 返回不会结束它所在的已授权任务（methodology 03 的[授权与续接](../../../yaya/methodology/03-execute-loop.md#授权与续接)）。
