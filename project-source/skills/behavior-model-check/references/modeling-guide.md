## 一步与一步之间

Godot 的游戏逻辑在单线程上按帧或固定步长推进。一步之内的代码连续执行，玩家输入、暂停切换这类外部事件只能落在两步之间。模型要保留这个边界，否则会查出代码里不可能发生的交错，或漏掉真实的交错。

- 用一个阶段变量区分“两步之间”和“一步之内”，例如 `stage ∈ {"idle", "auto", "resolve"}`。玩家动作只在 `idle` 时允许。
- 一步之内的循环（例如“按顺序结算所有到期的敌人”）写成每次处理一个对象的动作，再加一个循环结束的动作；选择顺序按代码写，例如偏移最小者先结算，相同时 ID 小者先。
- 一步之内的几个子系统按代码的调用顺序分成几个阶段，例如“敌人推进 → 自动攻击 → 敌人进攻结算”。
- 代码里跨 `await`、信号回调或计时器的流程不是一步之内的原子操作；在等待点拆成独立动作，让其他动作可以插进来。

## 抽象其他系统

本 Feature 不负责的系统，只保留它对本模型状态的影响，写成“任意时刻可能发生”的非确定动作。例如自动攻击抽象为“任意存活敌人可能在这一步被击杀”，不建模伤害数值。

- 这种抽象允许的行为比真实系统多。性质在更宽的行为下仍成立，结论才可靠；因此不为了通过而收窄抽象动作。
- 抽象掉的内容写在模型开头的注释里，并写进 1D 材料的“没有覆盖的部分”。

## 性质的写法

| 要表达的需求 | 写法 |
| --- | --- |
| 每个可达状态都要满足的条件，例如“生命值非负” | 不变量（`INVARIANT`） |
| 某个事件发生时要满足的条件，例如“只有宽限期结束且仍为空位才打武装环” | 用一个记录变量保存最近一次事件的关键信息（目标、事件前是否在宽限期、剩余时间），对它写不变量 |
| 关于状态变化的约束，例如“暂停时计时不变”“失败不可逆”“生命值不自然恢复” | 动作性质 `[][条件 => 约束]_vars`（`PROPERTY`） |
| 只在某个时刻检查的条件，例如“每步结算结束时不留下到期的攻击” | 动作性质，限定在那次转换上，例如 `[][(stage = "resolve" /\ stage' = "idle") => ...]_vars` |

性质按需求写，不按实现写：“暂停时计时不变”要对照环境里真实成立的暂停条件，而不是对照实现保存的暂停标志，否则实现写错了性质也跟着错。

## 错误注入

用常量 `Mutation` 在同一个模型里切换错误版本，不复制模型：

```tla
CONSTANT Mutation   \* "none" | "no_grace" | ...

ResolveOne ==
    ...
    /\ IF it = None /\ ~grace[e] /\ Mutation # "no_grace"
       THEN ...  \* 正确行为：进入宽限期
       ELSE ...
```

- 每个错误注入模拟一种合理的实现错误：漏掉一个条件、用单个标志代替多个条件、按次数计数、失败后继续处理。
- 在清单的 `caught_by` 写明由哪条性质抓到。由别的性质抓到时，工具判为不满足，因为这说明对应的性质没有起作用。
- 正确版本必须用 `Mutation = "none"` 运行；工具会自动设置。

## 见证路径

正确版本通过，可能只是因为模型把要检查的行为限制掉了，例如禁止了所有购买操作，“金币非负”就一定成立。见证路径用一条期望被违反的不变量证明合法路径可达：

```tla
WitnessCanFail == phase # "failed"   \* 工具期望 TLC 报告它被违反，即“片段能够失败”可达
```

每条 AC 的主要路径、每个错误注入要走到的关键状态，都写一条见证路径。

## 参数选择

参数越小，状态越少，但取值不当会让参与者始终同步，某类交错根本不会出现，错误注入跑完全部状态也抓不到：

- **不同的计时常量取不同值。** 例如宽限期和攻击间隔都取 2 时，两个敌人永远同时行动。
- **耐久、生命值不取攻击者数量的整数倍。** 例如耐久取 2、两个敌人各打 1 时，物品总在第二个敌人手里被摧毁，两个敌人永远不会错开。
- **参与者至少两个**：交错问题至少需要两个会同时行动的对象。
- **状态无限增长时**（计数器、时钟）用 `CONSTRAINT` 限制范围，清单的 `constraint` 写约束名，并在 1D 材料里写明范围。

错误注入没被抓到、或见证路径走不到时，先按这几条检查参数。

## 时间、浮点与活性

- 时间离散为整数刻度，1 刻度对应代码里的一步或一个计时间隔。浮点误差、`minf`、`maxf` 的边界 TLC 查不到，写进“要由随机序列测试补上的部分”。
- 活性（“最终会发生”）只在确有异步等待时检查。玩家可以一直暂停，所以活性性质必须写明对玩家输入的假设；没有异步等待的系统不加调度模型。

## 失败的分类

| 现象 | 可能的原因 | 处理 |
| --- | --- | --- |
| 正确版本报出反例，对照代码或设计，这条路径本来就允许 | 性质写得过严，例如在玩家操作后、下一步结算前就检查 | 改性质的检查时机或条件，注释写明为什么 |
| 正确版本报出反例，路径在代码里不可能发生 | 模型写错，例如把一步之内的操作拆开、让玩家插进去 | 改模型，对照代码的执行顺序 |
| 正确版本报出反例，路径真实可能发生 | 设计漏洞，或依赖 Feature 的代码有缺陷 | 改设计稿；依赖 Feature 有缺陷时按 Bug 流程报告，写进 1D 材料 |
| 错误注入没被抓到，或见证路径走不到 | 参数让参与者始终同步，或模型限制了行为 | 按[参数选择](#参数选择)检查，再查模型 |
| 错误注入由别的性质抓到 | 对应的性质没有起作用，或 `caught_by` 写错 | 查对应性质；确认两条性质都该抓到时，`caught_by` 写两条 |
| 工具退出码 `2` | 模型语法、清单或环境配置出错 | 读 `logs/` 下的 TLC 输出修正 |

## 改写成 GdUnit4 测试

模型和代码之间唯一能执行的连接是测试。Stage 3 按 1D 批准的测试清单改写：

- 从 `logs/` 中见证路径和错误注入的反例输出里取操作序列，按同样的步骤边界调用项目接口；
- 关键步骤之后都断言状态，不只断言最终结果，因为中间的非法状态可能被后续动作掩盖；
- 断言预期来自 AC 和 GDD，不读当前实现的结果作为答案；
- 测试按 AC 登记逻辑 ID，见 `yaya/methodology/08-test-traceability-and-evidence.md` 的[Feature 的可追溯性](../../../../yaya/methodology/08-test-traceability-and-evidence.md#feature-的可追溯性)。
