# Answer a question with a Godot prototype

Identify the question to settle, the current task's authorization and the evidence that would answer it. Apply **GDD prerequisite and authority** in `methodology/01-product-doc-structure.md`; an experiment does not initialize missing game design or approve a proposed rule. Discussion-only work can define the experiment without building it.

## Read the matching prototype method

Use the relevant sections in methodology 01, retaining their existing source ownership, validation and adoption rules:

| Question | Read |
| --- | --- |
| Layout, scale, content density, representative assets or visual/interaction feedback | **Visual prototype before dependent implementation**, including scope/resources and validation/adoption |
| Logic, state transitions or technical feasibility | **Scoped logic prototypes**; read visual requirements as well only when judging visual or perceptual qualities |
| Resources must be prepared or supplied before the experiment can answer its question | **Resource requirements and handoff** |

Default to the actual project's Godot environment and a small runnable scene. Follow the selected method for isolated sample state versus a necessary real engine path. HTML is not a default prototype format or a precursor to Godot verification. Read relevant professional sources and affected engineering domains through project `AGENTS.md`, without loading unrelated specifications.

## Build and report within the task

Reuse an existing prototype when it still answers the question. Build only the state, controls and observations needed for the authorized experiment; keep assumptions visible. Use the scoped-experiment route in `methodology/00-overview.md` for standalone work or the owning Feature's current plan for delivery work. Runtime checks and modifications remain subject to that task's actual permissions.

Return the runnable entry, question answered, actual observations, unresolved limits and next source owner when a decision needs adoption. When comparing a presentation alternative, link the experiment to that section; adopted choices and actual file/consumer relationships return to its owning document before final verification. State what was not run or still needs human experience; a screenshot, static check or simulated state change has only its actual coverage. Follow methodology 01 for notes/Progress, source updates and prototype disposition, without creating a second plan or status ledger.

A prototype's acceptance covers its agreed scope, not production readiness or later game behavior. Preserve necessary human feedback and do not infer it from successful execution. If authorized delivery remains after the experiment, continue through its existing owner; do not create another approval step merely because the prototype method returned.
