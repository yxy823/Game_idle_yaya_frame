# 用 Godot 原型回答问题

先确定要解决的问题、当前任务的授权，以及什么证据能回答它。按 `yaya/methodology/01-product-doc-structure.md` 的 **GDD 前提与职责** 执行；实验不能补出缺失的游戏设计，也不能批准拟议的规则。只要求讨论时，可以只定义实验而不构建。

## 阅读匹配的原型方法

使用匹配的小节，并遵守其中的来源归属、验证和采纳规则：

| 问题 | 阅读 |
| --- | --- |
| 布局、比例、内容密度、代表性素材，或视觉与交互反馈 | `yaya/methodology/13-prototypes.md` 的 **依赖实现前的视觉原型**，包括其中的范围、资源、验证和采纳 |
| 逻辑、状态转换或技术可行性 | `yaya/methodology/13-prototypes.md` 的 **限定范围的逻辑原型**；只有在判断视觉或感知质量时，才同时阅读视觉一节 |
| 实验要回答问题，必须先准备或提供资源 | `yaya/methodology/11-specialist-workflows.md` 的 **资源需求与交接** |

默认使用项目自己的 Godot 环境和一个可运行的小场景。按所选方法决定使用隔离的样例状态，还是必要的真实引擎路径。HTML 不是默认的原型格式，也不是 Godot 验证之前的一个步骤。通过项目 `AGENTS.md` 阅读涉及的专业来源和受影响的工程领域，不加载无关的规格。

## 在任务范围内构建和报告

仍能回答问题的原型直接复用。只构建获准实验需要的状态、控件和观察点，并让假设保持可见。单独的实验按 `yaya/methodology/00-overview.md` **任务路由表** 中“用户明确要求的原型或技术探针”一行处理；交付工作按所属 Feature 的当前计划进行。运行时检查和修改不超出该任务的实际权限。

返回：

- 可运行的入口；
- 回答了什么问题，以及实际观察到的结果；
- 尚未解决的局限；
- 需要采纳某项决定的来源负责方。

比较表现方案时，从对应章节链接这次实验。最终验证之前，采纳的选择以及实际的文件与使用方关系，要写回所属文档。写明哪些没有运行、哪些仍需人的实际体验；截图、静态检查或模拟的状态变化只覆盖它实际展示的内容。notes 或 Progress（进度记录）、来源更新和原型的后续处理按 `yaya/methodology/13-prototypes.md` 执行，不另建第二份计划或状态记录文件。

原型的验收只覆盖约定的范围，不代表达到正式产品质量，也不代表后续的游戏行为。保留必要的人工反馈，不能从运行成功推断出反馈。

返回调用方；Skill 返回不会结束它所在的已授权任务（methodology 03 的 **授权与续接**）。
