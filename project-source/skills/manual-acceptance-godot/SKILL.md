# 准备或记录人工验收

确认实际的 Feature、当前范围和请求的操作。沿用已批准的验收模式和人工验收义务；不为了套用本方法而编造 Feature、新需求或空清单。是否调用本方法，取决于需要的能力及其输入，不需要重新进入执行流程。

## 使用验收约定中对应的部分

清单、快照绑定、命令和结果含义，以 `yaya/methodology/contracts/manual-acceptance-files.md` 为准。只读这次操作需要的小节，以及涉及的 Feature、实际的源文件和清单。

| 请求的操作 | 阅读并执行 |
| --- | --- |
| 准备给用户试玩的材料 | **定义与准备**：把已批准的验收义务展开为具体的待验收检查项，绑定到最终实现，并提供实际的清单路径、交回方式和用户自己运行的启动命令。不替用户打开 Godot 窗口：Agent 留下的窗口会占用用户的桌面，也可能让 Agent 的命令一直等它关闭而无法结束 |
| 记录用户的结论 | **记录用户的结论**：用户在对话中表态时，把结论写进清单对应项的状态和备注（写明“来自对话”和原话）；用户自己改过清单时，先读它的状态和备注。然后用同一个命令记录 |
| 绑定之后项目又有变化 | **绑定之后内容又有变化**：逐个核对工具列出的变化文件，都不涉及本 Feature 才确认沿用 |

清单全部通过，就是用户接受了它覆盖的范围；不再要求用户说一句接受。用户的话没有覆盖全部检查项、备注与状态矛盾，或决定不清楚时，只就具体问题澄清。Agent 自己判断的结果、用户沉默和“继续”的请求，都不构成人工接受，不能据此把检查项改成 `passed`。

只改清单的状态和备注，不改检查项的定义，也不改写用户的观察。源文件或验收约定变化时，按已有的过期和更新规则处理；不要把已准备的清单重新绑定。自动检查和截图可以辅助准备材料，但不能代替用户的体验。

## 交回记录的结果

使用已有的记录工具，报告准备了什么或实际记录了什么、覆盖的范围，以及仍不确定的地方。记录成功也可能是 `pending` 或 `rejected`；记录成功不证明验收通过或 Feature 已完成。失败和后续工作按验收约定处理，实现上的修改交回已有的负责方。

长期保存的文字按 `yaya/methodology/05-document-language.md` 书写；写入和提交按 `AGENTS.md` 的 **Git 与提交** 执行。任务同时要求实际验收和明确的提交许可时，按 `AGENTS.md` **Git 与提交** 中的 **提交**，两者都要满足：任何一个都不能代替另一个。

报告实际结果和证据。只做记录的工作不推进 Stage，也不宣布交付完成。返回调用方；Skill 返回不会结束它所在的已授权任务（methodology 03 的 **授权与续接**）。
