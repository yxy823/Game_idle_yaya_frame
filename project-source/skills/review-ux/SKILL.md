# UX 审核

独立审核按 `yaya/methodology/12-independent-review.md` 执行；作者在 Stage 4 按界面任务试用时只借用本 Skill 的试用方法和问题分级，不受独立审核的约束。阅读涉及的用户目标、GDD 行为、Product 交付范围和 UI 规格（来源位置按 `yaya/methodology/11-specialist-workflows.md` 的 **归属与决策** 查找；只有空章节的 Bible 不构成审核标准），再针对请求的流程以及显示与输入条件，检查实际的画面和交互证据。

追踪：操作是否容易发现，状态和反馈是否容易理解，导航与焦点是否可预期，错误能否恢复，流程是否支持用户目标。包括涉及的空状态、加载、禁用、错误、内容密集或长文本，以及重复进入等状态。任务要求时，检查文字对比度、点击目标尺寸、输入方式和不依赖颜色的提示；不编造认证标准。

区分已经演示出来的交互问题、对需求的违反和设计建议。静态效果图不能证明鼠标、键盘操作及时机，单靠截图也不能证明端到端的可用性。没有实际交互证据时，相应地限定结论。审核涉及的界面有界面任务时，按下面的[按界面任务试用](#按界面任务试用)取得交互证据。

报告具体的用户操作、观察到的障碍、后果和证据位置。不重新设计画面。玩法动机和留存方面的试玩不在范围内。

## 按界面任务试用

在项目副本里用程序驱动界面，按用户想做的事逐个走一遍，找出要停下来猜、走错路或做不成的地方。本 Skill 的审核和 `yaya/methodology/03-execute-loop.md` 的 [Stage 4](../../../yaya/methodology/03-execute-loop.md#stage-4--自动验证与人工检查清单) 作者侧试用都用这个方法；作者侧试用由实现者自己完成，不算独立审核，也不代替人工验收。

**输入**：游戏界面的界面任务写在 UI 规格的“界面任务”小节，写法见 [design-ui-spec](../design-ui-spec/SKILL.md#界面任务)；调试台的界面任务和通用标准在 `dev/debug/_shared/usage-scenarios.md`。要试的界面还没有界面任务时，按请求的流程列出要试的任务，在报告中注明由试用者补写，不替 UI 规格的负责方写进规格。

**工具**：用 `yaya/tools/ui-trial/` 准备改名的项目副本、编写驱动脚本、运行和静态扫描，参数、退出码和限制见[按界面任务试用工具](../../../yaya/tools/ui-trial/README.md)。

- 只在副本里运行，副本改名没有确认成功就停下，不在项目本身运行：试用会执行真实代码，可能写入用户的真实存档。
- 先用无头模式把驱动脚本调通；真实窗口只在最后需要截图时开一次。不操控用户的鼠标、键盘或桌面。
- 静态扫描的结果只是线索，对照界面任务和截图确认后才写进结论，误报删除。

**每一步问四个问题**：

1. 用户会想到要做这一步吗？
2. 用户能看到这一步要用的控件吗？
3. 用户能把这个控件和自己的目标联系起来吗？
4. 操作之后，用户能看懂反馈，知道自己离目标更近了吗？

任一回答为“否”，记一个问题。

**再按检查组看整个任务**：

| 检查组 | 检查问题 |
| --- | --- |
| C1 步骤与输入 | 完成任务要几步、几次输入？有没有可以合并的步骤？ |
| C2 入口可发现 | 不问人能否找到入口？入口在不在第一眼会看的位置？ |
| C3 控件可理解 | 按钮文字和图标是否只有一个意思？操作前能否预测结果？ |
| C4 顺序合乎直觉 | 步骤顺序是否符合用户的想法？是否要先做一件和目标无关的事？ |
| C5 状态与下一步 | 用户是否知道当前在哪、操作是否成功、下一步做什么？ |
| C6 路径与重复 | 是否要在界面之间往返，或每次重复同样的设置？ |
| C7 误操作与恢复 | 相邻控件是否容易误点？高风险操作有没有确认和撤销？ |
| C8 分组与层级 | 功能分组是否符合用户的任务？层级是否过深？ |

**必须项**，任一不满足，相关界面任务判为未通过：

| 编号 | 必须项 |
| --- | --- |
| M1 | 每个全屏界面都有一致的“返回”或“关闭”操作 |
| M2 | UI 规格要求键盘导航时，只用键盘可以完成全部导航；游戏面向鼠标和键盘，没有这项要求时不检查 |
| M3 | 每次输入都有可感知的反馈 |
| M4 | 消耗货币、改动文件或不可逆的操作有确认，确认中写明后果 |
| M5 | 任务完成后，界面显示结果和下一步可做的事 |

试用调试台这类开发工具时跳过 M1、M2 和 C2 中的键盘到达问题，同时对照 `usage-scenarios.md` 的通用标准：任何一步需要懂系统内部（目录、文件、引擎报错）才能完成，都算问题。

**分级**：

| 级别 | 含义 |
| --- | --- |
| 阻断 | 任务做不成，必须懂系统内部才能做成，或会丢失数据、写坏用户文件 |
| 困惑 | 能做成，但用户会停下来猜、误解结果或走错路 |
| 小问题 | 不影响完成和理解，例如措辞不统一、对齐或间距 |

**报告**：每个界面任务写通过或未通过；每个问题写步骤、检查组或必须项、现象、证据（`steps.log` 的步骤、截图、`文件:行`）和级别。程序驱动只证明这条路径能走通：`click` 不经过鼠标、不检查按钮是否被遮住，也不代表真人第一次使用时的理解；观感、手感和最终接受仍由用户判断。
