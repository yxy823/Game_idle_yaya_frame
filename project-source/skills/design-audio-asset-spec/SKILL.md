# 音频资源规格

归属、授权、来源影响和定稿按 `yaya/methodology/11-specialist-workflows.md` 执行。该文件的 **资源需求与交接** 章节负责：

- 选定所属章节：表现、UI 或已抽出组件的章节，或 `docs/audio/sound-bible.md` 中的 **共享资源规格**；
- 判断是否需要文件条目，按准备和检查需要选择信息；
- 说明归属变化时规格怎样迁移；
- 交付时怎样说明准备需求和待定选择。

不要另建一份准备清单。使用 `document_language` 编写。

先核对当前范围是否需要声音。已排除音频时沿用范围说明，不扩写空资源集合或调查无关示例。

需要声音时，阅读已确认的 GDD 触发条件、Product 交付范围、适用的 Sound Bible 和相关资源。详细的共享声音标准由 `design-audio-direction` 维护，共用依据集中引用。复用已定决定，只澄清影响准备的缺口；不要给每个交互都加声音提示（cue），也不要默认有配音。必要参数未知时保持待定，继续不依赖它的部分。Sound Bible 中标为“待试听”的特征，规格按备选分开写，不替用户选定其中一版。

## 具体交付物

| 类型 | 有用的规格 |
| --- | --- |
| 音效 | 准确的触发方式和条件；反馈目的；时长或范围；沿用的共享风格或明确的例外；重复、叠加和优先级要求；可用的参考和要避免的特征 |
| 音乐或环境声 | 使用场景和过渡；情绪、质感和节奏；时长和循环方式；需要时写明相对混音和优先级预期；参考和要避免的特征 |

正式制作中的触发条件与调试台里的试播动作分开写。不要把振荡器设置、响度数值或采样率当作已确认的要求；只记录影响本次准备或接收判断的约束与测量结论，无关字段直接省略。

沿用真实文件名和已有的有效 ID；名称足以定位时不另编 ID。来源、准备状态和已知去向按通用资源条目要求维护，区分样本与成品；本次未测量的时长或格式不能标为实测。

文件尚未命名时可以按用途描述；不要为填字段在规格里编造文件名、预定格式或目录。实际放入项目的占位文件仍按项目规则使用 `_placeholder_` 前缀。备选方案需要的文件保持备选身份，不自动纳入必备集合。

## 交接与边界

把可用的可播放示例、缺失的文件，以及需要做的检查（例如反馈时机、遮蔽或循环接缝）交给已授权的交付任务：需要试听比较的，作为调试台插槽的候选（见 in-game-tuning 的[候选](../in-game-tuning/SKILL.md#候选)）在游戏中比较。缺少参考不一定阻塞起草，但实际的听感评估仍保持未验证。文字描述或没有声音都不算证据。

音乐和音效在项目外的制作项目中制作（methodology 11 的 **在项目外制作**），交接时给出本规格所在的章节和提交号。本 Skill 不合成、不录制、不获取，也不处理音频文件。外部提供的音频由 `content-asset-integration` 接入；用户要求独立审核时，由另一个实例中的 `review-audio` 评估。没有实际的操作和证据，不要声称已经制作、播放或验收。

行为变化交给 `design-gdd`；专业要求的变化按 methodology 11 的 **编写与采纳** 中的变更路径处理。

返回调用方；Skill 返回不会结束它所在的已授权任务（methodology 03 的 **授权与续接**）。
