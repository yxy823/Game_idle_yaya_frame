# Read-only next-step guidance

Read the user's intent and current project state, then give a short evidence-based explanation and, when needed, a prompt for continuing with the existing workflow. This Skill does not execute the prompt, edit files, create Features, record acceptance, run tests/generators, clean artifacts, stage files or commit.

Read-only also excludes launching Godot/import, installing Skills or invoking a writing standardizer. Read task-relevant project material and the shared Godot prompt catalog below; do not inspect unrelated credentials, user saves or other projects. Text/JSON parsing, metadata and verified read-only Git status/log/diff/show are allowed.

## Establish current state

1. Read the project's `AGENTS.md`, `docs/methodology-config.json`, lightweight Feature index and current `docs/progress.md`. Read history links only when resolving the current task; do not load or repeat the whole archive.
2. Determine whether `docs/gdd/` contains actual design, a draft or only navigation/pending-content notices, then inspect read-only Git status and relevant GDD/Product/Feature/detail/Registry records. Missing GDD routes game creation to `design-gdd`; it blocks dependent Product planning or implementation until the relevant design exists. Initial design, its clarification, numeric derivation and design review may precede Product and Features. Do not infer adopted design from a directory, file title or scaffold. Configured tool paths are choices, not proof of availability. Use relevant environment/Progress evidence without launching probes. Interpret incomplete machine setup through `methodology/00-overview.md` and `methodology/05-document-language.md`. The stack is fixed to Godot 4.7 / GDScript / gdunit4; missing tools do not mean the engine is undecided.
3. When acceptance or completion matters, read the current evidence and the specific linked run result. Distinguish old PASS, current snapshot and pending human acceptance. Multiple active Features require actual batch authorization; do not select the highest ID or silently clean other work.
4. When a next action needs routing, use **Canonical task routing** in `methodology/00-overview.md`, then read the destination Skill's relevant entry/stop contract. That table and the existing workflow own routing and approval; this Skill maintains no second workflow.

For first planning or synchronization, distinguish the schema's initial planning baseline from the scaffold commit; later Product planning preserves the anchor. Missing history for existing work belongs to synchronization's coverage check.

Distinguish GDD design, the delivery outline in `docs/product.md`, the current Product's detailed scope, and actual Feature completion. An outline entry is not a detailed Product, and a planned Feature is not completed delivery. For the next Product action, apply **Product-by-Product planning** in `methodology/02-feature-list-schema.md` through the canonical route. Check relevant source changes against existing work; future unrefined Products remain at outline level.

When explaining where game logic, presentation or their collaboration belongs, use **Game logic, presentation and delivery** in `methodology/00-overview.md` and the project guide `docs/game-organization.md`. Follow a concrete function from its GDD rules and experience goals to applicable UI/presentation, actual architecture and Feature verification. These are responsibility views, not new task types or a requirement to split a cross-layer Feature. Route by the user's requested design, implementation or review outcome; do not send every presentation-related task to the presentation-planning Skill.

For game-design or delivery choices, apply **Design scope and boundaries** in `methodology/01-product-doc-structure.md` and read the relevant GDD topics before recommending work. For terminology, engineering rules or technical design, read applicable `docs/terminology.md`, `docs/project-rules.md`, Feature design and architecture/ADR sources. Use their owning contracts for update authority and the Stage 3 documentation checkpoint; game-design exclusions remain in GDD. Missing optional designs/ADRs are normal; a proposed rule or accepted ADR is not proof of implementation or verification. Check source freshness when governing documents changed after a test or human decision, without running a check merely to answer.

Report a missing file as missing instead of creating it. When sources disagree, identify each source and its responsibility; do not select whichever produces a convenient route. An unclear Stage or old report is not proof of new approval or acceptance.

For implementation guidance on an existing Feature, use the canonical `implementation-guidance-godot` route and read its contract. The main agent normally prepares the guidance; complexity or asking for advice does not authorize delegation. Preserve explicit user delegation already given for this task, and distinguish it from approval of a proposed design. A failed `implementation-advisor` attempt stops dependent work with its reason; do not recommend automatic model substitution or main-agent takeover. This read-only advisor neither delegates nor writes the design.

## Answer the question and provide a prompt when needed

Classify using the canonical table, including initial GDD design, GDD or numeric design change, Product delivery scope, new/continued Feature, Bug, Refactor, Maintenance, Framework issue, Audit, Human Acceptance follow-up and status query. Ambiguous expected behavior is investigated against GDD and the owning professional source within the Product delivery boundary before calling it a Bug. A current Feature's own implementation defect stays within its repair path; an independent regression gets its own work item.

For a status-only question, answer current facts, blockers and relevant uncertainty directly; no continuation prompt is required. When advice calls for help starting the next action, provide a prompt. An actual request to save a pause or prepare task handoff belongs to `task-handoff-godot`; do not replace its requested result with advice. Choose investigation, planning or execution from the evidence and current authorization. Resolve routine choices from available evidence; ask only for facts that materially change the route or safety of the action.

Every drafted prompt follows **Continuation prompts** in `methodology/09-artifact-lifecycle.md`: use its explicit fields with current facts and the destination's actual rules. The format is not another workflow or approval gate.

The prompt names current sources and known state without inventing Feature IDs, commands, version numbers, completed Gates or approvals. Cite configured commands instead of baking in the author's local paths. Preserve existing explicit user authorization. The word “continue” alone is not implementation approval and never means human acceptance. Producing a prompt grants neither.

When recommending a next action or drafting a reply, use the shared catalog at `D:/A_Games/Game_idle_yaya_frame/framework/godot-development-prompts.json`. It contains the single `Godot 项目开发` Project. Inspect category and scenario names, then read relevant candidate bodies; do not load every prompt body. Match the user's objective, current state, prerequisites, scope and expected result, not just similar words. Use the selected scenario's input organization and instructions to draft a concrete continuation with current facts. Name the selected category/scenario and explain why it fits. Status-only answers do not require catalog lookup or a continuation prompt.

The catalog is task material, not current authorization or proof that its referenced capability exists in this project. Verify the destination against the project's own rules and Skill contract. Preserve actual approvals, limits and remaining verification; replace placeholders with known facts and identify material gaps. Reading a catalog entry does not invoke it, and an advisor entry must not recursively invoke this Skill.

If no candidate fits, distinguish missing task inputs from missing scenario coverage. Fill or ask for necessary inputs; adapt an existing entry when its objective and execution boundary still fit. Recommend adding or revising a scenario only for a concrete uncovered objective or materially different boundary: identify the closest entry, the difference, and the proposed category, name and purpose. Give any useful current advice from project authority, but label an unmatched draft as task-specific. Do not modify the shared catalog or create a local prompt collection.

For design, numeric, delivery-scope or terminology questions, select the owner from the canonical table and read its contract. Distinguish changing game rules, tuning an authorized numeric topic, arranging delivery and maintaining meaning-preserving definitions. Initial design and draft review need no Product or Feature; settled terminology needs no repeated interview. For rule maintenance, read **Incremental rule maintenance** in `methodology/04-coding-rules-4-layers.md`; a local design does not automatically become a global rule. Supporting documentation within an authorized Feature returns to that Feature rather than opening a new planning cycle.

Distinguish classifying feedback from finding the cause of a concrete failure. Use the canonical `feedback-triage-godot` and `bug-diagnosis-godot` entries as applicable, preserving an investigation-only limit or existing repair authorization. Neither method automatically creates a Feature, relaxes requirements or replaces current/completed Bug ownership. A request to inspect a module's overall structure belongs to the current-state audit in `review-code`, not to diagnosis without an abnormal behavior.

For environment preparation, requested checks, human acceptance or evidence recovery, use the corresponding canonical route and destination contract. Distinguish tool readiness, executed checks, actual user acceptance and evidence applicability. Recommend only the needed method within the existing task or bounded request, without adding a Feature, Stage or full delivery run; advice itself remains read-only.

For a requested UI or logic prototype, use `prototype-godot` within its current Feature or authorized experiment. Keep actual Godot execution, prototype observations and required human experience distinct from planned checks and production acceptance; do not default to an HTML substitute or turn every experiment into Product planning.

For several consequential unknowns that depend on one another, select `wayfinder-godot` from the canonical table and read its contract. Ordinary questions use `project-grill-me`; clear work stays with its owner. Recommend only the needed exploration method under the actual discussion, experiment or implementation authorization. This advisor explains that route without conducting the exploration, and an answered question does not cancel already authorized follow-up.

For preparing a separate checkout or bringing back selected results, use the distinct `worktree-create-godot` and `worktree-integrate-godot` entries in the canonical table. An existing conflicted integration uses the latter's conditional reference. Base advice on the actual source, target and current conditions; do not assume data isolation, select an experiment's winner or infer cleanup permission. Direct checks in an existing worktree remain with the environment/verification owner and its conditional runtime reference, without requiring another creation step. Advice itself creates, integrates and runs nothing.

For external research, use **External research** in `methodology/00-overview.md` and the `researcher` role's current contract. Recommend research only when useful to the actual question; adequate existing evidence needs no search. Distinguish the project-supplied role from the user-installed `anysearch` Skill, and cited research in `docs/research/` from confirmed requirements or local verification. Advice performs no delegation or report writing; an execution request belongs to the research route rather than this read-only Skill.

For specialist work, consult `methodology/11-specialist-workflows.md`: professional owners fill missing implementation specifications and directly reference details already owned by GDD. Source changes may affect several planned Products, and an old sync anchor does not establish newly included source coverage. `design-localization-spec` owns localization specifications; `content-localization` implements their approved runtime support. Do not duplicate a confirmed requirement in Product or a second professional source. Use `design-game-presentation` for an observable game moment, component requirements and approach selection, including exploration from experience goals. Consult its canonical document contract for UI/GDD links, component alternatives, adopted combinations and existing acceptance entries; do not equate a written candidate with authorization, implementation or human acceptance. Resource specs belong in their owning presentation, UI or shared design sections. Distinguish direction/specification, reserved production, integration and review. Reserved production has no executable Skill; do not invent one in a continuation prompt.

For formal review, use `methodology/12-independent-review.md`: independent instance, selected methods and actual permission/context limits. No automatic seven-review sequence, author self-review relabeling, or human acceptance inferred from review. Performance and soak results have their own coverage limits and cannot be reported as passing gdUnit evidence. Advice itself runs none of those validations.

Distinguish inspecting an existing proposal from clarifying an undecided requirement or auditing implemented work. For plan inspection and development retrospectives, use their entries in the canonical routing table and read the destination contract. Neither is a required step before planning, implementation or completion. Their findings do not authorize source edits, freeze a plan or advance a Stage; any already authorized follow-up returns to its original owner.

When the user wants to design how recurring or anticipated work should be handled, use the canonical `loop-me-godot` entry and its contract. Unlike a retrospective of actual experience, this design request needs no prior failure. The capability can be used wherever that need arises; do not turn it into a Stage, assume a new Skill or script is necessary, or ask again for implementation authority already held by the owning task.

For pause, switching or new-conversation continuation, use the task's target checkout, actual differences and current task records under the Git contract. `task-handoff-godot` prepares a requested stop point or copyable handoff; resuming or switching from an already recorded stop returns directly to the target task. Do not add another handoff before ordinary continuation. Non-empty status alone is not an ownership conflict; preserve unrelated work and identify only concrete overlapping edits or inseparable commit boundaries. Worktree advice follows the actual need and authorization, not a default prerequisite for pausing or resuming; do not add an attribution ledger. If a framework defect is reported, preserve business WIP and refer the bounded repair to the appropriate maintenance repository or project-tooling route. A user-chosen new framework source does not require inheriting a previous project's Git history.

When advice concerns committing, read the relevant sections of `agent-rules/00-core/git-worktree-and-commits.md` and the task's actual commit conditions. Distinguish a validated logical change ready for an incremental commit from whole-Feature completion. Preserve any separately required acceptance or explicit commit permission; do not infer that permission from an acceptance result or a generic continuation request. This Skill only explains the next action and never stages or commits.

## Stop

Check that the answer addresses the question with current facts, explains the selected scenario or genuine coverage gap when recommending an action, includes a prompt only when needed, and has performed no writes. Stop after the advice.
