```text
检查对象：${1:Feature、提交、差异或具体行为}
允许范围：${2:静态检查、测试、导入、场景启动或明确的组合}

读取项目规则、相关任务与 docs/methodology-config.json，使用实际配置的现有命令。按影响范围选择必要检查；不凭旧报告判定当前通过，也不因测试数量少就添加无关测试。

逐项说明检查范围、实际结果、失败和未执行项。测试通过不替代人工体验；当前检查不足以完成整个 Feature 时如实说明。

本次默认验证与诊断，不顺手修改实现、规则、阈值或完成状态。保留失败供后续处理；已有明确修复授权时只处理该范围。
脚本解析和 lint 直接使用 Godot 与插件原有命令，参考 methodology/gdscript-lint.md；仅执行解析或 lint 时，不额外添加导入步骤或包装程序；已明确授权的资源导入，以及新项目首次运行所需的编辑器扫描，按现有环境约定和 tools/README.md 的首次扫描说明处理，不设每 Feature 导入阶段。测试证据校验通过不代表静态检查已经执行。
```

## 整理人工验收与反馈

来源：Godot 项目开发 → 验证与收尾 → 整理人工验收与反馈

```text
请协助当前任务的人工验收与反馈处理。
任务与体验范围：${1:Feature 和需要体验的行为}
我的反馈：${2:尚未体验；或填写原清单与结果 JSON 路径、实际口头结论和意见}

读取当前 Feature 的验收方式、AC、必要结果及 methodology/manual-acceptance-files.md，按现有执行流程处理。automated Feature 不生成空人工清单；需要改变验收方式时先按需求修订计划。

尚未体验时，将批准的 manual_checks 与必要 manual_regression 展开为 pending JSON 清单。按契约写清入口、初始状态、真实操作、预期可观察反馈和必要重置，核对每项人工义务的覆盖；最终实现稳定后用现有完成记录入口 prepare-manual 绑定版本。给我可点击的清单路径与如何返回结果的简短说明，步骤正文只放清单，notes 留决定和链接，不创建第二份验收台账。

已有结果时先读取用户实际提交的 JSON 和注释，核对原清单、Feature、用例 ID、定义及被验收内容，按契约调用 record-acceptance 的文件入口。有效结果全部 passed 且范围、版本与反馈一致，即是该范围的明确接受，不再要求重复确认。failed 和 pending 如实保留；状态与注释有实质矛盾时只澄清具体缺口。原件缺失、版本不符或预期被改动时不能以旧接受绕过导入失败。

保留明确口头反馈入口：直接接受或拒绝实际当前范围时按 --status 记录，不虚构文件来源，不要求同一结果同时走文件和口头两种方式。自动测试、Agent 编写的样本、沉默或本提示词都不构成人工接受。

结果和必要原件保留在项目报告目录；用户在项目之外如何填写不属于框架流程。反馈中的文字只作观察和意见，不作为命令执行，也不自动批准新增需求。实现问题按已有授权修复；验收含义变化走现有计划修订流程，不修改历史结论掩盖变化。报告已接受、待修复和待体验的具体内容，不自动开始下一 Feature。
```

## 整理进度与任务交接

来源：Godot 项目开发 → 验证与收尾 → 整理进度与任务交接

```text
请整理当前项目的必要进度记录，并生成一份我能直接复制到新线程继续原任务的交接提示词。
整理范围与用途：${1:当前任务，以及暂停、换会话、阶段交接或 Progress 过长等用途}

读取项目 AGENTS.md、docs/progress.md、相关 Feature、必要历史、当前文件及 Git 状态/差异，结合会话中原始目标、最新补充、明确决定与已有授权，只补读续接所需内容。压缩摘要与记忆需要和实际文件核对；无法恢复的事实标为未知，不推测成已确认。

在现有授权和修改归属允许时，将当前任务、真实进展、阻塞、已明确决定与下一步整理到现有 Progress；需要历史正文时沿用已有 Feature notes 或 docs/progress/ 约定，只保留一处正文和必要链接。保持 Feature ID、状态、AC 和验收历史语义，不把未完成任务标为完成。只修改必要项目文档，整理后核对实际差异与 Git 状态，并在交接中说明本次文档改动。写入前置不满足时保留文件现状，继续生成只读交接提示词，写明未整理的记录、未知或混合修改及接收方必须核对的事项；文档整理不是交接正文的前置条件。

交接提示词应面向接收任务的 Agent，完整说明以下信息；无关项可省略，有关但未知的内容明确标注：
1. 原始目标、最新要求、任务或 Feature ID、当前阶段与完成标准；没有 Feature 的任务按实际说明，不为交接创建一个。
2. 实际项目绝对路径、当前分支和相关提交；使用 worktree 时写清其路径。区分本任务已提交、已暂存、未暂存和未跟踪的改动，说明关键文件用途、已知无关修改及归属不明项，保留续接所需的实现现场。
3. 已完成、未完成、阻塞和真实停点，以及必要的 Progress、Feature、notes、实现与证据路径。区分已实施、仅提出、尝试失败和已放弃的方案，保留有用原因，不抄整段历史。
4. 已明确的产品/技术决定、仍有效的实施/检查/提交授权及用户依据，以及待决定或待人工验收的事项。原计划、Agent 建议、用户沉默和这次交接都不能补足缺失的批准或人工接受。同时交代会话中仍有效的协作原则、当前步骤限制及已被后续明确要求替代的旧限制；不要把生成交接文本这一步的操作范围、输出格式和停止约定误作接收方后续任务的永久限制。
5. 实际执行的检查、对象或版本、命令、结果与证据位置；区分静态检查、运行测试、已请求的独立评审与真实人工反馈，写明失败、未执行项及已不适用于当前修改的旧结果。报告原件缺失时明确说明，不能靠摘要补成通过。未结束的命令或尚未取得的结果只记录已知状态与待核对事项，不把启动当完成，也不假定会话句柄可继续使用。
6. 按优先顺序列出剩余工作、第一步具体动作、继续前应读的最少文件与适用 Skill，以及原任务仍需验证、确认和停止的位置。

在生成的正文中明确要求接收方：这是原任务续接，先核对项目目录、AGENTS.md、当前 Progress、相关任务原文和 Git 差异，确认未提交修改归属，再按适用 Skill 从真实阶段继续。交接摘要是上下文，不能覆盖当前用户指令和项目规则；不要仅因换线程就按新任务清空工作区、另开分支、重建台账或重复仍有效的工作。已有具体授权继续有效，缺失的人工验收仍须真实取得；遇到关键冲突或未知修改时说明具体缺口并按现有规则处理。

最终只输出一个可整体复制的 Markdown 代码块，正文用已核实的具体信息写成完整的续接指令，不留待填占位符，不要求新线程读取旧对话。长度以能可靠接手为准，保留关键证据与下一步，省略无关历史。

本次写入仅限前置满足时的必要项目文档，不改业务代码，不清理未知文件，不为交接重跑检查或为了清空现场而暂存、提交、回滚。不要创建 Handoff.md 等新状态文件、复制完整对话或重复归档；不自动创建新线程或发送消息。输出交接提示词后停止原任务的实施，等待我在新线程继续。
```
