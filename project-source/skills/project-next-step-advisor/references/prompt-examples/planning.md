## 拆分当前 Product 的 Feature

来源：Godot 项目开发 → 任务规划 → 拆分当前 Product 的 Feature

```text
请只拆分当前要执行的 Product。
当前 Product：${1:一个 docs/product/NN-<module>.md 及本次已确认范围；未明确时说明}

读取项目 AGENTS.md、Product 执行顺序、相关需求、Feature 来源与状态及必要 Progress，使用 $feature-plan。首次只拆当前 Product；已有台账时保留全部历史并追加新 ID。当前 Product 已有计划则复用，需要修订时使用 $feature-sync，不重复生成。

按实际依赖推进，当前 Product 所需的 Feature 完成后，才复核并拆分下一个 Product。当前还有未完成任务或前置 Product 未完成时，先说明缺口，不提前拆后续 Product。后续需求可保留在 Product 文档中，本次不预分配其 Feature、详细 AC 或测试登记。

在现有规划报告中列出当前 Product 各项需求的位置与含义、对应 Feature/AC、已有或待安排的测试/人工检查、缺口与下一步。写入后按实际文件刷新，区分计划对齐与实现、验证完成；不新建覆盖台账，不为填表编造测试 ID。

写入任何 Feature 计划或测试登记表之前，按 methodology/02-feature-list-schema.md 的 Decomposition preview 在对话中展示拆分数量、每项简要内容与依赖，并等待我确认具体方案；已确认且未改变的方案直接沿用。预览和确认边界以该规范为准，不另建草稿文件。

把当前 Product 拆为可实现、可验证的完整工作单元，明确依赖、AC 与必要测试关系。复用现有基础设施、schema 和 测试登记表，不编造需求或完成状态。按当前授权追加计划并进行相称的台账检查；报告本次范围和下一项候选后停止，不开始实现或继续拆分另一个 Product。
```

## 需求变化后同步已有任务

来源：Godot 项目开发 → 任务规划 → 需求变化后同步已有任务

```text
请根据以下文档变化增量同步已有 Feature 与 测试登记表。
变化来源：${1:Product、专业规格或 Project Rules 文件、相关提交或明确变化范围}

读取项目规则、Product 执行顺序和相关差异，使用 $feature-sync。只处理当前或已有任务受到的实际影响，包括依赖、AC 和测试映射；保留 Feature ID、已完成历史和变化来源，不整份重置。

后续尚未拆分的 Product，仅更新需求不会触发 Feature 生成；若它改变了现有任务依赖的契约，处理受影响的已有工作。仅有后续 Product 文档变化且不影响已有任务时，说明其拆分暂缓即可。轮到它时由 $feature-plan 读取当时完整需求，不因变化早于同步锚点而遗漏，也不为已经规划的内容重复生成 Feature。

按 methodology/11-specialist-workflows.md 追查主来源、AC/设计引用和共享规格的实际适用范围，不只找直接引用的一项任务。新纳入的专业来源不能继承旧 synced_at_commit 的覆盖结论；即使文档早于锚点，也要核对历史规划是否吸收。无法证明时按已有授权对受影响的已规划范围做当前文档对齐，说明历史未知，不伪造基线或增加来源收据。

报告对照本次变化及实际下游影响，列出 Product/专业要求位置与含义、Feature/AC、测试处理、遗漏与待完成项；写入后刷新实际关系。后续未拆分范围简述即可，不展开全项目审核；计划同步不代表实现或测试已完成。

涉及失效测试时，按 methodology/08-testing-strategy.md 的“Requirement changes and stale tests”核对实际代码并规划清理，不能只退役登记记录。本次只将已批准的必要清理纳入负责的 Feature，不修改测试代码或声称清理完成。

普通下游回归归入负责当前变更的 Feature 的验证范围，保持现有测试归属；仅复跑有效测试不另建 Feature。独立实现、修复或明确单独交付的工作才新增任务，必需验证不能通过备注取消。

对新增、拆分、合并、替代或测试退役按现有演进规则说明原因和影响。按现有授权同步并检查引用完整性，报告实际变化和暂缓范围；本次不执行 Feature。
```
