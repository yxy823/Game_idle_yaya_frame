```text
## 背景与入口条件

项目尚无正式 Product，本次形成首份可用需求。

## 范围

形成第一份正式 Product，明确当前模块边界；本入口不同时规划 Feature。

## 决策边界与授权

使用 product-init-elicitor 澄清核心行为，再由 product-author 保存确认内容；同类关键问题集中询问并给推荐。

## 约束

遵循项目 AGENTS.md 和 methodology/01-product-doc-structure.md，不把未确认设想写成确定需求。

## 输出与交付

保存首份正式 Product，说明当前模块范围及未决项。

## 验证要求

核对已确认行为、边界和来源覆盖，确保需求足以指导当前模块的后续规划。

## 完成条件

第一份 Product 已确认并保存，当前模块边界与未决项清楚。

## 停止与异常处理

尚缺影响需求定稿的决定时报告缺口；来源定稿后若已有明确后续规划授权，衔接对应入口继续，不重复批准。
```

## 已有模块的玩法要求变了，需要更新需求

来源：Godot 项目开发 → 需求设计 → 已有模块的玩法要求变了，需要更新需求

```text
## 目标

请更新已有模块的确认玩法要求。

## 背景与入口条件

已有正式 Product，需要修改已确认的玩家行为。

## 范围

更新已有模块的确认玩法要求及来源关系，不直接实现或改写历史验收。

## 输入与事实来源

${1:所属模块、原要求、新决定、影响范围}

对照原正式 Product、新决定及实际受影响范围。

## 决策边界与授权

product-spec-elicitor 只澄清必要差异，product-author 保存确认行为；有效决定不重复批准。

## 约束

遵循项目 AGENTS.md 的需求变更路由；不把偏离既有要求的 Bug 写成新需求，不改历史 AC 掩盖失败。

## 输出与交付

保存并提交来源变更，说明受影响计划及对应同步入口。

## 验证要求

核对新要求、原要求差异和消费者影响，完成来源所需检查。

## 完成条件

新要求已成为可核实的正式来源，影响范围和后续同步入口明确。
```
