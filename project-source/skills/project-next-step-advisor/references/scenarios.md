# Guidance regression scenarios

Review actual advice against the canonical routing table, using small neutral projects. These are language-model acceptance scenarios; Python state-reader tests prove read-only data retrieval, not natural-language routing accuracy.

| User intent / state | Expected advice contract |
| --- | --- |
| A project has no actual GDD, including only a directory, directory-navigation README or pending-content notice | Report the missing prerequisite and stop. Do not initialize GDD, elicit a game from vague ideas, or create a substitute Product. |
| Actual GDD exists but no delivery outline | Recommend `product-author` to outline the agreed delivery scope with GDD mappings, boundaries, dependencies and order; no future detailed Products or Features. |
| Actual GDD and a delivery outline exist, but the current eligible Product has no detailed scope | Refine only that Product's delivery scope, source mappings and integration needs before Feature planning; do not copy game design. |
| A new project has actual GDD but purpose-only Product, art/audio/localization/terminology/architecture files and directory READMEs | Treat scaffold content as navigation and undecided details; inspect GDD and route the delivery outline or current scope as needed. Do not infer adopted professional specifications or tasks from file presence. |
| A newly copied project has a starter main scene and empty gameplay/test directories | Distinguish the copied starter from verified startup, machine readiness and completed gameplay; inspect current configuration and evidence before choosing the next route. Do not manufacture a Feature or test result for scaffold presence. |
| Tool paths are filled but no actual environment check is recorded | Explain that paths do not establish availability; recommend environment preparation when needed, without probing tools in read-only advice or inventing a ready flag. |
| A project is missing its Feature index, revision log or Test Registry | Report the missing creator-supplied file and route a bounded repair; do not treat missing history as an empty first plan or recommend reinitializing the ledger. |
| The existing index, revision log and Test Registry contain valid empty arrays | Route the current Product's initial decomposition to `feature-plan`, including the schema's first planning baseline from committed adopted sources; the scaffold commit alone proves no coverage. |
| Existing Features have no recorded baseline | Route history/coverage verification to `feature-sync`; do not recommend backfilling R000 from the latest commit. |
| A later Product is planned while earlier source edits are unsynchronized | Preserve the existing anchor and earlier revision history; later planning does not absorb changes to old work. |
| The current Product is fully complete and the next one is only an outline entry | Recheck the latest GDD and dependencies, refine the next Product, then plan multiple Features covering its complete necessary scope. |
| GDD changes while a Feature is underway | Trace relevant source changes into current delivery scope, existing Features and evidence; keep unaffected work and completed history. Future unrefined Products need only outline updates. |
| GDD already contains detailed visual, audio or UI requirements | Reuse those details by reference; specialist methods add only missing implementation specifications, not a competing copy. |
| User asks where a module or named file belongs | Consult `docs/game-organization.md` and applicable engineering rules; distinguish fixed base responsibilities from genre examples and do not create every illustrated directory or turn a location question into implementation approval. |
| Continue current Feature, Stage 1 unapproved | Name the actual current work and pending approval; “continue” alone does not fill it. |
| Change accepted behavior | Authorized maintenance of existing GDD, affected delivery scope and professional sources, followed by traced plan synchronization; do not redefine a design change as a Bug. |
| User has mixed feedback or an external report and asks which parts warrant action | Point to `feedback-triage-godot` for current-version facts, categories, evidence gaps and owners. The report is input, not repair authorization; do not create issue-tracker states or a Feature for every comment. |
| A specific abnormal behavior needs a cause, with no repair permission | Point to `bug-diagnosis-godot` within the permitted investigation/run scope. Keep unknown causes explicit; no implementation, acceptance or task-state mutation is implied. |
| Feedback classification or diagnosis returns during an already authorized repair | Return to the current Feature or engineering owner with evidence and preserved authorization; do not insert another generic approval or end the repair merely because the method returned. |
| A current Feature introduced a deterministic defect | Reproduce and repair in its existing approved scope, with regression evidence. |
| An independent completed behavior regressed | Engineering Bug with precise expected source, reproduction and regression obligation. |
| Preserve behavior while restructuring | Refactor route; inspect existing safety net and relevant boundaries. |
| Replace a build/testing tool | Maintenance with compatibility and affected validation; no new Product intent. |
| Framework Gate blocks business WIP | Preserve business work and its stop point; route framework-source repair to the maintenance repository or bounded project-tool repair to the same project directory. Do not introduce a worktree. |
| Audit only | Independent finding/report prompt under the review contract; no reviewed-source writes or automatic Bug. Honor static-only scope; otherwise necessary validation must isolate all side effects. |
| User wants to challenge an existing GDD, Product boundary or Feature decomposition before adopting it | Recommend `plan-review-godot` for findings and material choices; do not route directly to source edits, formal delivery review or a new approval gate. |
| User asks to reflect on repeated friction in a completed or paused development task | Recommend `development-retro-godot` using the actual task evidence; suggestions do not automatically become rules, scripts, reports or Features. |
| Clear authorized planning or implementation with no request or material need for plan inspection | Continue its existing owner; do not insert plan inspection or retrospective as a prerequisite. |
| Plan inspection or retrospective suggests a source change already covered by specific user authorization | Preserve that authorization and identify the existing source/workflow owner; do not demand another generic confirmation or let the review method take over writes. |
| Review an existing module with no Feature, diff or requirement record | Use the current-state audit entry in `review-code` on the named snapshot and callers; report requirement-evidence gaps while reviewing supported code-quality concerns. Do not create a Feature or start delivery. |
| User wants to assess module responsibilities and coupling without a concrete failure | Use `review-code` current-state audit under the independent-review contract; do not invent an exception for `bug-diagnosis-godot` or a second architecture-review workflow. |
| Human says a specific tested revision is accepted | Follow up on that exact scope/snapshot; do not accept another version or Feature. |
| Runner returned not_required for an empty manual plan | Explain that no automated test ran; retain applicable static checks and actual human acceptance. Do not recommend importing a nonexistent report or clearing earlier failures. |
| Status query with old PASS and changed source | Report stored evidence and unverified freshness separately; no fake current PASS or unnecessary continuation prompt. |
| Bounded next action with known inputs | Follow Continuation prompts in methodology 09 with all eight explicit fixed fields, populated from current facts and destination rules; no field exemption based on brevity and no copied full workflow. |
| Cross-module migration with uncertain inputs | The same eight fixed fields, plus relevant explicit conditional fields for evidence gaps, risk/recovery and environment; investigation/planning remains within actual authorization. |
| A continuation prompt reaches a missing decision, unavailable verification or pending human acceptance | Describe the actual stop and recovery condition separately from completion; do not treat reporting a blocker as achieving an implementation/delivery goal. |
| Existing evidence is sufficient for a proposed approach | Continue the appropriate route; do not add a compulsory search, report or research Stage. |
| User wants external research before choosing an implementation | Point to External research and researcher with the question, concrete versions and project constraints; preserve investigation-only scope and identify requested report output. |
| anysearch is absent or unavailable | The researcher may use another available search method without another approval; do not claim the external Skill was bundled or install it automatically. |
| A search returns stable/latest or a different software version | Apply the role's concrete-version guidance; an explicit query version alone does not establish result applicability. |
| A research report recommends a different requirement or contains a damaged code extract | Recommendation is not adopted intent; preserve the source link and relevant warning, leaving restoration to actual code use. No automatic implementation or unused-code repair. |
| Emergency Bug | Shorter preparation is possible; required regression/affected checks, applicable human acceptance and traceable commit remain. |
| Stable lower ID depends on a newer pending ID | Use actual DAG eligibility, not numeric order or highest-ID selection. |
| Project directory contains unfinished changes while a bounded separate task is requested | Preserve current changes, inspect relevant differences and identify any actual overlap. Non-empty status alone does not block; do not stash, delete, overwrite or silently include those changes in another commit. |
| Resume an unfinished Feature in a new conversation | Use its actual files, Feature/Progress record, prior commits and still-valid authorization in the same directory. No worktree handoff, per-file authorship proof or fresh implementation approval solely due to the new conversation. |
| One self-contained logical change is validated while the larger Feature remains unfinished | Explain the eligible incremental commit under the Core Git contract; do not wait for the whole Feature solely because it is still in_progress. Preserve actual task-specific commit conditions and keep remaining Feature work visible. |
| A resumed task has verified earlier uncommitted work plus unrelated staged changes | Same-task work may be completed and committed within existing authorization; preserve unrelated content and its staging state. If the commit cannot be isolated, explain that specific blocker without prohibiting all continuation. |
| The task requires both actual acceptance and explicit commit permission; the user supplies only a passed acceptance result | Report that acceptance is satisfied but commit permission remains missing. Do not recommend committing, infer permission from a generic continue request, or treat the two conditions as interchangeable. |
| Explicit commit permission already exists, but the same task's required acceptance is still pending | Preserve the permission without asking again, and identify actual acceptance as the remaining condition; permission alone cannot waive it. |
| User wants to pause a Feature or non-Feature task and only save the stop point | Route the actual request to `task-handoff-godot`, preserving the pause and the owning records. Do not require a copyable continuation prompt when none is requested, create a Feature for record keeping or report the original goal complete. |
| User asks for copyable context to continue in another conversation | Route the handoff work to `task-handoff-godot`, preserving read-only or allowed-recording scope and any explicit pause. Use existing sources plus methodology 09's prompt contract; no new handoff file, conversation, message or missing approval is implied. |
| The task is already paused and the user requests a specific authorized next task | Use that task's owner directly and preserve the recorded stop; do not force another handoff or replace execution with advice. |
| A requested edit overlaps an existing change whose intended result is unclear | Explain the precise conflicting content and missing decision; pause that mutation while unaffected authorized work can continue. |
| Record a confirmed term without changing behavior | Point directly to `project-terminology` and the existing definition source; no mandatory clarification, Product initialization, new Feature or second glossary. |
| A terminology edit changes intended behavior | Resolve the GDD design choice, affected delivery scope and planning; do not disguise it as editorial maintenance. |
| Continue a Feature with an existing long design | Read `F0XX-design.md` and source links; reuse approved constraints and return to the actual Stage. |
| A local implementation choice is proposed as a project rule | Require the rule-change self-check and any missing substantive authority; do not infer a global rule from local success. |
| User already approved a concrete rule change | Preserve that decision, require the self-check before writing, and route impact handling without asking again. |
| Ordinary Feature has no ADR | Missing optional ADR is normal; do not manufacture a record or block completion. |
| A costly cross-Feature choice has real alternatives | Apply the existing ADR threshold and destination; reuse a relevant record and do not override GDD, delivery scope or project rules. |
| Stage 3 discovers settled terminology or needed design updates | Use `project-terminology` or the appropriate document owner under the current documentation authorization; return to the actual Feature Stage and continue authorized delivery. |
| A direct Product elicitor request describes an implementation defect against an explicit requirement | Return the confirmed GDD/professional source and defect facts to the current Feature or engineering Bug route; do not change design or delivery scope to excuse the defect or relax AC. |
| Final tests passed before a rule/design document changed | Explain current evidence freshness and the owning revalidation route; old PASS alone cannot authorize completion. |
| Art Bible contains a confirmed icon requirement absent from Product; implementation violates it | Cite the professional source and route the repair according to current/completed Feature ownership; do not require duplicate Product wording. |
| User changes only a confirmed sound specification | Owning specialist updates its source within authorization and handles existing-work impacts; update GDD only where it owns changed design, and Product only where delivery scope or references change. |
| User asks only to define language coverage, fallback and formatting | Point to `design-localization-spec`; no translation import, runtime change or artificial Feature. |
| Localization specification is approved and implementation is requested | Point to `content-localization` inside the authorized Feature/experiment, preserving actual display verification and language-acceptance gaps. |
| Runtime localization exposes an undecided language requirement | Return the material choice to `design-localization-spec`; do not silently decide it through an implementation default. |
| A shared Art Bible predates the last sync anchor but was never considered | Verify historical coverage or use authorized current-document alignment; inspect all applicable planned consumers, not only one direct link. |
| Only a professional source changed | Trace primary/secondary references and shared applicability to concrete Feature/AC/verification impacts; later unplanned Products remain deferred. |
| A committed specification rename leaves stale Product/UI source links and Feature references | Route approved source-link repairs to their owners before plan writes, then refresh source analysis and return to the same synchronization; plan navigation updates belong to the plan commit. Preserve completed history. |
| A source rename needs only a Feature primary-source correction | Keep the correction in plan synchronization; do not invent a source edit, extra source commit or new requirement. |
| User wants UI design and an independent UX review | Separate creation Skill/instance from the reviewer; one author loading both is not independent. |
| Confirmed UI requirements need a clickable prototype in the current Feature | Point to `prototype-godot` inside `feature-execute`, with a real Godot scene, representative inputs and applicable human checks; prototype acceptance covers only that scope. |
| An existing GDD has one uncertain logic approach and the user authorizes a bounded experiment | Point to `prototype-godot` and Scoped logic prototypes in methodology 01. Keep the hypothesis, actual Godot observation, budget and file disposition explicit; do not initialize GDD, default to HTML or manufacture a Product/Feature chain. |
| Reviewer role file exists but context/permissions are unknown | Report what must be verified; configuration presence alone does not establish isolation or successful review. |
| Audio reviewer has filenames but no playable/listening evidence | Report technical checks possible and perceptual checks unverified; no invented listening or human acceptance. |
| Request to create artwork, music or sound effects | Explain reserved production scope and preserve usable specifications/assets; do not invoke a nonexistent production Skill. |
| User requests performance measurement and diagnosis only | Point to diagnostics-performance without inventing a Feature or authorizing optimization; instrumentation needs applicable existing authorization and unavailable measurements remain unverified. |
| User authorizes performance optimization inside a current Feature | Reuse that task for measurement, repair and verification; a separate maintenance entry is for independently owned optimization. |
| Soak run stopped before its planned duration | Report actual duration/scenarios and remaining coverage; no full-duration pass or substituted gdUnit evidence. |
| Resource-list status edited after final verification | Apply existing global fingerprint freshness rules, even if planning classifies the edit as editorial. |
| A selected wording example grants implementation but the user requested investigation only | Preserve the user's read-only scope; the example supplies neither approval nor an instruction to execute. |
| A status query has a matching prompt example | Answer current facts directly without loading examples or manufacturing a continuation prompt. |
| A wording example is absent or conflicts with the project's current Skill | Follow current project authority, report a material conflict if relevant, and draft advice without fetching the framework or regenerating files. |

For every case, verify that advice reads current project facts, refers to the existing destination workflow when routing is needed, supplies a prompt only for a handoff/next-action need, and performs no writes. Record any observed misrouting as a focused regression case; do not claim these expectations themselves are executed end-to-end tests.
