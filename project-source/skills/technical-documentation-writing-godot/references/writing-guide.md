# 写作指南

改善当前 Godot 项目的说明，但不改变文档的含义和它授予的权限。按读者要完成的事决定需要多少背景和细节。

## 确定文档契约

从当前任务确认要交付的结果和受影响的文件。修改前先读要改的现有正文和它的事实来源。已经定下的决定直接复用；只在缺口会改变交付结果时才提问。从代码观察到的是当前行为，不等于批准修改预定的游戏规则。

下表的路径属于目标项目，不属于源框架或其他 Skill 包。只读取与本次所写文档有关的契约，并复用当前上下文已有的内容：

| 正在编写的文档 | 内容与约束的来源 |
| --- | --- |
| 项目 README 或工具说明 | 现有入口页、实际的命令或编辑器界面，以及项目本地的配置和使用约定 |
| 已有的 GDD 或 Product 说明 | `yaya/methodology/01-product-doc-structure.md`；输出 Product 时，另看 `yaya/methodology/templates/` 下的当前模板 |
| Feature 记录或设计说明 | `yaya/methodology/02-feature-list-schema.md`，以及受影响 Feature 的实际来源和记录 |
| 架构或技术决策记录 | `yaya/methodology/10-architecture-overview.md`，以及已实现的职责和已采纳的决策 |
| 可复用的项目经验知识 | `docs/knowledge/README.md`、所属主题和原任务的证据 |
| 调研或验证记录 | `yaya/methodology/09-records-reports-and-handoff.md`、实际证据，以及所属任务对调研或验证的约定 |

遵循目标项目的 `AGENTS.md`，长期保存的产出使用项目配置的 `document_language` 编写。确定语言或渲染模板时，使用 `yaya/methodology/05-document-language.md`。

- 项目标识符和机器可读结构不随语言改变形式；沿用项目的术语和模板。
- 缺少的设计、批准或证据仍是所属任务的缺口，本写作方法不能补上。
- 尤其是，它不会根据一个想法创建 GDD，也不会从代码反推出已批准的游戏设计。

保留模板要求的栏目、固定路径、ID、字段名、机器可读结构和历史事实。可选大纲可以省略无关栏目；Product 的必填栏目即使答案是“不适用”也要保留。是否保留由文档所属的规范决定，不凭“页面越短越好”的一般偏好。

## 按需读取其他参考

- 涉及多份文档、归属不清、命名、导航或重复说明时，读[文档结构与归属](document-structure.md)。
- 编写操作说明、复现步骤或验证指南时，读[操作说明与验证指南](procedure-writing.md)。
- 局部措辞修正只处理当前页面和必要的引用，不意味着要迁移目录或改写整个仓库。

## 把项目讲清楚

文档结构允许时，开头先给出读者眼下的目的或结论。规则的解释、适用范围和重要的注意事项放在一起。前提条件或副作用紧挨着受它影响的动作。

长期维护的文档只写当前有效的要求和影响使用的缺口。调查时看过的内容、未采用方案的细节和逐次检查经过不进入正文，只保留影响当前选择的结论；需要保存过程时，使用已有的报告或任务记录。

GDD、专业规格、架构、方法规范、规则和 Skill 不写实现或验证的进度，例如“尚未实现”“还没验证”“目前只接了……”。因为进度一变这类句子就过时，链接检查也查不出来。进度写在 `docs/progress.md` 或任务记录里，长期文档只写目标行为、契约和职责。设计层面还没定下的内容不在此列：可以标成“待定”“工作假设”或占位值，并链接 `docs/gdd/open-questions.md` 中对应的开放问题。

场景、资源、信号、功能和领域概念沿用项目已有的名称。打包场景（packed scene）、实例化后的节点和它的所有者，在区分有意义时写清楚；普通行文不另造一套术语。要改变玩法含义，回到它的设计所属文档处理。

选择能让关系一目了然的形式：

- 推理和后果用段落，彼此独立的条件用列表，真实存在先后依赖的操作用编号步骤。
- 各行回答同一组问题时用表格，例如工具选项的用途和效果；一列回答一个主要问题。理由、调查经过和多个例外需要展开时，移到相关段落，不把整段说明塞进单元格。
- 图示用于说明运行流程或职责边界，前提是这能让说明更清楚。流程有分支、回路或失败后的返回时，用 Mermaid 图画出走向，表格只说明每一步的产出，因为逐行排列的表格表达不了“仅……时才有这一步”和“失败后回到哪一步”；线性步骤和逐项对照不画图。图示解释的是已核实的关系，不是重新设计这些关系的依据。

句子层面遵循以下规则：

- **一句只做一件事。** 每句只写一个动作、条件或事实。一句话同时包含动作、条件和例外，且长度达到约 40 个英文单词（中文约 100 字）时，拆成短句或列表。命令、路径和标识符不计入长度。
- **通用提醒只讲一次。** 通用提醒在它的所属位置完整解释一次，其他位置只在能防止真实错误时保留短提醒，例如紧挨着有破坏性的工具选项。链接的放置与正文概括遵循文档结构参考的[去掉重复正文，保留有用的上下文](document-structure.md#去掉重复正文保留有用的上下文)。
- **用具体措辞，不用公文腔和压缩词。** 写出实际的文件、字段、Skill、小节或动作，不用“所属契约”“长期”“这项工作”这类抽象名词。写完整的句子（英文要带冠词），不写电报式短语；三个及以上的并列选项写成“A、B 或 C”，不用斜杠串联。
- **不用含糊词、空动词和包装动词。** 用数字、名称或条件代替含糊的程度词，写出实际动作，不用空动词和包装动词，例如写“压缩日志”，不写“对日志进行压缩处理”；要避免的写法由[措辞检查](#措辞检查)列出。不知道数字时只删掉空的程度词，不编造数字。“开箱即用”“无缝”这类套话同样换成具体做了什么。
- **写出主语和句间关系。** 主语换了就写出来，“它”“这”“该”只在指代唯一时使用；因果、条件和转折用“因为”“所以”“如果”“但”写明。一个名词前最多两个“的”，修饰更多时拆成两句。
- **一个概念只用一个词。** 同一个对象或动作全文用同一个词，不为读起来有变化而换说法；项目概念用 `docs/terminology.md` 中的写法。
- **链接文字用目标标题。** 带锚点的链接，链接文字用锚点所在章节的实际标题；只链到文件、不带锚点的链接，用该文件的一级标题，`yaya/methodology/` 下的方法论文件可以去掉“NN · ”编号。页内锚点链接同样适用。不另起“X规范”“X约定”“X流程”之类的叫法，因为按字面执行的 Agent 会照着链接文字去找标题。需要说明标题属于哪份文件时，把文件说明写在链接外面，例如 `08 号规范的[测试影响评估](…)`，链接文字本身仍是标题。只链到文件、不带锚点的链接，链接文字可以逐字写目标的 Skill 名（可带 `$`）、文件名或目录名，例如 `[$design-gdd](…/design-gdd/SKILL.md)`、`[02-feature-list-schema.md](…)`，因为 Agent 按 Skill 名调用 Skill；带锚点的链接仍用章节标题。页面顶部只由链接和“·”组成的导航行可以用缩写。[check-link-text.py](../../../../yaya/tools/README.md#check-link-textpy) 列出不符合的链接。
- **要求的强弱用固定的词。** “必须”“不得”表示强制要求和禁止；“可以”“不必”表示允许和不要求；“默认”“优先”表示没有另行指定时的选择，并写明何时可以改变。“能”只表示能力，“需要”只表示依赖或缺少，都不表示要求。不用“应”“应该”“宜”“务必”“尽量”“最好”“建议”表达要求，按实际强度改用上面的词；其中规则文件里的“应”“宜”“务必”由[措辞检查](#措辞检查)拦截。操作步骤用祈使句，不加这些词；直接写出的动作本身就是要求。`yaya/agent-rules/` 和 `docs/project-rules.md` 的条目另按[规则的写法](../../../../yaya/agent-rules/00-core/rule-precedence-and-routing.md#规则的写法)：条目默认是要遵守的要求，推荐的做法写成“建议：”开头的条目。
- **只有真实的类别与成员关系才嵌套列表。** 列表默认只有一层。只有每个父项是一个类别、子项是它的成员时才嵌套；其他情况用段落、编号步骤或表格。

写出带条件的具体陈述。例如在验证记录里写“面板正常”是不够的。如果确实观察过，就写清打开了哪个面板、用了什么输入、显示了什么结果，以及还有哪些状态没有覆盖。不要把示例措辞写成交互确实运行过的说法。

Markdown 段落保持自然书写，不按固定宽度手工折行。列表、表格、代码、图示和机器可读模板中有意义的结构要保留。这里示例使用的语言不决定项目的输出语言。

## 措辞检查

[check-wording.py](../../../../yaya/tools/README.md#check-wordingpy)按[配置文件](../../../../yaya/tools/checks/wording-check.json)中的检查项找出要避免的写法。配置是这些写法的唯一清单，每项写明级别、适用范围（规则文件或全部文档）和推荐写法，并用一条正则写出要找的写法和例外，例如“应”不包括“应用”“对应”。“规则文件”包括哪些文件，见措辞检查的说明。

级别有两种：

- **硬性**：在适用范围内出现时检查失败，提交钩子拒绝提交。
- **待复核**：只列出位置，由作者看上下文决定是否改写，不影响退出码和提交。

检查项分三类：

- **表达要求却说不清强度的词**，例如“应”“宜”“务必”。规则文件中这类词是硬性的；用“建议”表达要求的写法待复核。
- **说不清范围或数量的词**，例如“尽量”“适当”“若干”，待复核。
- **固定的空洞写法**，例如“进行处理”“做出决定”，待复核。

用下面的命令查看完整清单：

```powershell
python -B yaya/tools/checks/check-wording.py --list
```

在正文中举例这些写法时，放进引号或行内代码。

## 核对并完成写作任务

对照来源检查改写后的说明：需求仍是需求，提议仍是提议，结果只陈述证据能支持的内容。保留预期行为、当前实现和实际执行观察三者之间的区别。

检查受影响的链接、小节锚点、标识符和命令示例。已授权的移动改变了路径时，先处理该路径的实际读者和读取它的工具，再完成修改。按目标项目的规则使用项目里已有的链接、格式或构建检查；不要引入框架的命令，也不要声称运行过没有运行的检查。

关于运行结果的文档需要对应的证据。单纯的措辞或导航修改本身不需要启动 Godot、重新生成项目或重放未改变的测试。来源或契约的变化是否让之前的验证失效，由所属工作流判断。无法完成的检查要明确写出。

交付改好的文档、这些修改为什么有帮助、实际做过的核对，以及重要的缺口。只要求分析时，交付发现，不写入文件。完成后返回调用方；Skill 返回不会结束它所在的已授权任务（methodology 03 的 **授权与续接**）。
