# UI 规格

归属、授权和来源影响按 `yaya/methodology/11-specialist-workflows.md` 执行。该文件的 **UI 文档边界** 章节规定了界面文件和组件文件，以及共享控件怎样迁到 `docs/ui/components/<component-key>-design.md`。同一文件的 **留在 GDD 中的内容** 说明了怎样把界面规格从 GDD 中移出。在授权范围内直接写入，使用配置的 `document_language`；只要求讨论时，返回方案。

GDD 负责玩家行为，Product 为交付链接已采用的要求。GDD 的规则和目标直接引用，不要复制。保持受保护的来源输入原样。`product-author` 不代为保存这份规格。

阅读本次涉及的 GDD 目标和操作、Product 交付范围、当前界面、适用的 Art Bible、显示与输入条件，以及外部提供的代表性资源。复用已定的选择；只就会实质改变布局或交互的缺口提问。共享视觉风格属于 `design-art-direction`，文件级要求属于 `design-visual-asset-spec`，行为变化通过 `design-gdd` 回到 GDD。

确定输出名称之前，先按 **UI 文档边界** 选定界面文档或共享控件文档。新建、改名或删除界面规格或组件规格，或者改变导航中显示的用途、关联 Product 或组件使用方时，阅读 `docs/ui/README.md`，并在同一个已授权的修改中更新受影响的条目。不要把这次更新变成对整个目录的审查。

## 有用的规格

说明层级、分组和反馈怎样服务于当前的用户目标。布局用[草稿界面](#草稿界面)讨论，规格写明采纳的元素、分组、区域比例和状态差异，并链接所依据的草稿目录。

交互影响游戏规则或业务状态时，使用 `docs/game-organization.md` 中的职责模型。链接起决定作用的游戏规则，区分玩家发出的操作请求和它被接受或拒绝的结果，并描述对应的显示。悬停、焦点、面板展开和显示过渡可以作为 UI 内部状态。界面上显示的“买得起”提示不能代替逻辑中的购买判定；实际的连接属于实现。

每个状态的主操作都要清楚。需要时写明焦点、禁用、错误、空和密集状态，以及输入导航；不要求设计未来所有可能的屏幕。

区分已确认的显示和可读性约束与试用值。写明周围的屏幕上下文、视口和缩放条件（项目还没有确定显示基线时，先按 `yaya/agent-rules/40-project-config/subsystem-settings.md` 的“视口、窗口与拉伸”确定）、代表性的文本和资源引用、源图尺寸与可见主体尺寸的区别，以及需要在运行时评估的未决问题。节点属性和顺手的微调留在实现中。

布局、尺寸和状态反馈的默认做法见[界面布局与尺寸](references/ui-layout-and-sizing.md)和[界面反馈与输入](references/ui-feedback-and-input.md)，字号和数字显示见[界面字体与数字](../design-art-direction/references/ui-type-and-numbers.md)；规格采用了不同的做法时写明。

普通控件状态写在这里。一次完整的游戏表现（例如领取奖励）属于 `design-game-presentation`。按 methodology 11 的 **游戏表现文档** 的说明，从 UI 文档链接它；UI 文档不能代替表现文档中的采用关系或实现引用。

## 草稿界面

草稿界面是一个 Godot 场景，用写死的假数据摆出界面，供用户和 Agent 讨论布局、比例和对齐。用户要求讨论界面布局时，Agent 直接创建草稿界面，不再画文字线框图。

- **位置**：`dev/drafts/ui/<interface>-<YYYYMMDD>/`，日期是创建当天。`dev/` 在正式导出时整体排除。同一界面重新讨论时新建目录，旧目录保留，作为历史参考。同日新开一轮时，目录名追加 `-<N>`。`N` 从 2 开始，取该界面当日已有编号的最大值加 1；继续同一轮时沿用原目录。
- **内容**：只有场景、节点和写在节点属性里的假数据，不写脚本，也不接游戏状态，所以它不是骨架，也不是 `dev/` 中的假系统。视口、主题和字体用项目当前的设定；项目还没有确定显示基线时，先按 `yaya/agent-rules/40-project-config/subsystem-settings.md` 的“视口、窗口与拉伸”定下来，再建草稿，否则草稿里定下的比例在正式窗口中不一定成立。需要比较空、密集、长文本等状态时，每个状态做一个场景。
- **说明文件**：目录里放 `README.md`，按模板 [ui-draft-readme.md.tmpl](../../../yaya/methodology/templates/ui-draft-readme.md.tmpl) 写明创建日期、依据、讨论与不讨论的内容、场景、结论和写入去向。过不过期按依据链接判断：依据的设计改过，或 UI 规格已改为依据另一份草稿，这份草稿就过期了。
- **查看**：按 `dev/debug/README.md` 的“启动”三行命令运行，把最后一行的场景路径换成草稿场景；也可以在编辑器中打开草稿场景按 F6。

草稿界面只讨论下表左栏。右栏的内容依赖真实数据、真实资源或手感，在草稿里定不下来：

| 草稿界面讨论 | 留到骨架和调试台的视觉决策 |
| --- | --- |
| 有哪些元素、分组、层级和主操作 | 具体像素、间距和字号 |
| 大致区域和比例，例如“左侧列表约占三分之一” | 配色细节、动画时长、反馈强度 |
| 状态差异：空、密集、禁用 | 真实数值和长文本会不会溢出 |
| 对齐方式和阅读顺序 | 手感，例如点击反馈是否够明显 |

用户开始反复调整右栏的内容时，Agent 主动提醒一次：说明这一项在草稿里定不下来，把它写进 UI 规格中“需要在运行时评估的未决问题”，然后建议结束这一轮草稿讨论。用户坚持继续时，照常讨论，不再重复提醒。

## 界面任务

每份界面规格都有“界面任务”小节，按用户想做的事列出这个界面要支持的任务。它是 `yaya/methodology/03-execute-loop.md` 的 [Stage 4 · 自动验证与人工验收清单](../../../yaya/methodology/03-execute-loop.md#stage-4--自动验证与人工验收清单) 作者侧试用和 review-ux 的[按界面任务试用](../review-ux/SKILL.md#按界面任务试用)的输入。

- **选哪些任务**：覆盖经常做的、会改动数据或不可逆的、第一次使用必经的任务；不按控件逐个罗列。
- **每个任务写**：目标（用用户自己的话）、起点（从哪个界面、什么状态开始）、步骤（每步一个鼠标或键盘操作）、每步预期看到的反馈、怎样算完成，以及试用要点（容易误解的词、相邻的危险操作、失败或空状态）。
- **要求**：任何一步需要用户懂系统内部（目录、文件、引擎报错、内部字段名）才能完成，都是设计缺陷，在规格中改掉，不写进步骤。界面任务涉及的游戏规则链接 GDD，不复制。
- **何时更新**：界面的布局、入口或流程变化时，同步修改受影响的任务。

调试台自己的界面任务写在 `dev/debug/_shared/usage-scenarios.md`，不写进 UI 规格。

## 交接

新界面按 `yaya/methodology/13-debug-console-and-validation.md` 的[界面的开发顺序](../../../yaya/methodology/13-debug-console-and-validation.md#界面的开发顺序)推进：先做最小的真实骨架，再在调试台做视觉决策，最后补完整逻辑。规格为这些 Feature 提供问题、输入和界面任务。草稿界面只用于讨论布局，不创建游戏场景，也不能证明可用性；骨架在 `game/<对象>/` 中搭建，可以复制草稿的节点布局。

视觉资源章节与 `design-visual-asset-spec` 协调，音频要求与 `design-audio-asset-spec` 协调。所属章节由 `yaya/methodology/11-specialist-workflows.md` 的 **资源需求与交接** 选定；不要另建资源清单。颜色、字号、间距等样式引用设计 token 的语义值和主题类型变体（`game/shared/tuning/ui/`），只有这个界面用的样式写明属于本界面；放置规则见 `yaya/agent-rules/20-scenes/ui-and-scripts.md` 的“布局”。用户在调试台采纳的设定保存在调参资源中，规格链接它，不抄写数值；采纳带来的布局或交互变化更新 UI 规格，行为变化通过 `design-gdd` 回到 GDD。

返回来源路径、已确认的决定、尚未决定的问题，以及本次涉及的规划和视觉决策输入。正式的 UX 审核在另一个实例中使用 `review-ux`；本 Skill 不能给出人工验收。

返回调用方；Skill 返回不会结束它所在的已授权任务（methodology 03 的 **授权与续接**）。
