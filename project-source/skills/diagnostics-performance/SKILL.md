# 性能剖析

遵循 `yaya/methodology/11-specialist-workflows.md` 的 **设计、制作、接入与审核** 和 **定稿与证据**，尤其是后者关于证据局限的要求；原始数据按 `yaya/methodology/09-records-reports-and-handoff.md` 的 **报告与清理** 保存。从任务中弄清实际的症状和负载：帧时间尖峰、启动/加载、模拟吞吐量、内存或其他需要测量的问题。有已批准的预算时使用它；不要编造通过阈值。

记录下列条件：

- 实际的版本及未提交改动状态；
- Godot 版本；
- 机器；
- 运行模式；
- 显示条件；
- 负载；
- 测量工具。

选择有代表性的稳定场景和过渡场景；区分预热、导入/编辑器工作和稳定运行阶段。收集分布、尖峰和趋势，不要只依赖平均 FPS。保留原始采集数据和比较条件。

报告数字之前，核对这几项：

- **工作确实发生了**：计时区间内执行了被测的工作。测绘制开销时，无头模式不渲染，隐藏或被剔除的节点不绘制，测出的数字与被测问题无关。测逻辑或物理开销时，隐藏不等于停止处理，分别确认处理回调是否开启、节点是否在场景树中、被测方法是否真的被调用。
- **出错的运行单独计数**：加载失败、提前退出或报错的运行往往更快，不混进结果。
- **比较时交替运行**：两个版本按 A、B、A、B 交替运行，报告中位数和范围；差距小于各自的波动范围时，结论写成没有可测出的差别。
- **换算成整体占比**：局部提速按它在整帧时间或整个流程中所占的比例下结论；只占 5% 的部分，再快也只能让整体快约 5%。

把观察和因果解释分开。在已授权的实验范围内，每次检验一个有依据的假设；只有缺少信号导致无法区分原因时，才请求 [diagnostics-instrumentation](../diagnostics-instrumentation/SKILL.md)。临时埋点会改变被测量的版本，也可能干扰测量结果。没有证据时，不要把编辑器或调试模式下的测量推广到交付配置。

返回瓶颈的证据、置信度的局限和按优先级排列的修复建议。已获授权的修复按其所属的执行流程进行，然后在可比较的基线上重新测量，并做正确性检查。性能剖析不能自己认证修复，也不代替 gdUnit 的结果。
