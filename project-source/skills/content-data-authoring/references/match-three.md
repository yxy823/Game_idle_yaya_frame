# 三消内容

## 通用约定

只适用于项目已采用的机制。下面某一类在 GDD 中没有对应的规则时，跳过它，不为它补设计。各类中列出的检查是常见候选，只采用与 GDD 和 `balance/` 已采用的规则一致的项；例如 GDD 允许免费项或折扣项时，不检查“成本严格递增”。数据能加载、ID 唯一、引用有效、数值有限这类结构检查始终适用。

- **规则侧**：重力、补充、匹配、元素行为和目标类型写在 `docs/gdd/systems/`，难度目标写在 `docs/gdd/balance/` 与 `progression.md`；**数据侧**：每一关的布局、目标、步数和关卡顺序。数据里只放 ID、枚举和数值，不写新规则。
- **格式**：棋盘有嵌套结构，用 JSON 或 `.tres`，不塞进 CSV 单元格，见 CSV 规则的[编写](../../../../yaya/agent-rules/50-data-files/csv.md#编写)。棋盘可以写成每行一个字符串，每个字符对应一个枚举值；字符与枚举的对应写在 schema 中，不靠猜。JSON 的解析与写出见 [解析](../../../../yaya/agent-rules/50-data-files/json.md#解析) 和 [规范写出](../../../../yaya/agent-rules/50-data-files/json.md#规范写出)。
- **位置**：关卡数据放在所属模块下，例如 `game/<module>/levels/`。
- **自动对局**：通过率之类的检查用固定种子和写明的策略（随机、贪心等）运行，复用正式的匹配与结算代码。补充棋子随机时，一般无法证明一关“一定有解”，只能报告在这些种子下的结果。

## 关卡布局

- **分界**：重力方向、补充方式和生成点规则归 `systems/`；每关的棋盘形状、空洞、初始棋子（固定或给定种子）和生成点归数据。
- **机器可检查**：
  - 尺寸在规则允许的范围内，每格都是合法的枚举值；
  - 每个可填的格子都能从某个生成点补到；
  - 规则要求时，初始棋盘没有现成的匹配，并且至少有一步合法交换。
- **需要人判断**：版面是否好看、是否一眼能读懂。

## 目标与步数

- **分界**：有哪些目标类型、怎样计数归 `systems/`；每关的目标、数量和步数归数据。
- **机器可检查**：
  - 目标引用的元素在本关存在，或按规则能生成；
  - 目标在结构上可以达到，例如要清除的果冻数量不超过可达的格子数；
  - 步数大于 0。
- **需要人判断**：步数松紧带来的紧张感是否合适。

## 障碍

- **分界**：障碍的行为、层数含义和与其他元素的交互归 `systems/`；每关障碍的位置和层数归数据。障碍的定义适合做成 `.tres`，见 Resource 角色、共享与复制中的[角色](../../../../yaya/agent-rules/21-resources/roles-sharing-and-locality.md#角色)。
- **机器可检查**：
  - 引用的障碍 ID 都能找到，见 [业务 ID 与引用](../../../../yaya/agent-rules/50-data-files/schema-identity-and-migration.md#业务-id-与引用)；
  - 层数在该障碍定义的范围内；
  - 没有规则禁止的叠放或位置。
- **需要人判断**：障碍组合是否有趣，是否只是在拖慢节奏。

## 关卡序列与难度曲线

- **分界**：教学顺序和难度目标归 `progression.md` 与 `balance/`；关卡顺序表和每种新元素首次出现的关卡归数据。顺序表的顺序有意义，要在 schema 中声明。
- **机器可检查**：
  - 关卡 ID 不重复、序列不缺号；
  - 每种新元素出现在它的教学关之后；
  - 固定种子下的自动对局通过率落在目标带内；
  - 没有连续超过目标上限的高难关（按自动对局的指标判定）。
- **需要人判断**：实际难度手感、挫败感、“差一步就过”的感觉，以及整条曲线的起伏。

## 可解性

- **分界**：无路可走时怎样处理（例如死局洗牌）归 `systems/`；可解性本身不是数据，是对数据的检查。
- **机器可检查**：
  - 确定的部分：目标在结构上可达，开局有合法交换；
  - 概率的部分：固定种子的自动对局至少能通关一次，并报告通过率、策略和种子数量。
- **需要人判断**：自动对局的通过率能否代表真人玩家；对局不能通过但用户觉得可玩，或者反过来，以用户的实际游玩为准。
