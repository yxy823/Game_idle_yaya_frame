# 增量放置类内容

只适用于项目已采用的机制。下面某一类在 GDD 中没有对应的规则时，跳过它，不为它补设计。各类中列出的检查是常见候选，只采用与 GDD 和 `balance/` 已采用的规则一致的项；例如 GDD 允许免费项或折扣项时，不检查“成本严格递增”。数据能加载、ID 唯一、引用有效、数值有限这类结构检查始终适用。

## 通用约定

- **规则侧**：公式、目标区间和行为规则写在 `docs/gdd/systems/` 与 `docs/gdd/balance/`；**数据侧**：每个实体一行的具体数值。数据里只放 ID、引用和数值，不写新规则。
- **格式**：生产者、升级和解锁阈值这类扁平表优先用 CSV，导入方式改为 keep，见 [导入方式](../../../../yaya/agent-rules/50-data-files/csv.md#导入方式)；要在检查器中批量编辑时，改用 `.tres` 和表格插件，见 [权威来源](../../../../yaya/agent-rules/50-data-files/data-lifecycle-and-authority.md#权威来源)。
- **大数**：放置类的数值容易超过 2^53 和浮点上限。表示方式由设计和架构确定；数据中超过 2^53 的精确整数写成十进制字符串，见 [解析](../../../../yaya/agent-rules/50-data-files/json.md#解析)。所有数值字段拒绝 NaN 和 ±Inf。
- **模拟用的策略**：解锁时间这类检查要用确定性的模拟。购买策略（例如总买回本最快的项）写进检查本身，并说明它只代表这一条路线。

## 生产者与产出

- **分界**：产出公式、成本公式（例如 `base × rate^owned`）和倍率的叠加方式归 `balance/`；每个生产者的 ID、基础产出、基础成本、增长率和解锁条件归数据。
- **格式**：一张生产者表，每行一个生产者。
- **机器可检查**：
  - ID 唯一，解锁条件引用的 ID 都能找到；
  - 基础产出和基础成本都是大于 0 的有限值；
  - 成本随拥有数量严格递增；
  - 按公式算出的回本时间落在 `balance/` 的目标带内；
  - 没有在任何阶段都被别的生产者完全压过的生产者（同样花费下产出总是更低）。
- **需要人判断**：数字增长是否有爽感，每个新生产者出现时有没有新鲜感。

## 升级与成本曲线

- **分界**：升级怎样作用（乘或加、作用对象）和曲线形状归 `balance/`；每个升级的目标、效果类型、数值、成本和前置条件归数据。
- **格式**：一张升级表。效果有多种结构时，用明确的类型字段区分，见 [字段与取值](../../../../yaya/agent-rules/50-data-files/schema-identity-and-migration.md#字段与取值)。
- **机器可检查**：
  - 目标和前置条件引用的 ID 都能找到，前置条件不成环，每个升级都有可满足的前置链；
  - 倍率大于 1，加成大于 0；
  - 同一条升级线的成本单调递增；
  - 按公式计算的升级后产出，与运行时规则代码算出的一致。
- **需要人判断**：购买时有没有“值得”的感觉，升级是否改变了玩法而不只是数字。

## 解锁时间表

- **分界**：节奏目标（某个解锁大约在第几分钟到达）归 `progression.md` 和 `balance/`；解锁的顺序和阈值归数据。
- **格式**：一张有序的解锁表。顺序有意义，要在 schema 中声明，见 [业务 ID 与引用](../../../../yaya/agent-rules/50-data-files/schema-identity-and-migration.md#业务-id-与引用)。
- **机器可检查**：
  - 用固定策略做确定性模拟，每个解锁的到达时间落在目标带内；
  - 不存在超过目标上限的“无物可买”空档；
  - 解锁顺序与 `progression.md` 一致。
- **需要人判断**：等待是否无聊，节奏是否合适。

## 离线收益

- **分界**：哪些过程在离线时继续、时间上限和效率规则归 `systems/` 与 `balance/`；离线上限时长和效率值归数据或参数资源。
- **格式**：几个标量参数，适合放在一个 `.tres` 参数资源中。
- **机器可检查**：
  - 离线所得不超过同时长在线所得乘以效率；
  - 超过上限的离线时长被截断；
  - 极端时长下不出现 NaN、Inf 或溢出。
- **需要人判断**：回来时是惊喜还是像惩罚。

## 转生与重置

- **分界**：奖励依据、加成公式以及保留和清空规则归 `systems/` 与 `balance/`；转生货币的加成表，以及每个状态字段属于保留还是清空，归数据。
- **格式**：加成表用 CSV；状态字段的归类用 `.tres` 或 JSON，字段用 ID 引用，取值是枚举 `keep` 或 `reset`。
- **机器可检查**：
  - 存档中的每个状态字段都已归类为保留或清空，没有遗漏；
  - 首次转生能在目标时间内达到；
  - 转生后回到上一轮进度所需的时间短于上一轮的用时；
  - 加成表中的数值单调，并且都在表示范围内。
- **需要人判断**：转生时机的抉择感，下一轮是否有足够的变化。
