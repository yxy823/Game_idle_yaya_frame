# 验证策略

本页是各规则模块共用的验证证据规则。测试范围（Required、affected、full）和测试运行的失败条件见 [08 · 测试追溯与证据](../../methodology/08-test-traceability-and-evidence.md)；各模块需要的验证写在模块 README 末尾的验证节。

## 选择与组合

- 每个改动的产物都要满足所有适用模块的验证要求，这些要求相互叠加。
- 运行适用于这次修改的验证，不运行所有能想到的昂贵检查。影响范围不确定时，选稍宽一些的相关范围，不声称一个缺乏依据的最小范围。
- 使用项目已配置的入口：`tools/` 下的命令，以及 [GDScript lint 约定](../../methodology/contracts/gdscript-lint.md) 中的解析和 lint 命令。不编造不受支持的检查器，不为填满清单安装新的工具链。
- 一类验证不代替另一类，除非项目规则明确规定它们对受影响的契约等价。上层检查通过不抵消下层的失败。
- 只有实际执行并成功结束的检查才算通过。按工具的退出码或结构化结果判断，不根据控制台文字猜测。包装脚本不能用退出码 0 掩盖底层检查的失败。

## 失败处理

- 不通过放宽 lint 阈值、扩大忽略范围、跳过失败的测试、关闭错误监控、降低 schema 严重级别、移除检查或改写规则来换取通过。
- 验证失败是需要归类的证据。不能仅因为检查阻碍了完成，就认定检查出错。
- 修复失败后，重新运行失败的检查，以及这次修复牵连的检查。

## 证据的适用范围

- 证据只证明它实际运行到的环境。规则要求新进程、新导入、新导出或目标运行时的证据时，已有编辑器或会话的结果不能代替。
- 人工验收和自动验证是不同的证据，不把其中一种汇报成另一种。
- 日志、JUnit 报告和临时导出等验证产物按[临时文件规则](third-party-generated-and-temporary-files.md#临时备份与草稿文件)处理，不变成正式源文件。

## 汇报验证结果

- 写实际执行过的检查及其结果。只有实际执行了完全相同的范围，才能说“所有测试通过”“已完整验证”或同等的话。
- 必需的检查没有执行或被阻塞时，写明原因和具体的剩余风险，不假定通过。
- 清楚列出仍然存在的失败和阻塞，不把部分失败的运行概括为成功。
- 不声称未经测量的性能、平台兼容性、无泄漏、视觉质量或其他没有实际评估过的性质。
- 结果与版本有关时，写明确切的 Godot 或工具版本。
- 概括日志，只在解释失败需要时引用片段。

## Windows 编辑器检查

本节适用于在本机 Windows 的 Codex 受限沙箱中运行 Godot 编辑器检查（包括 `--headless --editor`）。在其他机器上，先检查实际的权限和目录行为。本节不要求每个 Feature 都启动编辑器。

- 编辑器检查通过 `require_escalated` 审批在沙箱外运行。审批被拒绝或不可用时，把这项检查汇报为未执行或被阻塞，不绕过审批。
- 输出出现 `Could not create editor data directory` 或 `Could not create editor config directory`，或访问 `AppData/Roaming/Godot` 失败时，调查环境权限。停止依赖这次运行的后续验证，不汇报为通过，也不因此修改业务代码或削弱检查。
- 检查前后对比项目根目录的列表，包括 Git 不跟踪的空目录。出现 `export_templates`、`feature_profiles`、`script_templates`、`text_editor_themes` 等意外目录时，先查明来源。只清理确认由这次运行创建的空目录，保留事先已存在的同名目录。
