# 规则优先级与路由

本页规定 `agent-rules/` 和 `docs/project-rules.md` 中规则的写法与冲突处理，不改变系统、开发者或用户指令之间的优先级。

## 规则的写法

- `agent-rules/` 的条目默认是要遵守的要求。
- 写“建议：”的条目是默认做法。有理由时可以偏离，并在汇报中说明偏离的做法和理由。
- 写“注意：”的句子提醒一个容易出错的事实，随所在条目适用。
- Warning、Critical 等工具输出的严重级别与规则的写法无关。

## 模块之间的关系

- 根 `AGENTS.md` 和 `00-core` 定义全局约束。规则模块默认叠加：跨领域的修改要满足每一个适用模块。
- 专项模块只在它明确覆盖的范围内细化通用规则，不能悄悄削弱适用的 `00-core` 要求。
- 两条要求看起来冲突时，先核对各自的适用范围、有无明确的专项细化、目标 Godot 语义和指定的权威配置，再判断是否真的冲突。

## 规则冲突的处理流程

核对后，两条适用的要求仍然无法同时满足时：

1. 停止受影响范围内的实现。不受影响的已授权工作继续。
2. 汇报每条冲突规则及其路径，以及受影响的文件、行为和验证。
3. 不悄悄选用其中一条，不削弱任何一条，也不用绕开冲突的变通做法实现。
4. 请求澄清，或请求批准修改规则。冲突解决后，再恢复受影响的实现。

## 疑似规则错误

- 有具体证据质疑一条规则（事实错误、过时的版本假设或过宽的范围）时，向用户汇报：规则及来源、证据及其局限、受影响的行为。个人偏好不构成规则缺陷；偏离“建议：”条目只需按上文说明理由。
- 代码是否合规与规则是否正确分开评估。修改规则按[规则的增量维护](../../methodology/04-project-rules.md#规则的增量维护)处理，不悄悄修改或豁免规则。只暂停依赖未决定事项的那部分实现。

## 机器配置与已有代码

- 明确委托给机器配置的确切值（例如 `gdlint.json` 的阈值或某个 schema），以该配置为准。配置只说明当前值，不证明这个值符合项目规则或 Godot 语义。
- 已有实现是当前惯例的证据，不凌驾于明确的项目规则或架构之上。
- 已有测试编码的是过去确定的行为。只在批准的行为已经改变，或已证明测试本身有误时修改它；不能因为它阻碍实现就称它“过时”。
