# Yaya 框架 Bug 诊断

围绕一个具体异常查明原因，或准确指出还缺什么证据。只供框架维护使用，不随游戏项目分发；维护仓库不启用生成项目的开发 Stage。

## 确定调查对象和可用验证

沿用当前任务的目标、范围和有效授权。核对预期行为、实际症状、触发条件、对应版本，以及已有复现和排除结果。预期不明确时先核实，不直接把当前实现当作正确标准。

按问题读取相关实现及实际调用方。涉及复制结果时区分源材料和具体目标项目，核对[复制清单](../../../framework/commands/project-files.json)；涉及 Codex 指令时追查入口与条件引用，并区分静态推演、有限试用和客户端真实行为。

选择检查方法前，按[维护验证范围](../../../framework/docs/framework-maintenance/updating-the-blank-project.md#按修改选择验证范围)确认本次允许的方法和地点；确需运行维护检查时再查[现有命令](../../../framework/README.md#按需检查)。诊断请求不自动授权修改外部项目、生成游戏或扩大验证范围。

## 用证据缩小原因

- **让判断对应原症状。** 写清怎样观察问题与正确结果。工具退出码为零、日志安静或某项断言通过，都可能没有覆盖用户报告的异常。可复用现有测试、明确操作步骤、输入夹具或原始日志，不强制先创建脚本。
- **在保留症状的前提下简化。** 对复杂复现逐次去掉一个无关因素，并核对仍是同一异常。记录版本、输入和必要前提；间歇问题记录实际触发次数与观察条件，不凭一次未出现就认定解决。
- **提出可被证据推翻的解释。** 对主要候选原因说明它预测的现象，以及什么观察能区分候选；优先检查有依据且有区分力的项，不凑固定数量的假设。
- **有目的地观察。** 使用能区分候选的现有日志、调试器、差异或局部观测，避免无差别加日志。需要临时改动时先核对当前授权和[变更范围](../../../project-source/agent-rules/00-core/change-scope-and-ownership.md)，说明用途；结束时按已授权范围清理自己的临时观测或明确保留原因。
- **性能异常先建立可比条件。** 核对版本、负载和测量方式，比较同类结果；日志数量、主观快慢或不同环境的孤立数字不构成性能根因。

不能运行复现时，可以继续获准的静态调查并提出待检验假设；不得把它写成已复现或已定位。需要确认根因而证据不足时，报告尝试、未排除原因、最小下一项证据及获取前提，不以“保存了日志”替代根因结论。

## 交付诊断并继续有效授权

说明原症状、实际调查范围、根因证据或剩余候选、负责位置和建议验证方式。事实、推断与未验证项分别标明，引用必要原件，普通诊断在对话中交付。

只授权诊断时，不实施修复。已有具体修复授权时，按[会话延续约定](../../../framework/docs/framework-maintenance/updating-the-blank-project.md#后续用口语继续)继续原任务的最小完整修复和适用回归，不因本 Skill 返回重新确认。回归须覆盖原先失败的行为；使用简化复现定位后，还应核对原始完整情境。适用的运行或人工证据尚缺时保留缺口，不把静态判断写成修复验证通过。

真实剩余工作与验证缺口按[框架待办规则](../../../AGENTS.md#维护边界与查阅)维护，不新建 Bug 台账、报告或自动检查机制。
