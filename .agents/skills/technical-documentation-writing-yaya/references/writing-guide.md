# 框架文档写作指南

将已确认的框架事实、设计理由和操作要求整理成容易查找、理解和执行的说明。保持当前规范的行为、授权、验收和完成条件，按本次任务处理指定文档。

## 适用范围与内容契约

本指南适用于框架的各级 README、Godot 项目手册、场景速查手册、维护文档、职责设计准则、审核报告，以及规则、Skill、提示词中的说明文字。各类材料仍由所属规范决定记录什么；写作整理不能替代业务、指令行为或职责设计。

- 保留已有模板要求的字段、栏目、固定路径和机器可读结构；不为了目录分组或统一风格移动工具依赖的文件、改写标识或重排固定输出。
- 沿用框架确认的语言和术语；修改分发源中的说明时保留这些文件自身的语言与格式契约。中文手册不能反向改变生成项目的文档语言。
- 11 类信息用于操作流程和使用场景；框架场景的固定栏目要求由其编写规范决定，不套到概念页、设计依据、审核报告或提示词字段上。

## 确定本次改写范围

- 从现有上下文确认读者、用途、目标文件和允许改动的范围；只补问会改变交付结果的缺口。
- 按需读取框架的写作约定、相关文档和实际依据。工具参数看当前入口，流程含义看所属规范；不把通读整个仓库设为前置。
- 区分文字问题与行为矛盾。能按现有事实澄清的直接改写；需要新的业务决定时指出冲突与依据，不靠换词替用户决定。
- 单页润色不自动扩大为目录迁移或全仓规范化。已授权的整理继续完成必要链接和索引更新。

## 按内容选择组织方式

| 当前需要 | 使用方式 |
| --- | --- |
| 普通单页写作或润色 | 使用本页的表达和检查原则，无需加载全部参考 |
| 整套手册或维护材料整理、页面分工、命名、术语或正文去重 | 阅读 [框架文档结构](document-structure.md) |
| 操作步骤、维护流程或场景页 | 阅读 [流程与场景文档](procedure-writing.md)；具体场景同时遵循当前[场景手册的编写规范](../../../../framework/prompt-scenarios/scenarios/README.md) |

例如，解释创建器的复制范围时，工具契约来自实际创建器和复制清单，手册说明读者会得到什么；解释某次静态审核时，报告写清被审版本、覆盖和未验证项，不把审核建议写成框架已经采用的规则。描述项目开发 Stage 时注明其属于生成项目，不能让维护任务因阅读手册进入该 Stage。

## 表达与排版

- **先给当前需要的信息**：开头说明文档用途或关键结论。动作旁提供会影响执行的前提、风险和必要解释；背景、实现细节和历史后置。
- **同一主题就近讲清**：一个段落或条目围绕一个主要问题，建议、理由与适用边界相邻。短提醒和准确链接可以帮助恢复上下文，不反复复制整段正文。
- **按关系选形式**：因果解释用段落，并列材料、职责和条件用无序列表，有先后依赖的操作用编号步骤，同维度比较用表格。保留条件、例外和顺序，不按逗号机械拆句。流程有分支、回路或失败后的返回时，用 Mermaid 图画出走向，表格只说明每一步的产出：逐行排列的表格表达不了“仅……时才有这一步”和“失败后回到哪一步”，读者只能自己拼出流程。线性步骤和逐项对照不画图。
- **层级服务查找**：列表通常一层，有真实的“类别 → 事项”关系时再加一层；更复杂的内容考虑小节或拆页。紧密相关短语可以同项表达，不为每个短词增加层级，也不把独立事项压进长行或表格单元。
- **用具体对象和动作**：沿用准确术语，读者可能不认识的术语在首次出现处就地短释。展开“固定问题”“接回检查”等压缩表达；结果用可观察的证据说明，不只写“正常”“成功”或“已处理”。
- **一句只做一件事**：一句话里同时塞进几个动作、条件和例外时，拆成列表或几句短句；说明句超过约 100 字通常就该拆。命令行和路径不受此限。
- **通用提醒只在一处讲清**：同一句提醒（例如“X 不证明 Y”“授权会延续”）不要在每页重复。通用规则写一处完整正文，其他页面链接它；只在确实容易误判的位置保留一句提醒。出现次数本身不是删除理由，要看这句提醒在该位置是否有防误判的作用。
- **长期文档不写进度**：手册、维护规范、方法规范、规则、Skill 和提示词不写实现或验证的进度，例如“尚未实现”“还没在真实项目中验证过”“目前只支持……”。因为进度一变这类句子就过时，链接检查也查不出来。框架的进度写在[框架待办](../../../../framework/progress.md)，生成项目的进度写在它的 Progress。设计层面还没定下的内容不在此列：可以标成“待定”“工作假设”或占位值，并链接记录这个问题的待办条目或开放问题。
- **少用公文腔和压缩词**：“办理”“适用评审”“当前接受”这类说法要换成具体的对象和动作，例如“检查完成证据”“用户指定的评审结果”“当前内容上的人工接受”。
- **不用含糊词、空动词和包装动词**：用数字、名称或条件代替含糊的程度词，写出实际动作，不用空动词和包装动词，例如写“删掉重复的检查”，不写“对检查进行优化”；要避免的写法由措辞检查的配置列出，说明只维护在 Godot 版写作指南的[措辞检查](../../../../project-source/skills/technical-documentation-writing-godot/references/writing-guide.md#措辞检查)一节。不知道数字时只删掉空的程度词，不编造数字；“开箱即用”“无缝”这类套话同样换成具体做了什么。
- **写出主语和句间关系**：主语换了就写出来，“它”“这”“该”只在指代唯一时使用；因果、条件和转折用“因为”“所以”“如果”“但”写明。一个名词前最多两个“的”，修饰更多时拆成两句。
- **一个概念只用一个词**：同一个对象或动作全文用同一个词，不为读起来有变化而换说法；框架与生成项目共用的概念用[框架术语](../../../../framework/terminology.md)中的写法。
- **链接文字用文件标题**：链接到方法论文件或其他有标题的规范文件时，链接文字用该文件的标题（去掉编号），不另起“X规范”“X约定”“X流程”之类的叫法。
- **要求的强弱用固定的词**：“必须”“不得”表示强制要求和禁止；“可以”“不必”表示允许和不要求；“默认”“优先”表示没有另行指定时的选择，并写明何时可以改变。“能”只表示能力，“需要”只表示依赖或缺少，都不表示要求。不用“应”“应该”“宜”“务必”“尽量”“最好”“建议”表达要求，按实际强度改用上面的词；规则文件里的“应”“宜”“务必”由[措辞检查](../../../../project-source/skills/technical-documentation-writing-godot/references/writing-guide.md#措辞检查)拦截。操作步骤用祈使句，不加这些词；直接写出的动作本身就是要求。
- **保留 Markdown 结构**：普通段落和同一列表项不按固定字符数手工折行；保留段落分隔、列表、表格及代码块需要的换行。遵循当前仓库的格式约定，不设统一字数或栏目数量。

## 核对与交付

沿读者路径核对“找到内容 → 理解或行动 → 判断结果 → 继续或恢复”。说明型页面核对概念与查找路径，操作型页面再核对输入、实际入口、执行者、副作用和完成条件，不为每类文档强加操作步骤。

- 对照实际依据检查改写，保留授权边界、关键条件、限制和未确认信息。发现缺口时明确说明，不编造工具、角色、结果或已完成状态。
- 移动或重命名已授权的文件时，更新受影响的引用、索引与构建入口；不借文档调整改变业务行为。
- 按框架维护约定核对受影响的正文、链接和必要回归；读取真实诊断。工具与权限要求查当前入口，不在写作指南维护第二份命令。
- 审核报告保留当次版本和证据；入口迁移不把旧报告改写为对新版本的审核。当前使用说明描述现在的有效行为，历史原因按所属记录保存。
- 自动检查与实际阅读分别报告；格式和链接检查不能证明阅读体验。文字整理不额外设立审批、记录文件或独立报告。
- 交付改好的文档、简短改动理由及实际检查结果；仅要求分析时交付有依据的建议，保持只读。
