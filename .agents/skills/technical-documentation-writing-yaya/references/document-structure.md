# 框架文档结构与正文归属

用于框架的多专题目录、页面分工、命名、术语和重复正文整理。先确认读者是在理解框架、查工具契约、执行某个场景还是核对维护依据，再决定是否移动或拆分文件。

## 目录与页面分工

本次允许调整结构时，先按材料讲述的对象划分目录，再在对象内按功能建立子目录，使索引与文件位置一致：

- **按对象划分**：讲生成项目的、讲框架维护的、讲提示词与场景的材料分别成区；不建立只按文件类型归堆的 `docs/` 一类目录。
- **按功能建子目录**：同一目录内的文件功能不同时，即使目前只有一两个文件，也按功能建立子目录；功能相同的文件放在一起，不为每篇文章单建文件夹。
- **脚本与说明同处**：脚本放在所属对象的 `tools/`，用法写在同目录 README，入口页只做索引。
- **入口只导航**：目录的 README 说明本目录内容与查找方式，不复制各专题正文，也不重画上层目录。

本仓库的具体约定与当前目录以根 AGENTS.md 的「目录与入口组织」和[框架入口](../../../../framework/README.md#目录与职责)为准，本参考不单独授予新增目录或搬迁的权限。

整套文档整理仍须保留模板、工具和构建依赖的路径契约，移动时同步全部读写方；范围仅为单页润色时，仍以该页及必要引用为限。

例如，介绍创建器参数、处理复制失败和说明维护验证，分别服务生成项目的对象查询、具体场景操作与框架维护，应放在 Godot 项目手册、场景速查手册和维护文档三个不同位置；创建器脚本与它的用法说明则一起放在 `project-creation/tools/`。

以下按用途区分正文，不为每种用途机械新增一种文件：

| 文档用途 | 应保存的内容 | 避免混入的内容 |
| --- | --- | --- |
| 入口与索引 | 谁来使用、按什么问题选择、到哪里继续 | 每个主题的完整操作正文 |
| 概念与参考 | 框架对象含义、配置字段、工具契约及适用限制 | 大量针对具体情境的处理流程 |
| 操作与场景 | 当前目标、必要输入、具体动作和可验证出口 | 另一套独立任务、工具的全部参考资料 |
| 维护规范 | 长期内容归属、编写约定与维护责任 | 当次迁移状态和已经完成的工作记录 |
| 历史与报告 | 对应版本、当次事实、范围及未验证项 | 未核实就作为当前规则的旧结论 |

同一页可以有多个共同完成目标的小节。只有读者入口、处理目标或独立使用方式需要区分时才拆页，不按单个命令或固定篇幅拆分。

例如，“快速上手与全部控件说明”混在一页时，可以按阅读目的分工：

- **上手页**：带读者完成第一次操作、看到结果并知道下一步；步骤保留当下所需的参数与副作用提醒。
- **参考页**：集中说明完整控件含义、默认值和限制，供按对象查询。

诊断页中的多种原因若共同服务于同一问题，则可以保留为分支，不为每个原因另建一页。

授权涉及移动文件时，先核对受影响的引用、索引、复制映射和构建入口，再一并更新。按框架当前约定处理旧入口，不自行新增重定向体系或兼容副本。

## 标题与命名

- 标题在目录中单独出现时也应可懂，写出关键对象与要解决的问题。
- 场景标题包含会改变处理方式的状态；具体例子和背景放进正文，不把所有细节挤进名称。
- 概念页按对象命名，操作页按任务命名，配置参考按被解释的配置或工具命名；不同用途不强制同一种句式。
- 文件名和目录名沿用框架语言、工具约定与命名规则，保持可辨识性。场景文件名以既有提示词映射为准；没有必要时不再引入一套英文别名、编号或映射记录文件。

例如，“错误处理”不能区分不同的查找意图；“导入完成后发现缺少文件”更适合具体场景，“导入错误码”更适合工具参考。两者分别说明处理动作和结果含义。

## 正文去重与衔接

先找一项事实或规则的权威位置，再决定其他页面要保留多少解释。

- 完整规则、完整工具参数或完整流程各有明确来源，相关页面保留本次使用所必需的内容和准确链接。
- 使用位置仍需短提醒、适用条件或关键参数时就地提供，避免读者反复跳转才能开始。
- 导航入口可以链接整篇；步骤需要某项准备、检查或恢复方法时，链接到相关小节。例如“执行桌面验收”应直接到验收小节，不只到同时包含多种检查的验证文档首页。标题或路径改变后核对目标锚点，不用“上表”“见文档”等表达代替定位。
- 重复频率本身不证明内容多余；检查它是否提供必要入口、恢复提示或防漏提醒。重复完整正文造成冲突时，合并来源，不新增同步程序。
- 资料矛盾时核对实际依据。历史报告、示例和迁移待办不能默认为当前行为；未知内容标明待确认，不写成已具备能力。

## 术语与状态

优先使用框架已有词表，在写作位置就地短释必要术语。框架术语与游戏业务词汇由各自所有者维护；手册中的游戏例子不成为所有项目必须采用的业务定义。

| 类别 | 记录重点 |
| --- | --- |
| 名词 | 对象指什么、与相似对象有什么区别、正式名称与必要缩写 |
| 动词 | 动作对哪个对象产生什么变化，如保存、提交、发布、验收 |
| 状态用语 | 哪些证据支持该状态，哪些相似状态不能混用 |
| 形容词与副词 | 仅记录会影响技术判断的限定含义，如“稳定”“自动”；普通修饰词无需收录 |

保留工程中的准确名称、标识和正式状态值。自然语言使用统一写法，不随意翻译代码字段，也不为普通表达夹入没有实际指代的英文词。

例如，复制检查通过、工具回归通过、真实引擎运行通过和用户已验收是不同结论。框架手册或报告依赖某种状态时，引用对应证据标准，不能把它们写成同义词。

## 排版示例

原文的信息分别服务于不同查找目标：

> 工具说明包含安装、环境变量、命令参数、错误码，操作指南包含首次运行、导入数据和恢复失败任务。

可以按类别展开：

- **工具说明**：安装与环境变量、命令参数、错误码。
- **操作指南**：首次运行、导入数据、恢复失败任务。

每类继续增长、需要独立导航时再增加子项或对应主题目录。紧密相关的短语可以同项表达，不为展示层级再拆出没有用途的栏目。

参数、例外与动作混在一段时，分别采用适合的形式。例如：

> 默认保留 100 条记录，上限为 500 条，单条文本最多 200 字符，超出时截断，截断标记不计入原文长度。

可以写为：

| 参数 | 值 |
| --- | --- |
| 默认保留条数 | 100 |
| 保留条数上限 | 500 |
| 单条文本上限 | 200 字符 |

超过文本上限时截断，截断标记不计入原文长度。以上数值仅作排版示例，实际文档使用项目的真实参数。

同理，一段中同时包含“完成条件、临时停用、彻底移除”时，可以分别组织：

- **完成条件**：用无序列表列出需要同时满足的结果。
- **临时停用**：用短段落说明动作和保留的状态。
- **彻底移除**：用编号步骤说明依赖顺序与清理对象。

不要因为都涉及同一个工具，就挤成一行或一张长表格。

检查时区分“链接目标存在”与“读者能够定位所需信息”。前者用[链接与锚点检查](../../../../framework/maintenance/tools/README.md#检查链接与锚点)核对；后者需要沿当前任务阅读受影响段落，确认入口、目标小节和所需内容一致。
