# Godot 项目手册的组织与语言风格

用于编写、更新或整理 [Godot 项目手册](../../../../framework/godot-project-manual/README.md)。本页规定手册每类页面必须有的要素和统一的语言风格，让多次更新后的页面仍保持同一种组织方式和口吻。通用的表达规则见[框架文档写作指南](writing-guide.md)，本页只写手册特有的部分。场景速查手册按[场景速查手册的编写与维护](../../../../framework/prompt-scenarios/scenarios/README.md)，不适用本页。

## 核心原则：写读者在自己项目里会遇到什么

手册的读者是用框架开发游戏的人。每一段至少回答下面一个问题：

- **会看到什么**：Agent 的输出、生成的文件、工具的结果。
- **要决定什么**：在哪一步停下来，有哪些选择，每个选择带来什么。
- **为什么这样**：第一次遇到时会意外的行为，它防住了什么问题。
- **怎样回头或换路**：拒绝、修改或中途暂停之后，回到哪一步。

Agent 内部怎样推进、工具读哪些字段，只在读者要据此动手或判断结果时写；其余内容留在权威规范，手册链接过去。

例如说明 1D 批准时，写“用户收到一份批准材料，开头三行写做什么、改哪些文件、怎样验证；用户批准后 Agent 才写代码”。不写 Agent 拼装材料的内部步骤。

这套组织方式参考了 AI-DLC 用户指南的叙述页（本地参考库 `references/aidlc-workflows/docs/guide/`），只取适合单人、单平台项目的部分。

## 每类页面的固定要素

### 入口页

指手册的 `README.md`。

- 第一段写本册回答什么问题，以及和场景速查手册怎样分工。
- 「先建立的整体印象」一节：先用一段话写手册里所有流程共用的模型，再列 4 到 6 条最容易让人意外的行为。每条写一句行为、一句原因，并链接到正文所在页。
- 阅读路线：先教程，后参考页，每项一行写读完能做什么。
- 全部专题：每页一行，写这页回答的问题。

### 教程页

- 顶部导航行：手册首页、上一篇、下一篇。
- 开头写三件事：跟着哪个示例走，读完能做什么，本篇新引入哪一个主要概念。每篇只引入一个主要概念，前一篇讲过的概念直接使用。
- 正文按实际发生的顺序写。每一步写“你会看到什么”和“你在这里决定什么”，引用示例项目的真实输出或提交；节选时注明是节选。
- 结尾用「你会直接感受到的几处」列出本篇要点，再给下一篇的入口。

### 专题参考页

- 顶部导航行回到手册首页。
- 开头一段写本页回答什么问题。有容易混淆的概念时，紧接着用一两句区分。
- 讲有先后顺序的流程时（例如阶段、验收、审核），必须包含四项：
  - **停点**：用户会在哪几处被叫停，要决定什么，哪些条件会增减这些停点。
  - **执行条件**：每一步是总会执行，还是只在某个条件下执行。
  - **前后依赖**：后一步要用前一步的哪些产出。
  - **为什么这样设计**：只写第一次遇到时会意外的行为。每条写原因，以及不这样做会出什么问题。
- 有分支或回路的流程用 Mermaid 图，图后紧跟一张表，写每一步的产出和执行条件。图渲染不出来时，读者靠表格也能读懂流程。
- 选择类内容用“情境 → 选择”表；排障类内容用“现象 / 含义 / 该怎么做”表。

## 语言风格

- **称呼固定**：教程页称读者为“你”；参考页称“用户”，和项目规则里的角色名一致。执行者一律称“Agent”。同一页不混用“你”和“用户”指同一个人。
- **行为配原因**：写到会让人意外的行为时，紧跟一句“因为……”，写它防住的问题。原因必须来自权威规范或实际案例，找不到依据时不写原因，不编造。
- **先常见情况，后例外**：先写大多数时候发生什么，再逐条写例外，每条例外一句。
- **写出回头的路**：每个停点写清拒绝或修改之后回到哪一步，已经完成的部分是否保留。
- **用示例项目说话**：教程和参考页的例子沿用手册已有的三消示例和商店购买例子，不另起新的示例项目。
- **不写内部机制**：钩子、字段名、内部状态只在读者要动手或判断结果时出现。

## 不照搬的写法

AI-DLC 指南里以下写法不适合本手册，更新时不要加：

- 按读者身份分流的阅读路线，因为框架只有一位使用者。
- “关键数字”一类统计表，因为数字随框架变化，单独维护容易过时。
- 按多种 Agent 工具、多种平台列差异的段落，因为框架只支持 Windows PC 上的 Godot。
- 把全部命令参数写进手册的长参考页，因为参数正文在各工具的 README。

## 修改手册时的核对

改完手册页面后，按页面类型逐条核对上面的固定要素和语言风格，只核对本次改过的页面。新增页面时，先确定它属于入口页、教程页还是专题参考页，再按对应要素写。某条要素对某一页确实不适用时，在本次汇报里写明哪条、为什么，不为凑齐要素硬写。
