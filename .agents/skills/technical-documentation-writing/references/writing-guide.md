# 技术文档写作指南

将已确认的事实和操作要求整理成容易查找、理解和执行的文档。保持目标项目的术语、行为、授权、验收和完成条件，按当前任务处理指定文档。

## 适用范围与内容契约

本指南适用于 README、使用手册、操作指南，以及需求、设计、知识和报告中的自然语言说明。各类文档仍由所属规范决定记录什么，本指南说明如何组织和表达。

- 保留已有模板要求的字段、栏目、固定路径和机器可读结构；不为了目录分组或统一风格移动工具依赖的文件、改写标识或重排固定输出。
- 沿用项目确认的文档语言和术语；指南所用语言与示例不替项目选择语言、参数或业务要求。
- 需求与设计文档保留各自的结构和验收语义；11 类信息只用于流程与场景，不套入所有文档。

## 确定本次改写范围

- 从现有上下文确认读者、用途、目标文件和允许改动的范围；只补问会改变交付结果的缺口。
- 按需读取目标项目的写作约定、相关文档和实际依据。工具参数看当前入口，流程含义看所属规范；不把通读整个仓库设为前置。
- 区分文字问题与行为矛盾。能按现有事实澄清的直接改写；需要新的业务决定时指出冲突与依据，不靠换词替用户决定。
- 单页润色不自动扩大为目录迁移或全仓规范化。已授权的整理继续完成必要链接和索引更新。

## 表达与排版

- **先给当前需要的信息**：开头说明文档用途或关键结论。动作旁提供会影响执行的前提、风险和必要解释；背景、实现细节和历史后置。
- **同一主题就近讲清**：一个段落或条目围绕一个主要问题，建议、理由与适用边界相邻。短提醒和准确链接可以帮助恢复上下文，不反复复制整段正文。
- **按关系选形式**：因果解释用段落，并列材料、职责和条件用无序列表，有先后依赖的操作用编号步骤，同维度比较用表格。保留条件、例外和顺序，不按逗号机械拆句。
- **层级服务查找**：列表通常一层，有真实的“类别 → 事项”关系时再加一层；更复杂的内容考虑小节或拆页。紧密相关短语可以同项表达，不为每个短词增加层级，也不把独立事项压进长行或表格单元。
- **用具体对象和动作**：沿用准确术语，必要时首次出现就地短释。展开“固定问题”“接回检查”等压缩表达；结果用可观察的证据说明，不只写“正常”“成功”或“已处理”。
- **保留 Markdown 结构**：普通段落和同一列表项不按固定字符数手工折行；保留段落分隔、列表、表格及代码块需要的换行。遵循目标项目的格式约定，不设统一字数或栏目数量。

## 核对与交付

沿读者路径核对“找到内容 → 理解或行动 → 判断结果 → 继续或恢复”。说明型页面核对概念与查找路径，操作型页面再核对输入、实际入口、执行者、副作用和完成条件，不为每类文档强加操作步骤。

- 对照实际依据检查改写，保留授权边界、关键条件、限制和未确认信息。发现缺口时明确说明，不编造工具、角色、结果或已完成状态。
- 移动或重命名已授权的文件时，更新受影响的引用、索引与构建入口；不借文档调整改变业务行为。
- 目标项目已有适用的链接检查或构建命令时，按该项目约定运行并读取诊断；缺少自动检查时核对受影响引用，说明覆盖范围，不宣称脚本已验证。
- 自动检查、实际阅读和浏览器交互分别报告。构建成功不能证明视觉体验；文字整理不额外设立审批、台账或独立报告。
- 交付改好的文档、简短改动理由及实际检查结果；仅要求分析时交付有依据的建议，保持只读。
