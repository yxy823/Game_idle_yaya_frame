# Yaya 框架 Codex 指令编写与审核

让 Codex 在正确的任务中找到所需约束，理解授权范围，并完成有依据的交付。适用于框架维护规则与 `project-source/` 中待分发的指令源材料；本 Skill 仅在框架仓库使用，不随游戏项目分发。

先沿用当前任务的对象、目标和授权。只读审核交付问题与建议；已授权修改时完成相应修正、引用同步和必要验证，不把 Skill 返回当作整个任务结束。普通说明文档的表达与组织使用 [框架文档编写 Skill](../technical-documentation-writing-yaya/SKILL.md)；同一文件同时涉及指令行为与说明文字时，分别按实际需要使用。

普通局部修改只读取相关正文与必要调用方；复用仍有效的上下文，不把所有参考设为固定前置。

## 让引用能在正确时机生效

指向其他文件的链接、Skill description 和规则入口都要说明“处理什么事情时，去哪里解决什么问题”。先检查入口措辞和目标内容是否匹配，再判断需要内联正文还是修改引用。

- **按实际条件引用**：例如“变更测试登记时，读取测试策略的 Registry rules”，比“请参考测试文档”更能定位用途。已在上下文且仍有效的正文可直接复用。
- **把主要用途放在前面**：合并同一任务的近义触发词；只保留会改变处理路径的分支。排除项用于避免实际混淆，不扩大为关键词黑名单。
- **检查可达性与作用域**：链接应能从消费文件所在位置到达目标；分发源还要核对生成后的路径，不能让游戏项目依赖框架绝对路径。

入口越常加载，越应只保留影响选择的内容；详细规则放在被引用材料中。文件存在、链接可打开与触发可靠是不同结论，不能相互代替。

## 安排正文与细节

同一概念的定义、条件与例外放在一起。所有适用任务都需要的边界留在入口；只有部分任务使用的详细规则，通过条件明确的引用展开。引用材料可以是纯参考，不必把所有内容改写为步骤。

拆分应减少无关阅读，并让使用者容易找到入口。比较保留、合并、局部改写和拆分的实际收益，不因文件长就增加 Skill、路由层或交接。出现抢先结束时，先核对完成条件与授权表达；不要靠隐藏后续任务来制造停点。

## 去重时保留真正有用的信息

先定位规则的权威正文，再处理其余位置。工具参数与默认值可从当前配置、入口或帮助核实时，指令保留查阅条件及无法推断的约束；操作说明仍可保留读者实际需要的命令示例。

- **重复正文**：多处完整维护同一规则，改动需要同步时，优先归并到所属规范。
- **必要提醒**：恢复上下文、避免漏项或说明当前动作前提的短提醒可以保留，并准确指向完整规定。出现频繁本身不是删除理由。
- **表达方式**：使用已有且含义明确的术语；用具体条件与可观察结果替代“严格”“彻底”等强度词。精简不能把信息压成需要猜测的暗语。
- **禁令与例外**：优先写清应该怎样处理；明确禁止事项及其触发条件仍要保留，不能假设否定句必然无效。

例如，测试登记的完整路径和时机规则放在测试策略，规划入口保留当前操作提醒，schema 负责结构定义；知识条目的写法放在知识 README，其他入口保留何时查询或整理的提醒。这里只说明归属判断方法，不替代这些对象的当前规范。

## 检查授权与完成含义

对照改前改后的指令，核对输入、范围、必要依赖、副作用、证据与完成结果是否仍明确。局部步骤完成、当前任务完成、正式人工接受要按原有契约区分；润色不能扩大授权，也不能取消尚未完成的已授权工作。

完成条件应能区分已完成、受阻、待决定和待验收。要求全量审核时，枚举真实范围并逐项阅读必要正文，交付实际覆盖与未检查项；抽样须标明抽样，不能把“列出文件”或固定前若干项写成全量通过。

## 验证与交付

按本次变化检查入口、引用、归属和语义；Skill 元数据变化按其参考验证。复杂的新职责或明显触发调整，可用真实场景做独立试用：只给必要输入，观察是否正确选择材料、保留边界并完成任务，不把预期答案交给试用者。

发现问题时说明具体文件或片段、影响、依据和最小改法；没有证据的行为猜测标为待验证。格式与链接检查、静态语义审核、有限试用、客户端实际调用分别报告。普通修正不额外建立脚本、评分、审批或报告层；有归档要求时沿用现有位置。

本 Skill 根据 Matt Pocock 的 writing-for-agents 本地材料改编，保留条件引用、信息层级与正文归属等方法，并针对 Codex 和本框架重新组织。上游许可见 [LICENSE](LICENSE)。
