# Yaya 框架维护方案检验

对已经提出的维护方案形成有依据的判断：哪些选择成立，哪些需要局部调整，还有什么证据或决定会影响实施。方案可以来自当前对话或已有文件，不要求先写成正式文档。本 Skill 只供框架维护使用，不随游戏项目分发，也不是维护任务的必经关卡。

## 确认被检验的方案

从当前任务确认目标、方案版本、拟改范围和用户已接受的决定。阅读相关现状与约束，区分需求、方案假设、实现事实及历史结果。缺少具体方案时，说明需要检验的对象尚未形成，返回原讨论；不代替渐进式需求澄清重新访谈。

只追查影响判断的材料：

- 涉及 Skill、脚本或提示词职责时，按[职责设计准则](../../../framework/review/baselines/skill-script-prompt-design.md)阅读对应维度、实际入口和必要调用方。
- 涉及项目分发时，核对[复制清单](../../../framework/project-files.json)、相关源文件和生成后的使用路径；有路径或字段变化时追查受影响的消费者与回归夹具。
- 涉及验证安排时，按[维护验证范围](../../../framework/docs/framework-maintenance/updating-the-blank-project.md#按修改选择验证范围)核对现有检查能力、执行地点与必要人工证据。历史通过只说明其当时版本与覆盖。

## 检验关键推断

围绕当前方案中会改变结果的选择检查，按实际适用性展开，不为凑问题遍历所有未来分支。

| 关注点 | 检验方法 |
| --- | --- |
| 假设与事实 | 指出方案依赖什么事实、是否已核实；实现现状不能自动代替有效需求，未证实假设不能写成失败事实。 |
| 反例与失效条件 | 用与当前范围相关的具体输入、边界、错误或续接情形挑战关键推断；说明怎样观察其成立或失败，不把假想反例写成已复现故障。 |
| 职责与改动必要性 | 比较保留、复用、合并、删除和局部修正的效果；检查新增入口或工具是否解决独立问题，是否重复维护规则、状态或授权。 |
| 分发与使用影响 | 区分框架自用、项目分发源和已创建项目；检查入口、相对引用、配置及调用链是否一致，不把修改源材料当作已有游戏已更新。 |
| 验证可行性 | 判断计划中的检查能否证明所声称的结果，哪些依赖尚不可用；静态核对、工具回归、真实引擎运行和人工验收分别判断。 |

先给证据支持的判断，再集中提出会改变该判断的实质问题，配上可比较的选择与推荐理由。已确认且仍有效的决定直接复用；普通实现细节由 Agent 判断。资料可查时先查，不要求用户回答环境事实，也不强制为每项调查派生 Agent。

## 返回结论并回到原任务

在对话中说明检查的方案与范围、重要结论及依据。每个需要处理的问题包含具体片段或路径、成立条件与影响、最小调整建议；将必须解决的决定、证据缺口和可选改进分开。方案合理时说明保留理由；证据不足时说明什么材料能改变判断，不以无发现宣称实际运行通过。

检验默认只读，不修改正式方案、代码、规则或计划，不因检验而运行测试、创建项目或增加报告。主任务明确要求归档时，按其既有报告约定交付，不另造状态或批准记录。

当前范围内的关键选择已有判断或明确缺口后，本方法即可返回。只读讨论停在结论；已有实现、验证或交付授权由主任务按[会话延续约定](../../../framework/docs/framework-maintenance/updating-the-blank-project.md#后续用口语继续)继续原职责，不因本 Skill 返回重新索取相同授权。检验结论本身不授予新范围，也不替代独立审核或实际人工验收。
