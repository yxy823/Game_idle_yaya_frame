# Yaya 框架开发复盘

从实际执行中判断哪些做法应保留、哪些问题值得修正，以及最小改动应放在哪里。允许结论为无需修改或证据不足。本 Skill 只供框架维护使用，不随游戏项目分发；它不承担方案从零设计、任务交接或业务验收。

## 还原发生了什么

先确定本次复盘的任务、版本、时间范围和实际困扰。读取相关对话、命令结果、差异、现有记录及其必要原件，区分当时有效的要求、用户授权、Agent 动作和可观察结果。当前文件与事发版本不同则明确说明，不能用今天的规则解释成当时已经违反。

对每个重要现象追查必要证据，不重建完整操作流水账：

- 症状是什么，在哪个条件下出现，产生了什么实际影响。
- 哪些原因已有直接证据，哪些只是推测；是否也能由环境限制、输入缺失、过时材料或一次操作失误解释。
- 是同一次事件被重复描述，还是多个可区分的实例；重复实例的版本、输入和条件是否可比较。单次严重问题可以值得修复，但不能据此宣称普遍发生。
- 哪些现有约束或做法仍有效，避免修复时连同必要保护、验证与自主空间一并删除。

没有足够执行材料时，明确缺口并只交付现有证据支持的判断；不从“过程不顺”直接推断必须新增规则或工具。需要重现、运行测试或改动现场的调查，由主任务在相应授权与验证范围内安排，本次复盘不自行执行。

## 比较改法与归属

先比较不改、局部修正、复用现有能力、合并或删除，再考虑新增。说明建议如何针对已支持的原因、会影响谁，以及新增维护成本；不能仅凭缺少 Hook、CI 或自动化把设计判为缺陷。遵循[根维护原则](../../../AGENTS.md#核心决策原则)，不引入监督 Agent 逐动作执行的 Hook、重复状态、收据、评分或发布资格；验证应针对实际成果。

按问题归属追查权威材料，只读取相关部分：

| 发现涉及什么 | 应核对的归属 |
| --- | --- |
| 框架职责、流程、源材料或说明不一致 | [维护与同步说明](../../../framework/docs/framework-maintenance/updating-the-blank-project.md#先判断修改属于哪里)及对应源规范；框架维护不启用待分发项目的 Stage。 |
| Skill、脚本、提示词职责或指令组织 | [职责设计准则](../../../framework/review/baselines/skill-script-prompt-design.md)和实际调用方；方法、规则与工具各自只承担必要职责。 |
| 创建器、路径或配置的分发问题 | [复制清单](../../../framework/project-files.json)、实际读写方与相关夹具；区分源材料修正和已创建项目的独立维护。 |
| 本机环境或单个游戏的特有问题 | 当前机器配置、个人环境约定或该游戏的原件；不要把局部现象提升成全部框架任务的普遍要求。 |
| 只有任务局部经验 | 现有任务记录或报告；没有可复用价值时不新增规则、工具或长期条目。 |

每项建议给出最小改动位置、应保留的边界及如何验证改法有效。按[维护验证范围](../../../framework/docs/framework-maintenance/updating-the-blank-project.md#按修改选择验证范围)区分静态核对、工具回归、真实引擎运行和人工验收；建议执行的验证与已经取得的结果分别陈述。

## 交付与继续

默认在对话中返回复盘范围、主要现象与证据、原因及其不确定性、值得保留的做法、最小建议与归属。不为固定数量制造发现；无需修改时说明理由，证据不足时指出必要补充而不写成已定位根因。

复盘不自动修改规则、代码、配置、正式方案或待办，也不默认创建报告文件。主任务有明确归档要求时，沿用现有报告位置与范围；建议不是实施权限或新的完成门槛。

完成所请求范围的判断后返回主任务。已有具体授权按[会话延续约定](../../../framework/docs/framework-maintenance/updating-the-blank-project.md#后续用口语继续)保留，由原职责继续相应修改、验证和交付，不再要求用户确认同一个决定；新的实质选择或超出范围的改动仍须明确解决。复盘完成不意味着原任务、修复验证或人工验收已经完成。
