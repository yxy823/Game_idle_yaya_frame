# Yaya 框架反馈核实与分流

先弄清反馈是否成立、具体影响什么，再决定由哪项维护工作处理。本 Skill 只供框架维护使用，不随游戏项目分发。核实结果不自动授权修复，也不创建工单状态或拒绝台账。

## 核实反馈

复用当前对话中已确认的范围、事实和决定，读取反馈对应的实际文件、版本与必要调用方。针对反馈核对：

- **预期与实际**：分别写明用户期待、已确认要求和观察到的行为；当前实现说明“现在怎样”，不能自行替代“应该怎样”。
- **能力与入口**：按行为和业务含义查找现有能力，核对入口、配置和必要前提；找到同名文件或类似实现不等于反馈已解决，也不因功能存在就否定入口难找的问题。
- **对象与版本**：区分维护工具、项目分发源和已创建项目。外部报告及旧运行结果须对照当前被查版本；框架源已修改不代表现有游戏已更新。
- **证据与缺口**：能以现有资料确认的直接确认；需要运行才能判断时，说明适用的复现方法和当前权限。没有复现不等于问题不存在，不为分流启动范围外的验证。

资料可直接读取时先查，只补问会改变判断的缺口。一个反馈含有独立问题时分别处理，同一根因合并说明；不要求先获得类别批准才继续核实。

## 选择后续归属

| 核实结果 | 返回的判断与后续方向 |
| --- | --- |
| 违反有效要求的异常，原因仍不清楚 | 给出实际与预期的差异、影响和证据，交给 [Bug 诊断](../bug-diagnosis-yaya/SKILL.md)。 |
| 实现满足要求，但入口或说明误导 | 定位负责的入口或说明，提出局部改法；修文档与改行为分别判断。 |
| 请求改变已有约定或增加能力 | 明确新旧行为及受影响范围，交回需求讨论；不把新需求伪装成已存在的缺陷。 |
| 有效反馈已被当前版本解决 | 给出当前依据与版本限制；必要运行尚未覆盖时保留缺口。 |
| 证据不足或来源冲突 | 说明尚不能判断什么、缺少哪项材料或决定；不预先指定修复方案。 |

涉及源材料分发或验证安排时，按[维护与同步说明](../../../framework/docs/framework-maintenance/updating-the-blank-project.md)读取对应主题；运行检查的地点、范围与限制以其[验证约定](../../../framework/docs/framework-maintenance/updating-the-blank-project.md#按修改选择验证范围)为准。进入已授权修改前，按[变更准备与范围约定](../../../project-source/agent-rules/00-core/change-scope-and-ownership.md)定位负责文件与必要影响；项目开发 Stage 不在维护仓库启用。

## 返回原任务

在对话中交付结论、具体路径或行为证据、受影响范围，以及下一步所需的最小动作或缺口。未查、静态推断和实际运行分别说明；简单反馈无需固定报告格式，不为核实另建文件。

只要求核实时，返回判断即可。原任务已有具体修复或验证授权时，按[会话延续约定](../../../framework/docs/framework-maintenance/updating-the-blank-project.md#后续用口语继续)继续原任务，不重复索取相同授权；外部报告建议本身不授予修改权限。需要保存真实剩余工作时，沿用[框架待办规则](../../../AGENTS.md#维护边界与查阅)，不把所有建议自动登记为待办。
