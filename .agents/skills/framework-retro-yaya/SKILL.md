# Yaya 框架复盘

用一次框架维护或 demo 试验的实际经过，找出值得改的地方，并判断每条建议改在哪里，交给用户选择实施范围。本 Skill 只供框架维护仓库使用，不随游戏项目分发。

## 适用范围与边界

- **何时使用**：用户要求复盘时，例如一次框架修改或 demo 试验结束后、当前任务反复返工时、用户转来另一个项目线程的开发输出时。任务不必已经结束。
- **何时不用**：例行任务收尾不做复盘；审核代码、文档或职责按[审核与报告](../../../framework/maintenance/design-guidelines/reviews-and-reports.md)；为以后会反复出现的工作设计处理方法，用框架维护提示词「同类工作会反复出现，先设计处理方法」。
- **允许的动作**：读取证据，写一份复盘报告。不修改规则、Skill、提示词、工具、项目文件或用户全局规则，不运行项目、测试或 Godot；需要动态证据时，写明最小复现、所需环境和预期结果，等用户另行授权。
- **不加监督机制**：不提议 Hook、评分、收据、逐动作检查或监督 Agent 的流程，也不把没有这些机制当成问题。依据是根规则[核心决策原则](../../../AGENTS.md#核心决策原则)一节中“不监督 Agent 的每个动作”这条基本约束。

## 收集证据

默认只读当前这一次对话，以及用户在对话中提供的材料（转发的输出、日志、项目路径）。用户点名时，最多再读最近 3–5 次对话；更早的对话不读。上限按主对话计，各自的子智能体记录随主对话一起算；子智能体记录多时，先用脚本统计全部，再只细读耗时或失败异常的几份。当前对话的内容仍在上下文中时直接复用；对话已被压缩、需要准确时间或用户点名了其他对话时，才读对话记录。

**对话记录的位置与读法**：

- 记录在 `~/.claude/projects/<项目目录名>/<会话 ID>.jsonl`。项目目录名由仓库绝对路径把 `:`、`\`、`/` 换成 `-` 得到，例如本仓库是 `D--A-Games-Game-idle-yaya-frame`。子智能体的记录在同名目录的 `subagents/agent-*.jsonl`。
- 按文件修改时间取最近几次；用每份记录开头的用户消息核对是不是要找的那次对话。
- 一次工作可能跨多个会话文件：上下文压缩或续接后会换新的会话 ID，前后两份记录有重叠。按复盘对象的时间范围合并，用每条记录的 `uuid` 去重。
- 复盘智能体自己的记录也在 `subagents/` 里，批量统计时按首条用户消息排除。
- 记录的时间是 UTC，提交时间带本地时区（如 `+0800`），对照前先统一时区，报告里写明用的是哪个时区。
- 识别权限拦截和失败，看 `tool_result` 的 `is_error` 和拦截提示的固定文字，不按“denied”“拒绝”全文搜索：正文措辞会被误算进去。
- 每行是一条 JSON 记录，带 `timestamp`（UTC）、`type` 和 `message`。单个文件可达几十 MB，用错误信息、文件名、工具名、命令等关键词抽出相关行和时间戳，不把整份记录读进上下文。

**其他证据**：与本次工作相关的提交（`git log --date=iso` 可看提交时间）、`tmp/` 下的方案与报告、测试和运行日志的修改时间。只读与本次复盘问题有关的部分，不扫描全部规则或全部对话。

区分证据的时间：今天才存在的规则不能当作当时的事实；没读过的对话、没执行的验证不能写成证据。

## 分析

1. **还原经过与耗时**：按时间列出主要阶段和每段耗时，标出重复的动作，例如同一检查跑了几次、同一文件改了几轮、失败后重试、等待用户。耗时从时间戳计算，没有时间戳时写未知。首末时间之差不等于干活时间，至少拆成：命令执行（`tool_use` 到 `tool_result`）、交回结果后等下一条指令的空闲、卡满超时的单条命令、其余的模型思考与编辑；判断“上下文太长变慢”时，按上下文大小分段比较每步延迟。重复本身不等于浪费，先核对每次重复是不是因为内容或范围变了。
2. **归类每条观察**：一次性失误、工具或环境限制、规则冲突、反复出现的摩擦、值得保留的做法。一次事件不上升为通用规则。可能的原因标为假设，并写出能区分它的证据。
3. **对照核心决策原则**：用[核心决策原则](../../../AGENTS.md#核心决策原则)检查两件事：这次的做法本身，以及准备提出的改法。提议新规则或新机制前，先查已有内容是否覆盖；一条更清楚的引用、合并重复内容、删除过时约束或一次局部修正可能就够。改法过重时保留问题，给出更小的完整替代。
4. **判断是否做成工具**：本次出现的临时脚本，按[何时把临时脚本做成工具](../../../framework/maintenance/design-guidelines/skills-and-scripts.md#何时把临时脚本做成工具)判断；条件不满足时写明不保存的理由。
5. **按出处分配归属**：位置判断依据[先判断修改属于哪里](../../../framework/maintenance/maintenance-and-sync.md#先判断修改属于哪里)，复盘时按下面五类给出归属：

| 归属 | 范围 | 注意 |
| --- | --- | --- |
| 分发材料 | `project-source/` 中的规则、Skill、模板和工具 | 会进入以后创建的新项目；已创建的项目是否更新由用户决定 |
| 框架维护文档 | 根 `AGENTS.md`、`framework/`、`.agents/skills/` | 只影响框架维护，不进入项目 |
| 具体项目 | 某个已创建项目自己的文件 | 在那个项目里修改，不写回框架 |
| 用户全局规则 | `~/.claude/CLAUDE.md` | 只写拟议的文字，是否修改由用户决定 |
| 项目记忆 | `~/.claude/projects/<项目目录名>/memory/` | Agent 自己的经验记录，适合一两次失误留下的陷阱；判断已有内容是否覆盖时也要查 |

一条观察可以同时有几个归属。例如记录显示每改一处都跑一次全量测试：测试怎样按改动范围选择，归分发材料的测试规则；Agent 怎样分轮使用子智能体，归用户全局规则。

可能根本不需要任何改进。这时报告这个结论和支撑它的证据，不硬造建议。

## 报告

按[当次报告的保存与清理](../../../framework/maintenance/design-guidelines/reviews-and-reports.md#当次报告的保存与清理)保存到 `tmp/reports/<任务>/`，文件名带实际日期，例如 `retro-20261008.md`。报告包括：

- **开头**：结论（有几条值得改、最优先的是哪条）和证据范围（读了哪些对话、提交与日志，哪些没读）。
- **经过与耗时**：主要阶段、耗时和重复的动作。
- **每条建议**：观察到的问题或收益、证据位置（对话记录文件与时间戳、提交号、文件路径与行号）、拟议改动、归属与理由、仍缺的决定或验证。
- **值得保留的做法**：写明适用条件，不凑数量。

复盘结论不改写过去的决定，不补上缺失的验收，也不证明某个实现已经通过。

## 交付之后

在对话中给出报告路径、最优先的 1–3 条建议和需要用户选择的范围，然后停下等用户选择。用户选定范围后，按归属转给对应的维护任务实施，验证与提交按根规则执行；修改提示词、场景或关系图时使用[提示词与关系图维护 Skill](../prompt-and-graph-maintenance-yaya/SKILL.md)。选定后仍有未完成的部分，才按[框架待办](../../../AGENTS.md#框架待办)记录；建议本身不自动变成待办。报告的用途结束后按保存与清理的约定删除。

本 Skill 返回不结束它所在的已授权任务，已有的具体授权按[授权在后续对话中的延续](../../../framework/maintenance/maintenance-and-sync.md#授权在后续对话中的延续)继续有效。
