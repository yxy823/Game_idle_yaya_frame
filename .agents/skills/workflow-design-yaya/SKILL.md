# Yaya 框架重复工作方法设计

把一类经常要做的维护工作讲清楚，让下次可以从合适的入口开始。可以分析已发生的重复操作，也可以为预计反复进行的工作提前设计；无需先证明发生过失败。本 Skill 只在框架维护仓库使用，不随游戏项目分发。

历史任务为什么返工、哪些经验值得保留，由 [development-retro-yaya](../development-retro-yaya/SKILL.md) 负责。这里的目标是设计以后怎样处理用户指定的这一类工作，不顺带调查用户的全部习惯或所有对话。

## 确定反复发生的事情

沿用用户已经说明的目标、范围与偏好。已发生的工作选取相关实例，分清哪些输入和动作每次相同、哪些随任务变化；未来工作从预期输入和使用情境推导，不编造历史频次或节省效果。

先查当前相关 Skill、提示词场景、权威文档和工具是否已经承接这项工作。只读取影响本次设计的材料；比较补充现有入口、改清引用、普通 Agent 判断与新增能力，不把“重复”直接等同于“需要脚本”。

## 设计一次完整处理

围绕这项工作的具体需要，说明：

- 什么情况开始，处理哪个对象，需要哪些已有资料和本次可变输入。
- Agent 可依据什么独立判断，哪些选择确实需要用户决定；先完成不依赖答案的准备，已有决定不重复询问。
- 哪些共同方法值得复用，详细规则由哪个现有文档或工具拥有，入口如何按条件找到它们。
- 一次处理交付什么、怎样判断达到目的；若有真实中断或副作用风险，如何保留现场并恢复。

只有答案会改变方法时才提问。需要比较未决方案时沿用个人的 progressive-requirement-clarifier，不重复建立一套访谈流程；该 Skill 不可用时，直接成组说明相关选项与推荐理由。普通实现细节由 Agent 判断，不追求“再也没有任何问题”才结束。

## 选择最小承载位置

按 [职责设计准则](../../../framework/review/baselines/skill-script-prompt-design.md) 比较本次候选。稳定的条件入口与判断方法适合 Skill；具体使用情境由 `framework/prompts.json` 的同名提示词和场景承接；详细说明归现有权威文档；确实可机械重复且值得维护的操作才考虑工具。多种场景可以复用一个能力，不合并输入、授权或出口不同的场景。

框架自用内容与项目分发源各有归属。为 Godot 项目提出的能力应能由项目独立拥有，不依赖框架绝对路径或自动同步。只在确有不同职责时拆 Skill，不为每个动作增加入口。

默认在对话交付可审阅的处理方案：实际需求、建议入口、输入与产出、关键判断、正文归属，以及仍影响采用的选择。没有必要新增机制也是有效结论。用相关实例或明确标注的未来情境检验方案，不把静态推演说成已运行验证。

不默认创建 `workflows/`、个人背景档案、新报告、周期任务、审批节点或流程台账。设计请求不授权实施；已有具体修改授权则返回原维护任务完成相应修改和必要验证，不因本 Skill 返回再请求同一批准。
