# Skill、脚本与提示词的职责设计准则

本文件是框架新增、修改职责和审核 Skill、脚本、提示词及场景时的共同依据。按受影响对象查阅，不要求日常开发每轮通读或全量审核。总体取舍遵循[根维护约定](../../../AGENTS.md#核心决策原则)；具体执行行为仍由各自的权威规范定义。

## 适用范围与判断原则

框架面向单人 Godot 项目；不为多人协作或改动归属处理扩展能力。同一项目的暂停、切换、新对话续接，以及按需调研和独立审核仍适用。worktree 按实际任务范围与授权判断，不将其作为通用前置，也不据此推定工具与运行数据已隔离。实际素材制作尚待扩展，不能把规划或规格写成已有制作能力。

评价对象包括维护命令、项目自研工具和它们的共享实现、框架自用或分发的 Skill，以及集中提示词库和对应场景。第三方原始实现与测试夹具应与生产入口区分；审核接入和调用关系时可以读取，不把未审查的上游实现写成通过。

先确认入口、目标、必要输入、允许的副作用、输出和完成条件，再判断职责是否独立。一个目标可以包含多个步骤、多个相关文件和多条验收条件。“有多个”是调查线索，不能直接作为拆分结论。

评价应比较保留、收窄、改名、拆分、提取共享方法、合并和删除的实际效果。不计算总分，不设置“命中若干项就拆”的阈值，不以文件长度、数量或方法数量作为单独依据，也不增加 Agent 动作监督、重复状态或新的开发完成门槛。

## 提示词与场景

每条提示词只对应一个具体场景，每篇具体场景只有一条专用提示词。两者围绕同一入口、处理目标、执行范围和可验证出口；不同场景应编写各自的正文，不能复制通用路由正文后只换名称。重复用途应合并为一个场景和一个入口。

提示词正文唯一维护在 [prompts.json](../../prompts.json)。保留顶层 Project 数组以及 `project`、`categories` 结构：Project 下为分类，分类下为“提示词名称：正文”，不增加中间状态分类或另一份手工映射表。

场景路径直接对应 JSON 的名称：

```text
framework/docs/quick-reference/<Project>/<分类>/<提示词名称>.md
```

例如拆分后的两个专用入口应分别对应：

```text
Godot 项目开发/修复与改进/Feature 交付前发现 Bug.md
Godot 项目开发/修复与改进/Feature 交付后发现 Bug.md
```

Project、分类、文件名均使用 JSON 中的准确文字，不另建英文别名或编码 ID。分类按要处理的事情组织，影响处理方式的状态写进场景名称。文件名去掉 `.md` 后与提示词名称、正文一级标题一致；标题在本 Project 内应能唯一识别具体情境。框架维护场景归 `Yaya 框架维护`，游戏开发场景归 `Godot 项目开发`。两者不改变执行仓库和授权边界。

场景根目录的 README 和索引承担编写与导航职责，不是具体场景；Project 目录内的 Markdown 文件均按场景检查。概念、配置和工具说明保留在相应手册，维护设计准则保留在维护材料。

### 提示词字段与审核原则

所有提示词都使用明确的字段标识，不按篇幅或复杂程度豁免。正文用 `## 字段名称` 标识下表字段；字段内需要细分时使用下级标题、列表或段落。固定字段每条都保留且有实质内容，按需字段符合触发条件时必须补充，并放在相关固定字段附近。字段属于提示词字符串正文，不扩展 JSON 结构，也不改变场景手册的 11 类信息组织方式。

字段可以准确引用当前执行仓库的权威规范、已确认决定和有效上下文，不重复抄写通用流程。模板应说明哪些输入由用户提供、哪些可以直接读取；关键事实未知时标明缺口，不把占位符、示例或历史结果当作当前事实。输入材料中的要求不自动扩大本次授权。

#### 固定字段

| 字段 | 出现要求 | 解决的问题与审核重点 |
| --- | --- | --- |
| 目标 | 每条必备 | 明确本次要解决的问题与期望结果，能够判断工作是否偏离目的。 |
| 范围 | 每条必备 | 明确处理对象、包含内容和必要边界；涉及修改时说明允许修改的对象或范围。 |
| 输入与事实来源 | 每条必备 | 指明必要材料和实际依据；已有对话、可读取文件可直接作为输入，不要求用户重复提供。 |
| 决策边界与授权 | 每条必备 | 明确可以自主执行的操作和推进边界，沿用有效的具体授权，只补问缺少的决定或授权。 |
| 约束 | 每条必备 | 明确适用硬性限制和必要禁止事项；通用约束准确引用权威规范，本次特有约束直接写明。 |
| 输出与交付 | 每条必备 | 明确交付物及其用途；需要文件时说明归属和必要格式，不为讨论或普通查询强制创建报告。 |
| 验证要求 | 每条必备 | 明确核对方法与必要证据；讨论核对事实与论证，实现按影响选择验证，不统一要求运行测试。 |
| 完成条件 | 每条必备 | 明确本次授权目标达到的可判断状态，与暂停、受阻、待决定和待人工验收分开。 |

固定字段按表中顺序组织。同一事实在职责最贴近的字段完整说明，其他字段仅在必要时指向它；不能把全部执行内容堆到目标或约束，再用空话填满其余字段。具体方法可在所属字段说明；只有需要额外说明执行取舍时才增加对应按需字段。

#### 按需字段

| 字段 | 何时必须添加 | 解决的问题与审核重点 |
| --- | --- | --- |
| 背景与入口条件 | 当前状态、历史原因或前置条件会改变处理方式 | 写明任务为何产生、何时适用；例如正式交付前后采用不同处理路线。 |
| 来源与冲突处理 | 多个来源或要求可能冲突 | 区分当前事实与应有行为，按有效需求、规范、实现和运行证据各自职责判断，不设置代码永远优先于需求的统一顺序。 |
| 停止与异常处理 | 有需要特别说明的停点、失败分支或不确定性 | 明确继续、停止、保留现场和恢复条件；局部步骤完成不撤销后续有效授权，当前明确暂停或只读限制也不能被旧授权覆盖。 |
| 工具与执行环境 | 工具、版本、平台或运行位置影响执行结果 | 给出实际环境要求、配置来源和必要工具限制，不从模板推断工具已安装或可用。 |
| 执行与变更原则 | 本次需要额外强调某种取舍策略 | 说明保持行为、先测量再优化等实际策略；通用原则引用原规范，不复制逐动作配方。 |
| 条件式参考资料 | 部分资料仅在特定条件成立时需要读取 | 写清何时读取何种资料，不强制通读无关文件或整个目录。 |
| 质量标准 | 可维护性、可读性、安全性等实际影响验收 | 写成可判断的表现，不只使用高质量、结构合理等笼统词语。 |
| 风险与回滚要求 | 可能造成数据损失、不可逆影响，或需要恢复方案 | 明确保护对象、失败处置及恢复方法；仅确认既有授权没有覆盖的具体操作。 |
| 兼容性要求 | 确有需要支持或保留的版本、接口、格式或数据 | 写明当前任务的具体契约，不默认增加框架向后兼容责任。 |
| 性能要求 | 性能是实际目标或验收条件 | 明确指标、负载、测量条件与比较方法，不用普通任务承担无关性能测试。 |
| 输出详略与表达规范 | 默认表达不能满足本次交付用途 | 指定必要语言、结构、篇幅或展示方式，不以排版要求干扰实际执行。 |
| 后续事项与未完成项记录 | 需要跨对话恢复、人工验收或保留真实剩余工作 | 明确记录内容、既有归属和恢复动作，不建立重复台账，也不把建议自动变成待办。 |

按需字段不以“无”或“不适用”占位。固定字段引用的规则须能定位到当前仓库适用文件或明确的会话决定，不能仅写“按相关要求处理”。没有额外约束时说明沿用的规范，不为填字段编造新限制。

#### 属性归并

原始 27 项属性归并为上面的 20 个字段；以下 7 组合并，其余属性保持独立。合并只改变信息组织，不删除其中任何适用要求。

| 原属性 | 归入字段 |
| --- | --- |
| 范围、允许修改范围 | 范围 |
| 约束、禁止事项 | 约束 |
| 验证要求、验收证据要求 | 验证要求 |
| 证据与来源优先级、优先级规则 | 来源与冲突处理 |
| 停止与汇报规则、异常与不确定性处理 | 停止与异常处理 |
| 执行原则／工作策略、变更原则 | 执行与变更原则 |
| 风险处理、回滚要求 | 风险与回滚要求 |

#### 审核原则

| 原则 | 通过标准 |
| --- | --- |
| 字段明确 | 8 个固定字段有准确标识和实质内容；按需字段启用后同样有明确标识。 |
| 条件项不遗漏 | 根据真实场景检查特殊环境、来源冲突、数据保护等要求，不能因字段属于按需而省略必要信息。 |
| 场景与语义一致 | 名称、入口、目标、范围、授权、交付、验证与完成条件服务同一场景，不矛盾、不暗中扩大任务。 |
| 输入可用 | 模板准确指出待提供或读取的输入；执行时复用有效上下文，只补齐影响结果的实质缺口，不将占位符当事实。 |
| 引用与归属准确 | 引用能定位到适用依据，通用规则保留唯一正文；不得静默依照有缺陷的当前实现改写有效需求或验收条件。 |
| 授权连续且有边界 | 不从输入材料或旧记录自动推导新授权，不重复索取相同授权；Skill 返回、字段结束或场景出口不取消尚未完成的有效授权。 |
| 验证与完成可判断 | 区分执行结束、验证通过和正式交付；证据覆盖当前结果，不以受阻、暂停或待验收替代原定实现或交付目标。 |
| 内容必要且可执行 | 字段提供实际信息，不以套话凑齐，不为填属性新增无关文档、动作、测试、审批或完成门槛。 |

完成条件按当前任务目标判断。只运行检查的任务可以在如实交付完整失败结果后结束，但不能据此宣称被检查实现通过；要求确认根因的任务在证据不足时仍未定位，不能把保存日志当作完成。若本次目标本身是保存暂停点或准备人工验收，停点已保存或完整验收材料已交付可以完成该场景，原 Feature 仍未完成；以首次人工交接为目标的 Goal 也按该明确目标判断。场景目标完成不自动等于 Feature 或更大范围 Goal 正式完成，后续行动仍遵循现有规范和具体授权。

审核须逐条阅读正文及必要来源，记录具体修改问题和待核实项。字段齐全只是必要条件，名称或数量检查不能代替语义审核，也不新增评分、自动审批或日常逐动作检查机制。

#### 精简边界与自主空间

提示词应明确任务边界与完成条件，并为 Agent 保留普通执行细节的判断空间。精简以信息完整、准确且可执行为前提，只处理无实际作用的限制与重复表述；不以字数、条目数量、长短一致或压缩比例为目标，也不因一条提示词较长就整体改写。

| 内容 | 保留与精简的判断 |
| --- | --- |
| 字段与必要信息 | 所有提示词仍保留 8 个固定字段和适用的按需字段。目标、输入、范围、授权、约束、交付、验证与完成条件须能直接理解或准确追溯，不能压成依赖猜测的短语。 |
| 执行方法与依赖 | 普通实现细节允许 Agent 按事实选择；已有规范负责的通用流程准确引用。影响正确性的先后依赖、工具契约和本次特有步骤须保留；任务本身用于验证流程时，实际经过的阶段及证据也是必要交付。 |
| 报告与交付格式 | 提示词的固定字段不等于报告必须使用固定章节。报告应完整覆盖所需信息，章节、顺序和展开程度可按内容组织；用户明确指定，或确实服务复用、对照、交接、工具处理的结构仍保留，不一律取消表格、编号或模板。 |
| 同义内容与提醒 | 同一规则在所属字段完整说明，其余位置按需概括或引用。帮助恢复上下文、避免遗漏的短提醒，以及完成条件对关键结果的概括可以保留；只合并没有新增作用的复述。 |
| 保护、异常与验收 | 数据与原件保护、停止及恢复条件、实际人工接受、验证证据和完成边界不得因篇幅删弱。固定数量或顺序若定义真实任务范围或工具行为，不能仅因形式固定就判为过度要求。 |
| 修改依据与核对 | 先指出具体片段的重复、无用途限制或与权威规范的重叠，再选择局部改写。改后核对适用条件、必要信息、依赖和授权均有明确落点，验证义务与完成含义未变；没有充分依据的部分保留，不顺带扩大精简范围。 |

### 路径校验的职责

校验工具只从 JSON 计算应有相对路径，与实际场景文件路径集合比较，报告缺少、多余、重复或不合法的名称。非法路径名称应报错，不能静默替换字符使对应关系失真；读取 JSON 时不能静默覆盖重复键。无需读取场景正文、解析提示词声明或新增元数据。结果可作为简短清单供 Agent 阅读，不维护缓存或第二份手工登记。

路径一致仅证明目录对应关系；正文一级标题和内容是否符合单一场景仍由内容审核核对。路径匹配不能证明提示词语义、Skill 行为或实际运行已通过。迁移期间如实报告未完成项，不靠空页面、同文复制或忽略差异宣称覆盖完成。

## Skill 的评价维度

| 维度 | 检查问题 | 不能直接推导拆分的情况 |
| --- | --- | --- |
| 用户意图 | 用户是否实际要求不同结果，能否分别提出并独立完成？ | 同一需求有不同说法 |
| 触发场景 | 不同入口是否需要不同前提、方法和结束位置？是否在一个入口中重新选择不同任务？ | 多个触发词指向同一项工作 |
| 输出结果 | 是否存在可独立交付、独立验收的成果或互不相干的完成条件？ | 同一成果有多条验收条件、支持文件或多种表示格式 |
| 变化原因 | 某部分是否因独立需求变化，并持续牵动无关部分？ | 同一目标需要同步调整几个步骤 |
| 外部依赖 | 某职责是否迫使其他职责承担不需要的系统、权限或配置？ | 同一个目标确实需要多个工具 |
| 状态生命周期 | 是否存在独立开始、暂停、恢复和结束的工作，其状态与清理是否互相干扰？ | 一条完整流程包含多个阶段 |
| 授权与副作用 | 只读分析、规格写入和实现修改等边界是否清楚？调用前能否预知执行范围？ | 已授权的一项任务修改多个相关文件 |
| 拆分收益与衔接成本 | 拆开是否更易选择、理解和验证？会不会复制规则、反复交接或重新索取既有授权？ | 文件更短或 Skill 数量更多 |

### 能力划分与正式审核

按可复用能力和独立交付结果组织 Skill，不按 Stage、步骤、文件数量或场景名称机械拆分。一个职责明确的 Skill 可以编排同一目标所需的多个步骤，按需调用其他方法；具体方法及权威规则仍保持单一来源。阶段之间有必要依赖，不等于职责混杂。多个场景可以共享同一 Skill，同一能力也可以跨阶段使用；场景与提示词一对一，不要求场景与 Skill 一对一。

同一功能的实现与正式审核必须使用两个独立 Skill，不在同一 Skill 中切换“实现模式”和“正式审核模式”。实现入口负责获准编写、修改及必要作者自查；正式审核入口只读被审成果，交付问题、依据与结论，修复交回实现负责人。两者可以引用同一份规则或纯参考，不能复制两套评判正文。

两个 Skill 还不等于独立审核已经成立。正式独立审核须由未参与被审成果创作的独立实例执行，核对实际上下文和权限；作者加载审核 Skill 仍不能把自查称为独立审核。拆分不增加每次实施后必经的审核关卡，审核范围与时机由本次请求及已有契约决定。

### 入口、正文与完成边界

| 原则 | 应落实的要求 |
| --- | --- |
| 轻量入口 | Skill 可以只承担常用入口，但须说明何时使用、必要输入、允许动作、交付结果及何种条件下读取哪份正文；不要求复制完整流程，也不能只留下无条件的“读某文档”。 |
| 唯一正文与必要提醒 | 同一作用域内的同一规则只维护一份完整正文，其他位置保留条件明确的引用及必要防漏提醒。提醒频繁出现本身不是删除理由；框架与生成项目的不同职责、部署范围应分别判断。 |
| 覆盖真实调用路径 | 条件引用须能从实际会进入的路径触发，包括直接调用、续接与跳过上游准备的情况。文件存在或创建入口有提醒，不能证明后续直接运行的入口已读到约束。 |
| 按需增加能力 | 高频使用是发现候选入口的线索，仍须比较复用、补引用、合并与新增的收益；不因为重复出现就新建 Skill，也不为每条场景复制一个入口。 |
| 授权连续而不扩张 | 既有具体授权跨 Skill 和阶段沿用，方法返回不取消尚未完成的获准工作；只读、只讨论、暂停、人工验收和提交条件仍有效。审核结论不授权修复，已获准的修复由原负责人继续，不在只读审核实例内执行。 |
| 不制造附加流程 | 新增入口不自动新增 Stage、固定全套调用、批准轮次、报告、台账或监督脚本；复用现有记录和完成契约。 |
| 验证证据分层 | 分别报告格式与链接检查、静态语义和情境推演、实际加载后的有限试用、客户端发现/触发、真实工具运行与人工验收。按变化需要选择验证，不要求每次全套执行，也不把其中一层的通过写成另一层已通过。 |

审核须读实际正文及影响职责判断的 references、调用方和权威规范，不能只看名称、description 或触发词。还要横向检查不同 Skill 是否重复维护同一事实、输出或规则。内含独立路径时分别评价，不能用一条笼统结论覆盖所有路径。

## 脚本的评价维度

先按公开命令或调用接口评价，再决定是否拆文件。一个文件包含多个子命令时分别检查每个命令；没有命令行的 Godot 工具模块对应检查公开方法、返回值、错误信号与对象生命周期。入口、实现模块和共享函数可以采用不同的拆分粒度。

| 维度 | 检查问题 | 需要调整的典型信号 |
| --- | --- | --- |
| 调用目标与参数 | 一次调用完成什么？参数是否围绕同一操作？ | 大量互斥参数实际选择几套独立任务 |
| 输出与成功条件 | 返回值、退出码和输出是否表达同一个操作结果？ | 当前操作成功，却因另一任务未完成而报失败 |
| 权限与副作用 | 调用者能否预知读写、删除、进程启动和外部影响？ | 查询入口隐含写入，普通操作要求无关高权限 |
| 失败与重试 | 失败后应重做什么？哪些修改必须共同成功？部分结果如何保留？ | 重试会重复另一项写入，部分成功无法解释 |
| 资源与生命周期 | 进程、连接、临时文件和缓存由谁创建、持有、停止和清理？ | 独立任务共享模糊状态、互相清理，或拆分后丢失资源所有者 |
| 依赖与运行环境 | 每条路径是否只需适用依赖？能否按需加载？ | 简单查询被不相关的引擎或处理依赖阻塞 |
| 变化原因与验证 | 修改一项能力是否需要理解并验证大量无关能力？ | 无关需求持续修改同一部分，相关行为难以独立验证 |
| 拆分成本与共享实现 | 拆开是否减少耦合？稳定的解析和规则能否共享？ | 拆分复制逻辑、增加无意义的中间文件或调用层 |

命令应有明确目标、允许的副作用和成功条件。相关命令可以放在同一脚本，共用解析或校验函数；不因被多个场景调用而复制脚本。参数变化、输出格式变化、多个依赖或有意的原子操作都不是单独拆分依据。

例如，查看记录的成功条件应围绕是否成功读取并显示；判断全部完成条件应由明确的检查入口承担。显示业务尚未完成的信息与读取失败应可区分。创建项目包含检查目标、复制文件和建立 Git 仓库与初始提交，这些步骤共同交付一个独立项目，可以保留为一个命令。审核具体实现时仍需核对既有调用方契约和失败行为，不因例子预先裁定修改方案。

## 文本编写的评价维度

审核 AGENTS、Skill、脚本说明、提示词和手册时，同时评价表达是否准确、容易查找和执行，不只检查路径或技术行为。

编写、修改及作者自查使用 [Codex 指令编写 Skill](../../../.agents/skills/writing-for-agents-yaya/SKILL.md)；正式只读审核使用 [Codex 指令审核 Skill](../../../.agents/skills/review-agent-instructions-yaya/SKILL.md)。两者按任务引用同一份[指令设计参考](../../../.agents/skills/writing-for-agents-yaya/references/agent-instruction-design.md)，本准则继续拥有职责评价、提示词字段及审核覆盖契约，各入口不另立一套标准。

已确认的框架说明文字，其表达与组织使用[框架文档编写 Skill](../../../.agents/skills/technical-documentation-writing-yaya/SKILL.md)；生成项目的写法由独立的 [Godot 文档编写 Skill](../../../project-source/skills/technical-documentation-writing-godot/SKILL.md) 负责。下表保留审核问题与框架特有要求。

| 维度 | 检查问题 |
| --- | --- |
| 标题与术语 | 标题能否独立说明对象和目标？名词、动作与状态是否按[公共术语](../../docs/terminology.md)一致使用？是否用“正常”“成功”等含糊词代替可验证结果？ |
| 信息层级 | 并列事项是否按主题分项，先后步骤是否仍保留顺序？多专题文档是否有对应实体分类目录，而非索引分组、正文仍平铺？是否存在无用途的过深目录或空分类？ |
| 内容归属 | 概念、执行步骤、权威规则、工具契约、历史报告是否各有所属？同一事实是否被复制到多处？能否改为必要解释与来源链接？ |
| 执行清晰度 | 输入、前置、实际 Agent/Skill/命令、允许副作用与完成结果是否明确？是否把模板值、文件存在或旧日志当成当前通过？ |
| 简洁与必要性 | 能否删掉重复和无实际作用的指令而保留边界？是否用一行堆叠多个独立事项，或反过来将紧密相关短语过度分层？ |

表达问题与职责问题分别判断：措辞不清可以只改文字；独立目标、权限或生命周期混杂则追查实际职责。不用统一字数、列表数量或固定目录深度代替判断。修改方案应先定位唯一正文，再同步必要引用，不靠增加同步程序补救重复来源。

## 审核覆盖与结论

全量审核先枚举真实对象，明确生产入口、共享模块、第三方和验证夹具的范围。每个范围内对象都须有结论；不能以抽样、目录清单、关键词命中或读取说明替代审核。引用材料按判断需要追查，不以未读取正文的对象计入已审核。静态审核与真实运行分别报告。

| 可用结论 | 含义 |
| --- | --- |
| 保留 | 职责一致，组织合理 |
| 收窄范围或改名 | 入口承诺或描述不清，未必需要拆实现 |
| 拆分入口 | 不同任务需要明确选择，底层实现仍可共享 |
| 拆分 Skill 或实现模块 | 职责、依赖或生命周期能够独立成立 |
| 提取共享方法 | 多处重复同一规则或算法，应保留一份实现 |
| 合并或删除 | 用途重复、过度拆分或失去必要性 |
| 证据不足 | 无法支持保留或调整，明确还需什么依据 |

每项结论说明实际职责、文件位置或可核实依据、判断理由、最小调整以及受影响调用方。简单保留项可汇总成表；复杂问题单独展开。拆分建议说明各新职责的输入、输出与结束位置，并核对授权、状态、原子性、重试和清理责任是否丢失。

框架整体审核报告分别给出以下结论，详情引用同一问题，避免重复展开：

- **文本编写**：标题、术语、内容层级、目录和正文归属。
- **Skill 职责**：意图、触发、输出、变化原因、依赖、生命周期及授权边界。
- **脚本职责**：公开命令或接口的目标、成功条件、副作用、失败重试、资源所有者及共享实现。
- **提示词与场景**：一个入口是否只对应一个同名场景，输入、目标、范围与出口是否一致。

每类写清实际覆盖、判断依据和最小建议；未发现问题、证据不足和未涉及分别说明。限定范围审核只评价相关对象，不借四类汇总扩大为无关全量审核。

报告保存于 `framework/review/reports/`，写清检查版本、范围、执行者及未验证项。报告中的建议不自动授予修改被审核实现的权限。用户指定由子智能体审核时，由子智能体独立形成结论；协调者负责范围覆盖、报告归档和结构核对，不能把自己的复述称作独立审核。

## 维护与应用

新增对象或实质改变职责时，按对应维度判断并核对调用方、源规范、复制映射、说明和相关验证；普通局部修改不触发无关全量审核。调整框架路由或完成机制时，仍须按根规则检查 advisor 及其场景参考，不能在提示词或 Skill 中复制另一套流程。

本文件保存长期准则；场景写法见[编写要求](../../docs/quick-reference/README.md)，总体取舍见[设计复盘](design-quality.md)。审核报告保留当次事实，[框架待办](../../progress.md)只保留后续工作，不把报告或旧待办当作最新运行结果。

根据真实误触发、职责冲突或维护成本修订相应条款与正反例，同时核对受影响引用。避免仅为单个异常叠加全局限制，也不增加独立规则版本号、评分或自动审批流程。
