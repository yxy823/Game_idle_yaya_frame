# 使用场景覆盖与职责入口

本文件维护当前场景范围与提示词导航，不是逐项必跑清单，也不以篇数或路径匹配证明真实流程已经通过。单一职责与一对一契约见[职责设计准则](skill-script-prompt-design.md)，正文入口见[场景索引](../../docs/quick-reference/scenario-index.md)。历史版本和过去验证通过 Git 查阅，不混入当前通过声明。

## 范围与责任

| 领域 | 当前责任与边界 |
| --- | --- |
| 框架维护 | 评估、借鉴、修复、删减、目录整理、静态/动态审核分别有专用入口；维护源与外部验证项目分开 |
| 创建与环境 | 创建器复制并建立独立 Git 与初始提交；配置、更新、路径恢复和首次扫描分别处理；环境可用不代表业务通过 |
| 需求与专业来源 | design-gdd 可从零形成或维护 GDD，整体范围与排除项归《设计范围与边界》，当前未决设计归固定的《开放问题》，供后续讨论、规划、审核和相关实验使用；局部规则留在所属主题；design-balance 维护获准数值主题，product-author 只维护交付范围；专业文档引用已有细节，术语由 project-terminology 维护，开发约束归 Project Rules |
| 任务规划 | 先预拆分当前约定范围，再逐个细化 Product 并完整拆分 Feature；首次 R000、后续追加、来源变化与基线恢复分别处理；保留 ID 和真实完成历史 |
| 实现与修复 | 新任务执行、原型、交付前后 Bug、重构和 maintenance 明确目标；feature-execute 编排完整交付，专业方法不另建 Stage |
| 素材与诊断 | 准备、接收、技术审核、按类型新增与替换资源分开；已定方向的变化追查消费者；临时观测与持久指标分开；测量诊断与优化分开 |
| 验证与人工 | 解析/lint、自动测试、实际场景、独立专业/代码审核、清单准备及两种真实结果登记分开；测量结论由独立实例核实；无 Feature 组件测试使用 --target；不互相代替证据 |
| 恢复与交接 | 区分报告路径、原件缺失、内容过期和运行中断；同目录暂停、切换、原/新对话续接保持真实停点；无 Feature 的研究、讨论和独立审核有实际任务入口，不为续接创建任务 |
| 知识 | 只读总结、知识写入与脚本实现分别有入口，先查已有覆盖，不因复盘自动新增规则 |

具体场景名称、前提与出口统一查[场景索引](../../docs/quick-reference/scenario-index.md)。提示词正文分别由 [Godot 开发库](../../godot-development-prompts.json)与 [Yaya 维护库](../../yaya-maintenance-prompts.json)维护，路径检查器直接读取这两份 JSON；此处不重复登记名称、数量或路径。
