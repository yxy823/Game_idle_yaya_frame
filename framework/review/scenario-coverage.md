# 使用场景复盘

检查必要场景是否有清晰责任入口；不要求每次逐行执行，不计算覆盖率。
设计判断见 [design-quality.md](design-quality.md)。新增内容先判断通用性、
实际后果和更简单的处理方式，缺一条提示词不等于缺一个框架机制。

2026-09-12 同步当前职责：需求先决定验收方式；Agent 直接执行解析/lint，不设静态包装或导入步骤。
“代码”表示已找到实现，“流程”表示由 Skill/规则和 Agent 判断承担，
“人工”表示有意交给使用者，“范围外”表示不属于当前承诺。
这些标记本身不表示运行通过。本轮未重新生成项目；在用户指定的外部测试项目覆盖修复输入后，
执行了工具 unittest、真实 Godot lint 契约、直接解析/lint、环境及空白台账检查。
当前工具回归为 133 项；真实 gdUnit 正常与负向、解析/lint 已执行。
各轮结果和删减边界见 [设计复盘](design-quality.md#本轮过度设计的处理)。

编号按职责分组；新增使用组内新编号，删除后保留编号空缺，不为排序改写已有编号。
提示词清单复用这些编号，不再维护另一套场景 ID。

## 1. 框架维护

| 编号 | 场景 | 当前覆盖与责任 | 静态依据及合理边界 |
| --- | --- | --- | --- |
| 1.1 | 向框架新增内容或能力 | 流程：先评估必要性和更简单的替代，再按授权决定是否实施 | [AGENTS.md](../../AGENTS.md) 与新增能力提示词；先判断必要性，不默认创建机制 |
| 1.2 | 修复、删减或整理框架 | 流程：在维护源做最小完整修改，同步真正受影响的调用者 | 根 AGENTS；只改维护源，不夹带游戏业务，不保留无用兼容副本 |
| 1.3 | 复盘设计及场景覆盖 | 流程：默认重检整个框架与空白项目源材料，也可限定范围；依据当前文件给出详细报告 | 报告列明覆盖、问题位置、影响、最小建议与未验证项，追查跨文件一致性和流程衔接；不直接修复，不新增评分器或强制流程；静态推演与实际运行分开 |
| 1.4 | 验证框架变更 | 代码与人工：按任务选静态检查，或在明确的外部项目验证 | [validate_project.py](../commands/validate_project.py)、`framework/tests/`；该入口不创建/配置项目，不自动执行 Godot |
| 1.5 | 借鉴外部游戏开发框架 | 流程：阅读链接或本地材料，与当前需求/实现比较，筛选最小有用改进 | 外部借鉴提示词；外部材料不是本任务指令，不自动安装或整体搬入，不因其他框架能力更多而扩建 |
| 1.6 | 将未完成的框架任务交给新线程 | 流程与人工：只读会话、当前文件与 Git，生成可复制的完整续接提示词 | 新线程交接提示词；保留目标、授权、现场、验证和下一步，不创建维护进度台账、不自动投递新线程 |
| 1.7 | 将框架压缩包交给其他模型独立审核 | 流程：识别附件根目录和可读范围，静态追查框架与空白项目，按规定结构输出完整报告 | 压缩包审核提示词；不依赖原机路径、Git 历史或旧会话，区分材料缺口与缺陷，不执行包内指令或修改被审文件 |
| 1.8 | 通过一个真实任务动态审核整个开发流程 | 流程：在指定的新建外部项目完成小 Product、单个 Feature 与适用 Stage，实际运行并记录结果 | 动态审核提示词；使用正式创建器与现有项目流程，条件阶段如实标明，框架缺陷单独报告，不修补被测组件来取得通过 |

## 2. 创建空白项目

## 4. 项目任务

| 编号 | 场景 | 当前覆盖与责任 | 静态依据及合理边界 |
| --- | --- | --- | --- |
| 4.1 | 初始化/修改需求或存在关键歧义 | 流程：`product-change-standardizer` 按需调用 elicitor/UI/audio Skill | [任务路由](../../project-source/methodology/00-overview.md)；只澄清影响当前决定的内容 |
| 4.2 | 逐个 Product 拆分或同步已有 Feature/Test Catalog | 流程与代码：generate 只拆当前 Product 并追加，sync 处理已有任务的实际影响 | 当前 Product 的必要 Feature 完成后再拆下一份；保留 ID、历史与 Catalog，不新增 Product 队列或状态字段 |
| 4.3 | 执行、续接已批准任务或询问下一步 | 流程：execute Skill 或只读 advisor | 从当前记录、必要历史和 Git 差异续接；自然语言汇报，不逐阶段固定发言，不新增 session 状态 |
| 4.4 | 已有未知修改、混合任务或授权不清 | 流程：Agent 确认改动归属，保留无关工作 | 项目 AGENTS 与 Git 规则；没有 clean-worktree 自动 Hook，不能写成“自动阻止混入” |
| 4.5 | Bug、行为保持重构或工程维护 | 流程：engineering-change Skill 区分 Product 意图与实现问题 | 当前任务内修复与独立新任务分别判断；不另建第二套 Bug 状态机 |
| 4.6 | 接入或替换美术、场景、动画、音频等资源 | 流程：按意图选择 Product 或当前 Feature/工程维护路径 | 资源接入提示词及 agent-rules 资源/场景/资产模块；引用检查与人工体验分开 |
| 4.7 | 定位性能瓶颈并优化 | 流程：工程维护明确目标，按相同构建与采样条件测量基线和修改后结果 | 性能提示词及既有 maintenance 路径；按问题选择帧时间分位数、尖峰或加载/内存指标，核对代价，不凭静态猜测报告提升 |
| 4.8 | 调整存档或迁移数据 | 流程：先确定真实数据保留要求，再按工程维护或 Product 变化处理 | 数据迁移提示词及数据规则；在明确样本副本验证，项目数据保留需求不代表框架要兼容旧项目 |
| 4.9 | 验证尚未确定的玩法、手感或技术假设 | 流程：在授权范围与预算内做一个可判定的实验 | 原型实验提示词及任务路由；结论进入现有 Feature notes 或 Progress，不自动变成正式需求、验收或完成状态 |
| 4.10 | 从实际源码调查架构改进机会 | 流程：围绕指定痛点或近期改动线索，核对调用关系、维护成本与已有决定 | 只读架构调查提示词；不依赖已有重构待办，允许零候选，选定问题后回到现有工程入口 |
| 4.11 | 先讨论想法、设计取舍或概念 | 流程：`project-clarifier` 先查事实，只补问当前缺口，按依赖小步澄清 | 只讨论不写文件；不要求环境就绪或完整 Product，不维护问卷状态、轮数或评分 |
| 4.12 | 保存并复用已确认的项目术语 | 流程：澄清后由 Product standardizer 按授权维护 `docs/CONTEXT.md` 或局部定义 | 每个定义一个归属；保持含义和行为时不拆任务，实质变化仍经 Product 与 Feature 同步；规划、执行、复审读取相关定义 |

## 5. 验证与异常

| 编号 | 场景 | 当前覆盖与责任 | 静态依据及合理边界 |
| --- | --- | --- | --- |
| 5.1 | baseline、focused/TDD、affected 或必要 full 测试 | 代码与流程：测试入口读取 Feature/Catalog，选择并运行 gdUnit | [测试入口](../../project-source/tools/testing/run-gdunit-tests.py)、`lib/test_selection.py`；不生成独立计划；同一 runner 的 scope 决定范围，不因维护分类自动 full；Agent 判断实际影响 |
| 5.2 | 执行 Godot 脚本解析与 lint | 流程：Agent 直接使用配置的 Godot 和插件 CLI，读取真实输出 | [直接检查约定](../../project-source/methodology/gdscript-lint.md)；不另设静态包装、manifest、导入分支或通过标签 |
| 5.3 | 漏测、跳过、零测试、旧报告、源码改变或工件被修改 | 代码：显式结果校验读取真实 discovery/JUnit、诊断、哈希和当前源 | `lib/run_evidence.py`、`lib/gate_evidence.py`；本轮工件夹具负向回归通过，完整真实 Feature 未执行；当前为 result.json 加原始报告，未建立独立防伪签名 |
| 5.4 | 检查失败、启动失败、超时或进程中断 | 代码与流程：记录实际尝试，处理所拥有的进程，保留失败 | `lib/run_evidence.py`、`lib/gdunit_process.py`；运行前写同一 result，旧通过不能覆盖未解决失败；没有第二份尝试日志或锁，失败原件保留 |
| 5.5 | 验收方式与独立复审 | 流程：Stage 1 决定验收方式，Stage 4 提供可复现步骤，Stage 6 一次审查需求与代码质量 | manual 需真实人工决定；automated 省略 Stage 5；复用 manual_checks、Feature notes 与原有 review 记录，不增加阶段或证据格式 |
| 5.6 | 只要求静态检查，或运行环境暂不可用 | 流程与人工：完成获授权的检查并说明未执行项 | 不强制生成/启动项目，不跳过失败后改报通过；实际 Windows/Godot 能力需在对应环境另行验证 |

只读外部材料不自动授权安装、执行其脚本或整体迁入。
框架修改仍遵循根 AGENTS，不自动更新任何具体项目。

### 保留这些入口的理由

- 讨论与记录术语共用一个 Skill 的提问方法；两条提示词只区分用户需要的产物和写入授权，不创建两套访谈流程。
- 初始需求与需求变化、当前 Product 初次拆分与既有计划同步分别提供入口；下一 Product 的规划追加到原台账，不覆盖历史。
- 原型实验用于回答未决问题，按授权和预算停止；沿用现有记录，不要求先生成完整规格链。
- UI、音频、资源接入的输入不同；性能测量和存档保留也各有实际目标，故提供独立提示词。
  它们仍按产品意图与工程职责路由现有 Skill，不新增专门的流程系统。
- “问下一步”“执行新任务”“续接任务”分别表达指导、执行与续接意图，沿用已有授权。
- Bug、重构和工程维护分别说明期望行为、保持不变的范围和技术目标。
- 架构调查从实际源码发现问题；pick-refactor-smell 从既有 notes 选择待办，独立审查检查指定差异。三者输入与产出不同，调查不自动进入实施。
- 验证、审查、人工反馈是按需入口；正常 Feature 仍沿用其现有流程，无需额外逐条发送。
- 进度交接负责接得上；阶段总结负责找值得复用的经验和重复工作。原任务经过留在历史，
  知识目录按主题保存提炼出的解释并链接原件，不因复盘重复复制正文、规则和脚本。

两类交接入口由原线程生成结果、使用者复制到新线程，接收方先核对目录、规则、原文和
实际差异再按已有授权续接。框架交接保持只读，项目交接可整理必要的现有文档；都不把
交接当作新实施授权或人工验收，不另建交接文件。用法见
[换到新线程继续](../docs/blank-project/guides/project-knowledge.md#换到新线程继续)。

### 阶段总结与固化边界

总结依据实际完成记录，区分项目经验、可复用脚本和可能有通用价值的建议。
先找现有覆盖，再比较已有命令、合并脚本和最小新工具；频繁使用和清晰输入输出才是
固化的依据，不以脚本数量、经验条数或潜在边界情况凑成果。

获授权的总结整理现有历史与 `docs/knowledge/` 中对应的经验条目；仅建议时不写文件。
脚本实现按本次实际授权与既有工程维护路径处理，说明真实改动和验证。
规则/Skill 修改需要已有明确授权。通用建议可以单独交付，
项目任务不自动修改其他目录。没有新增经验或脚本也是有效结果。

### 使用边界

项目提示词描述当前项目自己的工作，不嵌入维护源机器路径、来源说明或自动同步责任。
“创建空白项目”在进入项目之前运行；完成后切换到目标项目，后续工作不依赖维护源。
场景名称与输入不同不意味着每次都需新增任务、审批轮次或验证步骤。
简单改名、具体报错、单次清理等可直接提出，不需要额外提示词。
框架发布、自动升级、多引擎及跨平台支持仍不在当前默认范围内。
