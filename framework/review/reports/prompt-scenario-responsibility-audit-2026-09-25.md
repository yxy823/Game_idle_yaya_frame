## 检查基线与范围

本报告由子智能体 `audit_all_prompts_scenarios` 独立形成，日期为 2026-09-25。检查基线为提交 `8fe14d6e4f63fe824eef485d34ea6313f31ac65f` 的提示词、八篇场景样稿、相关 Skill 和工具；审核期间主智能体正在补充职责准则及维护入口。结论采用本轮已确认的[职责设计准则](../baselines/skill-script-prompt-design.md)，不把正在进行的规则文档更新当成被审入口已经修复。

完整读取 [prompts.json](../../prompts.json) 的全部 50 条正文：`Yaya 框架维护` 10 条，`Godot 项目开发` 40 条；完整读取 [场景目录](../../docs/quick-reference/scenario-index.md)中的全部 8 篇样稿。下表按 JSON 中的实际顺序编号，编号仅用于本报告定位，不是新场景 ID。JSON 每条正文保存在一行，表中行号指向该键及完整正文。

定向追查了样稿使用的 Skill、工具入口、首次规划和 Bug 路由规范，以及提示词名称的导出与文档调用方。这里不代替另外两份 Skill 和脚本全量审核，不声称逐一审查了这些目录的全部实现。没有执行提示词、项目工具、测试、项目创建、Godot 或 HTML 构建。

## 总体结论

现有库包含明确的多场景入口，需要先重新划分提示词正文，再建立对应场景，不能只改标题。最明显的混合是：评估与实施、已有实现的文档补录与实际交付、首次与后续规划、交付前后 Bug、规格与实现、性能诊断与优化、验收清单准备与验收结果登记、总结建议与知识写入及脚本实现。

同时应保留真正完整的一项工作。例如创建空白项目中的复制和 Git 初始化，动态流程审核中的创建、规划、执行和报告，都共同服务于各自唯一的交付目标。不能因为阶段多、检查对象多或允许选择报告输出位置就一律拆分。

## 50 条提示词的逐项判断

表中“改名”表示采用具体情境标题，迁移时提示词名、场景文件名和 H1 三者同时采用同一名称。“拆分入口”不要求为每个入口复制 Skill 或脚本。后续已明确的实施授权仍然有效；拆分仅让单次入口的目标可识别，不能重新引入逐阶段重复确认。

### Yaya 框架维护：10 条

来源：[prompts.json](../../prompts.json)，行 6–17。

| 序号与行号 | 当前提示词 | 实际职责与判断依据 | 结论及建议场景 |
| --- | --- | --- | --- |
| 1 · 行 6 | 向框架新增内容或能力 | 输入允许“先评估建议”或“已授权实施”。前者只产出必要性、成本和落点；后者修改维护源、验证并提交，两种结束位置能够独立成立。 | **拆分入口**：“想给框架增加一项能力，先判断是否值得做”；“新增能力的方案已确定，现在修改框架”。第二篇直接消费已确认范围，不重新进行完整方案问答。 |
| 2 · 行 7 | 借鉴外部框架的有用设计 | 外部比较报告与把选中设计引入当前框架混在同一输入开关中。实际读取参考、许可边界属于比较；实施额外需要所选项和写入范围。 | **拆分入口**：“看到外部框架的一个设计，先判断是否适合借鉴”；“已经选定外部设计，现在引入框架”。后一入口保留出处、必要许可核对和最小引入范围。 |
| 3 · 行 10 | 修复、删减与整理框架 | 同时接受已复现缺陷、重复机制删减、文件目录整理，成功条件分别是错误消除、职责接替无缺失、引用及复制路径正确。只用“最小修改”无法说明是哪项交付。 | **拆分入口**：“框架出现可复现问题，需要修复”；“框架中两套机制重复，需要合并或删减”；“框架文件位置混乱，需要整理目录”。共享 Git、引用检查和维护方法，不在整理入口改变 Skill 行为。 |
| 4 · 行 11 | 静态审核框架与空白项目源材料 | 对当前工作区做静态审核，范围和报告保存位置是同一报告任务的参数；八类检查主题不是八个独立执行授权。 | **保留并改名**：“想检查本地框架是否自洽，先做静态审核”。保持报告写入与被审文件修改分离；后续实施请求另按其已经明确的范围继续。 |
| 5 · 行 12 | 静态审核 GitHub 框架快照 | 固定远端 SHA，读取快照，产出有证据的独立报告；与本地工作区入口的版本来源、可见文件和权限边界不同。 | **保留并改名**：“想请独立 Agent 审核 GitHub 上的框架快照”。不能与第 4 条仅以一个路径参数合并；报告格式较长不是职责混合证据。 |
| 6 · 行 13 | 通过实际任务动态审核框架流程 | 一个微型任务贯穿创建、规划、执行、报告，唯一目标是取得一条实际流程的证据。框架源只读，验证项目可写，边界明确。 | **保留并改名**：“想用一个小任务实际验证框架流程”。有界流程编排合理；清理“创建器只复制、不加入 Git”的旧措辞，见后文，避免误写创建职责。 |
| 7 · 行 14 | 复核外部审核结果并讨论取舍 | 外部意见、被审版本与当前版本是输入；逐项核实事实及改法，唯一交付是可供选择的复核报告。后续授权说明不属于当前实施分支。 | **保留并改名**：“收到外部审核意见，先核实哪些值得修改”。报告写文件是输出方式；不因此拆另一条提示词。 |
| 8 · 行 15 | 依据实际开发反馈复盘框架 | 输入是别的实际项目输出，产出归因与建议；无需亲自重跑。给接收方起草下一步文本是归因结果的表达，不执行修复。 | **保留并改名**：“实际开发遇到问题，想判断框架是否需要改进”。保留与动态审核、正式外部意见复核的证据来源差异。 |
| 9 · 行 16 | 按需验证框架变更 | 静态阅读与在外部项目实际运行共用入口，后者还可能创建新项目、配置环境；目标位置、权限、结果含义不同。 | **拆分入口**：“框架刚改完，只检查文件和引用”；“框架刚改完，在指定外部项目验证工具行为”。验证项目缺失时转创建/准备场景，不让验证页再承担另一套建项目流程。 |
| 10 · 行 17 | 生成新线程交接提示词 | 只读整理维护任务、会话和 Git，输出可复制交接文本，不保存项目状态或启动新任务。职责单一。 | **保留并改名**：“框架任务还没做完，准备换一个对话继续”。去除 worktree 续接与专门的未知改动归属处理；保留实际目录、真实差异和不覆盖现有内容。 |

### Godot 项目开发：创建、需求与规划，17 条

来源：[prompts.json](../../prompts.json)，行 25–45。

| 序号与行号 | 当前提示词 | 实际职责与判断依据 | 结论及建议场景 |
| --- | --- | --- | --- |
| 11 · 行 25 | 复制并迁移旧框架项目 | 默认只读分析；也可执行副本迁移、格式适配、验证、Git 历史接入和交付。分析方案与真正迁移的原件保护责任、写入及失败现场不同。 | **拆分入口**：“旧项目想采用当前框架，先评估复制迁移方案”；“复制迁移方案已确定，现在迁移旧项目”。复制与必要格式转换共同交付独立副本，可留在第二篇；原件只读、历史不伪造、真实数据副本验证必须保留。 |
| 12 · 行 26 | 创建空白项目 | 一个明确空目标，复制清单后由创建器初始化独立 Git 与首次提交，交付独立空白项目即结束。 | **保留并改名**：“准备开始新游戏，先创建空白项目”。不拆“复制”和“初始提交”提示词，也不扩成环境与 Feature 开发入口。 |
| 13 · 行 27 | 准备 Godot 开发环境 | 首次配置要求完整初始化报告；后续更新只改指定路径/工具、追加记录并复用原环境信息。状态与报告动作已由正文分别定义。 | **拆分入口**：“空白项目已经创建，现在配置开发环境”；“工具位置或版本变了，需要更新项目环境”。缺工具/版本不符的恢复场景另收录；不能自动寻找替代引擎。 |
| 14 · 行 30 | 调研外部资料与技术方案 | 输入是一个待回答的问题及版本约束，输出有依据的调查结论；直接查询或 researcher 委派是执行方法，报告是否保存是表达方式。 | **保留并改名**：“方案有一个外部问题没确定，需要查资料”。不因是否委派、是否保存报告拆重复场景；不开展本地实验或实现。 |
| 15 · 行 31 | 从已有实现补齐需求与任务 | 文档补录模式不运行、不改实现、不办理完成；交付模式由执行 Skill 补验证、修复和实际收尾，两个契约正文已明确分开。 | **拆分入口**：“功能已经写出来，需要补齐需求和任务记录”；“已有实现和任务已对齐，现在补验证并办理交付”。后一篇保留实际人工验收、当前完成时间及允许修复范围，不能从代码存在倒推完成。 |
| 16 · 行 32 | 只读适配外部需求内容 | 各种外部文本都被整理成同一种未写入、未执行的工作流适配草稿。输入可包含 Bug/产品/工程片段不意味着当前执行多个任务。 | **保留并改名**：“拿到一份外部需求，先整理成项目可用的草稿”。保持原件、未决项和建议的身份，不把适配变成正式写 Product。 |
| 17 · 行 33 | 轻量讨论与澄清 | 只读当前事实，讨论一个问题，结束于结论与待定事项；话题或问法多样，输出与副作用一致。 | **保留并改名**：“有一个项目问题没想清楚，先讨论”。同类问题可以一起询问并提供推荐，避免“小步讨论”被解释为每轮只能一两问；该措辞改进不需要新增 Skill。 |
| 18 · 行 34 | 澄清并记录项目术语 | 澄清用于形成已确认定义，随后写术语及引用，目标是消除同一概念歧义；明确排除改变行为、规划和实现。 | **保留并改名**：“项目里同一个词有不同理解，需要统一并记录”。澄清和保存共同交付可用定义，无需强拆两次；后续 writer Skill 的拆分须同步此调用。 |
| 19 · 行 35 | 验证视觉、玩法或技术假设 | 视觉使用真实素材/独立场景和用户感知，玩法实验验证循环或手感，技术实验验证实现可行性；证据与方法显著不同。 | **拆分入口**：“界面效果还没确定，先用真实素材试一下”；“玩法效果还没确定，先做小实验”；“技术方案是否可行还不确定，先做验证”。都限定一个假设和预算，保留共同实验记录方法；不要把第 1 篇与已确认界面的实现样稿混用。 |
| 20 · 行 36 | 从想法或已有 GDD 整理 Product 并衔接规划 | 同时覆盖无正式需求的访谈、已有 GDD 的适配、既有 Product 增量变更；输出又可选仅文档或文档加计划。输入充分度、原件保留和写入集合不同。 | **拆分入口**：“只有游戏想法，需要整理第一份 Product”；“已有 GDD，需要整理为项目 Product”；“已有 Product 的要求已改变，需要更新正式文档”。三篇收窄到所属来源定稿；规划使用专用场景，已经授权的连贯后续仍直接衔接。第 3 篇与第 21 条合并用途，不建两个改需求入口。 |
| 21 · 行 37 | 新增、删除或调整玩法需求 | 普通已有模块的行为修改与新增独立 Product/模块共用；后者需要模块身份、依赖和顺序，前者维护原来源及已规划消费者。新增/删除一个行为本身可作为同一种变化参数。 | **拆分入口并去重**：“已有模块的玩法要求变了，需要更新需求”；“想增加一个独立玩法模块，需要确定边界和顺序”。前者承接第 20 条既有文档变化；不要为加、删、改三个动词各复制一篇。 |
| 22 · 行 38 | 确定或调整美术风格 | 唯一主产物是当前范围的共享视觉规范；参考比较、定稿与已有消费者影响核对是维护该来源的步骤，不制作或接入素材。 | **保留并改名**：“当前资产的美术方向不明确，需要定下来”。已有方向的小范围调整可在同一来源维护方法中处理；若另设“已交付美术要求实质改变”，必须有专用变化场景，不能让本条继续共用。 |
| 23 · 行 39 | 确定或调整声音风格 | 产物是声音方向，具体文件规格和播放实现明确交其他入口；多个声音角色并未形成独立执行目标。 | **保留并改名**：“当前模块的声音风格不明确，需要定下来”。方向、具体资源准备要求及实际播放保持不同出口。 |
| 24 · 行 40 | 设计界面与交互 | 当前以编写界面规格为主，但混有既有界面要求的实质调整与适用规划。初始规格不需要重评已实现消费者，修改已有规格需要。 | **拆分入口**：“玩家要做什么已确定，需要设计界面和交互”；“已确认的界面要求要变，需要更新规格并明确影响”。不把真实原型制作或正式 UX 审核塞进这两条。 |
| 25 · 行 41 | 设计音效与音乐需求 | 已知用途与方向，维护音频资源清单中的交付规格，明确排除制作、购买、播放和审核。音效/音乐有不同字段，但都交付同一类准备要求。 | **保留并改名、收窄**：“声音用途已确定，需要列出音频文件准备要求”。明确聚焦文件规格；和第 37 条任务资源总清单去重，同一音频条目只有一处正文。 |
| 26 · 行 44 | 拆分当前 Product 的 Feature | 首次空台账建立 R000；后续 Product 追加任务但保留旧同步锚点；已有计划则改走 sync。首次和后续是不同入口状态与历史写入契约。 | **拆分入口**：“当前模块的需求已确认，准备做项目的第一份 Feature 计划”；“前一个模块已完成，准备规划下一个 Product”。已有计划变更从这里排除，按对应同步页处理。 |
| 27 · 行 45 | 需求变化后同步已有任务 | 有可核实差异、历史基线缺失、新专业来源历史覆盖未知，及任务未开工/进行中/已完成，都由同一入口分流；其历史保护和写入行为不同。 | **拆分入口**：“Feature 还没开工，但已经确认要修改其中一条要求”；“Feature 正在开发，已确认要求发生变化”；“Feature 已交付，后来确认要改变要求”；“已有计划，但采用的来源基线无法核实”。新来源历史覆盖无法证明可归最后一篇，不能假造以前的差异。 |

### Godot 项目开发：日常开发、修复与资源，16 条

来源：[prompts.json](../../prompts.json)，行 48–67。

| 序号与行号 | 当前提示词 | 实际职责与判断依据 | 结论及建议场景 |
| --- | --- | --- | --- |
| 28 · 行 48 | 以 Goal 逐个推进 Product 至人工验收 | 一个已界定范围内持续推进到人工交接或全部完成；规划、执行、提交和返回是同一连续目标。manual/automated 是有效结束规则，不是任意选择不同任务。 | **保留并改名**：“Product 范围已确定，想自动推进到首次人工验收”。保留真实人工停点、原型局部停点和预算/阻塞区别，不拆成逐 Stage 提示词。人工结果后重新启动下一段 Goal，可另设“人工验收已有结果，继续原 Goal”，避免启动与结果续接共用专用场景。 |

## 关键问题与约束保留

### 1. 同名与一对一尚未落地，必须同时修改正文契约

**P1，已确认结构与语义问题。** 八篇样稿全部引用比自身更宽的入口，其中两组重复。静态路径比较应从 JSON 直接计算，不能用 H1、正文里的提示词声明、额外 ID 或迁移映射表掩盖不一致。报告中的对照表是一次审核证据，不是工具的新数据源。

先把每个入口的实际前提、目标、写入范围和结束位置写清，再建立同名页面；普通异常退出仍可保留。一篇场景里出现“材料缺失则停止”不等于该场景承担了另一项素材制作任务。反之，用“授权：诊断或优化”让同一入口临时选择不同交付，确实应拆。

### 2. Bug 专用入口不能丢掉现有提交约束

**P1，拆分时的行为保留要求。** [提示词](../../prompts.json)行 56 明确要求用户实际验收前不创建任何本地提交，包括计划和阶段性提交。两篇样稿目前通过引用“当前有效提交约束”避免重复规则，这个方向正确。拆分后两份正文都必须表达该任务特有约束，或者在用户明确改变后采用新行为；不能只保留一般 Skill 的“计划提交”，导致交付后 Bug 在验收前先提交计划。

依据：[工程规划 Skill](../../../project-source/skills/engineering-change-plan/SKILL.md)的 Write and hand off，以及[工程 Bug 路由](../../../project-source/methodology/07-engineering-change.md)，行 19–32。共享工程方法与专用提示词权限是不同层；本报告没有执行修复或修改提交规则。

### 3. “查看记录”与“全部完成”含义在样稿和脚本间不一致

**P2，已确认静态契约冲突。** [结果导入恢复页](../../docs/quick-reference/verification/existing-results/import-passed-tests.md)的 S4 表述 `show` 只展示记录；[实际工具](../../../project-source/tools/features/record-feature-completion.py)，行 96–102，在输出 JSON 后调用 `validate_completion_evidence`，以全部完成条件决定返回 0 或 2。

因此，即使 `record-tests` 成功保存结果，人工验收尚未完成也可能使后续 `show` 返回 2。它不能作为“测试引用保存失败”的证据。专用恢复场景应分别判断导入退出码和实际保存内容；是否将 `show` 调整为纯读取，由脚本职责审核及获准实现处理。只改样稿措辞不会修复该命令行为；改脚本则需要同步调用方和对应验证。

### 4. 单人范围应落实到旧提示词，不能删掉普通内容保护

**P2，已确认范围残留。** 行 17 和行 75 的交接正文仍包含 worktree 续接信息与专门的改动归属核对，行 51 的通用续接也以归属处理为前置。后续迁移应去掉这些专项流程，保留同一目录内真实 Git 状态、已有内容、原授权和未完成任务。

复制迁移中的符号链接、外部路径及 `.git` 指针检查用于确保目标写入不返回原件，属于必要的路径保护；不能见到 `worktree` 字样就删除全部目标校验。多名开发者协调与普通“不要覆盖现有文件”也不能等同处理。

### 5. 动态审核提示词保留旧创建器职责措辞

**P2，已确认说明不一致；未运行验证。** 行 13 仍写“创建器只执行现有复制职责；不要往其中加入……Git 操作”，而行 26 和[创建器](../../commands/create_project.py)的 `create_project`（行 76 起）明确包含 `git init`、`git add` 与初始提交。动态审核入口无需拆成多个阶段场景，但应按当前创建契约改写，读取创建器实际 Git 结果，避免误认为还需另做同一初始化。

这不证明当前动态流程已实际重复提交；结论仅是提示词和实现的职责说明不一致。

### 6. 专业资源准备的相邻入口需要横向去重

**P2，职责重叠风险。** 行 41 的音频文件规格和行 61 的任务资源清单都调用 `design-audio-asset-spec` 并写同一资源清单。合理分工是：前者确定某音频用途对应的准备要求，后者整理一个任务需要的最小素材集合并引用已有规格。若某次实际任务输入和输出完全相同，应合并为同一场景，不为保留旧的两个名字而重复正文。

同理，“发现框架可复现问题”和“采用外部方案修改框架”可以共享维护方法，但用户目标与输入不同；“同一报告保存为文件或显示在对话”仍是同一产物，不需要复制入口。

## 最小迁移顺序与新增场景缺口

1. 先在 JSON 中确定八篇样稿的专用正文和准确名称；同时拆出通用入口仍需保留的其他独立用途，不能删除旧入口后静默丢掉后续规划、规格调整或其他验收路径。
2. 将八篇样稿迁入 `<Project>/<分类>/<提示词名称>.md`，同步同名 H1、索引和关联链接。开工前同步与报告路径恢复两篇优先按其真实前提调整标题。保留样稿讨论阶段，不制造剩余场景的空壳文件。
3. 按本报告逐项处理其余提示词。先处理授权/产物明显分离的入口，再清理模糊命名和相邻用途重复。来源变化、执行、审核等共用 Skill 的最终职责以 Skill 全量报告为依据，不把本报告的提示词拆分等同于 Skill 拆分批准。
4. 与 JSON 改名一起同步导出选择、重新生成精选表达，并更新覆盖说明及活动文档；结构校验只计算 JSON 预期路径与实际文件集合，不读取正文或维护第二份映射。
5. 按修改范围验证 JSON、名称、链接、导出及实际受影响的工具契约；提示词语义还需逐条复核，不能用路径检查通过替代。工具运行和实际 Agent 行为另记结果，未执行保持未验证。

当前 50 条不是完整需求清单的上限。依照已确认范围，下一批还需单独界定：准备后接收素材与检查规格、环境工具不可用/版本不符、原始测试报告丢失、内容变化导致旧证据失效、测试实际失败或运行中断、同目录任务暂停与切换。它们不能继续全部借用“继续中断的当前任务”。素材制作仍为待扩展；打包/发布尚未决定；多人协作、改动归属处理和 worktree 续接不纳入。
