## 初审 P2：执行契约和内容一致性问题（均已关闭）

以下均为影响可用性、授权或用途覆盖的实质修正，不是措辞喜好。

### R1 暂停及交接场景的通用页尾撤销了停止语义

`Godot 项目开发/项目恢复与交接/当前 Feature 需要暂停，先保存真实停点.md:39` 和 `Feature 还没做完，准备换一个对话继续.md:51` 都写“本页达到出口后，仍已明确授权的后续工作按其所属场景继续”。对应提示词明确要求停止实施、暂停原任务（`framework/prompts.json:134–135`）。读者可能据旧授权在保存停点后立即继续原任务。

修正：暂停/交接页明确停止原实施，收到续接指令后再恢复；检查框架交接页同一通用尾句。保留普通场景中跨阶段授权延续，不对所有场景一律删除它。

### R2 动态验证页把获准写入误写为全程只读

`Yaya 框架维护/维护与复盘/想用一个小任务实际验证框架流程.md:39` 写“被审源与原始证据只读；只写获准报告”，但对应提示词授权在指定外部项目创建项目、实施微型任务、运行验证和按其规则提交。该页第 19、23 行又只有“调用创建器”“沿真实需求、规划、执行”的概括，未给实际入口。

修正：资源影响区分框架源只读与外部验证项目获准新增/修改；列真实创建器入口及关键参数、Product/规划/执行所用 Skill，保持微型任务范围和真实人工停点。不在维护仓库激活生成项目流程。

### R3 本地静态审核的独立执行要求在提示词和页面不一致

`Yaya 框架维护/维护与复盘/想检查本地框架是否自洽，先做静态审核.md:19` 指定“独立审核 Agent”，第 25 行称独立结论；`framework/prompts.json:15` 对应正文是当前 Agent 直接审核，没有委派独立实例的要求。

修正：按已确认意图统一执行者；若该场景承担独立审核，在提示词中明确委派独立实例和只读边界，否则将页面恢复为当前 Agent 的静态检查。不要只在标题上宣称独立。

### R4 研究报告保存位置与真实 researcher 契约冲突

`Godot 项目开发/需求设计/方案有一个外部问题没确定，需要查资料.md:27` 将有保存价值的报告写到 `reports`，对应提示词允许指定 `docs/research/`。`project-source/agents/researcher.toml:46` 默认研究报告为 `docs/research/<descriptive-topic>.md`；第 62 行的 `reports/scratch/<task>/` 是原始下载/探针材料，不是研究结论报告。

修正：页面遵循研究报告真实归属，并引用 Agent 源契约；简单查询不强制创建报告。

### R5 三个实验入口只替换类型，没有把不同观察重点带进提示词

`需求设计/界面效果还没确定，先用真实素材试一下`、`玩法效果还没确定，先做小实验`、`技术方案是否可行还不确定，先做验证` 的提示词主体是同一段“针对给定视觉/玩法/技术假设完成一次最小实验”。虽然输入和出口稍有区分，但关键执行主体仅替换类型词，场景页已有的不同观察重点未带入真正发送给 Agent 的入口。

修正：视觉入口明确真实素材、目标显示条件和可运行原型；玩法入口明确最小循环、输入反馈和实际体验；技术入口明确版本/环境、最小探针、可核验测量或行为判定。维持单一假设和预算边界，不复制三套完整方法论。

### R6 证据恢复页面没有给关键执行命令及导入副作用

`Godot 项目开发/验证与收尾/测试摘要还在，但原始报告找不到了.md:23–27`、`实现又改过了，需要更新已经过期的验证证据.md:23–27`、`测试运行中断了，需要从真实结果恢复验证.md:27` 只写运行/导入必要结果。用户明确要求场景步骤说明实际 Skill、Agent、提示词和工具，这些页目前不足以直接找到执行入口。

修正：给 `tools/testing/run-gdunit-tests.py --feature <ID> --scope <范围>` 与 `tools/features/record-feature-completion.py record-tests --feature <ID> --run <实际结果>` 的适用调用，说明兼容结果整组导入、替换当前引用且失败导入清除旧引用，原件保留。`record-feature-completion.py:66` 明确失败清除旧引用。人工过期部分引用相应真实人工入口，不以自动结果替代。

### R7 自动测试入口允许组件任务，步骤却只接受 Feature

`Godot 项目开发/验证与收尾/已有变更需要重新运行相关自动测试.md:7` 及对应提示词接受“Feature 或组件”，但第 23 行只给 `--feature <实际ID>`。实际运行器 `run-gdunit-tests.py:134–135` 支持互斥的 `--target` 和 `--feature`，无 Feature 的合法组件检查不应被迫造 ID。

修正：根据一场景一入口原则明确无 Feature 检查的承接方式，给真实 `--target` 调用；或把当前场景限定为 Feature，另设组件测试场景。不得把选择参数当成虚构任务的理由。

## 初审 P2：旧用途覆盖缺口（均已关闭）

### R8 已确认美术/声音方向变化没有独立承接

旧提示词“确定或调整美术风格”“确定或调整声音风格”都包含修改已确认共享方向及其消费者影响。目前 `需求设计/当前资产的美术方向不明确，需要定下来.md:11` 和 `当前模块的声音风格不明确，需要定下来.md:11` 限于“共享专业方向尚不明确”。“已确认的界面要求要变”已有独立入口，美术/声音的对应变化尚缺。

修正：补齐明确已确认方向变化的独立场景与提示词，区分来源修改、现有资源/计划影响和后续实施授权；不要扩大初次定方向入口，使一条提示词重新包办两个不同状态。

### R9 测量证据充分性的独立审核用途丢失

旧“独立审核专业成果”明确覆盖测量证据充分性，涉及测量实现交给 `review-code`。当前专业独立审核仅有 UX、美术、音频、资产、本地化、平衡，代码差异/模块审核没有明确承接“测量数据已经取得，需要独立核实结论”的用途；性能诊断和长测执行属于生成证据，不等于独立复核证据。

修正：补有明确对象、输入、判定和真实审核角色的测量证据审核入口，覆盖适用性能/长测数据的版本、条件、原件、样本和结论边界。按真实输出职责决定是否需要两个入口，不为数量机械拆分。

### R10 无 Feature 的合法任务续接和交接用途丢失

旧“继续中断的当前任务”接受任务或 Feature；旧“整理进度与任务交接”明确“没有 Feature 的任务按实际说明，不为交接创建一个”。当前项目侧恢复/暂停/新对话交接入口都使用 Feature 及其执行来源。下一步 advisor 是建议入口，不能替代已授权的非 Feature 原任务续接。

修正：承接同一项目目录中非 Feature 的研究、讨论、审核等真实任务的暂停/交接/恢复，保留实际授权、证据和适用执行方法；不引入多人归属、worktree 或为交接造 Feature。
