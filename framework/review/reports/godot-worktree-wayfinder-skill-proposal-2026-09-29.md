# Godot worktree、wayfinder 与项目澄清入口拟改报告

## 1. 建议采用的整体方案

建议新增 `worktree-create-godot`、`worktree-integrate-godot`、`wayfinder-godot` 三个项目 Skill，并将现有 `project-clarifier` 改名为 `project-grill-me`。创建工作目录、整合成果、理清复杂任务各有自己的入口；它们可以在需要时配合使用，不组成每项任务必须经过的固定流程。

本报告供讨论和确定实施范围。本轮只保存报告与待讨论入口，尚未创建这些 Skill、改名或修改项目行为。检查基线为 `41bf4e38bbe957f7bb0207a82f874f34fcc9a2c9`，编写日期为 2026-09-29。

| 拟改对象 | 用户遇到的事情 | 这次建议 |
| --- | --- | --- |
| `worktree-create-godot` | 想保留当前实现，同时试另一套方案，或需要另一个可工作的目录 | 新建项目 Skill，负责创建或复用合适的 worktree，并确认此次工作所需的准备 |
| `worktree-integrate-godot` | 已选好某套试验成果，要把它带回指定分支 | 新建项目 Skill，负责选定成果的整合和整合后验证 |
| `wayfinder-godot` | 目标大致清楚，但有几个互相影响的问题，不知道应先查什么、问什么或试什么 | 新建项目 Skill，逐步理清影响当前目标的决定及其依赖 |
| `project-grill-me` | 有一个具体项目问题需要追问和讨论 | 改名现有 `project-clarifier`，保留已适配的方法与职责 |
| `resolving-merge-conflicts-godot` | 接手一次已经产生冲突的合并等操作 | 是否再设独立入口待选择；推荐先将详细方法放在整合 Skill 的按需参考中 |

按推荐方案是 **3 个新增、1 个改名**。如果再保留独立冲突入口，则是 **4 个新增、1 个改名**。以上都放在项目分发源；框架自用目录不再维护同功能的一套。

### 已确定的方向

- 创建 worktree 和整合成果分成两个职责，PR 不属于这次需求。
- worktree 按实际任务使用，日常工作仍可在原目录推进。已有允许按需使用的方向继续沿用。
- Skill 按功能选择，可以跨开发环节使用；不以“当前处于哪一个 Stage”人为限制普通讨论或方案检验。
- 详细规则保留一个正文归属，入口提供选择条件与必要提醒。
- 保留 Bug 的提交特例：要求人工验收和明确提交许可的两个 Bug 入口，仍须分别满足这两个条件。其他任务沿用及时分段提交约定。

### 已有能力，不重复创建

项目已有 `retro-godot`、`loop-me-godot`、`plan-review-godot`、`prototype-godot`、`task-handoff-godot`，以及环境、限定检查、人工验收和证据处理入口。本方案复用它们；已有成果不因本次讨论重新实现。

`project-grill-me` 的命名方向按上一轮讨论列入方案。保留 Matt Pocock 原方法名称有助于识别来源，但实际行为仍以项目自己的授权、记录与验证规范为准。

## 2. 创建 worktree：交付一个能开展指定工作的目录

拟新增目录：`project-source/skills/worktree-create-godot/`。

典型请求是：“当前背包界面先保留，另开一个目录试网格布局。”它需要知道基准版本、此次试验目标，以及是否已有可复用的目录。这些信息优先从当前请求、Git 状态和现有记录中取得；只有无法判断且会影响结果的选择才问用户。

这个入口负责以下事情：

1. 确认实际仓库、基准分支或提交及已有 worktree，选择合适的现有目录或创建新目录。创建分支的动作必须处于本次任务授权内。
2. 分清要带入的是已提交版本，还是当前尚未提交的改动。新 worktree 不会自动包含当前目录的所有工作；不能为方便搬运而提交尚未验收的 Bug，或带走无关修改。
3. 按此次任务检查必要的本地依赖、Godot 导入与运行数据。启动编辑器、导入、测试、游戏或其他可能写入的工具前，按该操作核对实际副作用；纯只读代码比较无需运行准备，也不要求每种操作都做一套完整隔离。
4. 返回实际目录、分支或提交、可执行的下一步，以及仍缺的具体条件。已有实施授权时，交回任务继续执行，无需再次确认“开始”。

**完成含义：** 指定工作已有明确、可用的执行目录，且该工作的必要准备已完成。若只完成 Git 检出而运行条件不足，就明确报告“目录已创建，运行尚受阻”，不将两者合成一个“准备完毕”。

这个入口不负责选择哪套游戏方案更好，也不负责将试验成果合回去。它不要求每个新任务创建 worktree，不把建立目录等同于创建新的 Codex 对话。

### Godot 中需要特别处理的内容

普通 worktree 会检出所选提交中受 Git 管理的场景、脚本、图片、音频等文件。它们不是一律共享主目录中的同一份资源；`res://` 以各自的项目目录为根。Git 对象与历史的共享，也不等于工作目录里的资源文件共享。

| 内容 | 实际区别与拟处理方式 |
| --- | --- |
| 受 Git 管理的资源 | 随所选版本检出。保留 `.uid`、需要的 `.import` 等关联文件；整合时检查资源引用，而不只看脚本 |
| 未提交、未跟踪或被忽略的内容 | 不会因为创建 worktree 自动迁入。只按此次工作需要检查、准备或在授权内带入 |
| `.godot/` | 本项目将其忽略；新目录可能需要自己的导入缓存，不能拿主目录已有缓存作为新目录已经验证的证据 |
| `user://`、项目外绝对路径和外部服务 | 可能在两个目录间指向同一份可写数据。只有此次会触及的副作用需要检查；多存档槽位也不能证明设置、缓存等其他写入已分开 |
| 本机工具配置与被忽略的工具运行环境 | 路径可用性按目标目录和当前机器核实，复用现有环境入口；不自动复制整份本机配置或重装所有工具 |

建议先实现“检查实际用途，并准备此次运行需要的隔离”，不新增一个未经验证的通用开关后就宣称全隔离。现有 gdUnit4 也会使用并清理 `user://tmp`，因此只跑测试同样需要关注实际写入；仅修改游戏存档槽位不足以证明测试数据互不影响。修改临时试验的存档位置时，应有可核实的实际写入路径；这些试验设置也不应未经检查进入最终游戏成果。

具体用哪些项目设置、启动参数或现有存档接口，是实施时结合项目与 Godot 版本核实的技术问题。缺少适用手段时先报告运行限制，仍可继续不依赖该条件的代码工作。

## 3. 整合 worktree 成果：带回选中的改动，并验证组合结果

拟新增目录：`project-source/skills/worktree-integrate-godot/`。

用户说“合并 worktree”时，实际需要确认的是：哪组分支或提交中的成果，要进入哪个目标分支及工作目录。Git 整合的是版本历史或选定改动，不是把两个目录直接拼起来。

这个入口从“采用哪一套成果已经确定”开始。它负责核对来源、目标、变更范围和依赖，选择与当前历史相称的整合方式，处理实际冲突，并验证组合后的结果。采用完整分支还是选定提交，应由真实改动决定，不预设每次都 merge 或每次都 cherry-pick。

例如，用户决定采用网格背包：要带回的不只是网格场景，也包括它依赖的资源、脚本与必要测试；另一次试验中的无关音效调整不能因为在同一分支上就自动带入。若两部分已纠缠，先说明无法独立带回的原因和可行处理。

**完成含义：** 选定成果进入正确目标，必要验证覆盖整合后的实际版本，并按当前任务的提交与验收条件交付。没有文本冲突只说明 Git 能完成该层面的组合，不能证明场景路径、节点引用或游戏行为正确。

整合后的检查复用 `project-verification-godot` 及所属工作流；证据归属复用 `verification-evidence-godot`。源分支的旧运行结果不能直接冒充目标组合已经通过，仍有效的检查则无需机械重复。

执行整合命令前，还要识别它是否会自动生成提交或前移目标分支，并核对本次授权及提交条件。需要先验证、验收再提交时，选择能保留可审阅候选结果的做法，不先默认执行自动提交的合并再补验。具体 Git 命令由实际历史和有效授权决定。

### 冲突处理放在哪里

**推荐：先用两个主要入口，把冲突方法放在 `worktree-integrate-godot/references/merge-conflicts.md`。** 只有出现冲突时才读取。方法保留原版中有价值的部分：查双方意图、理解依赖、按整合目标处理、验证结果。

不继承原版“总要解决、永远不能 abort”“暂存全部”“自动持续完成 rebase”的要求。已经卡住的操作要先核实它的来源和当前授权；双方意图确实冲突时不能替用户发明第三种业务行为。

如果用户希望经常直接调用一个“接手已冲突操作”的入口，则另建 `resolving-merge-conflicts-godot`，由它拥有冲突方法，整合入口条件调用它；两边不各维护一份详细正文。此选择见第 8 节的第 3 题。

### 整合与清理分开判断

整合完成不自动授权删除源 worktree 或分支。先保留试验目录及仍有用的证据；用户要求清理时再核实使用中的任务、进程和未保存内容。使用 Codex 管理的 worktree 时，沿用宿主的归档与恢复能力，不另造一套删除脚本。创建、归档和整合的工具选择服从当前宿主实际能力。

Bug 成果也不能借这个入口绕过原有提交特例。如果所需提交条件尚未满足，应交付可审阅的整合方案或允许范围内的准备，并明确尚不能完成的整合动作。

## 4. wayfinder：先找到解决问题的顺序，再决定要不要实现试验

拟新增目录：`project-source/skills/wayfinder-godot/`。建议保留 `wayfinder` 名称并注明借鉴来源，中文说明可用“复杂任务的逐步探索”。

**值得引入。** 它承接的情况是：已有一个目标，但几项未知互相影响；解决一个问题以后，才能看清下一个问题。它的价值在于管理这些决定的依赖关系，而不在于强制生成 worktree 或一开始就拆完所有 Feature。

例如：“想让背包支持大量物品，但列表、网格和搜索怎么组合还不确定，性能是否够也不清楚。”应先确认需要比较的目标与约束，再区分展示选择、数据规模和技术事实；没有必要第一步就各建一个完整实现。

### 依据缺少的证据选择方法

| 当前缺口 | wayfinder 如何推进 | 是否需要 worktree |
| --- | --- | --- |
| 用户偏好、业务边界或取舍没明确 | 由 `project-grill-me` 组织相关问题，用具体情境比较 | 通常不需要 |
| Godot API、第三方能力或项目已有实现不清楚 | 读取本地材料；需要外部资料时使用现有调研能力，保存必要来源 | 通常不需要 |
| 文字讨论无法判断布局、操作感受或实际可行性 | 使用 `prototype-godot` 做范围明确的 Godot 原型 | 小原型可在现有目录中安排；按影响判断 |
| 两种实现都要运行、切换比较，且互相覆盖或难以保留 | 定义相同的比较问题与必要输入，再使用 `worktree-create-godot` | 这时有实际价值 |
| 已有完整方案，需要检查假设、反例与验证缺口 | 使用 `plan-review-godot` 检验当前方案 | 通常不需要 |
| 决定已经足够明确 | 返回原有 Product、Feature 或工程任务入口继续 | 不为结束 wayfinder 再造试验 |

是否使用 worktree，不能只看“任务复杂不复杂”。一个复杂但纯文档的问题无需多个代码目录；一个很小、却需要保留两种互相覆盖实现的试验，也可能适合 worktree。

### 保留原版方法，调整原版机制

保留：先说清目的、区分已确认与尚未知、先处理能够推进的问题、按实际依赖展开后续问题、只读取相关细节。已经排除的范围不因探索又自动进入任务。

项目版不引入 issue/tickets、领取状态、调研专用分支或另一套台账；不规定每次对话只能处理一题，也不要求每次都调用一整组 Skill。依赖用户实际回答的问题，Agent 不代答；能够通过事实调查解决的内容，Agent 自己查。

**完成含义取决于这次请求。** 用户要求梳理，交付当前结论、依据、待决定项与下一步即可；用户已授权连同实现一起完成，则在问题解决后把结论交回原有工作继续。探索结论不等于功能交付，也不替代人工体验和验收。

它在项目现有 GDD 前提内工作，不借探索入口从一句模糊游戏设想初始化整个项目。

### 与其他 Skill 的分工

| 入口 | 它回答的核心问题 |
| --- | --- |
| `project-grill-me` | “这个具体问题还没想清楚，哪些取舍需要讨论？” |
| `wayfinder-godot` | “有几件互相影响的事情没想清楚，应按什么依赖逐步弄明白？” |
| `project-next-step-advisor` | “根据当前材料核实状态，下一步适合进入哪个现有工作入口？”自身不推进探索，也不执行所推荐的工作 |
| `plan-review-godot` | “这份已有方案有哪些假设、漏洞或遗漏？” |
| `loop-me-godot` | “这类事情以后会反复做，怎样形成合适的处理方法？” |
| `retro-godot` | “实际做过的这件事为什么返工、失败或顺利，有什么经验？” |

wayfinder 可以按需使用具体方法，但不接管每个方法的全部职责。普通问题直接进入对应入口，无需先经过 wayfinder。

## 5. 改名 project-grill-me 与记录归属

拟将 `project-source/skills/project-clarifier/` 改名为 `project-source/skills/project-grill-me/`，同步 frontmatter、标题及有效引用；保留一个入口，不留下同功能的旧名转发 Skill。

现有方法已经吸收了 grill-me 的核心：先找事实、成组讨论、沿依赖追问、只重新检查受修正影响的结论、到有用的结果时停止。改名表达来源和用途，不把行为退回原版的穷尽追问或统一再确认。

`product-spec-elicitor` 继续使用共享提问方法，但仍负责自己的 Product 相关提案；`plan-review-godot` 继续检验已有方案。正式 GDD/Product 修改、Feature 规划、术语写入仍由原有负责者承接。

跨会话保留信息时，建议按现有归属记录：

| 内容 | 现有归属与拟用方式 |
| --- | --- |
| 当前目标、尚未决定的问题、下一步、相关材料入口 | `docs/progress.md`；简短保存当前状态，不复制完整讨论 |
| 某个 Feature 的局部决定和设计 | Feature notes 与必要的 `docs/features/F0XX-design.md` |
| 已确认的游戏规则或交付边界 | 对应 GDD 或 Product，由原有负责者更新 |
| 有用的外部调研结论 | `docs/research/<descriptive-topic>.md`，按现有调研契约记录 |
| 重要且满足现有条件的跨模块技术取舍 | 现有 ADR 约定；普通问题不自动生成 ADR |
| 原型和真实运行证据 | 现有 Feature 或 maintenance 报告位置，与决定正文分开 |

没有 Feature 的调查也可以用 Progress 与已有任务材料续接，不必先造 Feature、ADR 或专用探索台账。普通一次性讨论不强制落盘。现有规范已经给出了这些归属，本次无需再把文档位置当作一项需要用户决定的新机制；如果以后出现现有材料确实容纳不了的具体论证，再讨论那个缺口。

## 6. 实施时会同步哪些位置

### Skill 与规则

- 在 `project-source/skills/` 创建三个独立入口，配套 `agents/openai.yaml`；默认沿用 Codex 隐式选择策略，只在存在条件细节时增加参考文件。正确字段是 `policy.allow_implicit_invocation`，不复制 Claude 的 `disable-model-invocation`。
- `project-clarifier` 当前只有 `SKILL.md`，没有已有的 `agents/openai.yaml` 可迁移；改名时按实际文件处理，不假定旧元数据存在。
- Git 授权、已有改动保护、暂存与提交仍由 [Git 规范](../../../project-source/agent-rules/00-core/git-worktree-and-commits.md) 拥有。Godot worktree 的共同运行准备细节建议只写在创建 Skill 的参考中，整合入口在确有运行准备需要时引用；通用环境和验证方法继续引用现有负责人。
- 核对并更新 [项目总路由](../../../project-source/methodology/00-overview.md)、[设计与 Product 规范](../../../project-source/methodology/01-product-doc-structure.md)、[项目 README 源文件](../../../project-source/Project_README.md) 和 [advisor](../../../project-source/skills/project-next-step-advisor/SKILL.md) 及其场景参考。只有新职责确实影响根入口时，才补 `Project_AGENTS.md` 的短提醒。
- 同步旧名的直接调用方：`product-spec-elicitor`、`project-terminology`、`loop-me-godot`、`plan-review-godot`；保留有效的共享方法锚点。旧审核报告作为历史保留，不伪装成对新名字或新实现的审核。
- [复制清单](../../project-files.json) 已将整个项目 Skill 目录分发到 `.agents/skills/`，本次不需要逐个新增映射。已有外部游戏项目不自动更新。

### 3. 是否保留独立的冲突处理入口？

- **A. 先保留创建与整合两个入口（推荐）。** 冲突方法放在整合 Skill 的按需参考中。用户仍可直接说“帮我处理这次合并冲突”，入口需要明确覆盖接手已开始的整合；整合本身并不以出现冲突为前提。
- **B. 再建 `resolving-merge-conflicts-godot`。** 适合希望单独点名使用，或经常接手已中断冲突操作的情况。整合入口只引用它，代价是多维护一个发现入口与职责边界。

两者都保持创建与整合分开。差别只在“处理冲突”是否值得独立成为常用入口。

是否采用某套试验成果、整合到哪个分支、是否清理目录，属于以后每次具体任务的决定。此次无需预先统一回答，也不需要决定所有 worktree 必须使用同一种整合方式。
