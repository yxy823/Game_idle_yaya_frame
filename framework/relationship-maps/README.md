# 文档关系图与开发场景图

[框架入口](../README.md) · [文档系统关系图](document-system.readable.json) · [开发场景图](game-development-workflow.readable.json) · [文件格式](graph-map-format.md)

本目录保存两张关系图，用途不同，格式相同（Graph_Map）。它们是阅读辅助，只保存在框架仓库，不进入生成项目，也不被任何程序依赖。

| 要了解什么 | 图文件 |
| --- | --- |
| 文档从哪里找到，设计、任务、实现说明和验证依据怎样关联 | [document-system.readable.json](document-system.readable.json) |
| 当前开发场景可以衔接哪些其他场景 | [game-development-workflow.readable.json](game-development-workflow.readable.json) |

两张图共用的 JSON 结构、字段、保存格式与本地次数文件见 [Graph_Map 文件格式](graph-map-format.md)，日常编辑无需读取查看器源码。

## 打开与保存

在 Windows 的 Edge 中打开 Graph_Map 页面：

1. 点击“打开图目录”，选择 `D:/A_Games/Game_idle_yaya_frame/framework/relationship-maps`。
2. 选择要看的图文件。查看器会同时读取这张图，以及目录内所有图共用的使用次数文件 `graph-usage.json`。打开会替换当前画布；有未保存的内容时，按查看器的提示处理。
3. 点击“保存”或按 Ctrl+S，分别保存有修改的图和次数文件；只改了次数时不会重写图文件。
4. “另存为”会把两份文件存到新目录，并切换到新位置。

刷新页面后需要重新打开目录；缩放和平移只是临时视图，不会保存。

其他说明：

- 两张图各有固定的 `documentId`。
- 个人使用次数保存在本目录的本地 JSON 中，不纳入 Git；新图没有次数文件时，全部从 0 开始。
- 节点上的本地链接只能在查看器中显示和复制，不能直接打开文件。

## 查找与沿关系查看

- **搜索**：可以输入节点的完整名称，标签里为排版加的换行不影响命中。
- **直接关联筛选**：选中节点后，属性面板的「直接关联」可按连入、连出和连线样式（颜色加线型）筛选，画布只突出匹配的连线和端点。两张图里线条样式代表的关系含义，见各图顶部的图例。
- **多跳专注**：开启专注模式后，可选 1、2、3 跳和方向，范围只沿当前选中的连线样式扩展。跳数越多、方向越宽，突出的节点越多；先限定方向和样式再加跳数。

两个例子：

1. 在开发场景图搜索「Feature 已规划并可开始，现在实施这一项」，选连出和蓝色实线，开启专注并选 2 跳，可以同时看到实施之后的人工验收清单、验收记录和下一个 Product 共 4 个节点。
2. 在文档系统关系图选中 Feature 详情节点，选连出和紫色虚线，开启专注并选 2 跳，可以同时看到测试登记、完成证据、人工验收和原始测试报告等 6 个节点。

筛选和专注范围只是临时视图，不写入图文件；连线上的条件文字只说明何时衔接，不代表条件已经满足。

## 文档系统关系图

上区是框架仓库，下区是生成后的游戏项目。节点按文档职责或产物类型组织，例如 GDD、Product、Feature、原始测试报告；不是全仓文件清单。“资源规格与准备”代表所属设计中的章节，Feature notes 归入任务详情，不为画图额外拆出文档。

每个文档节点：

- **标题**：显示职责与文件名。
- **备注**：说明实际位置、是初始就有还是按需创建，以及关键的引用关系，并用固定格式登记文件路径（见下文“节点名称与文件登记”）。
- **链接**：指向本仓库中能打开的入口、分发源、模板或规范；按需产物还不存在时，不链接虚构的项目文件。
- **填色**：区分材料类别，不表示任务状态或验证结果。分区标题与图例只是阅读辅助。

连线按标签理解，四类方向如下：

| 外观 | 箭头含义 | 例子 |
| --- | --- | --- |
| 灰色虚线 | 阅读入口 → 可查阅的目标 | Feature 索引 → 任务详情；项目 Progress → 执行历史 |
| 蓝色实线 | 要求或约定 → 使用、细化它的材料 | GDD → Product；共享美术规范 → UI 设计 |
| 紫色虚线 | 记录 → 所引用或按身份关联的依据、证据 | 完成证据 → 原始测试报告；局部设计 → 当前架构 |
| 橙色实线 | 来源 → 创建时复制的结果，具体动作见标签 | 分发源 → 创建后的项目入口 |

蓝线表示来源被谁采用，与超链接写在哪个文件里无关；紫线的关联可能只靠 Feature ID 建立，不一定有专门的 JSON 字段；橙色跨区线只表示创建项目时复制一次，之后项目独立维护。所有箭头都只表示关系，不表示自动执行或授权。

例如查看“商店购买”涉及的文档：

1. 从游戏组织指南进入 GDD。
2. 沿“界面”和“获得反馈”找到 UI 文档、表现方案和资源章节。
3. 沿 Product 找到具体的 Feature、局部设计和当前架构。
4. 由 AC、测试登记和完成证据找到实际的检查原件。

Progress 保留当前停点，完成历史和知识条目各自引用原记录。这只是演示查找路径：不是每个功能都要建齐所有可选文档，空白项目里也没有商店。

### 联系与孤立的判断

当前规范要求各材料有合适的入口和用途：设计由所属目录或来源文档进入，Feature 由任务索引进入，局部设计从 notes 进入，报告由所属任务或 Progress 引用，知识条目从主题索引进入。正文维护一份，使用方引用它；规范依据见[专业工作与来源](../../project-source/methodology/11-specialist-workflows.md)、[Feature 列表与测试追溯结构](../../project-source/methodology/02-feature-list-schema.md)、[架构概览](../../project-source/methodology/10-architecture-overview.md)及[记录、报告与交接](../../project-source/methodology/09-records-reports-and-handoff.md)。

“没有被链接”“缺少必要来源”和“完全没有关联”是三种不同的问题。报告这类末端产物只需要有入口，不必人为添加回链。图只画出契约中的主要关系；某个项目里实际的正文、来源覆盖和证据原件，仍要在项目中核对。

### 维护与检查

文档职责、路径、产物归属或实际引用契约改变时，由 [prompt-and-graph-maintenance-yaya](../../.agents/skills/prompt-and-graph-maintenance-yaya/SKILL.md) 局部更新对应节点、备注、链接和连线；不把新增一份同类报告或 Feature 当作新增节点。节点改名保留 ID，不按文件数、排序或当前任务状态重画整个系统。图不保存另一套流程正文、任务状态或孤立文件清单。

文档图使用 `doc-`、`relation-` 标识文档节点与连线，`caption-`、`legend-` 标识阅读辅助。核对实际链接、全局 ID 唯一性、端点、单向箭头、节点尺寸和保存格式，并沿本次受影响的具体查找场景检查关系含义。开发场景的名称与链接脚本只处理场景图；文档图的全仓覆盖扫描按下文显式调用，不接入每次维护或提交。

### 节点名称与文件登记

固定产物在标题独立一行显示准确文件名，例如 `feature-list.json`；按需同类产物显示约定名称，例如 `F0XX.json`、`F0XX-design.md`。目录型节点显示入口名及同类文件模式。所属设计中的资源章节仍保存在原设计文件内，不为节点创建独立文件。

每个 `doc-` 节点在 `note` 的独立行登记路径，冒号后留一个空格，一行只写一个路径；仍使用现有 `note` 字符串，不增加 Graph_Map 字段：

```text
文件： framework/terminology.md
项目文件： docs/features/F[0-9][0-9][0-9].json
```

`文件：` 后是框架仓库相对路径；`项目文件：` 后是生成项目相对路径。分发源到项目的换算只读取[复制清单](../project-creation/project-files.json)，不另建源与目标映射。同一模板复制到两个位置时，两处分别检查。引用链接仍指向能打开的源文件或规范，路径登记可以描述尚未生成的可选产物。

路径区分大小写，使用 `/`；`*`、`?`、`[0-9]` 只匹配当前目录的一段名称，独立的 `**` 匹配零层或多层目录。标题中的 `F0XX.json` 是给人阅读的示例，登记使用 `F` 加三位数字的模式；编号是否有效仍由 Feature 规范与检查器判断。按职责选择准确文件或类型目录，不能用整个仓库的通配规则掩盖遗漏。

### 按需检查文档覆盖

用户需要找出未纳入文档图的文件时，才按[检查文档图覆盖](tools/README.md#检查文档图覆盖)显式运行检查；不接入每次维护或提交。覆盖只表示路径归入了某个职责节点，正文是否被使用、引用是否正确仍须另行判断。

## 游戏项目开发场景图

[game-development-workflow.readable.json](game-development-workflow.readable.json) 展示 [Godot 开发提示词库](../prompt-scenarios/prompts/godot-development-prompts.json)的全部场景及其衔接关系，不包含 `Yaya 框架维护` 场景。节点只显示提示场景名称，不复制提示词正文，不新增阶段、判断、标题或说明节点。具体操作仍查对应提示词或[场景速查索引](../prompt-scenarios/scenarios/scenario-index.md)。

图中保存为阅读调整的布局、文字换行、尺寸和连线外观，以及同名场景文件链接；节点不写备注，场景含义以提示词和场景页为准。已有名称检查和链接维护命令默认处理此文件；提示词顺序变化不要求重排整图。

### 阅读与维护

节点按实际关系安排主线和分支位置，维护时保留已有布局。颜色只辅助辨认分类，不表示任务状态；分类名称不另建节点。

- **蓝色实线**：常见交付路径中的场景衔接，仍需满足线上的条件。
- **灰色虚线**：按需选择、替代入口、问题处理或续接关系。箭头不代表自动执行或新增授权。
- **条件标签**：说明何时可转入目标场景，不替代提示词自身的前提与完成要求。跨区长线按端点与标签辨认。

图展示场景之间的关系，不是要逐个执行的清单；GDD 前提、授权、验证和人工验收的要求仍以项目规范为准。图中没有单独的“完成”节点：转入下一个 Product 的连线，要求当前 Product 的全部完成条件都已满足。自动验收的 Feature 不需要经过人工验收场景。

维护时先核对 `godot-development-prompts.json` 的分类与名称；每个场景都恰好对应一个节点。节点 `label` 允许为阅读插入 CR/LF 换行，去除换行后仍须逐字一致，不能改动空格、标点、大小写或添加编号、步骤、Skill 名称。

- **集合、名称或分类变化**：更新相关节点、分类颜色和场景链接。新增或删除场景时相应增删节点，重命名时保留身份；新增节点使用新的唯一 ID，不占用旧 ID，也不因排序改变而重编号。
- **实际衔接变化**：核对对应连线的方向、条件和必要布局；不把按需入口串成固定必经流程。仅修改提示词措辞且这些关系未变时，无需改图。
- **局部布局或样式变化**：只修改选定元素，保留其他节点、连线、换行、链接及有效的外观配置。
- **编写或保存 JSON**：遵循[编写与保存格式](graph-map-format.md#编写与保存格式)，保留查看器保存后的字段顺序和已测量尺寸。

没有场景入口的工作不自行补成节点。Godot 场景调整后使用下文的检查命令核对图文件；框架场景变化不加入图中。
