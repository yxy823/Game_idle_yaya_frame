# 专业来源与资源

[Godot 项目手册](../README.md)

本页说明美术、声音、UI、游戏表现和本地化等专业工作在生成项目中怎样分工。这类工作分四种：

- **专业设计**：写出要求。
- **资源准备**：提供真实的文件。
- **接入**：把资源接到运行中的游戏里。
- **验证与审核**：取得各自性质的证据。

一个任务只用到它需要的部分。项目里有 Art Bible 或 Sound Bible 的占位文件，不代表要先把整款游戏的美术和声音都设计完。

本页的 UI 文档、游戏表现文档和共享方向文档，分别细化[游戏表现](../foundations/game-logic-and-presentation.md)中的不同问题。逻辑和表现都来源于 GDD，专业文档不替代游戏规则的正文。专业规格可以和 GDD 一起逐步形成；但开始接入、测量或实现前，本次行为必须有真实的规则支撑，判断方式见 [GDD 前提](../requirements-and-tasks/requirements-and-planning.md#gdd-是项目开发的前提)。

## 各类来源由谁维护

每类内容只有一个维护者和一个固定位置：

| 内容 | 位置 | 维护的 Skill |
| --- | --- | --- |
| 整体游戏设计、玩家行为与反馈意图 | `docs/gdd/` | `design-gdd` |
| 数值模型、公式、参数、曲线与计算说明 | 单个系统：`docs/gdd/balance/<system-key>.md`；跨系统：`docs/gdd/balance/cross-system.md` | `design-balance`，在授权内直接维护 |
| 交付预拆分与当前 Product 范围 | `docs/product.md`、`docs/product/` | `product-author` |
| 已确认的项目术语与别名 | `docs/terminology.md`；GDD 与专业文档引用它 | `project-terminology` |
| 共享视觉方向 | `docs/art/art-bible.md` | `design-art-direction` |
| 共享声音方向 | `docs/audio/sound-bible.md` | `design-audio-direction` |
| 界面布局、状态及相关表现的引用 | `docs/ui/<interface>-design.md`；多个界面共用的控件写在 `docs/ui/components/<component-key>-design.md` | `design-ui-spec` |
| 一次游戏表现的过程、组件要求、候选方案与采用组合 | `docs/presentation/<scope>.md`；多份表现共用的组件见下文 | `design-game-presentation`；实现任务负责同步实际文件和接入关系 |
| 具体视觉资源的准备要求 | 写在所属表现、UI 或组件的资源章节；多个独立所有者共用的资源写在 `docs/art/art-bible.md` 的“共享资源规格” | `design-visual-asset-spec` |
| 具体音频资源的准备要求 | 写在所属表现、UI 或组件的资源章节；多个独立所有者共用的资源写在 `docs/audio/sound-bible.md` 的“共享资源规格” | `design-audio-asset-spec` |
| 语言覆盖、术语译名、回退、排版与翻译惯例 | `docs/localization/localization-spec.md` | `design-localization-spec` |
| 按已定要求接入真实资源 | 当前 Feature 或实验中的资源、引用与配置 | `content-asset-integration` |
| 按已定本地化要求实现运行支持 | 翻译资源、字体、界面适配与语言逻辑 | `content-localization` |

### GDD 与专业文档的分工

GDD 写玩家应该获得什么感受、需要辨认出哪些对象；画风、色板、质感等视觉标准写在 Art Bible，音色、节奏等声音特征写在 Sound Bible。例如“安静，且奖励一眼可辨”是体验目标，写在 GDD；“低饱和手绘”是美术标准，写在 Art Bible，两者互相引用。

专业文档把 GDD 的设计意图细化成可以使用和验证的规格：

- **专业规格写在所属文件**：GDD 只保留整体目标、玩法规则和引用。获准编写或整合 GDD 时，本次确定的专业规格一并放到所属位置；原先写在 GDD 里的当前规格迁过去。归属不取决于第一次写在哪里，也不取决于游戏复杂度。
- **Product 选择交付范围**：只保存必要的引用。
- **专业 Skill 直接维护自己的正文**：数值主题也不需要 `design-gdd` 代为保存。
- **需要改变整体设计时**：专业工作中发现要改变整体玩法规则或已确认的体验目标，由 `design-gdd` 协调这个决定；交付范围随之变化时，再由 `product-author` 处理。
- **维护不等于决定**：负责维护一份文档，不代表可以自行采用尚未决定的要求；本地化的翻译用词也不能改变玩法含义。

### 数值设计

数值设计从目标体验、单位、边界、规则和已知数据出发，交付可以复算的公式、参数，以及典型和关键边界的情景。

- 候选值、已采用的值和实际验证状态分开标注。
- 普通规格中出现的数字，不会自动变成数值建模任务。
- 计算成立不代表游戏已经平衡或有趣；写入数值也不授权修改运行时的资源或代码。
- 独立的数值审核由 `review-balance` 负责。

### 术语译名

本地化规范中的“术语译名”章节，是目标语言用词的唯一规格。每个条目引用项目术语的定义，写明语言、采用的译名和适用语境。

- `design-localization-spec` 维护这份表，`content-localization` 在运行译文中使用它，`review-localization` 据此检查一致性。
- 完整的句子和对话保存在运行资源中，不在 Markdown 里另存一份。
- 概念定义和开发时查找用的别名，仍然写在 `docs/terminology.md`。

规则见[本地化术语译名](../../../project-source/methodology/11-specialist-workflows.md#localization-term-translations)。

## 来源怎样约束任务

- **Feature 有一个主 `source`**：可观察的要求及其来源写进 AC；实施约束及其来源写进同编号的设计稿。共享来源对哪些任务生效，由适用范围、实际依赖和引用共同决定。
- **AC 要具体**：“符合 GDD”“符合 Art Bible”都不是合格的 AC，要写出本任务的实际状态、尺度和可观察的结果。
- **要求变化时**：在所属入口修改来源，再分析对已规划任务的影响。
- **Bug 的依据**：实现违反了已确认的专业要求，就可以作为 Bug 处理，不需要再在 Product 里抄一份要求；没有被采纳的设计建议不构成缺陷。
- **基线**：旧的同步锚点不能证明新纳入的来源当时已被吸收。“历史未知”和“当前已对齐”要分开说明。

GDD、专业规格、表现正文和本地化要求，都要在最终验证前完成本轮的必要更新，包括采用的组合、实际的实现与使用位置、资源的准备状态。这些文件都参与内容指纹，只改文字或准备状态也可能使旧结果失效，GDD 目录里的 README 也算在内。约束性的正文不能只写在不参与指纹的普通 README、notes、知识或报告里，规则见[内容指纹与失效判断](../methods-and-tools/commands-and-evidence.md#内容指纹与失效判断)。

## 用一次游戏表现连接设计与实现

以“物品入包”反馈为例：

- **UI 文档**：说明领取按钮在哪里、什么状态下可以点击。
- **表现文档** `item-added.md`：说明确认入包后，图标怎样飞行、数字怎样变化、目标位置怎样反馈。

设计时先从体验目标或口头描述整理出可观察的过程，再选择实现手段：已有实现、序列帧、Shader、粒子、Tween 或 AnimationPlayer。Shader 和粒子参考帮助整理标准化的需求，具体算法、节点和代码由实施任务决定。

能否领取、发放多少、能否重复领取，都由游戏逻辑决定；表现使用逻辑给出的有效结果，不能在图标飞到背包时再发一次奖励。普通控件的悬停、焦点或展开状态写在 UI 文档里即可，不需要为每一处表现单独建游戏表现文档。

### 从哪里找到什么

| 情况 | 怎样找 |
| --- | --- |
| 背包物品入包 | 从 UI 文档中对应的交互位置，或末尾的“关联游戏表现”，找到表现正文、采用的方案、实现和验收入口 |
| 奖励领取由多个部分组成，各有多个方案 | 分别写“图标飞行 A / B”“目标反馈 A / B”；当前采用“图标飞行 B + 目标反馈 A”时，引用各部分，不重复写整套组合 |
| 多个界面使用同一种奖励反馈 | 共用一份表现正文；各界面只写自己的触发方式、采用组合和使用位置 |
| 角色死亡 | 从相关 GDD 章节和表现总览进入，不需要为此建 UI 文档 |
| 只替换某个组成部分的实现技术 | 保留已确认的要求，同步采用组合和真实路径，完成相应验证；如果目标本身变了，按设计变更处理 |

### 表现文档怎样拆分

- **按触发时刻和玩家感知划分**：商店购买和奖励领取若都是同一种“物品入包”反馈，共用 `docs/presentation/item-added.md`，各自说明来源上下文。“奖励揭晓”这种独立过程另写一份，它的结尾发生入包时，引用已有的正文。不会只因为使用的界面不同就拆成两份。
- **正文按需组织**：目标与过程、组件的标准化需求、候选方案、资源规格、采用关系、实际实现和验收入口。
- **共享组件**：组件只属于一份表现时，写在父文档的小节里；第二份独立的表现也需要同样的组件时，把共同的要求、候选方案和资源规格迁到 `docs/presentation/components/<component-key>.md`，原正文改为引用。多个界面引用同一份表现，不会触发这种迁移。迁出后只要还有使用方就保留原路径，各父表现只维护自己的过程、触发上下文、采用组合和验收入口。规则见[表现文档约定](../../../project-source/methodology/11-specialist-workflows.md#game-presentation-documents)。
- **UI 文档的拆分**：按[界面文档边界](../../../project-source/methodology/11-specialist-workflows.md#ui-document-boundaries)，有独立进入、退出和交互流程的屏幕或弹层单独成文；从属的面板、标签页和 HUD 部件留在宿主文档的章节里。第二个界面也使用同一控件或对话框行为时，把共用正文迁到 `docs/ui/components/<component-key>-design.md`，调用处改为引用；只是外观相同，则引用 Art Bible。
- **导航**：`docs/presentation/README.md` 列出各表现和共享组件之间的实际使用关系，具体要求写在各自的正文中。UI 界面或组件规格新增、改名或删除，或者导航中的用途、关联 Product、组件使用方发生变化时，`design-ui-spec` 同步维护 `docs/ui/README.md` 中受影响的条目，不需要审查无关的目录内容。

### 表现与任务、验收的关系

- 表现文档和开发任务不需要一一对应。只把已采纳的要求和当前获准的方案接入现有 Feature 的来源、AC 或设计稿；候选方案可以只有描述，不必全部做出来。
- 有具体的不确定之处时，才用 Godot 原型验证；正式实现仍走已有的开发任务。
- “规划完成”“实现可用”“用户人工接受”要分别说明。表现文档链接到原任务的验收条件、运行入口和已有报告或完成记录，结果本身留在原记录里。替换方案之后，旧记录保持原来的版本和覆盖范围；不要把验收结果抄回表现正文，再声称它覆盖了修改后的文档。

## 资源规格随所属设计保存

资源规格的位置按[资源规格归属](../../../project-source/methodology/11-specialist-workflows.md#resource-requirements-and-handoff)确定：

- 某个表现方案专用的资源，写在该方案中。
- 某个界面专用的资源，写在该 UI 文档中。
- 已抽出的共享组件专用的资源，写在该组件文档中。
- 被多个独立所有者共用的视觉或音频资源，分别写在 `docs/art/art-bible.md` 或 `docs/audio/sound-bible.md` 的“共享资源规格”章节。

用途扩大导致归属改变时，连同准备状态一起迁移，使用方改为引用同一份正文。项目里没有单独的资源清单目录，也不按 Feature 或到货批次另建台账。

每个资源条目按需要写明：用途、文件名、格式、尺寸或时长、透明或循环等约束、准备状态、源位置与目标位置、与真实文件的对应关系。

- 视觉资源要区分源图像素、显示尺寸，以及去掉透明边距后的主体大小；音频资源不填无意义的像素字段。
- 需要资源 ID 时，只在所属文档或章节内保持稳定；跨文档引用时带上路径和章节。
- 候选值、已确认的要求和实测信息分开写；来源和许可不清楚时，保留为缺口。

例如“命中时出现短暂火花”，即使最终的纹理还没到，也可以先写清运动方式、数量感、持续时间和触发方式；选定的粒子方案需要纹理时，再把纹理的规格和准备状态写进该方案。缺少文件只影响依赖它的实现或体验判断，规划可以继续。

框架目前覆盖资源的准备要求、接收和检查，不包括图片、音乐、音效的制作，也不包括在本地资源库中检索素材。外部交付真实文件后，由接收任务更新同一个所属章节，再由获准的接入任务检查实际使用。参考图、占位文件名或规格文档都不是成品；提出规格也不代表授权制作、购买或导入资源。

## 视觉原型与实际接入

### UI 规格与原型

UI 规格描述信息层级、ASCII 布局、状态差异、显示条件和待验证的问题；节点、路径和参数属于实现。新界面或明显的布局变化，需要一个能单独运行的 Godot 原型作为视觉判断依据；已有且仍适用的原型可以复用。

- **原型范围**：在已授权的 Feature 或限定实验内进行，可以使用本地示例数据和悬停、焦点等必要交互，默认不接入正式的存档和业务规则。
- **判断条件**：真实素材、目标窗口、缩放比例、空状态与密集状态、裁切和可读性共同决定结论；图片的原始像素不足以说明主体尺寸合适。
- **接受与采用**：用户接受原型只覆盖原型本身，正式功能仍有自己的验证义务。采用之后，清理示例数据和失去用途的副本，不长期维护两套竞争的界面。

原型和正式逻辑谁先做，取决于要回答的问题：验证商品排列可以先用示例余额；正式接入购买时，就要核对真实的请求、状态和结果。替换动画技术时，保留已确认的规则和表现目标；动画需要参与命中判定或流程时机时，由实现明确时序和结果判定，不能把“动画播放完”当作业务成功。

### 接入素材

- 对照实际文件、规格、来源记录和使用方，检查导入设置、路径与 UID，以及场景、主题和代码中的绑定。
- 声音的触发、停止、循环接缝、重复叠加和相对音量，要在真实场景中试听；文件存在或播放器启动了，都不说明听感合格。
- 保留外部原件和无关资产，不要盲目重新导入整个资源库。

占位资源使用 `_placeholder_` 前缀，并在原任务中说明用途、何时替换以及验收上的缺口。源资源、导入结果、工作台预览和正式游戏各有自己的验证范围；示例通过不代表游戏的 Feature 完成。

## 测量与实现

具体的异常统一由 [bug-diagnosis-godot](../../../project-source/skills/bug-diagnosis-godot/SKILL.md) 按[因果诊断](../../../project-source/methodology/07-engineering-change.md#causal-diagnosis)处理：先看症状、预期和证据，再选择需要的专业方法。用户不需要先判断问题属于逻辑、表现还是两者的连接。

例如已确认“角色受击后闪红”，但实际上生命值正确减少了，却没有闪红。扣血正确只说明状态变化符合预期；Agent 还要检查受击结果有没有传到反馈控制、播放有没有被打断、材质和参数是不是接到了正确的对象。只有证据指向 Shader 的数据流时，才按需使用 [Shader 诊断参考](../../../project-source/skills/bug-diagnosis-godot/references/shader-diagnostics.md)中的临时可视化或固定条件比较。不能只因为画面异常就认定 Shader 有错，也不需要预先拆成“逻辑 Bug”和“表现 Bug”。

修复由原任务承接。涉及算法选择时，可以直接查阅 [Shader 实现方法](../../../project-source/skills/implementation-guidance-godot/references/shader-implementation-methods.md)，同时遵守 [Shader 工程规则](../../../project-source/agent-rules/30-shaders/README.md)；读参考不会启动新的指导任务，也不增加写入授权。表现要求、采用的方案，或文档中记录的实际文件与接入关系变化时，同步所属设计；诊断和验证的结果留在原任务的证据位置。

### 诊断用的 Skill

| Skill | 用途 |
| --- | --- |
| `diagnostics-instrumentation` | 提供有明确目的、单位和开销边界的日志、计数或时序信号 |
| `diagnostics-performance` | 在可重复的负载下测量性能，找出瓶颈 |
| `diagnostics-soak-test` | 在明确的时长和停止条件下观察长期运行的趋势和失败 |

使用时注意：

- **只有静态推测时**：不能写成“已定位瓶颈”。
- **授权与副作用**：只做测量和诊断，不代表获准做持久的优化；日志、缓存和报告本身也是副作用。接入、本地化、埋点和优化等持久修改，由原 Feature、限定实验或获准的工程任务承接。
- **版本与条件**：临时埋点的版本和最终交付的版本要分开。可比较的测量要说明设备、引擎版本、场景、负载、参数和测量条件；计划运行六小时、实际只运行了四十分钟，就要记为缺口。

专项测量的结果不能包装成 gdUnit 通过，完成记录工具也不判断性能、长测或感官证据是否充分。修复之后，相应的真实检查仍然要做。

## 独立审核

各审核 Skill 分别检查自己的对象：`review-code`、`review-ux`、`review-art`、`review-audio`、`review-assets`、`review-localization` 和 `review-balance`。一个新的审核实例可以同时使用多个适用的 Skill，不要求每个 Skill 各审一轮，也不要求每个 Feature 都经过独立审核。

### 审核前要准备什么

- **输入**：明确的范围、权威来源、实际版本或差异、原始证据，以及允许运行的范围。
- **快照**：包含相关的未提交内容；只复制 HEAD 可能漏掉本次成果。
- **独立性**：作者的解释只是待核实的陈述；作者自查不能称为独立审核。

### 审核中的保护

- 被审成果、原验收记录和原证据都是只读的。
- 获准做针对性验证时，使用安全副本或指定的外部验证环境，把日志、缓存、导入结果和测试数据一并隔离。只换报告目录不够；使用 worktree 也不能代替对实际副作用的核对。
- 条件不足时保留未验证项；没有实际看到或听到，就不宣称视觉或音频体验通过。

### 审核什么、怎样报告

- **审核现有实现**：不需要 Feature 或差异基线，按相关 GDD 判断是否符合。
- **审核设计本身**：GDD 草稿或完整设计可以用 `plan-review-godot` 审核，不要求 Product、Feature 已经建立，也不要求所有规则都已确定。
- **要求缺失时**：某项具体要求缺失，就限定“是否符合”的结论范围，在有依据的其余部分继续检查质量。
- **报告内容**：检查的版本、实际覆盖的范围、问题、依据和限制。审核过程中成果发生变化，要限定结论或补查变化的部分。
- **报告位置**：默认在对话中交付；需要留存时，放在 `reports/features/` 或 `reports/maintenance/` 下的相应目录。

报告已交付、审核条件已满足、用户已人工接受，是三件不同的事。问题的优先级不授予修复权限；但已确认会阻断完成的问题，也不能因为“审核是可选的”而忽略。

权威规则见[专业职责规范](../../../project-source/methodology/11-specialist-workflows.md)和[独立审核规范](../../../project-source/methodology/12-independent-review.md)。
