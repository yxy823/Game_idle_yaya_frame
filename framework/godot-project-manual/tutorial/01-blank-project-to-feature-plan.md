# 教程一：从空白项目到第一份 Feature 计划

[Godot 项目手册](../README.md) · 下一篇：[完成第一个 Feature](02-first-feature-to-done.md)

这组教程用一个真实项目，带你按顺序走一遍框架的主线。共三篇：

1. **本篇**：创建项目、配置环境、整合 GDD、拆分 Product、定美术方向，做出第一份 Feature 计划。
2. [完成第一个 Feature](02-first-feature-to-done.md)：做视觉样例，等待验收期间先推进别的 Feature，记录验收并收尾。
3. [修正时过时不过的测试](03-fix-a-flaky-test.md)：交付后发现不稳定的测试，按维护任务修正。

教程只写每一步做什么、当时为什么这样做。规则正文以链接的参考页为准；两者不一致时，以参考页为准。

## 示例项目与阅读方式

示例是一个最简三消游戏：8×8 棋盘，交换相邻棋子形成三连，看着消除、下落、补充和连锁，没有分数、关卡和胜负。它的仓库在本机 `D:/A_Games/Game_Match_Three`，按本教程的顺序开发，已完成两个 Product、13 个 Feature。

- **摘录**：教程直接摘录关键内容，不需要打开示例项目也能读懂。
- **提交**：形如 `7c66804` 的是示例仓库的提交。想看全文时，在示例仓库运行 `git show 7c66804`。
- **路径**：`docs/`、`yaya/tools/` 等路径相对项目根目录，和手册其他页面一致。

## 怎样发出每一步

每一步都从 [Godot 开发提示词库](../../prompt-scenarios/prompts/godot-development-prompts.json)选一条提示词：复制正文，把 `${…}` 占位处换成你的材料，发给 Agent。下文写成「分类 → 名称」。

不确定该用哪条时，可以问 Agent“下一步该做什么”，由 advisor 推荐并起草，见[advisor 的共享场景入口](../methods-and-tools/skills-and-agents.md#advisor-的共享场景入口)。

## 1. 创建空白项目

在框架仓库根目录运行创建器，或者用「项目创建与接入 → 准备开始新游戏，先创建空白项目」让 Agent 运行。目标路径不能含中文或空格：

```powershell
python -B framework/project-creation/tools/create_project.py --output D:\A_Games\Game_Match_Three
```

**得到什么**：创建器按复制清单复制文件，建立独立的 Git 仓库并做初始提交（示例 `c697cba`）。框架的流程、规则和工具在 `yaya/` 下，游戏内容放在 `game/`、`components/`、`assets/` 和 `tests/`。

**为什么这样做**：项目从这一刻起独立拥有自己的文件，框架之后的更新不会自动同步进来。创建器只复制文件，不探测环境、不运行 Godot，所以接下来要配置环境。详见[框架和项目各管什么](../foundations/framework-and-project.md#框架和项目各管什么)与[项目对象与目录](../foundations/project-layout.md)。

## 2. 配置环境并完成首次扫描

**配置工具路径**：使用「项目创建与接入 → 空白项目已经创建，现在配置开发环境」，材料填已确认的 Python 3.12+ 路径、Godot 路径，以及可选的项目名称。

Agent 把路径写进 `docs/methodology-config.json`，运行环境检查，并把过程写进本机的 `reports/initialization.md`。你提供了项目名称时，它还会改掉 `project.godot` 里默认的“New Godot Project”。示例配置（`bb42e73`）：

```json
{
  "document_language": "zh-CN",
  "engine_executable": "E:\\GameTools\\Godot\\4.7.1\\Godot_v4.7.1-stable_win64.exe",
  "python_executable": "C:\\Users\\89523\\anaconda3\\envs\\codex-python\\python.exe"
}
```

环境检查输出 `READY`，只说明路径可用、Godot 版本符合要求，不说明测试能跑通，见[环境就绪的含义](../foundations/framework-and-project.md#环境就绪的含义)。

**首次扫描**：接着使用「项目创建与接入 → 第一次运行项目，Godot 还没有完成资源扫描」。还没遇到错误时，“首次运行错误”填“无”，作为预防性扫描。

- **为什么要先扫描**：Godot 没扫描过的项目，测试运行器会报找不到 `GdUnitTestSuite` 这类类名。这是环境没准备好，不是业务测试失败。
- **扫描的产物**：会为插件资源生成 `.import` 文件，它们随项目提交。示例 `bcac609` 提交了 12 个。

## 3. 把已有设计整合成 GDD

GDD 是之后一切规划和实现的依据，空模板不能代替它，见[GDD 是项目开发的前提](../requirements-and-tasks/requirements-and-planning.md#gdd-是项目开发的前提)。

- **已有设计资料**：一份完整的外部设计稿，或散在几处的资料，都使用「需求设计 → 设计资料分散在多处，需要整合 GDD」。材料填资料位置、已确认的决定，以及资料之间已知的冲突。
- **只有想法**：改用「需求设计 → 只有游戏想法，先形成 GDD 草稿」，先讨论成形。

**示例怎样做的**（`7c66804`）：用户提供了桌面上的一份完整设计稿，Agent 按固定位置拆分，原件不改。

| 原稿内容 | 去处 |
| --- | --- |
| 定位、体验、范围、核心循环、状态机 | `docs/gdd/` 下的 `concept-and-experience.md`、`design-scope-and-boundaries.md`、`gameplay.md` |
| 棋盘、输入、匹配连锁、死局洗牌的规则 | `docs/gdd/systems/` 下各一个主题 |
| 术语定义 | `docs/terminology.md` |
| 选中标识、轻抖、“重新随机”按钮 | 界面规格 `docs/ui/game-board-design.md` |
| 消除特效、洗牌淡出淡入 | 表现文档 `docs/presentation/` |
| 棋子外观 | 美术圣经 `docs/art/art-bible.md` |
| 洗牌能否可靠完成、目标体验还缺证据 | 开放问题 `docs/gdd/open-questions.md` |

**为什么要拆**：后面的 Product 和 Feature 都按章节引用这些文档，作为“这条要求从哪里来”的依据。规则与表现规格各有维护者，分开后改一处不会牵动另一处，见[专业来源与资源](../specialist-work-and-records/specialist-work.md#各类来源由谁维护)。

**你要做的**：核对整合后是否保留了原意。资料互相冲突时，Agent 会问你，不会替你决定。

## 4. 先预拆分 Product，再细化第一个

**预拆分**：使用「需求设计 → 已有 GDD，需要预拆分 Product 交付范围」。Agent 把 GDD 的整个范围拆成几个交付单元，写进 `docs/product.md`，只定粗边界、来源和建议顺序。

示例拆成两个候选（`592741f`）：

1. **可玩的三消核心循环**：启动后能选择、交换，看到消除、下落、补充和连锁。
2. **死局恢复与洗牌**：棋盘没有合法交换时，用“重新随机”恢复。

洗牌的可靠性还缺实测证据，所以单独放在后面，不拖慢第一个可玩版本。

**细化当前 Product**：轮到哪个再细化哪个。使用「需求设计 → Product 已预拆分，准备细化当前交付范围」，Agent 写出 `docs/product/01-playable-core-loop.md`（`2e7f149`）：交付目标、逐项来源、包含与推迟的范围、前提，以及 8 个端到端验收场景。

示例中的一个边界取舍：GDD 要求“重新随机”按钮始终显示，但按钮属于第二个 Product。第一个 Product 只在布局中为它预留位置，不显示按钮。这种交付顺序造成的中间状态写在 Product 里，不改界面规格。

**为什么分两步**：预拆分不是承诺，前一个单元交付后可能改变后面的顺序。只细化当前单元，避免过早写死细节，见[先预拆分，再逐个细化与交付](../requirements-and-tasks/requirements-and-planning.md#先预拆分再逐个细化与交付)。

## 5. 有新界面时先定美术方向

Product 包含新界面、而 `docs/art/art-bible.md` 只有一句占位时，先定美术方向，再做 Feature 计划。使用「需求设计 → 当前资产的美术方向不明确，需要定下来」，材料填资产范围、目标体验、参考和显示条件。

示例的结果（`8619407`）：扁平几何、深色中性背景、高亮只留给反馈；6 种棋子的色相和亮度同时拉开，兼顾常见色觉缺陷。具体色值不在这里定，留给视觉样例确认后写回。

**为什么要先定**：视觉样例的验收条件依赖这个方向。方向不定，样例只能盲目尝试，验收也没有标准。

**示例的教训**：示例是在第一份计划写好之后才定美术方向的。结果又用「任务规划 → 要求已经改好，同步受影响的 Feature」修订了 F001、F005、F006 的验收条件（`04cba80`）。先定方向，可以省掉这一轮修订。

## 6. 做第一份 Feature 计划

使用「任务规划 → 当前模块的需求已确认，准备做项目的第一份 Feature 计划」，材料填已细化的 Product 和相关来源。

**先预览，后写入**：Agent 先展示 Feature 数量、每项的范围、验收条件（AC）要点和依赖。你没有授权它自主拆分时，它停下等你确认，再写入。

示例拆出的 7 个 Feature（`14f52f1`）：

| Feature | 内容 | 验收方式 | 依赖 |
| --- | --- | --- | --- |
| F001 | 视觉样例：布局、配色、选中标识与轻抖 | 人工 | 无 |
| F002 | 生成并验证合格的初始棋盘 | 自动 | 无 |
| F003 | 结算消除、下落、补充与连锁 | 自动 | F002 |
| F004 | 状态机：选择、交换与输入锁定 | 自动 | F002、F003 |
| F005 | 视觉样例：消除特效 | 人工 | F001 |
| F006 | 正式棋盘主界面，可用鼠标选择与交换 | 人工 | F001、F004 |
| F007 | 主界面呈现消除、下落、补充与连锁 | 人工 | F005、F006 |

这份拆分有两个值得注意的安排：

- **视觉先行**：F001、F005 是视觉样例，需要你看过才能定参数。依赖布局的 F006、F007 通过依赖关系排在它们之后。
- **规则可以并行**：F002～F004 是纯规则，不依赖布局，可以在等你验收视觉样例时推进。[教程二](02-first-feature-to-done.md#等待验收时先做别的-feature)会用到这一点。

每条 AC 写明来源和验证方式。F001 的 AC04 摘录：

> 选中标识显示在被选棋子所在格的四个角，不使用棋子整体高亮，同一时刻只有一处；标识为中性浅色……（来源：ui/game-board-design.md#选中标识、art/art-bible.md#反馈的视觉层级）
>
> 人工检查：点击棋子后所在格四角出现中性浅色标识，同一时刻只有一处，转选时标识移到新格，棋子本身不被高亮。

**基线**：计划写入时绑定当时的来源提交，作为基线 R000。之后 GDD 或规格变化时，Agent 据此判断哪些 Feature 受影响，示例第 5 步的修订就是这样找出来的，见[基线与需求修订](../requirements-and-tasks/requirements-and-planning.md#基线与需求修订)。

**你要做的**：确认拆分和依赖是否合理，尤其是每项的验收方式。需要人看、人听、人操作才能判断的，用人工验收，见[自动与人工验收](../requirements-and-tasks/feature-lifecycle.md#自动与人工验收)。

计划写好后，F001 和 F002 可以开始。下一篇从执行 F001 讲起：[完成第一个 Feature](02-first-feature-to-done.md)。
