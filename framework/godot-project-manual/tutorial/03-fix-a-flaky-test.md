# 教程三：交付后维护：修正时过时不过的测试

[Godot 项目手册](../README.md) · 上一篇：[教程二：完成第一个 Feature：视觉样例、等待验收与收尾](02-first-feature-to-done.md)

本篇讲交付之后的一类常见维护：同一份代码，某个测试有时通过、有时失败。示例项目的两个 Product 都交付后遇到了这种情况，用一个维护任务 F013 修好。示例项目的读法见教程一的[示例项目与阅读方式](01-blank-project-to-feature-plan.md#示例项目与阅读方式)。

## 现象：同一份代码，时过时不过

示例里有个测试检查“交换时棋子有可见的移动过程”（F006-AC05-02）。

- **在项目目录跑全量测试时**：它偶尔失败，报告棋子位移为 0。
- **单独运行、或在干净副本里运行时**：它都通过。
- **游戏本身**：交换动画已经人工验收过，实际玩起来正常。

另一个检查洗牌淡出时长的测试（F011-AC04）也失败过一次：要求不短于 0.2 秒，测得 0.199257 秒。

代码没变、结果却变，问题出在测试本身。这样的测试比没有测试更糟：它失败时，你分不清是游戏坏了还是测试不稳；它通过时，也不能完全相信。

## 用哪条提示词

使用「出了问题 → 同一个测试时过时不过，需要修正测试本身」。材料填：

- 不稳定的测试；
- 失败和通过的运行记录；
- 出现失败的环境，例如“在项目目录跑全量时失败，单独运行通过”。

如果查下去发现是游戏行为本身有错，Agent 会停下，改走 Bug 的处理方式（「出了问题 → 发现 Bug，需要修复」）。

## Agent 怎样处理

修正测试不改变游戏行为，所以按维护任务处理：先用 `engineering-change-plan` 的 maintenance 模式建立任务，再由 `feature-execute` 实现和交付。示例中新建了 F013，验收方式为自动（`ec8c28e`）。

**1. 从失败的原始记录查原因**

示例的两个测试都按真实的帧来观察动画：

- **测位移的测试**：每帧采样一次位移。
- **测时长的测试**：把每帧的时间间隔累加起来。

Agent 逐帧记录后发现，交换动画开始的那一帧，时间间隔就有约 0.10～0.13 秒，和整段 0.12 秒的交换动画一样长。动画在一帧之内就播完了，下一阶段又在同一帧把棋子放回原位，所以采样从来没看到移动后的位置。帧间隔取决于机器当时的快慢，于是测试时过时不过。

**2. 按原因修改：由测试控制动画时间**

既然问题是“时间由机器决定”，就改成由测试决定：

- 被测代码创建动画后，测试立刻把它暂停；
- 测试按固定的小步长（1/128 秒）一步步推进动画；
- 每推进一步就检查一次状态，直到动画播完。

这样每次运行看到的过程完全相同。游戏代码一行没改，用的是 Godot 动画（Tween）自带的暂停和手动推进接口（`d24e93b`）。写法和示例代码见[动画与 Tween 的测试规则](../../../project-source/agent-rules/70-tests/time-randomness-and-async.md#动画与-tween)。

**3. 验证：既要稳定，也要仍然有效**

- **稳定**：在原来出现失败的项目目录，连续 5 次全量运行，每次 101/101 通过。
- **仍然有效**：临时把交换动画缩短到 0.05 秒、把淡出淡入缩短到 0.15/0.2 秒，三个测试都按时长断言失败，然后恢复。这证明修改后的测试仍能抓住“动画太短”的问题。

示例的收尾提交是 `9bd0eb2`。

## 不能用的“修法”

下面这些做法能让测试变绿，但都没有解决问题。提示词明确禁止它们：

- **放宽断言**：例如把“不短于 0.2 秒”改成“不短于 0.15 秒”。
- **加长等待**：多等几帧碰运气。
- **失败重试**：跑到通过为止。
- **跳过或删除测试**：问题被藏起来了。
- **为了测试改游戏行为**：例如把已验收的动画改长。

## 教训的去处

这次的教训分两层保存：

- **工程规则**：动画测试由测试推进时间、不采样真实播放，写进了时间、随机数与异步测试规则的[时间与帧](../../../project-source/agent-rules/70-tests/time-randomness-and-async.md#时间与帧)，以后创建的项目都会带上。
- **示例项目的知识条目**：记录本项目的具体情况和测试辅助代码的位置，见[知识、设计与记录](../specialist-work-and-records/knowledge-and-records.md)中项目知识的说明。

示例早先还有一条“逐帧累加时间来判断动画时长”的经验，工程规则里也有同样的写法。这次证明它是错的，两处都已删除，没有保留成“已取代”的旧做法。
