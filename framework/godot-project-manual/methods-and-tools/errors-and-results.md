# 错误与结果的含义

[Godot 项目手册](../README.md)

本页按“遇到的现象”解释生成项目中工具的输出。看到非零退出或异常时，先判断问题出在哪一层：环境、调用方式、测试发现、行为断言、引擎诊断还是记录导入。不同层的问题处理方式不同，不要一律当作游戏 Bug。

各种成功结果分别能证明什么，见[命令与验证证据的「每种结果能证明什么」](commands-and-evidence.md#每种结果能证明什么)。

## 创建与环境

| 现象 | 含义 | 该怎么做 |
| --- | --- | --- |
| 创建器拒绝目标路径 | 目标是文件或非空目录，或者路径含中文或空白，或者与框架目录互为上下级 | 换一个符合条件的空目录；拒绝不代表可以强制覆盖 |
| 复制或 Git 失败后留下了目录 | 创建器不会自动回滚 | 根据原始输出判断哪些步骤已完成，不能因为目录存在就报告创建成功 |
| 普通配置检查成功 | 只说明字段结构正确；Godot 路径暂时为空也会通过 | 需要确认可用时运行 `--require-ready` |
| Godot 文件存在但就绪检查失败 | 实际启动失败、返回码异常，或版本不是 4.7.x | 核对路径指向的真实程序；目录名里的版本号不算数 |
| 路径写法错误 | Godot 路径按项目根目录解析，不能带 shell 引号、参数或只写命令名；Python 可以写已确认的 PATH 命令名 | 按[配置参考](../foundations/configuration.md#路径与命令的写法)修正 |
| CLI 报告缺少测试基类或运行器全局类 | 首次资源与类扫描可能还没完成，测试其实没有执行 | 先完成首次扫描；就绪检查不包含扫描 |
| Windows 上读不到退出码 | 很可能没有等 Godot 进程结束 | 使用命令示例中的 `| Out-Host`；空值不能当作 0 |
| 权限、AppData、缓存或沙箱错误 | 环境限制，与业务逻辑无关 | 先按实际环境规则定位；不要因此改业务断言、删除未核实的目录，或断定引擎有错 |

创建器的完整契约见[框架、创建器与项目边界](../foundations/framework-and-project.md#创建器用法)。

## Feature 记录与任务

| 现象 | 含义 | 该怎么做 |
| --- | --- | --- |
| 索引或必要的详情文件缺失 | Feature 记录不完整，不是“空项目已初始化” | 如实报告当前文件状态 |
| `--eligible` 输出为空 | 当前没有依赖已满足的 pending 任务，可能是被依赖阻塞 | 检查依赖链；不要推断所有 Product 已完成 |
| ID 冲突、依赖成环、依赖已废弃或引用不一致 | 计划结构或历史关系不满足契约 | 修正计划结构；不能靠随意修改完成状态消除错误 |
| 组件没有单元测试路径 | `unit_test_paths: []` 是合法写法 | 无需处理；已登记但文件缺失才是错误 |
| 用 planned 或 retired 测试支撑当前完成 | 当前完成必须有 active 的真实测试映射；退役测试只用于追溯历史 | 为当前 Feature 补上 active 的验证 |
| 改了 AC 之后测试通过 | 新的预期是否已被正式采纳，需要用户的真实决定 | 先确认需求变更；测试变绿不代表需求获准 |

## 测试与完成依据

| 现象 | 含义 | 该怎么做 |
| --- | --- | --- |
| 零测试、发现集合不完整、必需用例被跳过 | 覆盖不满足；源文件里有方法不代表它执行了 | 修正测试发现或登记后重跑 |
| focused 或 baseline 运行通过 | 只说明那一次的用途和范围 | 最终验证仍按 Feature 运行 |
| JUnit 全绿但运行器报告失败 | 还有引擎诊断、进程退出、覆盖或报告方面的问题 | 读取诊断找原因；不能把运行器结果改成通过 |
| 超时，或 `result.json` 仍是 running | 本次运行没有完整结束 | 处理超时原因后重新运行；不要并发启动同一运行，也不能用旧摘要补全 |
| 运行器提示历史结果无效 | 那份历史文件不能作为依据 | 按当前结果和契约分别判断能否继续、能否完成 |
| 报告写入失败，或只打印了路径 | 打印路径不代表文件存在 | 如实报告实际输出和缺失范围 |
| `record-tests` 非零退出 | 本次导入失败，旧的测试引用已被清除；原始报告仍在 | 修正问题后重新导入；不能手填哈希或通过次数 |
| `show` 退出 0 | 记录结构和 Feature 身份匹配，可以展示 | 不代表能完成；用 `validate` 判断 |
| `validate` 退出 0 | 测试引用与适用的人工接受满足记录契约 | 直接静态检查、独立评审、性能和目标平台仍需各自确认 |
| `record-acceptance` 退出 0 | 状态已如实记录，可能是 accepted、rejected 或 pending | 只有 accepted 才满足人工接受 |
| 人工验收记录失败 | 清单缺失、检查项定义被改、覆盖不全，或绑定后内容有变化；旧记录被保留 | 按报告处理本次问题；绑定后有变化时逐个核对变化文件；旧记录不能抵消这次错误 |
| 运行器返回 `not_required` | 有效的 manual 计划没有自动测试义务，也没有阻断条件 | 这不是测试通过；人工验收等其他义务照常进行 |

测试失败时，预期和实现哪一方错了，要依据已确认的 GDD、Product 交付要求、专业规格或工具契约来判断。意图不明确时先澄清，不能先改断言让测试变绿。

已有证据突然失效，原因常常不在代码：GDD、Product、术语、专业规格、设计、规则、架构或资源准备状态的任何字节变化都可能改变内容指纹，GDD 目录里的 README 和尚未开发的章节也算在内。只有 Progress 历史、知识与调研中的 Markdown 等少数位置不参与计算，完整规则见[内容指纹与失效判断](commands-and-evidence.md#内容指纹与失效判断)。原件缺失时状态就是“未知”，不能靠修改摘要或哈希修复。

## 引擎诊断与专项观察

`Orphan StringName`、`Unclaimed StringNames` 等 verbose 输出本身不能证明业务代码有泄漏。用同版本、同参数、不含业务代码的最小项目做对照有助于定位，但对照中出现同样信息也不足以断定是引擎缺陷；反过来，进程退出 0 也不能证明没有泄漏。记录版本、复现步骤、原始日志和仍未知的影响。

场景启动、图片显示、声音试听、输入、长时间运行、资源包和导出依赖，各自都需要对应的实际结果。报告时把“未执行”“失败”“报告丢失”“只有旧版本成功”分别写清，不要合并成“没有问题”。

工具的错误契约见[工具说明](../../../project-source/tools/README.md)、[测试策略](../../../project-source/methodology/08-test-traceability-and-evidence.md)和[人工验收文件契约](../../../project-source/methodology/contracts/manual-acceptance-files.md)。
