# 游戏逻辑、表现与协作

[Godot 项目手册](../README.md)

游戏逻辑负责规则、业务状态和有效结果；游戏表现负责让玩家看见、听见、感受到这些结果。用这两个概念可以理解一个功能由哪些部分组成，并找到对应的设计和实现。环境、测试、构建与开发流程属于两者共用的工程支持，不归入任何一层。

阅读一个功能时，可以按“游戏目标 → 规则与表现要求 → 所属文档 → 实现与协作 → 验证与验收”的顺序查找。本页用一次商店购买走一遍这条路径；生成项目里对应的说明是[游戏组织指南](../../../project-source/defaults/docs/game-organization.md)。

## 1. 从一次购买看职责

玩家想购买商品时，界面显示价格并接受操作；游戏逻辑判断余额、库存及背包条件，执行获准的购买并给出结果；表现根据结果更新界面、播放获得物品的反馈。

| 玩家经历的过程 | 游戏逻辑负责什么 | 游戏表现负责什么 |
| --- | --- | --- |
| 打开商店 | 提供当前余额、商品及可购买条件 | 展示商品、价格、按钮与当前可操作状态 |
| 点击购买 | 接收请求，检查条件，决定成功或失败 | 采集操作并提交请求，提供按压反馈 |
| 购买成功 | 扣费、增加物品、更新库存，给出实际结果 | 刷新显示，播放图标飞入背包、提示与声音 |
| 购买失败 | 给出失败结果及适用原因 | 显示相应提示，避免播放成功反馈 |

界面显示“可以买”只是当前判断的展示。真正处理购买时，逻辑仍根据有效状态决定结果；图标到达背包的动画也不能自行再发放一次物品。

表现不必等所有逻辑结束才开始：按钮按下时可以立即缩放，购买成功的反馈则等待有效结果。AI、计时器和其他游戏系统也能触发状态变化，因此玩家输入只是入口之一。

## 2. 请求、状态与事件分别说明什么

| 协作内容 | 购买中的例子 | 使用目的 |
| --- | --- | --- |
| 行为请求 | 购买指定商品 | 表达意图；逻辑判断是否允许及实际结果 |
| 当前状态 | 余额、库存、已持有物品 | 打开或恢复界面时重建正确显示 |
| 一次性事件 | 本次购买成功，获得了哪些物品 | 触发与这一次结果有关的动画、提示和声音 |

请求、状态和事件描述协作含义，具体可以通过已有方法、返回值、API、Godot Signal 或必要的协调者实现。并非每个功能都要建立三种对象，也不要求统一使用全局事件总线。

游戏规则所依据的状态需要明确所有者；表现也有自己的状态。例如玩家真实生命值已经从 100 变成 80，血条仍可以在过渡中显示 90。重新打开界面时应恢复当前生命值，不能把“读到 80”当成又受到一次伤害。悬停、焦点、提示框展开和播放进度通常由表现维护；装备选择是否生效等会改变游戏规则的决定则归逻辑。

动画参与玩法时，按实际需要说明时序输入、打断条件和结果判定责任。例如攻击动画提供命中时刻，逻辑检查攻击是否仍有效并决定伤害。两层职责不禁止这种协作，也不能把“动画播放完了”直接当成无条件成立的游戏结果。

## 3. 沿文档找到设计、实现与验收

下表按职责定位正文；实际项目链接已有文件与章节，不要求为一次购买创建所有文档。

| 需要知道的内容 | 正文归属 | 商店购买中的具体内容 |
| --- | --- | --- |
| 为什么这样设计，哪些行为与反馈成立 | GDD | 购买规则、价格规则、失败条件和获得物品的体验目标 |
| 当前交付多少 | Product | 本次交付哪些商店能力，哪些内容暂缓 |
| 界面怎样组织 | UI 设计文档 | 商品排列、余额显示、按钮状态和交互，引用购买成功表现 |
| 一次反馈怎样展开 | 游戏表现文档 | 图标飞行、数字变化、声音的过程、备选方案及当前采用组合 |
| 实际由谁维护状态、怎样连接 | 架构或必要的 Feature 设计 | 购买操作、余额与背包所有者、界面消费者和运行入口 |
| 本次做到什么、怎样判断完成 | Feature 与验证记录 | 规则与反馈的 AC、相关测试、人工检查及真实验收结果 |

注意两点：GDD 同时包含玩法规则和体验目标，不是“逻辑文档”；“表现”也不只是游戏表现文档，普通控件的状态写在 UI 文档里，共享的视觉与声音要求写在美术和声音方向文档里。每项内容只写一份正文，其他地方引用。

文档之间这样连接：商店 UI 文档在“购买成功”处链接到奖励表现，并在末尾汇总相关的表现；多个界面共用同一种奖励反馈时，都引用同一份表现正文，各自只写自己的接入方式。角色死亡这类不属于界面的表现，从 GDD 和表现总览进入。实现任务负责同步采用的方案、实现文件和使用位置，验收结果仍链接到原有的验收记录，详见[专业来源与资源](../specialist-work-and-records/specialist-work.md#用一次游戏表现连接设计与实现)。

架构文档描述项目当前的真实结构，Feature 设计稿描述这一次的改变；两者都不复制游戏规则，也不另立验收标准。小项目靠现有模块说明和任务记录已经能看清结构时，不需要额外的架构地图，见[局部设计与当前架构](../specialist-work-and-records/knowledge-and-records.md#局部设计与当前架构)。

## 4. 按职责判断，按需要组织实现

逻辑与表现可以放在同一个业务模块里，例如 `game/shop/`，专用的脚本、场景和资源放在一起。职责要看实际作用，而不是看节点类型、场景或文件扩展名：碰撞判定可能参与游戏规则，一个场景也可能同时包含状态处理和视觉节点。能独立计算的规则可以单独组织；依赖引擎行为的逻辑照常使用 Godot，不要求所有逻辑都脱离引擎。

“编排”属于哪一层，要看编排的是什么：推进回合、结算购买属于游戏逻辑；安排图标、提示和声音的先后属于表现；由谁创建双方、连接信号、处理退出和释放，属于组装关系，按实际复杂度在现有结构里说明，不需要固定增加一层协调对象。

描述一项任务时，可以说它主要涉及哪一层：只换奖励动画主要涉及表现，只改价格计算主要涉及逻辑，新增一个完整的购买流程则两者都涉及。这只是帮助理解范围，任务本身仍按普通 Feature、实验或工程任务处理，不会产生新的任务类型或 Skill，也不要求先做完全部逻辑。新界面需要在游戏里定画面时，顺序是：先做最小的真实骨架，再在调试台定画面，最后补完整逻辑。例如先做商店的真实余额和一次购买的状态变化，外观用占位；再在调试台比较购买反馈的候选并采纳；补完价格规则后，还要验证真实的购买结果能否正确触发反馈。顺序的规则见[界面的开发顺序](../../../project-source/methodology/13-debug-console-and-validation.md#界面的开发顺序)。

Agent 必须守住的是状态归属、有效结果和文档一致性。至于选用哪些节点、怎样划分代码、用什么方式通信、用 Shader、粒子还是 Tween 实现，由当前需求、已有结构和验证结果决定。本页的例子只用来说明判断方法，不要求每个功能照搬同样的文件、类或目录。

验证也按要求来选：购买规则可以用自动测试检查成功、余额不足和重复点击等情况；接入部分检查真实结果是否正确传给界面、重新打开界面时是否显示当前状态；动画、声音和手感则通过人工验收确认。各类证据能证明什么，见[命令与验证证据](../methods-and-tools/commands-and-evidence.md#每种结果能证明什么)。
