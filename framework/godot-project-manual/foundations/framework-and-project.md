# 框架、创建器与项目边界

[Godot 项目手册](../README.md)

框架保存可以复制的 Godot 项目材料。用创建器生成项目后，项目独立拥有自己的代码、配置、文档、Git 历史和开发记录；之后修改框架，不会影响已经创建的项目。

## 框架和项目各管什么

| 位置 | 内容 | 在这里做什么 |
| --- | --- | --- |
| 框架仓库（根目录、`framework/`、`.agents/skills/`） | 维护约定、创建器、手册、提示词库、回归夹具和框架自用 Skill，目录见[框架入口](../../README.md#目录与职责) | 维护框架；这里不是游戏开发目录，内容也不复制给项目 |
| `project-source/` | 待复制的代码、插件、默认文件、Skill、角色配置与方法规范 | 只作为源材料编辑；不在这里启动游戏开发流程或 Godot |
| 生成的项目 | 项目自己的 `AGENTS.md`、`.agents/skills/`、`yaya/methodology/` 和工具 | 在这里开发游戏；它不读取框架状态，也不与框架同步 |

新项目从源材料中得到这些起点：最小入口 `main/main.tscn`、示例工作台、空的 Feature 记录，以及只有用途说明的 `docs/gdd/`。这些只是起点：环境还没配置，游戏设计也是空的。在项目里用 `design-gdd` 形成设计；依赖设计的工作需要满足什么前提，见[GDD 是项目开发的前提](../requirements-and-tasks/requirements-and-planning.md#gdd-是项目开发的前提)。

手册和提示词库不复制到项目。项目里的 advisor 通过固定的绝对路径直接读取本机的 Godot 开发提示词库，结合项目现状选择场景并起草指令。

## 创建器用法

在框架根目录，用已确认的 Python 3.12+ 运行：

```powershell
python -B framework/project-creation/tools/create_project.py --output D:\Games\MyGodotGame
```

- **参数**：`--output` 是目标项目目录；`-B` 让 Python 不生成字节码缓存。
- **前提**：需要可用的 Git 和已配置的提交身份。
- **做什么**：按[复制清单](../../project-creation/project-files.json)复制和重命名文件，然后建立独立的 Git 仓库并创建本地初始提交。
- **不做什么**：不安装依赖、不运行环境检查或 Godot、不生成需求、不运行测试、不配置远程或推送。
- **成功消息**：显示的复制数量是清单条目数，不是实际文件数。

创建器的完整契约：

| 方面 | 规则 |
| --- | --- |
| 目标路径 | 应传入框架之外的绝对路径（相对路径会按当前目录解析）；完整路径不能含中文或空白，也不能是框架目录的上级 |
| 目标内容 | 目标只能不存在或为空；已有文件或非空目录会被拒绝。创建器不检查目标是否位于其他 Git 仓库内，不要把项目建在别的仓库里 |
| 复制映射 | 清单中 `source` 相对框架根目录，`target` 相对目标目录；文件原样复制，不替换模板变量或机器路径 |
| 符号链接 | 待复制的路径必须是普通文件或目录；符号链接和 Windows junction 在预检时拒绝，防止借链接复制其他位置的内容 |
| 缓存文件 | 复制目录时跳过 `__pycache__/`、`.pytest_cache/` 及 `.pyc`、`.pyo`；复制范围不受 `.gitignore` 影响，源码、素材、`.uid` 和 `.import` 都保留 |
| 冲突检查 | 写入前展开全部清单项；目录可以合并，同一目标文件重复或文件与目录冲突时拒绝 |
| 失败处理 | 预检失败时不复制任何文件；复制或 Git 步骤失败可能留下部分内容，创建器不会删除、回滚或重试 |

参数与拒绝条件以[创建器源码](../../project-creation/tools/create_project.py)为准。项目名称、机器路径和文档语言在生成后的项目里配置。

## 环境就绪的含义

默认配置里的工具路径只是候选值，要在项目里确认。环境检查器的普通模式和 `--require-ready` 各检查什么、为什么 Python 版本要单独确认，见[配置参考的检查能力边界](configuration.md#检查能力边界)。

新项目要依次经过三步，每一步都是单独的证据：

1. **首次资源与全局类扫描**：没有完成时，CLI 会报告缺少 `GdUnitTestCIRunner` 或测试基类。这表示测试还没执行，不是业务断言失败。
2. **命令行测试**。
3. **启动最小入口场景**。

之后的日常任务复用已经可用的环境，不需要每次重新导入整个项目。

初始化结果记录在项目的 `reports/initialization.md`，Progress 需要时引用它。环境变化后只追加真实的新结果，不把配置字段或旧的成功记录写成当前状态。注意 `reports/` 默认被 Git 忽略，提交代码不会把这些报告带到其他位置。

## 已有项目采用框架

有两种方式：

- **复制迁移**：建立一个新的目标项目，原项目和框架都保持只读。
  - **复制当前内容**：包括未提交、未跟踪和必要的已忽略文件，以及删除状态；不能只复制 HEAD。
  - **Git 历史**：默认保留当前分支可达的历史，使用独立仓库；不复制远程、hooks、worktree 关系或指回原项目的链接。用户明确选择从新历史开始时，要说明旧历史因此无法追溯。
- **原地采用**：在指定的现有项目中合并框架材料。

两种方式都要区分纯框架文件、业务文件和两者混合的配置：

- **保留**：业务代码、素材、UID、导入设置、许可证、Feature 身份与依赖，以及真实的完成历史。
- **按实际意图合并**：机器路径、主场景和定制过的配置。
- **不能覆盖业务记录**：空白的默认 Feature 记录不能用来替换已有的业务记录。

迁移报告可以放在 `reports/maintenance/framework-migration/migration.md`。已有文件没有依据时不覆盖。历史测试只证明历史版本；无法恢复的旧决定、基线或原件保持“未知”，不能补造过去的审批、TDD、验收或完成时间。替换框架和交付业务功能是两件不同的事，框架也不提供持续升级。
