# 提示词与场景准则

[职责设计准则](README.md)

## 一条提示词对应一篇场景

- **一一对应**：每条提示词只对应一篇场景页，每篇场景页只有一条专用提示词。两者围绕同一个入口、处理目标、执行范围和可验证的出口。
- **各写各的正文**：不同场景要有各自的正文，不能复制一段通用的路由正文、只换个名称。
- **用途重复就合并**：用途相同的两条合并成一个场景和一个入口。
- **入口按用户能否辨认划分**：入口是用户在提示词库里能凭自己掌握的情况选中的条目。区分条件只有 Agent 查得到时（例如 Feature 是否已正式交付、测试证据为什么失效、当前是不是新对话），合并为一个入口，由 Agent 读取记录或状态后分流到原有流程；各流程的区分条件和处理差异都写进这一条提示词和场景页，不删除流程。用户能辨认哪些情况，按[入口的情境分层](#入口的情境分层)判断。

## 入口的情境分层

两份提示词库的分类会原样成为用户挑选提示词的分组，用户凭“我现在是什么情况”找入口。用户常常不经过 advisor，直接从快捷浮窗挑提示词，所以分类名、提示词名称和顺序都是用户的查找路径；改动它们等于改用户界面，要按用户能否找到入口来评估。本节规定怎样判断一条提示词属于哪种情况，用于新增、修改、合并提示词和调整分类。情境只是判断工具，不写进 JSON，也不增加分类层级。

### 四层结构

最上层是一个嵌套循环：定目标 → 定计划 → 执行 → 看结果 → 评估，评估后回到目标或计划；一次任务内部、几次任务之间都按这个循环推进。依据是 Norman 的行动七阶段和 Hacker 的行动调节理论（目标—计划—执行—反馈，循环可以嵌套）。循环之下分四层：

| 层 | 回答的问题 | 谁来判断 | 例子 |
| --- | --- | --- | --- |
| 第 1 层：情境 | 我现在处在什么情况 | 用户 | R5 看到出错或不对 |
| 第 2 层：关键判断 | 这个情况下，哪几个判断决定接下来走哪条路 | 用户和 Agent 都能用；只有 Agent 查得到的判断不用来区分入口 | 能指出具体错处吗 |
| 第 3 层：对象 | 要处理的是什么东西 | 用户 | GDD、Feature、素材、规则、做事方法 |
| 第 4 层：提示词 | 具体用哪一条 | 用户在提示词库里选 | 「发现 Bug，需要修复」 |

### 10 项情境

“入口条件”写用户自己能判断的情况，不写只有 Agent 查得到的状态。

| 编号 | 情境 | 入口条件 | 与相邻项的分界 |
| --- | --- | --- | --- |
| R0 | 回来了，或想知道现状和下一步 | 刚回来、刚换了对话，或做完一段后想知道做到哪、改了什么、还剩什么、下一步做什么；也包括继续一件记得的、没做完的事 | 手上有新成果或新结论 → R4；知道做什么、不知道怎么做 → R2；要离开 → R8 |
| R1 | 有新想法或外部参考，还没决定做不做 | 起点是一个想加或想借的东西（新能力、外部 Skill、教程、别的框架），还没决定做不做、做成什么样 | 已经决定做 → R2；起点是对现有东西不放心 → R7；已经决定怎样改已有的 → R6 |
| R2 | 已决定做什么，要定方案 | 能说出这次任务做完是什么样，但设计、方案或顺序还没定 | 方案已定 → R3；对象已经存在 → R6 |
| R3 | 方案已定，开始做 | 方案、规格、素材已经确定，现在要实施、接入、制作，或做出来后和用户一起调到满意 | 东西已经做完、要判断结果 → R4 |
| R4 | 刚做完或刚收到成果，要检查、验收、记录或收尾 | 手上有一份新成果（刚做的、Codex 或另一个对话交来的、外部审核意见、到货的素材）或一个新结论（验收通过或不通过），要判断、记录或交付 | 能指出具体错处 → R5；只问现状 → R0；对象是存量、不是刚做完的这一份 → R7 |
| R5 | 看到出错或不对 | 能指出一处具体的错：报错、测试失败、表现和说好的不同、前后矛盾、内容过时；或者看到不对，但说不清是做错了还是要求要改。不用判断它是刚做的还是以前完成的 | 还没看到具体错处 → R4 或 R7；已经决定改法、不认为是错 → R6；错在做事过程 → R9 |
| R6 | 已决定改动已有的要求或成果 | 要改的东西已经存在（GDD、规格、已完成的 Feature、素材、规则写法、工具版本、已验收的数值），而且已经决定改成什么样 | 不确定是不是错 → R5；还没决定 → R1；对象是新的 → R2 |
| R7 | 现有的东西没报错，但想查一查或觉得不好 | 指不出具体错处，只是觉得乱、长、难改、不放心，或想全面审一遍、想用一次试用检验流程 | 能指出错处 → R5；对象是刚做完的这一份 → R4；起点是新想法 → R1 |
| R8 | 要离开：暂停、切换或换对话 | 这次要停下、换一项工作，或把工作交给新对话 | 回来 → R0 |
| R9 | 想改进做事方法 | 问题或心得是关于“怎么做”的：太慢、反复返工、漏查、想复盘一段工作、想把重复做法固化成工具或规则 | 错在产物 → R5；对象是新的框架能力或游戏内容 → R1 |

### 一条消息命中多项时

一条消息常同时带着几种情境，例如“验收通过了，先暂停，修这次遇到的问题，还有个新想法”。按下面三步选出一个主格情境，消息里的其余事项照样由 Agent 排在后面做：

1. **先分 Project。** 游戏项目里的事用 `Godot 项目开发`，框架本身的事用 `Yaya 框架维护`；一条消息两边都有时拆成两条，各自再选。
2. **消息写明了先后时，选写明的第一件。** 例如“先回顾整轮试用，再结合这两个改”选 R9。
3. **否则按固定顺序选第一个命中的**：R5 → R4 → R8 → R6 → R3 → R2 → R1 → R7 → R9 → R0。

顺序的理由：先纠正事实（出错、还没写进记录的结论），因为后面的工作依赖它，而且只在对话里说过的结论容易丢；离开前先保存停点；然后按推进的先后；复盘和问下一步放在最后，因为它们要等前面的事落定。

### 每项情境的关键判断

第 2 层只列决定走向的判断，供用户选入口时自问，也供 Agent 收到消息后确认走向；判断不是固定流程。标“由 Agent 查记录”的判断不交给用户。

| 情境 | 决定走向的判断 |
| --- | --- |
| R0 | 要的是现状，还是现状加下一步建议？→ 要继续的那件事是否属于 Feature、是不是新对话，由 Agent 查记录 |
| R1 | 是一个问题没想清楚，还是多个问题互相牵连？→ 结论是采用、适配、不采用，还是缺证据？ |
| R2 | 方案缺的是设计、技术可行性，还是外部资料？→ 先做的是哪一部分，后面哪些部分依赖它？ |
| R3 | 做出来就算完，还是要用户在调试台一起调到满意？→ 做完转到 R4 检查或验收 |
| R4 | 当前 Agent 自查就够，还是用户要求独立审核？→ 结论是通过还是不通过？验收不通过仍在 R4 记录 → 结论写在清单里还是对话里，由 Agent 查记录 |
| R5 | 能指出具体错处吗？说不清是错还是要求要改时，先分诊 → 影响当前工作吗？→ 先停下修，还是先记下来接着做？→ 出错内容已交付或已验收时走哪条修复路线，由 Agent 查记录分流，不由用户选入口 |
| R6 | 先改哪份来源（GDD、规格、规则）？→ 受影响的 Feature 按各自状态怎样同步，由 Agent 查记录 |
| R7 | 查一个模块或专题，还是整体？→ 发现具体错处后转到 R5 |
| R8 | 停下后在同一个对话回来、切换到另一项，还是交给新对话？→ 当前工作是否属于 Feature，由 Agent 查记录 |
| R9 | 是复盘已经发生的（返工原因、阶段经验），还是为以后设计做法（处理方法、脚本、规则）？→ 经验已经确认了吗？未确认先复盘，确认后再写进知识或做成工具 |

### 不需要入口的消息

两类消息不选提示词，也不为它们补情境或提示词：

- **只问一个事实或概念**：例如“分发包里一共有多少个 Skill”“调试台的预设保存在哪里”，直接问 Agent。
- **与本框架无关的工具请求**：例如安装某个 Claude Code 插件、写一个会话结束提醒。

对话进行中的反馈（例如调参时说“粒子太少”）是对上一轮的回复，不是新入口，也不按情境重新选提示词。

### 维护提示词时怎样使用

- **定主格情境**：新增或修改提示词时，按它的「背景与入口条件」选一个情境，看的是用户此刻处在什么情况，不看提示词内部会走到哪一步。
- **同一格有多条时检查能否合并**：同一情境、同一对象下出现两条以上提示词时，检查用户能否只凭自己的情况选中其中一条。只有 Agent 查得到区分条件时，按[一条提示词对应一篇场景](#一条提示词对应一篇场景)中的「入口按用户能否辨认划分」合并为一条，由 Agent 分流。
- **新增前先看空格**：要新增提示词时，先确认它落在哪个情境与对象的组合上。这个组合已有入口时，修改已有入口的名称或入口条件，不新增；这个组合为空时，再确认用户在这个情境下确实会处理这个对象，而且没有别的入口承接。
- **名称写出入口条件**：提示词名称让用户凭自己的情况看出该不该选，写法见场景速查手册的编写与维护中的[标题与措辞](../../prompt-scenarios/scenarios/README.md#标题与措辞)。

## 提示词库的结构

提示词正文按用途分别维护在 [Godot 开发提示词库](../../prompt-scenarios/prompts/godot-development-prompts.json)和 [Yaya 框架维护提示词库](../../prompt-scenarios/prompts/yaya-maintenance-prompts.json)中，每条正文只有这一个来源。

- 每份文件的顶层是只含所属 Project 的数组，元素包含 `project` 和 `categories`：Project 下是分类，分类下是“提示词名称：正文”。
- 不增加表示状态的中间层分类，也不另建一份手工映射表。
- 框架维护场景归 `Yaya 框架维护`，游戏开发场景归 `Godot 项目开发`。归属决定了在哪个仓库执行，不改变授权边界；唯一的例外是创建空白项目，它归 `Godot 项目开发`，但在框架仓库运行创建器。

## 场景页的路径与命名

场景路径直接由 JSON 中的名称组成：

```text
framework/prompt-scenarios/scenarios/<Project>/<分类>/<提示词名称>.md
```

例如：

```text
Godot 项目开发/出了问题/发现 Bug，需要修复.md
Yaya 框架维护/出了问题/框架出现可复现问题，需要修复.md
```

- Project、分类和文件名都使用 JSON 中的准确文字，不另建英文别名或编号。
- 分类按情境（见[入口的情境分层](#入口的情境分层)）和对象混合组织，会改变处理方式的状态写进场景名称：
  - **转折情境单独成组，放在最前面**：出错（R5）、要求变了（R6 中改设计要求、规格、规则和同步 Feature 的部分）、回来与离开（R0、R8）。能指出具体错处的 R5 条目都放进出错组，报错对象明确也不例外。
  - **正常推进按对象成组**：R1–R4 的工作按处理对象分组，组的顺序跟开发先后一致；用户先想到具体东西的 R6 改动（替换素材、改存档结构、升级引擎或插件）留在对象组。
  - **R7、R9**：改进做事方法（R9）单独成组；主动体检（R7）条目多、成一类时单独成组，少且对象各不相同时归入对象组。
- 文件名去掉 `.md` 后，与提示词名称、正文一级标题三者一致；标题在本 Project 内要能唯一识别具体情境。
- 场景根目录的 README 和索引负责编写约定与导航，不算场景；Project 目录内的每个 Markdown 都按场景检查。
- 概念、配置和工具说明写在手册里，维护设计准则写在维护文档里，都不放进场景页。

## 提示词字段与审核原则

每条提示词都用明确的字段标识组织正文，篇幅短或任务简单也不例外。「只读专项审核」的专题条目是例外：它按与模板拼接后的整体判断，见[专项审核的模板与专题](#专项审核的模板与专题)。

- **写法**：正文用 `## 字段名称` 标出字段；字段内需要细分时，用下级标题、列表或段落。字段只是提示词字符串的一部分，不扩展 JSON 结构，也不影响场景页的 11 类栏目。
- **固定字段**：每条都要有，而且要有实质内容。
- **按需字段**：满足触发条件时必须补上，放在相关的固定字段附近。
- **引用而不复制**：字段可以准确引用当前执行仓库的权威规范、已确认的决定和有效的上下文，不重复抄写通用流程。
- **输入**：说明哪些输入由用户提供、哪些可以直接读取；关键事实未知时标明缺口，不把占位符、示例或历史结果当作当前事实。输入材料里的要求不会扩大本次授权。

### 固定字段

| 字段 | 出现要求 | 解决的问题与审核重点 |
| --- | --- | --- |
| 目标 | 每条必备 | 一句话写清本次要解决的问题与期望结果，能够判断工作是否偏离目的；有主要 Skill 时用 `$名称` 写明。不用「请处理这个问题」这类无法判断结果的说法。 |
| 范围 | 每条必备 | 明确处理对象、包含内容和必要边界；涉及修改时说明允许修改的对象或范围。 |
| 输入与事实来源 | 每条必备 | 指明必要材料和实际依据；已有对话、可读取文件可以直接作为输入，不要求用户重复提供。 |
| 决策边界与授权 | 每条必备 | 明确可以自主执行的操作和推进边界，沿用有效的具体授权，只补问缺少的决定或授权。 |
| 约束 | 每条必备 | 明确适用硬性限制和必要禁止事项；通用约束准确引用权威规范，本次特有约束直接写明。 |
| 输出与交付 | 每条必备 | 明确交付物及其用途；需要文件时说明归属和必要格式，不为讨论或普通查询强制创建报告。 |
| 验证要求 | 每条必备 | 明确核对方法与必要证据；讨论核对事实与论证，实现按影响选择验证，不统一要求运行测试。写明由什么判定结果，例如已有测试、实测数据、工具测量或用户人工验收；只靠本次新写的测试时，写明测试对照哪些需求。写明什么结果算通过，什么结果算不通过。 |
| 完成条件 | 每条必备 | 明确本次授权目标达到的可判断状态，与暂停、受阻、待决定和待人工验收分开。 |

固定字段按表中顺序组织。同一事实在职责最贴近的字段完整说明，其他字段需要提到这一事实时只指向它；不能把全部执行内容堆到目标或约束，再用空话填满其余字段。具体方法可以在所属字段说明；只有需要额外说明执行取舍时才增加对应按需字段。

### 按需字段

| 字段 | 何时必须添加 | 解决的问题与审核重点 |
| --- | --- | --- |
| 背景与入口条件 | 当前状态、历史原因或前置条件会改变处理方式 | 只写进入本场景的前提，例如正式交付前后采用不同处理路线；不复述「范围」或「决策边界与授权」。 |
| 来源与冲突处理 | 多个来源或要求可能冲突 | 区分当前事实与需求要求的行为，按有效需求、规范、实现和运行证据各自职责判断，不设置代码永远优先于需求的统一顺序。 |
| 停止与异常处理 | 有需要特别说明的停点、失败分支或不确定性 | 明确继续、停止、保留现场和恢复条件；局部步骤完成不撤销后续有效授权，当前明确暂停或只读限制也不能被旧授权覆盖。 |
| 工具与执行环境 | 工具、版本、平台或运行位置影响执行结果 | 给出实际环境要求、配置来源和必要工具限制，不从模板推断工具已安装或可用。 |
| 执行与变更原则 | 本次需要额外强调某种取舍策略 | 说明保持行为、先测量再优化等实际策略；通用原则引用原规范，不复制逐动作配方。 |
| 条件式参考资料 | 部分资料仅在特定条件成立时需要读取 | 写清何时读取何种资料，不强制通读无关文件或整个目录。 |
| 质量标准 | 可维护性、可读性、安全性等实际影响验收 | 写成可判断的表现，不只使用高质量、结构合理等笼统词语。 |
| 风险与回滚要求 | 可能造成数据损失、不可逆影响，或需要恢复方案 | 明确保护对象、失败处置及恢复方法；仅确认既有授权没有覆盖的具体操作。 |
| 兼容性要求 | 确有需要支持或保留的版本、接口、格式或数据 | 写明当前任务的具体契约，不默认增加框架向后兼容责任。 |
| 性能要求 | 性能是实际目标或验收条件 | 明确指标、负载、测量条件与比较方法，不用普通任务承担无关性能测试。 |
| 输出详略与表达规范 | 默认表达不能满足本次交付用途 | 指定必要语言、结构、篇幅或展示方式，不以排版要求干扰实际执行。 |
| 后续事项与未完成项记录 | 需要跨对话恢复、人工验收或保留真实剩余工作 | 明确记录内容、既有归属和恢复动作，不建立重复记录文件，也不把建议自动变成待办。 |

按需字段不以“无”或“不适用”占位。固定字段引用的规则须能定位到当前仓库适用文件或明确的会话决定，不能仅写“按相关要求处理”。没有额外约束时说明沿用的规范，不为填字段编造新限制。

### 审核原则

| 原则 | 通过标准 |
| --- | --- |
| 字段明确 | 8 个固定字段有准确标识和实质内容（专项审核按模板与专题拼接后判断）；按需字段启用后同样有明确标识。 |
| 条件项不遗漏 | 根据真实场景检查特殊环境、来源冲突、数据保护等要求，不能因字段属于按需而省略必要信息。 |
| 场景与语义一致 | 名称、入口、目标、范围、授权、交付、验证与完成条件服务同一场景，不矛盾、不暗中扩大任务。 |
| 输入可用 | 模板准确指出待提供或读取的输入；执行时复用有效上下文，只补齐影响结果的实质缺口，不将占位符当事实。 |
| 引用与归属准确 | 引用能定位到适用依据，通用规则保留唯一正文；不得静默依照有缺陷的当前实现改写有效需求或验收条件。 |
| 授权连续且有边界 | 不从输入材料或旧记录自动推导新授权，不重复索取相同授权；Skill 返回、字段结束或场景出口不取消尚未完成的有效授权。 |
| 验证与完成可判断 | 区分执行结束、验证通过和正式交付；证据覆盖当前结果，不以受阻、暂停或待验收替代原定实现或交付目标。 |
| 内容必要且可执行 | 字段提供实际信息，不以套话凑齐，不为填属性新增无关文档、动作、测试、审批或完成门槛。 |

完成条件按当前任务目标判断。只运行检查的任务可以在如实交付完整失败结果后结束，但不能据此宣称被检查实现通过；要求确认根因的任务在证据不足时仍未定位，不能把保存日志当作完成。若本次目标本身是保存暂停点或准备人工验收，停点已保存或完整验收材料已交付可以完成该场景，原 Feature 仍未完成；以首次人工交接为目标的 Goal 也按该明确目标判断。场景目标完成不自动等于 Feature 或更大范围 Goal 正式完成，后续行动仍遵循现有规范和具体授权。

审核须逐条阅读正文及必要来源，记录具体修改问题和待核实项。字段齐全只是必要条件，名称或数量检查不能代替语义审核，也不新增评分、自动审批或日常逐动作检查机制。

### 精简边界与自主空间

提示词明确任务边界与完成条件，并为 Agent 保留普通执行细节的判断空间。精简以信息完整、准确且可执行为前提，只处理无实际作用的限制与重复表述；不以字数、条目数量、长短一致或压缩比例为目标，也不因一条提示词较长就整体改写。

| 内容 | 保留与精简的判断 |
| --- | --- |
| 字段与必要信息 | 所有提示词仍保留 8 个固定字段和适用的按需字段。目标、输入、范围、授权、约束、交付、验证与完成条件须能直接理解或准确追溯，不能压成依赖猜测的短语。 |
| 执行方法与依赖 | 普通实现细节允许 Agent 按事实选择；已有规范负责的通用流程准确引用。影响正确性的先后依赖、工具契约和本次特有步骤须保留；任务本身用于验证流程时，实际经过的阶段及证据也是必要交付。 |
| 报告与交付格式 | 提示词的固定字段不等于报告必须使用固定章节。报告完整覆盖所需信息，章节、顺序和展开程度可以按内容组织；用户明确指定，或确实服务复用、对照、交接、工具处理的结构仍保留，不一律取消表格、编号或模板。 |
| 同义内容与提醒 | 同一规则在所属字段完整说明，其余位置按需概括或引用。帮助恢复上下文、避免遗漏的短提醒，以及完成条件对关键结果的概括可以保留；只合并没有新增作用的复述。 |
| 保护、异常与验收 | 数据与原件保护、停止及恢复条件、实际人工接受、验证证据和完成边界不得因篇幅删弱。固定数量或顺序若定义真实任务范围或工具行为，不能仅因形式固定就判为过度要求。 |
| 修改依据与核对 | 先指出具体片段的重复、无用途限制或与权威规范的重叠，再选择局部改写。改后核对适用条件、必要信息、依赖和授权均有明确落点，验证义务与完成含义未变；没有充分依据的部分保留，不顺带扩大精简范围。 |

## 专项审核的模板与专题

`Yaya 框架维护 → 只读专项审核` 分类是唯一的拼接式入口：「专项审核通用模板」保存全部专项共用的固定字段（授权、判定标准、报告结构、完成与停止条件），各专题条目只保存「审核问题、范围、必读来源、检查要点、不算问题」等专题内容，使用时粘贴到模板末尾的「本次专题」下。

- 字段要求按拼接后的整体判断；专题条目本身不重复模板字段。
- 只影响一个专题的要求写进该专题；影响全部专题的才改模板。专题需要不同的报告结构时，在专题中写「输出要求」，模板约定以专题为准。
- 模板也有同名场景页，说明拼接方法；其他分类不使用拼接方式。

## 路径校验的职责

[提示词与场景路径检查](../../prompt-scenarios/tools/README.md#提示词与场景路径检查)只比较 JSON 推出的路径与实际场景文件，不读场景正文、不维护缓存或第二份登记。路径一致只证明目录对应，一级标题和正文是否符合单一场景由作者自查。
