# Skill 与脚本

[职责设计准则](README.md)

## Skill 的评价维度

| 维度 | 检查问题 | 不能直接推导拆分的情况 |
| --- | --- | --- |
| 用户意图 | 用户是否实际要求不同结果，能否分别提出并独立完成？ | 同一需求有不同说法 |
| 触发场景 | 不同入口是否需要不同前提、方法和结束位置？是否在一个入口中重新选择不同任务？ | 多个触发词指向同一项工作 |
| 输出结果 | 是否存在可独立交付、独立验收的成果或互不相干的完成条件？ | 同一成果有多条验收条件、支持文件或多种表示格式 |
| 变化原因 | 某部分是否因独立需求变化，并持续牵动无关部分？ | 同一目标需要同步调整几个步骤 |
| 外部依赖 | 某职责是否迫使其他职责承担不需要的系统、权限或配置？ | 同一个目标确实需要多个工具 |
| 状态生命周期 | 是否存在独立开始、暂停、恢复和结束的工作，其状态与清理是否互相干扰？ | 一条完整流程包含多个阶段 |
| 授权与副作用 | 只读分析、规格写入和实现修改等边界是否清楚？调用前能否预知执行范围？ | 已授权的一项任务修改多个相关文件 |
| 拆分收益与衔接成本 | 拆开是否更易选择、理解和验证？会不会复制规则、反复交接或重新索取既有授权？ | 文件更短或 Skill 数量更多 |

### 能力划分

Skill 按“可复用的能力”和“能独立交付的结果”组织，不按 Stage、步骤、文件数量或场景名称机械拆分。

- 一个职责明确的 Skill 可以编排同一目标所需的多个步骤，并按需调用其他方法；具体方法和权威规则仍只有一个来源。
- 阶段之间有必要的依赖，不等于职责混杂。
- 多个场景可以共用同一个 Skill，同一项能力也可以在不同阶段使用。场景和提示词一一对应，但场景和 Skill 不需要一一对应。

正式审核与实现的分工见[正式审核的独立性](reviews-and-reports.md#正式审核的独立性)。

### 入口、正文与完成边界

| 原则 | 必须落实的要求 |
| --- | --- |
| 轻量入口 | Skill 可以只承担常用入口，但须说明何时使用、必要输入、允许动作、交付结果及何种条件下读取哪份正文；不要求复制完整流程，也不能只留下无条件的“读某文档”。 |
| 唯一正文与必要提醒 | 同一作用域内的同一规则只维护一份完整正文，其他位置保留条件明确的引用及必要防漏提醒。提醒频繁出现本身不是删除理由；框架与生成项目的不同职责、部署范围分别判断。 |
| 覆盖真实调用路径 | 条件引用须能从实际会进入的路径触发，包括直接调用、续接与跳过上游准备的情况。文件存在或创建入口有提醒，不能证明后续直接运行的入口已读到约束。 |
| 按需增加能力 | 高频使用是发现候选入口的线索，仍须比较复用、补引用、合并与新增的收益；不因为重复出现就新建 Skill，也不为每条场景复制一个入口。 |
| 授权连续而不扩张 | 既有具体授权跨 Skill 和阶段沿用，方法返回不取消尚未完成的获准工作；只读、只讨论、暂停、人工验收和提交条件仍有效。审核结论不授权修复，已获准的修复由原负责人继续，不在只读审核实例内执行。 |
| 不制造附加流程 | 新增入口不自动新增 Stage、固定全套调用、批准轮次、报告、记录文件或监督脚本；复用现有记录和完成契约。 |
| 验证证据分层 | 分别报告格式与链接检查、静态语义和情境推演、实际加载后的有限试用、客户端发现/触发、真实工具运行与人工验收。按变化需要选择验证，不要求每次全套执行，也不把其中一层的通过写成另一层已通过。 |

审核 Skill 时：

- 读实际正文，以及影响职责判断的 references、调用方和权威规范；不能只看名称、description 或触发词。
- 横向检查不同 Skill 是否重复维护同一事实、输出或规则。
- Skill 内部有几条独立路径时，分别评价，不用一条笼统的结论覆盖全部。

## 脚本的评价维度

先按公开命令或调用接口评价，再决定是否拆文件。一个文件包含多个子命令时分别检查每个命令；没有命令行的 Godot 工具模块对应检查公开方法、返回值、错误信号与对象生命周期。入口、实现模块和共享函数可以采用不同的拆分粒度。

| 维度 | 检查问题 | 需要调整的典型信号 |
| --- | --- | --- |
| 调用目标与参数 | 一次调用完成什么？参数是否围绕同一操作？ | 互斥参数实际在几套独立任务之间选择 |
| 输出与成功条件 | 返回值、退出码和输出是否表达同一个操作结果？ | 当前操作成功，却因另一任务未完成而报失败 |
| 权限与副作用 | 调用者能否预知读写、删除、进程启动和外部影响？ | 查询入口隐含写入，普通操作要求无关高权限 |
| 失败与重试 | 失败后重做什么？哪些修改必须共同成功？部分结果如何保留？ | 重试会重复另一项写入，部分成功无法解释 |
| 资源与生命周期 | 进程、连接、临时文件和缓存由谁创建、持有、停止和清理？ | 独立任务共享模糊状态、互相清理，或拆分后丢失资源所有者 |
| 依赖与运行环境 | 每条路径是否只需适用依赖？能否按需加载？ | 简单查询被不相关的引擎或处理依赖阻塞 |
| 变化原因与验证 | 修改一项能力是否需要理解并验证与它无关的能力？ | 无关需求持续修改同一部分，相关行为难以独立验证 |
| 拆分成本与共享实现 | 拆开是否减少耦合？稳定的解析和规则能否共享？ | 拆分复制逻辑、增加无意义的中间文件或调用层 |

命令必须有明确目标、允许的副作用和成功条件。相关命令可以放在同一脚本，共用解析或校验函数；不因被多个场景调用而复制脚本。参数变化、输出格式变化、多个依赖或有意的原子操作都不是单独拆分依据。

例如，查看记录的成功条件围绕是否成功读取并显示；判断全部完成条件由明确的检查入口承担。显示业务尚未完成的信息与读取失败必须可区分。创建项目包含检查目标、复制文件和建立 Git 仓库与初始提交，这些步骤共同交付一个独立项目，可以保留为一个命令。审核具体实现时仍需核对既有调用方契约和失败行为，不因例子预先裁定修改方案。

## 何时把临时脚本做成工具

确定性的工作交给脚本，需要理解和取舍的工作留给 Agent。工作中临时写的脚本，按下面的条件决定是否保存为正式工具：

- **触发**：临时脚本放在 `tmp/<任务>/`。写临时脚本时，判断这类操作以后是否还会用到；会再用到时按下面的条件判断是否保存，不每次重写一份。不靠数“第几次出现”触发，因为临时目录会清理，换对话后也看不到之前的脚本。
- **保存条件**：检查有明确的对错、操作有明确的成功条件，输入格式稳定，做错的代价高或人工核对容易漏，三条同时满足才保存。例如提示词正文里的路径和标题引用每次修改都要核对，人工多次漏过，已并入[检查链接与锚点](../tools/README.md#检查链接与锚点)的脚本。
- **先改输入**：需要理解才能判断的事，例如一句话指的是哪个章节，不写靠猜的脚本；改规则，让输入变成机器能检查的形式，例如[触发与按需阅读](instruction-files.md#触发与按需阅读)中的“引用用带锚点的链接”。
- **不保存的**：一次性的探索、验证失败的原型，以及只为绕开 Agent 自身编辑限制的辅助脚本，留在临时目录。
- **先征求同意**：保存超出当前任务的范围。满足条件时先不保存，在完成汇报的待确认中写明脚本做什么、计划放置的路径，以及要同时修改的 README 和索引，用户同意后再保存。用户说某类脚本不要再提时，把这一类写进上一条“不保存的”。
- **保存后**：按[目录组织](document-responsibilities.md#目录组织)放进所属对象的 `tools/`，同目录 README 写参数和退出码，在框架入口的[维护命令](../../README.md#维护命令)表加一行，并补回归测试；之后随路径和字段变化一起维护。
