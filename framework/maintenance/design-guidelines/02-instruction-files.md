# 规则与提示词文件

[职责设计准则](README.md)

维护 `AGENTS.md`、Skill、任务提示词和条件引用时，先读当前正文和必要的调用方，再按实际变化逐项核对下面的内容。写法可以参考 [OpenAI 的 Astra 指令设计建议](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra)，但以本仓库已确认的边界为准。

## 内容放在哪里

- **AGENTS.md**：只写代码和配置推断不出来的约束。
- **任务提示词**：补充本次的目标、输入和特有约束。
- **规范**：定义、条件和例外集中写在所属规范；流程和测试规则以权威规范为唯一正文。
- **其他入口**：只保留准确的引用和必要的提醒。已由 README 或工具配置负责的内容不重复展开，意思相同的规则合并。
- **只供部分任务或部分步骤使用的资料**：按条件引用。普通的参考资料不必包装成 Skill。

## 触发与按需阅读

- **description**：简短写出职责和具体适用的任务；不堆砌关键词，不用宽泛的领域词强行触发。有职责相近、可能被同一句请求选中的 Skill 时，双方的 description 都写明排除项并指向对方：Agent 选择 Skill 时只看得到 description，正文里的区分要等选中之后才起作用。
- **条件引用**：写明在什么任务或条件下读取哪份资料。核对直接调用、续接和跳过上游准备这几种进入方式，都能读到必要的约束。
- **引用用带锚点的链接**：引用其他文档的章节时，写成带锚点的 Markdown 链接，例如 `[本地提交](../../AGENTS.md#本地提交)`，链接文字用目标章节的实际标题，具体写法和可以接受的变体见框架文档写作指南的[表达与排版](../../../.agents/skills/technical-documentation-writing-yaya/references/writing-guide.md#表达与排版)。按字面执行的模型会照着标题去找，写一个意思相近的叫法，它就找不到；写成链接后，[检查链接与锚点](../tools/README.md#检查链接与锚点)的脚本会在标题改名或写错时直接报失效。分发源中的文件按生成项目的目录写相对路径。已有的纯文本引用不必一次改完，编辑到时改成链接。
- **引用只保留一层**：`SKILL.md` 直接列出需要读的参考文件和规范章节，不靠参考文件再层层转引；必需的约束不放在两层以外。超过 100 行的参考文件，开头放目录或按任务阅读的指引：Agent 读长文件时可能只读开头一部分。
- **不设阅读前置**：复用仍有效的上下文，不把固定的一组文档、通读某个目录或全仓地图设为每轮任务的前提。
- **路径**：框架和生成项目各自使用自己有效的路径。

## 流程粒度

写清必要的依赖关系，把普通实现细节留给 Agent 判断。不照搬逐个动作的配方，不规定没有依据的提问轮数、产物数量或逐阶段汇报。

按风险决定写到多细，同一个 Skill 里可以混用：

- **开放的判断**：给原则和理由，让 Agent 结合实际取舍。
- **不可逆或顺序敏感的步骤**：例如 Git 写操作、合并、删除和覆盖，给出一个最小可行的命令和执行前后的检查方式。只写“不要依赖某做法”而不给可行做法，按字面执行的模型容易直接执行出错。
- **要运行工具时**：点名入口脚本，例如“测试用 `run-gdunit-tests.py`”，参数和退出码链接到工具的 README，不在 Skill 里复制命令正文。
- **输入与推断**：写明开始前必须有哪些输入，缺了是追问还是停下；写明哪些内容可以推断，哪些必须标为不明确。例如验收结果不能推断，只能由用户回报。
- **交给下游的输出**：输出要交给下一个 Skill 或脚本读取时，固定字段和格式；只给人看的报告按内容组织，不强制固定章节。
- **失败时默认做法会出错的步骤**：写明正确做法。例如测试失败时不改断言来求通过；查不到资料时写“未找到”，不编造。Agent 默认就能处理对的失败不写；本机已满足的环境前提（例如已安装的 Node、Godot），也不写缺失时的处理，依据见框架 Lessons 的[环境前提按本机实测，不写降级分支](../../lessons.md#环境前提按本机实测不写降级分支)。超出职责的请求转给哪个 Skill，由 description 的排除项负责，不在正文重复。

## 授权与完成

- **完成标准**：按本次授权定义，覆盖适用的实现、必要的验证和交付。
- **授权延续**：已有的具体授权按[授权在后续对话中的延续](../maintenance-and-sync.md#授权在后续对话中的延续)，在各 Skill、各阶段和之后的口语请求中一直有效。某个 Skill 结束或某一步完成，不代表已授权的工作结束了。
- **何时停止**：授权范围已完成、必要的前提受阻、缺少决定、范围发生实质变化，或用户要求暂停。
- **仍有效的条件**：未被用户后续明确要求替代的只读、只讨论、暂停、人工验收和提交条件继续有效。替代关系按[授权在后续对话中的延续](../maintenance-and-sync.md#授权在后续对话中的延续)判断。静态检查和实现授权都不能代替实际运行或人工验收。
- **阻塞要说清**：指令确实导致暂停或改变方向时，指出具体的文件、条款和当前缺口。先核对适用范围和已有授权，不因为猜测的风险而追加确认。

## Skill 的格式与元数据

- `SKILL.md` 必须有 `name` 和 `description`。界面显示的名称和短描述保存在 `agents/openai.yaml` 的 `interface` 中，它们不能代替正文。
- **名称前缀**：前缀只在属于用途时保留，例如 `review-art` 和 `design-art-direction` 去掉前缀就分不清；不为按类别分组而加前缀。分发 Skill 都在游戏项目里使用，`project-` 这类前缀说明不了用途。
- **名称后缀**：`name` 直接写出用途，例如 `in-game-tuning`。只在会和同一会话里可见的其他 Skill 重名时加后缀：分发 Skill 和用户全局 `~/.agents/skills/` 中的 Skill 同名时加 `-godot`，例如 `technical-documentation-writing-godot`；框架自用 Skill 加 `-yaya`。常和游戏项目一起加入会话的分析工具项目（GVA、GAA）已给自己的 Skill 加了 `-gva`、`-gaa`，不需要分发 Skill 避让。没有重名的不加后缀。
- 维护时保留没有获准调整的调用策略和无关配置。
- 格式或产品行为发生变化时，按当前的 Codex 官方资料和可用的 `skill-creator` 核对字段与格式；普通改字不需要每次重新查证。
- 格式正确、路径有效、加载后的行为正确、客户端实际选中，是四件不同的事，分别验证。后两件按[Skill 与规则的行为演练](../validation/validation-scope.md#skill-与规则的行为演练)验证。

## 排版与持续调整

表达与排版遵循 [technical-documentation-writing-yaya](../../../.agents/skills/technical-documentation-writing-yaya/SKILL.md)。模型或工作方式变化后，按真实出现的误触发、冲突、等待和重复工作检查相关指令，不因为个别现象就叠加一条普遍规则。

框架的适用范围和提交规则沿用根 `AGENTS.md`，验证地点见[按修改选择验证范围](../validation/validation-scope.md#按修改选择验证范围)；具体的反馈、排错、方案判断和交接按本次任务和对应场景处理，不为通用的做事方法另建框架 Skill；复盘有固定的证据范围、归属判断和报告格式，由 [framework-retro-yaya](../../../.agents/skills/framework-retro-yaya/SKILL.md) 负责；设计经验引入有固定的取舍、归属表和出处记录，由 [design-knowledge-intake-yaya](../../../.agents/skills/design-knowledge-intake-yaya/SKILL.md) 负责。
