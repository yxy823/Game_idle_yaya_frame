# 审核与报告

[职责设计准则](README.md)

本页说明正式审核怎样保持独立、怎样判断和写结论，以及外部审核报告的核实和当次报告的保存。用户要求独立审核、转来外部审核报告，或要写审核报告时读。

## 正式审核的独立性

实现负责获准修改及必要作者自查；正式审核只读被审成果，交付问题、依据与结论，修复交回实现负责人。是否设置专用 Skill 取决于实际复用价值，不强制为实现和审核分别建立 Skill；两类任务直接引用所属规范，不复制两套评判正文。

用户要求正式独立审核时，由未参与被审成果创作的独立实例执行，核对实际上下文和权限；更换方法或 Skill 名称不能把作者自查变成独立审核。普通框架维护由作者自查，不自动追加独立审核。

用户指定由子智能体审核时，由子智能体独立形成结论，需要保存时由它把报告写入获准的路径；主 Agent 负责范围覆盖和结构核对，核对报告已保存，不改写报告内容，也不能把自己的复述称作独立审核。

## 外部审核报告的核实

收到外部审核报告或意见时，先核对当前文件和版本，逐条分别判断问题是否成立、改法是否合适；用户明确选择实施范围后才修改。

## 审核的判断方法

框架的整体静态审核和专项审核都按下面三条判断。[框架好像有问题，先判断从哪里查起](<../../prompt-scenarios/scenarios/Yaya 框架维护/只读专项审核/框架好像有问题，先判断从哪里查起.md>)只帮助选择入口，不做任务推演；冗余设计、脚本化审核等其他审核入口按各自提示词组织。只核对文件之间是否一致，查不出设计方向本身错了，也查不出只有运行时才出现的问题。交给用户判断的产出物形式不对（例如用文字线框图讨论布局比例），一致性检查同样查不出，由专题[只审核产出物能否支撑用户的判断](<../../prompt-scenarios/scenarios/Yaya 框架维护/只读专项审核/只审核产出物能否支撑用户的判断.md>)负责。

- **已确认的取舍也可以质疑**：AGENTS 与所属规范中已确认的取舍不是免审对象。质疑时必须用一个具体任务说明它在哪一步造成什么代价，例如要多读哪些文件、在哪一步要猜、写错哪个文件或要返工什么；只凭偏好的意见列为可选改进，不能推翻已确认的取舍。
- **带 2–3 个具体任务走一遍**：任务由用户指定；用户没指定时，审核者从两份预设提示词库中挑。不能只挑最简单的：至少一个跨 Stage，至少一个是“中途发现以前做完的东西有问题”，例如已交付的 Feature 要改需求，或采纳到游戏的值后来发现错了。对每个任务逐步写出：读哪个提示词或文档、调用哪个 Skill 或工具、写哪个文件或产出什么、在哪一步卡住或要猜。推演框架维护任务时没有 Stage，“至少一个跨 Stage”改为至少一个涉及多个维护对象的任务，例如一次修改同时涉及提示词、场景页和规范。任务推演是报告主体；按方面或专题要点的检查放在后面，补充任务没走到的部分。专题已给出推演情形时，这些情形计入任务数，不满足上面两个“至少”时再补；专题写明它的推演情形或推演方法可以替代这两个“至少”时，以专题为准。
- **新机制或新工具要实际试用**：被审范围包含还没实际用过的新机制或新工具时，静态审核的结论不能代替试用；只能运行才能确认的行为同样是运行证据缺口。审核本身仍只读，报告对每项缺口写明：用哪个任务、在哪个目标项目、被测文件是哪些、观察什么结果。目标项目没指定时写“待指定”；试用建议不授予执行权限，用户选定后按对应入口执行。试用之前不能写成可用或通过。按缺口选择现有入口，不转入明确排除这类缺口的入口：
  - 从已有 GDD 到 Product、Feature 交付的流程：[想用一个小任务实际验证框架流程](<../../prompt-scenarios/scenarios/Yaya 框架维护/整体体检与整理/想用一个小任务实际验证框架流程.md>)。它不覆盖创建器、GDD 初始化、续接和迁移。
  - 项目工具或测试运行方式的行为：[框架刚改完，在指定外部项目验证工具行为](<../../prompt-scenarios/scenarios/Yaya 框架维护/改完检查/框架刚改完，在指定外部项目验证工具行为.md>)。
  - 创建项目、配置环境与首次扫描、GDD 起草、续接等：用场景速查索引中[Godot 项目开发](../../prompt-scenarios/scenarios/scenario-index.md#godot-项目开发)下对应的场景，例如「准备开始新游戏，先创建空白项目」「第一次运行项目，Godot 还没有完成资源扫描」「只有游戏想法，先形成 GDD 草稿」「当前工作还没做完，准备换一个对话继续」。

## 审核覆盖与结论

全量审核先枚举真实对象，明确生产入口、共享模块、第三方和验证夹具的范围。每个范围内对象都须有结论；不能以抽样、目录清单、关键词命中或读取说明替代审核。引用材料按判断需要追查，不以未读取正文的对象计入已审核。静态审核与真实运行分别报告。

| 可用结论 | 含义 |
| --- | --- |
| 保留 | 职责一致，组织合理 |
| 收窄范围或改名 | 入口承诺或描述不清，未必需要拆实现 |
| 拆分入口 | 不同任务需要明确选择，底层实现仍可以共享 |
| 拆分 Skill 或实现模块 | 职责、依赖或生命周期能够独立成立 |
| 提取共享方法 | 多处重复同一规则或算法，保留一份实现 |
| 合并或删除 | 用途重复、过度拆分或失去必要性 |
| 证据不足 | 无法支持保留或调整，明确还需什么依据 |

每项结论说明实际职责、文件位置或可核实依据、判断理由、最小调整以及受影响调用方。简单保留项可以汇总成表；复杂问题单独展开。拆分建议说明各新职责的输入、输出与结束位置，并核对授权、状态、原子性、重试和清理责任是否丢失。

框架整体审核报告分别给出以下结论，详情引用同一问题，避免重复展开：

- **文档职责**：内容类型、作用域、固定位置、唯一正文及生产与使用契约。
- **文本编写**：标题、术语、内容层级、目录和正文归属。
- **Skill 职责**：意图、触发、输出、变化原因、依赖、生命周期及授权边界。
- **脚本职责**：公开命令或接口的目标、成功条件、副作用、失败重试、资源所有者及共享实现。
- **提示词与场景**：一个入口是否只对应一个同名场景，输入、目标、范围与出口是否一致。

每类写清实际覆盖、判断依据和最小建议；未发现问题、证据不足和未涉及分别说明。限定范围审核只评价相关对象，不借分类汇总扩大为无关全量审核。

## 当次报告的保存与清理

审核默认在对话中交付。明确要求保存或当前任务确实需要留存的报告，放在仓库根目录的 `tmp/reports/<任务>/`，可以按专题或检查轮次分层；写清被审版本、范围、执行者、实际证据和未验证项。报告中的建议不自动授予修改被审核实现的权限，旧报告也不证明当前版本通过。

当次用途结束后删除报告及失效导航。需要长期保留的结论写回职责所属正式文档，由 Git 保存历史；仍有待办时，只在[框架待办](../../todo.md)保留继续工作需要的事实与入口，不建立永久报告目录或报告清单。
