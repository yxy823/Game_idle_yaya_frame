# 文档职责、目录组织与文本编写

[职责设计准则](README.md)

## 文档职责与固定归属

目标是：只要知道内容类型、作用范围和状态，就能确定唯一的存放位置。Agent 按约定保存和引用，不必每次任务重新选择放在哪里。

- **约定写在哪里**：每类产物的内容职责和存放位置，写在该产物的所属规范中；本节只规定这些约定要满足什么要求，不另建一份全仓归属清单。
- **不随规模变化**：从游戏初期到持续扩展，使用同一套职责和目录约定，不为“简单游戏”另设存放方式。归属不随游戏规模、文档篇幅或复杂度改变，也不能写成让 Agent 多选一的描述。

| 设计要求 | 应明确的内容 |
| --- | --- |
| 固定存放位置 | 固定文件写出准确路径；Product、Feature、专题等多实例产物写出目录、命名模式及按对象确定实例的规则。只有目录名或“放到合适文档”不足以确定归属。 |
| 划清内容职责 | 说明该文档维护什么，以及易混淆内容归哪个现有所有者。定义、玩法规则、交付范围、实现决定、执行证据与当前状态分别按各自职责保存；同一主题出现在多处不直接等于职责重复。 |
| 分开创建条件与位置 | “有已确认内容时才创建”可以保留；一旦需要保存，位置就应确定。不得将按需创建解释成可以任选存放位置，也不为固定位置预建全部空文档。 |
| 明确分流条件 | 不同内容职责、作用域或状态确需不同位置时，写出可核实且互斥的场景条件、各自唯一位置与必要迁移关系。不使用“可放 A 或 B”“简单时放 A，复杂时另建 B”“由 Agent 按需选择”等存放规则，也不以复杂度阈值替代职责划分。 |
| 保持一个现行正文 | 使用方保留引用及必要的简短解释；导航、摘要、派生产物和注明版本的历史材料不成为另一份现行正文。迁移时同步生产方、使用方、模板与必要链接，移除获准范围内的重复正文。 |

遇到约定没有覆盖的新内容类型时：先在获准的设计工作中确定归属、更新所属规范，再让写入任务采用。已有规范之间冲突，或需要的变更超出当前授权时，明确列为待决定项，不能临时另存一份来掩盖缺口。具体怎么写由 Agent 判断，但放在哪里由框架设计决定。

例如，已确认的游戏术语固定由项目 `docs/terminology.md` 保存，GDD 保存玩法规则并引用定义；“这个术语暂时只用于一个主题”不改变位置。Feature 等按标识区分的产物可以有多个文件，但同一个 Feature 的同类内容仍按规范定位到同一处。

审核时，按内容类型追查“谁写入 → 权威正文在哪 → 谁使用”，用一个具体的写入场景判断位置是否唯一、职责是否重叠。报告问题时，列出互相竞争的位置、允许二选一的原文和实际后果。搜索到“可选”“或”只是线索，不代表都是缺陷。文档的入口与保留期限是否合理，另按它的使用和生命周期约定判断。

## 目录组织

维护侧目录的约束条文在根 AGENTS.md 的[目录与入口组织](../../../AGENTS.md#目录与入口组织)，本节说明怎样判断以及容易出错的做法。新增、移动或拆分文件时，按下面三个问题依次确定位置：

1. **这份材料讲的是什么对象？** 生成的 Godot 项目、提示词与场景、关系图、框架维护、项目创建还是测试。对象决定顶层目录。
2. **它在该对象里承担什么功能？** 说明正文、准则、验证、第三方记录、脚本、夹具等功能不同的文件分到各自子目录，即使目前只有一个文件；功能相同的文件放在一起。
3. **它是不是脚本或脚本说明？** 脚本放在所属对象的 `tools/`，用法写在同目录 README；框架入口只登记索引。

| 容易出现的做法 | 问题 | 应该怎样放 |
| --- | --- | --- |
| 建一个 `docs/` 收纳所有 Markdown | 按文件类型归堆，讲生成项目的手册和讲框架维护的文档混在一起，读者无法从目录判断内容属于谁 | 按对象分区：`godot-project-manual/`、`maintenance/` 等 |
| 把所有脚本集中到一个 `commands/`，再用一份 README 说明全部命令 | 脚本离开它处理的数据和文档，修改提示词工具要跨目录找；集中说明随脚本增多越来越长 | 脚本放在所属对象的 `tools/`，同目录 README 写用法，入口只做索引 |
| 脚本直接和 JSON、Markdown 平铺在同一目录 | 数据、文档与程序混在一起，难以分辨哪些是可执行的 | 即使只有一个脚本，也放进 `tools/` |
| 因为“只有一两个文件”就不建子目录，把不同功能的文件平铺 | 之后新增同类文件时没有现成位置，只能继续平铺或再整体搬迁 | 功能不同就建子目录，例如 `validation/`、`dependencies/` |
| 两个入口页各自导航同一批材料 | 同一导航维护两份，改一处漏一处 | 合并为一个入口，其余页面只链接它 |
| 夹具的放置与运行步骤写在远离夹具的维护文档里 | 运行夹具时要在两处来回对照，维护文档也被操作细节撑长 | 写在夹具所在目录的 README，维护文档只说明何时需要哪层验证 |

搬迁时追到全部读写方：脚本内的路径常量与仓库根层级、测试的加载方式、文档链接与锚点、提示词与场景中的路径文本、文档系统图的文件登记、`.gitignore` 与 `.editorconfig` 的路径规则。完成后用链接检查和仓库回归确认没有遗漏；文档图覆盖检查按[根约定](../../../AGENTS.md#修改时的联动检查)只在用户明确要求时运行。

## 文本编写的评价维度

审核 AGENTS、Skill、脚本说明、提示词和手册时，同时评价表达是否准确、容易查找和执行，不只检查路径或技术行为。

规则、Skill 与任务提示词文件的编写要求见[规则与提示词文件](instruction-files.md)，正式审核见[审核与报告](reviews-and-reports.md)。

已确认的框架说明文字，其表达与组织使用[框架文档编写 Skill](../../../.agents/skills/technical-documentation-writing-yaya/SKILL.md)；生成项目的写法由独立的 [Godot 文档编写 Skill](../../../project-source/skills/technical-documentation-writing-godot/SKILL.md) 负责。下表保留审核问题与框架特有要求。

| 维度 | 检查问题 |
| --- | --- |
| 标题与术语 | 标题能否独立说明对象和目标？框架专用词是否按[术语表](../../terminology.md)一致使用？是否用“正常”“成功”等含糊词代替可验证结果？ |
| 信息层级 | 并列事项是否按主题分项，先后步骤是否仍保留顺序？多专题文档是否有对应实体分类目录，而非索引分组、正文仍平铺？是否存在无用途的过深目录或空分类？ |
| 内容归属 | 概念、执行步骤、权威规则、工具契约、历史报告是否各有所属？同一事实是否被复制到多处？能否改为必要解释与来源链接？ |
| 执行清晰度 | 输入、前置、实际 Agent/Skill/命令、允许副作用与完成结果是否明确？是否把模板值、文件存在或旧日志当成当前通过？ |
| 简洁与必要性 | 能否删掉重复和无实际作用的指令而保留边界？是否用一行堆叠多个独立事项，或反过来将紧密相关短语过度分层？ |
| 重复提醒 | 同一句提醒（例如“X 不证明 Y”“授权会延续”）在多页反复出现时，逐处判断它在该位置是否真能防止误判：有作用的保留一句并链接通用规则的正文，没有作用的删除。出现次数本身不是删除理由，但通用规则要有一处完整正文 |
| 句子长度 | 一句话是否塞进了多个动作、条件和例外？超过约 100 字的说明句，通常应拆成列表或几句短句；命令行和路径除外 |

表达问题与职责问题分别判断：措辞不清可以只改文字；独立目标、权限或生命周期混杂则追查实际职责。不用统一字数、列表数量或固定目录深度代替判断。修改方案应先定位唯一正文，再同步必要引用，不靠增加同步程序补救重复来源。
