# 测试改动场景表

[框架维护](../README.md) · [框架验证范围](validation-scope.md)

本表按“谁、怎样、什么时候改了什么”列出项目里文件改动的全部组合，并写出当前的测试选择、完成证据和 Feature 流程对每种组合的实际处理。修改测试选择、完成证据或 Feature 执行流程时，逐行对照判断列，确认每一行仍然成立；结论变了就同步改表。

判断列描述 `project-source/` 中工具和规范的现行行为。选择规则的唯一正文在 08 号规范的[起点以来的改动](../../../project-source/methodology/08-test-traceability-and-evidence.md#起点以来的改动)，本表只写各场景的结论，不复述规则。

## 怎样使用

1. 先在“What 对结论的影响”表找到改动文件的类型，确认会不会选中、会不会触发 full。
2. 再在“等价组”表找到 How-When 组合，读测到的时机、证据和验收是否失效，以及要提醒什么。
3. 需要具体到执行者时，查“全部组合”表；worktree 合回和其他事件分别查对应的表。
4. 修改了相关代码或规范后，逐行核对判断列和依据；覆盖范围变化时，同步“选择覆盖不到的场景”。

## 定义

- **一行的单位**：一个文件的一次改动。同一文件部分暂存时，拆成两行，见 X17–X20。
- **Who 指执行这个动作的人**：B1–B5 是改文件的人；B6 是撤销的人；B7 是改写提交的人。
- **A2 和 A3 的分界**：A2 是 Feature 执行流程 Stage 0–8 之内；A3 是执行流程之外，包括规划新 Feature、问答中顺手修、文档整理。
- **A4 只包括无人主动决定的副作用**：例如编辑器重存场景，导入时生成 `.uid`、`.import`。Agent 运行工具生成的文件算 A2 或 A3；用户在调试台点采纳、由工具写入的文件算 A1。
- **When 按 Stage 划分，不按 Feature 状态**：C2 是 Stage 2 到 Stage 3A 基线；C3 是 Stage 3；C4 是 Stage 4 自动验证通过后，到 Stage 7 完成提交为止，包括完成提交本身。Stage 7 先设 `done` 再提交，所以完成提交仍算 C4。C1 是完成提交之后，到下一个 Feature 的 Stage 2 之前。
- **“当前 Feature”按被检查的 Feature 而定**：按 Stage 0 例外，可能同时有两个 `in_progress`。同一个提交从 F014 看是 B3-C3，从 F013 看是 B4-C4，两种视角各算一行。
- **worktree 内部的改动**：在 worktree 里执行的 Feature，内部改动按主表另算一遍；合回主线的动作见“worktree 合回”。
- **示例中的 Feature**：F012 是刚完成的 Feature；F013 是被检查的当前 Feature；F014 是下一个 Feature，或 Stage 0 例外中的另一个 Feature；F015 是在 worktree 里完成、要合回主线的 Feature。
- **起点与验证点**：起点是 Feature 详情中的 `base_revision`，Stage 2 写入后固定；验证点是最近一个仍在 HEAD 历史上的已完成 Feature 的证据提交。F013 在 C1 之后的改动，相对的都是它自己的起点。
- **“失败按 R3”**：失败的测试由别人的改动引起时，按 R3 停下当前 Feature，报告失败测试、选择原因和触发文件，请用户选择出口，不修改触发文件。

## 维度

| 5W1H | 取值 |
| --- | --- |
| Who | A1 用户；A2 Agent 在执行流程内；A3 Agent 在执行流程外；A4 无人决定的自动改动 |
| How | B1 未提交；B2 提交，无 Work item；B3 提交，带当前 Feature；B4 提交，带另一个 Feature；B5a 混进带 Work item 的提交；B5b 混进无 Work item 的提交；B6a revert 提交；B6b 丢弃未提交的改动；B7 改写已有提交 |
| When | C1 两个 Feature 之间；C2 已开始、实现前；C3 实现中；C4 验证通过后到完成提交 |
| What（可多选，判断时用） | D1 当前 Feature 的组件；D2 已完成 Feature 的组件；D3 多个组件共用的文件；D4 不属于任何组件的文件；D5 测试或测试登记表；D6 契约文件；D7 不参与指纹的文件；D8 测试基础设施、依赖或引擎升级；D9 删除或重命名 |
| Where | E1 当前分支；E2 worktree 合回，见下文 |
| Why（备注） | W1 实现需求；W2 修 Bug；W3 调参数或观感；W4 重构 |

“等价组”是 How-When 组合。同一组的行，脚本看到的 Git 事实相同，只有 Who 不同；结论相同也照样列出。

几条贯穿各表的现行行为：

- **选择只看内容**：改动文件是起点与当前工作区之间内容不同、参与指纹的文件，加上未跟踪的文件。提交、暂存和提交说明（包括 Work item 行）都不影响选择，所以 B1、B2、B3、B4、B5a、B5b 在同一 When 下选中的测试相同，差别只在提交历史的追溯（R1、R2、R4）。
- **证据只看指纹**：完成证据、运行结果和人工验收都绑定内容指纹；内容相同的提交、amend、squash 不让它们失效，参与指纹的内容一变就失效（R4、R5、R6）。
- **已完成 Feature 不重开**：之后的改动碰到它的组件时，只选中测试并提醒用户判断是否重新人工验收（R10、R14）。
