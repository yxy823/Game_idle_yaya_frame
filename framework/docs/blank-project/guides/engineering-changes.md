# Bug、重构、维护与实验

[返回手册](../README.md) · 相关：[Feature 开发流程](feature-delivery.md)、[故障排查](../reference/troubleshooting.md)

需要顺序处置时，查看 [Bug 定位、修复与回归检查单](scenarios-verification-recovery.md#发现-bug-后定位修复并回归)、[设计复杂度与共享能力检查单](scenarios-requirements-design.md#新增核心对象或发现设计过重时重新判断边界)，或 [文档与实际状态不一致检查单](scenarios-context-handoff.md#文档与实际状态不一致时确定修复位置)。

本页用于将问题归入需求变更、Bug、重构、维护或实验。分类依据是实际预期与授权范围；通常的工程任务写入同一份 Feature 索引和详情，由现有执行流程交付。用户主动发起的一次性框架替换见 [原地替换项目框架](#原地替换项目框架)。

## 按实际目标选择路线

| 情况 | 路线 | 应说明的结果 |
| --- | --- | --- |
| 预期行为缺失、矛盾，或用户想改变它 | `product-author` | 新的 Product 意图与验收条件 |
| 已有明确预期，代码没有做到 | `engineering-change-plan` 的 `bug` 模式 | 恢复预期并覆盖回归 |
| 已确认专业要求变化，Product 行为不变 | 对应专业 Skill 与现有计划同步路线 | 更新所属来源及受影响任务，不要求 Product 重复保存 |
| 外部行为保持不变，调整内部结构 | `engineering-change-plan` 的 `refactor` 模式 | 真实维护收益与行为保持证据 |
| 工具、构建、依赖、日志、测试设施或数据迁移 | `engineering-change-plan` 的 `maintenance` 模式 | 技术成功条件、兼容边界与验证 |
| 只想知道架构有什么问题 | 只读调查 | 有证据的发现、优先级和建议，不自动改文件 |
| 明确验证一个玩法或技术假设 | 限定范围的实验 | 假设、观察、结论和实验文件处置 |

工程 Feature 在详情中以 `engineering_change` 标明模式，不另建任务系统。

## 调查结果如何进入执行

在**生成项目根目录**提供实际现象、预期来源、复现材料和本次允许的调查/修复范围。Agent 读取相关 Product、已确认专业规格、项目规则、当前任务、真实代码/日志与测试登记表，先确认问题和修改归属。

工程标准化负责诊断、分类、提出工作项，并在相应授权下写入任务。规划时，Agent 读取测试登记表，区分复用组件与本次新增组件；批准后先使用现有组件合并入口登记缺少的组件，再写任务并运行台账检查。没有单元套件就用 `unit_test_paths: []`，不创建虚假路径；已有组件和测试保留，同名不同定义须明确处理。

新增组件与任务一同提交，具体测试映射仍在执行阶段确定。`feature-execute` 负责实现、验证、适用验收、用户指定的可选评审和交接。用户已对具体工作给出的授权持续有效，后续不重复询问同一批准。

复盘中发现的另一项工具问题或跨模块改进，不顺手塞进当前修复。保留证据和建议，按用户决定进入下一项工作。

## Bug 先查归属，再查根因

当前未完成 Feature 内的缺陷，优先在当前范围中修复。已完成行为中的独立缺陷才按独立 Bug 工作组织。预期可以来自已确认 Product、专业规格或工具契约；不明确或改变中的要求返回其归属入口，不能先改实现再补理由。详见 [专业来源与任务](specialist-workflows.md#专业来源怎样进入任务)。

诊断至少让人看懂：实际发生什么、原本应发生什么、预期依据在哪里，以及最短复现步骤。根因未确认时明确保留未知；不能把最先想到的解释当成已证实事实。

需要保存诊断时，Agent 在 `bug_diagnosis` 中记录实际行为、预期、来源、复现方法和根因。将 Feature 标记为完成前，已有 Bug 诊断记录必须包含已确认的根因；字段定义见 [Feature 规范](../../../../project-source/methodology/02-feature-list-schema.md)。

适合自动验证的 Bug 建立 `F0XX-RTyy` 回归测试。无法合理自动化时，说明具体原因并给出可重复的人工回归路径。回归关注原始触发条件和错误结果，不仅证明修复后的某条代码执行过。

Bug 成功验证并完成适用验收后，Stage 5.5 将根因、触发条件、回归覆盖和防范原则保存在当前 Feature notes。值得长期复用的防范原则按 [规则增量维护](project-knowledge.md#维护项目规则与读取工程规则) 检查归属、写前输出自检并核对授权，再决定是否进入项目规则、专项规则或不变量；不要把每个缺陷都变成新规则。晚于最终验证的治理文档变更仍需更新失效依据。

## 重构应解释实际收益

重构提案从已经观察到的维护困难或下一项确定需求出发，例如同一业务规则需要在多处同步、调用顺序分散、对象生命周期难以判断。验收既要证明行为保持，也要能解释改后为什么更容易修改。

可用一个检查问题帮助判断：移除某层后，调用者是否更简单？若移除只是把校验、错误处理、状态归属和生命周期知识散到各处，这些职责仍需有清楚的位置。文件数量减少、类名变短、评分提高都不足以单独证明改进。

`engineering-refactor-select` 在用户指定的 Feature 范围内读取 notes，按需追查代码、历史和依赖；没有记录不先创建计划。它保持只读，不改写历史 notes。

| 判断 | 处理 |
| --- | --- |
| 问题已解决或被后续工作替代 | 排除候选；同一根因合并论证并保留来源 |
| 当前问题成立 | 比较不处理的影响、最小完整改法、修改风险和验证成本；文件数、关键词与引用次数只作线索 |
| 现在有足够收益 | 推荐一项并说明优先理由，不计算分数或新增排序台账 |
| 收益不足或证据不明 | 分别说明暂缓或待核实；无有效候选时结束，不写成已解决 |
| 行为违背已接受契约 | 回到工程标准化入口判断 Bug 归属，不以重构名义改变预期 |

例如，阻碍下一项已确定功能且修正范围清楚的问题，可以先于大范围普通命名整理。独立架构调查也可直接分析代码与已有决定，无需制造 smell 记录。选出候选不自动授权实现，已有具体授权继续有效；判断依据见 [架构约定](../../../../project-source/methodology/10-architecture-overview.md)。

## 工程维护如何确定边界

| 维护类型 | 应先核对的内容 | 可观察的成功条件示例 |
| --- | --- | --- |
| 项目工具修复 | 实际错误、入口参数、输出与调用 Skill | 原始触发命令给出正确结果，相关失败边界仍有效 |
| 插件或依赖调整 | 项目使用方式、本地补丁、许可证和实际目标引擎 | 所需行为在配置的引擎中得到验证 |
| 性能处理 | 复现条件、当前测量、热点和行为约束 | 在相同有意义条件下改善指标并保持行为 |
| 存档或数据迁移 | 数据归属、已有格式、受影响版本、恢复方式 | 新旧边界按批准方案处理，失败能够辨认和恢复 |
| 素材替换 | 需求是否变化、引用与导入设置、授权来源 | 实际场景资源可用，并完成适用的视觉或听觉验收 |
| 测试或 lint 配置调整 | 规则意图、真实误报或适用边界 | 解决真实问题，同时保留仍需检出的错误 |

表中的成功条件是提案思路，不是已批准任务。维护是否需要全量测试取决于实际影响；`maintenance` 标签本身不会触发全量。项目工具已由生成项目拥有，可以在明确授权下修复，不依赖框架先发布新版本。

## 原型与技术实验

用于确定界面布局、尺寸和真实资源效果的 Godot 视觉原型，按 [视觉原型说明](product-and-planning.md#先验证视觉原型再接入依赖它的逻辑) 准备与验证。正式计划中的视觉基础复用 Feature 与人工验收；只探索一个未知问题时使用本节实验路线，两者不另建任务系统。

当用户明确要求验证假设时，先界定一个问题、允许修改和运行的范围、时间或尝试预算，以及保留还是移除实验文件。独立实验可以不建立完整 Product/Feature 链；已有 Feature 内的实验继续遵守其任务边界。

例如验证一种拖拽操作是否容易误触，可以保留实验场景、输入条件和观察结果。观察到“某参数更顺手”仍是实验结论，不会自动变成已批准的正式数值需求。

实验的假设、结果、决定和文件处置写入当前 Feature notes；没有 Feature 时写入当前 Progress。采纳结果进入正式开发时，再回到 Product 或工程变更入口。超出实验预算或范围需要用户决定。

## 手动修改后检查需求一致性

在目标游戏项目使用 [提示词库](../../../prompts.json) 的“Godot 项目开发 → 验证与收尾 → 检查手动修改与需求的一致性”，填写修改范围、意图与比较基线。适用于手改代码、场景、资源、配置、Product 或 Feature 后，判断是否偏离需求；先交付只读结论，再按明确选择的范围处理。

未提供基线时，Agent 检查相关已暂存、未暂存和未跟踪内容；已提交修改应指定提交或范围，并核实比较版本。工作区干净不代表没有待检查的修改。历史基线无法确定时，仍可核对指定范围的当前一致性，但需说明哪些变化无法还原；无需先清空或提交工作区。

Agent 将实际差异与相关 Product、已确认专业要求、Feature/AC、已有决定及必要调用关系对照，按 [实际目标路线表](#按实际目标选择路线) 判断。代码描述实际实现，需求来源描述预期；手改 AC 也不能自动改变产品意图。已明确的新决定直接沿用，区分尚未同步的决定与意图不明的冲突。例如，“每次点击增加 1”被改成“增加 5”时，应先判断是误改、实验还是已决定的新玩法，再给出相应建议。

检查结果引用需求与文件位置，区分已确认一致、存在冲突和证据不足，指出受影响的计划、测试及人工验收。规则与提示词约束 Agent 的处理方式，无法拦截人工保存；测试仅证明实际覆盖并执行过的部分，格式或引用检查不能证明行为一致。本入口不运行测试、启动 Godot 或修改文件。

得到只读结论并确认处理范围后，按当前情况继续：

| 当前情况 | 下一步 |
| --- | --- |
| 保持行为或恢复已有预期 | 沿 Bug、重构或维护路线处理，通常无需改 Product。 |
| 改变已确认要求 | 玩家行为由 Product 承接；专业要求由所属 Skill 更新。来源就绪后按 [要求变更检查单](scenarios-requirements-design.md#已确认要求变化后对齐已有计划) 同步受影响任务与验证。只改专业来源也需判断影响。 |
| 继续当前 Feature | 将相关手动差异纳入原任务，核对旧证据是否有效，保留已完成历史；按 [Git 规则](../../../../project-source/agent-rules/00-core/git-worktree-and-commits.md) 与 [执行规范](../../../../project-source/methodology/03-execute-loop.md) 续接。 |

`feature-sync` 处理已提交来源对计划的影响，不承担通用代码审查。共享影响、Project Rules/工程规则和历史覆盖未知的处理，见 [来源发现规则](specialist-workflows.md#专业来源怎样进入任务)；历史无法证明时不能据空差异认定已同步。

需要正式独立评审时使用“独立审查代码或指定变更”；需要实际运行验证时使用“单独验证某次变更”。各入口位置见 [提示词导航](../reference/skills.md)。

## 原地替换项目框架

在实际项目中使用 [提示词库](../../../prompts.json) 的“Godot 项目开发 → 修复与改进 → 审核并原地替换项目框架”，填写项目目录、待采用框架目录和补充限制。此入口在当前项目内更新，框架来源只读；要保留原项目并另建副本时，使用 [复制迁移入口](../getting-started/migrate-existing-project.md)。

先审核归属、定制、状态读取关系和必要适配，说明本次采用的来源与方案。发送该提示词即授权审核通过后的替换、适配、验证及一次本地提交；一般文件增删、改名和少量字段调整直接处理，不逐项重复确认。无法保护项目内容、关键状态含义冲突或需要较大重写时，拒绝本次直接覆盖并说明影响；材料或环境不足单独报告，不自动改做复杂迁移。

已确认的纯框架内容采用新版，并移除已确认废弃的旧入口；项目业务、数据、进度和历史保留，混合配置与有效定制做最小合并。创建用的复制清单包含空白数据，不能直接全量覆盖已有项目。状态只允许确定且无损的必要格式适配，保留 ID、语义和完成事实；旧证据留作历史，不能代替新版下的当前验证。

这是一次性替换，不新增 Feature、升级系统或同步台账，也不重演已有任务阶段。相称验证通过后，将更新、必要适配和使用说明合为一个提交，保留无关工作；未完成验证则如实报告。必要交接复用 Progress，更新结束后不自动开始业务开发。具体授权与边界以 JSON 正文为准。
