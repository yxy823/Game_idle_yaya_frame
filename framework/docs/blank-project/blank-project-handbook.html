空白 Godot 项目使用手册

这份手册帮助你从空目录、游戏想法或已有 GDD 开始，使用 Coding Agent 整理需求、规划任务、实现并验收游戏功能。

打开 HTML 阅读版，目录检索、字号与图表操作见 HTML 阅读操作。阅读版包含全部手册正文与图表，可离线使用；独立阅读包不包含完整提示词、项目工具和源规范。实际操作需要完整框架或生成项目中的对应文件，带 ↗ 的链接用于定位这些材料。

这套起点提供什么

创建后，你会得到 Godot 项目文件与插件、Agent 规则和 Skill、需求与任务模板、检查工具。玩法代码、主场景和业务测试由后续任务建立；初始 Product 和任务索引为空。

当前目标环境为 Windows 11、PowerShell 7、Godot 4.7、GDScript、gdunit4，维护命令使用 Python 3.12+。创建器只复制文件，Agent 随后在目标项目核实工具并准备开发环境。

第一次使用路线

  1. 创建空白项目：你指定外部空目录，Agent 按清单复制材料；已生成框架项目时跳过这一步。
  2. 准备首次使用：你提供必要的项目选择，Agent 核实工具、记录配置与实际准备结果，并按授权处理初始 Git 基线。
  3. 整理需求与计划：你提供想法或 GDD，Agent 整理 Product 总览与模块需求，只澄清关键缺口，再拆分当前模块的 Feature。
  4. 开发与验收 Feature：你确认具体方案与适用的人工结果，Agent 完成实现、验证和提交；已有具体授权可以连续推进。

只想讨论设计时，可以从需求指南开始；已有完整材料无需重新口述。下一章表示全书阅读顺序，各页的“本任务下一步”表示当前工作应进入的操作。

先认识需求与任务

以“玩家点击按钮收集资源”为例：Product 总览说明这项玩法在整款游戏中的作用，模块需求明确数量和交互规则，Feature 则安排一项可实现、可验证的工作。

名称 用来判断什么
GDD 已有游戏设计输入中，哪些意图和规则需要纳入本项目？
Product 总览 游戏的核心循环是什么，模块之间如何配合？
模块需求 当前模块应该表现出哪些行为，哪些内容暂不做？
Feature 本次要交付什么，依赖哪些任务？
AC（验收条件） 用哪些可观察结果判断这项任务达到预期？

文档中的“逐个 Product 推进”指按模块交付：可以先保留整款游戏的设计，再逐个拆分并完成模块任务。计划文件只描述待做工作，实际结果由测试报告和适用的人工验收记录证明。

创建空白项目

返回手册 · 下一步：首次使用

创建器按复制清单把源材料复制到外部目录，得到独立项目文件。它不配置环境、不导入 GDD、不初始化 Git，也不运行游戏或测试；这些工作在目标项目中按后续任务进行。

准备目标位置

目标必须是维护仓库之外的新目录或空目录。你已经手动创建的空文件夹可以直接作为目标；已生成框架文件的项目应跳过复制，进入 首次使用。已有 GDD 留在原位置，复制完成后再按 GDD 接入说明 整理需求。

检查的是完整路径，包括父目录和解析后的路径：

目标情况 结果
D:\Games\MyGodotGame 不存在或为空 可以创建
D:\Games\My Game 或 D:\My Games\Game 因空白字符被拒绝
D:\游戏\MyGame 因中文路径被拒绝
当前维护仓库的子目录 被拒绝
包含维护仓库的祖先目录 被拒绝，不能把源仓库包含在输出中
已有文件的目录、已有普通文件 被拒绝，不覆盖已有项目

目录名和 Godot 显示名称是两个概念。项目路径遵循上述限制；后续修改 project.godot 的 config/name 不会重命名目录。示例统一使用简短 ASCII 路径。

执行复制

在框架根目录运行以下命令。本机使用个人规则指定的解释器；在其他机器上应先换成已确认的 Python 3.12+ 完整路径。

powershell
Set-Location -LiteralPath 'D:\A_Games\Game_idle_yaya_frame'
& 'C:\Users\89523\anaconda3\envs\codex-python\python.exe' -B framework/commands/create_project.py --output 'D:\Games\MyGodotGame'
$LASTEXITCODE

--output 是唯一业务参数且必填。-B 属于 Python，用于避免本次进程写字节码缓存。上述路径是调用示例，不表示本手册已经为你创建了该项目。

创建器从自身位置找到维护仓库，再读取 project-files.json。它先核对目标与全部清单源路径，再创建目录并复制；文件可以改名，目录会连同子目录内容一起复制。它没有模板替换步骤。

成功输出的数量是清单条目数，不是文件总数；一个目录条目可能包含很多文件。以退出码和实际输出判断复制是否完成。

为什么本手册不会进入项目

复制清单只选择 project-source/ 中的交付材料。本手册、集中提示词和维护工具留在 framework/，不会先复制再删除。生成项目使用自己的 README、规范与工具；完整分工见 手册入口。

复制失败后如何处理

  1. 先阅读 Copy failed 后的实际原因，区分目标不合法、缺少源文件、路径越界和读写权限问题。
  2. 前置检查失败时修正输入或源材料，不把它解释为 Godot 环境失败。
  3. 复制途中失败会保留现场。检查目标内容后，再由本次任务决定如何处理这份未完成输出；创建器没有回滚或覆盖重试模式。
  4. 不直接对半成品再次执行复制：非空目标仍会被拒绝。不要为重试删除用户文件，也不要把新路径当作自动获得创建更多项目的授权。

修复框架源材料不会更新已存在的游戏项目。需要保留旧项目并使用当前框架继续开发时，使用复制迁移已有项目入口；不对已有内容运行创建器。

创建成功后，打开目标项目继续 首次使用。

首次使用与环境准备

返回手册 · 前一步：创建项目 · 本任务下一步：需求与规划

复制完成后，你在目标项目中向 Agent 发送“准备 Godot 开发环境”提示词，并提供项目名称、文档语言或工具位置等尚未确定的选择。Agent 核实配置、记录真实准备结果，之后即可按授权进入需求整理与开发。已有设计文档可直接使用 GDD 入口。

打开正确的工作目录

你将 Coding Agent 的工作目录切换到生成项目。Agent 先读取项目自己的 AGENTS.md、README.md、docs/methodology-config.json 和 docs/progress.md，再按任务加载 Skill 与规则。

从完整框架的 集中提示词 中选择“Godot 项目开发 → 项目初始化 → 准备 Godot 开发环境”，填写后在目标项目发送。只有独立阅读包时，需要另取该提示词正文；生成项目运行时不依赖框架目录。

普通 Feature 复用已确认配置。安装位置、工具版本或命令改变，以及实际调用失败需要诊断时，再进行相关就绪核对；不用为每项任务重复搜索安装位置。

首次 Git 状态如何处理

创建器本身不建立 Git 仓库。当前集中管理的环境准备提示词显式授权：若目标没有自己的仓库，先核对不位于其他仓库内，再执行本地 git init；同时明确要求本次初始化不提交、不创建远程、不 push。

因此，按该提示词完成环境准备后看到尚未提交的初始文件是预期结果。获准提交初始基线后，可以继续同一次初始化，核对并仅提交已知初始文件及本次环境准备的改动；工作区干净后再开始新的修改任务。不能把初始化提示词当作初始提交授权，也不能把这些文件混入第一个业务 Feature。

如果使用其他初始化请求，以该请求已经给出的范围为准。已有仓库保留原状态；仓库发现和文件归属存在疑问时先查清，不执行清理、覆盖或自动暂存。

没有主场景与业务测试时

初始 project.godot 没有 run/main_scene，默认目录也没有游戏脚本或测试套件。此时可以说明项目已经复制、工具环境已经确认，但不能声称游戏启动或业务测试通过。

主场景、业务目录、测试根目录及首个可运行行为由后续获批任务按需要建立。初次 Product 规划通常先安排可运行基础，再按依赖实现行为；不要为了给初始化报告填写成功结果而虚构一个 Feature 或测试。

首次命令行运行前的扫描

配置 ready 不会生成 Godot 的全局类缓存或导入资源。新项目尚未在编辑器中打开时，直接运行 CLI 测试可能报找不到 GdUnitTestCIRunner；此时用例尚未执行，不能据此判断业务行为是否正确。

Agent 在首次获授权的命令行测试或项目脚本运行前，让配置中的 Godot 完成一次编辑器扫描，确认进程结束并检查退出码和解析、导入错误。已正常打开过的项目可复用已有准备；失败时按实际错误排查。

仅核对配置时可以暂不扫描，Agent 在初始化报告中注明未执行；实际扫描遵守项目 AGENTS.md 的权限与审批约束。完整命令见 项目工具的首次扫描说明，独立阅读包用户应在完整框架或生成项目的 tools/README.md 查阅。

生成文件按项目资产与引用规则处理，不能把 .import、.uid 与 .godot 都当作可删除缓存。

初始化报告和下一步

Agent 将实际过程写入 reports/initialization.md，已有报告追加并保留失败；docs/progress.md 保存当前结果、阻塞、下一步和报告链接。

你查看报告中的工具版本、修改、命令结果、未执行项和 Git 状态，便可判断准备是否完成以及剩余问题。后续 Agent 也从这些记录续接。

仅使用环境准备提示词时，交付准备结果后结束；已有具体后续授权则继续其范围。准备完成后通常先处理初始基线，再从 想法或 GDD 整理 Product；只讨论设计可以提前进行。

从想法或 GDD 到 Product 与 Feature

返回手册 · 本任务下一步：开发与交付 Feature

你提供游戏想法、已有 GDD 或已确认的设计，Agent 将它们整理成 Product 总览与模块需求，再把当前模块拆成 Feature。本章帮助你判断需求写到什么程度、任务如何验收，以及规划结果还缺什么；尚未明确的关键设计仍由你选择。

在目标项目使用 提示词库 的“Godot 项目开发 → 需求设计 → 从想法或已有 GDD 整理 Product”，填写材料、限制与本次范围。默认交付需求与适用规划，不开始游戏实现。

有现成 GDD 可以直接提供路径或附件。目录状态、原件保留和新旧材料冲突的处理见 接入已有 GDD，无需重新口述全部设计。

用一个收集资源的例子理解层次

假设输入只有：“玩家点击按钮收集资源，并能看到当前数量。”为了讲解，以下约定初始值为 0，每次有效点击增加 1，暂不包含存档或自动生产。这些是教学片段，不是已批准需求、完整模板或仓库中的实际任务。

Product 总览先说明游戏的核心循环是“收集资源 → 看到数量反馈”，并列出资源收集模块。它提供全局入口，不展开按钮和计数器的全部细节。

模块需求再把这段想法变成可判断的规则：初始数量为 0，有效点击增加 1，界面显示当前数量。输入含义、界面反馈与暂缓范围在这里确定；GDScript 类名和节点布局留给实现方案。

Feature 则确定一次交付：示例 F001 实现计数、收集输入和数量显示。它引用模块需求，用 AC（验收条件）约束结果，例如初始显示 0，连续两次有效点击后依次显示 1、2。计划还要区分哪些结果适合自动测试、哪些需要人工体验。

这几步分别增加全局关系、行为细节、任务边界与结果证据。原始设计由正式需求承接，Feature 引用需求，报告记录实际观察，避免把同一份正文抄进所有文件。交付指南 会继续说明这项示例工作如何验收。

Product 分成总览和模块

文件 回答的问题 内容边界
docs/product.md 整款游戏做什么，各模块如何配合？ 定位、玩家、核心循环、模块清单与依赖、视听方向、变更历史；通过链接进入模块细节
docs/product/NN-name.md 这个模块具体应怎样表现？ 行为、数据含义、状态、UI、音频、数值、验收条件、暂缓边界及变更历史

数据字段的业务含义保存在模块需求中，GDScript 类型、节点布置和算法选择由实现方案或工程记录承接。

模块文件使用两位编号和 ASCII kebab-case 名称，例如 01-gathering.md。已有模块编号保持稳定；新增模块追加可用编号。模块废弃按规范保留可追溯历史，不为重新排序而批量改名。

模板必需章节保留，不适用时说明原因。共享概念可引用 CONTEXT，具体行为仍写在负责的模块中，不复制多份定义。

完整结构见 Product 规范。

已有明确答案直接沿用。需求整理、拆分或同步结束后，Agent 按本次授权决定下一步：只要求文档或规划时交付后结束，已明确授权实现时进入任务执行。仍会改变验收含义的关键选择由你决定。

Feature 如何拆分

Agent 每次拆分一个模块的已确认需求，完成其所需 Feature 后，再拆下一模块。 一个模块对应 docs/product/NN-name.md；推进顺序根据总览中的实际依赖确定，稳定文件编号只用于定位。

后续模块可以先保留已有设计，轮到它时再复核需求、分配 Feature ID、详细 AC 和测试登记。这样既能保存全局设计，也能结合已实现结果调整后续计划。

任务拆分入口 generate-feature-list 将新任务追加到现有索引，保留历史 Feature、测试登记与修订记录。当前模块已有计划时直接复用，需要改变计划则由 sync-feature-list 增量同步。

一项 Feature 交付可独立验证的完整行为或工程结果，工作量为 small 或 medium，过大的工作继续拆分。Agent 复用已有基础设施，只补当前模块必需的运行基础；模块所需前置未完成时，先调整推进顺序。

进入下一模块前，Agent 对照当前模块已确认需求、Feature 来源与状态确认交付完整。仍有待做、进行中或受阻任务时，应说明剩余工作；没有可执行候选或模块文档标为 done 不能代替这一判断。拆分规则见 逐模块规划规范，授权续接见交付指南。

规划产物的分工见 文件职责参考：索引定位任务，详情定义范围，测试登记表连接验证，修订记录保留需求变化对计划的影响。

F001 等 ID 记录分配顺序，不直接决定执行先后。depends_on 构成无环依赖图；只有前置任务均为 done 的 pending 项才可被列为下一项候选。同样可执行时再用稳定 ID 顺序选择。

验收条件和测试 ID

每条 AC 使用稳定 ID，例如 AC01。条件写成可观察的结果，避免“体验好”“性能高”这类缺少判据的描述。机器可验证内容关联逻辑测试 ID，人工判断内容记录可重复的检查步骤。

标识示例 意义
F012-AC01 F012 的 AC01 自动验收测试
F012-AC01-02 同一 AC 下的另一个自动测试
F052-RT01 F052 修复 Bug 时建立的回归测试
INV-LIFECYCLE-01 跨 Feature 的生命周期不变量
resource_collection 资源收集语义组件，用来选择相关安全网

规划阶段 verification.acceptance_mode 可以为 null，表示尚未决定；正式执行在 Stage 1 先根据需求选择 manual 或 automated，再填验证项。初始空列表不表示自动选择了全自动验收。

允许先登记 planned 的验收/回归测试，随后在实现中创建并改为 active。组件的 unit_test_paths 只登记已存在套件，没有套件时用空数组；不要用未来目录冒充现有安全网。

测试登记表的作用与位置

docs/test-registry.json 是项目的测试登记表（Test Registry），固定保存在这个位置。它将组件、Feature / AC 和实际测试文件、测试函数关联起来：组件记录已存在的单元测试路径，测试条目记录逻辑 ID、用途、来源、组件及 planned / active / retired 状态。

例如，后续 Feature 改动资源收集行为时，Agent 声明影响 resource_collection 组件，选择器便可找到已登记的计数单元测试及相关历史测试。空项目尚无这些记录，随实际规划和实现建立；登记表提供查询关系，真实报告才说明是否通过。

规划完成时应能回答

哪些需求已经规划？ Agent 根据实际写入结果，列出当前模块的已确认需求位置、对应 Feature/AC，以及拟采用的自动测试或人工检查。逐项检查遗漏与重复，不能用来源链接或任务编号代替覆盖判断。

还缺哪些工作？ 报告分别说明尚未覆盖的当前需求、尚未实现的功能、尚未编写的测试和尚未执行的验证。后续模块和已确认排除的范围只说明去向；增量同步只展开本次变化及真实下游影响。

下一步从哪里继续？ 可执行事项留在所属 Feature 或当前 Progress，已有具体授权继续有效。规划对齐不等于实现或验收通过；正式字段与覆盖检查见 Feature 规范。

接入已有 GDD

现有 GDD 可以直接作为需求整理的输入，不必重新口述整套设计。 使用 提示词库 的“Godot 项目开发 → 需求设计 → 从想法或已有 GDD 整理 Product”，提供文件路径或附件、材料中的当前有效范围和本次要完成的工作。

先判断项目目录状态

目录现状 接入方式
只有一个空文件夹 按 创建说明 向该空目录复制框架材料，再进入目标目录整理需求；GDD 先留在原处，避免目标提前变成非空目录
已由当前框架生成，尚无实质 Product 跳过创建器，按 首次使用 核对准备状态，再以 GDD 整理初始 Product
已有实质 Product 或 Feature 对照 GDD 与现有规格，按实际差异增量修改；文件更完整或日期更新不构成覆盖已有决定的依据
已有其他框架的代码、规则或任务 使用 复制迁移已有项目，先处理项目结构与成果续接

只阅读、讨论 GDD 不要求运行 Godot；正式写入需要遵循项目文档语言与 Git 约定，进入实现前须完成环境准备。

按内容对应到正式文件

GDD 中的内容 整理后的归属
游戏定位、目标玩家、版本核心循环、模块依赖、整体美术与声音方向 docs/product.md，保持为可快速浏览的总览
玩法流程、数据含义、状态转换、UI 交互、声音触发、数值和可观察结果 对应 docs/product/NN-name.md，保留模板章节语义
多处共用且容易混淆的概念 优先复用模块定义；确有跨模块需要时整理到 docs/CONTEXT.md
引擎类、节点布局、算法或存储格式等技术建议 与产品行为分开说明；经采用的技术选择进入实现方案或相应工程记录
备选方案、未来版本、待定数值或互相矛盾的描述 标明待定或暂缓范围；只解决影响当前模块与其依赖的关键决定

按语义和模块责任建立对应关系，不按 GDD 章节数机械生成模块，也不直接把整个 GDD 改名为 product.md。读取范围应覆盖总览、当前模块及其依赖；不可读附件、缺失图表和外链材料明确列为缺口，不能以推测补齐。整理时用简短的“GDD 章节 → Product 位置 → 待处理内容”对应说明检查有无遗漏。

保留原件，确定后续维护位置

外部 GDD 原件保留在原位置。通常直接读取即可；需要让目标项目保留独立参考副本时，按授权复制原文和必要附件，使用能说明用途的名称，并注明它是参考快照。复制不移动原件，不覆盖已有项目文件。

整理完成后，已确认的 Product 是后续规划与实现依据。原 GDD 保留来源价值，不与 Product 双向同步；日后引入新版 GDD，仍通过 Product 变更入口核对差异。来源定位写在相关 Product 内容或现有变更记录中即可。

从整理结果继续开发

Agent 先复用 GDD 中已明确的设计，分别列出已确认内容、提议和关键冲突；材料中有答案的事项不重新访谈。已有具体授权继续有效，重要未决选择不由 Agent 静默决定。

接入 GDD 后沿用 逐模块拆分 路线。你可以继续选择“拆分当前 Product 的 Feature”或“执行指定或下一项 Feature”，也可明确一段连续执行范围；完整设计本身不等于实现授权。

需求变化后怎样保留历史

已有计划由 sync-feature-list 对照真实 Git 源差异、规划基线和当前文件增量更新。已有变更说明直接复用；无法恢复可靠基线时，按授权对当前完整规格与计划做核对，明确历史未知，使用现有修订字段记录新基线。最后一次 notes 提交或复制空台账的提交都不能冒充规划基线。

变化 处理方式
已完成行为需要改变 通常新增 Feature，保留旧 AC、测试 ID 和完成事实
未完成任务修改、拆分或合并 更新当前详情、下游依赖、替代任务和测试映射，记录修订关系
旧工作被替代 obsolete 表示未完成即废弃，obsolete_done 表示曾完成；未完成任务不能继续依赖这些旧项
旧 AC 或测试失效 退役记录保留历史来源；planned/active 测试仍关联当前 AC，不能为消除失败无依据地删测试
只需重跑有效下游测试 归入当前变更 Feature 的 notes 与 Stage 1 验证范围，不另建任务、不改变原测试归属
后续未拆分模块变化 不影响现有工作时只改 Product；轮到该模块再读取完整最新规格，不能因早于同步基线而漏拆

写入顺序为：先合并新增组件，再更新 Feature、测试和修订关系，最后检查完整台账。无单元套件时登记空路径数组；保留已有数据，同名冲突须解决，不能重置登记表让检查通过。本次写入错误在原授权内修正，已有损坏或权限问题按实际边界处理。

独立实现、修复或单独交付的回归工作才新增任务。仍需执行的测试不能以备注免除，尚未实现的替代测试不能作为完成依据；真实测试删除与替换方式见 实现与测试。

先讨论，按需留下术语

project-clarifier 默认只讨论；按实际缺口提问，用具体情景检验概念，上游决定变化后只复核受影响结论。需求与音频澄清入口沿用同一方法，返回草案或补丁；已知信息直接复用，不设置问答、模块或 AC 数量下限。

跨模块或 Feature 使用的稳定概念按需放在 docs/CONTEXT.md，局部定义已有合适位置时保留原处。每个概念只维护一份定义，其他位置链接过去。具体职责见 项目知识。

仅记录已同意的区别、统一名字或移动定义，且含义和行为不变时，不要求 Product 初始化或 Feature 同步。若定义变化实际改变玩法、数值或验收条件，就先解决产品决定，再按授权更新 Product 并同步任务，不能把它当成纯文字整理。

UI 与声音产物的边界

product-ui-sketcher 在布局或交互需要澄清、或用户要求草图时返回 ASCII 线框、交互意图和状态差异。已有明确交互的文案或数值调整可直接更新需求。HTML/Tailwind 探索须有实际用途或用户请求，不在每次 UI 修改后固定追加询问；探索稿不等同于已实现的 Godot 界面，也不能证明适配和手感。

product-audio-sketcher 返回声音触发、时长、风格和稳定的 _placeholder_ 文件名等要求。它复用已知信息和共同声音约定，只补问有影响的缺口，不要求每个声音完成固定次数的问答；不生成正式音频资产，播放实现或调试仍走工程入口。

这些辅助 Skill 形成 Product 草案或补丁，Product 的正式写入由 product-change-standardizer 负责。确认界面或音频需求后，仍需在 Feature 中说明具体实现和人工验收范围。

开发、验收与交付一个 Feature

返回手册 · 前一步：需求与规划 · 相关：命令与验证

开始本章前，应已有确定的 Feature、所需需求和可用开发环境。Agent 通过 execute-next-feature 实现这项任务，交付代码、验证结果、适用的人工验收记录与本地提交；中断任务从实际停点继续。

需要主动发起开发时，在目标项目使用 提示词导航 中的“Godot 项目开发 → 日常开发 → 执行指定或下一项 Feature”，说明目标任务与本次范围。已有明确实施授权的任务可直接续接，无需重新发送同一批准。

你与 Agent 各自做什么

你主要提供实施范围、解决关键设计选择，并在需要时体验实际结果。Agent 负责读取当前任务、提出具体方案、实现和验证；已有具体授权直接沿用，不因进入新阶段重复询问。

时机 你的参与 Agent 留下的结果
开始实现前 确认具体方案，决定材料中尚未明确的重要取舍 任务范围、验收方式与验证计划
实现与自动验证 出现超出原范围的选择或阻塞时参与决定 代码、测试、实际运行与静态检查结果
需要人工验收时 按清单实际操作并返回观察 绑定当前内容的清单，随后记录你的结果
交付时 查看结果并决定未授权的后续工作 完成状态、报告、提交与剩余事项

正常路线是“确认方案 → 实现与验证 → 适用的人工验收 → 记录与提交”。Bug 经验和用户指定的独立评审按条件执行；需要定位阶段编号时，再查 Stage 0–8。

沿用资源收集示例完成交付

继续 需求指南中的教学片段：示例 F001 要实现点击收集与数量显示。以下说明如何取得结果，不表示本仓库存在该任务，也不预填任何通过记录。

  1. 把 AC 变成检查方法。 Agent 根据已确认的“初始 0、点击后 1、再次点击后 2”设计自动测试；若需求还包含按钮辨识或操作手感，就在方案中加入对应人工检查。
  2. 实现并取得证据。 Agent 编写计数与显示行为，运行适用测试和静态检查。测试失败先查实际原因，再在原范围修复；验证方法与文件位置见命令参考。
  3. 交付真实结果。 报告分别说明数值与显示测试是否实际执行、人工项是否完成、还有什么问题。需要人工验收时，你的有效结果文件或明确口头反馈才提供接受依据。

示例中的 0、1、2 是预期值，实际日志与报告才说明执行结果。若操作链未验证或人工项尚未完成，报告应停留在对应事实，不能只因代码已提交就说功能已验收。

Stage 1 为什么先决定验收方式

涉及画面、声音、动画、手感或其他人的判断时采用 manual；所有 AC 都可用自动方式充分验证时可以选择 automated。选择从需求出发，不能根据“人工检查列表为空”倒推不需要人工验收。

例如资源计算和存档字段的确定性结果可以自动检查；按钮是否容易辨认、声音是否刺耳或角色移动是否合适仍需要人在实际体验中判断。manual Feature 也可以包含大量自动测试。

Stage 1 一次说明任务范围、影响组件、已有安全网、新测试、资源依赖、人工检查和全量测试理由。用户已经对这个具体范围作出批准就沿用，不在后续阶段重复问同一件事；实现批准仍不等于用户已经验收结果。

实现与测试怎么配合

Agent 先运行与变更相关的已有测试，作为修改前的安全网。空项目尚无相关测试时如实说明；已有测试本来就失败时保留原始错误，不记成本次修改引入，也不自行吸收无关修复。

适用 TDD（测试驱动开发）的新行为先建立对应测试，确认失败来自缺失或错误行为，再实现并取得通过。这里的 RED 指测试因目标行为尚未实现或存在错误而失败；解析错误、环境故障和未发现测试用例不属于这种有效失败。窄范围运行支持调试，最终验证按当前 Feature 和测试登记表计算。

最终默认使用 --scope auto 运行受影响测试集合（affected），必要时执行全量（full）。一次覆盖充分且内容仍匹配的全量成功可同时满足必需集合（Required）和受影响集合，不必重复运行。命令、报告与静态检查见 命令与验证。

若需求变化涉及旧测试，同步报告先说明要处理的断言、方法/文件和当前引用，批准后交给对应 Feature notes。实现阶段按该范围实际删除或替换，并更新有效映射与注册路径；同一文件里的有效用例继续保留。测试登记表的 retired 只表示记录退役，仍在被选中套件内的旧方法仍可能执行。已完成 Feature 和退役记录保留历史用途，详见 失效测试处理约定。

人工验收应如何操作

manual Feature 按 人工验收文件契约 交付清单并接收结果。每项检查对应批准的 AC 或必要回归，写清入口场景、起始状态、输入、预期反馈和重置方法；设备、时长或随机种子影响结果时再补充。

Agent 先编写初始项为 pending 的 JSON 清单，运行 prepare-manual 绑定最终内容，并提供 reports/manual-acceptance/ 中原清单的可点击路径。Feature notes 只留决定与链接。

你按清单完成实际检查后，可以返回结果 JSON，也可以在对话中明确反馈当前范围的接受或拒绝。同一次决定只需采用一种反馈方式；有歧义时，Agent 只澄清具体问题。两种方式都以清单和实际检查为前提。

使用结果文件时，按以下步骤操作：

步骤 执行者与文件 结果
留存清单 用户保留原清单，另存结果 JSON 结果与清单共用结构，不覆盖原清单
填写结果 用户按实际观察填写 status 与 comment 每项填写 passed/failed，未执行项保留 pending；用例 ID、版本、步骤和预期保持不变
接收 Agent 阅读反馈，再导入原清单与结果 对照用例 ID、定义、覆盖和版本，记录 accepted/rejected/pending；完成前重读原件

项目不限定操作工具，截图可以辅助说明，不能代替实际结果。

清单的完整字段、模板与导入命令由项目 methodology/manual-acceptance-files.md 定义；只有独立阅读包时，需要从完整框架或生成项目取得这份文件。普通验收者可直接填写 Agent 提供的清单，无需自行拼装结构。

你提交的有效结果中所有必需项均为 passed，且范围、版本和反馈一致，即表示明确接受该范围，不再要求重复说“验收通过”。任何失败登记 rejected，仍有未执行项则保持 pending。

采用文件反馈时，文件缺失、旧版本结果或改变预期不能当作当前通过；导入成功只表示已记录结果，不表示 Feature 已完成。报告保存和普通使用说明变化不会自动使业务测试失效。复验保留仍需引用的失败原件，不覆盖原清单。

失败按已有授权修复；反馈改变了需求含义时，回到对应 Product/计划修订路线，不悄悄改 AC 迎合结果，也不把注释中的建议当作新增实施授权。automated 模式省略 Stage 5，不生成空人工清单或虚构接受。

完成记录与 Git

Agent 完成前核对 AC 与最终差异、测试原件、适用人工决定和直接解析/lint，并满足你明确指定的评审条件。完成依据工具负责检查测试与适用人工接受，其他检查仍由 Agent 根据实际结果确认。

显式检查通过后才把 Feature 记为 done 并填写完成时间。随后保留长期 notes，将执行历史归档一份到 docs/progress/，在当前 Progress 中链接它。

本次形成的成功做法、排障方法或失败教训，有复用价值时在提交前写入 docs/knowledge/ 对应主题并更新索引；原任务经过仍在 Feature notes，知识条目链接过去。Stage 8 汇报已有条目，不在提交后再开始补文档。纯知识 Markdown 不使业务测试证据失效；新增脚本、规则或验收契约仍按其实际影响验证。

项目默认在当前分支提交本任务明确路径或检查过的差异块，提交前查看暂存区完整差异和检查结果；用户要求不提交时遵守该要求。Feature 提交标题采用 <type>(F0XX): <中文行为摘要>，正文包含 Work item: docs/features/F0XX.json，非简单变更补充原因和主要验证。提交后再次核对状态，不自动 push 或改写历史。

交付后如何继续

Agent 在 Stage 8 汇报实际交付、验证范围与报告路径、提交和工作区状态，以及占位资源、未处理事项和下一项候选。你据此判断哪些成果可用、哪些仍需决定；已有具体授权继续有效，候选本身不授予执行权限。

只有本次范围已完成、你要求暂停、缺少必要决定或前置受阻时停止。若后续任务已经具体获批，Agent 可继续执行；当前模块的所需 Feature 完成后，再按授权复核下一模块需求。

2 标记 in_progress，写入批准的验证计划 AC 映射、测试登记表和完成依据初始化
3 已有安全网 baseline、适用的 TDD、实现 有意义的失败原因与通过结果；必要占位资源登记
4 运行相关或必要全量测试，直接解析与 lint 原始结果；manual 模式准备可重复验收步骤
5 仅 manual 模式执行人工验收 用户对实际范围的明确接受或拒绝
5.5 仅 Bug 任务记录经验 根因、触发条件、回归与防范原则
6 用户指定时才执行独立评审，可合并多项 Feature 默认省略；报告问题与证据，按用户选择处理
7 检查完成依据、更新台账和历史、整理有价值的知识、本地提交 当前最终内容满足适用检查，提交只含本任务
8 交接结果并核对后续范围、授权和前置条件 已授权则继续；范围完成、要求暂停或缺少必要决定时停止

各阶段详细行为由 执行规范 统一定义，execute-next-feature 提供操作入口与按需参考。这张图用于查找人工验收、Bug 经验和指定评审等分支；各分支的实际要求见对应小节。

按需独立评审与再次验证

独立评审默认不启动，也不在每项 Feature 完成时例行询问。你可以通过“Godot 项目开发 → 验证与收尾 → 独立审查指定修改”选择单项、多个 Feature、提交范围或明确差异，并说明评审时机。多项评审核对当前合并成果及直接受影响的调用者，输出一份报告，不逐项重复审查整套内容。日常实现仍由作者核对 AC、范围、规则和最终差异，不另建自查阶段或报告。

可以等选定 Feature 完成并提交后再集中评审，之前各项无需停留在未完成状态；明确要求“评审后再继续”时，Agent 遵守该顺序。具体授权沿用原会话，不另建队列、开关或待评审状态。

执行评审时使用新的独立上下文，读取实际差异、需求、规则和原始证据，分别给出“需求符合性”和“代码质量”的结论及依据；同一根因映射到相关 Feature，问题注明维度和严重程度。缺少依据或独立上下文时如实说明限制，不把作者自查称为独立评审。详细方法以执行规范 Stage 6 为准。

只要求评审时交付发现并停止，问题等级不是修改授权。分别核实问题与改法，在已选修复范围内处理；仅保留已接受且有用的后续事项，不把每条建议变成 TODO。当前任务中的确认缺陷回到实现阶段，已完成 Feature 保留历史并走已有工程修复入口。确认的完成阻断缺陷不能因评审可选而被忽略。

当前运行结果在只读评审后仍有效时可复用。修复改变最终内容则更新失效验证，影响已接受行为时更新对应人工验收；再次评审依据用户约定或尚未解决的具体问题，不机械重跑全部检查。

Bug、重构、维护与实验

返回手册 · 相关：Feature 开发流程、故障排查

本页用于将问题归入需求变更、Bug、重构、维护或实验。分类依据是实际预期与授权范围；工程任务仍写入同一份 Feature 索引和详情，由现有执行流程交付。

按实际目标选择路线

情况 路线 应说明的结果
预期行为缺失、矛盾，或用户想改变它 product-change-standardizer 新的 Product 意图与验收条件
已有明确预期，代码没有做到 engineering-change-standardizer 的 bug 模式 恢复预期并覆盖回归
外部行为保持不变，调整内部结构 同上，refactor 模式 真实维护收益与行为保持证据
工具、构建、依赖、日志、测试设施或数据迁移 同上，maintenance 模式 技术成功条件、兼容边界与验证
只想知道架构有什么问题 只读调查 有证据的发现、优先级和建议，不自动改文件
明确验证一个玩法或技术假设 限定范围的实验 假设、观察、结论和实验文件处置

工程 Feature 在详情中以 engineering_change 标明模式，不另建任务系统。

Bug 先查归属，再查根因

当前未完成 Feature 内的缺陷，优先在当前范围中修复。已完成行为中的独立缺陷才按独立 Bug 工作组织。新问题若来自不明确或改变中的需求，应回到 Product，而不是先修代码再补理由。

诊断至少让人看懂：实际发生什么、原本应发生什么、预期依据在哪里，以及最短复现步骤。根因未确认时明确保留未知；不能把最先想到的解释当成已证实事实。

需要保存诊断时，Agent 在 bug_diagnosis 中记录实际行为、预期、来源、复现方法和根因。将 Feature 标记为完成前，已有 Bug 诊断记录必须包含已确认的根因；字段定义见 Feature 规范。

适合自动验证的 Bug 建立 F0XX-RTyy 回归测试。无法合理自动化时，说明具体原因并给出可重复的人工回归路径。回归关注原始触发条件和错误结果，不仅证明修复后的某条代码执行过。

Bug 成功验证并完成适用验收后，Stage 5.5 将根因、触发条件、回归覆盖和防范原则保存在当前 Feature notes。通用建议先核对已有规则，只有值得复用且获得明确授权时才提升为 Coding Rule 或不变量；不要把每个缺陷都变成新规则。

重构应解释实际收益

重构提案从已经观察到的维护困难或下一项确定需求出发，例如同一业务规则需要在多处同步、调用顺序分散、对象生命周期难以判断。验收既要证明行为保持，也要能解释改后为什么更容易修改。

可用一个检查问题帮助判断：移除某层后，调用者是否更简单？若移除只是把校验、错误处理、状态归属和生命周期知识散到各处，这些职责仍需有清楚的位置。文件数量减少、类名变短、评分提高都不足以单独证明改进。

pick-refactor-smell 在用户指定的 Feature 范围内读取 notes，按需追查代码、历史和依赖；没有记录不先创建计划。它保持只读，不改写历史 notes。

判断 处理
问题已解决或被后续工作替代 排除候选；同一根因合并论证并保留来源
当前问题成立 比较不处理的影响、最小完整改法、修改风险和验证成本；文件数、关键词与引用次数只作线索
现在有足够收益 推荐一项并说明优先理由，不计算分数或新增排序台账
收益不足或证据不明 分别说明暂缓或待核实；无有效候选时结束，不写成已解决
行为违背已接受契约 回到工程标准化入口判断 Bug 归属，不以重构名义改变预期

例如，阻碍下一项已确定功能且修正范围清楚的问题，可以先于大范围普通命名整理。独立架构调查也可直接分析代码与已有决定，无需制造 smell 记录。选出候选不自动授权实现，已有具体授权继续有效；判断依据见 架构约定。

工程维护如何确定边界

维护类型 应先核对的内容 可观察的成功条件示例
项目工具修复 实际错误、入口参数、输出与调用 Skill 原始触发命令给出正确结果，相关失败边界仍有效
插件或依赖调整 项目使用方式、本地补丁、许可证和实际目标引擎 所需行为在配置的引擎中得到验证
性能处理 复现条件、当前测量、热点和行为约束 在相同有意义条件下改善指标并保持行为
存档或数据迁移 数据归属、已有格式、受影响版本、恢复方式 新旧边界按批准方案处理，失败能够辨认和恢复
素材替换 需求是否变化、引用与导入设置、授权来源 实际场景资源可用，并完成适用的视觉或听觉验收
测试或 lint 配置调整 规则意图、真实误报或适用边界 解决真实问题，同时保留仍需检出的错误

表中的成功条件是提案思路，不是已批准任务。维护是否需要全量测试取决于实际影响；maintenance 标签本身不会触发全量。项目工具已由生成项目拥有，可以在明确授权下修复，不依赖框架先发布新版本。

原型与技术实验

当用户明确要求验证假设时，先界定一个问题、允许修改和运行的范围、时间或尝试预算，以及保留还是移除实验文件。独立实验可以不建立完整 Product/Feature 链；已有 Feature 内的实验继续遵守其任务边界。

例如验证一种拖拽操作是否容易误触，可以保留实验场景、输入条件和观察结果。观察到“某参数更顺手”仍是实验结论，不会自动变成已批准的正式数值需求。

实验的假设、结果、决定和文件处置写入当前 Feature notes；没有 Feature 时写入当前 Progress。采纳结果进入正式开发时，再回到 Product 或工程变更入口。超出实验预算或范围需要用户决定。

调查结果如何进入执行

工程标准化负责诊断、分类、提出工作项，并在相应授权下写入任务。规划时，Agent 读取测试登记表，区分复用组件与本次新增组件；批准后先使用现有组件合并入口登记缺少的组件，再写任务并运行台账检查。没有单元套件就用 unit_test_paths: []，不创建虚假路径；已有组件和测试保留，同名不同定义须明确处理。

新增组件与任务一同提交，具体测试映射仍在执行阶段确定。execute-next-feature 负责实现、验证、适用验收、用户指定的可选评审和交接。用户已对具体工作给出的授权持续有效，后续不重复询问同一批准。

复盘中发现的另一项工具问题或跨模块改进，不顺手塞进当前修复。保留证据和建议，按用户决定进入下一项工作。

项目知识、架构与交接

返回手册 · 相关：目录参考、工程变更

中断后继续任务时，你需要知道做到哪里、还缺什么、下一步是否已获授权。Agent 用 Progress 交代当前停点，用任务历史保留执行经过；值得复用的经验再进入知识目录。以下先说明续接，再介绍其他记录的使用时机。

Progress 如何帮助继续任务

当前 Progress 只需清楚记录：活动 Feature 或获批批次、真实阶段、阻塞、待决定事项、下一步，以及计划和报告链接。不能从“下一步实施”这句话推断用户已经批准。

任务完成后将执行历史归档一份到 docs/progress/<key>.md，保留原文和证据链接；已有归档先读取，不能覆盖或重复复制。未解决问题仍留在当前交接中。移动历史不要求翻译原文，新写的项目知识遵循 document_language。

接手时按 Progress → 当前 Feature → 相关历史/证据 → 实际差异的顺序读取，核对已有授权和现在的代码。历史完成与当前内容是否重新验证是不同事实；后续迁移不应伪造过去曾做过的检查。

换到新线程继续

对话过长、经过多次压缩，或需要换一个任务继续时，可以让原线程先生成交接提示词。按实际需要使用，不设置必须换线程的压缩次数。

  1. 在原线程发送提示词库中“Godot 项目开发 → 验证与收尾 → 整理进度与任务交接”，填入当前任务与用途。Agent 只整理必要的现有 Progress/历史，并生成一个完整的交接代码块。
  2. 检查输出是否包含原始目标与最新要求、实际项目/worktree 路径、当前分支、修改归属、真实停点、已有授权、实际检查和下一步。交接内容应当已经填好具体信息；未知事项保留为未知。
  3. 在同一个实际项目目录或原 worktree 中打开新任务，把整个代码块复制过去。复制的是原线程生成的结果；库中的提示词用于让原线程整理上下文。原线程输出后停止实施，避免两边继续改同一份文件。
  4. 新线程先读取项目规则、相关记录与实际差异，确认原任务现场后，从真实阶段继续。已有具体授权仍然有效；未取得的人工验收、未运行的检查和失效的旧结果仍须如实处理。

交接内容还应区分会话中仍有效的协作原则、当前步骤限制与已被后续明确要求替代的旧限制。生成交接文本这一步的文档整理或只读范围、代码块输出和停止约定，不作为接收方后续任务的永久限制；原任务仍有效的范围继续保留。

交接摘要帮助定位事实，项目原文和实际文件仍需核对。无需为了换线程提交未完成代码、清空工作区、另开分支、重建台账或重跑所有检查；未提交修改按项目规则确认归属并保留。若原线程仍有命令运行，交接写明已知状态，新线程先确认是否结束及结果是否可用，再继续相关操作。

框架维护中的未完成任务使用“Yaya 框架维护 → 维护与复盘 → 生成新线程交接提示词”。该入口只读仓库与会话，保留框架和具体游戏的职责边界，不建立维护 Progress 或交接状态文件。两类正式提示词都只维护在 提示词库，这里不复制正文，也不自动创建或投递新任务。

每条独立经验使用单独的 Markdown 文件，索引只放链接与简短说明。实际内容需要时可增加游戏模块或更细子目录；不按每个 Feature 机械建文件夹，也不把一条经验复制到多个主题。

Agent 开始规划、调查、开发、调试或复审时，先确认当前任务与规则，再从知识总索引定位相关主题和条目。可按模块、现象、API 或工具缩小范围；继续原任务时复用仍有效的已读内容，无需通读整个知识库。相关分类为空时，仍可继续工作。

采用已有经验前，Agent 核对版本、场景和证据是否适用于当前任务。知识条目提供参考，不能覆盖用户意图、Product、已接受决定或工程规则。完成核对后再拟定方案，必要时补查外部资料。

经验正文保存场景、有效做法或根因、适用范围和真实依据。成功做法说明观察到的收益与限制，不必编造“根因”；有项目独有条件的做法也可以保留。版本和平台影响结论时明确记录，疑点标为未确认，不把一次运行现象当成通用引擎事实。

经验写在哪里？ Agent 先检查已有条目，再更新或新增有价值的知识与最近一级索引。Feature notes 保留原事件和局部决定，知识条目提炼适用做法并链接原件；技术决定与工程约束仍分别由 ADR 和规则负责。

何时写入？ 在已授权任务的文档整理中完成。Feature 相关知识在 Stage 7 提交前落盘，Stage 8 汇报链接；只读或讨论任务不会因此取得写入授权。

改后检查什么？ Agent 核对事实、适用条件与来源链接。纯知识 Markdown 不使业务测试证据失效；代码、测试或契约变化仍需验证。

没有新知识就不新增条目。目录只链接实际运行脚本、数据或报告原件，维护沿用现有任务流程。现有经验已经不适用时明确修正适用条件，跨项目吸收和规则升级仍按原授权处理。

何时维护 CONTEXT

当同一项目中的概念需要反复解释，或在不同模块、Feature 中出现同名异义、异名同义时，使用 project-clarifier 通过具体情景澄清。需要保存的已确认定义由 product-change-standardizer 按授权写入 docs/CONTEXT.md；缺少该文件不阻塞讨论或开发，也不预先放一个空模板。

文件只需简短背景、术语名称和一两句话的定义，按需说明概念关系、别名或易混淆项。例如区分“物品定义”“持有物品”“堆叠”，随后链接到 Product 的实际堆叠规则。已有定义直接复用，移入 CONTEXT 时将范围内的重复定义改为链接。

详细行为、数值和状态转换由 Product 负责；实现状态归属和技术取舍由架构文档负责；待定想法、聊天记录和当前进度不放在 CONTEXT。仅保持含义的术语维护不会触发完整 Product 初始化或 Feature 拆分；实质行为变化仍走需求变更。规范与格式见 项目术语约定。

何时需要架构地图

当仅从源码已经难以看清模块职责、状态归属和依赖方向时，建立 docs/architecture.md。复杂子系统展开到单独文件，总览保持可浏览。

地图应指向实际模块，解释谁拥有状态、谁可以调用谁，以及为什么这样划分。需要说明运行过程时，在子系统文档记录触发、参与者、状态变化、结果、Godot 生命周期和失败处理。使用 flowchart 展示依赖，用 sequenceDiagram 展示交互顺序，用 stateDiagram-v2 展示真实状态转换；只画能帮助读者判断的内容。

生成的引用关系只说明解析器看到了什么。动态加载、运行时 Signal 和状态归属不能仅靠文本搜索确定。观察、推断、提议和已实现行为要区分，图表也不是依赖设计的自动批准。

何时使用 ADR

某项技术选择跨多个 Feature、长期约束项目或代价较高时，可建立 ADR。记录问题、约束、候选方案、决定、收益、接受的成本、依据和有用的重新考虑条件。普通局部选择保留在 Feature notes 即可。

这些是普通 Markdown 状态，不需要注册表。Accepted 说明决定得到确认，不证明相关 API 或运行行为已经测试；Superseded 保留旧理由并链接替代 ADR。真实任务已经确认的决定直接沿用，不额外增加一轮批准。

架构地图保存当前结构，ADR 保存跨任务理由，Feature notes 保存局部决定，Progress 保存当前链接。按需更新边界变化，不为每次改函数写 ADR，也不把缺少可选地图当成门禁失败。

资源、数据与占位内容

空白项目不指定业务素材目录。资源文件按游戏模块与实际资产流程组织，修改前核对源文件、运行资源、导入信息和生成缓存的归属。

占位内容使用 _placeholder_ 前缀，并在当前 Feature notes 说明用途、替换方式和未完成的验收。替换素材时核对引用、UID/路径与实际场景；外观、声音、动画和手感仍按需求保留人工验收。

数据格式改变时核对已有内容和加载方，再决定版本、迁移与兼容范围。资产来源和许可证按现有规则记录。工具生成的输出不应成为可复用脚本或重要项目决定的唯一副本。

报告保留与清理

当前验证、人工验收、未解决失败或后续工作需要的报告继续保留。默认报告不进入 Git，因此代码提交不保证另一台机器拥有报告原件。需要跨目录或跨机器交接时说明实际可用证据，缺失原件不能靠提交说明补成通过。

清理报告是明确的维护动作：读取拟处理目录和当前引用，只清理已理解且获授权的输出。目录较旧、后面有成功运行、文件未被 Git 跟踪，都不自动授权删除。测试运行器不会自动清理旧报告，也不需要额外的保留登记表。

依据：历史与报告规范、架构与 ADR 规范。

复制并迁移旧框架项目

返回手册 · 创建空白项目

已有旧项目时阅读本章。 新建项目直接进入 需求与规划；只有外部 GDD、尚无旧实现和任务时，使用 GDD 接入说明。

已有代码、Product、Feature 或进行中任务的旧项目，使用 集中提示词 中的“Godot 项目开发 → 项目初始化 → 复制并迁移旧框架项目”。这是由 Agent 按具体方案完成的一次性接入，创建器仍只负责空白复制。

输入与执行位置

填写原项目、当前框架、新目标、本次授权范围以及 Git/数据选择。目标须在两个输入之外、互不包含、不属于其他仓库且不存在或为空，完整路径不含中文或空白；用户也可明确允许 Agent 自行选择。

默认先只读分析，再讨论方案。已有具体实施授权时，Agent 展示方案后继续完成获选范围，不逐文件重复确认。编写或阅读提示词本身不会启动迁移。

原项目继续保存在原位置。“不迁移”表示不纳入目标，原件不删除；验证的配置、存档和输出也应与原项目及共享用户数据隔离。所有运行和 Git 写入仅在目标进行，不能通过链接、worktree 或共享对象把写入引回原件。

成果与框架材料如何处理

对象 使用者应预期的结果
当前工作区 包含应保留的未提交、未跟踪和忽略文件；恢复历史后仍落实当前删除，不只复制最后一次提交
业务实现与资源 保留有效代码、场景、测试、UID、导入设置及许可；不因框架迁移重做功能
纯框架材料 采用当前版本，先识别项目定制；旧自动监督和废弃状态不继续作为活动入口
混合配置与规则 保留游戏设置和有效项目约束，合并当前工具契约，避免被空白默认值覆盖
活动需求与任务 保留语义、编号、依赖和完成事实，转换全部被当前索引读取的必要格式
历史材料 当前续接或追查需要的材料可选择性复制；其余留在原项目，不要求全量改写旧文档

对应关系根据职责、内容和实际读写方确定。同名文件可能采用不同格式，改名也可能同时涉及结构和配置变化。现行格式以 Feature 与测试登记规范 为准，提示词不提供长期旧格式兼容层。

默认保留当前分支的可达 Git 历史，并把实际工作区成果纳入独立目标；不照搬原仓库管理目录、Hook 或 worktree 关联，不配置远程。目标的输入基线提交只表示保存成果，不代表原有未完成任务已通过验收。选择新 Git 历史时，报告说明旧提交的追查限制。

状态、验证与交接

已完成的 Feature 保留历史完成事实；进行中的 Feature 保留真实停点，不重演从零开发，也不自动转为完成。无法确认的历史字段如实说明，不能用迁移时间或本次测试补造过去的完成、批准和验收。

旧测试记录不能当作当前运行结果。根据迁移影响执行环境、台账、解析/lint 及真实测试；跨工具和大量引用的迁移通常需要一次完整现有业务回归，同次运行已覆盖的子集无需重复。现有 UI、音频或手感工作尚待人工验收时，迁移通过仍不代表业务验收完成。

目标的 reports/framework-migration.md 保存一次性迁移报告，现有 Progress 指向报告并说明真实下一步；已有同名报告未获覆盖授权时使用不冲突名称。报告区分实际通过、失败、未执行、历史记录及来源未变核对，不额外建立同步台账。目标 README、规则和工具继续描述项目自身使用，维护手册与提示词库不进入目标项目。

迁移完成后停止，再由用户决定是否续接原任务。完整开发流程仍使用 Feature 开发说明，框架不会自动更新这个项目。

路径与命令的写法

以下是配置片段示例，不是可覆盖整个配置文件的 ready 配置；其中 Godot 路径必须换成该项目已经确认的值：

json
{
  "python_executable": "C:\\Users\\89523\\anaconda3\\envs\\codex-python\\python.exe",
  "test_cmd": "\"C:\\Users\\89523\\anaconda3\\envs\\codex-python\\python.exe\" -B tools/testing/run-gdunit-tests.py --godot-binary \"C:\\Godot\\Godot.exe\""
}

JSON 中反斜杠写成 \\，命令内的双引号写成 \"。路径字段本身不需要额外嵌入引号：带空格的可执行文件路径仍是完整的一个值。不能把 $env:...、& 或 --version 当作可执行文件路径的一部分。

PowerShell 直接调用路径变量时使用调用运算符，并把参数分开传入：

powershell
$projectConfig = Get-Content -LiteralPath 'docs/methodology-config.json' -Raw | ConvertFrom-Json
$projectPython = $projectConfig.python_executable
$projectGodot = $projectConfig.environment_bootstrap.engine_executable
& $projectPython -B tools/checks/check-project-environment.py --require-ready
$LASTEXITCODE

test_cmd 是一整条命令文本，不能用 & $projectConfig.test_cmd 把它当作一个可执行文件名。日常调用可按已确认命令展开为独立参数，示例见 命令参考。

Godot 的 engine_executable 必须是实际文件路径，可以是绝对路径，也可以相对项目根目录；环境检查和测试运行器使用同一解析方式，不去 PATH 寻找同名安装。python_executable 仍支持完整路径或 PATH 中的命令名。路径字段不含额外 shell 引号或参数，带空格和非 ASCII 字符的完整工具路径可保留。

项目输出目录禁止中文或空白，与工具路径字段能否包含空格是两个不同约束。不要把创建器的目录限制误套到所有配置字符串上。

文档语言

document_language 控制新生成的 Product、Feature 自然语言、Progress 和项目知识。zh-CN 与 en 是当前规范明确给出示例的语言；其他合规语言标签按现有规范处理，不扩展验证声明。

环境检查器会检查基本字符和分段形式，拒绝 zh_CN、包含空白、空子段或子段超过八个字符等输入，并保留原值的大小写。它不验证完整 BCP 47 子段顺序或注册信息，也不代替用户确认；特殊标签的合法性和使用选择仍由 Agent 按语言规范核对。

JSON 键、Feature ID、pending 等状态、manual 等枚举、文件路径、Skill 名称、命令和测试 ID 保持不变。聊天换语言不会自动翻译项目。修改已建立的文档语言需要核对活动文档、标题锚点和历史范围；只改一个配置字段不等于完成迁移。

复制阶段不会把英文模板翻译成中文。后续生成内容遵循已确认的语言与模板结构，不删除不适用章节来缩短模板，也不建立平行的翻译版 Skill 树。详见 文档语言约定。

用户发送的任务提示词可以使用当前会话语言；其产出的持久项目内容仍遵循 document_language，不因此翻译工作流规范或 Skill。

这份手册不承诺所有 Agent 客户端都以相同方式自动加载 Skill；目标项目的实际文件与当前客户端行为需要分别确认。

命令、测试范围与结果解释

返回手册 · 相关：配置参考、故障排查

所有项目命令在生成后的项目根目录运行。按当前任务调用所需入口，以下命令参考不意味着每次都要整页执行。涉及写记录的命令遵循对应 Skill 和已有授权。

调用准备

先确认项目配置已经就绪。本页 PowerShell 示例共用以下变量：

powershell
$projectConfig = Get-Content -LiteralPath 'docs/methodology-config.json' -Raw | ConvertFrom-Json
$projectPython = $projectConfig.python_executable
$projectGodot = $projectConfig.environment_bootstrap.engine_executable

在本机，python_executable 应是个人规则指定并已确认的完整解释器路径。F001 和示例脚本路径都需换成实际存在的任务与文件。每条原生命令后立即读取 $LASTEXITCODE；缺失退出码不能当作 0。

新项目首次 CLI 测试或项目脚本运行前，按 首次扫描说明 处理编辑器准备；配置 ready 不代替这次扫描。

入口与副作用

入口 常用参数 行为
tools/checks/check-project-environment.py --require-ready、--config 读配置；就绪检查可能启动 Godot --version，不写配置
tools/checks/check-feature-list.py --eligible、--completion-feature F001、--repo-root 读 Feature/测试登记表/历史和依赖，不修改台账、不运行测试
tools/testing/run-gdunit-tests.py --godot-binary、--feature 或 --target、--phase、--scope 启动真实 Godot 测试进程，写隔离的运行目录
.agents/skills/execute-next-feature/scripts/record-feature-completion.py 子命令与 --feature；全局 --repo-root 在子命令之前 写入测试/人工记录，或只读展示、校验已有依据
.agents/skills/generate-feature-list/scripts/merge_test_registry.py --components 在项目根目录运行，将批准的组件合并到固定的 docs/test-registry.json；属于规划写操作

测试登记表合并应使用 generate-feature-list 提供的实际输入结构与约束，不用临时生成的空文件替代历史测试登记表。它不负责生成真实测试或证明测试通过。

环境与台账检查

powershell
& $projectPython -B tools/checks/check-project-environment.py --require-ready
$LASTEXITCODE
& $projectPython -B tools/checks/check-feature-list.py
$LASTEXITCODE
& $projectPython -B tools/checks/check-feature-list.py --eligible
$LASTEXITCODE

就绪检查细节见 首次使用。台账检查读取完整索引、详情、测试登记表和修订关系，检查 ID、字段、引用、路径、依赖与历史规则。--eligible 校验后输出依赖已满足的 pending Feature ID 集合，不能代替实现授权。

规划或同步完成后使用这个完整入口即可，它已经包含 JSON 解析；单文件语法检查只用于定位具体错误。Agent 仍需核对需求覆盖、真实依赖和历史保留，这些语义不能由结构检查代替。

--completion-feature F001 额外要求当前待完成任务的直接自动验证映射处于 active 状态。正常历史检查可以接受可追溯退役的旧测试；当前完成不能拿已退役测试替代实际验证。

三种常见测试调用

在已经批准的任务范围内，按用途选用：

powershell
# Stage 3：已有安全网，不包含尚未创建的 planned 测试。
& $projectPython -B tools/testing/run-gdunit-tests.py --godot-binary $projectGodot --feature F001 --phase baseline --scope auto
$LASTEXITCODE
powershell
# TDD 或定点诊断：替换成实际已存在的套件或目录。
& $projectPython -B tools/testing/run-gdunit-tests.py --godot-binary $projectGodot --target tests/features/F001/example_test.gd
$LASTEXITCODE
powershell
# Stage 4：读取当前 Feature/测试登记表和已批准范围。
& $projectPython -B tools/testing/run-gdunit-tests.py --godot-binary $projectGodot --feature F001 --scope auto
$LASTEXITCODE

--feature 与 --target 互斥；两者都不传时 target 默认为 tests。--phase 支持 baseline、final，默认 final。baseline 和 focused/target 运行用于基线或调试，不能直接作为当前 Feature 完成依据。

其他参数：--timeout-seconds 默认 120，必须是大于 0 的有限数；--require-test 使用 <suite-path>::<test-case> 格式，要求原始报告确实覆盖该用例；--continue 传给 gdUnit 的 -c，不表示继续一个已有 Yaya 任务或复用上次报告。

运行器启动真实引擎和测试，而非纯文件检查。所需权限、窗口行为与运行范围按当前项目和任务确认；不能因为名字含“测试”就认为无副作用。

测试范围怎样计算

Stage 1 的完整测试范围规则见测试规范中的 Test Impact Review 与 Runtime Test Impact selection。下文用中文说明 Required、affected、full 与命令的对应关系。

text
Required Test Set =
  当前 Feature 的自动验收测试
  + 当前 Feature 的回归测试
  + 影响组件已登记的 unit_test_paths
  + 与影响组件相交的 active 历史回归
  + 与影响组件相交的 active 不变量
  + 已批准的 additional_tests

affected = Required + 与影响组件相交的 active 验收测试
--scope 用途
auto 默认执行 affected；当前计划需要全量时升级为 full
required 显式运行 Required，适合局部迭代；不能据此绕过最终 affected/full 要求
affected Required 加相关验收测试
full 运行配置的现有测试根目录范围，并核对必需覆盖

影响组件设有 full_suite_on_change、已批准的 full_suite_reasons、广泛工具链影响或无法界定影响时，需要按规范执行 full；工程维护标签本身不触发升级。附加测试及理由保存在 Feature 的 verification.test_impact，没有独立计划文件。

没有单元套件的组件使用 unit_test_paths: []，不产生虚构选择器。已登记路径丢失、被选中目录零测试、必需用例跳过或报告缺失都不能记为通过。不存在且未登记的测试层不会贡献全量选择器；这不把空项目变成有成功测试证据的项目。

一次运行留下什么

每次调用创建 reports/gdunit-wrapper/run-<id>/，输出真实 result.json 路径。使用命令打印的路径，不猜测 run ID 或报告文件夹编号。

text
reports/gdunit-wrapper/run-<id>/
├── result.json                 同一个文件从运行中更新为成功或失败
├── engine.log                  原始引擎输出
├── discovery.json              实际展开后的测试发现集合
└── report_<...>/
    ├── results.xml             原始 JUnit
    └── diagnostics.jsonl       运行诊断

启动或中途失败时，部分原件可能尚未产生；缺失本身就是要读取的结果，不应补造空报告。实际报告还可能包含 gdUnit 生成的其他文件。

运行器核对过程结果、实际发现集合、JUnit 用例和诊断。参数化用例需要对应真实展开后的集合，源码里存在 test_* 方法不证明它实际执行。JUnit 看起来成功也不能遮住引擎错误或未完成运行。

同一内容上的较新失败需要由之后覆盖该失败范围的成功解决；更早成功或更窄的通过不能盖掉它。保留原始失败，再说明修复与后续结果。

记录完成依据

完成依据入口位于执行 Skill 的 scripts/。下表是参数速查，不是让使用者批量填“通过”的步骤：

子命令 何时使用
initialize --feature F001 Stage 2 初始化当前 Feature 依据；会写入当前记录，不作为失败恢复按钮
record-tests --feature F001 --run <result.json> 导入真实 final Feature 运行；必要时重复 --run 覆盖不同运行
prepare-manual --feature F001 --checklist <清单.json> 检查 Agent 编写的 pending 清单并绑定最终内容；已绑定清单不能重新绑定
record-acceptance --feature F001 --checklist <清单.json> --result <结果.json> 读取用户真实结果，与原清单和当前内容对照；记录 accepted、rejected 或 pending
record-acceptance --feature F001 --status accepted manual 模式下，用户已经明确接受当前范围之后
record-acceptance --feature F001 --status rejected 记录真实拒绝与后续修复需要
show --feature F001 只读查看已有记录
validate --feature F001 检查当前内容对应的完成依据

人工文件均保留在 reports/manual-acceptance/，输入/结果格式和命令示例见 人工验收文件契约。--result 与 --checklist 配对，不能与口头决定的 --status 混用。有效全通过结果本身就是该范围的人工接受；注释存在实质矛盾时先澄清。命令退出 0 表示成功记录实际状态，pending、rejected 仍不能完成。无效导入退出非零且保留已有记录，Agent 必须处理本次错误，不能退回旧接受绕过。

真实报告导入示例：

powershell
& $projectPython -B .agents/skills/execute-next-feature/scripts/record-feature-completion.py record-tests --feature F001 --run reports/gdunit-wrapper/run-actual-id/result.json
$LASTEXITCODE

把 run-actual-id 换成刚才输出的目录。原件引用和当前内容绑定用于发现错误复用；脚本不接受手填通过次数来创建成功。record-tests 失败会清除旧测试引用并保留原始报告，不能改写结果文件绕过失败。

若有效 manual 计划的 Required、affected 都为空且不要求全量测试，省略自动运行和 record-tests，保留 initialize 生成的 test_runs: []。后续仍按真实结果记录人工接受，再运行完成检查；工具从当前计划计算 not_required，不生成空的成功报告。任何自动测试义务、无效映射或当前内容上的未解决失败都会阻止这个分支，不能用重新初始化消除失败。

完成依据保存测试原件引用与适用的人工决定，新任务按当前模板初始化。独立评审的范围和时机由用户选择；遇到旧命令或旧记录时，查阅 故障排查。

完成检查由两部分配合，Agent 还要单独确认直接静态检查与用户指定的评审条件：

powershell
& $projectPython -B .agents/skills/execute-next-feature/scripts/record-feature-completion.py validate --feature F001
$LASTEXITCODE
& $projectPython -B tools/checks/check-feature-list.py --completion-feature F001
$LASTEXITCODE

生产代码、测试、配置、AC、验证计划和测试登记表等语义内容改变时需要核对依据是否失效；仅改完成时间、notes、整理 Progress 历史、知识 Markdown 或普通使用 README.md 不自动要求业务测试重跑。例如，在业务测试通过后补充场景 README，可继续使用同一份有效结果，同时检查说明中的事实、链接和示例。

这不等于排除所有 Markdown：规则、Skill、流程、Product 和 Feature 契约目录中的 README 仍参与验证，知识目录中的非 Markdown 文件也仍参与。使用说明不承载正式需求、规则或可执行输入；确切目录与绑定语义见 测试规范。

直接脚本解析与 lint

从项目根目录，使用同一个已确认 Godot 可执行文件：

powershell
# 替换成实际变更脚本，并按影响解析必要依赖。
& $projectGodot --headless --path . --check-only --script res://path/to/changed_script.gd | Out-Host
$LASTEXITCODE
powershell
# 每次选用不会覆盖仍需保留原件的报告名称。
& $projectGodot --headless --path . --script res://addons/gdscript-linter/analyzer/analyze-cli.gd -- --json --output reports/lint-current.json res:// | Out-Host
$LASTEXITCODE

对 Windows GUI 可执行文件，Out-Host 管道用于等待进程，立即检查退出码。lint 扫描完整 res:// 并遵循项目配置；修改了被默认排除的依赖时，仍需验证该依赖变更本身。

当前 lint CLI 的退出码：0 表示无问题或仅 Info，1 表示 Warning，2 表示 Critical，3 表示输入无效、空发现、配置错误或 JSON 报告写入失败。--severity 和 --top 只影响显示，不会抹去真实判定。--output 支持 JSON 和 HTML 文件；默认文件名 code_quality_report.html 仅用于 HTML。报告真实范围与 Critical/Warning/Info 数量，未知数量不能写成零。

解析证明脚本在实际引擎中的相关语法/类型契约，lint 检查配置的质量规则；两者都不替代运行、资源、场景、导出或人工质量判断。需要编辑器检查时遵循本机项目规则的沙箱外审批路径。普通 Feature 不增加单独导入阶段。

退出码和结果边界

环境与台账检查成功通常为 0、校验失败为 2；gdUnit 包装器成功为 0、运行失败为 1，参数解析错误可为 2。最终结论仍结合原始输出和检查范围，不能将不同工具的非零值统一解释为业务测试失败。

已有结果 可以报告 不应推断
配置就绪 实际环境检查通过 游戏或测试通过
台账通过 数据结构、引用和依赖满足该检查 AC 已实现
focused 通过 指定套件在本次运行成功 最终 Required/affected/full 已满足
完成依据校验通过 它负责的测试与适用人工接受契约满足 脚本解析、lint、独立评审或所有目标平台已检查
静态检查通过 已执行静态范围通过 手感、外观、声音和导出质量已接受

JUnit 通过但包装器失败 同时检查 discovery、diagnostics、引擎日志和进程结果；不要只读绿色计数

超时 读取超时和进程结果，判断卡住或必要运行时长；调整超时要有真实依据

record-tests 拒绝导入 核对 Feature、final 阶段、scope、当前源码绑定、原件和真实覆盖

整理历史后担心必须重跑 纯 Progress 历史整理不自动失效；核对是否同时修改了语义内容

manual 没有 accepted 需要用户针对实际检查作出决定；实现批准和自动测试不能替代

lint、静态检查和资源问题

lint 的 Warning、Critical、输入错误与仅 Info 有不同退出码。先看准确位置、当前配置和源代码，再判断是实现问题、词法检查边界还是明确的引擎接口契约。行数警告不自动要求拆文件，Info 也不表示每个数字都必须提取常量。

静态解析遇到资源或缓存问题时保留原始错误，核对当前项目准备情况。导入、解析、lint、真实场景和导出分别验证不同内容；其中一项通过不抵消另一项必要检查失败。被默认排除的插件发生修改时，仍需对修改本身验证。

本仓库 linter 有本地补丁，诊断与上游示例不完全一致时先读 YAYA_PATCH.md，不要直接覆盖插件文件。

运行退出时的 StringName 诊断

verbose 日志出现 Orphan StringName 或 Unclaimed StringNames 时，结合原始上下文、进程退出码、实际行为和其他诊断判断，不能仅凭这类文字认定业务对象泄漏。

需要定位时，在已有运行授权内使用相同 Godot 版本和启动参数，以不加载业务代码的最小入口作对照。两者出现相同记录只能说明尚不能归因于当前业务逻辑，不能直接确认引擎根因；退出码为 0 也不能证明没有泄漏。依据不足时保留未知结论，不屏蔽诊断或改写为“已修复”；已定位的资源释放问题仍按其实际原因处理。

哪些结论应明确保留为未知

没有运行的测试、没有启动的场景、没有观察的声音和画面、没有执行的导出，以及缺失原件的历史结果，均说明实际未验证范围。若缺少的检查对当前任务必要，报告原因和剩余事项；若不在本次范围内，也不扩展成新的自动流程。

内容完整与定位稳定 导航过滤、视觉换行和图表变换只影响呈现；正文仍可全文查找，复制保持原始代码。阅读位置引用实际锚点，锚点失效或浏览器拒绝保存时正常降级，不依赖旧像素位置或另建阅读台账。

按风险核对成果 导航、弹窗、缩放、字号和恢复机制改变时，检查它们之间的衔接与原始内容保留，不只看单个控件。验证服从本次授权，未做浏览器排版或真实交互检查时明确保留该限制。

按需验证 核对变更与相关说明，报告实际检查结果和过期步骤、路径、参数或结果解释；不顺手修改手册
新线程交接 只读相关说明，将手册入口、本页和受影响专题写入交接阅读清单，指出尚待同步之处；本次交接不改文件

读取维护说明不会扩大提示词的实施授权。后续修复、运行检查和提交仍按当前用户范围与根规则处理；已生成项目中的开发任务读取项目自身文档，不新增对框架手册的依赖。

整体重检与详细报告

框架持续更新后需要重新检查时，选择“Yaya 框架维护 → 维护与复盘 → 复盘框架设计与场景”。它默认覆盖整个框架和全部空白项目源材料，也保留只复盘某个模块或变更的用法。无需再发送一组分散的检查提示词。

输入 使用方式
检查范围 整体检查时保留默认范围；局部检查时写明模块、变更与关注点，报告会标明范围边界
对照基线 可填写相关提交或旧报告路径；没有则填“无”。基线用于比较，旧通过记录不代表当前版本已验证
报告输出 默认在对话中输出详细 Markdown；需要文件时填写 framework/ 内路径，例如 framework/review/reports/2026-09-12-framework-review.md

报告应说明当前 Git 与文件状态、实际阅读范围、检查方法、问题依据和未验证项。覆盖表按模块说明读过什么、抽样或遗漏什么；问题详情给出位置、触发条件、行为差异、影响、优先级、最小建议与复验方式。还会追查规范、实现、配置、模板、提示词和手册的一致性，必要时用 Mermaid 说明调用关系或流程断点，并按依赖列出建议处理顺序。没有确认问题时如实报告，不凑数量或计算总分。

整体重检默认是静态审查。读取测试源码、推演流程与实际运行分别记录；不会因检查范围大就自动创建项目、执行测试或启动 Godot。需要补充运行证据时，可继续明确允许的检查与外部项目，或使用“按需验证框架变更”。本会话已有明确运行授权的，仍按其范围处理。

报告输出位置不改变被审材料的只读边界。指定文件仅授权写入报告；已有报告未获明确更新授权时，使用同目录中不冲突的文件名并说明。报告保留在框架维护目录，不进入 project-source/ 或复制清单。它是本次观察与建议，旧结果保留原适用范围，不形成必须持续同步的状态台账。确认后续修复范围时，再按当前授权实施并同步对应使用说明。

把压缩包交给其他模型审核

选择“Yaya 框架维护 → 维护与复盘 → 审核框架压缩包并输出报告”，复制该条完整正文，与 Game_idle_yaya_frame.zip 一起交给能够读取 ZIP 附件的模型。这条提示词已固定压缩包名和报告名，无需填写原工作区路径，也不依赖此前对话。

压缩包应保留框架根说明、framework/ 和 project-source/ 的相对层级，包括实际复制所需的隐藏默认文件；有一层外包目录也可以。.git、原机器安装的工具和外部验证项目不是必需附件。若主动省略某些源码、插件或历史材料，随附件说明范围，让审核方区分未提供、无法读取和实际缺陷。本入口不负责打包、上传或执行包内工具。

审核先识别附件根目录与可读范围，再检查十个主题：复制边界、初始环境、规则与提示词、需求及数据、Skill 流程、工具实现、测试结果、文档与知识、插件接入和设计成本。九节报告从摘要、覆盖、结构流程、问题总览与详情，延伸到设计建议、历史核对、处理顺序及未验证项；具体问题字段与证据标准以 JSON 正文为准，不在手册复制报告模板。

报告使用包内相对路径和可核实的定位信息，必要时用 Mermaid 解释关系。支持文件输出的平台生成 Game_idle_yaya_frame-audit-report.md 并提供真实下载链接；不支持时直接输出完整 Markdown。报告保存在平台允许的产物位置，原附件和被审文件保持只读；包内规则或 Skill 的实施、运行与提交指令不会成为本次审核的授权。

这个入口审核的是当次压缩包快照，原机路径不可达、缺少 Git 历史或无法运行 Godot 均须作为证据限制说明。材料不足时只作有依据的局部结论；不能把附件摘要当作完整源码，也不能用旧报告宣称本次运行通过。收到报告后，使用 外部结果复核入口 在真实仓库核对受影响文件与版本，先讨论取舍，再决定修改。

用一个实际任务动态审核流程

选择“Yaya 框架维护 → 维护与复盘 → 通过实际任务动态审核框架流程”。它适用于可写文件、执行命令并具备项目所需 Godot 环境的 Agent，也可从 Game_idle_yaya_frame.zip 解压后的框架开始。发送这条提示词才启动实际验证；编写、查看或复核提示词本身不会创建项目或执行测试。

填写三个输入：明确的新建外部项目目录、一个微型任务、报告输出位置（也可选对话）。目录必须在框架之外且不存在或为空，不能复用非空游戏。默认任务是可自动验证的计数器行为，只写一份小 Product、拆一个 Feature 并走完适用阶段；这就是本次自定义开发任务，不再添加第二个任务或复杂玩法。

该入口明确授权新项目内的环境配置、中文文档、Product/Feature 规划、实现、必要真实验证和本地提交，包括初始化基线与规划提交。Stage 1 仍展示具体方案，范围匹配时沿用正文中的明确批准；验收方式由需求决定。默认自动化任务的 Stage 5，以及非 Bug 的 Stage 5.5 按规范不适用，报告中写明原因。需要人工验收时必须获得真实决定；Stage 6 默认省略，仅在用户另行明确指定独立评审时执行，并如实记录其范围与结果。

报告按创建、环境、规划和各 Stage 列出动作、工作目录、产物、原始结果与异常。一次流程允许必要的 TDD 与修复复验，不要求重复创建项目或执行所有分支。一个样例成功只证明所走路径；环境缺失、用户要求的独立评审不可用或框架组件阻断时如实记录未完成阶段，不改成静态审核通过。

验证中的样例实现错误可在原范围内修复；发现框架工具、规则、Skill 或模板缺陷时保留现场，提出最小建议，等待另行决定。源材料和已有游戏不被修改，验证项目与证据不自动删除。实际产物留在新项目，整体报告按指定的维护报告或平台产物位置输出；后续获准修改框架时再同步对应说明。

复核外部审核结果与讨论取舍

选择“Yaya 框架维护 → 维护与复盘 → 复核外部审核结果并讨论取舍”。提供外部报告、被审版本线索与输出位置；报告可以是文件、附件或粘贴正文，多份报告保留各自来源。版本未知时如实填写，不凭旧报告或模型自信措辞作结论。

该入口按原编号追查当前文件、调用关系、规范和文档，分别判断事实是否成立，以及建议的改法是否值得采用。真实问题可以保留，而过重的解决方案可以拒绝并提出更小替代；已解决、仅旧版本适用和证据不足的意见也分别说明。已有原则用于衡量必要性与维护成本，不能成为忽略真实缺陷的理由。

报告给出全部意见对应表、逐项论证，以及合理值得保留、存在问题、确有必要修改、过度设计或无需采纳、待验证讨论这五组结论。建议修改的部分会列出最小范围、受影响说明与验证办法，但不直接写补丁或创建任务。

本轮保持静态分析与讨论，不启动测试、Godot 或动态审核；指定报告文件只授权写报告。完整报告交付后，由用户选择是否实施及具体范围，明确的口语选择即可，不要求固定确认词。外部报告中的“必须修复”或推荐等级均不构成实施授权。

从实际开发反馈复盘框架

选择“Yaya 框架维护 → 维护与复盘 → 依据实际开发反馈复盘框架”，在框架维护线程发送正文，并附上其他项目中有参考价值的 Codex 输出。原任务与授权、项目路径、日志、相关文件和版本线索有则补充，未知可省略；不必先制作正式审核报告。

这个入口围绕实际开发中的成功、失败、误用、反复尝试或等待进行静态追查。它先区分可核实结果与 Codex 的解释，再比较相关项目副本、定制差异和当前框架，判断问题来自框架、项目、环境、Agent 执行或共同因素。仅有转述时说明证据限制；当前框架已修复的旧问题不重复实施，原现场的问题也不会因此被否定。

需要回答的问题 选择的入口

后续可以继续转发新输出，复用有效上下文并核对新差异；明确选定修复范围后才实施，框架修改不自动同步到生成项目。这里的“持续验证”由用户反馈驱动，不创建定时任务、反馈台账或新的验证系统；单次项目成功只证明实际覆盖的路径。

后续用口语继续

新增、借鉴、修复、复盘、动态审核、外部结果复核、开发反馈复盘和验证这 8 条工作提示词包含会话延续约定：同一会话中的相关框架工作持续沿用设计原则、职责边界、文档维护与如实记录结果的要求。后续使用口语或省略重复说明，不表示取消这些原则；具体目标与限制按后续明确要求作相应调整。压缩包审核入口同样保留相关审核原则，补发新版本时需区分附件，重新核对受影响结论。

例如，先要求只读复盘，再明确说“按你刚才的方案修改这两处”，即可在这两处的范围内转入实施，无需重新发送整份提示词。此前仍有效的目录、检查范围和提交/发布限制继续保留，涉及使用方式的改动仍需同步说明。仅问“这样改合适吗”则仍是讨论，不能视为实施授权。

原步骤要求的结论表格、只输出某种格式或交付后停止，不固定后续新请求的形式。交接时区分仍有效的原则、当前步骤限制与已被明确替代的旧要求。长期仓库规则仍以根 AGENTS.md 为依据，不因增加会话约定而复制整套规则或新建状态文件。
