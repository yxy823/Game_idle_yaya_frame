空白 Godot 项目使用手册

这份手册说明 Yaya 空白项目包含什么、如何开始开发、怎样组织需求与代码、如何验证和交接，以及框架维护者应在哪里修改源材料。面向使用这套起始文件的用户和维护框架的 Coding Agent。

桌面阅读：打开 HTML 使用手册。所有章节和图表保存在这一个文件内，可离线查看、点击目录跳转、用 Ctrl + F 搜索全文和复制代码。Markdown 是正文维护来源；更新方法见 生成离线阅读版。

手册保存在 framework/docs/blank-project/，仅属于框架维护目录，不进入新项目。新项目仍使用简明的 Project_README.md 作为入口，并携带自身的规则、Skill、方法说明和工具。生成后的项目可以独立开发，不需要访问本手册或框架目录。

这套起点提供什么

  • 可独立使用的项目材料：Godot 项目文件、两个插件、编辑器和 Git 文本约定。
  • 需求到开发的工作方法：轻量讨论与澄清、产品梳理、Feature 拆分与增量同步、Bug/重构/维护分类，以及单项任务的执行流程。
  • 可持续读取的项目知识：Product、Feature、测试登记表、当前进度、历史，按主题组织的实践经验索引，以及按需维护的 CONTEXT 术语与架构记录。
  • 显式检查工具：环境配置检查、任务台账检查、gdUnit 测试运行与完成依据记录。
  • 按修改领域读取的 Godot 工程规则：脚本、场景、资源、Shader、项目配置、导出、数据、资产和测试。

初始内容没有预制玩法、角色、存档系统、主场景或业务测试；docs/knowledge/ 初始只有分类说明和索引，实际经验随任务积累，使用方式见项目知识。New Godot Project 是显示名称默认值；引擎路径是待核实配置。创建成功、环境就绪、测试通过、人工接受和任务完成分别描述不同事实。

当前源材料面向 Windows 11 / PowerShell 7 / Godot 4.7 / GDScript / gdunit4，维护命令使用已确认的 Python 3.12+。这些是本仓库的目标和配置约定，不表示每台机器都已经安装工具，也不构成对其他平台或版本的验证声明。

创建空白项目

返回手册 · 下一步：首次使用

创建项目的结果是一份独立的文件集合。复制成功后，环境准备和游戏开发在目标项目中分别进行。

准备目标位置

目标必须是维护仓库之外的新目录或空目录。检查的是完整路径，包括父目录和解析后的路径：

目标情况 结果
D:\Games\MyGodotGame 不存在或为空 可以创建
D:\Games\My Game 或 D:\My Games\Game 因空白字符被拒绝
D:\游戏\MyGame 因中文路径被拒绝
当前维护仓库的子目录 被拒绝
包含维护仓库的祖先目录 被拒绝，不能把源仓库包含在输出中
已有文件的目录、已有普通文件 被拒绝，不覆盖已有项目

目录名和 Godot 显示名称是两个概念。项目路径遵循上述限制；后续修改 project.godot 的 config/name 不会重命名目录。示例统一使用简短 ASCII 路径。

执行复制

在框架根目录运行以下命令。本机使用个人规则指定的解释器；在其他机器上应先换成已确认的 Python 3.12+ 完整路径。

powershell
Set-Location -LiteralPath 'D:\A_Games\Game_idle_yaya_frame'
& 'C:\Users\89523\anaconda3\envs\codex-python\python.exe' -B framework/commands/create_project.py --output 'D:\Games\MyGodotGame'
$LASTEXITCODE

--output 是唯一业务参数且必填。-B 属于 Python，用于避免本次进程写字节码缓存。上述路径是调用示例，不表示本手册已经为你创建了该项目。

创建器从自身位置找到维护仓库，再读取 project-files.json。它先核对目标与全部清单源路径，再创建目录并复制；文件可以改名，目录会连同子目录内容一起复制。它没有模板替换步骤。

成功输出的数量是清单条目数，不是文件总数；一个目录条目可能包含很多文件。以退出码和实际输出判断复制是否完成。

复制完成后的初始状态

项目内容 初始状态
项目说明与规则 Project_README.md、Project_AGENTS.md 分别成为根 README.md、AGENTS.md
开发 Skill skills/ 成为 .agents/skills/
环境配置 Project_Workflow_Config.json 成为 docs/methodology-config.json，状态仍为 incomplete
Product docs/product.md 是空文件
Feature 与测试登记表 空索引、空修订记录、空组件与测试集合
Godot 显示名称为 New Godot Project，未设置主场景
Git 创建器不执行 git init，没有由它建立的提交
实际验证 没有执行环境检查、Godot、lint 或测试

完整映射见 项目目录与文件职责。复制器保留源文件原文，因此部分模板起始文字是英文；后续生成项目知识时由配置中的 document_language 决定人类可读内容的语言。

为什么本手册不会进入项目

清单只选择 project-source/ 中的交付材料。本手册位于 framework/docs/blank-project/，与 framework/prompts.json、维护回归和复盘材料一样，不在复制范围内。

这个边界由目录位置和复制清单共同表达，不依赖“复制后删除文档”的步骤。增加章节时不修改复制清单；项目 README 继续负责简短导航，也不要求生成项目回查本仓库。

复制失败后如何处理

  1. 先阅读 Copy failed 后的实际原因，区分目标不合法、缺少源文件、路径越界和读写权限问题。
  2. 前置检查失败时修正输入或源材料，不把它解释为 Godot 环境失败。
  3. 复制途中失败会保留现场。检查目标内容后，再由本次任务决定如何处理这份未完成输出；创建器没有回滚或覆盖重试模式。
  4. 不直接对半成品再次执行复制：非空目标仍会被拒绝。不要为重试删除用户文件，也不要把新路径当作自动获得创建更多项目的授权。

修复框架源材料不会更新已存在的游戏项目。需要保留旧项目并使用当前框架继续开发时，使用复制迁移已有项目入口；不对已有内容运行创建器。

创建成功后，打开目标项目继续 首次使用。

对应源文件

  • create_project.py：路径检查、复制顺序与错误返回。
  • project-files.json：实际文件选择与重命名。
  • 复制器回归源码：已有边界用例；阅读源码不等于已运行回归。

首次使用与环境准备

返回手册 · 前一步：创建项目 · 下一步：需求与规划

复制后的项目具备开发材料，机器工具和游戏内容仍待确认。首次环境准备只解决“当前项目如何调用工具”，具体玩法和业务 Feature 另行处理。

打开正确的工作目录

将 Coding Agent 的工作目录切换到生成后的项目。先读取该项目自己的 AGENTS.md、README.md、docs/methodology-config.json 和 docs/progress.md，再按任务需要加载 Skill 和规则。

不要在 project-source/ 中打开业务开发任务。那里文件名和目录尚处于复制前形态，例如 Skill 位于 skills/，配置也不在项目最终位置。

从 集中提示词 的“Godot 项目开发 → 项目初始化 → 准备 Godot 开发环境”选取当前正文，在目标项目中使用。手册只解释其行为，提示词正文仍由 JSON 单独维护。

环境准备需要确认的内容

内容 如何确认 保存位置
Python 使用本机已确认的 Python 3.12+；本机个人规则指定 codex-python 解释器 python_executable
Godot 直接核对已配置路径，执行 --version 并保留真实输出 environment_bootstrap
插件 检查项目 addons/gdUnit4/ 与 addons/gdscript-linter/ 的实际文件 初始化报告；不建立另一份插件清单
测试入口 按项目工具实际参数组成可调用命令 test_cmd
显示名称 用户提供名称时修改；未提供时保留现值 project.godot 的 config/name

初始 Godot 路径已经写入配置，准备环境时直接使用它。路径不可用就报告该路径和失败原因；只有用户要求更换位置或提供新路径时才修改。预填路径不证明安装存在，也不应自动搜索另一个版本替代。

Godot 配置按绝对路径或相对项目根目录的文件路径解析，不通过 PATH 查找。使用相对路径时，直接命令也从项目根目录运行，并保留 ./ 等路径前缀以明确选择项目内文件。

可执行文件字段保存单独的完整路径，不附加参数或 shell 引号；带参数的测试命令保存在 test_cmd。具体字段和转义示例见 配置参考。

配置就绪的判定

先核对实际工具和命令，填写真实配置，再将 environment_bootstrap.status 设为 ready 并运行就绪检查。如果失败，保持或恢复 incomplete，将原因记录到 Progress 和初始化报告。

首次 Git 状态如何处理

创建器本身不建立 Git 仓库。当前集中管理的环境准备提示词显式授权：若目标没有自己的仓库，先核对不位于其他仓库内，再执行本地 git init；同时明确要求本次初始化不提交、不创建远程、不 push。

因此，按该提示词完成环境准备后看到尚未提交的初始文件是预期结果。获准提交初始基线后，可以继续同一次初始化，核对并仅提交已知初始文件及本次环境准备的改动；工作区干净后再开始新的修改任务。不能把初始化提示词当作初始提交授权，也不能把这些文件混入第一个业务 Feature。

如果使用其他初始化请求，以该请求已经给出的范围为准。已有仓库保留原状态；仓库发现和文件归属存在疑问时先查清，不执行清理、覆盖或自动暂存。

没有主场景与业务测试时

初始 project.godot 没有 run/main_scene，默认目录也没有游戏脚本或测试套件。此时可以说明项目已经复制、工具环境已经确认，但不能声称游戏启动或业务测试通过。

主场景、业务目录、测试根目录及首个可运行行为由后续获批任务按需要建立。初次 Product 规划通常先安排可运行基础，再按依赖实现行为；不要为了给初始化报告填写成功结果而虚构一个 Feature 或测试。

首次命令行运行前的扫描

配置 ready 不会生成 Godot 的全局类缓存或导入资源。新项目尚未在编辑器中打开时，直接运行 CLI 测试可能报找不到 GdUnitTestCIRunner；此时用例尚未执行，不能当作业务测试 RED。

在首次获授权的 CLI 测试或项目脚本运行前，让配置中的 Godot 正常完成一次编辑器扫描，具体命令、退出码和失败处理见 项目工具的首次扫描说明。已正常打开过的项目复用已有准备；仍有解析或导入错误时按实际错误排查。

仅配置环境、尚不运行项目命令的初始化可以把扫描留到首次运行时，在初始化报告中注明尚未执行。扫描遵守项目 AGENTS.md 的本机沙箱与审批约束；它不属于创建器的复制职责，也不增加导入包装程序、业务测试或每个 Feature 的固定阶段。生成文件按项目现有资产和引用规则处理，不把 .import、.uid 与 .godot 一律视为可删除缓存。

初始化报告和下一步

实际过程写入 reports/initialization.md；已有报告时追加，保留发生过的失败。docs/progress.md 只保留当前结果、阻塞、下一步和报告链接。

报告应能让下一次接手的人确认：项目位置和工具版本、修改了什么、执行过哪些命令、每项结果证明什么、哪些未执行、实际问题与处理、最终 Git 状态和剩余工作。初始化报告供人阅读，不是另一个机器门禁。

输入与执行位置

填写原项目、当前框架、新目标、本次授权范围以及 Git/数据选择。目标须在两个输入之外、互不包含、不属于其他仓库且不存在或为空，完整路径不含中文或空白；用户也可明确允许 Agent 自行选择。

默认先只读分析，再讨论方案。已有具体实施授权时，Agent 展示方案后继续完成获选范围，不逐文件重复确认。编写或阅读提示词本身不会启动迁移。

原项目继续保存在原位置。“不迁移”表示不纳入目标，原件不删除；验证的配置、存档和输出也应与原项目及共享用户数据隔离。所有运行和 Git 写入仅在目标进行，不能通过链接、worktree 或共享对象把写入引回原件。

Product 保存玩家行为的意图，Feature 保存可逐项交付的工作。先说清楚需要什么，再决定怎样拆分和验证，可以减少边写代码边猜规则造成的返工。

先讨论，按需留下术语

project-clarifier 将询问深度与是否写文档分开：问题已经清楚就直接回答，缺一个关键条件就只问那个条件，较大设计才按依赖顺序分几轮。用实际情景检验概念区别；上游决定改变时，只重查受影响的结论。它不维护问卷状态、轮数或评分，也不要求每轮固定格式。

只讨论时不会创建文件，空项目不必先准备 Godot 环境或补完整 Product。需要留下词汇时，沿用已确认的答案和写入授权，由 product-change-standardizer 统一落盘。init/spec/audio elicitor 复用同一套提问方法，返回各自草案或补丁；信息足够时不再访谈，有独立缺口时可以合并询问。模块和 AC 数量由实际范围决定，不凑数量；已批准部分不逐模块反复全文展示和确认。

跨模块或 Feature 使用的稳定概念按需放在 docs/CONTEXT.md，局部定义已有合适位置时保留原处。每个概念只维护一份定义，其他位置链接过去。具体职责见 项目知识。

仅记录已同意的区别、统一名字或移动定义，且含义和行为不变时，不要求 Product 初始化或 Feature 同步。若定义变化实际改变玩法、数值或验收条件，就先解决产品决定，再按授权更新 Product 并同步任务，不能把它当成纯文字整理。

Product 分成总览和模块

docs/product.md 让人快速了解整个游戏：定位、目标玩家、当前版本的核心循环、模块列表、依赖、视觉和声音方向、变更历史。详细模块使用 docs/product/NN-name.md，保存行为流程、数据含义、状态转换、UI、音频、数值规则、验收条件和暂缓边界。

例如描述一个资源收集玩法时，应明确玩家做什么、何时增加资源、何时不能操作、界面如何反馈，以及哪些结果可以验证。数据结构字段的业务含义属于 Product；具体 GDScript 类型、节点布置和算法选择交给实现或工程记录。

模块文件使用两位编号和 ASCII kebab-case 名称，例如 01-gathering.md。已有模块编号保持稳定；新增模块追加可用编号。模块废弃按规范保留可追溯历史，不为重新排序而批量改名。

模板中的必需章节应保留；不适用时说明原因。例如“物品定义”和“玩家持有的一件物品”是否有不同身份，会影响堆叠和存档规则。概念定义可引用 CONTEXT，具体堆叠、存档行为仍写入负责的 Product 模块；已有清楚定义不再复制一份。

完整结构见 Product 规范。

UI 与声音产物的边界

product-ui-sketcher 在布局或交互需要澄清、或用户要求草图时返回 ASCII 线框、交互意图和状态差异。已有明确交互的文案或数值调整可直接更新需求。HTML/Tailwind 探索须有实际用途或用户请求，不在每次 UI 修改后固定追加询问；探索稿不等同于已实现的 Godot 界面，也不能证明适配和手感。

product-audio-sketcher 返回声音触发、时长、风格和稳定的 _placeholder_ 文件名等要求。它复用已知信息和共同声音约定，只补问有影响的缺口，不要求每个声音完成固定次数的问答；不生成正式音频资产，播放实现或调试仍走工程入口。

这些辅助 Skill 形成 Product 草案或补丁，Product 的正式写入由 product-change-standardizer 负责。确认界面或音频需求后，仍需在 Feature 中说明具体实现和人工验收范围。

Feature 如何拆分

Product 按实际执行顺序逐个拆分，当前 Product 的 Feature 完成后，再拆下一个 Product。 在现有结构中，以一个 docs/product/NN-name.md 模块及其已确认范围为单位。Product 总览说明依赖和推进顺序，文件编号保持稳定，不代替实际执行顺序。

先把当前 Product 拆成所需的完整、可验证 Feature，完成它们后再根据实际结果复核下一 Product 的需求。后续 Product 可以先有描述，但不预分配 Feature ID、Feature 的详细 AC 或测试登记。这样后续调整主要发生在需求文档中，不必同时维护一整批尚未执行的任务。

generate-feature-list 用于第一份以及后续每份 Product 的初次拆分。默认空台账可直接开始；已有历史时沿用同一台账，在最大 ID 后追加，保留以前的 Feature、测试登记表和修订记录。当前 Product 已有计划就复用；修改该计划交给 sync-feature-list。

一项 Feature 应是可独立验证的完整行为或工程结果。复用已有基础设施，只补当前 Product 必需的可运行基础；最终工作量使用 small 或 medium，过大的工作继续拆分。若当前 Product 依赖尚未完成的另一 Product，先调整推进顺序，不同时拆出两份完整计划。

判断是否可以进入下一 Product，要核对当前范围、Feature 来源和完成状态。有 pending、in_progress 或 blocked 工作就还未完成；没有可执行候选、没有任务或 Product 文档标为 done 都不等于功能已交付。Stage 8 依据剩余具体授权决定续接或停止，下一 Product 的规划同样需要实际授权。详见 逐个 Product 规划规则。

测试登记表的作用与位置

docs/test-registry.json 是项目的测试登记表（Test Registry），固定保存在这个位置。它将组件、Feature / AC 和实际测试文件、测试函数关联起来：组件记录已存在的单元测试路径，测试条目记录逻辑 ID、用途、来源、组件及 planned / active / retired 状态。

例如，Feature 声明影响 inventory 组件后，选择器结合登记表找到背包单元测试、相关历史验收与回归测试，再加入本次明确要求的测试。影响范围由 Agent 核实，登记表提供查询关系；测试是否通过仍取决于真实运行报告。空白项目的 components 和 tests 为空，后续随实际规划和测试实现维护。

验收条件和测试 ID

每条 AC 使用稳定 ID，例如 AC01。条件写成可观察的结果，避免“体验好”“性能高”这类缺少判据的描述。机器可验证内容关联逻辑测试 ID，人工判断内容记录可重复的检查步骤。

标识示例 意义
F012-AC01 F012 的 AC01 自动验收测试
F012-AC01-02 同一 AC 下的另一个自动测试
F052-RT01 F052 修复 Bug 时建立的回归测试
INV-LIFECYCLE-01 跨 Feature 的生命周期不变量
inventory 语义组件，用来选择相关安全网

规划阶段 verification.acceptance_mode 可以为 null，表示尚未决定；正式执行在 Stage 1 先根据需求选择 manual 或 automated，再填验证项。初始空列表不表示自动选择了全自动验收。

允许先登记 planned 的验收/回归测试，随后在实现中创建并改为 active。组件的 unit_test_paths 只登记已存在套件，没有套件时用空数组；不要用未来目录冒充现有安全网。

需求变化后怎样保留历史

已有计划采用 sync-feature-list，它对照实际 Git 源差异、历史锚点、当前任务和测试登记表，区分编辑性调整与行为变化，并记录新增、修订、拆分、合并或退役关系。已有变更说明直接复用；没有说明就先读取差异，仅在实际含义不清时询问，不先要求用户复述一次。

首次同步不能直接用“最近修改 Feature 的提交”作为需求基线。例如先规划、后改 Product、再整理 notes，最后一次 notes 提交并未吸收前面的需求变化。应核对实际规划提交和对应源内容；复制空台账的提交也不等于规划完成。无法可靠恢复基线时，在明确授权下比较当前完整源文档和计划，说明历史未知；使用现有修订字段记录当前 HEAD 作为新基线，不虚构历史差异。

同步新增组件时，先按已批准方案复用现有合并入口登记组件，再更新 Feature、替代测试、退役关系和修订记录，最后对完整集合做台账检查。无套件组件使用空路径数组；保留原有组件和测试，不能重置测试登记表或覆盖同名冲突来让检查通过。本次写入引入的格式错误或未完成写入，核对实际结果后在原授权内修正并复查；已有数据损坏、未知归属或权限拒绝按其真实边界处理，不借恢复操作丢弃历史。

对于已完成行为，新的实质需求通常建立新的 Feature；保留旧任务的历史 AC、测试 ID 和完成事实。不要重写旧记录，让它看起来从一开始就实现了新行为。

普通下游回归归入负责当前变更的 Feature：同步时在其 notes 说明受影响行为、现有测试或人工检查和覆盖缺口，Stage 1 纳入验证范围。仅复跑有效测试不另建 Feature，也不改变原测试归属；有独立实现、修复或明确单独交付范围时才新增工作项。必需测试不能用“已放弃回归”的备注排除。

未完成 Feature 经批准修订并删除旧 AC 时，对应 retired 测试保留历史 AC ID，通过来源、修订和替代测试追溯，不要求把旧 AC 留在当前详情中。planned、active 测试仍必须关联当前 AC；替代测试尚未实现时不能据此完成 Feature。

拆分或合并时同时处理下游依赖、替代任务和测试映射。obsolete 表示未完成工作已废弃，obsolete_done 保留曾完成但后来被替代的历史；未完成任务不能继续依赖它们。旧测试退役必须有对应需求来源和替代关系，不能仅因为它失败就删掉。

仅修改后续尚未拆分的 Product，且不影响已有任务时，保留文档变化并暂缓拆分。若改变了现有行为依赖的契约，则处理真正受影响的任务和回归；不借同步一次性展开所有 Product。

轮到下一 Product 时，生成入口读取它当时的完整规格。即使其文档修改早于最近一次同步锚点，也不能漏拆；反过来，同步时已被先前规划吸收的变化不重复生成 Feature。历史与已有工程任务始终保留，不使用全量重建来推进下一 Product。

规划完成时应能回答

拆分或同步报告用简短表格或清晰列表串起“需求位置与当前含义 → Feature / AC → 测试或人工检查的处理 → 缺口与下一步”。首次拆分核对当前 Product 的完整已确认范围；增量同步只展开本次变化及真实下游影响。双向阅读需求和 AC，查找遗漏、重复和不合适的任务范围，不能只凭来源链接、ID 或旧 done 判断已经覆盖。

写入后用实际文件刷新同一份报告。明确哪些只是计划已对齐，哪些实现、测试编写或验证尚未完成；未覆盖的当前需求不能默认为已同步。后续未拆分 Product 和已确认排除的范围简述去向即可，不提前创建任务。可执行的后续事项沿用所属 Feature 或当前 Progress，不新增覆盖台账，也不为补齐报告编造测试 ID。详见 需求覆盖复核。

现在要实现的行为是什么、依据哪个 Product、受影响组件有哪些、前置任务是否完成、AC 怎么检查、有哪些尚未确定的选择。规划完成说明工作可理解，不代表已批准 Stage 1 实现或已经通过验收。

开发、验收与交付一个 Feature

execute-next-feature 每次执行一项已经确定的工作。交接后，已有具体授权覆盖下一步且前置条件满足时继续；范围完成、用户要求暂停或缺少必要决定时停止。它也可以从当前任务的真实阶段继续。

开始前读取什么

Agent 读取当前项目 Git 状态、Progress、Feature 索引与详情、相关 Product、适用 Coding Rules、环境配置和受影响工程规则。由各模块 README 按主题选择相关章节，不把一种文件类型等同于整目录必读。已有 docs/CONTEXT.md 时读取相关概念定义，已有架构地图或相关 ADR 时一并查看，核对实际代码和需要修改的路径。Stage 6 复审也读取这些相关定义，检查命名与含义是否一致。

提出方案或查外部资料前，优先从 docs/knowledge/README.md 进入相关主题，读取适用于本任务的经验条目并核对条件。Stage 6 也参考相关知识；继续原任务时复用已读内容，不重复通读目录。初始索引为空或没有相关经验时正常继续。

新修改任务按项目规则要求干净工作区；继续当前任务时，按真实差异确认任务归属。保留无关文件，不通过自动 stash、删除或恢复解决归属问题。环境须已准备，普通任务复用确认过的命令。

Stage 0 准备当前任务、关键资料、实际约束、修改范围和验证的简短快照，在 Stage 1 方案中展示一次，不限定规则条数。继续任务时引用已有快照，仅补充实质变化。

Product 开发保持逐个推进：先完成当前 Product 所需的 Feature，再复核并拆分下一 Product。Stage 8 说明当前 Product 的剩余任务或真实阻塞，按已有授权衔接后续执行或下一 Product 的规划。--eligible 只说明依赖就绪，没有候选不能直接判定 Product 已完成。已有后续计划保留，工程修复仍按其实际授权处理。

Stage 1 为什么先决定验收方式

涉及画面、声音、动画、手感或其他人的判断时采用 manual；所有 AC 都可用自动方式充分验证时可以选择 automated。选择从需求出发，不能根据“人工检查列表为空”倒推不需要人工验收。

例如资源计算和存档字段的确定性结果可以自动检查；按钮是否容易辨认、声音是否刺耳或角色移动是否合适仍需要人在实际体验中判断。manual Feature 也可以包含大量自动测试。

Stage 1 一次说明任务范围、影响组件、已有安全网、新测试、资源依赖、人工检查和全量测试理由。用户已经对这个具体范围作出批准就沿用，不在后续阶段重复问同一件事；实现批准仍不等于用户已经验收结果。

实现与测试怎么配合

先运行与变更相关的已有安全网。它若本来就失败，应保留原始错误并说明，不能记成本任务引入，也不能自行吸收无关修复。

适用 TDD 的新行为先建立对应测试，确认失败来自缺失或错误行为，再实现并取得通过。解析错误、环境故障和无测试发现不是有意义的 RED。窄范围运行支持调试，最终验证按当前 Feature 和测试登记表计算。

需求变化涉及旧测试时，同步报告说明要处理的断言、方法/文件和当前引用，批准后交给对应 Feature notes。实现阶段按该范围实际删除或替换，并更新有效映射与注册路径；同一文件里的有效用例继续保留。测试登记表的 retired 只表示记录退役，仍在被选中套件内的旧方法仍可能执行。已完成 Feature 和退役记录保留历史用途，详见 失效测试处理约定。

最终默认 --scope auto 运行 affected 集合，必要时升为 full。一次覆盖充分、内容仍匹配的全量成功可以覆盖 Required 和 affected；无需为填多处状态重复跑同一范围。测试选择、报告和静态检查详见 命令与验证。

只有有效的 manual 计划确实没有 Required、affected 或全量测试义务时，才省略自动运行和 record-tests，保留初始化的 test_runs: []，说明自动测试为 not_required。这不表示“空测试通过”：人工验收和适用的静态检查仍需完成，当前内容上的失败或未完成运行也不能被省略操作掩盖。已登记但缺失的测试路径仍是错误。

人工验收应如何操作

人工步骤围绕批准的 AC 展开：入口场景、起始状态、实际输入、预期反馈和必要重置。输入时长、设备、随机种子或参数会影响结果时再说明。

例如检查一个已实现的面板重开行为，应写清进入哪个场景、如何打开和关闭面板、何时切场景、再次打开时应看到什么，以及如何从初始状态重做。截图可以标明观察位置，但不单独证明操作链成立或用户已经接受。

用户明确接受当前范围后才能登记 accepted；验收失败登记 rejected 并修复。反馈改变了需求含义时，回到对应 Product/计划修订路线，不悄悄改 AC 迎合结果。automated 模式省略 Stage 5，也不写入虚构的人工接受。

按需独立评审与再次验证

独立评审默认不启动，也不在每项 Feature 完成时例行询问。你可以通过“Godot 项目开发 → 验证与收尾 → 独立审查指定修改”选择单项、多个 Feature、提交范围或明确差异，并说明评审时机。多项评审核对当前合并成果及直接受影响的调用者，输出一份报告，不逐项重复审查整套内容。日常实现仍由作者核对 AC、范围、规则和最终差异，不另建自查阶段或报告。

可以等选定 Feature 完成并提交后再集中评审，之前各项无需停留在未完成状态；明确要求“评审后再继续”时，Agent 遵守该顺序。具体授权沿用原会话，不另建队列、开关或待评审状态。

执行评审时使用新的独立上下文，读取实际差异、需求、规则和原始证据，分别给出“需求符合性”和“代码质量”的结论及依据；同一根因映射到相关 Feature，问题注明维度和严重程度。缺少依据或独立上下文时如实说明限制，不把作者自查称为独立评审。详细方法以执行规范 Stage 6 为准。

只要求评审时交付发现并停止，问题等级不是修改授权。分别核实问题与改法，在已选修复范围内处理；仅保留已接受且有用的后续事项，不把每条建议变成 TODO。当前任务中的确认缺陷回到实现阶段，已完成 Feature 保留历史并走已有工程修复入口。确认的完成阻断缺陷不能因评审可选而被忽略。

当前运行结果在只读评审后仍有效时可复用。修复改变最终内容则更新失效验证，影响已接受行为时更新对应人工验收；再次评审依据用户约定或尚未解决的具体问题，不机械重跑全部检查。

完成记录与 Git

完成前核对 AC 与最终差异、测试原件、适用人工决定和直接解析/lint，并满足用户明确指定的评审条件。完成依据脚本只检查测试与适用人工接受，不记录评审计数，也不能替代作者检查、独立评审或用户决定。

显式检查通过后才把 Feature 记为 done 并填写完成时间。随后保留长期 notes，将执行历史归档一份到 docs/progress/，在当前 Progress 中链接它。

本次形成的成功做法、排障方法或失败教训，有复用价值时在提交前写入 docs/knowledge/ 对应主题并更新索引；原任务经过仍在 Feature notes，知识条目链接过去。Stage 8 汇报已有条目，不在提交后再开始补文档。纯知识 Markdown 不使业务测试证据失效；新增脚本、规则或验收契约仍按其实际影响验证。

项目默认在当前分支提交本任务明确路径或检查过的差异块，提交前查看暂存区完整差异和检查结果；用户要求不提交时遵守该要求。Feature 提交标题采用 <type>(F0XX): <中文行为摘要>，正文包含 Work item: docs/features/F0XX.json，非简单变更补充原因和主要验证。提交后再次核对状态，不自动 push 或改写历史。

中断和失败时怎么继续

继续之前读取 Progress 与任务记录，确认最后真实阶段、当前差异和哪些依据仍适用于现有内容。不能只凭上一轮“通过”的文字就把任务置为完成。

先确定问题是在改变游戏意图，还是在恢复或维护已经明确的契约。分类决定应该修改哪些记录，避免用修 Bug 的名义改变 Product，或为技术维护虚构玩家需求。

工程 Feature 仍使用普通 Feature 索引和详情，在详情中以 engineering_change 标明模式。它们进入同一套执行流程，不另建工程任务系统。

规划时同时读取测试登记表，区分复用组件与本次新增组件。批准后先使用现有组件合并入口登记缺少的组件，再写任务并运行台账检查；没有单元套件就用 unit_test_paths: []，不创建虚假路径。已有组件和测试保留，同名不同定义须明确处理；新增组件与任务一同提交，具体测试映射仍在执行阶段确定。

Bug 先查归属，再查根因

当前未完成 Feature 内的缺陷，优先在当前范围中修复。已完成行为中的独立缺陷才按独立 Bug 工作组织。新问题若来自不明确或改变中的需求，应回到 Product，而不是先修代码再补理由。

诊断至少让人看懂：实际发生什么、原本应发生什么、预期依据在哪里，以及最短复现步骤。根因未确认时明确保留未知；不能把最先想到的解释当成已证实事实。

bug_diagnosis 非空时使用现有结构保存 actual、expected、source、reproduction、root_cause。当前完成时，非空诊断中的根因必须已经确认。完整字段约束见 Feature schema。

适合自动验证的 Bug 建立 F0XX-RTyy 回归测试。无法合理自动化时，说明具体原因并给出可重复的人工回归路径。回归关注原始触发条件和错误结果，不仅证明修复后的某条代码执行过。

Bug 成功验证并完成适用验收后，Stage 5.5 将根因、触发条件、回归覆盖和防范原则保存在当前 Feature notes。通用建议先核对已有规则，只有值得复用且获得明确授权时才提升为 Coding Rule 或不变量；不要把每个缺陷都变成新规则。

重构应解释实际收益

重构提案从已经观察到的维护困难或下一项确定需求出发，例如同一业务规则需要在多处同步、调用顺序分散、对象生命周期难以判断。验收既要证明行为保持，也要能解释改后为什么更容易修改。

可用一个检查问题帮助判断：移除某层后，调用者是否更简单？若移除只是把校验、错误处理、状态归属和生命周期知识散到各处，这些职责仍需有清楚的位置。文件数量减少、类名变短、评分提高都不足以单独证明改进。

pick-refactor-smell 先应用用户指定的 Feature 范围，再读取对应 notes；分类筛选在该范围内进行，全项目分类检索才可能需要全部 notes。相关历史与依赖按需追查，没有记录不要求先创建计划。先排除已解决或已被后续工作替代的问题，再比较确认仍未解决的候选。排序结合当前证据、不处理的实际影响、最小完整改法，以及现在修改的风险和验证成本。涉及几个文件、出现 BUG 字样、存在多少依赖，或多条 notes 指向同一文件，都只提供调查线索，不直接决定优先级，也不计算分数或新增优先级台账。同一根因可以合并论证，但保留每条来源。

有值得现在处理的候选时推荐一项，并解释为何优先于其他项；若全部候选的当前收益不足，就明确建议暂缓。没有有效候选时直接停止；记录含义或现状不明确时单列待核实，不强行排序，也不把暂缓或未知写成已解决。例如，阻碍下一项已确定功能、且修正范围清楚的结构问题，可以先于一项涉及更多文件的普通命名整理；具体顺序仍以实际证据和用户目标为准。

发现当前行为违背已接受的契约时，应单独说明缺陷并回到工程标准化入口按 Bug 归属判断，不用“重构”替代修复分类。整个选择过程保持只读，不改写历史 notes；选择候选本身不自动授权实现，用户同时给出的具体授权继续有效。独立架构调查也可以直接从真实代码和已接受决定评估，无需先制造 smell 记录。具体原则见 架构约定。

工程维护如何确定边界

维护类型 应先核对的内容 可观察的成功条件示例
项目工具修复 实际错误、入口参数、输出与调用 Skill 原始触发命令给出正确结果，相关失败边界仍有效

素材替换 需求是否变化、引用与导入设置、授权来源 实际场景资源可用，并完成适用的视觉或听觉验收

原型与技术实验

当用户明确要求验证假设时，先界定一个问题、允许修改和运行的范围、时间或尝试预算，以及保留还是移除实验文件。独立实验可以不建立完整 Product/Feature 链；已有 Feature 内的实验继续遵守其任务边界。

例如验证一种拖拽操作是否容易误触，可以保留实验场景、输入条件和观察结果。观察到“某参数更顺手”仍是实验结论，不会自动变成已批准的正式数值需求。

实验的假设、结果、决定和文件处置写入当前 Feature notes；没有 Feature 时写入当前 Progress。采纳结果进入正式开发时，再回到 Product 或工程变更入口。超出实验预算或范围需要用户决定。

调查结果如何进入执行

工程标准化负责诊断、分类、提出工作项，并在相应授权下写入任务。execute-next-feature 负责实现、验证、适用验收、用户指定的可选评审和交接。用户已对具体工作给出的授权持续有效，后续不重复询问同一批准。

复盘中发现的另一项工具问题或跨模块改进，不顺手塞进当前修复。保留证据和建议，按用户决定进入下一项工作。

优先查阅与积累项目知识

新项目携带 知识目录入口 和主题索引，初始没有实际经验条目。目录吸收外部材料按主题积累经验的思路，正文和流程按当前项目重新编写：

每条独立经验使用单独的 Markdown 文件，索引只放链接与简短说明。实际内容需要时可增加游戏模块或更细子目录；不按每个 Feature 机械建文件夹，也不把一条经验复制到多个主题。

规划、调查、开发、调试或复审开始时，先明确当前任务和规则，再查总索引与相关主题、条目，随后决定方案或补查外部资料。按模块、现象、API、工具缩小范围，继续原任务时复用已读内容；不要求每次通读整个知识库。优先参考不等于自动适用：还要核对当前版本、场景和证据，知识不能覆盖用户意图、Product、已接受决定或工程规则。分类为空也不阻塞工作。

经验正文保存场景、有效做法或根因、适用范围和真实依据。成功做法说明观察到的收益与限制，不必编造“根因”；有项目独有条件的做法也可以保留。版本和平台影响结论时明确记录，疑点标为未确认，不把一次运行现象当成通用引擎事实。

在已授权任务的文档整理中，先检查已有覆盖，再更新或新增有价值的条目与最近一级索引。Feature notes 保留原事件与局部决定，知识保存提炼出的解释并链接原件；ADR 和规则仍各自负责决定与约束。Feature 的知识文档在 Stage 7 提交前完成，Stage 8 只汇报链接。纯知识 Markdown 不使业务测试证据失效；代码、测试和契约变更仍须验证。

只读或纯讨论任务维持原写入边界；没有新知识就不新增条目。目录只链接实际运行脚本、数据或报告原件，维护沿用现有任务流程。现有经验已经不适用时明确修正适用条件，跨项目吸收和规则升级仍按原授权处理。

何时维护 CONTEXT

当同一项目中的概念需要反复解释，或在不同模块、Feature 中出现同名异义、异名同义时，使用 project-clarifier 通过具体情景澄清。需要保存的已确认定义由 product-change-standardizer 按授权写入 docs/CONTEXT.md；缺少该文件不阻塞讨论或开发，也不预先放一个空模板。

文件只需简短背景、术语名称和一两句话的定义，按需说明概念关系、别名或易混淆项。例如区分“物品定义”“持有物品”“堆叠”，随后链接到 Product 的实际堆叠规则。已有定义直接复用，移入 CONTEXT 时将范围内的重复定义改为链接。

详细行为、数值和状态转换由 Product 负责；实现状态归属和技术取舍由架构文档负责；待定想法、聊天记录和当前进度不放在 CONTEXT。仅保持含义的术语维护不会触发完整 Product 初始化或 Feature 拆分；实质行为变化仍走需求变更。规范与格式见 项目术语约定。

何时需要架构地图

当仅从源码已经难以看清模块职责、状态归属和依赖方向时，建立 docs/architecture.md。复杂子系统展开到单独文件，总览保持可浏览。

地图应指向实际模块，解释谁拥有状态、谁可以调用谁，以及为什么这样划分。需要说明运行过程时，在子系统文档记录触发、参与者、状态变化、结果、Godot 生命周期和失败处理。使用 flowchart 展示依赖，用 sequenceDiagram 展示交互顺序，用 stateDiagram-v2 展示真实状态转换；只画能帮助读者判断的内容。

生成的引用关系只说明解析器看到了什么。动态加载、运行时 Signal 和状态归属不能仅靠文本搜索确定。观察、推断、提议和已实现行为要区分，图表也不是依赖设计的自动批准。

何时使用 ADR

某项技术选择跨多个 Feature、长期约束项目或代价较高时，可建立 ADR。记录问题、约束、候选方案、决定、收益、接受的成本、依据和有用的重新考虑条件。普通局部选择保留在 Feature notes 即可。

这些是普通 Markdown 状态，不需要注册表。Accepted 说明决定得到确认，不证明相关 API 或运行行为已经测试；Superseded 保留旧理由并链接替代 ADR。真实任务已经确认的决定直接沿用，不额外增加一轮批准。

架构地图保存当前结构，ADR 保存跨任务理由，Feature notes 保存局部决定，Progress 保存当前链接。按需更新边界变化，不为每次改函数写 ADR，也不把缺少可选地图当成门禁失败。

资源、数据与占位内容

空白项目不指定业务素材目录。资源文件按游戏模块与实际资产流程组织，修改前核对源文件、运行资源、导入信息和生成缓存的归属。

占位内容使用 _placeholder_ 前缀，并在当前 Feature notes 说明用途、替换方式和未完成的验收。替换素材时核对引用、UID/路径与实际场景；外观、声音、动画和手感仍按需求保留人工验收。

数据格式改变时核对已有内容和加载方，再决定版本、迁移与兼容范围。资产来源和许可证按现有规则记录。工具生成的输出不应成为可复用脚本或重要项目决定的唯一副本。

Progress 如何帮助继续任务

当前 Progress 只需清楚记录：活动 Feature 或获批批次、真实阶段、阻塞、待决定事项、下一步，以及计划和报告链接。不能从“下一步实施”这句话推断用户已经批准。

任务完成后将执行历史归档一份到 docs/progress/<key>.md，保留原文和证据链接；已有归档先读取，不能覆盖或重复复制。未解决问题仍留在当前交接中。移动历史不要求翻译原文，新写的项目知识遵循 document_language。

接手时按 Progress → 当前 Feature → 相关历史/证据 → 实际差异的顺序读取，核对已有授权和现在的代码。历史完成与当前内容是否重新验证是不同事实；后续迁移不应伪造过去曾做过的检查。

换到新线程继续

对话过长、经过多次压缩，或需要换一个任务继续时，可以让原线程先生成交接提示词。按实际需要使用，不设置必须换线程的压缩次数。

  1. 在原线程发送提示词库中“Godot 项目开发 → 验证与收尾 → 整理进度与任务交接”，填入当前任务与用途。Agent 只整理必要的现有 Progress/历史，并生成一个完整的交接代码块。
  2. 检查输出是否包含原始目标与最新要求、实际项目/worktree 路径、当前分支、修改归属、真实停点、已有授权、实际检查和下一步。交接内容应当已经填好具体信息；未知事项保留为未知。
  3. 在同一个实际项目目录或原 worktree 中打开新任务，把整个代码块复制过去。复制的是原线程生成的结果；库中的提示词用于让原线程整理上下文。原线程输出后停止实施，避免两边继续改同一份文件。
  4. 新线程先读取项目规则、相关记录与实际差异，确认原任务现场后，从真实阶段继续。已有具体授权仍然有效；未取得的人工验收、未运行的检查和失效的旧结果仍须如实处理。

交接内容还应区分会话中仍有效的协作原则、当前步骤限制与已被后续明确要求替代的旧限制。生成交接文本这一步的文档整理或只读范围、代码块输出和停止约定，不作为接收方后续任务的永久限制；原任务仍有效的范围继续保留。

交接摘要帮助定位事实，项目原文和实际文件仍需核对。无需为了换线程提交未完成代码、清空工作区、另开分支、重建台账或重跑所有检查；未提交修改按项目规则确认归属并保留。若原线程仍有命令运行，交接写明已知状态，新线程先确认是否结束及结果是否可用，再继续相关操作。

框架维护中的未完成任务使用“Yaya 框架维护 → 维护与复盘 → 生成新线程交接提示词”。该入口只读仓库与会话，保留框架和具体游戏的职责边界，不建立维护 Progress 或交接状态文件。两类正式提示词都只维护在 提示词库，这里不复制正文，也不自动创建或投递新任务。

报告保留与清理

当前验证、人工验收、未解决失败或后续工作需要的报告继续保留。默认报告不进入 Git，因此代码提交不保证另一台机器拥有报告原件。需要跨目录或跨机器交接时说明实际可用证据，缺失原件不能靠提交说明补成通过。

清理报告是明确的维护动作：读取拟处理目录和当前引用，只清理已理解且获授权的输出。目录较旧、后面有成功运行、文件未被 Git 跟踪，都不自动授权删除。测试运行器不会自动清理旧报告，也不需要额外的保留登记表。

依据：历史与报告规范、架构与 ADR 规范。

路径与命令的写法

以下是配置片段示例，不是可覆盖整个配置文件的 ready 配置；其中 Godot 路径必须换成该项目已经确认的值：

json
{
  "python_executable": "C:\\Users\\89523\\anaconda3\\envs\\codex-python\\python.exe",
  "test_cmd": "\"C:\\Users\\89523\\anaconda3\\envs\\codex-python\\python.exe\" -B tools/testing/run-gdunit-tests.py --godot-binary \"C:\\Godot\\Godot.exe\""
}

JSON 中反斜杠写成 \\，命令内的双引号写成 \"。路径字段本身不需要额外嵌入引号：带空格的可执行文件路径仍是完整的一个值。不能把 $env:...、& 或 --version 当作可执行文件路径的一部分。

PowerShell 直接调用路径变量时使用调用运算符，并把参数分开传入：

powershell
$projectConfig = Get-Content -LiteralPath 'docs/methodology-config.json' -Raw | ConvertFrom-Json
$projectPython = $projectConfig.python_executable
$projectGodot = $projectConfig.environment_bootstrap.engine_executable
& $projectPython -B tools/checks/check-project-environment.py --require-ready
$LASTEXITCODE

test_cmd 是一整条命令文本，不能用 & $projectConfig.test_cmd 把它当作一个可执行文件名。日常调用可按已确认命令展开为独立参数，示例见 命令参考。

Godot 的 engine_executable 必须是实际文件路径，可以是绝对路径，也可以相对项目根目录；环境检查和测试运行器使用同一解析方式，不去 PATH 寻找同名安装。python_executable 仍支持完整路径或 PATH 中的命令名。路径字段不含额外 shell 引号或参数，带空格和非 ASCII 字符的完整工具路径可保留。

项目输出目录禁止中文或空白，与工具路径字段能否包含空格是两个不同约束。不要把创建器的目录限制误套到所有配置字符串上。

文档语言

document_language 控制新生成的 Product、Feature 自然语言、Progress 和项目知识。zh-CN 与 en 是当前规范明确给出示例的语言；其他合规语言标签按现有规范处理，不扩展验证声明。

环境检查器会检查基本字符和分段形式，拒绝 zh_CN、包含空白、空子段或子段超过八个字符等输入，并保留原值的大小写。它不验证完整 BCP 47 子段顺序或注册信息，也不代替用户确认；特殊标签的合法性和使用选择仍由 Agent 按语言规范核对。

JSON 键、Feature ID、pending 等状态、manual 等枚举、文件路径、Skill 名称、命令和测试 ID 保持不变。聊天换语言不会自动翻译项目。修改已建立的文档语言需要核对活动文档、标题锚点和历史范围；只改一个配置字段不等于完成迁移。

复制阶段不会把英文模板翻译成中文。后续生成内容遵循已确认的语言与模板结构，不删除不适用章节来缩短模板，也不建立平行的翻译版 Skill 树。详见 文档语言约定。

用户发送的任务提示词可以使用当前会话语言；其产出的持久项目内容仍遵循 document_language，不因此翻译工作流规范或 Skill。

常见组合

  • 先想清楚：project-clarifier → 对话结论；有术语落盘授权时交给 standardizer，按需更新 CONTEXT 或局部定义。
  • 新游戏：Product standardizer → 按需 init/spec/UI/audio → 只拆当前 Product → 完成它的 Feature → 复核并按授权拆下一 Product。
  • 改需求：Product standardizer → 同步对已有任务的影响；仅后续未拆分 Product 的变化先留在需求文档中。
  • 修独立 Bug：工程 standardizer 的 bug 模式 → execute → 回归、适用验收与经验。
  • 选择重构：pick-refactor-smell → 工程 standardizer 的 refactor 模式 → execute。
  • 当前任务中断：读取 Progress 和原任务 → execute 从真实阶段继续。
  • 只读调查：按明确问题读取资料并报告；调查本身不自动进入实现。

这些组合用于理解职责，不要求每个任务机械调用所有 Skill。当前用户明确范围和已有具体授权优先，重要未决问题仍需解决。init/spec/audio 只补问材料中缺失且影响决定的内容，不设模块、AC 或问答数量下限；UI 草图和 HTML 探索按实际需要选择。

所有项目命令在生成后的项目根目录运行。按当前任务调用所需入口，以下命令参考不意味着每次都要整页执行。涉及写记录的命令遵循对应 Skill 和已有授权。

调用准备

先确认项目配置已经就绪。本页 PowerShell 示例共用以下变量：

powershell
$projectConfig = Get-Content -LiteralPath 'docs/methodology-config.json' -Raw | ConvertFrom-Json
$projectPython = $projectConfig.python_executable
$projectGodot = $projectConfig.environment_bootstrap.engine_executable

在本机，python_executable 应是个人规则指定并已确认的完整解释器路径。F001 和示例脚本路径都需换成实际存在的任务与文件。每条原生命令后立即读取 $LASTEXITCODE；缺失退出码不能当作 0。

新项目首次 CLI 测试或项目脚本运行前，按 首次扫描说明 处理编辑器准备；配置 ready 不代替这次扫描。

入口与副作用

入口 常用参数 行为
tools/checks/check-project-environment.py --require-ready、--config 读配置；就绪检查可能启动 Godot --version，不写配置
tools/checks/check-feature-list.py --eligible、--completion-feature F001、--repo-root 读 Feature/测试登记表/历史和依赖，不修改台账、不运行测试
tools/testing/run-gdunit-tests.py --godot-binary、--feature 或 --target、--phase、--scope 启动真实 Godot 测试进程，写隔离的运行目录
.agents/skills/execute-next-feature/scripts/record-feature-completion.py 子命令与 --feature；全局 --repo-root 在子命令之前 写入测试/人工记录，或只读展示、校验已有依据
.agents/skills/generate-feature-list/scripts/merge_test_registry.py --components 在项目根目录运行，将批准的组件合并到固定的 docs/test-registry.json；属于规划写操作

测试登记表合并应使用 generate-feature-list 提供的实际输入结构与约束，不用临时生成的空文件替代历史测试登记表。它不负责生成真实测试或证明测试通过。

环境与台账检查

powershell
& $projectPython -B tools/checks/check-project-environment.py --require-ready
$LASTEXITCODE
& $projectPython -B tools/checks/check-feature-list.py
$LASTEXITCODE
& $projectPython -B tools/checks/check-feature-list.py --eligible
$LASTEXITCODE

就绪检查细节见 首次使用。台账检查读取完整索引、详情、测试登记表和修订关系，检查 ID、字段、引用、路径、依赖与历史规则。--eligible 校验后输出依赖已满足的 pending Feature ID 集合，不能代替实现授权。

规划或同步完成后使用这个完整入口即可，它已经包含 JSON 解析；单文件语法检查只用于定位具体错误。Agent 仍需核对需求覆盖、真实依赖和历史保留，这些语义不能由结构检查代替。

--completion-feature F001 额外要求当前待完成任务的直接自动验证映射处于 active 状态。正常历史检查可以接受可追溯退役的旧测试；当前完成不能拿已退役测试替代实际验证。

三种常见测试调用

在已经批准的任务范围内，按用途选用：

powershell
# Stage 3：已有安全网，不包含尚未创建的 planned 测试。
& $projectPython -B tools/testing/run-gdunit-tests.py --godot-binary $projectGodot --feature F001 --phase baseline --scope auto
$LASTEXITCODE
powershell
# TDD 或定点诊断：替换成实际已存在的套件或目录。
& $projectPython -B tools/testing/run-gdunit-tests.py --godot-binary $projectGodot --target tests/features/F001/example_test.gd
$LASTEXITCODE
powershell
# Stage 4：读取当前 Feature/测试登记表和已批准范围。
& $projectPython -B tools/testing/run-gdunit-tests.py --godot-binary $projectGodot --feature F001 --scope auto
$LASTEXITCODE

--feature 与 --target 互斥；两者都不传时 target 默认为 tests。--phase 支持 baseline、final，默认 final。baseline 和 focused/target 运行用于基线或调试，不能直接作为当前 Feature 完成依据。

其他参数：--timeout-seconds 默认 120，必须是大于 0 的有限数；--require-test 使用 <suite-path>::<test-case> 格式，要求原始报告确实覆盖该用例；--continue 传给 gdUnit 的 -c，不表示继续一个已有 Yaya 任务或复用上次报告。

运行器启动真实引擎和测试，而非纯文件检查。所需权限、窗口行为与运行范围按当前项目和任务确认；不能因为名字含“测试”就认为无副作用。

测试范围怎样计算

Stage 1 的完整测试范围规则见测试规范中的 Test Impact Review 与 Runtime Test Impact selection。下文用中文说明 Required、affected、full 与命令的对应关系。

text
Required Test Set =
  当前 Feature 的自动验收测试
  + 当前 Feature 的回归测试
  + 影响组件已登记的 unit_test_paths
  + 与影响组件相交的 active 历史回归
  + 与影响组件相交的 active 不变量
  + 已批准的 additional_tests

affected = Required + 与影响组件相交的 active 验收测试
--scope 用途
auto 默认执行 affected；当前计划需要全量时升级为 full
required 显式运行 Required，适合局部迭代；不能据此绕过最终 affected/full 要求
affected Required 加相关验收测试
full 运行配置的现有测试根目录范围，并核对必需覆盖

影响组件设有 full_suite_on_change、已批准的 full_suite_reasons、广泛工具链影响或无法界定影响时，需要按规范执行 full；工程维护标签本身不触发升级。附加测试及理由保存在 Feature 的 verification.test_impact，没有独立计划文件。

没有单元套件的组件使用 unit_test_paths: []，不产生虚构选择器。已登记路径丢失、被选中目录零测试、必需用例跳过或报告缺失都不能记为通过。不存在且未登记的测试层不会贡献全量选择器；这不把空项目变成有成功测试证据的项目。

一次运行留下什么

每次调用创建 reports/gdunit-wrapper/run-<id>/，输出真实 result.json 路径。使用命令打印的路径，不猜测 run ID 或报告文件夹编号。

text
reports/gdunit-wrapper/run-<id>/
├── result.json                 同一个文件从运行中更新为成功或失败
├── engine.log                  原始引擎输出
├── discovery.json              实际展开后的测试发现集合
└── report_<...>/
    ├── results.xml             原始 JUnit
    └── diagnostics.jsonl       运行诊断

启动或中途失败时，部分原件可能尚未产生；缺失本身就是要读取的结果，不应补造空报告。实际报告还可能包含 gdUnit 生成的其他文件。

运行器核对过程结果、实际发现集合、JUnit 用例和诊断。参数化用例需要对应真实展开后的集合，源码里存在 test_* 方法不证明它实际执行。JUnit 看起来成功也不能遮住引擎错误或未完成运行。

同一内容上的较新失败需要由之后覆盖该失败范围的成功解决；更早成功或更窄的通过不能盖掉它。保留原始失败，再说明修复与后续结果。

记录完成依据

完成依据入口位于执行 Skill 的 scripts/。下表是参数速查，不是让使用者批量填“通过”的步骤：

子命令 何时使用

当前 lint CLI 的退出码：0 表示无问题或仅 Info，1 表示 Warning，2 表示 Critical，3 表示输入无效、空发现、配置错误或 JSON 报告写入失败。--severity 和 --top 只影响显示，不会抹去真实判定。--output 支持 JSON 和 HTML 文件；默认文件名 code_quality_report.html 仅用于 HTML。报告真实范围与 Critical/Warning/Info 数量，未知数量不能写成零。

解析证明脚本在实际引擎中的相关语法/类型契约，lint 检查配置的质量规则；两者都不替代运行、资源、场景、导出或人工质量判断。需要编辑器检查时遵循本机项目规则的沙箱外审批路径。普通 Feature 不增加单独导入阶段。
