# 框架的复制与运行验证

[返回手册](../README.md) · 相关：[维护与同步](updating-the-blank-project.md#按修改选择验证范围)、[创建项目](../getting-started/create-project.md)

`project-source/` 是未初始化的分发材料；不在这里启动 Godot，也不要求它拥有实际游戏的主场景、
本机就绪配置、业务需求或已完成任务。可用性通过源材料检查和独立项目中的真实运行共同验证。

## 分层验证

| 层次 | 要检查的结果 | 证据与限制 |
| --- | --- | --- |
| 源材料与分发 | 清单可展开；相对引用、JSON/TOML、Skill 元数据、Prompt 路由及文档链接一致；默认配置仍 incomplete，Product/Feature/Registry 为空 | 静态核对及创建器回归；不代表引擎或 Agent 已执行 |
| 项目工具 | 在指定外部项目调用既有工具回归，验证输入拒绝、任务规划/演进、测试选择、证据、人工记录及文档指纹 | unittest 是工具契约验证；合成夹具不是实际游戏或人工体验 |
| 新项目初始化 | 从正式复制清单创建全新外部目录；核实工具版本、配置 ready、正常导入、建立项目入口 | 保留实际命令、退出码、配置与初始化报告；ready 不等于测试通过 |
| 真实 Godot 行为 | 导入真实资源；解析、lint、gdUnit、独立入口及消费场景实际运行；按本次变化检查保存、重载、取消、音频和生命周期 | 原始引擎/JUnit/诊断、可选截图与运行观察；画面和声音的人工接受单独记录 |
| 工作流与迁移 | 对一个明确的小任务，实际经过需求、规划、开发/维护、验证、记录和续接；再在新路径从无缓存副本核对启动与资源引用 | 标明实际执行的 Skill/脚本和未经过分支；不能据一次样例宣称全部 Skill、所有提示词及所有平台已验证 |

每次按改动选择适用层，不要求纯文档修改也建立游戏项目。
现有命令在 [维护工具](../../../README.md#按需检查)；实际流程入口仍是提示词库中的“通过实际任务动态审核框架流程”。
Skill 是 Agent 阅读的方法，Prompt 是输入；格式检查、脚本测试和一次真实委派是三种不同证据。
reviewer/researcher 的客户端加载与独立实例执行没有实测时，必须明确保留未验证项。

## 测试载体与文件归属

优先从当前源材料创建一个全新外部测试项目，再完成 Godot 初始化。
这样同时检验“复制是否完整”和“初始化后能否继续开发”，避免已有项目的缓存或旧文件遮住遗漏。
测试项目独立拥有文件，本次授权内修正具体文件后继续验证；不增加自动同步或升级机制。

| 文件类别 | 保留位置 | 是否回到分发材料 |
| --- | --- | --- |
| 框架通用代码、必要第三方依赖和明确提供的 `example-*` 素材 | `project-source/` | 属于正式分发源，通过清单复制 |
| Godot 为这些源文件生成的可移植 `.gd.uid`、素材 `.import` | 经目标版本核验后随对应源文件保留 | 可以，范围限定在本次正式分发文件；不复制 `.godot` 缓存 |
| 回归套件、截图驱动、合成任务与测试资源 | `framework/tests/` 的维护夹具，以及外部项目 `tests/` | 不进入 `project-source/` 或复制清单 |
| 测试项目名称/主场景、本机 ready 配置、Product、Feature、测试登记表、Git 历史 | 外部测试项目 | 不回灌；空白默认状态保持为空/未就绪 |
| 导入缓存、引擎日志、JUnit、截图、测试运行证据 | 外部项目 `.godot/`、`reports/` | 不回灌；维护报告只链接和总结事实 |

已经初始化且非空的项目可以作为有明确范围的集成验证载体，但不能直接用创建器覆盖。
现有创建器只接受不存在或空的目标；已有 `project.godot`、机器配置与业务文件须按接入/迁移范围逐项合并。
对新使用者，首选“创建外部空目录 → 复制 → 初始化 → 开发”的路径。

## 一次有意义的流程抽样

从未初始化副本开始，核对环境检查对 incomplete 和 ready 的不同结果，再建立一个很小的真实任务。
使用项目自己的 Skill/规范准备需求、AC、Feature 与 Registry；实际调用检查、测试运行和完成记录工具，
保留失败及修复后的结果，更新本项目 Progress/notes，并按授权完成本地提交与交接。

当前新增工作台已有实现时，可以把“复制后验证试调隔离、保存和消费一致性”作为维护任务；
不要伪称从需求到实现都重新执行过，也不要把补录文档称为当时发生的需求讨论或 TDD。
需要验证从零生成需求和开发的完整分支时，另按动态审核入口执行一个新微型功能，复用已确认授权。
涉及主观观感、音色与手感的 AC 保持人工待验收，实施授权和自动化通过都不能替代它。

迁移检查使用另一条干净路径、无 `.godot` 缓存和无已初始化数据的副本重新导入、加载资源与启动入口。
可以在指定测试项目已被 `.gdignore` 排除的报告区放置独立子项目，避免外层 Godot 扫描到重复全局类。
这证明本次版本在所测 Windows/Godot 版本和路径下可重建；跨机器仍需重新完成工具路径配置与验证。

## 本次工作台的回归入口

维护用例在 `framework/tests/project/asset_workbench_test.gd`，只复制到指定外部项目的
`tests/features/asset_workbench/asset_workbench_test.gd` 后，使用现有 `run-gdunit-tests.py --target` 或已登记 Feature 运行。
它覆盖试调隔离、磁盘冲突、无效参数、边界值、保存后游戏消费、延迟取消、声音重叠上限、浏览与绑定、A/B/连续触发及主题不修改事件数据。
测试生成的 `test-cue.tres` 留在外部测试目录，不改示例正式 Cue。

`framework/tests/project/asset_workbench_capture.gd` 在真实渲染器运行，当前截图写入外部项目 `reports/asset-workbench-ui-20260922/`。
它覆盖三个工作台入口、浅深色、1600×900 及 1152×648 / 900×540 / 720×480、图像与音频候选、固定停止/保存和真实鼠标/键盘路由。
同目录的 Shader、单项分析及批量分析渲染夹具分别检查真实像素/停止恢复、结果来源和图表/集合访问。
它们不支持 headless 截图，也不做听觉或人工接受判断；每次运行以实际日志、截图和版本为准。
首期历史结果见 [2026-09-21 首期验证报告](../../../review/reports/asset-workbench-implementation-validation-2026-09-21.md)；当前布局、行为、失败现场及人工待确认项见 [2026-09-22 UI/UX 整理与验证](../../../review/reports/asset-workbench-ui-ux-2026-09-22.md)。不能用本说明中的预期流程或旧版通过记录代替本轮实际结果。
