# 当前模块的需求已确认，准备做项目的第一份 Feature 计划

[返回场景索引](../../scenario-index.md#需求与计划) · [执行步骤](#执行步骤) · [完成标准](#完成状态与验证标准)

## 触发场景与使用时机

当前要做的模块已经讨论清楚，希望把它变成可以依次开发和验证的任务。

## 前置条件与适用范围

本页限定项目的首次规划：任务索引与修订记录均为空，当前模块及其已采用专业要求有明确来源，已获得规划授权。行为和验收意图尚不明确时，先完成需求讨论。

写入采用来源需要的正式状态和真实提交必须可核实；新规划任务按项目规则具备干净工作区。后续模块追加、修改已有计划和执行 Feature 均不在本页范围。

## 参与角色与职责边界

用户决定尚缺的重要取舍；Agent 提出拆分、维护计划并检查覆盖。台账工具检查结构、引用与依赖，不能替代 Agent 判断要求是否全部落实。

## 流程概览

核对首次规划输入 → 展示任务拆分 → 固定采用来源 → 写入计划与首次基线 → 检查并交付计划。

## 执行步骤

可用提示词入口：集中提示词库中的“Godot 项目开发 → 任务规划 → 拆分当前 Product 的 Feature”。提供当前模块、已确认来源和本次规划范围。

1. **S1 核对输入。** Agent 读取当前模块和已采用的相关规格，核对空任务索引、空修订记录及工作区。
2. **S2 展示拆分。** Agent 列出每项 Feature 的范围、验收条件（AC）、依赖和验证方式；用户解决尚缺的实质选择。已有自主拆分授权继续沿用。
3. **S3 固定来源。** Agent 核对实际采用来源，完成首次规划所需的来源提交，记录真实引用位置。
4. **S4 写入计划。** Agent 按现有规划入口合并必要测试登记，保存任务索引与详情，并建立覆盖当前已规划模块的 R000 首次基线。
5. **S5 检查并交付。** Agent 对照要求检查覆盖，执行项目的完整台账检查，核对本次差异并按项目约定提交，指出第一项任务。

## 步骤产出与状态变化

| 步骤 | 产出与继续条件 |
| --- | --- |
| S1 | 首次规划条件成立，当前模块及采用来源清楚 |
| S2 | 每项要求有任务、AC 和验证责任，拆分已在有效授权内确定 |
| S3 | 采用来源有真实提交，后续计划能引用实际内容 |
| S4 | 任务与登记已写入，R000 只覆盖实际采用范围 |
| S5 | 语义覆盖无缺口，台账检查通过，本地提交和首项任务可定位 |

## 资源与文件影响

| 项目内对象 | 影响 |
| --- | --- |
| 当前 Product 模块及已采用专业来源 | 读取，核对采用内容与来源提交 |
| `docs/feature-list.json`、`docs/features/` | 写入当前模块的任务索引和新详情 |
| `docs/test-registry.json` | 合并实际需要的组件与测试计划登记 |
| `docs/feature-list-revisions.json` | 建立 R000；不伪造历史覆盖 |
| Git | 提交本次已核对的来源和计划改动，按项目规则分别处理 |

## 异常与非正常退出

要求冲突或仍无法写出验收条件时，保留拆分建议，暂停依赖它的计划写入。来源无法提交、空台账条件不成立或存在未知修改时，保留现场，重新选择适用场景。

检查失败时在当前规划范围内修正实际缺口；未通过前不能称为可执行计划。恢复后从受影响步骤继续，不重复制造任务。

## 完成状态与验证标准

当前模块每项已确认要求都对应任务与可观察 AC；索引、详情、登记和 R000 一致；完整台账检查通过；实际提交和首项任务可定位。Feature 保持初始规划状态，本页不产生实现或测试通过结论。
