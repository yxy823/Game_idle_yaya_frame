# Bug 定位、修复与回归

[速查入口](README.md) · [执行步骤](#5-执行步骤) · [步骤产出](#6-步骤产出与状态变化) · [卡住时](#9-异常与非正常退出) · [完成判定](#10-完成状态与验证标准)

## 1. 触发场景与使用时机

开发或体验时观察到异常行为，希望确认是否为 Bug、找到原因、修复并防止同类问题复发。问题可以是间歇性的；稳定复现不是开始调查的硬性门槛。

## 2. 前置条件与适用范围

有可说明的实际现象和可检查的项目、材料或日志。调查可先明确预期与复现；开始修改前需有有效预期、任务归属、具体修复授权及相应写入前提。

只有测试或导入失败、尚不能证明实现错误时，先走验证恢复。用户要改变原要求时转需求变化。本页完整终点是根因、修复和适用回归满足后交回正式交付；仅诊断请求以证据、未知与建议交付。

## 3. 参与角色与职责边界

| 主体 | 负责什么 |
| --- | --- |
| 用户 | 提供现象与体验材料，解决缺少的行为决定，完成适用人工体验 |
| Agent | 固定现场、核实预期和归属、定位根因、实施获准修复并检查结果 |
| 测试工具与 Godot | 执行真实测试或引擎运行，产出原始结果；不自动决定任务完成 |

原未完成 Feature 内的缺陷继续归原任务。已完成行为的独立缺陷按工程 Bug 入口承接；无关缺陷不能悄悄并入当前范围。

## 4. 流程概览

固定现象 → 核实有效预期与任务归属 → 定位根因 → 建立回归并修复 → 复验最终内容 → 保存适用经验 → 回交付核对。

## 5. 执行步骤

提示词入口：`Godot 项目开发 → 修复与改进 → 定位与修复 Bug`。提供实际表现、预期及来源、已知触发条件、环境和日志等材料，说明本次是诊断还是包含修复。

1. **S1 固定失败现场。** Agent 记录实际版本、未提交差异、环境和最短已知触发，保留原始失败材料及尝试范围。
2. **S2 核实预期与归属。** Agent 对照 Product、专业规格、工具契约或 AC，确认行为差异及负责修复的任务。
3. **S3 定位根因。** Agent 追查代码、场景、资源和调用路径，把已证实原因与假设分开，按适用要求维护诊断记录。
4. **S4 建立回归并修复。** Agent 用原触发建立有意义的自动回归，或说明不适合自动化的原因与可重复人工路径，再实施最小完整修复。
5. **S5 复验最终内容。** Agent 验证原错误及受影响范围，取得当前任务需要的自动、静态、专项结果与适用人工体验，检查临时诊断改动的影响。
6. **S6 保存经验并移交。** 工程 Bug 按 Stage 5.5 留下有用根因、触发和防范信息；Agent 把修复与当前验证交回正常交付。

## 6. 步骤产出与状态变化

| 步骤 | 直接产出与可继续的判据 |
| --- | --- |
| S1 | 现象可复述且有实际材料；不能稳定复现时，限制与已尝试范围明确 |
| S2 | 有效预期、实际差异和唯一负责任务明确 |
| S3 | 根因已确认，或尚缺事实和下一次调查明确；假设不能作为修复已成立的依据 |
| S4 | 回归能暴露目标错误并验证修复；环境错误不充当目标行为失败 |
| S5 | 最终内容满足当前所需覆盖，原触发与受影响行为已验证，适用人工结果真实有效 |
| S6 | 适用经验有事实依据，交付入口及剩余义务明确；没有直接跳到 `done` |

## 7. 资源与文件影响

| 对象（生成项目内） | 影响类型与发生条件 |
| --- | --- |
| Product、专业规格、工具契约、原始日志与材料 | 读取与保留；不修改预期迁就错误实现 |
| 当前 Feature；独立 Bug 的计划与详情 | 核实归属，按授权创建或更新必要诊断、验证与 notes |
| 实际出错的脚本、场景或资源 | 根因和范围明确后修改；配置仅在确实属于原因时修改 |
| `tests/`、`docs/test-registry.json` | 适合自动化时新增或修改针对性回归及真实登记 |
| 本次运行报告、现有完成依据 | 保存真实运行；需导入时按完成依据契约记录，保留失败原件 |
| 临时诊断改动、经验与知识 | 修复定稿时处理临时内容；只保存有价值且获准的记录，不自动升级成全局规则 |

## 8. 条件分支与路径规则

| 条件 | 路径与汇合位置 |
| --- | --- |
| 预期缺失或冲突 | 交所属来源澄清，再回 S2；用户改变要求则转[需求变化](requirements-change.md) |
| 缺陷属于当前未完成 Feature | 保留原任务，继续 S3；独立缺陷按工程 Bug 入口建立责任后到 S3 |
| 原始问题不适合自动化 | 在 S4 说明原因和可重复人工回归，不制造无效测试 |
| S5 测试或人工结果未满足要求 | 按已知问题回 S3/S4；运行或导入层失败先转[验证恢复](verification-recovery.md) |
| 间歇问题暂未复现 | 继续有依据的调查；一次未出现不视为修复，也不直接进入完成 |
| 只要求诊断 | 交付证据、已确认原因或具体未知与下一动作，不执行未经授权的修改 |

## 9. 异常与非正常退出

| 无法继续的情况 | 停止范围、保留与恢复 |
| --- | --- |
| 必需现场或日志不可得，无法推进根因确认 | 保留已知现象、假设和尝试，指出最小补查；材料到位后回 S1/S3 |
| 环境无法提供必要验证 | 保留修复和原始错误，暂停完成结论；恢复条件后回 S5 |
| 修复需要新的产品决定或超出原范围 | 保留诊断，暂停依赖的修改；获得缺少决定后回 S2/S4 |
| 当前差异归属不清 | 保留全部现场，先核实所属任务；满足写入前提后继续 |

## 10. 完成状态与验证标准

完整修复场景完成时：错误行为与有效要求的差异明确；根因有证据；修复归属正确；回归能检验原始问题；最终内容已取得适用验证与人工结果；工程 Bug 的必要经验已记录；可转入正式交付核对。

未复现、原因仍是假设、缺少必要验证均不能称为修复完成。仅诊断的结果要明确调查边界；整个 Feature 的 `done` 仍由交付流程判断。

## 11. 流程关联与衔接关系

- 上游：开发、实际体验、[验证恢复](verification-recovery.md)或独立审核发现的已确认缺陷。
- 分流：[需求变化](requirements-change.md)、[中断与切换](../guides/scenarios-context-handoff.md#feature-中途切换中断或临时插入其他工作)。
- 下游：[Feature 交付](feature-delivery.md)。
