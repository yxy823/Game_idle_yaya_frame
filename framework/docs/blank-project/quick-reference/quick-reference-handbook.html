11 栏是信息目录。实际顺序以第 4、5、8 栏为准；每页顶部可直接跳到动作、产出、阻塞和完成判定。第 5 栏的 S1、S2 等步骤与第 6 栏同编号对应；S 编号只用于本页导航，不是新的 Stage、任务 ID 或台账字段。第 8 栏负责判断去向，第 11 栏集中提供相关流程与依据。

共用的操作边界

  • 工作位置： 八个场景均面向生成后的游戏项目。正文中的 docs/、tools/、场景与资源路径相对该项目根目录；来源链接指向框架材料，实际操作时核对项目自己的副本。F0XX、<scope> 等须换成真实对象。
  • 范围与授权： 用户提供目标、必要决定和真实体验结果，Agent 完成已有具体授权内的工作。只诊断、只规划、只写规格分别在其约定成果处结束；已有端到端授权继续沿用。人工接受必须来自实际反馈。
  • 写入前提： 新写入任务按项目规则从干净工作区开始；续接须核实未提交改动都属于原任务。混合或未知差异未厘清时保留现场，先做允许的只读核对。独立同步另有已提交来源前置，见需求变更样稿。
  • 结果表述： 第 6 栏中的“已定位”“待试听”等通常是事实描述，不自动写成 Feature 状态。场景完成、正常移交和 Feature done 分别判断；失败、未执行、过期依据和有效结果分别记录。
  • 缺口与恢复： 预期内的返工、交接和等待见第 8 栏；无法完成必要动作时见第 9 栏。只暂停依赖缺口的工作。没有相关内容写“不适用”，尚不知道则写“待确认”。

实际命令及准备见命令与验证。操作提示词正文统一在 framework/prompts.json，各页只给入口名称和所需输入，不另存一份提示词。

新功能形成可执行计划

速查入口 · 执行步骤 · 步骤产出 · 卡住时 · 完成判定

1. 触发场景与使用时机

有一个新玩法、功能想法或已有 GDD，希望把当前要做的模块整理成可执行任务。此时允许需求尚有待定问题；澄清这些问题属于本流程。

2. 前置条件与适用范围

已明确要讨论或规划的对象，并有可读取的想法、材料或用户说明。纯讨论可先进行；写入要求项目已建立，且满足共用写入前提。需要向空目录保存项目材料时先创建项目；环境准备在后续编码前完成，不作为需求讨论的门槛。

本页终点是当前模块的正式来源和可执行计划。已有有效计划直接复用；已规划范围的要求改变转计划同步；实现违背现有要求转 Bug。仅整理需求的授权不包含计划写入或实现。

3. 参与角色与职责边界

主体 负责什么
用户 提供目标，决定影响验收的未决行为与重要取舍
Agent 读取当前材料，按所属入口维护需求，展示拆分方案，完成获准的规划与检查
台账检查工具 检查文件结构、引用和依赖；语义覆盖仍由 Agent 核对

已有明确决定直接沿用。普通规划在写入前确认具体拆分方案；用户已明确授权自主拆分时，展示方案后继续，不重复索取同一授权。

4. 流程概览

定位当前模块 → 澄清可观察行为 → 保存所属来源 → 判断是否需要规划 → 展示并保存计划 → 交付计划或进入已授权实施。

5. 执行步骤

提示词入口：Godot 项目开发 → 需求设计 → 从想法或已有 GDD 整理 Product 并衔接规划。提供材料、当前模块、限制及本次允许讨论、写入或实施的范围。已有完整 Product 时可用 任务规划 → 拆分当前 Product 的 Feature。

  1. S1 定位当前工作。 Agent 核对项目、当前模块、已有任务与本次范围，读取相关 Progress 和文件差异。
  2. S2 明确验收意图。 Agent 梳理输入、行为、输出、边界与不做的部分；用户补齐会改变当前验收的决定。
  3. S3 保存权威来源。 Agent 把行为要求写入 Product，把专业要求交给相应入口，按原任务归属处理来源提交。
  4. S4 判断计划缺口。 Agent 对照已有 Feature，选择复用、同步或首次拆分；确认前置模块已交付，只拆当前模块。
  5. S5 展示并写入计划。 Agent 展示数量、范围、依赖及“要求 → Feature/AC → 检查”的对应；授权和来源前置齐备后写入，完成覆盖与台账检查。
  6. S6 交接下一动作。 Agent 给出实际任务 ID、来源、剩余义务和提交结果；按已有授权进入实施或在规划范围结束。

各步达到下一节同编号判据后继续；需要改道时查第 8 栏。

6. 步骤产出与状态变化

步骤 直接产出与可继续的判据
S1 当前模块、已有任务及允许动作明确；未知差异已说明，写入前归属可核实
S2 当前行为可观察、可验证；影响验收的冲突已解决
S3 已确认要求位于正确来源，可引用；需要来源提交的后续步骤已具备真实提交
S4 复用、同步或首次拆分的选择有依据，没有重复任务或提前拆分后续模块
S5 写入的计划、测试登记表及适用修订一致，台账检查通过，语义覆盖无未说明缺口
S6 用户可定位具体任务和第一步；计划完成与尚待实现、验证的工作分别说明

7. 资源与文件影响

对象（生成项目内） 影响类型与发生条件
用户提供的 GDD、相关规则与已有记录 读取；保留外部原件
docs/product.md、docs/product/ 与适用专业来源 获准整理需求时新增或修改；来源按职责分别维护
docs/feature-list.json、docs/features/F0XX.json 获准保存计划时修改索引、创建任务详情
docs/test-registry.json 按实际计划补充组件与逻辑测试登记；不伪造已存在的测试或通过结果
docs/feature-list-revisions.json 符合空台账首次规划条件时建立 R000；后续模块规划保留旧记录与锚点
Git 与现有 Progress 按所属任务提交；有必要续接信息时更新 Progress

8. 条件分支与路径规则

条件 路径与汇合位置
S4 已有完整有效计划 复用计划，直接到 S6
S4 已有计划但要求变了 转需求变化后对齐计划，完成后回 S6
Feature 索引与修订记录在首次规划前均为空 S5 前确认采用来源已提交；覆盖核对后建立 R000，再完成最终台账检查
后续 Product 的首次拆分 追加任务，保留全部修订记录，不推进旧锚点；继续 S6
本次只整理需求或只讨论 到约定来源或讨论成果即交付，明确未建立计划
S6 已有实施授权且环境、依赖齐备 进入原 Feature 的 Stage 0–1；否则交付计划与所缺前置

9. 异常与非正常退出

无法继续的情况 停止范围、保留与恢复
决定矛盾，无法写出可观察验收条件 暂停依赖该决定的规划，保留已有提案；用户解决后回 S2
来源无法提交、采用状态不明，或 WIP 归属不清 保留现场与分析；暂停依赖这些前置的写入，核实后回 S3/S5，不伪造 R000
台账或覆盖检查失败 不交付“可执行计划”的结论；按实际缺口修正 S5 并重查

10. 完成状态与验证标准

完整规划完成时：当前要求有可定位来源；本模块每项要求对应 Feature/AC 与检查方式，排除项和缺口明确；实际写入的计划通过台账检查；来源、适用基线和本地提交符合约定；下一任务与剩余实现、验证范围可定位。

只完成讨论或需求整理时，报告对应成果与尚未进入的步骤。计划完成不设置 Feature done，也不证明游戏已实现或验证通过。

11. 流程关联与衔接关系

  • 上游：创建项目、首次使用。
  • 分流：需求变化、Bug 修复。
  • 下游：Feature 开发主线；有视觉前置时进入 UI 原型。

详细说明：原新功能检查单。直接依据：当前模块规划与拆分预览、首次规划基线。

需求变化后对齐已有计划

速查入口 · 执行步骤 · 步骤产出 · 卡住时 · 完成判定

1. 触发场景与使用时机

用户已决定改变玩法行为、UI/美术/声音等专业要求或适用规则，已有任务和验证可能仍按旧要求执行。Product 没有改动、仅专业规格变化也属于本场景。

2. 前置条件与适用范围

有明确采用决定、可定位的新旧要求以及可能受影响的已有计划。尚未采纳的建议保留为提案；不清楚文档还是实现错误时先做一致性核对。

可先只读分析影响。独立同步写入前，来源应已由所属入口保存并提交，且满足项目的工作区前提；当前 Feature 内的辅助修改保持原归属，不能在混合 WIP 上另起同步。本页终点是计划与验证责任对齐；同步入口本身不执行 Feature。

3. 参与角色与职责边界

主体 负责什么

只交付规格或制作输入时，明确尚缺文件、接入或试听。接入和试听完成不自动满足原 Feature 的全部测试与最终验收。

11. 流程关联与衔接关系

  • 上游：新功能规划、UI 原型中的反馈需求。
  • 依赖：资源准备、资源接入；单项或组合试听可查资源工作台。
  • 下游：需求变化、Feature 交付。

详细说明：原声音检查单。直接依据：专业制作与接入边界、音频规格 Skill。

Bug 定位、修复与回归

速查入口 · 执行步骤 · 步骤产出 · 卡住时 · 完成判定

1. 触发场景与使用时机

开发或体验时观察到异常行为，希望确认是否为 Bug、找到原因、修复并防止同类问题复发。问题可以是间歇性的；稳定复现不是开始调查的硬性门槛。

2. 前置条件与适用范围

有可说明的实际现象和可检查的项目、材料或日志。调查可先明确预期与复现；开始修改前需有有效预期、任务归属、具体修复授权及相应写入前提。

只有测试或导入失败、尚不能证明实现错误时，先走验证恢复。用户要改变原要求时转需求变化。本页完整终点是根因、修复和适用回归满足后交回正式交付；仅诊断请求以证据、未知与建议交付。

3. 参与角色与职责边界

主体 负责什么
用户 提供现象与体验材料，解决缺少的行为决定，完成适用人工体验
Agent 固定现场、核实预期和归属、定位根因、实施获准修复并检查结果
测试工具与 Godot 执行真实测试或引擎运行，产出原始结果；不自动决定任务完成

原未完成 Feature 内的缺陷继续归原任务。已完成行为的独立缺陷按工程 Bug 入口承接；无关缺陷不能悄悄并入当前范围。

4. 流程概览

固定现象 → 核实有效预期与任务归属 → 定位根因 → 建立回归并修复 → 复验最终内容 → 保存适用经验 → 回交付核对。

5. 执行步骤

提示词入口：Godot 项目开发 → 修复与改进 → 定位与修复 Bug。提供实际表现、预期及来源、已知触发条件、环境和日志等材料，说明本次是诊断还是包含修复。

  1. S1 固定失败现场。 Agent 记录实际版本、未提交差异、环境和最短已知触发，保留原始失败材料及尝试范围。
  2. S2 核实预期与归属。 Agent 对照 Product、专业规格、工具契约或 AC，确认行为差异及负责修复的任务。
  3. S3 定位根因。 Agent 追查代码、场景、资源和调用路径，把已证实原因与假设分开，按适用要求维护诊断记录。
  4. S4 建立回归并修复。 Agent 用原触发建立有意义的自动回归，或说明不适合自动化的原因与可重复人工路径，再实施最小完整修复。
  5. S5 复验最终内容。 Agent 验证原错误及受影响范围，取得当前任务需要的自动、静态、专项结果与适用人工体验，检查临时诊断改动的影响。
  6. S6 保存经验并移交。 工程 Bug 按 Stage 5.5 留下有用根因、触发和防范信息；Agent 把修复与当前验证交回正常交付。

6. 步骤产出与状态变化

步骤 直接产出与可继续的判据
S1 现象可复述且有实际材料；不能稳定复现时，限制与已尝试范围明确
S2 有效预期、实际差异和唯一负责任务明确
S3 根因已确认，或尚缺事实和下一次调查明确；假设不能作为修复已成立的依据
S4 回归能暴露目标错误并验证修复；环境错误不充当目标行为失败
S5 最终内容满足当前所需覆盖，原触发与受影响行为已验证，适用人工结果真实有效
S6 适用经验有事实依据，交付入口及剩余义务明确；没有直接跳到 done

7. 资源与文件影响

对象（生成项目内） 影响类型与发生条件
Product、专业规格、工具契约、原始日志与材料 读取与保留；不修改预期迁就错误实现
当前 Feature；独立 Bug 的计划与详情 核实归属，按授权创建或更新必要诊断、验证与 notes
实际出错的脚本、场景或资源 根因和范围明确后修改；配置仅在确实属于原因时修改
tests/、docs/test-registry.json 适合自动化时新增或修改针对性回归及真实登记
本次运行报告、现有完成依据 保存真实运行；需导入时按完成依据契约记录，保留失败原件
临时诊断改动、经验与知识 修复定稿时处理临时内容；只保存有价值且获准的记录，不自动升级成全局规则

8. 条件分支与路径规则

条件 路径与汇合位置
预期缺失或冲突 交所属来源澄清，再回 S2；用户改变要求则转需求变化
缺陷属于当前未完成 Feature 保留原任务，继续 S3；独立缺陷按工程 Bug 入口建立责任后到 S3
原始问题不适合自动化 在 S4 说明原因和可重复人工回归，不制造无效测试
S5 测试或人工结果未满足要求 按已知问题回 S3/S4；运行或导入层失败先转验证恢复
间歇问题暂未复现 继续有依据的调查；一次未出现不视为修复，也不直接进入完成
只要求诊断 交付证据、已确认原因或具体未知与下一动作，不执行未经授权的修改

9. 异常与非正常退出

无法继续的情况 停止范围、保留与恢复
必需现场或日志不可得，无法推进根因确认 保留已知现象、假设和尝试，指出最小补查；材料到位后回 S1/S3
环境无法提供必要验证 保留修复和原始错误，暂停完成结论；恢复条件后回 S5
修复需要新的产品决定或超出原范围 保留诊断，暂停依赖的修改；获得缺少决定后回 S2/S4
当前差异归属不清 保留全部现场，先核实所属任务；满足写入前提后继续

10. 完成状态与验证标准

完整修复场景完成时：错误行为与有效要求的差异明确；根因有证据；修复归属正确；回归能检验原始问题；最终内容已取得适用验证与人工结果；工程 Bug 的必要经验已记录；可转入正式交付核对。

未复现、原因仍是假设、缺少必要验证均不能称为修复完成。仅诊断的结果要明确调查边界；整个 Feature 的 done 仍由交付流程判断。

11. 流程关联与衔接关系

  • 上游：开发、实际体验、验证恢复或独立审核发现的已确认缺陷。
  • 分流：需求变化、中断与切换。
  • 下游：Feature 交付。

详细说明：原 Bug 检查单。直接依据：工程变更规范、Bug 回归、Stage 5.5。

测试失败与证据恢复

速查入口 · 执行步骤 · 步骤产出 · 卡住时 · 完成判定

1. 触发场景与使用时机

测试未启动、未发现预期套件、断言或引擎诊断失败，结果无法导入，或过去的成功不能用于当前内容。先确定失败发生在哪一层，再判断要修复环境、调用、测试还是实现。

2. 前置条件与适用范围

能定位失败尝试及相关项目，具备已有输出或知道哪些原件缺失。先收集材料和诊断；执行修复前须有具体授权、可确认的契约及写入前提。

本页处理验证恢复，终点是取得当前义务需要的有效结果并返回交付核对。只有运行行为异常、尚无测试失败材料时可先走 Bug。性能、长测等专项结果使用各自契约，不能伪装为 gdUnit 报告。

3. 参与角色与职责边界

主体 负责什么
Agent 保留失败现场，判断层次与责任，执行获准修复并核实实际覆盖
测试运行器、Godot、结果导入工具 分别执行测试/引擎动作、保存原件、检查并记录证据引用
用户或要求所属入口 解决不明确或冲突的预期，以及范围外的修复决定

只验证请求不自动授权修改实现。工具成功导入只证明其负责的条件成立，不代替静态检查、专业验证或人工接受。

4. 流程概览

保存失败现场 → 判断是否实际执行及失败层 → 核对有效预期 → 确定责任并修复 → 复验正确范围 → 导入有效原件 → 返回交付。

5. 执行步骤

提示词入口：只测与诊断用 Godot 项目开发 → 验证与收尾 → 单独验证某次变更，提供对象、报告及允许的验证范围；包含修复时沿用已有任务授权或 修复与改进 → 定位与修复 Bug。

  1. S1 固定失败尝试。 Agent 记录目录、版本/差异、Feature、命令、退出码与报告位置，核实未结束的进程状态。
  2. S2 判断失败层。 Agent 查看实际结果、发现列表、日志及原件，区分未启动、发现不完整、行为断言、引擎诊断与导入失败。
  3. S3 核对预期与责任。 Agent 比较确认要求、测试和实现，确定原任务、独立 Bug 或工具修复的归属。
  4. S4 完成获准修复。 Agent 针对真实原因修正环境、调用、测试或实现；行为缺陷按适用要求建立回归。
  5. S5 复验所需范围。 Agent 先验证原触发恢复，再取得当前 Required、affected 及必要 full 范围，核对最终内容与旧证据有效性。
  6. S6 导入并返回。 Agent 用实际结果路径导入满足义务的原件，核对引用后返回静态、专项及适用人工验收等交付检查。

命令与参数查三种测试调用及导入测试结果，在实际项目中使用其已确认工具路径。

6. 步骤产出与状态变化

步骤 直接产出与可继续的判据
S1 可指出哪次尝试、哪个版本和范围失败，已有原件得到保留
S2 失败层明确，或缺失材料及最小补查明确；命令退出 0 但仅显示帮助不算测试已执行
S3 有来源依据的预期与责任分类；测试失败本身不证明测试错或实现错
S4 针对原因的修复已完成，或缺少的授权/环境明确
S5 最终版本的真实运行覆盖当前义务；较新失败被之后覆盖其失败范围的成功解决
S6 需要的测试证据已有效导入；恢复验证链路，可继续剩余交付义务

7. 资源与文件影响

对象（生成项目内） 影响类型与发生条件
失败命令输出、result.json、engine.log、发现与 JUnit 原件 读取并保留；通常位于 reports/gdunit-wrapper/<Feature-ID>/run-<id>/
当前 Feature、Registry、来源与环境配置 读取；仅在诊断证明需要且授权允许时修改对应对象
测试代码、运行器或实际实现 按确认的责任修复；只验证场景不写入
新运行目录 真正重跑时新增，需保留历史时使用未占用的运行子目录
docs/feature-completion-evidence.json 导入时更新引用；失败导入可能清除旧测试引用，不能手改哈希恢复通过
原 Progress 有阻塞或需要续接时更新具体停点及原件链接

8. 条件分支与路径规则

条件 路径与汇合位置
只有导入失败，已有满足当前义务的有效原件 修正引用后到 S6；不为修链接重复测试
未启动或发现不完整 查环境、参数、套件与运行器，到 S4/S5；不先改业务断言
测试预期错误或确认要求已变化 按真实来源修正测试及登记；要求变化先走计划对齐
实现违反有效要求 当前任务内修复，或转 Bug 场景，再回 S5
同一内容有较新失败，旧成功或较窄成功不足以覆盖 补齐 S5 的真实覆盖后再到 S6
内容、范围和原件均满足的结果已存在 复用有效结果，完成缺少的检查和导入，不机械重复运行

9. 异常与非正常退出

无法继续的情况 停止范围、保留与恢复
原件不足，不能判断执行结果或覆盖 保留已有输出，补取最小所需材料；无法恢复时执行获准验证，不据摘要补 PASS
环境、运行器或所需 full 范围不可用 暂停完成判定，记录具体缺口；条件恢复后回 S4/S5
预期冲突、修复未获准或修改归属未知 保留诊断与现场，只继续允许的只读工作；解决后回 S3/S4
导入仍因原件、版本或覆盖不符而失败 保留失败，回 S2/S5；不得转人工接受来抵消机器证据缺口

10. 完成状态与验证标准

失败原因和归属有实际依据；获准修复已完成；必要运行覆盖最终版本及当前义务；所需原件完整、引用有效且导入满足契约；未解决的失败或未完成运行已得到真实处置；可继续剩余交付检查。

JUnit 显示绿色但包装器失败、仅配置检查通过或仅报告文件存在，都不满足本场景完成条件。仅诊断时交付分类、证据与下一动作，明确恢复尚未完成。

11. 流程关联与衔接关系

  • 上游：Bug 回归、Feature 最终验证。
  • 依赖：故障排查、测试范围计算。
  • 下游：Feature 交付核对，其静态、专项和人工义务仍须分别满足。

详细说明：原验证恢复检查单。直接依据：证据与语义有效性、失效测试处置。

Feature 验证、验收与交付

速查入口 · 执行步骤 · 步骤产出 · 卡住时 · 完成判定

1. 触发场景与使用时机

当前 Feature 已有实现，希望判断是否可以进入最终验收、正式记录完成并交付。仅“代码写完”还不足以判断本场景已经结束。

2. 前置条件与适用范围

已有正式 Feature、明确 AC、批准方案与验证义务，并能读取实际实现和证据。早于正式计划的已有实现先走接管流程。只请求验证时可核对结果，不借此取得修改完成状态或实现的授权。

本页覆盖 Stage 3 文档定稿后的最终检查、适用人工验收及 Stage 7–8 收尾。正常等待人工结果与存在验证缺口均保留未完成状态；本场景完整终点是满足真实完成条件并完成交付。

3. 参与角色与职责边界

主体 负责什么
Agent 对照整个 Feature 的实现与 AC，完成必要检查、证据记录、台账更新、提交和交接
用户 在批准的 manual 验收方式下实际体验并给出结果，解决新要求与重要取舍
测试、证据与台账工具 各自执行测试或核对证据/结构，不代判全部交付条件，不自动写 done
独立审核角色 仅在用户明确指定的范围与时机参与；作者自查不冒充独立审核

已有实现授权和验证通过都不能替代用户的实际人工接受。

4. 流程概览

核对实现与文档 → 取得最终机器与专项依据 → 按验收方式分流 → 核对附加条件与新变化 → 检查并记录完成 → 收尾提交与交接。

5. 执行步骤

提示词入口：正常交付沿 Godot 项目开发 → 日常开发 → 执行指定或下一项 Feature / 继续中断的当前任务；仅验证使用 验证与收尾 → 单独验证某次变更；提供人工结果使用 整理人工验收与反馈。选择符合本次范围的一条即可。

  1. S1 核对整个交付范围。 Agent 检查本任务全部提交及未提交差异，对照每项 AC、来源、批准范围与排除项，定稿必要专业文档、资源清单及其他有用记录。
  2. S2 取得最终验证。 Agent 核对并完成当前 Required、affected、必要 full、直接解析/lint 与适用专项检查，按契约导入所需测试原件。
  3. S3 处理人工验收。 manual 模式下，Agent 准备并绑定当前内容的实际操作清单，用户体验后给出结果；Agent 按有效文件或明确口头结果记录。automated 模式跳过人工接受步骤。
  4. S4 核对附加条件。 Agent 完成适用 Bug 经验、用户指定的独立审核条件，检查最终内容的新变化并恢复失效依据。
  5. S5 检查并记录完成。 Agent 执行 evidence validate 与 check-feature-list.py --completion-feature；全部条件满足后写入 done 与真实完成时间，再运行完整台账检查。
  6. S6 收尾并交接。 Agent 整理必要 notes、知识和报告链接，归档一次执行历史，提交剩余自有改动并检查工作区；按剩余具体授权报告下一步或继续。

完成命令见检查完成依据与台账；人工准备与记录见人工验收操作。执行前采用实际项目路径和任务 ID。

6. 步骤产出与状态变化

步骤 直接产出与可继续的判据
S1 每项 AC 对应实际实现，必要来源定稿，没有未处理的遗漏、越界或意图冲突
S2 当前内容的机器与专项义务分别满足；有效无自动义务情形明确为 not_required
S3 manual 获得对应当前内容的真实接受，或明确待验收/拒绝；automated 不造人工记录
S4 用户指定条件与适用 Bug 经验满足，最终变化没有留下过期证据
S5 完成检查通过后记录 done/真实时间，最终台账一致；字段本身不充当完成证据
S6 收尾记录及本地提交可定位，工作区状态已核实，后续工作与授权边界明确

7. 资源与文件影响

对象（生成项目内） 影响类型与发生条件
Product、专业规格、Feature 设计、资源清单等 读取；本次确实改变且获准的必要内容在最终验证前定稿
测试、静态与专项报告 保存真实运行结果；有效原件复用，失效部分补验
人工清单与结果文件 manual 模式下准备、绑定和记录，保留真实拒绝与后续结果
docs/feature-completion-evidence.json 按实际测试与人工结果记录引用，不凭计划预填通过
任务索引、docs/features/F0XX.json 全部适用完成条件满足后更新完成状态和实际时间
notes、docs/knowledge/、docs/progress.md 与其历史目录 保留必要知识与当前停点；完成历史归档一次，不复制多份执行记录
Git 只提交本任务已检查的改动；保留用户明确不提交的例外

8. 条件分支与路径规则

条件 路径与汇合位置
S1 发现实现或文档缺口 原 Feature 回 Stage 3 补齐，再从 S1/S2 核对受影响内容
S2 有效 manual 计划确无自动义务，且无未解决失败/未完成运行 保留空测试引用和 not_required，仍完成适用静态、专项检查及 S3
S3 尚未体验或只完成部分操作 保持 in_progress，交付实际入口与待验收项；结果到位后继续 S3
S3 人工拒绝 保留拒绝；实现错误回 Stage 3，确认新要求转计划对齐，修复复验后回 S3
未指定独立审核 S4 完成其他适用条件后继续 S5，不额外征询常规审核许可
最终验证后源码或契约发生变化 核对失效范围，恢复相应 S2/S3；纯过程记录不机械触发重跑
S6 仍有具体授权内工作且前置满足 按当前 Product 顺序继续；否则交付本次结果或所缺决定

9. 异常与非正常退出

无法继续的情况 停止范围、保留与恢复
必要测试未执行、原件无效或导入失败 保留未完成状态，转验证恢复，满足后回 S2
人工结果不对应当前内容或无法确认 不记录接受，核实材料或重新准备清单后回 S3
指定审核存在阻断问题，或缺少必需覆盖 处理实际发现/缺口并补足失效验证，再回 S4
完成检查失败，或收尾过程中改动了验证契约 修正真实缺口，必要时回 S2/S3；不以已写状态替代条件
提交失败且没有不提交例外 保留文件与原始错误，报告收尾缺口；恢复后完成 S6，不声称已提交

10. 完成状态与验证标准

每项 AC 与批准范围得到核对；最终内容满足适用自动、静态及专项义务；manual 模式有真实有效接受；适用 Bug 经验和指定审核条件满足；完成依据与台账检查通过；done 与时间符合事实；必要收尾记录齐备；本地提交完成或用户明确的不提交例外已说明；下一步与工作区状态明确。

等待人工体验、验证失败和证据缺失都是清楚的当前结果，但均不是完整交付完成。已做过分批提交也不能跳过余下义务。

11. 流程关联与衔接关系

  • 上游：Feature 开发主线、Bug 修复、UI 原型、声音接入。
  • 恢复：测试与证据恢复、需求变化。
  • 下游：当前模块下一项已授权任务，或完成当前模块后复核下一模块规划；中断时用上下文恢复。

详细说明：原交付检查单。直接依据：执行 Stage 4–8、人工文件契约。

恢复上下文并续接任务

速查入口 · 执行步骤 · 步骤产出 · 卡住时 · 完成判定

1. 触发场景与使用时机

对话压缩、中断、换对话或较久未继续后，不能确定当前任务、修改归属、批准范围或验证状态。任务事实已清楚、只想知道下一步时，可以直接使用只读指导入口。

2. 前置条件与适用范围

可访问实际项目或原 worktree，并有现存文件、Git 状态或交接材料可核对。不要求能够访问全部旧对话，也不要求工作区先变干净才开始只读恢复。

恢复写入前，必须核实目录、任务、差异归属、有效决定及本次授权。原任务 WIP 可在确认属于同一任务后继续；混合或未知修改先保留并澄清。本页终点是恢复事实与合法的下一动作，原任务交付仍按其自身流程推进。

3. 参与角色与职责边界

主体 负责什么
用户 说明本次是查状态、准备交接还是继续实施，补齐无法从材料恢复的实质决定
当前 Agent 核对实际现场、现有记录与原件，恢复停点并执行仍有效的授权
原对话与接收对话中的 Agent 原对话准备交接后停止实施；接收方重新核实同一项目或原 worktree 的现场

交接正文供用户复制，流程不自动创建或投递新对话。摘要是核对线索，不能替代真实文件、授权或验收结果。

4. 流程概览

核对现场 → 恢复任务与决定 → 核实验证和运行 → 判断可继续范围 → 输出状态、准备交接或续接原任务 → 接收方复核。

5. 执行步骤

提示词入口：Godot 项目开发 → 日常开发 → 继续中断的当前任务 / 判断当前状态与下一步；准备换对话时用 验证与收尾 → 整理进度与任务交接。提供实际项目位置、当前线索和本次目标。

  1. S1 核对真实现场。 Agent 检查项目/worktree 绝对路径、规则、分支、Git 差异、相关提交和当前 Progress。
  2. S2 恢复任务与决定。 Agent 读取当前任务、相关来源及必要历史，区分计划、已实现、失败尝试、放弃方案和仍有效授权。
  3. S3 核实证据与进程。 Agent 检查结果对应版本和覆盖，核实未结束运行与已落盘原件，识别失效或缺失结果。
  4. S4 确定下一动作。 Agent 结合当前范围、用户最新要求与实际反馈，判断可直接继续的步骤以及依赖缺口的部分。
  5. S5 按目标交付或续接。 查状态时交付事实与建议；同对话续接时执行原任务；准备换对话时，在写入前提满足的范围内更新现有记录并生成可复制交接。
  6. S6 接收后复核。 用户在同一项目或原 worktree 的新对话粘贴交接；接收方核对现场是否改变，再从有效停点继续。

6. 步骤产出与状态变化

步骤 直接产出与可继续的判据
S1 目录、分支、暂存/未暂存/未跟踪内容与已知归属清楚
S2 当前任务、Stage 或实际维护停点、有效决定及未知项可定位
S3 有效、失败、未执行和过期结果分开，未结束运行没有被误当作失败或完成
S4 可执行第一步和需要补齐的具体条件明确
S5 有符合本次目标的状态说明、可用交接正文，或已经从原停点续接；没有人为创建新的完成状态
S6 接收方已核对当前现场，能够从明确步骤继续；交接材料与实际冲突已处理

7. 资源与文件影响

对象（生成项目内） 影响类型与发生条件
项目规则、配置、Git 分支/差异/历史 只读核对；不自动 stash、清空或提交未知改动
当前 Feature、来源、设计与必要历史 按缺口读取；没有 Feature 的工作不为恢复而造一个
原始测试、人工与审核材料，运行进程 核实版本与结果；不凭摘要生成或覆盖原件，不重复启动尚未结束的运行
docs/progress.md 与现有历史链接 必要且获准时更新当前停点和引用，不复制整段聊天
对话中的交接正文 准备换对话时生成，包含目录、停点、差异、授权、证据及下一步
原任务代码或其他文件 真正续接后按原任务范围修改；仅查状态或交接不因此取得实施授权

8. 条件分支与路径规则

条件 路径与汇合位置
本次仅判断当前状态 S4 后交付事实、未知与建议；不执行建议中的修改
同对话续接，现场和授权可核实 S5 从原阶段继续，复用已完成且仍有效的工作
准备换对话，写入前提满足 S5 更新必要现有记录并输出交接，原对话停止实施；新对话到 S6
准备换对话，暂不满足写入前提 S5 保留全部现场，输出只读交接与缺口，接收方从 S1 复核
旧验证因源码或规格变化失效 返回原任务补足适用验证；只变动纯 Progress 历史不机械重跑
原任务正在等待人工验收 明确清单与实际入口，沿原交付流程等待真实结果，不重复批准已定方案

9. 异常与非正常退出

无法继续的情况 停止范围、保留与恢复
目录不明，或改动归属混合/未知 暂停写入，保留所有文件；核实位置与归属后回 S1
只有摘要，无法确认关键授权或产品决定 明确未知及最小所需信息；补齐后回 S2/S4，不把“继续”当作缺失决定
原件缺失或摘要与实际结果矛盾 以可核实材料说明事实，转验证恢复补足依据，再回 S3
交接后现场已经变化 接收方重查受影响部分，回 S1–S4，不照搬旧下一步

10. 完成状态与验证标准

恢复结果能指出真实项目和任务、当前停点、差异归属、仍有效授权、有效结果与剩余义务，以及第一项可执行动作或具体阻塞。

本次只查状态时，上述说明就是约定交付；准备交接时，正文能供接收方核对现场并找到第一步；续接实施时，恢复完成后继续原已授权工作。恢复或交接完成均不把原 Feature 记为 done。

11. 流程关联与衔接关系

  • 上游：中断、插入工作与任务切换，或任一场景的中断点。
  • 恢复依赖：验证恢复、文档与实际不一致。
  • 下游：原任务的具体停点；已到最终验收时进入 Feature 交付。

详细说明：原恢复检查单、换对话操作。直接依据：Progress 职责、授权延续。
