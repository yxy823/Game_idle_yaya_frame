# 新功能形成可执行计划

[速查入口](README.md) · [执行步骤](#5-执行步骤) · [步骤产出](#6-步骤产出与状态变化) · [卡住时](#9-异常与非正常退出) · [完成判定](#10-完成状态与验证标准)

## 1. 触发场景与使用时机

有一个新玩法、功能想法或已有 GDD，希望把当前要做的模块整理成可执行任务。此时允许需求尚有待定问题；澄清这些问题属于本流程。

## 2. 前置条件与适用范围

已明确要讨论或规划的对象，并有可读取的想法、材料或用户说明。纯讨论可先进行；写入要求项目已建立，且满足[共用写入前提](README.md#共用的操作边界)。需要向空目录保存项目材料时先创建项目；环境准备在后续编码前完成，不作为需求讨论的门槛。

本页终点是当前模块的正式来源和可执行计划。已有有效计划直接复用；已规划范围的要求改变转计划同步；实现违背现有要求转 Bug。仅整理需求的授权不包含计划写入或实现。

## 3. 参与角色与职责边界

| 主体 | 负责什么 |
| --- | --- |
| 用户 | 提供目标，决定影响验收的未决行为与重要取舍 |
| Agent | 读取当前材料，按所属入口维护需求，展示拆分方案，完成获准的规划与检查 |
| 台账检查工具 | 检查文件结构、引用和依赖；语义覆盖仍由 Agent 核对 |

已有明确决定直接沿用。普通规划在写入前确认具体拆分方案；用户已明确授权自主拆分时，展示方案后继续，不重复索取同一授权。

## 4. 流程概览

定位当前模块 → 澄清可观察行为 → 保存所属来源 → 判断是否需要规划 → 展示并保存计划 → 交付计划或进入已授权实施。

## 5. 执行步骤

提示词入口：`Godot 项目开发 → 需求设计 → 从想法或已有 GDD 整理 Product 并衔接规划`。提供材料、当前模块、限制及本次允许讨论、写入或实施的范围。已有完整 Product 时可用 `任务规划 → 拆分当前 Product 的 Feature`。

1. **S1 定位当前工作。** Agent 核对项目、当前模块、已有任务与本次范围，读取相关 Progress 和文件差异。
2. **S2 明确验收意图。** Agent 梳理输入、行为、输出、边界与不做的部分；用户补齐会改变当前验收的决定。
3. **S3 保存权威来源。** Agent 把行为要求写入 Product，把专业要求交给相应入口，按原任务归属处理来源提交。
4. **S4 判断计划缺口。** Agent 对照已有 Feature，选择复用、同步或首次拆分；确认前置模块已交付，只拆当前模块。
5. **S5 展示并写入计划。** Agent 展示数量、范围、依赖及“要求 → Feature/AC → 检查”的对应；授权和来源前置齐备后写入，完成覆盖与台账检查。
6. **S6 交接下一动作。** Agent 给出实际任务 ID、来源、剩余义务和提交结果；按已有授权进入实施或在规划范围结束。

各步达到下一节同编号判据后继续；需要改道时查第 8 栏。

## 6. 步骤产出与状态变化

| 步骤 | 直接产出与可继续的判据 |
| --- | --- |
| S1 | 当前模块、已有任务及允许动作明确；未知差异已说明，写入前归属可核实 |
| S2 | 当前行为可观察、可验证；影响验收的冲突已解决 |
| S3 | 已确认要求位于正确来源，可引用；需要来源提交的后续步骤已具备真实提交 |
| S4 | 复用、同步或首次拆分的选择有依据，没有重复任务或提前拆分后续模块 |
| S5 | 写入的计划、测试登记表及适用修订一致，台账检查通过，语义覆盖无未说明缺口 |
| S6 | 用户可定位具体任务和第一步；计划完成与尚待实现、验证的工作分别说明 |

## 7. 资源与文件影响

| 对象（生成项目内） | 影响类型与发生条件 |
| --- | --- |
| 用户提供的 GDD、相关规则与已有记录 | 读取；保留外部原件 |
| `docs/product.md`、`docs/product/` 与适用专业来源 | 获准整理需求时新增或修改；来源按职责分别维护 |
| `docs/feature-list.json`、`docs/features/F0XX.json` | 获准保存计划时修改索引、创建任务详情 |
| `docs/test-registry.json` | 按实际计划补充组件与逻辑测试登记；不伪造已存在的测试或通过结果 |
| `docs/feature-list-revisions.json` | 符合空台账首次规划条件时建立 R000；后续模块规划保留旧记录与锚点 |
| Git 与现有 Progress | 按所属任务提交；有必要续接信息时更新 Progress |

## 8. 条件分支与路径规则

| 条件 | 路径与汇合位置 |
| --- | --- |
| S4 已有完整有效计划 | 复用计划，直接到 S6 |
| S4 已有计划但要求变了 | 转[需求变化后对齐计划](requirements-change.md)，完成后回 S6 |
| Feature 索引与修订记录在首次规划前均为空 | S5 前确认采用来源已提交；覆盖核对后建立 R000，再完成最终台账检查 |
| 后续 Product 的首次拆分 | 追加任务，保留全部修订记录，不推进旧锚点；继续 S6 |
| 本次只整理需求或只讨论 | 到约定来源或讨论成果即交付，明确未建立计划 |
| S6 已有实施授权且环境、依赖齐备 | 进入原 Feature 的 Stage 0–1；否则交付计划与所缺前置 |

## 9. 异常与非正常退出

| 无法继续的情况 | 停止范围、保留与恢复 |
| --- | --- |
| 决定矛盾，无法写出可观察验收条件 | 暂停依赖该决定的规划，保留已有提案；用户解决后回 S2 |
| 来源无法提交、采用状态不明，或 WIP 归属不清 | 保留现场与分析；暂停依赖这些前置的写入，核实后回 S3/S5，不伪造 R000 |
| 台账或覆盖检查失败 | 不交付“可执行计划”的结论；按实际缺口修正 S5 并重查 |

## 10. 完成状态与验证标准

完整规划完成时：当前要求有可定位来源；本模块每项要求对应 Feature/AC 与检查方式，排除项和缺口明确；实际写入的计划通过台账检查；来源、适用基线和本地提交符合约定；下一任务与剩余实现、验证范围可定位。

只完成讨论或需求整理时，报告对应成果与尚未进入的步骤。计划完成不设置 Feature `done`，也不证明游戏已实现或验证通过。
