# 需求变化后对齐已有计划

[速查入口](README.md) · [执行步骤](#5-执行步骤) · [步骤产出](#6-步骤产出与状态变化) · [卡住时](#9-异常与非正常退出) · [完成判定](#10-完成状态与验证标准)

## 1. 触发场景与使用时机

用户已决定改变玩法行为、UI/美术/声音等专业要求或适用规则，已有任务和验证可能仍按旧要求执行。Product 没有改动、仅专业规格变化也属于本场景。

## 2. 前置条件与适用范围

有明确采用决定、可定位的新旧要求以及可能受影响的已有计划。尚未采纳的建议保留为提案；不清楚文档还是实现错误时先做一致性核对。

可先只读分析影响。独立同步写入前，来源应已由所属入口保存并提交，且满足项目的工作区前提；当前 Feature 内的辅助修改保持原归属，不能在混合 WIP 上另起同步。本页终点是计划与验证责任对齐；同步入口本身不执行 Feature。

## 3. 参与角色与职责边界

| 主体 | 负责什么 |
| --- | --- |
| 用户 | 决定实质要求变化和新增取舍 |
| Product / 专业来源入口，由 Agent 执行 | 保存各自负责的要求，修复来源输入中的旧链接并提交 |
| 计划同步入口，由 Agent 执行 | 分析实际影响，更新获准的计划、引用、测试登记与修订记录 |
| 实现任务与检查工具 | 原任务或后续任务负责实现；工具核对台账结构与关系 |

## 4. 流程概览

确认变化 → 保存并提交来源 → 核实比较基线 → 找到实际受影响任务 → 展示并写入调整 → 检查计划 → 交回实施。

## 5. 执行步骤

提示词入口：行为变化用 `Godot 项目开发 → 需求设计 → 新增、删除或调整玩法需求`；来源就绪后用 `任务规划 → 需求变化后同步已有任务`。提供来源路径、实际变化和本次允许调整的范围。

1. **S1 确认改变的要求。** Agent 对比前后行为或约束，用户补齐尚缺的采用决定。
2. **S2 保存来源。** Agent 通过所属入口维护 Product、专业文档或规则，保护当前 WIP，完成独立同步需要的来源提交。
3. **S3 核实比较依据。** Agent 检查修订记录的锚点和历史采用范围，确认哪些来源确实已被旧计划吸收。
4. **S4 展示影响方案。** Agent 从来源引用、共享适用范围和依赖追到相关 Feature/AC，说明任务、测试与依赖的处置，补齐新增实质决定。
5. **S5 更新并检查计划。** 来源就绪后，Agent 写入获准的索引、详情、登记与修订，核对要求覆盖并运行完整台账检查。
6. **S6 交回实现。** Agent 指出原任务或后续任务、验证责任及旧结果能否复用，按同步任务规则提交并交付。

## 6. 步骤产出与状态变化

| 步骤 | 直接产出与可继续的判据 |
| --- | --- |
| S1 | 变化及其权威来源明确，已采用与仅建议分开 |
| S2 | 来源提交和工作区前置可核实；未满足时保留具体缺口 |
| S3 | 有可信历史基线，或明确历史未知及本次允许的当前文档对齐范围 |
| S4 | “变化 → 任务/AC → 处置 → 验证责任”清楚，具体调整在已有授权内 |
| S5 | 最终文件与实际分析的来源提交一致，引用、依赖、测试关系及台账检查满足 |
| S6 | 接手任务、尚待实现或清理的内容明确；计划更新与代码更新分别报告 |

## 7. 资源与文件影响

| 对象（生成项目内） | 影响类型与发生条件 |
| --- | --- |
| Product、专业规格、适用规则 | 读取；来源入口按获准变化修改、修链接并提交 |
| `docs/feature-list.json`、受影响的任务详情与设计导航 | 按批准方案修订、追加或更新引用；保留历史身份 |
| `docs/feature-list-revisions.json` | 按真实来源与调整追加同步记录，不重写既有记录 |
| `docs/test-registry.json` | 记录必要测试迁移、退役与替代关系，不能冒充代码已清理 |
| 测试代码、游戏代码和资源 | 本同步场景读取并安排责任；修改由接手的实现任务执行 |
| Git 与原始验证依据 | 读取来源历史，提交本次自有计划；保留历史验证事实 |

## 8. 条件分支与路径规则

| 条件 | 路径与汇合位置 |
| --- | --- |
| 实现有误，但确认的要求没变 | 转 [Bug 修复](bug-fix.md)，不修改要求迁就实现 |
| S3 不能证明历史覆盖 | 明确未知，在具体授权内对齐当前来源与已规划范围，再到 S4；不把空 diff 当作已同步 |
| S4 发现来源输入有旧链接 | 由来源入口修复并提交，再回 S3 分析实际 HEAD；只有计划引用过时时在 S5 修正 |
| 已完成行为需要改变 | 保留原验收事实，安排后续任务及必要替代关系；不把历史任务改成当时实现了新要求 |
| 变化只涉及后续尚未规划的模块 | 保留更新后的规格，轮到该模块再规划，不提前生成任务 |
| 只有有效下游测试需要重跑 | 纳入负责变更的任务，不新建纯复跑 Feature |

## 9. 异常与非正常退出

| 无法继续的情况 | 停止范围、保留与恢复 |
| --- | --- |
| 缺少实质决定，或来源之间互相矛盾 | 保留影响分析，暂停依赖的计划写入；所属入口解决后回 S1/S4 |
| 来源未提交、提交不可用或 WIP 归属不清 | 保留现场，暂停 S5；前置满足后重新核实 S2/S3 |
| 同步期间来源又改变 | 保留已知差异，回 S3 更新分析与必要决定，不能继续写旧锚点 |
| 台账关系或覆盖核对失败 | 保留未完成状态，在 S5 修正实际缺口后重新检查 |

## 10. 完成状态与验证标准

可指出实际采用的来源提交；受影响的已规划任务都有明确处置与验证责任；实际写入的索引、详情、登记、依赖和修订记录一致；完整台账检查通过；历史验收保留；本次自有计划已按约定提交，后续执行入口可定位。

只做影响分析时，以带依据的方案与未决项交付，明确尚未写计划。计划对齐不等于新要求已经实现，也不证明旧证据仍有效。
