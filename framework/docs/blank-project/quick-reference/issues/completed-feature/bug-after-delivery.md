# Feature 已经完成交付，后来又发现它有 Bug

[返回场景索引](../../scenario-index.md#问题修复) · [执行步骤](#执行步骤) · [完成标准](#完成状态与验证标准)

## 触发场景与使用时机

某项功能曾经正式完成交付，后来使用或修改其他内容时，发现它不符合仍然有效的要求。

## 前置条件与适用范围

能够核实原 Feature 的完成历史、当前异常及有效预期；本次明确包含独立 Bug 修复。建立新任务前满足项目的干净工作区要求，现有未提交内容的归属不能靠丢弃或混合提交解决。

当前 Feature 尚未交付且问题属于本次改动时，使用[交付前发现 Bug](../current-feature/bug-after-tests.md)。用户希望改变原行为属于要求变化。

## 参与角色与职责边界

用户提供现象和缺少的实质决定，完成适用验收；Agent 通过现有工程 Bug 入口建立修复归属、诊断、修复和验证。原 Feature 的历史保持真实，新修复由新任务负责。

## 流程概览

固定问题与来源 → 建立独立修复任务 → 定位并修复 → 取得回归结果 → 保存经验并交回修复任务收尾。

## 执行步骤

可用入口：“Godot 项目开发 → 修复与改进 → 定位与修复 Bug”。提供原 Feature、现象、有效预期、复现材料和修复范围。使用此提示词时，沿用其中“验收前不提交、验收后提交”的本次任务限制，不能被普通分阶段提交默认值覆盖。

1. **S1 固定缺陷。** Agent 核对原完成历史和当前版本，记录实际表现、有效要求及已知触发条件。
2. **S2 建立修复归属。** Agent 按现有工程变更规划入口确定独立 Bug 任务，写明修复范围、AC、回归责任与必要诊断。
3. **S3 确认原因并修复。** Agent 追到真实根因，建立能检验原错误的自动或可重复人工回归，实施获准修复。
4. **S4 核对最终结果。** Agent 运行原触发与所需受影响验证，记录实际结果；用户完成适用人工验收。
5. **S5 保存经验并移交收尾。** Agent 按工程 Bug 的 Stage 5.5 保存有价值的根因、触发和回归信息，交回本次修复任务的完成检查。

## 步骤产出与状态变化

| 步骤 | 产出与继续条件 |
| --- | --- |
| S1 | 能说明原要求、完成历史与当前错误的关系 |
| S2 | 独立 Bug 任务和验证责任明确，原 Feature 不被重新打开 |
| S3 | 根因得到确认，修复与回归针对同一问题 |
| S4 | 当前最终内容有有效验证和适用人工结果 |
| S5 | 必要经验已保存，修复任务可继续正式收尾检查 |

## 资源与文件影响

| 项目内对象 | 影响 |
| --- | --- |
| 原 Feature、原验收和历史报告 | 读取并保留，不篡改当时的完成事实 |
| 新 Bug 任务索引与详情 | 按既有工程规划规范创建，记录诊断与验证责任 |
| 出错实现、必要测试和登记 | 按获准修复修改，补充实际回归保护 |
| 本次报告、完成依据和修复任务 notes | 保存真实结果及有用经验 |
| Git | 按本次具体授权和提示词限制处理提交，不混入无关差异 |

## 异常与非正常退出

无法核实有效预期时，暂停依赖预期的修复，交回要求所属入口。根因不明或现场不足时，保留诊断和未知，不能宣称已经修复。

工作区混有其他任务改动时，保留现场，先解决归属或隔离问题。环境不足、必要回归失败或实际验收拒绝时，保留失败结果，在本次范围内处理后复验；不使用旧 Feature 的接受代替这次修复验证。

## 完成状态与验证标准

独立修复归属正确；根因和回归有证据，最终内容满足适用验证与人工验收；有用 Bug 经验可定位，原 Feature 历史未改写。本页出口是交回新修复任务的收尾检查；完成记录、约定提交和交接仍须随后执行，不凭修复现象消失直接写 done。
