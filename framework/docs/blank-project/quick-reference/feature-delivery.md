# Feature 验证、验收与交付

[速查入口](README.md) · [执行步骤](#5-执行步骤) · [步骤产出](#6-步骤产出与状态变化) · [卡住时](#9-异常与非正常退出) · [完成判定](#10-完成状态与验证标准)

## 1. 触发场景与使用时机

当前 Feature 已有实现，希望判断是否可以进入最终验收、正式记录完成并交付。仅“代码写完”还不足以判断本场景已经结束。

## 2. 前置条件与适用范围

已有正式 Feature、明确 AC、批准方案与验证义务，并能读取实际实现和证据。早于正式计划的已有实现先走接管流程。只请求验证时可核对结果，不借此取得修改完成状态或实现的授权。

本页覆盖 Stage 3 文档定稿后的最终检查、适用人工验收及 Stage 7–8 收尾。正常等待人工结果与存在验证缺口均保留未完成状态；本场景完整终点是满足真实完成条件并完成交付。

## 3. 参与角色与职责边界

| 主体 | 负责什么 |
| --- | --- |
| Agent | 对照整个 Feature 的实现与 AC，完成必要检查、证据记录、台账更新、提交和交接 |
| 用户 | 在批准的 manual 验收方式下实际体验并给出结果，解决新要求与重要取舍 |
| 测试、证据与台账工具 | 各自执行测试或核对证据/结构，不代判全部交付条件，不自动写 `done` |
| 独立审核角色 | 仅在用户明确指定的范围与时机参与；作者自查不冒充独立审核 |

已有实现授权和验证通过都不能替代用户的实际人工接受。

## 4. 流程概览

核对实现与文档 → 取得最终机器与专项依据 → 按验收方式分流 → 核对附加条件与新变化 → 检查并记录完成 → 收尾提交与交接。

## 5. 执行步骤

提示词入口：正常交付沿 `Godot 项目开发 → 日常开发 → 执行指定或下一项 Feature / 继续中断的当前任务`；仅验证使用 `验证与收尾 → 单独验证某次变更`；提供人工结果使用 `整理人工验收与反馈`。选择符合本次范围的一条即可。

1. **S1 核对整个交付范围。** Agent 检查本任务全部提交及未提交差异，对照每项 AC、来源、批准范围与排除项，定稿必要专业文档、资源清单及其他有用记录。
2. **S2 取得最终验证。** Agent 核对并完成当前 Required、affected、必要 full、直接解析/lint 与适用专项检查，按契约导入所需测试原件。
3. **S3 处理人工验收。** manual 模式下，Agent 准备并绑定当前内容的实际操作清单，用户体验后给出结果；Agent 按有效文件或明确口头结果记录。automated 模式跳过人工接受步骤。
4. **S4 核对附加条件。** Agent 完成适用 Bug 经验、用户指定的独立审核条件，检查最终内容的新变化并恢复失效依据。
5. **S5 检查并记录完成。** Agent 执行 evidence validate 与 `check-feature-list.py --completion-feature`；全部条件满足后写入 `done` 与真实完成时间，再运行完整台账检查。
6. **S6 收尾并交接。** Agent 整理必要 notes、知识和报告链接，归档一次执行历史，提交剩余自有改动并检查工作区；按剩余具体授权报告下一步或继续。

完成命令见[检查完成依据与台账](../reference/commands-and-validation.md#检查完成依据与台账)；人工准备与记录见[人工验收操作](../guides/feature-delivery.md#人工验收应如何操作)。执行前采用实际项目路径和任务 ID。

## 6. 步骤产出与状态变化

| 步骤 | 直接产出与可继续的判据 |
| --- | --- |
| S1 | 每项 AC 对应实际实现，必要来源定稿，没有未处理的遗漏、越界或意图冲突 |
| S2 | 当前内容的机器与专项义务分别满足；有效无自动义务情形明确为 `not_required` |
| S3 | manual 获得对应当前内容的真实接受，或明确待验收/拒绝；automated 不造人工记录 |
| S4 | 用户指定条件与适用 Bug 经验满足，最终变化没有留下过期证据 |
| S5 | 完成检查通过后记录 `done`/真实时间，最终台账一致；字段本身不充当完成证据 |
| S6 | 收尾记录及本地提交可定位，工作区状态已核实，后续工作与授权边界明确 |

## 7. 资源与文件影响

| 对象（生成项目内） | 影响类型与发生条件 |
| --- | --- |
| Product、专业规格、Feature 设计、资源清单等 | 读取；本次确实改变且获准的必要内容在最终验证前定稿 |
| 测试、静态与专项报告 | 保存真实运行结果；有效原件复用，失效部分补验 |
| 人工清单与结果文件 | manual 模式下准备、绑定和记录，保留真实拒绝与后续结果 |
| `docs/feature-completion-evidence.json` | 按实际测试与人工结果记录引用，不凭计划预填通过 |
| 任务索引、`docs/features/F0XX.json` | 全部适用完成条件满足后更新完成状态和实际时间 |
| notes、`docs/knowledge/`、`docs/progress.md` 与其历史目录 | 保留必要知识与当前停点；完成历史归档一次，不复制多份执行记录 |
| Git | 只提交本任务已检查的改动；保留用户明确不提交的例外 |

## 8. 条件分支与路径规则

| 条件 | 路径与汇合位置 |
| --- | --- |
| S1 发现实现或文档缺口 | 原 Feature 回 Stage 3 补齐，再从 S1/S2 核对受影响内容 |
| S2 有效 manual 计划确无自动义务，且无未解决失败/未完成运行 | 保留空测试引用和 `not_required`，仍完成适用静态、专项检查及 S3 |
| S3 尚未体验或只完成部分操作 | 保持 `in_progress`，交付实际入口与待验收项；结果到位后继续 S3 |
| S3 人工拒绝 | 保留拒绝；实现错误回 Stage 3，确认新要求转[计划对齐](requirements-change.md)，修复复验后回 S3 |
| 未指定独立审核 | S4 完成其他适用条件后继续 S5，不额外征询常规审核许可 |
| 最终验证后源码或契约发生变化 | 核对失效范围，恢复相应 S2/S3；纯过程记录不机械触发重跑 |
| S6 仍有具体授权内工作且前置满足 | 按当前 Product 顺序继续；否则交付本次结果或所缺决定 |

## 9. 异常与非正常退出

| 无法继续的情况 | 停止范围、保留与恢复 |
| --- | --- |
| 必要测试未执行、原件无效或导入失败 | 保留未完成状态，转[验证恢复](verification-recovery.md)，满足后回 S2 |
| 人工结果不对应当前内容或无法确认 | 不记录接受，核实材料或重新准备清单后回 S3 |
| 指定审核存在阻断问题，或缺少必需覆盖 | 处理实际发现/缺口并补足失效验证，再回 S4 |
| 完成检查失败，或收尾过程中改动了验证契约 | 修正真实缺口，必要时回 S2/S3；不以已写状态替代条件 |
| 提交失败且没有不提交例外 | 保留文件与原始错误，报告收尾缺口；恢复后完成 S6，不声称已提交 |

## 10. 完成状态与验证标准

每项 AC 与批准范围得到核对；最终内容满足适用自动、静态及专项义务；manual 模式有真实有效接受；适用 Bug 经验和指定审核条件满足；完成依据与台账检查通过；`done` 与时间符合事实；必要收尾记录齐备；本地提交完成或用户明确的不提交例外已说明；下一步与工作区状态明确。

等待人工体验、验证失败和证据缺失都是清楚的当前结果，但均不是完整交付完成。已做过分批提交也不能跳过余下义务。
