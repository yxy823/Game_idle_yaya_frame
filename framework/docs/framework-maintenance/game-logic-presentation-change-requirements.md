## 1. 背景与目标

现有框架已在[游戏组织指南](../../../project-source/defaults/docs/game-organization.md)中区分规则与表现，并按业务模块组织代码；[项目架构原则模板](../../../project-source/methodology/templates/project-rules.md.tmpl)在本次变更前使用“数据规则、编排控制、表现输入”三层表述。[专业来源约定](../../../project-source/methodology/11-specialist-workflows.md)已经区分 GDD、UI、一次游戏表现、架构和开发任务的记录职责。

这些能力需要统一的解释，让使用者阅读框架与空白 Godot 项目时，能够顺着“游戏目标 → 规则与表现要求 → 文档归属 → 实现与协作 → 验证与验收”找到相关内容。实施先明确职责，再整理文档关系，最后依据查找收益判断目录；本次保留现有物理目录和业务模块组织。

## 2. 已确认的组织原则

游戏逻辑负责规则、业务状态与有效结果，游戏表现负责这些内容如何被玩家感知。这是游戏功能的第一层职责模型；创建器、环境、测试、构建和任务流程是共同工程支持，不强行归入游戏的两层。

本次组织模型用于帮助理解职责、定位资料和作出设计判断。新增约束只规定必要的职责与一致性要求；普通实现方式由 Agent 根据当前需求、已有结构和验证结果选择。默认建议应说明适用条件，不把示例写成所有任务必须遵循的固定结构。

- **状态归属：** 影响游戏规则的状态有明确的权威所有者；表现可拥有悬停、界面展开、显示过渡和播放进度等自身状态。
- **协作含义：** 区分行为请求、当前状态与一次性事件。表现提出请求，逻辑判断并给出有效结果，表现据此反馈；AI、计时器等也可触发游戏变化。当前状态支持重新打开界面时恢复显示，历史事件不因此自动重放。
- **编排归属：** 游戏流程编排归逻辑，反馈时序编排归表现；连接双方的实际组装关系在架构中说明，不保留固定三层结构要求。
- **技术边界：** Godot 节点、场景、碰撞和输入按实际职责判断，不因使用引擎对象就属于表现，也不要求所有逻辑脱离引擎。动画参与玩法时明确时序输入、打断条件和有效结果判定责任。
- **实现选择：** 普通方法、已有 API、Signal 或必要的协调者按实际结构选择；不强制全局事件总线、独立类数量、目录层级或固定拆分顺序。

## 3. 文档与交付职责

| 读者需要找到的内容 | 正文归属 |
| --- | --- |
| 总体游戏目标、玩法规则、业务状态和体验要求 | GDD；数值主题仍由 design-balance 在所属 GDD 中维护 |
| 界面布局、显示状态、交互和界面专用资源 | UI 设计文档 |
| 一次具体表现的过程、候选方案、采用组合、资源规格与实现引用 | 游戏表现文档；“表现层”范围大于这类文档 |
| 当前模块、状态所有者、实现位置与实际协作 | 架构总览及必要的子系统文档 |
| 本次交付范围、局部设计与验证义务 | 既有 Product、Feature 及其设计和验证记录 |

以商店购买贯穿主要说明：从 GDD 找到购买条件与扣费规则，从 UI 文档找到商店界面，从游戏表现文档找到物品获得反馈，从架构或局部设计找到连接方式，再由开发任务关联验收。保持一项要求的唯一正文，不复制整套规格。

表现类、逻辑类、跨层类只用于说明功能涉及范围，不成为新的任务类型或入口。跨层功能可由同一 Feature 完成交付。实现顺序取决于实际依赖，保留先做视觉原型的有效方式；简单任务不强制建立设计文档。

## 4. 实施范围

- 扩展游戏组织指南，按职责模型、文档关系、业务模块与代码组织安排阅读；同步项目 README、架构模板、项目规则及必要工程规则入口。
- 操作手册增加“游戏逻辑、表现与协作”概念章节，放在框架与项目边界之后；同步目录说明、专业来源、规划、记录和公共术语。
- 在已有设计、规划、实施指导、执行、同步和审核中应用模型；同步 advisor 的说明和场景预期，核对已有相关提示词和场景，只修正实际失效的内容。
- 不新增 Skill、三类专用提示词、Feature 字段、Stage、运行通信机制、监督脚本或重复状态。API、配置结构和创建器复制契约保持原样。
- 修改仅覆盖框架和新项目分发源；不修改已有外部项目、Godot 运行代码，也不引入图片或音频制作。

## 5. 验收场景与检查

| 场景 | 应当能判断或找到的结果 |
| --- | --- |
| 商店购买 | 能从规则找到界面、获得反馈、协作和验收；购买合法性与扣费归逻辑 |
| 受击后血条变化 | 真实生命值与显示过渡分开；重新打开界面不会重放受击事件 |
| 更换奖励动画 | 保持已确认规则和表现目标，允许自主选择实现手段 |
| 动画命中帧参与攻击 | 明确时序输入、打断与结果判定责任，不机械禁止动画参与 |
| 角色死亡 | 不依赖 UI 文档也能从 GDD 找到表现、实现与验收入口 |
| 小型功能与界面原型 | 不强制额外对象、事件总线或先完成业务逻辑 |
| 环境、测试和构建 | 归共同工程支持，不强行归入游戏逻辑或表现 |

完成源材料及分发后引用检查、相关 Skill 格式检查和现有复制回归。提示词、场景或派生参考发生变化时，沿用原配对、导出与关系图约定检查。实质变化的指令和场景完成独立只读审核，修正后构建两册 HTML 手册。

静态检查、工具回归、独立审核、构建和实际人工阅读分别报告。静态场景推演不是 Godot 运行或人工体验通过；阅读体验保留真实人工确认，不作为生成 HTML 的前置。需求变更依据和组织模型落实分别形成自洽本地提交；已有无关待办保留。
