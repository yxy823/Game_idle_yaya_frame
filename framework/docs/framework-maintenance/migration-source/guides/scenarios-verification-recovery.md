# 场景处置：验证与恢复

[场景索引](scenario-procedures.md) · [需求与设计](scenarios-requirements-design.md) · [界面、音频与资源](scenarios-interface-audio-assets.md) · [上下文与交接](scenarios-context-handoff.md)

本组从一次实际失败或一项待交付 Feature 开始。先确定当前版本、批准的验证义务与原始证据，再判断下一步。命令参数沿用 [命令参考](../reference/commands-and-validation.md)，本页不维护第二份 CLI 清单。

## 发现 Bug 后定位、修复并回归

**适用条件：** 开发或体验时发现异常行为，需要从复现走到修复与回归。只有测试失败、尚未证明实现违反有效要求时，先走 [测试失败定位](#测试失败或证据导入失败时定位并恢复)。没有明确预期或预期正在改变时，先回需求/专业来源。

**目标：** 确认有效预期与根因，在正确任务内实施最小修复，用原触发条件保护回归，并回到正常交付。

**可用 Prompt：** “Godot 项目开发 → 修复与改进 → 定位与修复 Bug”，提供实际表现、期望及来源、最短复现、环境和日志/截图/音频等材料。已有 Feature 的缺陷沿原任务修复，不重复规划。只要求诊断时交付证据与建议，实施继续沿用已有具体授权。

```mermaid
flowchart TD
    A[观察到异常行为] --> B[固定实际表现和最短复现]
    B --> C{存在明确且仍有效的预期}
    C -->|缺失或冲突| D[回需求或专业来源澄清]
    C -->|用户正在改变预期| E[走要求变化与计划对齐]
    C -->|是| F{属于当前未完成 Feature}
    F -->|是| G[留在当前任务修复]
    F -->|否：独立缺陷| H[按授权建立 engineering bug 工作]
    G --> I[定位根因并建立自动或人工回归路径]
    H --> I
    I --> J[实施最小修复]
    J --> K[运行原触发回归及所需受影响验证]
    K -->|失败| I
    K -->|满足| L[取得适用人工验收]
    L -->|拒绝| I
    L -->|接受或不适用| M{engineering_change 为 bug}
    M -->|是| N[Stage 5.5 保存有价值的 Bug 经验]
    M -->|否| O[回正常交付核对]
    N --> O
```

| 步骤 / 操作 | 输入与需要检查的内容 | 执行说明与条件分支 | 预期输出与完成判据 |
| --- | --- | --- | --- |
| 1. 固定现象 | 实际版本/未提交差异、环境、复现步骤、日志或体验材料 | Agent 记录发生了什么、前置条件和最短触发；保留原始失败。间歇问题记录出现条件与已尝试范围，不能把一次未复现当作修复。 | 现象可复述，有实际证据；尚不能稳定复现的限制明确。 |
| 2. 找到有效预期 | Product、已确认专业规格、工具契约、Feature AC | 指出为什么这是错误行为。预期仍有效→Bug；缺失/冲突→所属入口澄清；用户改变要求→[要求变更](scenarios-requirements-design.md#已确认要求变化后对齐已有计划)。专业来源无需再复制进 Product。 | 预期、实际和差异明确；不修改需求迁就错误实现。 |
| 3. 确定任务归属 | 当前未完成 Feature、已完成行为、已有修复项和授权 | 原任务范围内缺陷留在当前 Feature；已完成行为的独立回归由 `engineering-change-plan` 的 `bug` 模式承接。无关 Bug 先分类，需立即切换时走 [中断与切换](scenarios-context-handoff.md#feature-中途切换中断或临时插入其他工作)。 | 有唯一负责修复的任务与范围，不重复建项，不以紧急为由吸收无关修改。 |
| 4. 定位根因 | 代码、场景、资源、生命周期、调用链与日志 | 核实导致违约的条件及传播路径；需要 `bug_diagnosis` 时保存实际、预期、来源、复现和根因。未证实解释标为假设；含诊断记录的 Feature 完成前必须确认根因。 | 已确认根因，或具体未知与下一次调查；不因猜测顺带重构。 |
| 5. 建立回归并修复 | 原始触发、测试登记表、自动化可行性 | 可自动验证则建立 `F0XX-RTyy`，确认失败来自目标行为；确实不适合自动化则说明原因并给可重复人工路径。按原范围实施最小完整修复，保护必要边界。 | 回归能够暴露原错误并验证修复，测试不只重复实现；环境错误不充当 RED。 |
| 6. 复验最终内容 | 修复、临时诊断改动、Required/affected/必要 full 与人工义务 | 先验证原始触发，再取得当前义务所需结果，复用仍有效证据；临时埋点影响结论时检查最终交付版本。适用人工验收实际拒绝则修复重验。 | 原 Bug 不再出现，当前最终版本的覆盖完整；未运行、失败、原件缺失分别保留，不能借旧成功收尾。 |
| 7. 保存经验并交付 | 根因、触发、回归保护和任务类型 | 仅 `engineering_change: bug` 进入 Stage 5.5，在 notes 保存有用根因、触发、回归和防范原则。普通 Feature 内修复保留必要记录即可；通用 guardrail 另按规则维护权限判断，晚改恢复失效验证。 | 经验有实际依据，不把每个缺陷变成新规则；回正常完成核对，而非修好现象直接记 `done`。 |

**最终产物与返回入口：** 可复现诊断、最小修复、自动或人工回归、真实验证与适用 Bug 经验；继续 [交付核对](#实现完成后判断能否交付)。根因未明、环境不足或仅诊断时交付实际边界。依据：[Bug 归属与根因](engineering-changes.md#bug-先查归属再查根因)、[Stage 5.5](../../../../../project-source/methodology/03-execute-loop.md#stage-55--bug-learning-capture)。

## 测试失败或证据导入失败时定位并恢复

**适用条件：** 测试失败、未启动、发现不完整、断言/引擎诊断失败、结果无法导入，或旧成功不能用于当前内容。观察到异常行为、需要从预期和复现开始时走 [Bug 处置](#发现-bug-后定位修复并回归)；性能/长测等专项失败不能伪装成 gdUnit 结果。

**目标：** 找到失败发生的层次与责任，完成获准的最小修复及所需复验；若缺少环境、决定或证据，则给出可操作的阻塞，保持未完成状态。

**可用 Prompt：** 只测与诊断用“Godot 项目开发 → 验证与收尾 → 单独验证某次变更”，填写对象与允许的静态/测试/导入/启动范围；已授权修复时用“修复与改进 → 定位与修复 Bug”，提供明确预期、实际现象与日志。当前 Feature 内已有修复授权时直接续接原任务。

```mermaid
flowchart TD
    A[观察到失败] --> B[保存版本、命令、退出码与原件]
    B --> R{是否只有证据导入失败}
    R -->|是| S[核对引用、版本、原件和覆盖]
    S -->|已有满足义务的有效原件| T[修正引用并重新导入]
    T -->|成功| M
    T -->|失败| S
    S -->|缺少有效原件或所需覆盖| C
    R -->|否| C{测试实际执行了吗}
    C -->|否或发现不完整| D[检查环境、参数、套件与运行器]
    C -->|是| E{预期与测试是否符合已确认契约}
    E -->|意图缺失或冲突| F[交需求所有者解决，不先改断言]
    E -->|预期错误或测试契约已失效| G[按真实来源处理测试及其登记]
    E -->|预期仍有效| H[定位实现或引擎协作根因]
    D --> I{本次修复范围与前置齐备}
    G --> I
    H --> I
    F -->|决定明确并处理计划影响| I
    I -->|否| J[报告具体阻塞与下一步]
    I -->|是| K[修复并取得所需最终运行]
    K --> L{原件完整、覆盖正确且导入成功}
    L -->|否| B
    L -->|是| M[返回静态及专项检查、适用验收和完成核对]
```

| 步骤 / 操作 | 输入与需要检查的内容 | 执行说明与条件分支 | 预期输出与完成判据 |
| --- | --- | --- | --- |
| 1. 固定失败现场 | 真实工作目录、Git 差异、Feature ID、批准验证计划、命令/退出码和本次报告路径 | Agent 记录实际版本及未提交变化。gdUnit 优先保留 `reports/gdunit-wrapper/<Feature-ID>/run-<id>/` 原件；无法写报告时保存已有输出并说明文件未生成。运行未结束先查进程状态，不并发重跑同一问题。 | 能指出哪次尝试、哪个版本、哪个范围失败。失败原件不覆盖、不删除，摘要不替代原件。 |
| 2. 判断失败层 | `result.json` 的状态/errors/process、`engine.log`、`discovery.json`、本次 JUnit 与诊断原件 | 未启动或缺类/解析失败→查配置、首次扫描和实际调用；零测试/集合不匹配→查真实套件及映射；断言或引擎诊断失败→进入契约判断。JUnit 绿色但包装器失败仍是未通过；退出 0 且只有帮助也不算执行测试。 | 区分环境/调用/发现、行为断言、引擎诊断和证据导入。无法判断时列出缺失原件与最小补查，不能直接修改业务逻辑。 |
| 3. 核对谁定义预期 | 对应 Product/专业规格/工具契约、Feature AC、测试断言、当前变更及需求修订 | 实现违反仍有效要求→查实现；断言与确认要求不符→修正测试；已批准需求变化使旧契约失效→按现有计划和测试清理规则处理；要求缺失/互相矛盾→由所属入口解决。怀疑设计有问题须指出哪个状态、接口或生命周期导致违约。 | 有文件依据的分类与最短触发。测试失败本身不决定“测试错”或“实现错”；技术假设与已确认根因分开。 |
| 4. 确定责任与修复 | 当前 Feature 状态、问题来源、修复授权和受影响组件 | 当前未完成任务内的问题留在原任务；已完成行为的独立回归走工程 Bug；测试工具问题按工具契约处理。只验证请求先交诊断，不顺手改实现。回归 RED 必须是目标行为失败，环境错误不算。 | 明确归属、最小修复与回归方式；关键前置未满足则保留阻塞。可自动化的缺陷用针对性回归，确实不适合时说明原因与可重复人工路径。 |
| 5. 复验正确范围 | 修复后源码、当前 Feature/Registry、失败范围、有效的已有结果 | 修复后先证明原触发恢复，再完成当前义务。Required/affected/full 按计划与真实组件选；同一内容上较新失败须有后来成功且覆盖失败范围的运行，不能拿旧成功或更窄运行顶替。内容与覆盖均满足的结果可复用。 | 真实运行及覆盖证据；必要 full 未取得就是未完成。诊断版本和最终交付版本分开，临时埋点改变结论时须对最终版复测。 |
| 6. 导入并恢复流程 | 实际打印的结果路径、`docs/feature-completion-evidence.json`、完整原件与当前内容 | 需要自动证据时用现有 `record-tests`。引用错误且有合格原件→修正引用重新导入；缺少合格运行、哈希或覆盖不符→补齐验证。失败导入会清除旧测试引用，不能手改结果或哈希恢复通过。 | 导入成功且覆盖当前义务，才回到下面的交付核对。导入失败即使指纹未变，也不能转去让用户验收抵消机器缺口。 |

**常见分支：** 环境检查通过但引擎没能加载套件，只证明配置检查曾满足，不能证明业务失败；旧需求已正式删除时也不能简单跳过旧测试，应在负责变更的任务里协调测试代码、Registry 和必要替代覆盖。

**最终产物与返回入口：** 失败原件、诊断及根因/未知、获准修复和真实复验，或具体阻塞；继续 [交付核对](#实现完成后判断能否交付)。具体错误看 [故障排查图与恢复表](../reference/troubleshooting.md#测试运行和完成依据)，证据规则以 [测试策略](../../../../../project-source/methodology/08-testing-strategy.md#artifact-backed-completion-and-semantic-freshness) 为准。

## 实现完成后判断能否交付

**适用条件：** 当前 Feature 已有实现，希望进入最终验证、人工验收或完成记录。不是“代码存在就补 done”；早于正式计划的实现先走 [已有实现接管](feature-delivery.md#接管已有实现的交付)。

**目标：** 得到三种明确结果之一：满足完成条件并正式收尾；已备妥人工验收且保持 `in_progress`；存在具体实现/验证/审核缺口并返回对应步骤。

**可用 Prompt：** 正常交付沿用“Godot 项目开发 → 日常开发 → 执行指定或下一项 Feature / 继续中断的当前任务”。只做验证用“验证与收尾 → 单独验证某次变更”，不能借它修改完成状态。需要用户体验时用“整理人工验收与反馈”，填写真实任务、清单与结果。

```mermaid
flowchart TD
    A[认为实现已完成] --> B[逐条核对 AC、范围与必要文档]
    B --> C{仍有实现或文档缺口}
    C -->|有| D[Stage 3 在原范围补齐]
    D --> B
    C -->|无| E[Stage 4 取得适用自动、静态及专项依据]
    E --> F{机器要求均满足}
    F -->|否| D
    F -->|是| G{批准的验收方式}
    G -->|manual| H[绑定清单并取得用户真实结果]
    H -->|未体验或反馈不足| W[交付入口与待验收项，保持进行中]
    H -->|拒绝| R[保存真实拒绝，区分实现错误与要求变化]
    R -->|实现错误| D
    R -->|要求变化| S[更新 Product 或专业来源及受影响计划]
    S --> D
    H -->|接受| I[适用 Bug 经验与用户指定的独立审核]
    G -->|automated| I
    I --> J{当前证据与所有适用条件满足}
    J -->|否| K[处理阻断项或恢复失效依据]
    K --> B
    J -->|是| L[Stage 7 检查完成依据、记 done 并收尾提交]
    L --> M[Stage 8 更新交接并核对后续授权]
```

| 步骤 / 操作 | 输入与需要检查的内容 | 执行说明与条件分支 | 预期输出与完成判据 |
| --- | --- | --- | --- |
| 1. 对照整个交付范围 | Feature/AC、专业主/次来源、批准方案、相关依赖、本项全部提交与未提交差异 | Agent 逐条核对实际行为与排除项，检查遗漏、越界和边界情况；分批提交时不能只审最后一次差异。发现新的产品决定不能用现状自动替代。 | 每项 AC 对应实际实现和检查方式；尚缺行为回 Stage 3，意图冲突转来源处理。 |
| 2. 完成必要文档定稿 | 实现结果、术语、规格/资源清单、Feature 设计、规则和适用架构/ADR | Stage 3 更新本次确实改变的有用内容；不需要时明确无更新即可。要求不能仅放 notes、知识或报告。规则变化沿写前自检与授权；不为套检查单创建空设计。 | 权威来源与本次决定一致，准备状态/资源位置等必要编辑已完成。晚改纳入指纹的文档，必须恢复失效依据。 |
| 3. 检查实际验证义务 | 当前 `verification`、`affected_components`、Registry、环境配置与专项计划 | 自动义务存在→运行并导入满足 Required/affected/必要 full 的结果；有效 manual 计划确无自动义务且无未解决失败/未完成运行→保留空引用，报告 `not_required`。直接解析/lint 和性能、长测、显示/试听义务分别核对，不由 evidence 工具代判。 | 所有适用机器与专项条件满足，有真实范围、版本和原件；环境缺失或报告无效仍是缺口，不能转人工通过。 |
| 4. 处理人工分支 | 已批准验收方式、manual checks/regression、当前最终内容与用户结果 | manual→将实际入口、初始状态、操作和可观察结果写入 pending 清单，用 `prepare-manual` 绑定；用户返回结果或明确口头判断后按契约记录。未体验→等待；拒绝→修复复验；有效全通过结果→接受，无需再索取同一确认。automated 不造空清单或假人工接受。 | 对当前内容的实际人工决定，或清楚的等待项。Agent 编写样本、用户沉默、实现授权均不算接受；原件/版本无效先处理错误。 |
| 5. 检查附加条件与新变化 | Bug 根因/回归记录、用户是否指定独立审核、审核结果与最终差异 | Bug 按 Stage 5.5 留有用经验；只有指定审核才执行。报告返回不等于审核条件满足；存在阻断发现或重要未验证项先处理。最终验证后改变契约或源码时核对指纹与覆盖，并取得失效的验证及适用人工接受。 | 用户指定条件确已满足；没有指定审核则跳过。仅过程记录变更不机械重跑，但不能按“没改代码”豁免专业文档。 |
| 6a. 执行完成检查 | 当前证据、全部 AC 覆盖与必要检查结果 | 按 [完成命令](../reference/commands-and-validation.md#检查完成依据与台账) 运行 evidence validate 与 `check-feature-list.py --completion-feature`。 | 两项检查和 Agent 负责的其他条件均满足；失败时保留真实状态，返回对应缺口。 |
| 6b. 记录完成结果 | 已满足的完成条件与实际时间 | 在 Stage 7 写入 `done`/真实完成时间，再运行完整台账检查。 | 完成状态、时间和最终台账与实际结果一致；命令不会代写状态。 |
| 6c. 整理收尾记录 | 本次 notes、知识、报告与执行历史 | 按 [Stage 7 收尾说明](feature-delivery.md#完成记录与-git) 保存必要知识与证据链接，历史只归档一次，Progress 留当前状态及历史链接。 | 有用记录在提交前齐备；纳入指纹的新修改已经恢复失效验证。 |
| 6d. 提交剩余工作 | 本任务自有差异与有效证据 | 按 [Git 说明](feature-delivery.md#自动分批提交) 检查并提交剩余实现及完成记录，再核对工作区。 | 提交不夹带无关修改；用户明确不提交时保留该例外并报告实际状态。 |
| 6e. 交接并判断能否继续 | 实际交付、剩余事项、后续授权与前置 | 在 [Stage 8](feature-delivery.md#交付后如何继续) 汇报结果并核对下一步。 | 后续仅在具体授权与前置齐备时继续；否则交付本次结果或说明阻塞。 |

**示例判断：** 数值计算测试全部通过，但按钮是否易辨认属于已批准要求，仍要取得实际体验结果。若验收后改了 UI 规格或资源清单，不能只凭旧截图和旧接受完成；应核对当前内容绑定与需重验的范围。

### 人工验收失败之后怎么办

先保存真实拒绝及失败项，在 Progress 记录停点，Feature 保持未完成。用户只做了部分操作或尚未体验时记录 pending，不能改成通过。

| 步骤 | 分支与动作 | 可继续的判据 |
| --- | --- | --- |
| 确定拒绝原因 | 实现违反有效要求→原 Feature 返回 Stage 3；用户提出新要求→由 Product 或专业入口保存决定，处理已有计划影响；反馈含糊→只补齐必要事实。 | 每个失败项有归属；不为了消除拒绝而改写旧验收事实。 |
| 修复并恢复验证 | 沿已有授权修复，定稿必要规格与资源清单，再恢复失效的自动/静态/专项验证；范围扩大才取得所缺决定。 | 当前最终内容满足机器义务，原拒绝条件已有修复或已确认的要求处置。 |
| 重新准备并实际验收 | 用现有 `prepare-manual` 生成或更新并绑定当前版本的清单，保留旧拒绝原件；用户按实际入口再次检查。 | 取得对应当前内容的真实接受；再次拒绝重复本路径，未体验保持等待。 |

恢复后回上表的附加条件与正式完成核对；人工反馈文件与命令仍遵循 [人工验收操作](feature-delivery.md#人工验收应如何操作)，不新增拒绝状态或独立审批。

**最终产物与返回入口：** 当前版本的测试/专项证据、适用人工结果与指定审核结论、完成记录和本地提交，或明确的等待/失败状态。续接记录的具体处置见 [上下文与交接](scenarios-context-handoff.md#上下文不足时恢复现场并续接)。判据以 [Stage 3–8](../../../../../project-source/methodology/03-execute-loop.md#stage-4--automated-verification-and-human-checklist) 和 [人工文件契约](../../../../../project-source/methodology/manual-acceptance-files.md) 为准。
