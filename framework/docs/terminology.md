# 框架与 Godot 项目术语

本页统一框架、手册、提示词及生成项目使用的公共词汇，不另行定义流程或完成门槛。按名词、动作和影响判断的状态用语分类；具体契约以各节所列来源为准。

- **本页**：保存框架及工程公共用语，由框架维护者更新，两本手册共用这一份正文。
- **游戏项目的 `docs/terminology.md`**：保存该游戏跨模块复用的业务名称、定义、关系与别名，由 `project-terminology` 维护；玩法数值和完整行为仍归 GDD。
- **写法**：保留 Feature、Bug、Agent、AC、Git 等准确名称。普通叙述使用“任务备注”“完成”；只有说明字段或状态值时才写 `notes`、`done` 等标识。

## 名词性术语

| --- | --- |

| 权威来源 | 对某项事实或规则负责的唯一正文或实现；索引、摘要和报告引用它，不各自维护另一套定义 |
| README / AGENTS.md | 前者提供人类使用导航；后者规定 Agent 必须遵守的约束与按需阅读路由 |

### 需求、任务与执行主体

| 术语 | 本框架中的含义与边界 |
| --- | --- |
| GDD | Game Design Document，游戏设计正文；在 `docs/gdd/` 持续维护定位、核心循环、系统规则、内容与版本设计范围，是项目开发前提 |
| Product | 依据 GDD 划定的可验收交付单元，可覆盖一个系统、其中一部分或跨系统体验；不重复定义游戏规则 |
| Product 总览 | `docs/product.md` 中的交付预拆分、来源、边界、依赖与建议顺序；不等于 GDD 游戏总览 |
| Feature | 具有范围、验收条件和状态的开发任务；工程 Bug、重构和维护也可按规范建为 Feature |
| AC | 验收条件（Acceptance Criteria），说明目标行为如何被客观判断；不等于一条测试用例 |
| Bug | 实现偏离仍有效的已确认要求或契约；用户改变要求不自动归为 Bug |
| 工程变更 | 修复、重构或维护已有系统的任务类型；具体分类由工程变更规范决定 |
| Stage | Feature 执行规范中的阶段定位，不是新增的逐阶段审批或自动状态机 |
| Goal | 承载持续授权工作的目标；Goal 停止或预算耗尽不证明 Feature 完成 |
| Agent | 负责当前任务的 AI 执行主体；采用 Skill 不等于已经委派另一个 Agent |
| Skill | 围绕一个明确职责组织的专项方法及按需资料；多个场景可以使用同一方法 |
| researcher | 按问题收集外部资料并区分事实、推断和未知的调研角色 |
| independent-reviewer | 在指定范围独立形成审核结论的角色；角色配置存在不证明实际独立实例已运行 |
| 提示词 / Prompt | 用户发送给 Agent 的当前任务输入；集中库中的每条入口只对应一个具体场景 |
| 公开接口 / API | 调用方依赖的参数、返回值、行为及失败约定；影响消费者时须核对实际契约 |

来源：[方法总览](../../project-source/methodology/00-overview.md)、[执行规范](../../project-source/methodology/03-execute-loop.md)、[工程变更](../../project-source/methodology/07-engineering-change.md)、[角色源文件](../../project-source/agents/)、[职责设计准则](../review/baselines/skill-script-prompt-design.md)。

### 验证与记录

| 术语 | 本框架中的含义与边界 |
| --- | --- |
| Registry / 测试登记表 | `docs/test-registry.json` 中的组件、测试身份、套件与生命周期记录；登记不等于执行通过 |
| 验证义务 | 当前任务必须取得的自动、静态、专项或人工依据；由适用规范和任务要求决定 |
| baseline / 基线 | 必须写清所属对象：修改前测试基线、规划覆盖基线或审核基线不能互换 |
| RED / GREEN | 目标行为的测试失败 / 修复后的通过；环境或解析失败不能冒充目标行为的 RED |
| 静态检查 | 不运行目标游戏行为，对文本、结构、引用、类型或规则进行核对 |
| lint | 按项目已配置规则检查代码问题与风格；不得为了通过而擅自放宽规则 |
| 类型检查 / type check | 核对实际技术栈支持的类型约束；使用现有入口，不凭空增加另一套工具链 |
| 回归测试 | 检查修改后原有相关行为是否仍符合要求；通过范围以实际执行的用例为准 |
| 人工验收 | 用户对当前内容取得并提供真实观察与接受结果；实施授权、自动通过与沉默均不能替代 |
| 完成检查 | 所属任务正式完成前的整体核对；统一使用此词，不另称“交付检查”或“收尾检查”，也不与一次人工验收混称 |
| 完成记录 / 完成依据 | `docs/feature-completion-evidence.json` 中对实际验证原件和接受结果的引用及绑定；文件存在本身不证明条件满足 |
| 内容指纹 | 按工具契约判定记录所对应内容是否仍适用的标识；不是额外授权或人工验收 |
| Progress / 进度记录 | 当前任务停点、阻塞与下一步；不代替需求、验收条件或完成证据 |
| ADR | 架构决策记录，保存有实质取舍的决定与理由；决定已接受不等于实现已经验证 |
| 报告 | 某次审核、调研或运行的事实与限制；旧报告不证明当前版本已通过 |
| Git 提交 | 对选定文件状态的本地版本记录；提交不等于测试通过、人工接受或正式交付 |

来源：[测试策略](../../project-source/methodology/08-testing-strategy.md)、[人工验收文件](../../project-source/methodology/manual-acceptance-files.md)、[验证政策](../../project-source/agent-rules/00-core/validation-policy.md)、[架构记录](../../project-source/methodology/10-architecture-overview.md)。

### Godot 与资源工具

| 术语 | 在本项目资料中的使用方式 |
| --- | --- |
| GDScript | 项目使用的 Godot 脚本语言；工程约束按对应领域规则查阅 |
| Node / 节点 | 可组成场景树的对象；创建、入树、离树和释放是不同生命周期阶段，职责按实际场景与代码确定 |
| Scene / 场景资源 | Godot 的场景文件及其节点结构；文档中的“使用场景”则指用户情境，必要时写全称区分 |
| Resource / 资源对象 | Godot 可被引用、共享和保存的数据对象；“素材”更侧重外部图像、音频等输入文件 |
| Shader | 本项目使用的着色器程序；工作台当前支持范围以实际工具契约为准 |
| Signal / 信号 | Godot 对象间的事件通知机制；不能仅凭静态文本搜索推定所有连接关系 |
| Autoload | 通过项目配置自动加载的对象；不是所有共享能力都必须采用的组织方式 |
| UID | Godot 资源身份标识；与文件路径相关但不应当作同一字段随意替换 |
| 导入元数据 / 导入缓存 | `.import` 保存源资源的导入配置，`.godot/` 保存生成缓存；两者不能一并当作可删除垃圾 |
| Cue | 工作台及消费示例用于保存所选资源与表现参数的配置资源；不等于源素材本身 |
| 工作台 | 编辑期查看、试调、比较和保存资源组合的工具；临时草稿与已保存 Cue 分开 |
| Analyzer / 源资源分析器 | 对图像、音频源文件进行分析的工具；结果不替代渲染效果、听感或运行性能测量 |
| 消费入口 | 读取已保存 Cue 并在运行时使用它的场景或代码；区别于工作台编辑入口 |
| A/B 比较 | 在规定条件下对照两份候选或参数；具体比较对象需写明 |

来源：[工程领域规则](../../project-source/agent-rules/)、[工作台与消费示例](../../project-source/examples/asset_workbench/README.md)。这里只解释项目用语，不代替 Godot API 文档。

## 动词性术语

| 动作 | 应表达的结果与边界 |
| --- | --- |
| 创建 | 产生新的项目或对象；创建器完成复制不代表环境已就绪 |
| 初始化 / 配置 | 建立或调整所需初始状态、工具路径等；就绪仍以对应实际检查为准 |
| 预拆分 | 在 Product 总览检查约定交付范围、粗略边界、来源与依赖；不提前生成后续 Product 正文或 Feature |
| 细化当前 Product | 轮到该交付单元时，依据最新 GDD 和已完成工作写明本次交付边界与衔接 |
| 规划 Feature | 一次覆盖当前 Product 的完整必要范围，确定任务、依赖、AC 和验证方式；规划完成不等于实现完成 |
| 实施 / 实现 | 在有效授权内改变代码、资源或配置，达到当前目标 |
| 诊断 / 定位 | 用证据确认问题及其原因；尚未证明的解释称为假设，不自动扩大为修复 |
| 修复 | 使偏离既有要求的行为恢复预期；不通过降低 AC 或改历史验收结果达成 |
| 重构 | 在保持约定行为的前提下改善结构；有具体收益与相应回归依据 |
| 优化 | 必须说明优化对象与比较依据，例如性能预算或查找成本；“优化了”本身不是可验证结果 |
| 迁移 / 替换 | 按明确方案改变承载位置或实现并核对消费者、引用及保留的数据；不是自动升级承诺 |
| 接入 / 消费 | 将已确认素材、资源或能力接到实际使用位置；收到文件不等于接入完成 |
| 同步 | 更新明确受影响的直接来源与引用；框架不因此自动更新已有游戏项目 |
| 验证 | 用适用检查判断某项要求是否成立；需要说明对象、范围与结果 |
| 复验 | 对修复或内容变化后的对象再次执行必要检查；不能用旧版本结果替代 |
| 审核 / 审查 | 根据证据评价内容、实现或职责并形成结论；不自动获得修改权限 |
| 验收 | 按约定条件接受当前交付物；人工验收须有实际用户结果 |
| 完成 / 正式交付 | 满足所属流程的出口；Feature 以规定状态及完成记录为准，不只看测试、提交或试玩 |
| 提交 | 创建 Git 版本记录；“提交到远端”应明确称为推送，不能混用 |
| 暂停 / 续接 | 保存真实停点 / 从已有文件、有效授权和记录继续；不重新推定旧验证仍有效 |
| 归档 / 清理 | 保存历史 / 移除已获准且不再需要的对象；未跟踪或暂存目录名称不授予删除权限 |

动作的授权与完成条件仍按[维护约定](../../AGENTS.md)、[项目执行规范](../../project-source/methodology/03-execute-loop.md)及所属场景执行；本表只统一表达。

## 状态、形容词与副词

只记录会影响执行判断或经常产生误解的词，不建立普通形容词词典。

| 用语 | 使用要求 |
| --- | --- |
| 已确认 / 已批准 | 写清被确认的是需求、方案、范围还是验收结果，不能互相代替 |
| 已通过 / 有效 | 指明检查对象、对应内容和范围；工具退出码为零不等于整个流程完成 |
| 待定 / 待验收 / 阻塞 | 分别表示尚缺决定、尚缺适用人工结果、存在不能继续的前置；不要统称“未完成”而隐藏原因 |
| 失效 / 过期 | 当前内容、版本或条件已使旧依据不再适用；日期较早本身不能证明失效 |
| 最小完整 | 完整解决本次目标所需的最小影响范围；不是文件最少或行数最少 |
| 自动 / 人工 | 表明谁实际完成动作；“可自动完成”不证明已经运行。Agent 不得编造人工观察或代替用户作出接受决定，可以如实记录用户的实际结果 |
| 正常 / 成功 / 没问题 | 不单独作为完成标准；改为具体可观察的状态或检查结果 |

新增或改义时先核对现有权威来源、别名和实际消费者，再更新本页及必要引用。具体玩法词汇、场景完整步骤、字段枚举和工具参数仍保留在各自所属文件，不复制进词表。
