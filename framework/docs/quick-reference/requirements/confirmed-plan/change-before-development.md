# Feature 还没开工，但已经确认要修改其中一条要求

[返回场景索引](../../scenario-index.md#需求与计划) · [执行步骤](#执行步骤) · [完成标准](#完成状态与验证标准)

## 触发场景与使用时机

已经有 Feature 计划，开始实现前确认某条行为或专业要求需要变化，原计划仍按旧要求安排。

## 前置条件与适用范围

变化已经确认，并已由所属需求或专业入口保存、单独提交。能够核实原计划采用的来源基线，受影响的任务均尚未开工；本次已授权分析和同步计划。

本页处理“来源就绪后的计划同步”。新来源尚未保存、历史基线无法核实、受影响任务已经开发或完成时，先解决对应前提，不在本页展开另一套同步路径。开始独立同步前按项目规则核对工作区。

## 参与角色与职责边界

用户决定新的实质取舍；Agent 分析影响、调整获准计划并核对一致性。来源所属入口负责需求原文，接手的实现任务负责后续代码变化。

## 流程概览

比较来源 → 追到受影响计划 → 确定调整 → 更新计划和修订 → 检查并交付。

## 执行步骤

使用 [集中提示词库](../../../../prompts.json)中的“Godot 项目开发 → 任务规划 → 需求变化后同步已有任务”。填入来源文件、真实变化提交、原 Feature 和允许调整范围；当前 Agent 使用 [$feature-sync](../../../../../project-source/skills/feature-sync/SKILL.md)，本页不切换到实现 Skill。

**S1｜比较变化**

Agent 按 `feature-sync` 读取当前来源提交、台账中的同步锚点和相关修订，比较实际采用来源的差异，列出新增、删除和调整的要求。核对来源已单独提交、受影响任务尚未开工。

**S2｜找到影响**

Agent 沿来源引用、共享规格和任务依赖追到全部受影响的已有计划，列出需要调整的 AC、依赖、测试映射及失效测试清理责任。展示具体调整及影响，沿用已确认方案，缺少实质取舍时由用户决定。

**S3｜同步计划**

Agent 使用 `feature-sync` 更新获准的 `docs/feature-list.json`、相关详情和 `docs/test-registry.json`，在 `docs/feature-list-revisions.json` 追加本次修订；同步锚点只采用实际分析过的提交。保留原 ID 与历史，不通过重置台账处理变化。

**S4｜检查并交付**

Agent 对照变化逐项检查需求覆盖、引用及历史保留。在游戏项目根目录，用配置中已确认的 Python 调用 `tools/checks/check-feature-list.py`，立即检查退出码。核对实际差异后按项目约定提交计划，明确后续负责代码修改与测试清理的 Feature；本页不修改游戏或测试代码。

## 步骤产出与状态变化

| 步骤 | 产出与继续条件 |
| --- | --- |
| S1 | 新旧要求差异和比较基线有证据 |
| S2 | 每项变化有负责的任务及验证安排，调整范围已明确 |
| S3 | 当前计划与采用来源一致，追加的修订可追溯 |
| S4 | 台账检查通过，历史未被改写，后续实现责任清楚 |

## 资源与文件影响

| 项目内对象 | 影响 |
| --- | --- |
| 已提交的 Product、专业文档或规则 | 读取变化与引用 |
| 任务索引、相关 Feature 详情 | 修改范围、AC、依赖或来源引用 |
| 测试登记与修订记录 | 保存获准调整和实际采用来源 |
| 游戏与测试代码 | 本页仅分析影响，修改责任交给实现任务 |
| Git | 提交本次计划改动，保留已有来源提交 |

## 阻塞、异常与范围变化

发现来源未提交、来源链接仍需修复或同步期间来源又发生变化时，暂停计划写入；由所属入口处理来源后，重新核实 S1 的比较和受影响决定。

发现某个受影响任务已开工或完成，保留影响分析，退出本页并处理该状态下的变更归属。要求冲突、登记冲突或台账检查失败时，只修正本次已授权范围内的缺口，不把未检查的计划报告为同步完成。

## 完成状态与验证标准

每项已确认变化都有对应任务和验证责任；最终计划引用实际采用来源；修订和登记一致，完整台账检查通过，本次计划已按约定提交。后续代码变化和测试清理明确标为尚待执行。

## 流程关联与衔接关系

上游可来自[首次规划](../ready-to-plan/plan-confirmed-module.md)之后的要求调整。下游是受影响任务的实现，本页同步完成不代替实现授权或执行结果。
