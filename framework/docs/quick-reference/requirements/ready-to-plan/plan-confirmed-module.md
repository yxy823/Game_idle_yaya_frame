# 当前模块的需求已确认，准备做项目的第一份 Feature 计划

[返回场景索引](../../scenario-index.md#需求与计划) · [执行步骤](#执行步骤) · [完成标准](#完成状态与验证标准)

## 触发场景与使用时机

当前要做的模块已经讨论清楚，希望把它变成可以依次开发和验证的任务。

## 前置条件与适用范围

本页限定项目的首次规划：任务索引与修订记录均为空，当前模块及其已采用专业要求有明确来源，已获得规划授权。行为和验收意图尚不明确时，先完成需求讨论。

写入采用来源需要的正式状态和真实提交必须可核实；新规划任务按项目规则具备干净工作区。后续模块追加、修改已有计划和执行 Feature 均不在本页范围。

## 参与角色与职责边界

用户决定尚缺的重要取舍；Agent 提出拆分、维护计划并检查覆盖。台账工具检查结构、引用与依赖，不能替代 Agent 判断要求是否全部落实。

## 流程概览

核对首次规划输入 → 展示任务拆分 → 固定采用来源 → 写入计划与首次基线 → 检查并交付计划。

## 执行步骤

使用 [集中提示词库](../../../../prompts.json)中的“Godot 项目开发 → 任务规划 → 拆分当前 Product 的 Feature”。填入当前 `docs/product/NN-<module>.md`、已确认专业规格和本次范围；由当前 Agent 使用 [$feature-plan](../../../../../project-source/skills/feature-plan/SKILL.md)完成规划，不需要另建规划 Agent。

**S1｜核对输入**

当前 Agent 按 `feature-plan` 读取模块、执行顺序与采用的专业规格，检查 `docs/feature-list.json`、`docs/feature-list-revisions.json` 确实为空，并用 `git status --short` 核对工作区及修改归属。

**S2｜展示拆分**

Agent 在对话中展示拆分数量、每项范围、验收条件（AC）、依赖和验证方式。按照规划入口的拆分预览要求，由用户确认具体方案；已确认且未改变的方案直接沿用，已有明确自主拆分授权时按该授权执行。

**S3｜固定来源**

Agent 核对本次采用的需求和专业来源，按首次规划规范完成必要的来源提交，取得真实提交号与引用位置。来源提交和后续计划提交分别处理。

**S4｜写入计划**

Agent 使用 `feature-plan` 写入索引、`docs/features/` 下的新详情及必要测试计划，建立仅覆盖当前采用范围的 R000 首次基线。需要新增组件时，将获准组件放入临时 JSON，用项目 Python 调用 `tools/features/merge-test-registry.py --components <实际候选文件>`；合并器只处理组件，具体测试登记仍按规划规范维护，候选文件不提交。

**S5｜检查并交付**

Agent 对照需求核对 Feature/AC 与验证安排，再用项目 Python 调用 `tools/checks/check-feature-list.py` 检查完整台账，并用 `--eligible` 查询满足依赖的候选。检查差异并按约定提交本次计划，指出第一项候选；候选可执行不代表已经授权实现。

这里的工具均在实际游戏项目根目录调用，使用 `docs/methodology-config.json` 中已确认的 `python_executable`，调用形式为 `& $projectPython -B <脚本路径> <参数>`，每次立即检查 `$LASTEXITCODE`。S4 会修改登记表；S5 的检查只读，不运行测试。

## 步骤产出与状态变化

| 步骤 | 产出与继续条件 |
| --- | --- |
| S1 | 首次规划条件成立，当前模块及采用来源清楚 |
| S2 | 每项要求有任务、AC 和验证责任，拆分已在有效授权内确定 |
| S3 | 采用来源有真实提交，后续计划能引用实际内容 |
| S4 | 任务与登记已写入，R000 只覆盖实际采用范围 |
| S5 | 语义覆盖无缺口，台账检查通过，本地提交和首项任务可定位 |

## 资源与文件影响

| 项目内对象 | 影响 |
| --- | --- |
| 当前 Product 模块及已采用专业来源 | 读取，核对采用内容与来源提交 |
| `docs/feature-list.json`、`docs/features/` | 写入当前模块的任务索引和新详情 |
| `docs/test-registry.json` | 合并实际需要的组件与测试计划登记 |
| `docs/feature-list-revisions.json` | 建立 R000；不伪造历史覆盖 |
| Git | 提交本次已核对的来源和计划改动，按项目规则分别处理 |

## 阻塞、异常与范围变化

要求冲突或仍无法写出验收条件时，保留拆分建议，暂停依赖它的计划写入。来源无法提交、空台账条件不成立或存在未知修改时，保留现场，重新选择适用场景。

检查失败时在当前规划范围内修正实际缺口；未通过前不能称为可执行计划。恢复后从受影响步骤继续，不重复制造任务。

## 完成状态与验证标准

当前模块每项已确认要求都对应任务与可观察 AC；索引、详情、登记和 R000 一致；完整台账检查通过；实际提交和首项任务可定位。Feature 保持初始规划状态，本页不产生实现或测试通过结论。

## 流程关联与衔接关系

后续实现由当前授权和任务前置决定。尚未开工便改变要求时，使用[计划变更场景](../confirmed-plan/change-before-development.md)。
