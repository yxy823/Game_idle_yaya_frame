# Feature 交付后发现 Bug

[返回场景索引](../../scenario-index.md) · [执行步骤](#执行步骤) · [完成标准](#完成状态与验证标准)

## 触发场景与使用时机

Feature 交付后发现 Bug。

需要的材料：

- 任务与要求：所属 Feature、仍有效要求。
- 问题证据：实际表现、复现与日志。

## 前置条件与适用范围

正式交付以项目规定的 Feature 完成状态和完成记录为准，不以测试通过、代码提交或用户试玩作为单独依据。本页限定已交付行为出现缺陷。

## 执行步骤

使用[集中提示词库](<../../../../prompts.json>)中的“Godot 项目开发 → 修复与改进 → Feature 交付后发现 Bug”。填入上述材料；已有对话直接补齐输入，不必重发入口。本页使用 [$engineering-change-plan](<../../../../../project-source/skills/engineering-change-plan/SKILL.md>)、[$feature-execute](<../../../../../project-source/skills/feature-execute/SKILL.md>)，具体执行者和切换位置见下文。

**S1｜记录问题与现场**

当前 Agent 核对仍有效要求、实际失败和交付状态，保留复现与日志。追到当前实现、已交付契约与直接消费者，分别记录已证实根因和假设，简述独立修复范围及旧行为回归。

**S2｜修复既有要求**

当前 Agent 先使用 `engineering-change-plan` 的 bug 模式建立独立任务和 `bug_diagnosis`，再使用 `feature-execute` 修复；原 Feature 历史保持真实。

- 按[共用变更规则](../../../../../project-source/agent-rules/00-core/change-scope-and-ownership.md)控制影响，保持无需变化的 API、依赖和代码风格。
- 为实际缺陷补必要回归；无法自动覆盖时保留原因与可重复的人工路径。
- 遵循专用入口当前有效的提交约束。

**S3｜取得实际复验**

当前 Agent 完成受影响自动测试与项目支持的适用解析、lint 或类型检查，向用户提供实际体验入口并记录明确结果；未通过继续在授权内修复。

**S4｜返回完成检查**

当前 Agent 核对测试原件、当前接受与适用评审，检查最终差异没有无关改动，说明关键文件、修复理由及具体剩余风险，按本次提交约束返回独立 Bug 任务的完成检查。

## 步骤产出与状态变化

| 步骤 | 可继续的依据 |
| --- | --- |
| S1 | 缺陷事实和任务归属明确 |
| S2 | 修复没有放宽原验收要求 |
| S3 | 最终内容有真实复验结果 |
| S4 | 独立 Bug 任务可办理完成检查，原交付历史未改写 |

## 资源与文件影响

实现、回归测试和所属任务记录修改；原 Feature 的 AC、完成状态与验收历史只读，不为新缺陷重写。

## 阻塞、异常与范围变化

- 要求实质改变：转需求变更。
- 无关功能缺陷：另按所属场景处理。
- 只诊断请求：使用只读定位。
- 无法复现：保留证据缺口，不宣称修复。

## 完成状态与验证标准

独立 Bug 任务满足其适用验证与实际人工接受，原交付历史保持真实。

## 流程关联与衔接关系

依据：[项目路由依据](<../../../../../project-source/methodology/00-overview.md>)。本页达到出口后，仍已明确授权的后续工作按其所属场景继续；准备、诊断、规划或记录完成不替代 Feature 的正式完成。
