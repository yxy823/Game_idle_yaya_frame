# Feature 已交付，后来确认要改变要求

[返回场景索引](../../scenario-index.md) · [执行步骤](#执行步骤) · [完成标准](#完成状态与验证标准)

## 触发场景与使用时机

Feature 已交付，后来确认要改变要求。需要的材料：已提交来源差异、受影响 Feature、批准的需求变化。

## 前置条件与适用范围

受影响 Feature 已交付，正式来源已由所属入口改好；本次同步计划。

## 执行步骤

使用[集中提示词库](<../../../../prompts.json>)中的“Godot 项目开发 → 任务规划 → Feature 已交付，后来确认要改变要求”。填入上述材料；已有对话直接补齐输入，不必重发入口。本页使用 [$feature-sync](<../../../../../project-source/skills/feature-sync/SKILL.md>)，具体执行者和切换位置见下文。

**S1｜确认有效差异**

当前 Agent 用 feature-sync 核对来源提交、真实基线及所有适用消费者，不只追直接链接。

**S2｜修订受影响计划**

保留原完成事实、原 AC 与历史，按现有演进规范为新的独立交付追加任务并明确消费者回归。

**S3｜检查并交接**

调用项目 tools/checks/check-feature-list.py，检查 ID、引用与覆盖后提交，交回获准执行。

项目工具命令在实际游戏项目根目录执行；使用 `docs/methodology-config.json` 中的 `python_executable`，调用形式为 `& $projectPython -B <脚本路径> <参数>`，每次立即检查 `$LASTEXITCODE`。尖括号参数替换为实际值。命令成功只证明该操作完成。

## 步骤产出与状态变化

| 步骤 | 可继续的依据 |
| --- | --- |
| S1 | 变化与消费范围可核实 |
| S2 | 计划变化忠实承接新要求 |
| S3 | 计划对齐不冒充实现完成 |

## 资源与文件影响

Feature 索引、详情、测试登记及必要修订修改；Product 读取，历史完成记录不篡改。

## 阻塞、异常与范围变化

来源尚未改好或基线无法核实时先交对应来源或基线恢复场景；不伪造差异。

## 完成状态与验证标准

新变更有独立可执行任务，旧完成历史保持真实。
