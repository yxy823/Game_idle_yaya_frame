# 设计资料分散在多处，需要整合 GDD

[返回场景索引](../../scenario-index.md) · [执行步骤](#执行步骤) · [完成标准](#完成状态与验证标准)

## 触发场景与使用时机

玩法已经在笔记、对话记录或几份文档里讨论过，但正文分散、同一规则出现多个版本，难以判断目前采用哪一个。希望整合为项目内可查找、可维护的 GDD。

需要的材料：指定资料的位置或内容、已有 GDD 入口、这次整合的主题与目标位置、有效决定和已知冲突。

## 前置条件与适用范围

可以尚未有完整 GDD，也不要求 Product 或 Feature。此处处理已有资料的整合；只有一个游戏想法时使用[形成 GDD 草稿](<只有游戏想法，先形成 GDD 草稿.md>)，只希望阅读外部需求并返回改写建议时使用[外部需求草稿](<拿到一份外部需求，先整理成项目可用的草稿.md>)。

## 执行步骤

使用[集中提示词库](../../../../godot-development-prompts.json)中的“Godot 项目开发 → 需求设计 → 设计资料分散在多处，需要整合 GDD”。当前 Agent 使用 [design-gdd](../../../../../project-source/skills/design-gdd/SKILL.md)，按需读取其整合参考。

**S1｜核对来源与有效决定**

对照现有 GDD《设计范围与边界》及相关主题，把当前范围内的重复、互补和冲突内容分清，核对哪些决定已采用。较新、较长的文档或已经存在的实现都不能自动压过有效设计决定；涉及玩法取舍的冲突只向用户补问必要问题。

同时核对 `docs/gdd/open-questions.md` 中相关问题，复用已有决定，避免再次提出已经解决的选择。

**S2｜整合唯一正文**

将可确定的内容放入所属 GDD 主题。涉及整体范围时按[设计范围与边界](../../../../../project-source/methodology/01-product-doc-structure.md#design-scope-and-boundaries)归到固定子文档，局部限制留在所属主题，其他位置通过导航和引用到达正文。保留不受影响的结构，不重排无关内容或预建空章节。保留原始输入资料，不能静默删除未采用材料或把候选改为确定规则。

按[开放问题规范](../../../../../project-source/methodology/01-product-doc-structure.md#open-design-questions)把尚未解决的设计冲突归入固定文件，保留来源、影响和所需决定，主题只保留必要上下文与引用。后续讨论和规划据此处理依赖；已解决项的结果写回所属主题并更新引用。

**S3｜核对覆盖和后续影响**

说明约定资料归到哪里、哪些内容未纳入以及原因，标明未解决的冲突。已有专业来源、Product 或 Feature 确受影响时指出消费者和所属同步入口；本次没有这些记录也不需要为整合补建一套。

## 资源与文件影响

本入口请求维护 `docs/gdd/` 的正文与必要导航；用户只要求讨论时，不写文件。引用原始资料不改变其文件，未经额外授权不删除或覆盖原件，不开始实现或重写历史验收。

## 阻塞、异常与范围变化

不能确定采用哪份设计时，保留冲突及其依据，只停止依赖该决定的部分。新的玩法决定回到设计讨论，不能把资料整理当作全款游戏的设计授权。

## 完成状态与验证标准

约定范围内可确定的资料已整合，原意、采用状态、正文归属和引用已核对。影响当前整合的关键冲突尚未解决时，明确未完成部分；文件保存不能代替这些决定，也不证明游戏已运行或体验已通过。

## 流程关联与衔接关系

数值主题需要建模时使用[数值模型设计](<体验目标已明确，需要设计数值模型.md>)；已有模型需要调整时使用[模型与参数调整](<已有数值需要调整，更新模型与参数.md>)。当前设计已采用且明确、且获准安排交付后，才进入 [Product 预拆分](<已有 GDD，需要预拆分 Product 交付范围.md>)。

已有明确的来源或计划同步授权按所属方法继续；本页不把整合完成当作 Feature 完成。
