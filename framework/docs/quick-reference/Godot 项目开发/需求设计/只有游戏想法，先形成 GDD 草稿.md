# 只有游戏想法，先形成 GDD 草稿

[返回场景索引](../../scenario-index.md) · [执行步骤](#执行步骤) · [完成标准](#完成状态与验证标准)

## 触发场景与使用时机

已有游戏想法或尚未完善的初稿，希望与 Agent 一起讨论“玩家会做什么、为什么愿意继续玩”，逐步明确当前范围的设计并形成游戏设计文档（GDD）。

需要的材料：游戏想法或已有 GDD 草稿、目标玩家与体验、平台及其他约束、已有决定或参考，以及这次希望明确的范围。

## 前置条件与适用范围

在实际游戏项目中进行，允许从零设计；不要求已经有完整 GDD、Product、Feature 或可运行环境。一次可以只形成核心循环和直接相关规则，不必补齐整款游戏。

## 执行步骤

使用[集中提示词库](../../../../godot-development-prompts.json)中的“Godot 项目开发 → 需求设计 → 只有游戏想法，先形成 GDD 草稿”。已有对话可以直接补齐输入，不必重发入口。

**S1｜确定当前要讲清的设计**

当前 Agent 使用 [design-gdd](../../../../../project-source/skills/design-gdd/SKILL.md)，核对现有想法、GDD《设计范围与边界》及相关主题、适用工程约束和有效决定，只补问会实质改变当前结果的问题。范围文档尚未形成时沿用已知设计与明确决定；参考游戏和 Agent 建议不能自动写成已采用要求。

已有 `docs/gdd/open-questions.md` 时，读取与本次范围有关的问题和依赖，复用已有答案，再继续讨论。

**S2｜讨论关键选择并形成草稿**

围绕目标体验、玩家过程、核心循环和当前相关规则展开，说明各机制如何产生预期体验。有关键选择需要共同决定时，使用 [GDD 共创方法](../../../../../project-source/skills/design-gdd/references/gdd-dialogue.md)，结合玩家情境提出问题与候选方案，说明取舍和推荐理由；需要构思或比较玩法方向时再读[构思方法](../../../../../project-source/skills/design-gdd/references/concept-ideation.md)。

等待回答时继续不依赖该决定的整理；回答后推进当前范围内下一项关键问题。已经明确的内容直接整理，不重复访谈。数值模型确实需要展开时再使用 [design-balance](../../../../../project-source/skills/design-balance/SKILL.md)。

**S3｜随讨论保存草稿并说明设计状态**

本入口请求保存 `docs/gdd/` 中的草稿，可随有效决定更新正文。新 GDD 使用 `docs/gdd/README.md` 入口，其他主题按[标准文件名与职责](../../../../../project-source/methodology/01-product-doc-structure.md#gdd-document-names)使用固定名称并按需创建；文件名不随正文语言变化。按[设计范围与边界](../../../../../project-source/methodology/01-product-doc-structure.md#design-scope-and-boundaries)建立 `design-scope-and-boundaries.md` 及入口引用，整体范围集中维护，局部限制留在所属主题。保留不受影响的既有结构，引用真实文件与章节，必要的迁移同步使用方。若用户限定只讨论，则只在对话中形成结论，并说明有用的已确认结论尚未保存。区分已采用决定、候选、明确暂缓事项和验证缺口，指出它们限制的下一步。

草稿保存不结束尚未完成的共创。仍需用户决定的关键选择应继续进入讨论；用户明确要求先交一版草稿时，可以先交付可读草稿并列明假设与缺口。

获准写入时，按[开放问题规范](../../../../../project-source/methodology/01-product-doc-structure.md#open-design-questions)维护 `docs/gdd/open-questions.md` 及入口引用。后续讨论、规划、审核和相关实验使用其中的问题；决定落实到所属主题后更新引用并移除已解决条目，避免与设计正文分别维护同一问题。

## 资源与文件影响

只维护当前 GDD 草稿和必要导航。不会因为写了草稿就创建 Product、Feature、运行资源或游戏代码；保存也不表示所有提案已被采用。

## 阻塞、异常与范围变化

能从资料或分析查清的问题由 Agent 先核实；需要试玩、测量或运行才能判断的问题保留为验证缺口，说明它限制哪部分设计采用，不自动启动原型或运行验证。缺少必要决定或证据时，只停止依赖它的工作；用户要求暂停或收窄时保留实际停点。不得用虚构决定填空，也不把整个任务强制改成长访谈。

## 完成状态与验证标准

当前约定范围的草稿已形成并按授权保存，或在只讨论的限制下形成同范围结论；关键玩法与体验选择已明确或由用户明确暂缓。需要实测的事项已说明验证问题及其对后续采用的限制；等待关键选择的回答仍是待决定状态，不能仅因文件已保存就宣告完成。用户明确仅要先交草稿时，以完成该草稿并说明关键缺口为本次出口。

草稿能用一段具体玩家过程解释玩法，规则冲突、来源和重要缺口已核对。文档自查不代表设计已全部采用，也不代表已经试玩、数值平衡或运行验证。

## 流程关联与衔接关系

资料已有多份且需要统一正文时，使用[整合 GDD](<设计资料分散在多处，需要整合 GDD.md>)。体验目标和机制已足以建模时，可以进入[数值模型设计](<体验目标已明确，需要设计数值模型.md>)。只有当前设计已采用且明确，并获准安排交付，才转入 [Product 预拆分](<已有 GDD，需要预拆分 Product 交付范围.md>)。

已有具体后续授权继续有效；本页完成不代替后续规划、实现或实际验收。
