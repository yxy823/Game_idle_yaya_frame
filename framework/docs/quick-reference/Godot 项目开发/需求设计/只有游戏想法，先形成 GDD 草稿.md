# 只有游戏想法，先形成 GDD 草稿

[返回场景索引](../../scenario-index.md) · [执行步骤](#执行步骤) · [完成标准](#完成状态与验证标准)

## 触发场景与使用时机

已经有一个游戏想法，希望把“玩家会做什么、为什么愿意继续玩”写成可讨论的游戏设计文档（GDD）。项目还没有设计正文，或现有材料仅是几句方向说明。

需要的材料：游戏想法、目标玩家与体验、平台及其他约束、已有决定或参考，以及这次希望明确的范围。

## 前置条件与适用范围

在实际游戏项目中进行，允许从零设计；不要求已经有完整 GDD、Product、Feature 或可运行环境。一次可以只形成核心循环和直接相关规则，不必补齐整款游戏。

## 执行步骤

使用[集中提示词库](../../../../prompts.json)中的“Godot 项目开发 → 需求设计 → 只有游戏想法，先形成 GDD 草稿”。已有对话可以直接补齐输入，不必重发入口。

**S1｜确定当前要讲清的设计**

当前 Agent 使用 [design-gdd](../../../../../project-source/skills/design-gdd/SKILL.md)，核对现有想法、有效决定与限制，只补问会实质改变当前结果的问题。参考游戏的做法与 Agent 建议属于候选，不能自动写成用户已采用的要求。

**S2｜形成可读的草稿**

围绕目标体验、玩家过程、核心循环和当前相关规则展开，说明各机制如何产生预期体验。按需读取 Skill 的构思、对话或字段参考；数值模型确实需要展开时再使用 [design-balance](../../../../../project-source/skills/design-balance/SKILL.md)。

**S3｜按授权保存并说明设计状态**

本入口请求保存 `docs/gdd/` 中的草稿；若用户限定只讨论，则只在对话中给方案。新建默认使用入口与实际需要的主题文档，已有有效结构继续使用，遵循项目文档语言。区分已采用决定、候选和必要未决项，指出哪些缺口会阻塞下一步。

## 资源与文件影响

只维护当前 GDD 草稿和必要导航。不会因为写了草稿就创建 Product、Feature、运行资源或游戏代码；保存也不表示所有提案已被采用。

## 阻塞、异常与范围变化

材料不足时先处理可明确的部分；涉及核心玩法或体验取舍的关键问题，说明它影响哪部分设计。不得用虚构决定填空，也不把整个任务强制改成长访谈。

## 完成状态与验证标准

当前约定范围的草稿已经形成并按授权保存，能用一段具体玩家过程解释玩法，规则冲突、来源和重要缺口已核对。文档自查不代表已经试玩、数值平衡或运行验证；需要这些证据时明确当前缺口。

## 流程关联与衔接关系

资料已有多份且需要统一正文时，使用[整合 GDD](<设计资料分散在多处，需要整合 GDD.md>)。体验目标和机制已足以建模时，可以进入[数值模型设计](<体验目标已明确，需要设计数值模型.md>)。只有当前设计已采用且明确，并获准安排交付，才转入 [Product 预拆分](<已有 GDD，需要预拆分 Product 交付范围.md>)。

已有具体后续授权继续有效；本页完成不代替后续规划、实现或实际验收。
