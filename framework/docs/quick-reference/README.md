# 场景速查手册的编写与维护

本 README 面向编写者，约定场景的范围、标题、内容分类和维护方式。使用者从[场景索引](scenario-index.md)进入具体页面。场景按已确认的 Project、分类和同名专用提示词规则维护；新增和实质改变职责时先应用[职责设计准则](../../review/baselines/skill-script-prompt-design.md)。

## 收录什么

收录项目开发与框架维护的具体情境，包括正常推进、要求变化、问题处理和中断续接。三类文档的分工如下：

- **场景速查手册**：每篇交付一个可验证结果，按 Project 区分执行仓库，不把维护源的操作带入游戏项目。
- **操作手册**：说明框架概念、配置字段和工具的完整用法。
- **维护文档**：保存框架维护准则与维护工具说明。

按单人项目组织场景：覆盖同一项目目录内的操作、暂停和新对话续接，不收录多人协作、改动归属处理或 worktree 隔离与续接。常见流程中断、环境故障和证据恢复都在范围内；处理目标或恢复位置不同才拆页，具体错误码留在对应页内。

完整清单以集中提示词库全部入口为覆盖底线，分别归入 `Godot 项目开发` 和 `Yaya 框架维护`。每篇场景对应一条同名专用提示词，每条提示词只处理这一篇场景；缺少专用入口时补齐对应提示词，不用通用路由正文代替。共同的方法和工具可按[职责设计准则](../../review/baselines/skill-script-prompt-design.md)复用。

素材范围包含准备要求、接收与检查，以及既有的接入和体验验证；实际美术、音乐、音效制作列为待扩展，不写成当前已具备的生产流程。

两本手册不互相引用。场景页就地提供必要输入、动作、参数和结果解释，不依赖另一册补齐关键步骤。相同工具可以被不同场景使用，同一场景的完整处理正文只维护一份。来源链接可以直接指向权威规范、实际工具或集中提示词库。

## 目录与单篇范围

采用 `quick-reference/<Project>/<分类>/<提示词名称>.md`，各层保留 JSON 中的准确名称：

- **Project 文件夹**：区分项目开发与框架维护。
- **分类子文件夹**：按要处理的事情组织，不额外增加状态目录或英文路径别名。
- **场景文件**：使用提示词名称，将影响处理方式的状态写进名称；正文一级标题等于文件名去掉 `.md` 后的名称。
- **README 与索引**：放在 Project 目录外，只提供编写约定、选择提示与链接；操作正文放在叶子页。

一篇场景应有明确入口、一个处理目标和一个可验证出口。多个步骤可以共同完成一个目标；出现不同入口、不同任务归属或两套完整处理路径时，应拆页。不要按单个命令碎片化拆分。

新页先检查已有场景。同义场景及其提示词合并，保留最容易识别的标题；导航链接可以从多个位置指向同一页，但不能配置多条提示词对应这一页。任务结束条件与 Feature 的正式完成条件分别说明，不把准备、规划、接入或恢复完成写成 Feature 已交付。

## 标题与措辞

标题先写出会改变处理路线的状态，再说明遇到的事情，例如“Feature 交付前发现 Bug”“Feature 交付后发现 Bug”。具体的测试、试玩等情境放进触发场景。标题要在目录里独立可懂，不能只写“Bug 修复”“验证恢复”。

保留 Feature、Product 等项目中的准确名称，必要术语就地短释。区分“代码写完”“测试通过”“待人工验收”“完成交付”；不把口语化变成状态模糊。路径和示例 ID 必须说明所属项目与替换位置。

同类场景采用相同的入口判定依据和例外分类。依赖“是否正式交付”分流时，写清需要核对的完成状态和记录；不靠标题、测试结果或一次提交推定。不同任务归属确实需要不同步骤时，保留该差异。

### 术语约定

术语及统一写法集中维护在[框架与 Godot 项目术语](../terminology.md)，按名词、动作和影响判断的状态用语查阅。本 README 不再保留另一份词表；具体场景仍可在首次出现时就地短释必要术语。

### 排版与层级

通用写法遵循[使用说明的可读性](../../../project-source/Project_AGENTS.md#使用说明的可读性)，在场景页中按实际阅读需要使用：

- **输入与条件**：多项材料、前置条件或例外情况分别列出；同类短语可以放在同一项中。
- **角色与对象**：多个角色的职责、多个资源的影响分项展示；需要按相同维度对照时保留表格。
- **步骤说明**：保留 `S1｜动作名称` 编号，在步骤内分开说明可独立阅读的动作和约束；有先后依赖的动作仍写清顺序。
- **必要层级**：通常一层列表，明确的“类别 → 事项”才使用两层；不为每个词建子项，不为了整齐把所有段落改成列表。

## 11 类信息如何使用

保留以下分类名称、边界和顺序，只展示有内容的栏目；空项省略，不写“无”或“不适用”。未知但会影响执行的信息写明缺口，不当作空项隐藏。正文标题不带固定栏目编号，避免省略后留下编号缺口。

| 分类 | 本栏只负责 |
| --- | --- |
| 触发场景与使用时机 | 什么事件使读者考虑这一页 |
| 前置条件与适用范围 | 当前能否开始，适用与不适用的范围 |
| 参与角色与职责边界 | 谁提供输入、决定、执行和验证 |
| 流程概览 | 从入口到本页出口的阶段路径 |
| 执行步骤 | 具体动作、执行者及操作对象 |
| 步骤产出与状态变化 | 用可核实的结果说明何时可以离开当前步骤 |
| 资源与文件影响 | 按对象汇总读取、新增、修改和删除影响 |
| 条件分支与路径规则 | 必要的正常路径规则；不能在此塞入另一套完整流程 |
| 阻塞、异常与范围变化 | 无法继续的原因、应保留的内容，以及恢复位置或转入的流程 |
| 完成状态与验证标准 | 如何客观证明本页目标已经达到 |
| 流程关联与衔接关系 | 相关场景及规范依据，不重复选择规则 |

场景应尽量保持单一正常路径。没有分支就省略该栏；若需要在两套处理方法间选择，先收窄入口或拆成不同场景。正常等待用户体验属于当前步骤的待完成状态，不伪装成异常。

执行步骤采用 `S1｜动作名称` 这一套编号，标题与说明分段，不再叠加 Markdown 的数字序号；产出表按同一 S 编号对应。编号只帮助阅读，不新增 Stage 或项目状态。

各部分应提供不同层次的信息：

- **流程概览**：只写经历的阶段；短场景没有额外导航价值时可以省略。
- **执行步骤**：展开具体动作；较长说明按语义分段或列项，不按固定字数断行。
- **产出表**：只写当前步骤的继续条件。
- **完成标准**：只判断整篇场景的出口。

避免把同一段话复制到多个栏目。

## 写到什么程度

使用者应能从本页确认第一步、提供哪些材料、由谁操作、会改什么以及何时结束。Agent 的内部判断保留必要依据，不写成逐动作监督脚本。

执行步骤开头写清集中提示词库中的完整位置、输入字段，以及实际负责的 Agent 和 Skill。已有对话不必重新发送提示词，直接补齐本场景所需材料。生成项目采用自己的 `.agents/skills/<名称>/SKILL.md`；源码链接只供核对。

每个 S 步骤写明执行者、实际操作对象及所用入口。一个 Skill 贯穿全篇时先统一说明，只有切换方法或角色时再就近标明；例如独立 Bug 先由 `engineering-change-plan` 规划，再由 `feature-execute` 实施。工具调用写出实际脚本与必要参数，不能只说“运行相关检查”。

区分当前执行 Agent 与已有命名角色。未配置专用 Agent 或专用 Skill 时直接说明使用当前 Agent 和已有适用方法，不编造“Bug Agent”“原型 Skill”等名称，不把 Skill 切换写成自动委派。独立评审只按实际授权启用。

可执行命令前写明工作目录、必要准备、替换参数及覆盖等副作用。步骤涉及既有工具时核对当前实际入口；解释工具结果的具体含义，不能把退出码为零泛称为整个任务完成。

项目路径相对生成后的游戏项目根目录，来源链接指向框架材料仅供核对，执行时采用项目自己的副本。保留用户已明确的授权及限制，不因拆页重新索取同一确认；页面出口也不终止仍需继续的已授权工作。

提示词正文统一在 [framework/prompts.json](../../prompts.json)。页面只写准确入口名称、用途、所需输入及必要的约束提醒，不复制提示词或详细的 Git 提交覆盖规则。适用时写“遵循该入口当前有效的提交约束”，具体规则由对应入口维护。

资源表按实际项目对象列读写影响；保护原验收条件、完成历史等核心约束，应在对应对象行明确。场景页只提供执行信息，待迁移范围和编写进度放在场景索引或现有维护待办中。

## 写完如何核对

- 从标题、前提、步骤到出口检查是否始终围绕同一目标；用户不应在页内重新选择另一套处理流程。
- 按 JSON 名称直接核对 Project、分类和场景文件路径；提示词名称、文件名与一级标题一致。路径校验与正文职责审核分别进行，不为匹配增加元数据或另一份手工登记。
- 核对实际规则、文件和工具；文章解释现有行为，不新增流程、状态、验收门槛或自动同步。
- 检查步骤和产出编号、内部链接与来源锚点；只为已有完整正文提供链接；未扩展能力留在范围说明，不创建空壳页面。
- 检查两本手册没有交叉引用，读者必需的动作没有藏在另一册。
- 修改 Markdown 后执行[阅读版构建](../../README.md#构建-html-阅读版)，由脚本检查收录范围、链接、锚点与生成结果；仅重建 HTML 不要求重复人工复审正文。实际阅读体验由用户反馈，构建通过不替代体验结论。

阅读检查关注：能否找到自己的情况，能否明确开始与结束，步骤和产出是否便于对照，以及是否仍有应拆分的正文。调整入口时同步 JSON、同名路径、索引和受影响引用，不建立新的流程台账。

路径核对在框架根目录使用已确认的框架 Python 运行 `framework/commands/check_scenario_prompt_paths.py`。该命令只读取 JSON 名称和目录文件名，不读取正文或维护映射缓存；正文 H1、专用输入、步骤和出口仍须内容审核。
