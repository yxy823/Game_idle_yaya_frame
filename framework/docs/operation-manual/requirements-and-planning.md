# 需求、Feature 与规划基线

[操作手册](README.md)

需求说明预期结果，计划分配实现与验证责任。外部 GDD、当前代码、讨论提案、Product 和 Feature 各自提供不同事实，不能因为文件较新或实现已存在就自动采用其中的要求。

## Product 和专业来源

- **总体说明：** `docs/product.md` 保存游戏目标、当前版本范围、模块列表、依赖与实际推进顺序。
- **模块说明：** `docs/product/NN-name.md` 保存模块的输入、状态、行为、反馈和边界。

具有独立数据模型和交互入口的行为才有理由成为独立模块，新名词本身不要求新模块。

模块编号是稳定身份，不是排序号。新增模块使用下一个可用编号，成为前置时调整总览依赖和 intended order，不重命名旧模块。删除或废弃保留真实历史与替代关系，不能为看起来连续而重排引用。

- **行为要求：** Product 拥有玩家可观察行为。
- **专业要求：** 美术、声音、UI、本地化及资源交付要求由对应专业文档维护；共享要求沿适用范围和实际依赖影响任务，未直接链接不代表不适用。
- **共享定义：** 由 `project-terminology` 保存，行为变化仍归 Product 或专业来源。已确认的新定义和待定提案分开。

外部 GDD 是输入材料，必要时保留明确标为快照的参考副本，不成为与 Product 双向同步的第二套正文。不可读材料、遗漏图片、矛盾和未采用方案保持可见。接管已有实现时，代码证明当前行为，不能证明用户曾批准它。

## Feature 的职责与身份

| 记录 | 含义 |
| --- | --- |
| 索引 | `docs/feature-list.json` 保存轻量身份、依赖、状态、详情路径 |
| 详情 | `docs/features/F0XX.json` 保存范围、来源、可观察 AC、组件及验证义务 |
| AC | 一个可客观判断的预期结果；ID 在演进中保持稳定 |
| 组件 | 可复用的真实影响范围，用于连接实现与相关测试；不是每个文件一个组件 |
| 验证方式 | `manual` 或 `automated` 根据要求选择；规划时未决定可为 `null`，空人工列表不能倒推 automated |
| notes / 可选设计 | 过程决定与解释；不能成为 AC、测试义务或专业要求的唯一正文 |

测试 ID 可为 `F012-AC01`、`F052-RT01` 或项目实际不变量 ID；这些例子不表示已有测试。

- **登记状态：** 记录有 `planned`、`active`、`retired` 生命周期。尚未创建的测试可先 planned，真实文件和 case 就绪后激活。
- **组件路径：** 没有套件的组件 `unit_test_paths: []` 合法，填一个不存在的路径不合法。

## 当前模块的覆盖与依赖

Feature 按当前模块的完整必要行为拆分，优先得到能独立理解、验证的小到中等任务。先完成当前 Product，再规划下一个；全局材料充分不意味着要预先拆完未来版本。已有有效计划直接复用。

依赖表达真实前置，不按编号串联全部任务。只有依赖已完成的 pending 项才是 eligible；没有 eligible 候选也可能是依赖阻塞，不能推出模块已经交付。

规划预览说明：

- 任务数量；若与先前预期数量不同，应解释变化。
- 各项名称与范围、可观察完成结果。
- 依赖理由及覆盖缺口。

普通规划需要具体方案确认；用户已明确授权自主拆分则展示后继续。Goal 名称或持续执行模式本身不授予规划权限。

语义覆盖需要能追到“来源要求 → Feature/AC → 自动测试或人工检查 → 未覆盖项”。格式检查成功只证明结构满足工具契约，不证明没有漏掉需求，也不证明功能已经实现。

## 基线与需求修订

首次 `R000` 记录当前确实采用、已提交且被计划吸收的来源。创建器的初始空文件提交不是需求基线。后续模块规划不重置已有锚点；`synced_at_commit` 记录真实分析的源版本，不是随手填最新 HEAD。

已确认要求变更时，来源归所属入口；规划由 `feature-sync` 处理现有影响。来源链接也属于输入：

- **需要修正来源时：** 先保存并提交有效来源，再依据实际 HEAD 分析。
- **只修 Feature 的计划引用时：** 不要求额外来源提交。

相关来源必须能独立保存，仓库有无关差异不是通用阻塞。

新专业来源可能早于旧锚点存在，旧提交时间不能证明其曾纳入计划。缺少可证实基线时只能说明历史未知，在授权内对齐当前来源及已规划范围，不把空 diff 写成完全同步。

| 受影响对象 | 演进原则 |
| --- | --- |
| 当前或待做 Feature | 修订范围、AC、依赖与验证；拆分/合并时保留替代关系和引用 |
| 已完成 Feature | 保留原验收事实，新的行为要求由后续任务承担；不改旧 AC 掩盖变化 |
| 不再有效的任务 | 使用既有 obsolete / obsolete_done 语义，保留完成或废弃历史 |
| 旧测试 | 保留仍有效保护；退役登记与删除测试代码是不同动作，清理范围交给负责实现的任务 |
| 只需复跑的有效下游测试 | 纳入负责修改的任务，不额外创建纯复跑 Feature |
| 未规划的后续 Product | 保存有效来源，轮到它时再拆分 |

登记为 retired 的旧方法若仍在被选中的套件中，仍可能执行；删除或替换需同时检查调用、文件、Registry 与历史引用，不能抹去失败原件。

## 已有实现与教学示例

功能先写出来再补记录时，采用已确认的真实意图，复用符合要求的实现和测试。文档补齐不等于交付，不能补造过去的 RED、批准、测试或完成时间；正式完成使用本次实际满足条件的时间。新测试立即通过可证明当前已有行为，不证明过去采用过 TDD。

例如“初始资源为 0，每次点击增加 1”的教学候选，可对应一个收集模块、含初始值和连续点击结果的两条 AC，再关联真实测试。它只说明对象如何连接，不为任何项目自动批准数值、文件名、Feature ID、存档范围或测试结果。
