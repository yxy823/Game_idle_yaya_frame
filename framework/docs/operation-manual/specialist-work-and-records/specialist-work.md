# 专业来源与资源

[操作手册](../README.md)

专业设计描述要求，资源准备提供真实文件，接入建立运行关系，验证和审核取得不同性质的证据。一个任务只使用所需能力；存在 Art Bible 或 Sound Bible 的占位文件，不要求先设计整款游戏的美术和声音。

[表现层](../foundations/game-logic-and-presentation.md)涵盖界面、反馈和它们的实际运行职责；本页的 UI、游戏表现及共享方向文档，分别细化其中不同问题。游戏逻辑与表现共同来源于 GDD，专业文档不会替代业务规则的正文。

专业工作按 [GDD 前提](../../../../project-source/methodology/01-product-doc-structure.md#gdd-prerequisite-and-authority)判断实际依赖：设计讨论、数值草模和 GDD 草稿审核可以协助形成设计，接入、测量或实现前须有支撑本次行为的真实规则。不要求预先写完全部 GDD 或专业细节，也不把缺失的规则当成已经确定。

## 来源的唯一维护者

| 内容 | 项目位置 | 维护 Skill |
| --- | --- | --- |
| 整体游戏设计、玩家行为与反馈意图 | `docs/gdd/` | `design-gdd` 创建、整合与维护 |
| 数值模型、公式、参数、曲线及计算说明 | 单系统：`docs/gdd/balance/<system-key>.md`；跨系统：`docs/gdd/balance/cross-system.md` | `design-balance` 在授权内直接维护 |
| 交付预拆分与当前 Product 范围 | `docs/product.md`、`docs/product/` | `product-author` |
| 已确认项目术语的定义与别名 | 固定为 `docs/terminology.md`；GDD 与专业来源引用 | `project-terminology` |
| 共享视觉方向 | `docs/art/art-bible.md` | `design-art-direction` |
| 共享声音方向 | `docs/audio/sound-bible.md` | `design-audio-direction` |
| 界面布局、状态及其表现引用 | `docs/ui/<interface>-design.md`；共用控件行为在 `docs/ui/components/<component-key>-design.md` | `design-ui-spec` |
| 一次游戏表现的过程、组件要求、候选与采用组合 | `docs/presentation/<scope>.md`；跨表现共享组件按下文固定存放 | `design-game-presentation`；实现任务同步实际文件和接入关系 |
| 具体视觉资源准备要求 | 所属表现/UI/组件的资源章节；跨独立所有者的共用资源固定在 `docs/art/art-bible.md` 的“共享资源规格” | `design-visual-asset-spec` |
| 具体音频资源准备要求 | 所属表现/UI/组件的资源章节；跨独立所有者的共用资源固定在 `docs/audio/sound-bible.md` 的“共享资源规格” | `design-audio-asset-spec` |
| 语言覆盖、术语译名、回退、排版与翻译惯例 | `docs/localization/localization-spec.md` | `design-localization-spec` |
| 已定要求的实际资源接入 | 当前 Feature/实验的资源、引用与配置 | `content-asset-integration` |
| 已定本地化要求的运行实现 | 翻译资源、字体、界面适配与语言逻辑 | `content-localization` |

GDD 记录玩家应获得的感受和需要辨识的对象；画风、色板、质感等视觉标准归 Art Bible，音色、节奏与声音特征归 Sound Bible。例如“安静且奖励可辨识”是体验目标，“低饱和手绘”是美术标准，两者通过引用关联。

专业文档把 GDD 的设计意图细化为可使用、可验证的规格，正文固定由上述所属文件维护；GDD 保留整体目标、玩法规则与引用。获准编写或整合 GDD 时，本次已确定的专业规格一并归位，原先写在 GDD 的当前规格迁入所属位置，不按首次写入位置或游戏复杂程度决定归属。Product 选择交付范围并保存必要引用。专业 Skill 直接维护自己的正文；数值主题同样不要求 `design-gdd` 代为保存。专业工作若需要改变整体玩法规则或已确认体验目标，则由 `design-gdd` 协调该设计决定，交付范围变化再由 `product-author` 处理。维护职责不授权自行采用未决要求；本地化翻译用词也不能改玩法语义。

数值设计从目标体验、单位、边界、规则与已知数据出发，交付可复算的公式、参数及典型和关键边界情景。候选值、已采用值与实际验证状态分别标明；普通规格中的数字不自动成为数值建模任务。计算成立不证明游戏已经平衡或有趣，数值写入也不授权修改运行资源或代码。独立数值审核继续由 `review-balance` 承担。

本地化规范的“术语译名”章节是目标语言用词的唯一规格，条目引用项目术语定义并说明语言、已采纳译名与适用语境。`design-localization-spec` 维护这份表，`content-localization` 在运行译文中使用，`review-localization` 据此检查一致性；完整句子与对话仍在运行资源中，不在 Markdown 维护第二份。概念定义和开发查找别名继续归 `docs/terminology.md`，具体边界见[本地化术语译名](../../../../project-source/methodology/11-specialist-workflows.md#localization-term-translations)。

## 来源如何约束任务

Feature 有一个主 `source`，可观察的要求及来源写入 AC，实施约束及来源写入同编号设计文件。共享来源的适用范围、实际依赖与引用共同确定消费者；“符合 GDD”或“符合 Art Bible”不是充分的 AC，应描述本任务的实际状态、尺度和可观察结果。

要求变化由所属入口修改来源，并分析已规划任务；实现违反已确认专业要求可以作为 Bug 依据，不要求再抄一份 Product。未经采用的设计建议不是缺陷。旧同步锚点也不自动证明新纳入来源曾被吸收，历史未知与当前对齐分开说明。

GDD、规格、表现正文及本地化要求在最终验证前完成本轮必要更新，包括采用组合、实际实现与消费位置、资源准备状态。这些文件按当前全局指纹契约参与内容绑定，准备状态或文字变化也可能使旧结果失效；GDD 目录中的 README 同样参与。约束正文不能只藏在豁免指纹的普通 README、notes、知识或报告中。

## 用一次游戏表现连接设计与实现

例如，设计领取后的物品入包反馈时，界面文档说明领取按钮在哪里、什么状态可以点击；`item-added.md` 说明入包确认后图标如何飞行、数字如何变化、目标位置如何反馈。先从体验目标或口语描述形成可观察过程，再选择已有实现、序列帧、Shader、粒子、Tween 或 AnimationPlayer。Shader 与粒子参考帮助整理标准需求，具体算法、节点和代码由实施任务决定。

能否领取、发放数量和重复领取规则由游戏逻辑决定；表现使用有效结果，不能在图标到达时再次发放奖励。普通控件的悬停、焦点或展开状态可以在 UI 文档中说明，不必为表现层的每一处行为单独建立游戏表现文档。

| 场景 | 从哪里找到什么 |
| --- | --- |
| 背包物品入包 | 从 UI 的实际交互位置或末尾“关联游戏表现”导航，找到表现正文、采用方案、实现和验收入口 |
| 奖励领取的组成部分有多个方案 | 图标飞行 A/B、目标反馈 A/B 分别说明；当前采用“图标飞行 B＋目标反馈 A”，引用各部分，不重复整套组合正文 |
| 多个界面共用奖励反馈 | 共用一份表现正文，各界面保留自己的触发、采用组合和消费位置 |
| 角色死亡 | 从相关 GDD 章节及表现总览找到正文，无需为此创建 UI 文档 |
| 替换一个组成部分的技术 | 当前任务保留已确认要求，同步采用组合及真实路径，再完成适用验证；目标改变按设计变更处理 |

表现以触发时刻和玩家感知结果确定范围：商店购买与奖励领取若都是同一种物品入包反馈，共用 `docs/presentation/item-added.md`，各自说明来源上下文。奖励揭晓等独立过程另写一份，结尾发生物品入包时引用已有正文。不会只因消费界面不同就拆出两份表现。

表现正文按需要组织目标与过程、组件标准需求、候选方案、资源规格、采用关系、实际实现和验收入口。组件仅属于一份表现时在父文档内分节；第二份独立表现使用相同组件要求时，将共同要求、候选及其资源规格迁入固定的 `docs/presentation/components/<component-key>.md`，原正文改为引用。多个界面引用同一份表现不会触发这次迁移。建立后的共享组件仍有消费者时保留原路径，各父表现只维护自己的过程、触发与目标上下文、采用组合和验收入口。具体身份与生命周期见[表现文档约定](../../../../project-source/methodology/11-specialist-workflows.md#game-presentation-documents)。

UI 按[界面文档边界](../../../../project-source/methodology/11-specialist-workflows.md#ui-document-boundaries)划分：有独立进入、退出和交互流程的屏幕或弹层单独成文，从属面板、标签页与 HUD 部件留在宿主章节。第二个界面使用同一控件或对话框行为时，共用正文迁入 `docs/ui/components/<component-key>-design.md`，调用处引用；仅共享外观则仍引用 Art Bible。

`docs/presentation/README.md` 导航到表现及共享组件，列出实际使用关系；绑定要求写在各自正文中。UI 界面或组件规格新增、改名或移除，以及导航中的用途、关联 Product 或组件消费者变化时，`design-ui-spec` 同步读取 `docs/ui/README.md` 并维护受影响导航条目，无需审查无关目录内容。

表现与开发任务不要求一一对应，只把已采纳要求和当前获准方案接入现有 Feature 的来源、AC 或设计。候选可以只保留描述，不要求全部制作。有具体不确定性才用 Godot 原型验证；正式实现沿用已有开发任务。

规划完成、实现可用和用户人工接受分别说明。表现文档链接原任务的验收条件、运行入口及既有报告或完成记录，结果仍保存在原记录中。替换方案后旧记录保留其原版本和覆盖范围；不在验收后把结果抄回表现正文，再宣称此前验证仍覆盖修改后的文档。

## 资源规格随所属设计保存

按[资源规格归属](../../../../project-source/methodology/01-product-doc-structure.md#resource-requirements-and-handoff)确定位置：表现方案专用资源随方案，界面专用资源随 UI，已抽出的共享组件专用资源随组件。跨这些独立所有者共用的视觉、音频资源，分别固定在 `docs/art/art-bible.md`、`docs/audio/sound-bible.md` 的“共享资源规格”章节。用途扩展导致归属改变时，一并迁移规格和准备状态，消费处改为引用同一正文。没有独立资源清单的默认目录，也不按 Feature 或收件批次另建台账。

资源条目按实际需要说明用途、文件名、格式、相关尺寸或时长、透明/循环等约束、准备状态、源与目标位置和真实文件关系。视觉资源区分源像素、显示尺寸和透明留白后的主体尺度；音频不填无意义的像素字段。需要资源 ID 时只在所属文档或章节内保持稳定，跨文档引用带路径与章节。候选值、已确认要求和实测信息分开写，来源与许可不明时保留缺口。

比如“命中时出现短暂火花”，即使最终纹理未到位，也能先说明运动、数量感觉、持续时间和触发方式；如果选用的粒子方案需要纹理，再把规格和准备状态写在该方案中。缺文件只影响依赖它的实现或体验判断，规划可以继续。

框架当前覆盖准备要求、接收和检查素材；图片、音乐、音效制作与本地资源库检索不纳入这项能力。外部准备交付真实文件后，接收任务更新同一所属章节，获准接入任务再检查实际使用。参考图、占位文件名或规格文档不是成品；规格请求本身也不授权制作、购买或导入资源。

## 视觉原型与实际接入

UI 规格描述信息层级、ASCII 布局、状态差异、显示条件和待验证问题；节点、路径和参数属于实现。新界面或明显布局变化需要能单独运行的 Godot 原型作为视觉判断材料，已有且适用的有效基础可复用。

- **原型范围：** 位于已授权 Feature 或限定实验，可用本地样例状态、Hover、焦点等必要交互；不默认接入正式存档和业务规则。
- **判断条件：** 真实素材、目标窗口、缩放、空/密集状态、裁切与可读性共同影响结论，图片原始像素不足以证明主体尺寸合适。
- **接受与采用：** 原型接受只覆盖原型范围，正式业务仍有独立验证义务；采用后处理样例状态与失去用途的副本，不长期维护两套竞争界面。

原型与正式逻辑的先后取决于本次问题：验证商品排列可以先用样例余额，正式购买接入则要核对实际请求、状态和结果。替换动画技术时保留已确认规则和表现目标；动画需要参与命中或流程时机时，由实现明确时序与有效结果判定，不能把表现完成无条件当作业务成功。

素材接入时：

- 对照实际文件、规格、源记录和消费者，检查导入设置、路径/UID、场景/主题/代码绑定。
- 声音的触发、停止、循环接缝、重复叠加和相对音量要在真实场景下试听；文件存在或播放器启动不能证明听觉效果可接受。
- 保存外部原件和无关资产，不盲目重导整个库。

占位资源采用 `_placeholder_` 前缀并在原任务说明用途、替换及验收缺口。源资源、导入结果、工作台预览与正式游戏分别有验证边界；示例通过不能替代游戏 Feature 完成。

## 测量与实现

具体异常统一由 [bug-diagnosis-godot](../../../../project-source/skills/bug-diagnosis-godot/SKILL.md) 按[因果诊断](../../../../project-source/methodology/07-engineering-change.md#causal-diagnosis)处理，先看症状、预期和证据，再选择所需的专业方法。用户不必先判断它属于逻辑、表现还是两者的连接。

例如，已确认“角色受击后闪红”，实际生命值正确减少却没有闪红。扣血正确只说明这部分状态变化符合预期；Agent 仍需检查受击结果是否到达反馈控制、播放是否被打断，以及材质和参数是否接到了正确对象。证据指向 Shader 数据流时，才按需使用[Shader 诊断参考](../../../../project-source/skills/bug-diagnosis-godot/references/shader-diagnostics.md)中的临时可视化或固定条件比较。不能仅因画面异常就认定 Shader 有错，也不需要预先拆成“逻辑 Bug”和“表现 Bug”。

修复仍由原任务承接。涉及算法选择时可直接查阅[Shader 实现方法](../../../../project-source/skills/implementation-guidance-godot/references/shader-implementation-methods.md)，同时遵守[Shader 工程规则](../../../../project-source/agent-rules/30-shaders/README.md)；读取参考不启动新的指导任务或增加写入授权。表现要求、采用方案或文档记录的实际文件与接入关系发生变化时，同步所属设计；诊断与验证结果沿用原任务的证据位置。

- `diagnostics-instrumentation` 提供有目的、单位和成本边界的日志、计数或时序信号。
- `diagnostics-performance` 获取可重复负载下的测量和瓶颈依据。
- `diagnostics-soak-test` 获取明确时长与停止条件下的趋势和失败。

只有静态猜测时不能写成已定位瓶颈。

- **授权与副作用：** 仅测量与诊断不自动授权持久优化，日志、缓存和报告仍有副作用。接入、本地化、埋点和优化的持久修改由原 Feature、限定实验或获准工程任务承接。
- **版本与测量条件：** 临时埋点版本与最终交付版本分开，可比性要包含设备、引擎版本、场景、负载、参数和测量条件；计划六小时只实际运行四十分钟仍有缺口。

专项结果不能包装为 gdUnit 成功；完成工具也不负责判断性能、长测或感官证据充分性。修复后相应真实检查仍适用。

## 独立审核

`review-code`、`review-ux`、`review-art`、`review-audio`、`review-assets`、`review-localization` 和 `review-balance` 分别核对自己的对象。同一个新上下文可以使用多个适用方法，不要求每项 Skill 各审一轮，也没有默认每个 Feature 都独立审核的要求。

- **审核输入：** 包括明确范围、权威来源、实际版本/差异、原始证据与允许运行范围。
- **快照范围：** 应包含相关未提交内容，只复制 HEAD 可能漏掉本次成果。
- **独立性：** 作者解释是待核实陈述；作者自查不能称为独立审核，角色配置存在也不证明独立性或隔离成立。

被审成果、原验收记录和原证据只读。获准的针对性验证使用安全副本或指定外部验证环境，将日志、缓存、导入和测试数据一起隔离；只改报告目录不够，使用 worktree 也不能代替对实际副作用的核对。条件不足时保留未验证项，未实际看到或听到时不宣称视觉/音频体验通过。

实现现状审核无需 Feature 或虚构差异基线，按相关 GDD 判断符合性。GDD 草稿或完整设计本身可使用 `plan-review-godot` 审核，不以 Product/Feature 已建立或所有规则已确定为前提。某项具体要求缺失时，限定符合性结论，在其余有依据的范围内检查质量。报告说明检查版本、实际覆盖、问题、依据和限制；过程中成果变化时限定结论或补查对应变化。

报告默认在对话，需留存时在相应 `reports/features/` 或 `reports/maintenance/`。报告已交付、审核条件满足、用户人工接受是三个不同事实。发现的优先级不授予修复权限；确认的完成阻断项也不能因为审核可选而忽略。

权威边界见 [专业职责规范](../../../../project-source/methodology/11-specialist-workflows.md) 和 [独立审核规范](../../../../project-source/methodology/12-independent-review.md)。
