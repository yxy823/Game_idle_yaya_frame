# 任务类型、开发阶段与完成语义

[操作手册](../README.md)

项目采用一位使用者与 Agent 的单目录开发方式。任务、阶段、Git 提交与实际验收分别表达不同事实；阶段号帮助定位工作，不构成额外自动状态机或逐阶段审批。

以下开发、调查、审核和实验均以项目内已有真实 GDD 为前提；缺少时说明缺口并停止。GDD 的内容与维护边界见 [需求与交付规划](requirements-and-planning.md#gdd-是项目开发的前提)。

## 任务边界

| 类型 | 对象与完成含义 |
| --- | --- |
| 普通 Feature | 交付已确认的玩家行为与对应 AC |
| Bug | 实现违反仍有效的 GDD、Product 交付要求、专业规格或工具契约；恢复既有预期 |
| 重构 | 保持外部行为，降低有具体依据的维护成本；文件变少或指标降低不单独证明收益 |
| 工程维护 | 工具、依赖、性能、资源或数据的明确技术目标，不借此增加玩法 |
| 限定实验 | 在假设、范围、预算和文件去向内取得证据；观察结果不是自动获准需求 |
| 只读调查或审核 | 提供证据与结论；发现问题不自动获得修复权限 |

正式交付以项目规定的 Feature 完成状态与完成记录为准，不以测试通过、代码提交或用户试玩作为单独判断依据。交付前原任务范围内的缺陷仍由该 Feature 处理；交付后的独立缺陷由新的工程 Bug 承担，原完成历史保持真实。需求尚不明确的疑问与用户改变要求不是“修 Bug”。

Bug 的实际表现、预期及来源、复现和根因应能对应证据；未知解释保持假设。可自动回归的缺陷以目标行为失败和修复后的通过保护，确实不适合自动化时保留原因与可重复人工路径。

## 修改前后的共用要求

Bug 修复、功能实现、重构、工具维护、资源接入、迁移和性能优化都应按实际影响采用以下要求，具体方法仍由所属任务决定：

- **修改前**：读取当前实现与直接消费者，找到行为实际所属位置，简述必要修改和验证范围；有效计划可直接复用，不新增审批关卡。
- **修改时**：完成最小且完整的目标，保持无需变化的 API、依赖与代码风格；必要契约变化同步实际消费者，不顺带改无关代码。
- **交付前**：完成相关测试及项目支持的适用静态检查，检查最终差异；说明关键文件、修改理由、实际验证和有依据的剩余风险。

共用正文见[变更准备与范围](../../../../project-source/agent-rules/00-core/change-scope-and-ownership.md)、[验证政策](../../../../project-source/agent-rules/00-core/validation-policy.md)与[交付说明](../../../../project-source/agent-rules/00-core/completion-and-reporting.md)。这些要求不扩大只读任务的授权，也不替代所属流程的实际人工验收。

## Stage 的含义

| 阶段 | 保存的决定或事实 |
| --- | --- |
| 0 上下文 | 当前目标、来源、规则、已有差异、有效授权及必要环境 |
| 1 方案 | 范围、真实影响、资源、测试策略、验收方式及必要设计决定 |
| 2 保存计划 | 已批准方案进入 Feature、Registry、Progress 与必要设计；状态为 in_progress |
| 3 实现 | 相关 baseline、小行为 RED → GREEN → 必要重构及适用分批提交 |
| 3D 文档检查 | 使本次改变的 GDD、Product、术语、专业规格、资源清单、设计、规则与架构符合实际决定 |
| 4 最终验证 | 当前义务对应的自动、直接静态与专项结果；适用时准备人工清单 |
| 5 人工验收 | 仅 manual 模式，取得用户对当前内容的真实结果 |
| 5.5 Bug 经验 | 仅 engineering_change: bug，保存根因、触发、回归与有用防范原则 |
| 6 独立评审 | 仅用户指定的范围与时机；可集中审多项，不是每项默认关卡 |
| 7 完成记录 | 所有适用条件满足后由 Agent 更新 done、实际完成时间、记录与收尾提交 |
| 8 交接 | 报告实际交付与限制，核对剩余授权；已授权后续工作继续推进 |

具体流程唯一正文在 [执行规范](../../../../project-source/methodology/03-execute-loop.md) 与 [feature-execute](../../../../project-source/skills/feature-execute/SKILL.md)。普通实现细节由 Agent 判断；未变的具体授权跨 Skill 和阶段沿用，原 Skill 返回不等于整项授权结束。

## 自动与人工验收

验收方式从要求出发。画面辨识、声音、动画、操作手感等需要人判断时采用 manual；所有 AC 都能充分自动验证时才可 automated。manual 同样可以有大量自动义务；实现授权、自动通过与用户沉默都不是人工接受。

人工清单与结果按以下职责分工：

- **清单内容：** 项目对应 AC 或必要回归，包含入口、起始状态、操作、可观察结果和重置方法；影响结果的设备、时长、种子才补入。
- **Agent 与工具：** Agent 提供 pending 原清单，工具绑定版本。
- **用户结果：** 用户另存结果填写 passed/failed/pending 与观察，不能改 ID、步骤或预期来消除失败。
- **接受判据：** 有效必需项全通过且无矛盾反馈已表示接受，无需重复索取相同确认。

口头明确结论和结果 JSON 是两种记录方式。原件缺失、版本失效或反馈有歧义时保留缺口，导入成功也可能记录 rejected 或 pending。automated 不生成空清单或伪造接受。契约与工具见 [人工验收文件](../../../../project-source/methodology/manual-acceptance-files.md)、[命令与证据](../方法与工具/commands-and-evidence.md)。

只有有效 manual 计划确无自动测试义务，且不存在未解决的失败或未结束最终运行时，运行器才可能返回 `not_required`。该结果不是放弃测试的开关；直接静态、专项检查与人工要求仍各自适用。

## 验证与证据

修改前 baseline 说明已有安全网；环境、解析或测试发现故障不算目标行为的 RED。一个 AC 可以包含多个小行为循环，不要求先写完所有测试再统一实现。接管旧实现不刻意破坏代码制造历史 RED。

最终验证按真实组件和计划选择 Required、affected 或必要 full，不因“维护”标签一律全量。一个当前且覆盖充分的结果可复用，较新失败不能用较旧或更窄成功掩盖。完成工具不代替解析、lint、性能、长测、实际显示或听觉判断。

纳入全局内容指纹的 GDD、Product、规格、规则或资源清单即使只是文字或状态变化，也可能使当前未完成任务的旧依据失效；后续 GDD 章节也不因尚未开发而豁免。notes 的豁免不传递给被链接的设计文档。纯过程历史整理不等同于业务变化，历史已完成记录不会因此自动重开。较晚的 Bug 经验或规则采纳同样核对实际影响。

## Git、暂停与持续任务

非空 Git 状态不是单人项目的统一阻塞。

- **已有差异：** Agent 查看当前差异，保留与本任务无关的内容及其暂存状态；同一任务续接的改动核实后可以完成并提交。仅对具体覆盖冲突、无法分离的提交或必要来源无法保存说明阻塞；不要求改动归属证明，不自动 stash、恢复、清空或创建 worktree。
- **暂停和切换：** 使用同一目录的 Progress、原任务及真实文件，不新建状态台账，也不为换对话强行提交半成品。

项目默认每完成一项可独立理解、通过相关验证的完整逻辑成果，就创建本地提交，不积攒到复杂任务全部结束。开始时可在已有方案中说明这些成果及依赖，执行中按实际情况调整；简单任务一次提交即可。

- **提交边界：** 每项成果带上必要实现、测试、引用和说明；不按文件数量或“代码、测试、文档”机械拆开。单项 Feature 可以多次提交，中途仍保持 in_progress，不能依赖遗留未提交配套内容才能工作。
- **用户指定条件：** “不提交”、先验收或需明确允许提交等条件按其具体范围优先，并跨 Skill 与续接沿用。如果当前任务同时要求实际验收和明确允许提交，两者都须满足；验收通过本身不等于允许提交，已取得的具体许可也不重复索取。
- **验证与核对：** 提交前审查明确路径和完整暂存差异，复用仍覆盖该提交的有效验证，补足缺失或失效部分。相关检查失败或必要验证未完成时不提交。最终审核覆盖全项提交与剩余差异，不能只看最后一次提交。
- **提交后：** 核对新提交范围和剩余差异；发现问题后修复验证，再新建修正提交，不改写历史。交付汇总本次提交与未提交的本任务工作。提交受权限、身份或钩子等阻止时保留现场并说明，不擅自改配置或绕过检查。

Feature 提交主题为 `<type>(F0XX): <中文行为摘要>`，正文 `Feature:` 用真实标题，`Work item:` 指向详情；非简单变更说明原因、关键取舍和真实验证。没有所属 Feature 的任务不虚构身份。具体命令、暂存保护与禁止操作统一见 [Git 规则](../../../../project-source/agent-rules/00-core/git-worktree-and-commits.md)。

Goal 只是持续工作的承载方式。

- **交接终点：** 现有专用入口可授权逐 Product 推进到首个已准备好人工验收的 Feature；该交接终点不等于 Feature 已 done。
- **原型缺少决定时：** 只暂停依赖部分，不能据此宣称最终验收材料齐备。
- **持续任务的结果：** 失败、预算耗尽或前置受阻不是成功完成；用户结果与继续授权决定后续段落。

独立审核的范围、真实性与修复权限见 [专业来源与资源](../专业工作与记录/specialist-work.md#独立审核)，工程分类见 [工程变更规范](../../../../project-source/methodology/07-engineering-change.md)。
