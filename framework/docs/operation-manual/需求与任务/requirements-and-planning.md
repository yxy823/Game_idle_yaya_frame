# 需求、Feature 与规划基线

[操作手册](../README.md)

GDD 说明游戏设计，Product 组织交付范围，Feature 分配实现与验证责任。当前代码、讨论提案和这些正式文档各自提供不同事实，不能因为文件较新或实现已存在就自动采用其中的要求。

[游戏逻辑与表现](../框架基础/game-logic-and-presentation.md)帮助识别本次要求：哪些规则与状态需要成立，哪些反馈需要让玩家感知，以及双方怎样连接。GDD 同时涵盖两者的设计目标，后续专业文档细化所属要求；两层职责不改变交付预拆分和逐个 Product 细化的顺序。

## GDD 是项目开发的前提

项目内可以使用 `design-gdd` 从想法形成 GDD、整理外部资料或修订已有设计，不需要先准备完整 GDD 或 Product。新 GDD 以 `docs/gdd/README.md` 为固定入口，主题使用[标准文件名与职责](../../../../project-source/methodology/01-product-doc-structure.md#gdd-document-names)中预先确定的名称与多实例命名模式，不按游戏规模、篇幅或复杂程度选择位置；包括 `design-scope-and-boundaries.md`（设计范围与边界）和 `open-questions.md`（开放问题）。实际保存设计时按各文档的建立条件补充正文，不为填满目录预建空文件。相同职责沿用名称；修改已有设计时只整理受影响范围，需要调整路径或引用章节时同步实际使用方。

`docs/gdd/open-questions.md` 是固定的《开放问题》文件，集中当前设计尚未确定的选择与证据缺口。条目链接相关主题，说明影响及需要什么才能解决；GDD 入口直接引用它。后续设计讨论据此继续问题，Product/Feature 规划判断哪些工作受阻，审核判断设计能否支撑下一步，相关调研或实验据此确定要取得的证据。具体读写和解决后处理见[开放问题规范](../../../../project-source/methodology/01-product-doc-structure.md#open-design-questions)。

例如“背包满时，采集应失败还是把资源掉在地上”尚未决定，可以记录为一个开放问题；采集 Product 引用它解释当前交付为何受影响。决定后把规则写入所属 GDD 主题，更新相关使用方引用，再移除开放条目。与当前交付无关的问题可以保留，文件为空也不证明整份设计已完整或已经验证。

开始依赖设计的规划、实现、专业接入或实验前，`docs/gdd/` 必须已有足以支撑当前范围的真实设计。空目录、用途说明和待填模板不满足这个条件；缺失或不可读时说明受阻部分，按已有授权回到设计工作，不能自行编造规则继续实现。概念讨论和草稿审核可以保留明确标记的未知，不要求先完成所有未来设计。

GDD 保存游戏定位、体验目标、核心循环、系统规则、状态与数值、内容进程和版本设计范围。固定子文档 `docs/gdd/design-scope-and-boundaries.md` 保存整体范围、明确排除项和版本边界；局部机制与表现限制留在所属主题，其他文档按需引用。正文标题遵循项目文档语言，中文为《设计范围与边界》。该主题的建立、读取与保存要求见[权威规范](../../../../project-source/methodology/01-product-doc-structure.md#design-scope-and-boundaries)。

例如已确认只做单机，讨论时就据此排除多人同步问题；“本版本不做交易”只约束对应版本，“尚未决定交易玩法”不能当成永久排除。相关 Skill 从 GDD 入口找到适用边界，再读当前主题；Project Rules 提供开发约束和工程原则。已授权的 GDD 写作随决定更新正文，纯讨论保留在对话并说明尚未保存的结论。当前交付及影响它的共同规则仍须足够明确，才能开展依赖这些决定的规划或实现。

`design-gdd` 负责 GDD 整体设计和跨主题一致性；`design-balance` 负责模型、公式、参数、曲线与计算说明，可在具体写入授权内直接维护所属数值主题。若调参需要新增玩法或改变体验目标，先回到整体设计决策。`product-author` 只负责交付预拆分和当前 Product，`product-spec-elicitor` 澄清交付取舍，不代写 GDD。来源变化仍须分析专业规格与既有 Feature 的实际影响。

保存候选值、采纳参数和验证效果是不同事实。获准保存草案可以写入清楚标记的候选，不自动替换已确认设计；已有具体采用与写入授权直接沿用，不为 Skill 切换重复批准。模型可复算不等于玩家体验已验证。

## Product 和专业来源

| 位置 | 保存内容 |
| --- | --- |
| `docs/gdd/` | 游戏设计正文；玩法规则和版本设计范围在这里维护一份 |
| `docs/product.md` | GDD 入口、约定交付范围的预拆分、各单元粗略边界、来源、依赖、建议顺序及影响拆分的未决项 |
| `docs/product/NN-name.md` | 当前交付单元的目标、采用与暂缓范围、来源、前置衔接、交付验收场景和实际缺口 |
| 专业文档 | 从 GDD 细化的美术、声音、UI、一次游戏表现、本地化及资源规格；已由 GDD 定义的细节直接引用 |
| `docs/terminology.md` | 已确认项目术语定义的固定唯一正文；完整行为归 GDD |

Product 是可验收的交付单元，可对应一个系统、某个系统的一部分，或跨系统的完整体验，不必与 GDD 章节一一对应。例如，手动采集闭环可以先交付，同一采集设计中的自动化保留为后续候选。游戏系统清单与 Product 交付清单因此可以不同。

Product 编号是稳定身份，不是排序号。新单元使用下一个可用编号，成为前置时调整总览依赖和建议顺序，不重命名旧文件。删除或废弃保留真实历史与替代关系，不能为看起来连续而重排引用。

未决交付选择按[交付决定归属](../../../../project-source/methodology/01-product-doc-structure.md#delivery-decision-ownership)保存一份正文：涉及多个已识别 Product 的分工、前置或顺序，以及尚未细化候选的局部选择，写在总览的“待解决规划决定”；仅涉及一个已有详细文档的 Product，写在该文档的“开放决定”。细化候选时，将它的局部问题正文迁入详情，总览改为引用；游戏规则仍未确定的问题引用 GDD 的开放问题。

各来源只维护自身正文。Product 不复制核心循环、系统清单或版本内容；专业规格补足具体交付要求，专业工作中改变整体设计时仍写回 GDD。共享要求沿适用范围和实际依赖影响任务，未直接链接不代表不适用。不可读材料、遗漏图片、矛盾和未采用方案保持可见；代码只能证明当前行为，不能证明用户曾批准它。

## Feature 的职责与身份

| 记录 | 含义 |
| --- | --- |
| 索引 | `docs/feature-list.json` 保存轻量身份、依赖、状态、详情路径 |
| 详情 | `docs/features/F0XX.json` 保存范围、来源、可观察 AC、组件及验证义务 |
| AC | 一个可客观判断的预期结果；ID 在演进中保持稳定 |
| 组件 | 可复用的真实影响范围，用于连接实现与相关测试；不是每个文件一个组件 |
| 验证方式 | `manual` 或 `automated` 根据要求选择；规划时未决定可为 `null`，空人工列表不能倒推 automated |
| notes | 任务提醒、事件教训、TODO 与正文链接 |
| `F0XX-design.md` | 实施设计、局部决定与理由的固定正文；不代替 AC、测试义务或专业要求 |

测试 ID 可为 `F012-AC01`、`F052-RT01` 或项目实际不变量 ID；这些例子不表示已有测试。

- **登记状态：** 记录有 `planned`、`active`、`retired` 生命周期。尚未创建的测试可先 planned，真实文件和 case 就绪后激活。
- **组件路径：** 没有套件的组件 `unit_test_paths: []` 合法，填一个不存在的路径不合法。

## 先预拆分，再逐个细化与交付

先在 `docs/product.md` 预拆分当前约定的交付范围，检查遗漏、边界和依赖；后续 Product 只保留总览条目，不提前创建详细文档、Feature ID、逐项 AC 或测试登记。

当前 Product 轮到时，依据最新 GDD 和前面交付结果编写其文档，然后一次覆盖完整必要范围，生成多个能独立理解、验证的小到中等 Feature。完成这些必要 Feature 后，再复核并细化下一 Product。已有有效计划直接复用，不因为来源充分就提前展开未来任务。

影响当前实现的跨系统问题应先在 GDD 中解决。例如，后续背包设计决定容量满时采集失败还是资源掉落，这项规则需要先明确，但无需因此提前编写完整背包 Product。预拆分随着实际结果调整，不是固定的实施承诺。

依赖表达真实前置，不按编号串联全部任务。只有依赖已完成的 pending 项才是 eligible；没有 eligible 候选也可能是依赖阻塞，不能推出当前 Product 已经交付。

“只涉及逻辑”“只涉及表现”“跨层”说明功能范围，不是新的 Feature 类型或强制拆分规则。例如一个购买 Feature 可以同时覆盖条件判断、扣费与获得反馈，分别给出可观察 AC；也可以按真实可独立交付的结果拆分。不能仅因为跨层，就预先安排两个 Agent 或规定必须先完成全部逻辑。

判断拆分时，要能说清每项工作在什么条件下、经过什么操作或检查、得到什么可观察结果。依赖则说明前项提供了哪项必要能力或决定，不能把“建议先做”直接当成“必须等它完成”。例如，采集界面的独立视觉原型可以使用本地示例状态，正式按钮接入资源变化才需要可用的采集操作；有明确技术结果的 Feature 也不必同时包含界面。

规划预览说明：

- 任务数量；若与先前预期数量不同，应解释变化。
- 各项名称与范围、可观察完成结果。
- 依赖理由及覆盖缺口。

普通规划需要具体方案确认；用户已明确授权自主拆分则展示后继续。Goal 名称或持续执行模式本身不授予规划权限。

语义覆盖需要能追到“来源要求 → Feature/AC → 自动测试或人工检查 → 未覆盖项”。格式检查成功只证明结构满足工具契约，不证明没有漏掉需求，也不证明功能已经实现。

## 基线与需求修订

首次 `R000` 记录当前确实采用、已提交且被计划吸收的 GDD、Product、专业与规则来源。创建器的初始空文件提交不是需求基线。后续 Product 规划不重置已有锚点；`synced_at_commit` 记录真实分析的源版本，不是随手填最新 HEAD。

已确认要求变更时，来源归所属入口；规划由 `feature-sync` 处理现有影响。来源链接也属于输入：

- **需要修正来源时：** 先保存并提交有效来源，再依据实际 HEAD 分析。
- **只修 Feature 的计划引用时：** 不要求额外来源提交。

相关来源必须能独立保存，仓库有无关差异不是通用阻塞。

新增采用的 GDD 或专业来源可能早于旧锚点存在，旧提交时间不能证明其曾纳入计划。缺少可证实基线时只能说明历史未知，在授权内对齐当前来源及已规划范围，不把空 diff 写成完全同步。

| 受影响对象 | 演进原则 |
| --- | --- |
| 当前或待做 Feature | 修订范围、AC、依赖与验证；拆分/合并时保留替代关系和引用 |
| 已完成 Feature | 保留原验收事实，新的行为要求由后续任务承担；不改旧 AC 掩盖变化 |
| 不再有效的任务 | 使用既有 obsolete / obsolete_done 语义，保留完成或废弃历史 |
| `blocked` 的未开始任务 | 按当前来源修订或撤回，并同步替换依赖；记录的前置条件恢复有效后回到 `pending`，再按依赖是否全部完成判断可执行性 |
| 旧测试 | 保留仍有效保护；退役登记与删除测试代码是不同动作，清理范围交给负责实现的任务 |
| 只需复跑的有效下游测试 | 纳入负责修改的任务，不额外创建纯复跑 Feature |
| 未规划的后续 Product | 更新 GDD 和总览预拆分，轮到时再编写其文档并拆 Feature |

登记为 retired 的旧方法若仍在被选中的套件中，仍可能执行；删除或替换需同时检查调用、文件、Registry 与历史引用，不能抹去失败原件。

`blocked` 的具体阻塞及恢复条件保存在已有 notes，不能靠该状态保留无效 ID 或已废弃的前置。正常等待尚未完成的有效依赖仍是 `pending`；已经开始实施的任务保留 `in_progress`，在执行记录中说明阻塞。恢复状态不代表已经开始或完成实施，见[状态转换](../../../../project-source/methodology/02-feature-list-schema.md#status-transitions)。

## 已有实现与教学示例

功能先写出来再补记录时，仍须有真实 GDD，以其已确认设计核对交付范围，并复用符合要求的实现和测试。文档补齐不等于交付，不能补造过去的 RED、批准、测试或完成时间；正式完成使用本次实际满足条件的时间。新测试立即通过可证明当前已有行为，不证明过去采用过 TDD。

例如 GDD 已确认“初始资源为 0，每次点击增加 1”时，Product 可选择交付手动收集闭环，Feature 再用初始值和连续点击结果的 AC 关联真实测试。这个例子只说明对象如何连接，不为任何项目自动批准数值、文件名、Feature ID、存档范围或测试结果。

权威结构见 [Product 规范](../../../../project-source/methodology/01-product-doc-structure.md)、[Feature 规范](../../../../project-source/methodology/02-feature-list-schema.md) 和 [测试策略](../../../../project-source/methodology/08-testing-strategy.md)。
