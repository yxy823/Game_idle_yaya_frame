操作手册

本册解释框架、概念、配置、职责和工具用法。按需要查阅专题，不要求按目录顺序执行；具体场景的处理步骤不在本册重复。两本手册独立阅读，整体选择由框架文档总入口提供。

  • 框架基础
    • 框架、创建器与项目边界：分发、创建器参数、副作用、环境就绪和已有项目的独立性。
    • 游戏逻辑、表现与协作：从商店购买理解职责，再找到设计、实际实现与验收；普通实现由 Agent 按需求选择。
    • 项目对象与目录：GDD、Product、Feature、Registry、证据、代码与报告的职责及读写关系。
    • 配置参考：工具路径、文档语言、Godot、插件、lint 和文本约定。
  • 需求与任务
    • 需求、Feature 与规划基线：GDD 前提、交付预拆分、逐个 Product 细化、AC、依赖、基线与历史演进。
    • 任务类型、开发阶段与完成语义：Bug/重构/维护/实验、Stage、授权、自动/人工验收、Git 和 Goal。
  • 方法与工具
    • Skill、Agent 与提示词：方法职责、角色、集中提示词与 advisor 表达参考。
    • 命令与验证证据：命令参数、测试范围、报告、完成记录、指纹及退出码。
    • 错误与结果的含义：环境、台账、运行和证据输出的解释边界。
  • 专业工作与记录
    • 专业来源与资源：来源所有者、素材准备、原型、接入、测量与独立审核。
    • 资源工作台：查看、试听、分析、A/B、组合、保存与消费工具用法。
    • 知识、设计与记录：术语、设计、架构、ADR、规则、调研、知识、报告与续接信息。
  • 公共参考
    • 框架与 Godot 项目术语：名词、动作和影响判断的状态用语；游戏自身业务词汇仍由项目维护。

项目路径均相对生成后的游戏项目根目录，示例 ID、路径与结果必须换成真实对象。文件存在、工具成功、实际运行与人工接受分别表述，手册不提供已运行的证据。

初次了解游戏功能的组织时，先读项目边界，再用逻辑与表现区分职责，随后按目录找到所属文档和实现。两层描述游戏职责，配置、测试、构建和开发流程作为共同工程支持继续按各自专题查阅，不要求把所有文件分进两个目录。

框架只面向单人 Godot 项目，支持同目录暂停、切换和新对话续接。生成项目独立拥有自身文件；本册、完整提示词库和维护文档不复制给项目，也不建立自动同步。

创建器只预设 docs/gdd/ 目录说明；项目内可由 design-gdd 从想法形成设计，或整合、修订已有资料，数值主题由 design-balance 按授权直接维护。规划和实现依赖的当前范围须有足够明确的真实设计，Product 据此组织交付，不代替 GDD。

行为依据为项目自身的 AGENTS 源、方法总览、Skills 和 工具。本册解释现行契约，不能通过文字重排改写授权、状态或验证要求。

框架、创建器与项目边界

操作手册

框架保存可复制的 Godot 项目材料。创建后的项目独立拥有代码、配置、文档、Git 历史和开发记录；修改框架不会更新已有项目。框架面向一位使用者与 Agent 配合开发，同一项目目录内支持暂停、切换和新对话续接，不提供多人改动归属机制；工作目录与 worktree 的使用按当前任务范围和授权决定。

维护源与生成项目

对象 职责
框架根目录 维护约定、入口说明；不是游戏项目工作目录
framework/ 创建器、复制清单、完整提示词库、手册、回归夹具和审核材料；不复制给项目
.agents/skills/ 框架自用 Skill，包括 Yaya 框架文档写作；不分发给游戏项目
project-source/ 待复制代码、插件、默认文件、Skill、角色与方法；不在这里启动游戏开发流程或 Godot
外部生成项目 用自己的 AGENTS.md、.agents/skills/、methodology/ 和工具开发；不查询框架状态或自动同步

源材料自带最小 main/main.tscn、示例工作台和空业务台账，以及只有用途说明的 docs/gdd/。文件存在不证明环境已就绪、需求已确定、示例已验证或业务已完成。提示词库与手册不随项目复制；advisor 通过固定绝对路径只读使用本机 Godot 开发提示词库，结合项目事实选择场景并起草具体指令。

创建后可以在项目内使用 design-gdd 从想法形成 GDD，也可以整合或修订已有设计。空白项目创建成功不代表设计已明确；依赖设计的规划或实现仍须有 docs/gdd/ 中支撑当前范围的真实规则，Product 据此组织交付预拆分和当前范围。详见 GDD 与交付规划。

项目 AGENTS.md 指向本地 technical-documentation-writing-godot Skill，创建器从项目分发源整包复制入口、元数据和参考。它面向游戏项目文档，与框架自用的 technical-documentation-writing-yaya 分别维护；两者可以独立修改，不跨包引用写作正文。已创建项目拥有自己的副本，后续更新由用户决定。

创建器用法

在框架根目录使用已确认的 Python 3.12+ 调用：

powershell
python -B framework/commands/create_project.py --output D:\Games\MyGodotGame
  • 参数： --output 是目标项目目录；-B 是 Python 的禁止字节码缓存选项。
  • 准备与写入： 创建器需要可用的 Git 和提交身份，按 复制清单 复制、重命名，随后建立独立 Git 仓库和本地初始提交。
  • 执行边界： 它不安装依赖、不运行环境检查或 Godot、不生成需求、不运行测试、不配置远程或推送。
  • 成功消息： 复制数量是清单项数，不是实际文件总数。
条件 契约
目标路径 使用外部绝对路径；完整路径不含中文或空白，不得位于框架内，也不能是框架的祖先
目标内容 只能不存在或为空；已有文件、非空目录和其他 Git 仓库范围不能直接覆盖
复制映射 source 相对框架根，target 相对目标；原文复制，不替换模板变量或机器路径
目录内缓存 目录映射的预检与复制均跳过 __pycache__/、.pytest_cache/ 及 .pyc、.pyo 文件；不读取 .gitignore 决定复制范围，源码、素材、.uid 和 .import 保留
写入前检查 展开所有清单项；目录可以合并，重复目标文件和文件/目录冲突拒绝
失败现场 预检失败不开始复制；复制或 Git 失败可能留下部分内容，不自动删除、回滚、重试覆盖

具体参数与拒绝条件以 创建器源码 为准。项目名称、机器路径和文档语言在独立项目中配置，初始提交不是业务验证证据。

环境就绪的含义

默认配置给出的工具位置是候选值。

  • 检查范围： 普通环境检查只验证配置结构；--require-ready 进一步探测工具与必要路径，仍不表示测试、导入、场景启动或实际体验已经通过。
  • Python： Python 3.12+ 的实际解释器需单独确认，环境检查器不代做 Python 版本探测。
  • Godot： 当前目标为 4.7.x；实际版本来自工具输出。

第一次 Godot 资源与全局类扫描、命令行测试、最小入口启动分别产生不同证据。缺少 GdUnitTestCIRunner 或测试基类时，测试可能尚未执行；不能记作业务断言失败。正常任务复用已有可用环境，不要求每次重做全项目导入。

初始化事实保存在项目 reports/initialization.md，Progress 按需引用。后续更新记录真实增量，不把配置字段或旧成功写成当前已验证；默认忽略的报告也不会因代码提交自动进入 Git。

已有项目采用框架的边界

复制迁移会建立与原项目、框架均独立的目标；原项目和框架保持只读。

  • 当前内容： 包括未提交、未跟踪及必要的忽略文件和删除状态，不能只复制 HEAD。
  • Git 历史： 默认保留当前分支可达的有效 Git 历史并使用独立仓库；不复制远程、hooks、worktree 管理关系或指回原项目的共享链接。若明确选择新历史，旧追踪能力的限制应保留。

原地采用则在指定现有项目中合并当前框架材料。两种方式都区分纯框架文件、业务文件与混合配置：

  • 业务代码、素材、UID、导入设置、许可证、Feature 身份/依赖与真实完成历史保留。
  • 机器路径、主场景及定制配置按实际意图合并。
  • 空白默认台账不是覆盖已有业务记录的依据。

迁移报告可放 reports/maintenance/framework-migration/migration.md，已有文件不可无依据覆盖。历史测试仅证明历史版本；无法恢复的旧决定、基线或原件保留未知，不能补造过去的审批、TDD、验收或完成时间。框架替换和业务功能交付是不同范围，没有持续升级服务。

配置字段见 配置参考，文件职责见 项目对象与目录，结果含义见 命令与验证证据。

游戏逻辑、表现与协作

操作手册

游戏逻辑负责规则、业务状态与有效结果，游戏表现负责玩家怎样看见、听见和感受到这些内容。这个划分帮助理解游戏功能、定位设计和判断实现职责；环境、测试、构建与开发流程是两者共用的工程支持。

阅读一个功能时，可以沿着“游戏目标 → 规则与表现要求 → 所属文档 → 实现与协作 → 验证与验收”查找。本页用商店购买说明这条路径，随项目分发的对应入口是 游戏组织指南。

1. 从一次购买看职责

玩家想购买商品时，界面显示价格并接受操作；游戏逻辑判断余额、库存及背包条件，执行获准的购买并给出结果；表现根据结果更新界面、播放获得物品的反馈。

玩家经历的过程 游戏逻辑负责什么 游戏表现负责什么
打开商店 提供当前余额、商品及可购买条件 展示商品、价格、按钮与当前可操作状态
点击购买 接收请求，检查条件，决定成功或失败 采集操作并提交请求，提供按压反馈
购买成功 扣费、增加物品、更新库存，给出实际结果 刷新显示，播放图标飞入背包、提示与声音
购买失败 给出失败结果及适用原因 显示相应提示，避免播放成功反馈

界面显示“可以买”只是当前判断的展示。真正处理购买时，逻辑仍根据有效状态决定结果；图标到达背包的动画也不能自行再发放一次物品。

表现不必等所有逻辑结束才开始：按钮按下时可以立即缩放，购买成功的反馈则等待有效结果。AI、计时器和其他游戏系统也能触发状态变化，因此玩家输入只是入口之一。

2. 请求、状态与事件分别说明什么

协作内容 购买中的例子 使用目的
行为请求 购买指定商品 表达意图；逻辑判断是否允许及实际结果
当前状态 余额、库存、已持有物品 打开或恢复界面时重建正确显示
一次性事件 本次购买成功，获得了哪些物品 触发与这一次结果有关的动画、提示和声音

请求、状态和事件描述协作含义，具体可以通过已有方法、返回值、API、Godot Signal 或必要的协调者实现。并非每个功能都要建立三种对象，也不要求统一使用全局事件总线。

游戏规则所依据的状态需要明确所有者；表现也有自己的状态。例如玩家真实生命值已经从 100 变成 80，血条仍可以在过渡中显示 90。重新打开界面时应恢复当前生命值，不能把“读到 80”当成又受到一次伤害。悬停、焦点、提示框展开和播放进度通常由表现维护；装备选择是否生效等会改变游戏规则的决定则归逻辑。

动画参与玩法时，按实际需要说明时序输入、打断条件和结果判定责任。例如攻击动画提供命中时刻，逻辑检查攻击是否仍有效并决定伤害。两层职责不禁止这种协作，也不能把“动画播放完了”直接当成无条件成立的游戏结果。

一次反馈怎样展开 游戏表现文档 图标飞行、数字变化、声音的过程、候选方案及当前采用组合
实际由谁维护状态、怎样连接 架构或必要的 Feature 设计 购买操作、余额与背包所有者、界面消费者和运行入口
本次做到什么、怎样判断完成 Feature 与验证记录 规则与反馈的 AC、相关测试、人工检查及真实验收结果

GDD 同时涵盖玩法规则和体验目标，不能简化成“逻辑文档”。“表现层”也大于“一次游戏表现文档”：普通控件状态仍可在 UI 文档中说明，共享视觉与声音要求分别留在原有专业来源。具体正文只保存一份，使用处引用它。

商店 UI 可以从购买成功处链接到奖励表现，并在末尾汇总关联表现；多个界面共用奖励反馈时引用同一正文，保留各自接入关系。角色死亡等非 UI 表现，则从 GDD 和表现总览进入。实际采用、实现文件和消费位置由当前任务同步，结果仍链接已有验收记录，详细职责见 专业来源与资源。

架构文档解释项目当前的真实结构，Feature 设计解释本次改变；两者都不复制游戏规则或另设验收标准。小型项目用现有模块说明和任务记录已经清楚时，无需额外建立架构地图，详见 局部设计与当前架构。

4. 按职责判断，按需要组织实现

逻辑与表现可以同属 game/shop/ 等业务模块，专用脚本、场景与资源相邻放置。节点、场景或文件扩展名不能直接决定职责：碰撞判定可能参与游戏规则，场景也可能同时包含状态处理和视觉节点。可独立计算的规则可以单独组织，需要引擎行为的逻辑保留真实 Godot 协作，不要求所有逻辑脱离引擎。

“编排”要看安排的是什么。推进回合、结算购买归游戏逻辑；安排图标、提示和声音的时序归表现；谁创建双方、连接信号、处理退出和释放，属于实际组装关系。根据具体复杂度在原有结构中说明，不固定增加第三层或某种协调对象。

任务可以用三种涉及范围帮助理解：只换奖励动画主要涉及表现，只改价格计算主要涉及逻辑，新增购买闭环则跨越两者。它们仍使用现有 Feature、实验或工程任务，不形成新的任务类型、Skill 或固定执行顺序。视觉原型可以先使用示例状态；正式接入时，再验证真实购买结果与反馈之间的关系。

Agent 需要守住状态归属、有效结果和文档一致性；普通节点选择、代码划分、通信方式及 Shader、粒子、Tween 等实现手段，由当前需求、已有结构与验证结果决定。示例用于解释判断，不要求所有功能照搬相同文件、类或目录。

验证同样跟随要求：购买规则可检查成功、余额不足和重复操作等实际条件；接入检查真实结果是否正确传给界面，界面恢复时是否显示当前状态；动画、声音与体验按适用人工验收取得真实结果。职责划分不会让静态检查、自动测试或原型观察替代正式验收。

路径与命令的写法

以下是配置片段示例，不是可覆盖整个配置文件的完整配置；其中 Godot 路径必须换成该项目已经确认的值：

json
{
  "python_executable": "C:\\Users\\89523\\anaconda3\\envs\\codex-python\\python.exe",
  "engine_executable": "C:\\Godot\\Godot.exe"
}

JSON 中反斜杠写成 \\。路径字段不额外嵌入引号：带空格的可执行文件路径仍是完整的一个值。不能把 $env:...、& 或 --version 当作可执行文件路径的一部分。

PowerShell 直接调用路径变量时使用调用运算符，并把参数分开传入：

powershell
$projectConfig = Get-Content -LiteralPath 'docs/methodology-config.json' -Raw | ConvertFrom-Json
$projectPython = $projectConfig.python_executable
& $projectPython -B tools/checks/check-project-environment.py --require-ready
$LASTEXITCODE

测试入口默认读取配置中的 Godot 路径，临时更换时可显式传入 --godot-binary <路径>；示例见 命令参考。

  • Godot 路径： engine_executable 必须是实际文件路径，可以是绝对路径，也可以相对项目根目录；环境检查和测试运行器使用同一解析方式，不去 PATH 寻找同名安装。
  • Python 路径： python_executable 支持完整路径、项目相对路径或 PATH 中的命令名。
  • 字段格式： 路径字段不含额外 shell 引号或参数，带空格和非 ASCII 字符的完整工具路径可保留。

项目输出目录禁止中文或空白，与工具路径字段能否包含空格是两个不同约束。不要把创建器的目录限制误套到所有配置字符串上。

检查能力边界

tools/checks/check-project-environment.py 只读取配置。

  • 普通调用： 检查字段与基本语言标签形式，允许 Godot 路径暂时为空。
  • --require-ready： 根据以下实际检查判定就绪，不读写状态字段。
  • --config： 可指定文件，项目根按该配置的上两级目录解析，不能任意把一份临时配置当作另一个项目。
对象 检查器实际做什么 Agent 仍需核对什么
Python 完整路径/项目相对路径，或裸命令的 PATH 解析结果是否为文件 独立执行所选解释器，确认 Python 3.12+ 与所需依赖；检查器不启动 Python 版本探针

文档语言

document_language 控制新写或修改的 GDD、Product、Feature 自然语言、Progress 和项目知识。zh-CN 与 en 是当前规范明确给出示例的语言；其他合规语言标签按现有规范处理，不扩展验证声明。

新项目直接沿用 zh-CN，不询问用户是否接受默认中文。用户明确指定其他语言时，保存对应配置并直接采用，不二次确认；已有项目继续使用现值，聊天语言变化不覆盖它。

环境检查器会检查基本字符和分段形式，拒绝 zh_CN、包含空白、空子段或子段超过八个字符等输入，并保留原值的大小写。它不验证完整 BCP 47 子段顺序或注册信息；特殊标签的合法性由 Agent 按语言规范核对，只有实际要求不清楚或相互冲突时才澄清。

  • 保持不变的标识： JSON 键、Feature ID、pending 等状态、manual 等枚举、文件路径、Skill 名称、命令和测试 ID。
  • 聊天语言： 聊天换语言不会自动翻译项目。
  • 已有文档迁移： 修改已建立的文档语言需要核对活动文档、标题锚点和历史范围；只改一个配置字段不等于完成迁移。

需求、Feature 与规划基线

操作手册

GDD 说明游戏设计，Product 组织交付范围，Feature 分配实现与验证责任。当前代码、讨论提案和这些正式文档各自提供不同事实，不能因为文件较新或实现已存在就自动采用其中的要求。

游戏逻辑与表现帮助识别本次要求：哪些规则与状态需要成立，哪些反馈需要让玩家感知，以及双方怎样连接。GDD 同时涵盖两者的设计目标，后续专业文档细化所属要求；两层职责不改变交付预拆分和逐个 Product 细化的顺序。

GDD 是项目开发的前提

项目内可以使用 design-gdd 从想法形成 GDD、整理外部资料或修订已有设计，不需要先准备完整 GDD 或 Product。新 GDD 以 docs/gdd/README.md 为固定入口，通用主题使用标准文件名与职责中预先确定的名称；包括 design-scope-and-boundaries.md（设计范围与边界）和 open-questions.md（开放问题）。实际保存设计时按各文档的建立条件补充正文，不为填满目录预建空文件。相同职责沿用名称；修改已有设计时只整理受影响范围，需要调整路径或引用章节时同步实际使用方。

docs/gdd/open-questions.md 是固定的《开放问题》文件，集中当前设计尚未确定的选择与证据缺口。条目链接相关主题，说明影响及需要什么才能解决；GDD 入口直接引用它。后续设计讨论据此继续问题，Product/Feature 规划判断哪些工作受阻，审核判断设计能否支撑下一步，相关调研或实验据此确定要取得的证据。具体读写和解决后处理见开放问题规范。

例如“背包满时，采集应失败还是把资源掉在地上”尚未决定，可以记录为一个开放问题；采集 Product 引用它解释当前交付为何受影响。决定后把规则写入所属 GDD 主题，更新相关使用方引用，再移除开放条目。与当前交付无关的问题可以保留，文件为空也不证明整份设计已完整或已经验证。

开始依赖设计的规划、实现、专业接入或实验前，docs/gdd/ 必须已有足以支撑当前范围的真实设计。空目录、用途说明和待填模板不满足这个条件；缺失或不可读时说明受阻部分，按已有授权回到设计工作，不能自行编造规则继续实现。概念讨论和草稿审核可以保留明确标记的未知，不要求先完成所有未来设计。

GDD 保存游戏定位、体验目标、核心循环、系统规则、状态与数值、内容进程和版本设计范围。固定子文档 docs/gdd/design-scope-and-boundaries.md 保存整体范围、明确排除项和版本边界；局部机制与表现限制留在所属主题，其他文档按需引用。正文标题遵循项目文档语言，中文为《设计范围与边界》。该主题的建立、读取与保存要求见权威规范。

例如已确认只做单机，讨论时就据此排除多人同步问题；“本版本不做交易”只约束对应版本，“尚未决定交易玩法”不能当成永久排除。相关 Skill 从 GDD 入口找到适用边界，再读当前主题；Project Rules 提供开发约束和工程原则。已授权的 GDD 写作随决定更新正文，纯讨论保留在对话并说明尚未保存的结论。当前交付及影响它的共同规则仍须足够明确，才能开展依赖这些决定的规划或实现。

design-gdd 负责 GDD 整体设计和跨主题一致性；design-balance 负责模型、公式、参数、曲线与计算说明，可在具体写入授权内直接维护所属数值主题。若调参需要新增玩法或改变体验目标，先回到整体设计决策。product-author 只负责交付预拆分和当前 Product，product-spec-elicitor 澄清交付取舍，不代写 GDD。来源变化仍须分析专业规格与既有 Feature 的实际影响。

保存候选值、采纳参数和验证效果是不同事实。获准保存草案可以写入清楚标记的候选，不自动替换已确认设计；已有具体采用与写入授权直接沿用，不为 Skill 切换重复批准。模型可复算不等于玩家体验已验证。

Product 是可验收的交付单元，可对应一个系统、某个系统的一部分，或跨系统的完整体验，不必与 GDD 章节一一对应。例如，手动采集闭环可以先交付，同一采集设计中的自动化保留为后续候选。游戏系统清单与 Product 交付清单因此可以不同。

Product 编号是稳定身份，不是排序号。新单元使用下一个可用编号，成为前置时调整总览依赖和建议顺序，不重命名旧文件。删除或废弃保留真实历史与替代关系，不能为看起来连续而重排引用。

各来源只维护自身正文。Product 不复制核心循环、系统清单或版本内容；专业规格补足具体交付要求，专业工作中改变整体设计时仍写回 GDD。共享要求沿适用范围和实际依赖影响任务，未直接链接不代表不适用。不可读材料、遗漏图片、矛盾和未采用方案保持可见；代码只能证明当前行为，不能证明用户曾批准它。

先预拆分，再逐个细化与交付

先在 docs/product.md 预拆分当前约定的交付范围，检查遗漏、边界和依赖；后续 Product 只保留总览条目，不提前创建详细文档、Feature ID、逐项 AC 或测试登记。

当前 Product 轮到时，依据最新 GDD 和前面交付结果编写其文档，然后一次覆盖完整必要范围，生成多个能独立理解、验证的小到中等 Feature。完成这些必要 Feature 后，再复核并细化下一 Product。已有有效计划直接复用，不因为来源充分就提前展开未来任务。

影响当前实现的跨系统问题应先在 GDD 中解决。例如，后续背包设计决定容量满时采集失败还是资源掉落，这项规则需要先明确，但无需因此提前编写完整背包 Product。预拆分随着实际结果调整，不是固定的实施承诺。

依赖表达真实前置，不按编号串联全部任务。只有依赖已完成的 pending 项才是 eligible；没有 eligible 候选也可能是依赖阻塞，不能推出当前 Product 已经交付。

“只涉及逻辑”“只涉及表现”“跨层”说明功能范围，不是新的 Feature 类型或强制拆分规则。例如一个购买 Feature 可以同时覆盖条件判断、扣费与获得反馈，分别给出可观察 AC；也可以按真实可独立交付的结果拆分。不能仅因为跨层，就预先安排两个 Agent 或规定必须先完成全部逻辑。

判断拆分时，要能说清每项工作在什么条件下、经过什么操作或检查、得到什么可观察结果。依赖则说明前项提供了哪项必要能力或决定，不能把“建议先做”直接当成“必须等它完成”。例如，采集界面的独立视觉原型可以使用本地示例状态，正式按钮接入资源变化才需要可用的采集操作；有明确技术结果的 Feature 也不必同时包含界面。

规划预览说明：

  • 任务数量；若与先前预期数量不同，应解释变化。
  • 各项名称与范围、可观察完成结果。
  • 依赖理由及覆盖缺口。

普通规划需要具体方案确认；用户已明确授权自主拆分则展示后继续。Goal 名称或持续执行模式本身不授予规划权限。

语义覆盖需要能追到“来源要求 → Feature/AC → 自动测试或人工检查 → 未覆盖项”。格式检查成功只证明结构满足工具契约，不证明没有漏掉需求，也不证明功能已经实现。

基线与需求修订

首次 R000 记录当前确实采用、已提交且被计划吸收的 GDD、Product、专业与规则来源。创建器的初始空文件提交不是需求基线。后续 Product 规划不重置已有锚点；synced_at_commit 记录真实分析的源版本，不是随手填最新 HEAD。

已确认要求变更时，来源归所属入口；规划由 feature-sync 处理现有影响。来源链接也属于输入：

  • 需要修正来源时： 先保存并提交有效来源，再依据实际 HEAD 分析。
  • 只修 Feature 的计划引用时： 不要求额外来源提交。

相关来源必须能独立保存，仓库有无关差异不是通用阻塞。

新增采用的 GDD 或专业来源可能早于旧锚点存在，旧提交时间不能证明其曾纳入计划。缺少可证实基线时只能说明历史未知，在授权内对齐当前来源及已规划范围，不把空 diff 写成完全同步。

已有实现与教学示例

功能先写出来再补记录时，仍须有真实 GDD，以其已确认设计核对交付范围，并复用符合要求的实现和测试。文档补齐不等于交付，不能补造过去的 RED、批准、测试或完成时间；正式完成使用本次实际满足条件的时间。新测试立即通过可证明当前已有行为，不证明过去采用过 TDD。

例如 GDD 已确认“初始资源为 0，每次点击增加 1”时，Product 可选择交付手动收集闭环，Feature 再用初始值和连续点击结果的 AC 关联真实测试。这个例子只说明对象如何连接，不为任何项目自动批准数值、文件名、Feature ID、存档范围或测试结果。

权威结构见 Product 规范、Feature 规范 和 测试策略。

任务类型、开发阶段与完成语义

操作手册

项目采用一位使用者与 Agent 配合的开发方式。任务、阶段、Git 提交与实际验收分别表达不同事实；阶段号帮助定位工作，不构成额外自动状态机或逐阶段审批。

依赖游戏设计的规划、实现、调查或实验须有支撑当前范围的真实 GDD 规则，缺失时不自行补造。项目内可以先形成设计，GDD 草稿审核也不需要先建立 Product 或 Feature；它们不启动下面的实施阶段。内容与维护边界见 需求与交付规划。

任务边界

类型 对象与完成含义
普通 Feature 交付已确认的玩家行为与对应 AC
Bug 实现违反仍有效的 GDD、Product 交付要求、专业规格或工具契约；恢复既有预期
重构 保持外部行为，降低有具体依据的维护成本；文件变少或指标降低不单独证明收益
工程维护 工具、依赖、性能、资源或数据的明确技术目标，不借此增加玩法
限定实验 在假设、范围、预算和文件去向内取得证据；观察结果不是自动获准需求
只读调查或审核 提供证据与结论；发现问题不自动获得修复权限

正式交付以项目规定的 Feature 完成状态与完成记录为准，不以测试通过、代码提交或用户试玩作为单独判断依据。交付前原任务范围内的缺陷仍由该 Feature 处理；交付后的独立缺陷由新的工程 Bug 承担，原完成历史保持真实。需求尚不明确的疑问与用户改变要求不是“修 Bug”。

逻辑类、表现类和跨层类描述功能涉及的职责，可以与上述任务类型交叉使用。例如购买失败却播放成功动画，属于跨层接入的 Bug；更换已确定的图标飞行方案，主要涉及表现。分类帮助定位要求和验证范围，不新增 Stage，也不决定必须创建多少对象、文件或任务。职责例子见 游戏逻辑、表现与协作。

Bug 的实际表现、预期及来源、复现和根因应能对应证据；未知解释保持假设。可自动回归的缺陷以目标行为失败和修复后的通过保护，确实不适合自动化时保留原因与可重复人工路径。

修改前后的共用要求

Bug 修复、功能实现、重构、工具维护、资源接入、迁移和性能优化都应按实际影响采用以下要求，具体方法仍由所属任务决定：

  • 修改前：读取当前实现与直接消费者，找到行为实际所属位置，简述必要修改和验证范围；有效计划可直接复用，不新增审批关卡。
  • 修改时：完成最小且完整的目标，保持无需变化的 API、依赖与代码风格；必要契约变化同步实际消费者，不顺带改无关代码。
  • 交付前：完成相关测试及项目支持的适用静态检查，检查最终差异；说明关键文件、修改理由、实际验证和有依据的剩余风险。

共用正文见变更准备与范围、验证政策与交付说明。这些要求不扩大只读任务的授权，也不替代所属流程的实际人工验收。

Stage 的含义

阶段 保存的决定或事实
0 上下文 当前目标、来源、规则、已有差异、有效授权及必要环境
1 方案 范围、真实影响、资源、测试策略、验收方式及必要设计决定
2 保存计划 已批准方案进入 Feature、Registry、Progress 与必要设计；状态为 in_progress
3 实现 相关 baseline、小行为 RED → GREEN → 必要重构及适用分批提交
3D 文档检查 使本次改变的 GDD、Product、术语、专业规格、表现文档及所属资源章节、设计、规则与架构符合实际决定
4 最终验证 当前义务对应的自动、直接静态与专项结果；适用时准备人工清单
5 人工验收 仅 manual 模式，取得用户对当前内容的真实结果
5.5 Bug 经验 仅 engineering_change: bug，保存根因、触发、回归与有用防范原则
6 独立评审 仅用户指定的范围与时机；可集中审多项，不是每项默认关卡
7 完成记录 所有适用条件满足后由 Agent 更新 done、实际完成时间、记录与收尾提交
8 交接 报告实际交付与限制，核对剩余授权；已授权后续工作继续推进

具体流程唯一正文在 执行规范 与 feature-execute。普通实现细节由 Agent 判断；未变的具体授权跨 Skill 和阶段沿用，原 Skill 返回不等于整项授权结束。

复杂 Feature 可按需使用 implementation-guidance-godot 准备指导，仍沿用 Stage 1 方案与 Stage 2 保存设计的顺序，不增加指导阶段或额外批准。默认由主 Agent 准备；明确要求时才委派指定顾问。主 Agent 核对关键原规则与实际代码后继续执行；调用方法、收到设计或顾问完成，都不表示 Feature 已实现、验收或独立审核。

自动与人工验收

验收方式从要求出发。画面辨识、声音、动画、操作手感等需要人判断时采用 manual；所有 AC 都能充分自动验证时才可 automated。manual 同样可以有大量自动义务；实现授权、自动通过与用户沉默都不是人工接受。

跨层功能同时核对规则结果、表现和真实接入。例如扣费正确、只在成功后播放奖励反馈，以及关闭再打开界面后余额正确，是不同的检查内容；计算测试通过不能替代动画体验，原型效果可接受也不能证明正式购买规则已接入。

人工清单与结果按以下职责分工：

  • 清单内容： 项目对应 AC 或必要回归，包含入口、起始状态、操作、可观察结果和重置方法；影响结果的设备、时长、种子才补入。
  • Agent 与工具： Agent 提供 pending 原清单，工具绑定版本。
  • 用户结果： 用户另存结果填写 passed/failed/pending 与观察，不能改 ID、步骤或预期来消除失败。
  • 接受判据： 有效必需项全通过且无矛盾反馈已表示接受，无需重复索取相同确认。

口头明确结论和结果 JSON 是两种记录方式。原件缺失、版本失效或反馈有歧义时保留缺口，导入成功也可能记录 rejected 或 pending。automated 不生成空清单或伪造接受。契约与工具见 人工验收文件、命令与证据。

只有有效 manual 计划确无自动测试义务，且不存在未解决的失败或未结束最终运行时，运行器才可能返回 not_required。该结果不是放弃测试的开关；直接静态、专项检查与人工要求仍各自适用。

验证与证据

修改前 baseline 说明已有安全网；环境、解析或测试发现故障不算目标行为的 RED。一个 AC 可以包含多个小行为循环，不要求先写完所有测试再统一实现。接管旧实现不刻意破坏代码制造历史 RED。

最终验证按真实组件和计划选择 Required、affected 或必要 full，不因“维护”标签一律全量。一个当前且覆盖充分的结果可复用，较新失败不能用较旧或更窄成功掩盖。完成工具不代替解析、lint、性能、长测、实际显示或听觉判断。

纳入全局内容指纹的 GDD、Product、规格、规则或表现文档及所属资源章节即使只是文字或状态变化，也可能使当前未完成任务的旧依据失效；后续 GDD 章节也不因尚未开发而豁免。notes 的豁免不传递给被链接的设计文档。纯过程历史整理不等同于业务变化，历史已完成记录不会因此自动重开。较晚的 Bug 经验或规则采纳同样核对实际影响。

Git、暂停与持续任务

非空 Git 状态不是单人项目的统一阻塞。

  • 已有差异： Agent 查看当前差异，保留与本任务无关的内容及其暂存状态；同一任务续接的改动核实后可以完成并提交。仅对具体覆盖冲突、无法分离的提交或必要来源无法保存说明阻塞；不要求改动归属证明，不自动 stash、恢复或清空现场。
  • 暂停和切换： 使用当前任务目标目录中的 Progress、原任务及真实文件；普通同目录续接不需要新建工作目录、状态台账或强行提交半成品。已有指定 worktree 时，以该目录的真实内容与 Git 状态为准，具体操作仍按任务授权执行。

项目默认每完成一项可独立理解、通过相关验证的完整逻辑成果，就创建本地提交，不积攒到复杂任务全部结束。开始时可在已有方案中说明这些成果及依赖，执行中按实际情况调整；简单任务一次提交即可。

  • 提交边界： 每项成果带上必要实现、测试、引用和说明；不按文件数量或“代码、测试、文档”机械拆开。单项 Feature 可以多次提交，中途仍保持 in_progress，不能依赖遗留未提交配套内容才能工作。
  • 用户指定条件： “不提交”、先验收或需明确允许提交等条件按其具体范围优先，并跨 Skill 与续接沿用。如果当前任务同时要求实际验收和明确允许提交，两者都须满足；验收通过本身不等于允许提交，已取得的具体许可也不重复索取。
  • 验证与核对： 提交前审查明确路径和完整暂存差异，复用仍覆盖该提交的有效验证，补足缺失或失效部分。相关检查失败或必要验证未完成时不提交。最终审核覆盖全项提交与剩余差异，不能只看最后一次提交。
  • 提交后： 核对新提交范围和剩余差异；发现问题后修复验证，再新建修正提交，不改写历史。交付汇总本次提交与未提交的本任务工作。提交受权限、身份或钩子等阻止时保留现场并说明，不擅自改配置或绕过检查。

Feature 提交主题为 <type>(F0XX): <中文行为摘要>，正文 Feature: 用真实标题，Work item: 指向详情；非简单变更说明原因、关键取舍和真实验证。没有所属 Feature 的任务不虚构身份。具体命令、暂存保护与禁止操作统一见 Git 规则。

Goal 只是持续工作的承载方式。

  • 交接终点： 现有专用入口可授权逐 Product 推进到首个已准备好人工验收的 Feature；该交接终点不等于 Feature 已 done。
  • 原型缺少决定时： 只暂停依赖部分，不能据此宣称最终验收材料齐备。
  • 持续任务的结果： 失败、预算耗尽或前置受阻不是成功完成；用户结果与继续授权决定后续段落。

独立审核的范围、真实性与修复权限见 专业来源与资源，工程分类见 工程变更规范。

Skill、Agent 与提示词

操作手册

Skill 保存可复用方法，Agent 是执行方法的实例，提示词表达本次具体任务。三者不具有相同粒度：每条正式提示词只对应一个具体场景，通用 Skill 与脚本则按职责和独立变化原因划界，不能为了每篇场景复制一套实现。

游戏逻辑与表现用于理解功能范围，Skill 仍按当前工作选择：规则与体验目标由设计入口处理，一次表现由 design-game-presentation 细化，获准开发由原 Feature 承接。跨层功能可以由同一任务完成，不要求分别委派逻辑和表现 Agent；环境、测试与构建方法作为共同工程支持使用。

工程规则、可复用方法和当前游戏方案各自承担不同职责。以 Shader 为例：

内容 保存位置与用途
工程约束 Shader 规则维护语言、坐标、材质参数和真实验证等适用要求，按既有 MUST、PREFER、REVIEW 区分强度
可复用方法 实现方法参考帮助推导数据流与算法选择；诊断参考帮助选择能辨别原因的检查，按当前问题读取
当前游戏方案与证据 表现目标和采用方案保存在所属游戏表现文档；已有 Feature 需要详细工程设计时使用其设计稿，原型、诊断与验证证据沿用原任务记录，具体归属见知识、设计与记录

Shader 规则入口同时导航这些可选方法。正式实现、限定原型或排错任务都可以直接阅读相关参考；文件位于某个 Skill 的 references/ 中，不表示需要启动该 Skill 的完整流程、创建 Feature 或委派顾问。方法不改变当前任务的授权与完成条件，具体效果数值也不因此成为通用规则。

design-gdd 可以在项目内从想法形成 GDD；设计讨论、数值建模和 GDD 草稿审核不要求先有完整 Product 或 Feature。依赖设计的规划与实现仍须先核对当前范围的真实规则，缺失时只停止依赖部分并明确设计缺口，详见 GDD 前提。

普通澄清由 project-grill-me 负责，GDD 设计由 design-gdd 处理，Product 问题由 product-spec-elicitor 使用共用提问方法，Feature 拆分由 feature-plan 负责。现有草稿、完整 GDD 或方案需要检验时才使用 plan-review-godot，按 GDD 阶段与范围读取其领域参考，不因尚无 Product 或 Feature 拒绝审核；正式独立审核仍须非作者实例。开发经验复盘使用 retro-godot。这些结论交回原有负责人，不增加必经关卡，也不替代人工验收。

design-balance 从已知目标与规则推导数值方案，也可以针对既有模型调整参数；它在写入授权内直接维护所属 GDD 数值正文，不要求另一 Skill 代为保存。参数采用、文件写入和验证状态分别记录，新增玩法或体验目标变化回到 design-gdd。检查现有模型、策略组合和已采用数值是否成立，使用 review-balance 独立审核；设计者的计算自查不能称为独立审核。普通尺寸或数量记录不自动触发专项建模。

收到反馈、尚不清楚是否要改时，使用 feedback-triage-godot 核对类别与归属；已经有具体异常、需要查原因时，使用 bug-diagnosis-godot。用户描述实际症状即可，Agent 随证据追查逻辑、表现及其连接，不要求用户先选层，也不因跨层自动拆成多个 Bug。它们不新增工单状态，也不改变交付前后 Bug 的归属。只调查就交付证据与结论；已有具体修复授权则返回原任务继续，不因方法结束重新索取同一批准。

环境准备、限定检查、人工验收和证据处理这四个入口可以在不同工作环节按需调用，也可以承接直接提出的限定任务，不是新增的固定阶段。例如，只要求跑现有测试时，有无 Feature 都按该检查的实际范围执行；登记人工验收时，则必须对应实际 Feature 与用户结果。工具可用、检查通过、用户接受和证据仍适用是不同事实，不能相互替代，也不因调用其中一个入口就扩展为整套交付。具体选择由任务路由统一维护，各 Skill 按需引用原有配置、测试、验收与证据规范，不复制第二套正文。

prototype-godot 用可运行的 Godot 场景或逻辑实验回答本次问题，保持实际运行、原型观察与生产验收的区别。task-handoff-godot 使用既有 Progress、Feature 或任务记录：只要求暂停时保存停点，需要换对话时再提供可复制文本；不自动创建对话、发送消息或另建交接台账。恢复已有停点直接回到原任务，不必再调用一次交接。

这些入口便于明确调用，description 也帮助按任务选择；文件存在或格式校验通过不证明客户端已经隐式选中它。工程规范中的必要调查与验证仍由原流程负责，不能只依赖 Skill 的自动发现。

逐步探索与 worktree

wayfinder-godot 适合几个问题互相牵连、要先解决一个才能判断下一个的情况。例如，背包容量会影响搜索需求和列表性能。它按当前缺口选择讨论、事实调查或限定原型，不要求把所有方法走一遍，也不让普通澄清、已有方案检验或清楚的实施任务先经过探索。只讨论就交付结论；已有具体实施授权则在问题解决后返回原任务继续。结论与证据按知识与记录保存。

确需另一个工作目录时，用 worktree-create-godot 准备或复用指定版本的 checkout。目录分开不证明运行数据分开；具体准备只在该 Skill 的运行参考维护，环境和验证入口在相关写入位置未知或变化时也直接引用它，不必重新创建 worktree。

已经选定要采用的成果，或要接手已有整合冲突时，用 worktree-integrate-godot。它负责带回必要依赖并检查组合结果，冲突方法是其按需参考。原任务的验证、人工验收及提交条件继续有效；整合不自动删除源目录或分支。Git 详细规则仍归项目 Git 规范。这三个能力可以分别调用，不构成新的固定阶段。

框架维护侧的方案检验与复盘

框架维护讨论继续使用个人的渐进式澄清 Skill；它不随项目分发。已有维护方案可交给 plan-review-yaya，检查假设、职责、分发影响和验证办法，指出具体问题或证据缺口。

框架的实际维护复盘由当前 Agent 按集中提示词中的对应场景，依据执行记录、根维护原则与职责设计准则分析。复盘不因缺少 Hook 或 CI 就判定存在问题，也不默认修改规则、建立脚本或新增报告。建议不自动成为需求或待办；已有具体实施授权则由原任务继续处理。独立入口表示职责可单独调用，不代表已经使用了独立审核实例。

重复工作方法设计

已经反复进行，或预计以后经常要做的工作，都可以使用方法设计入口，不必先发生失败。例如，经常要重新说明资源准备需要哪些输入，可以比较补充现有入口、明确资料引用和新增能力，设计下次怎样开始、判断与交付。它可以在讨论、开发或维护等环节按需调用；retro 则从真实经历分析原因和经验，两者不是固定的前后步骤。

Godot 项目使用 loop-me-godot，随项目分发，只使用项目自己的规范与能力。它与 retro-godot 分别借鉴 Matt Pocock 的 loop-me 与 retro，保留来源名称，按项目实际职责改编。框架侧由当前 Agent 按已有重复工作场景处理，需要讨论未决选择时使用个人渐进式澄清方法。

方法设计默认交付可讨论的处理方案，详细规则继续归已有正文，不自动创建脚本、报告或周期任务。用户已经明确授权的实施由原任务继续，不因方法设计结束再次索取同一批准。

框架维护侧的反馈、诊断与交接

以下三个入口只在框架维护仓库使用，与 Godot 版分别维护，不随项目分发：

  • feedback-triage-yaya：核实反馈或外部报告，区分当前问题、已有覆盖、设计取舍与证据缺口，提出处理归属。
  • bug-diagnosis-yaya：对具体维护异常调查因果关系，按本次获准的静态或运行范围取得证据。
  • task-handoff-yaya：核对真实停点与有效授权，按请求整理既有记录或生成可复制交接；明确要求只读时不写文件。

三者使用框架自己的维护、验证和记录约定，不启用待分发项目的 Stage。收到报告不等于获准修改；已批准的后续工作沿原任务继续，明确暂停则保持暂停。

主 Agent 与专用角色

  • 主 Agent： 定位实际目录、范围与已有决定，按任务调用方法并持续推进尚未完成的授权。
  • 用户： 负责未决意图与实际人工体验。
  • 工具： 负责可重复检查；工具退出成功不取代用户判断。

项目附带的 researcher 用于按需独立调研，independent-reviewer 用于独立审核。需要新上下文、宿主真实支持及适当有效权限，配置文件存在不证明角色已加载或文件系统已隔离。作者自己读审核 Skill 仍是自查。

已有 Feature 的实施指导使用 implementation-guidance-godot。默认由主 Agent 准备；只有用户在任务提示词或仍有效的具体授权中明确要求，才委派 implementation-advisor。任务复杂、加载 Skill 或要求详细设计本身都不自动触发委派。顾问角色固定使用 GPT-6 Astra、xhigh，模型设置只在角色配置维护。

顾问读取相关规则和实际代码，给出有来源的设计及验证思路。需要用户决定时，它把编号问题、A/B 选项和建议交给主 Agent；主 Agent 在当前对话正文中展示，并把回答传回同一顾问。未获批准的方案先在对话中讨论，批准后顾问才可保存获准的同一份 Feature 设计稿，主 Agent 负责核对、记录和后续实施。存放位置与生命周期见局部设计。

顾问不运行 Godot、测试或实验，不改业务实现、Feature JSON、Registry、状态或验收，不提交。主 Agent 仍阅读设计稿、关键适用原规则和实际要改的代码与消费者，不必重复顾问的全部背景调研。启动、指定模型或顾问执行失败时，停止依赖它的工作并报告原因与已完成部分，不自动换模型或改由主 Agent 接管。设计者不能兼任这份设计的独立审核者。

研究可使用用户级 anysearch；框架不复制其实现、密钥或个人路径。工具不可用时按角色规则选实际可用渠道并说明限制；没有可用来源不伪造已查证。调研方法与报告格式由角色维护，长期保存位置见 知识、设计与记录。

没有显示在客户端 Skill 列表，不等于文件未安装。核对当前实际项目路径、文件与客户端加载能力；不能把个人安装、框架源目录和生成项目的 Skill 混为同一份。

提示词库的结构与输入

正式可发送正文按用途分开维护：Godot 开发提示词库、Yaya 框架维护提示词库。

维护库内的提示词、分类或场景时，使用框架专用的 prompt-and-graph-maintenance-yaya。它根据实际变化核对同名场景、索引、覆盖清单、Godot 场景图与 advisor 的相关说明；文档职责、路径或引用关系变化时，也由该入口维护文档系统图中的文件名、路径和关系。详细写法和工具契约仍引用原有规范，普通局部修改不要求通读全部场景，全仓文档覆盖扫描只在明确要求时运行。该 Skill 不随游戏项目分发，也不用于临时对话中的提示词或项目内续接文本。

  • Project： 每份文件保留单元素顶层数组，分别保存 Yaya 框架维护 或 Godot 项目开发。
  • 名称与正文： 各自 categories 下的叶子键是提示词名称，字符串值是正文。
  • 目录映射： <Project>/<分类>/<提示词名称>.md，无需读取文档正文推断配对。

每条正文都用明确字段区分目标、范围、输入与事实来源、决策边界与授权、约束、输出与交付、验证要求和完成条件。其他字段按真实场景补充；完整表格及审核依据见提示词字段与审核原则。字段中的规范引用继续有效，无需重复填写可从当前对话或项目读取的信息。

发送时注意：

  • 填写输入： 发送前填写 ${1:说明} 等输入占位，提供真实目标、文件、状态与允许范围。
  • 附带材料： 长篇材料使用正文预留材料区，任务要求与原文保持可辨；材料位置不是安全边界，引用文本不能覆盖用户指令。
  • 选择与续接： 只选当前具体场景需要的一条，后续口语补充沿用仍有效的授权，不要求逐条发送整套模板。

框架维护在框架目录，业务工作在实际项目。创建/复制迁移明确输入与目标；读取模板或讨论提示词不启动命令、Goal、外部任务或自动写入。用户选择范围可扩大后续授权，也可替代原来的临时只读限制；实际人工接受始终单独核对。

advisor 的共享场景入口

advisor 根据项目自己的规则、状态和本次问题给出建议。它可以报告现状、判断下一步或拟一条已填写上下文的回复，但建议和候选不是实施授权，用户说“看看下一步”也不自动启动开发。

  • 核对现状： 读取当前项目记录和相关证据，判断现在做到哪里、还需要解决什么。
  • 选择场景： 直接读取 D:/A_Games/Game_idle_yaya_frame/framework/prompt_scenarios/prompts/godot-development-prompts.json，先看相关分类与名称，再读取候选正文，核对目标、前提、范围和预期结果。
  • 形成指令： 说明选中了哪个场景及适用理由，把项目当前事实、文件和已有授权填入续接文本；具体执行仍核对项目自己的规则与目标 Skill。
  • 判断缺口： 缺少输入时补齐信息；目标和执行边界相同则适配现有场景。只有真实缺少目标或边界明显不同，才建议新增或修改场景，说明最接近的条目、差异和建议用途；advisor 不修改共享库。

提示词正文只在共享库维护。advisor 读取当前正文，不需要导出副本；条目里的“执行”不代表当前任务已获准，Skill 名称也不证明本项目已经具备该能力。状态查询直接回答，不要求查找场景。

advisor 与交接入口起草的项目续接提示词共同遵循 Continuation prompts，不按任务长短省略固定字段。格式规范由项目持有；advisor 的场景素材来自共享 Godot 库。等待人工验收、缺少决定或验证受阻应与完成条件分开表达。

命令与验证证据

操作手册

所有项目命令在生成后的项目根目录运行。按当前任务调用所需入口，以下命令参考不意味着每次都要整页执行。涉及写记录的命令遵循对应 Skill 和已有授权。

Agent 按 GDD 前提 核对本次规划、实现或运行依赖的真实规则。设计可以逐步形成，命令成功不能代替内容判断，工具不通过新增状态字段宣告 GDD 就绪。

从运行结果到完成状态

Stage 4 记录最终测试结果，Stage 5 按需记录人工结果，首次记录时建立完成依据文件，Stage 7 检查完成条件。下面是实际读写关系；它不会因编辑文件自动触发。

实线表示实际调用、读写与结果交接，虚线表示原件引用。完成依据 JSON 位于 docs/feature-completion-evidence.json。record-tests、validate 均属于完成记录工具；不运行测试、不评估直接静态检查、不获取用户决定，也不修改 Feature 状态。人工文件导入还会核对清单与结果原件，具体操作见 人工验收。

文件交接 输入与产出 结果判定
测试运行器 当前 Feature、Registry、配置与源码 → 运行目录、result.json 和实际报告 等待进程结束，读取结果、发现集合、覆盖与诊断；仅打印路径不证明文件保存成功
record-tests 实际 final Feature 的 result.json 路径 → 完成依据中的路径/哈希引用 重新核对当前内容、原件、覆盖及未解决失败；不接受手写“通过次数”
人工反馈导入 绑定当前内容的清单 + 用户结果，或明确的口头决定 → 人工记录 命令成功只代表记录成功，状态仍可能 pending/rejected
validate 当前合同与完成依据 → 只读结论 重新计算测试义务并读取原件，核对适用人工接受；不替代其他检查

调用准备

先确认项目配置已经就绪。本页 PowerShell 示例共用以下变量：

powershell
$projectConfig = Get-Content -LiteralPath 'docs/methodology-config.json' -Raw | ConvertFrom-Json
$projectPython = $projectConfig.python_executable
$projectGodot = (Resolve-Path -LiteralPath $projectConfig.engine_executable -ErrorAction Stop).Path
$featureId = 'F001' # 教学占位，必须换成当前真实 Feature ID

在本机，python_executable 应是个人规则指定并已确认的完整解释器路径。F001 和示例脚本路径都需换成实际存在的任务与文件。每条原生命令后立即读取 $LASTEXITCODE；缺失退出码不能当作 0。

新项目首次 CLI 测试或项目脚本运行前，按 首次扫描说明 处理编辑器准备；环境检查通过 不代替这次扫描。

入口与副作用

入口 常用参数 行为
tools/checks/check-project-environment.py --require-ready、--config 读配置；就绪检查可能启动 Godot --version，不写配置
tools/checks/check-feature-list.py --eligible、--completion-feature F001、--repo-root 读 Feature/测试登记表/历史和依赖，不修改台账、不运行测试
tools/testing/run-gdunit-tests.py --godot-binary、--feature 或 --target、--phase、--scope 有测试时启动 Godot 并写运行目录；合法空集返回 not_required，不创建报告
tools/features/record-feature-completion.py 子命令与 --feature；全局 --repo-root 在子命令之前 写入测试/人工记录，或只读展示、校验已有依据
tools/features/merge-test-registry.py --components 在项目根目录运行，将批准的组件合并到固定的 docs/test-registry.json；属于规划写操作

组件合并器的输入和行为：

  • 候选格式： 完整组件对象的 JSON 数组，或含 components 数组的对象。
  • 调用： Agent 将批准的候选写入临时文件，使用 --components <实际候选文件> 调用合并器；候选不提交。
  • 冲突与保留： 现存同 ID 不同内容是冲突，不能覆盖。工具保留现存测试并报告 added_components/preserved_tests。
  • 能力边界： 只合并组件，不生成测试或证明测试通过；结构见 feature-plan。

环境与台账检查

前置： 在当前终端完成 调用准备。

powershell
& $projectPython -B tools/checks/check-project-environment.py --require-ready
$LASTEXITCODE
& $projectPython -B tools/checks/check-feature-list.py
$LASTEXITCODE
& $projectPython -B tools/checks/check-feature-list.py --eligible
$LASTEXITCODE

环境检查器的精确能力见 配置检查边界。台账检查读取完整索引、详情、测试登记表和修订关系，检查 ID、字段、引用、路径、依赖与历史规则。--eligible 校验后输出依赖已满足的 pending Feature ID 集合，不能代替实现授权。

组件套件和 active 测试必须登记项目内的相对路径，不带 res:// 前缀。合并器与台账检查都会拒绝绝对路径、父目录跳转以及解析后指向项目外的链接，避免到测试选择时才发现路径不可用。planned 和 retired 测试的 path 可为 null；已填写的路径不要求对应文件当前存在，已知历史路径仍须保留。

规划或同步完成后使用这个完整入口即可，它已经包含 JSON 解析；单文件语法检查只用于定位具体错误。Agent 仍需核对需求覆盖、真实依赖和历史保留，这些语义不能由结构检查代替。

--completion-feature F001 额外要求当前待完成任务的直接自动验证映射处于 active 状态。正常历史检查可以接受可追溯退役的旧测试；当前完成不能拿已退役测试替代实际验证。

三种常见测试调用

前置： 在当前终端完成 调用准备，再在已批准范围内按用途选用：

powershell
# Stage 3：已有安全网，不包含尚未创建的 planned 测试。
& $projectPython -B tools/testing/run-gdunit-tests.py --feature $featureId --phase baseline --scope auto
$LASTEXITCODE
powershell
# TDD 或定点诊断：替换成实际已存在的套件或目录。
& $projectPython -B tools/testing/run-gdunit-tests.py --target tests/features/F001/example_test.gd
$LASTEXITCODE
powershell
# Stage 4：读取当前 Feature/测试登记表和已批准范围。
& $projectPython -B tools/testing/run-gdunit-tests.py --feature $featureId --scope auto
$LASTEXITCODE
  • 目标： --feature 与 --target 互斥；两者都不传时 target 默认为 tests。
  • 阶段： --phase 支持 baseline、final，默认 final。baseline 和 focused/target 运行用于基线或调试，不能直接作为当前 Feature 完成依据。

其他参数：

  • --timeout-seconds 默认 120，必须是大于 0 的有限数。
  • --require-test 使用 <suite-path>::<test-case> 格式，要求原始报告确实覆盖该用例。
  • --continue 传给 gdUnit 的 -c，不表示继续一个已有 Yaya 任务或复用上次报告。

运行器启动真实引擎和测试，而非纯文件检查。所需权限、窗口行为与运行范围按当前项目和任务确认；不能因为名字含“测试”就认为无副作用。

测试范围怎样计算

Stage 1 的完整测试范围规则见测试规范中的 Test Impact Review 与 Runtime Test Impact selection。下文用中文说明 Required、affected、full 与命令的对应关系。

text
Required Test Set =
  当前 Feature 的自动验收测试
  + 当前 Feature 的回归测试
  + 影响组件已登记的 unit_test_paths
  + 与影响组件相交的 active 历史回归
  + 与影响组件相交的 active 不变量
  + 已批准的 additional_tests

affected = Required + 与影响组件相交的 active 验收测试
--scope 用途
auto 默认执行 affected；当前计划需要全量时升级为 full
required 显式运行 Required，适合局部迭代；不能据此绕过最终 affected/full 要求
affected Required 加相关验收测试
full 递归运行 tests/ 并核对必需覆盖；空分层目录不单独成为义务，测试总数为零仍失败

影响组件设有 full_suite_on_change、已批准的 full_suite_reasons、广泛工具链影响或无法界定影响时，需要按规范执行 full；工程维护标签本身不触发升级。附加测试及理由保存在 Feature 的 verification.test_impact，没有独立计划文件。

没有单元套件的组件使用 unit_test_paths: []，不产生虚构选择器。已登记路径丢失、被选中目录零测试、必需用例跳过或报告缺失都不能记为通过。不存在且未登记的测试层不会贡献全量选择器；这不把空项目变成有成功测试证据的项目。

合法空选择集的返回及完成记录衔接见记录完成依据。

一次运行留下什么

实际 Feature 运行创建 reports/gdunit-wrapper/<Feature-ID>/run-<id>/，focused/TDD 运行创建 reports/gdunit-wrapper/focused/run-<id>/。运行顺序和完成检查只读取对应 Feature 的目录。使用命令实际打印的 result.json 路径，不猜测 run ID 或报告文件夹编号。

text
reports/gdunit-wrapper/F001/run-<id>/
├── result.json                 同一个文件从运行中更新为成功或失败
├── engine.log                  原始引擎输出
├── discovery.json              实际展开后的测试发现集合
└── report_<...>/
    ├── results.xml             原始 JUnit
    └── diagnostics.jsonl       运行诊断

启动或中途失败时，部分原件可能尚未产生；缺失本身就是要读取的结果，不应补造空报告。实际报告还可能包含 gdUnit 生成的其他文件。

运行器核对过程结果、实际发现集合、JUnit 用例和诊断。参数化用例需要对应真实展开后的集合，源码里存在 test_* 方法不证明它实际执行。JUnit 看起来成功也不能遮住引擎错误或未完成运行。

同一内容上的较新失败需要由之后覆盖该失败范围的成功解决；更早成功或更窄的通过不能盖掉它。保留原始失败，再说明修复与后续结果。

记录完成依据

完成依据入口为 tools/features/record-feature-completion.py。下表是参数速查，不是让使用者批量填“通过”的步骤：

子命令 何时使用

prepare-manual --feature F001 --checklist <清单.json> 检查 Agent 编写的 pending 清单并绑定最终内容；已绑定清单不能重新绑定
record-acceptance --feature F001 --checklist <清单.json> --result <结果.json> 读取用户真实结果，与原清单和当前内容对照；记录 accepted、rejected 或 pending
record-acceptance --feature F001 --status accepted manual 模式下，用户已经明确接受当前范围之后

导入测试结果

前置： 在当前终端完成 调用准备。把示例运行路径换成运行器实际输出的 result.json，先确认文件确已写入。

调用前确认副作用：

  • 一次 record-tests 会用本次所有 --run 整组替换当前测试引用，不会逐次累加；需要保留的兼容运行必须一次列全。
  • 结果导入校验失败会清除旧测试引用，原始报告仍保留。应处理失败，不得改写结果文件绕过。

只有一个有效运行时：

powershell
& $projectPython -B tools/features/record-feature-completion.py record-tests --feature $featureId --run "reports/gdunit-wrapper/$featureId/run-actual-id/result.json"
$LASTEXITCODE

需同时保留两个兼容运行时，改用一次调用中的两个 --run；以下路径同样只是占位：

powershell
& $projectPython -B tools/features/record-feature-completion.py record-tests --feature $featureId --run "reports/gdunit-wrapper/$featureId/run-actual-first/result.json" --run "reports/gdunit-wrapper/$featureId/run-actual-second/result.json"
$LASTEXITCODE

导入后核对退出码与实际结果。原件引用和当前内容绑定用于发现错误复用；脚本不接受手填通过次数来创建成功。

统一调用运行器即可，空选择集的处理如下：

  • 适用条件： 有效 manual 计划的 Required、affected 都为空且不要求全量时，退出码为 0，stdout 输出 status: not_required 的 JSON。合法空基线也返回 not_required。
  • 运行与记录： 不启动 Godot、不读取引擎配置、不创建运行报告，也不调用 record-tests。真实人工验收结果随后建立完成记录，其中 test_runs: []。
  • 仍会报错的情况： 显式 --scope full 或 --require-test、无效映射、缺失路径、当前内容上的未解决最终失败。
  • 结果含义： 退出 0 在此仅表示无需自动测试，不是 PASS。

有结果时直接记录，不用提前建空记录，也不用额外执行初始化命令。

  • 首次记录： 记录测试结果或真实人工验收时建立完成记录。
  • 已有文件： 损坏或格式不受支持时会报错，不会覆盖。
  • 独立评审： 范围和时机由用户选择。

其他失败处理见 故障排查。

导入人工验收记录

人工文件均保留在 reports/manual-acceptance/，输入/结果格式和命令示例见 人工验收文件契约。--result 与 --checklist 配对，不能与口头决定的 --status 混用。

有效全通过结果本身就是该范围的人工接受；注释存在实质矛盾时先澄清。命令退出 0 表示成功记录实际状态，pending、rejected 仍不能完成。无效导入退出非零且保留已有记录，Agent 必须处理本次错误，不能退回旧接受绕过。

内容绑定与失效判断

内容指纹是工具计算的文件摘要，不等于 Agent 对“含义是否改变”的判断。当前实现先通过 Git 列出已跟踪文件与未被忽略的未跟踪文件，按路径排序；对纳入的文件记录路径、存在类型与内容，再计算摘要。它读取当前工作区字节，不依据修改时间，也不只看本 Feature 的差异。

删除或重命名纳入的源码会改变指纹；已经不存在、仅残留在 Git 索引中的路径不参与摘要。纳入的现存文件集合及内容保持不变时，在该删除或重命名之后取得的测试和人工证据，不会因随后仅暂存或提交同一变化而失效。再次改变纳入的内容仍需按当前义务补验证。

输入类别 当前实际计算
GDD、Product、术语、专业规格/表现文档及资源章节、项目规则、Feature design、架构与 ADR 通常按文件原始字节纳入；换行、措辞、准备状态或排版变化即使不改行为，也可能改变指纹
源码、测试、配置和其他未豁免文件 纳入路径与当前内容；增删、移动同样可能改变摘要
docs/features/ 下的 JSON、Feature 索引、Registry、修订记录、methodology-config 指定 JSON 先解析并排序对象键、统一序列化；数组顺序仍保留，只排除下表约定字段
docs/feature-completion-evidence.json、docs/progress.md、reports/ 从源码指纹排除；报告仍由结果导入/人工原件契约单独核对，不可随意改写
docs/progress/、docs/knowledge/、docs/research/ 中以 .md 结尾的文件 解释性 Markdown 排除；非 Markdown 文件仍参与，要求正文不能只放在这些目录
普通 README.md（文件名大小写不敏感） 排除；但在 .agents/、agent-rules/、methodology/、docs/gdd/、docs/product/、docs/features/ 下仍参与

未被 Git 列出的忽略文件不会进入这次摘要；这不是把正式需求、规则或可执行输入迁入豁免位置的许可。知识只保留参考经验，普通 README 只保存用法与导航。其他 Markdown 没有通用豁免。

semantic_json() 只在特定位置移除过程字段，不递归移除所有同名键：

JSON 位置 不参与摘要的字段
Feature 详情顶层、索引每条 Feature 顶层 notes、status、completed_at、created_at、updated_at、recorded_at
索引/Registry 的 meta 上述过程字段及以 _at 结尾的键
修订记录的每条 revision_log revised_at、created_at、updated_at、recorded_at、summary、notes
  • 仍参与的字段： AC 文本、验证计划、组件、嵌套测试 status、退役关系、修订 ID、源提交锚点和未知合同字段。
  • 被链接的设计： notes 中的链接是过程记录，被链接的 F0XX-design.md 自身仍纳入。
  • Git 提交号： 另作来源记录；仅提交了过程字段且指纹相同，不会凭提交号要求重跑或取得新接受。

治理文档尽量在 Stage 3 完成。最终测试或人工接受后再改了纳入的内容，包括 Stage 5.5 采纳新规则时，先核对当前指纹与验证义务，补齐失效的最终运行、导入和适用人工接受，不能只凭“未改代码”沿用旧结果。内容相同且覆盖仍满足的结果才可复用；只读评审不改变内容。

这一绑定是全局的。即使修改的是后续尚未开发的 GDD 章节，也可能使当前未完成 Feature 的已有测试或人工接受失效；已完成的历史记录不自动重开。最终验证前应完成本轮来源更新，不为 GDD 另建一套指纹或同步记录。

直接依据是 验证快照实现 的 _is_fingerprint_input()、semantic_json()、working_tree_fingerprint()，以及 测试策略。静态解析/lint 的实际影响仍由 Agent 单独判断。

性能、长测、显示或试听证据按原任务 AC/设计中的验证义务判断；当前适配器只接收实际 gdUnit 结果，不把专项测量包装为 gdUnit 通过。完成工具也不判断专项证据是否充分，详见 专业验证边界。独立审核产生的隔离报告、日志或缓存不得覆盖原证据或被审成果。

直接脚本解析与 lint

前置： 在当前终端完成 调用准备。从项目根目录使用同一个已确认 Godot 可执行文件：

powershell
# 替换成实际变更脚本，并按影响解析必要依赖。
& $projectGodot --headless --path . --check-only --script res://path/to/changed_script.gd | Out-Host
$LASTEXITCODE
powershell
# 替换成实际 Feature；需保留不同轮次时，选择尚未使用的运行子目录。
$reportDirectory = "reports/features/$featureId"
New-Item -ItemType Directory -Path $reportDirectory -Force | Out-Null
& $projectGodot --headless --path . --script res://addons/gdscript-linter/analyzer/analyze-cli.gd -- --json --output "$reportDirectory/lint.json" res:// | Out-Host
$LASTEXITCODE

未归属 Feature 的工作使用 reports/maintenance/<任务>/；需要保存的解析输出也放入相应报告目录。不要覆盖仍被引用的原件，目录选择见 报告保留与清理。

对 Windows GUI 可执行文件，Out-Host 管道用于等待进程，立即检查退出码。lint 扫描完整 res:// 并遵循项目配置；修改了被默认排除的依赖时，仍需验证该依赖变更本身。

当前 lint CLI 的结果与报告约定：

  • 退出码： 0 表示无问题或仅 Info，1 表示 Warning，2 表示 Critical，3 表示输入无效、空发现、配置错误或 JSON 报告写入失败。
  • 显示参数： --severity 和 --top 只影响显示，不会抹去真实判定。
  • 输出文件： --output 支持 JSON 和 HTML 文件；默认文件名 code_quality_report.html 仅用于 HTML。
  • 报告内容： 报告真实范围与 Critical/Warning/Info 数量，未知数量不能写成零。

默认项目配置必须成功读取；根 gdlint.json 缺失或不可读时不会静默换成插件内置阈值。显式 --config 遵循相同失败边界，--check 中任一未知检查 ID 都以 3 退出，不能把零检查结果当成成功。

解析证明脚本在实际引擎中的相关语法/类型契约，lint 检查配置的质量规则；两者都不替代运行、资源、场景、导出或人工质量判断。需要编辑器检查时遵循本机项目规则的沙箱外审批路径。仅执行解析或 lint 时不额外增加导入步骤或包装程序；已授权资源导入和新项目首次运行所需扫描按对应环境规范处理，普通 Feature 不增加单独导入阶段。

通用交付不默认增加截图或像素比较门禁；任务明确约定客观渲染契约时，可以补充限定范围和环境的检查。画面构图、艺术一致性与动画体验仍由人工验收，具体边界见 视觉验证规则。

退出码和结果边界

  • 环境与台账检查： 成功通常为 0、校验失败为 2。
  • gdUnit 包装器： 成功为 0、运行失败为 1，参数解析错误可为 2。

最终结论仍结合原始输出和检查范围，不能将不同工具的非零值统一解释为业务测试失败。

已有结果 可以报告 不应推断
配置就绪 实际环境检查通过 游戏或测试通过
台账通过 数据结构、引用和依赖满足该检查 AC 已实现
focused 通过 指定套件在本次运行成功 最终 Required/affected/full 已满足
完成依据校验通过 它负责的测试与适用人工接受契约满足 脚本解析、lint、独立评审或所有目标平台已检查

错误与结果的含义

操作手册

本页解释工具输出，具体恢复任务按其实际范围处理。先区分环境、调用、发现、行为断言、引擎诊断和记录导入，不把所有非零退出都解释为游戏 Bug，也不把文件或成功摘要当作完整证据。

创建与环境

现象 含义与需要核对的对象
创建器拒绝目标 目标可能是文件、非空目录、其他仓库范围，或路径含中文/空白、与框架存在祖先/后代关系；拒绝不是覆盖许可
复制/Git 失败后留下目录 创建器没有自动回滚；保留原输出判断哪些动作完成，不凭目录存在报告创建成功
普通配置检查成功 字段结构满足检查；Godot 暂时为空也可能合法，不能当作 require-ready 通过
Godot 文件存在但就绪失败 实际启动、返回码或版本不满足；目录名不证明 4.7.x 可执行
相对路径或带参数路径错误 Godot 相对项目根解析，不能写 shell 引号、参数或裸 PATH 命令；Python 支持已确认的 PATH 命令名

专业来源与资源

操作手册

专业设计描述要求，资源准备提供真实文件，接入建立运行关系，验证和审核取得不同性质的证据。一个任务只使用所需能力；存在 Art Bible 或 Sound Bible 的占位文件，不要求先设计整款游戏的美术和声音。

表现层涵盖界面、反馈和它们的实际运行职责；本页的 UI、游戏表现及共享方向文档，分别细化其中不同问题。游戏逻辑与表现共同来源于 GDD，专业文档不会替代业务规则的正文。

专业工作按 GDD 前提判断实际依赖：设计讨论、数值草模和 GDD 草稿审核可以协助形成设计，接入、测量或实现前须有支撑本次行为的真实规则。不要求预先写完全部 GDD 或专业细节，也不把缺失的规则当成已经确定。

专业文档把 GDD 的设计意图细化为可使用、可验证的规格；GDD 已定义的细节直接引用，不另存一套正文。Product 选择交付范围并保存必要引用。专业 Skill 直接维护自己的正文；数值主题同样不要求 design-gdd 代为保存。专业工作若需要改变整体玩法规则或已确认体验目标，则由 design-gdd 协调该设计决定，交付范围变化再由 product-author 处理。维护职责不授权自行采用未决要求；本地化翻译用词也不能改玩法语义。

数值设计从目标体验、单位、边界、规则与已知数据出发，交付可复算的公式、参数及典型和关键边界情景。候选值、已采用值与实际验证状态分别标明；普通规格中的数字不自动成为数值建模任务。计算成立不证明游戏已经平衡或有趣，数值写入也不授权修改运行资源或代码。独立数值审核继续由 review-balance 承担。

来源如何约束任务

Feature 有一个主 source，相应 GDD 规则及其他适用专业要求在 AC 或设计中精确引用。共享来源的适用范围、实际依赖与引用共同确定消费者；“符合 GDD”或“符合 Art Bible”不是充分的 AC，应描述本任务的实际状态、尺度和可观察结果。

要求变化由所属入口修改来源，并分析已规划任务；实现违反已确认专业要求可以作为 Bug 依据，不要求再抄一份 Product。未经采用的设计建议不是缺陷。旧同步锚点也不自动证明新纳入来源曾被吸收，历史未知与当前对齐分开说明。

GDD、规格、表现正文及本地化要求在最终验证前完成本轮必要更新，包括采用组合、实际实现与消费位置、资源准备状态。这些文件按当前全局指纹契约参与内容绑定，准备状态或文字变化也可能使旧结果失效；GDD 目录中的 README 同样参与。约束正文不能只藏在豁免指纹的普通 README、notes、知识或报告中。

用一次游戏表现连接设计与实现

例如，设计“奖励领取”时，界面文档说明领取按钮在哪里、什么状态可以点击；表现文档说明领取成功后图标如何飞行、数字如何变化、按钮如何反馈。先从体验目标或口语描述形成可观察过程，再选择已有实现、序列帧、Shader、粒子、Tween 或 AnimationPlayer。Shader 与粒子参考帮助整理标准需求，具体算法、节点和代码由实施任务决定。

能否领取、发放数量和重复领取规则由游戏逻辑决定；表现使用有效结果，不能在图标到达时再次发放奖励。普通控件的悬停、焦点或展开状态可以在 UI 文档中说明，不必为表现层的每一处行为单独建立游戏表现文档。

表现正文按需要组织目标与过程、组件标准需求、候选方案、资源规格、采用关系、实际实现和验收入口。组件默认在所属表现内分节，确需跨表现复用时再独立成篇。docs/presentation/README.md 只导航；绑定要求写在具体正文中。

表现与开发任务不要求一一对应，只把已采纳要求和当前获准方案接入现有 Feature 的来源、AC 或设计。候选可以只保留描述，不要求全部制作。有具体不确定性才用 Godot 原型验证；正式实现沿用已有开发任务。

规划完成、实现可用和用户人工接受分别说明。表现文档链接原任务的验收条件、运行入口及既有报告或完成记录，结果仍保存在原记录中。替换方案后旧记录保留其原版本和覆盖范围；不在验收后把结果抄回表现正文，再宣称此前验证仍覆盖修改后的文档。

资源规格随所属设计保存

方案专用纹理等资源写入该方案章节，界面专用资源写入界面文档，共用资源写入对应共享视觉或声音设计章节；消费处引用同一正文。没有独立资源清单的默认目录，也不按 Feature 或收件批次另建台账。

资源条目按实际需要说明用途、文件名、格式、相关尺寸或时长、透明/循环等约束、准备状态、源与目标位置和真实文件关系。视觉资源区分源像素、显示尺寸和透明留白后的主体尺度；音频不填无意义的像素字段。需要资源 ID 时只在所属文档或章节内保持稳定，跨文档引用带路径与章节。候选值、已确认要求和实测信息分开写，来源与许可不明时保留缺口。

比如“命中时出现短暂火花”，即使最终纹理未到位，也能先说明运动、数量感觉、持续时间和触发方式；如果选用的粒子方案需要纹理，再把规格和准备状态写在该方案中。缺文件只影响依赖它的实现或体验判断，规划可以继续。

框架当前覆盖准备要求、接收和检查素材；图片、音乐、音效制作与本地资源库检索不纳入这项能力。外部准备交付真实文件后，接收任务更新同一所属章节，获准接入任务再检查实际使用。参考图、占位文件名或规格文档不是成品；规格请求本身也不授权制作、购买或导入资源。

视觉原型与实际接入

UI 规格描述信息层级、ASCII 布局、状态差异、显示条件和待验证问题；节点、路径和参数属于实现。新界面或明显布局变化需要能单独运行的 Godot 原型作为视觉判断材料，已有且适用的有效基础可复用。

  • 原型范围： 位于已授权 Feature 或限定实验，可用本地样例状态、Hover、焦点等必要交互；不默认接入正式存档和业务规则。
  • 判断条件： 真实素材、目标窗口、缩放、空/密集状态、裁切与可读性共同影响结论，图片原始像素不足以证明主体尺寸合适。
  • 接受与采用： 原型接受只覆盖原型范围，正式业务仍有独立验证义务；采用后处理样例状态与失去用途的副本，不长期维护两套竞争界面。

原型与正式逻辑的先后取决于本次问题：验证商品排列可以先用样例余额，正式购买接入则要核对实际请求、状态和结果。替换动画技术时保留已确认规则和表现目标；动画需要参与命中或流程时机时，由实现明确时序与有效结果判定，不能把表现完成无条件当作业务成功。

素材接入时：

  • 对照实际文件、规格、源记录和消费者，检查导入设置、路径/UID、场景/主题/代码绑定。
  • 声音的触发、停止、循环接缝、重复叠加和相对音量要在真实场景下试听；文件存在或播放器启动不能证明听觉效果可接受。
  • 保存外部原件和无关资产，不盲目重导整个库。

占位资源采用 _placeholder_ 前缀并在原任务说明用途、替换及验收缺口。源资源、导入结果、工作台预览与正式游戏分别有验证边界；示例通过不能替代游戏 Feature 完成。

测量与实现

具体异常统一由 bug-diagnosis-godot 按因果诊断处理，先看症状、预期和证据，再选择所需的专业方法。用户不必先判断它属于逻辑、表现还是两者的连接。

例如，已确认“角色受击后闪红”，实际生命值正确减少却没有闪红。扣血正确只说明这部分状态变化符合预期；Agent 仍需检查受击结果是否到达反馈控制、播放是否被打断，以及材质和参数是否接到了正确对象。证据指向 Shader 数据流时，才按需使用Shader 诊断参考中的临时可视化或固定条件比较。不能仅因画面异常就认定 Shader 有错，也不需要预先拆成“逻辑 Bug”和“表现 Bug”。

修复仍由原任务承接。涉及算法选择时可直接查阅Shader 实现方法，同时遵守Shader 工程规则；读取参考不启动新的指导任务或增加写入授权。表现要求、采用方案或文档记录的实际文件与接入关系发生变化时，同步所属设计；诊断与验证结果沿用原任务的证据位置。

  • diagnostics-instrumentation 提供有目的、单位和成本边界的日志、计数或时序信号。
  • diagnostics-performance 获取可重复负载下的测量和瓶颈依据。
  • diagnostics-soak-test 获取明确时长与停止条件下的趋势和失败。

只有静态猜测时不能写成已定位瓶颈。

  • 授权与副作用： 仅测量与诊断不自动授权持久优化，日志、缓存和报告仍有副作用。接入、本地化、埋点和优化的持久修改由原 Feature、限定实验或获准工程任务承接。
  • 版本与测量条件： 临时埋点版本与最终交付版本分开，可比性要包含设备、引擎版本、场景、负载、参数和测量条件；计划六小时只实际运行四十分钟仍有缺口。

专项结果不能包装为 gdUnit 成功；完成工具也不负责判断性能、长测或感官证据充分性。修复后相应真实检查仍适用。

独立审核

review-code、review-ux、review-art、review-audio、review-assets、review-localization 和 review-balance 分别核对自己的对象。同一个新上下文可以使用多个适用方法，不要求每项 Skill 各审一轮，也没有默认每个 Feature 都独立审核的要求。

  • 审核输入： 包括明确范围、权威来源、实际版本/差异、原始证据与允许运行范围。
  • 快照范围： 应包含相关未提交内容，只复制 HEAD 可能漏掉本次成果。
  • 独立性： 作者解释是待核实陈述；作者自查不能称为独立审核，角色配置存在也不证明独立性或隔离成立。

被审成果、原验收记录和原证据只读。获准的针对性验证使用安全副本或指定外部验证环境，将日志、缓存、导入和测试数据一起隔离；只改报告目录不够，使用 worktree 也不能代替对实际副作用的核对。条件不足时保留未验证项，未实际看到或听到时不宣称视觉/音频体验通过。

实现现状审核无需 Feature 或虚构差异基线，按相关 GDD 判断符合性。GDD 草稿或完整设计本身可使用 plan-review-godot 审核，不以 Product/Feature 已建立或所有规则已确定为前提。某项具体要求缺失时，限定符合性结论，在其余有依据的范围内检查质量。报告说明检查版本、实际覆盖、问题、依据和限制；过程中成果变化时限定结论或补查对应变化。

报告默认在对话，需留存时在相应 reports/features/ 或 reports/maintenance/。报告已交付、审核条件满足、用户人工接受是三个不同事实。发现的优先级不授予修复权限；确认的完成阻断项也不能因为审核可选而忽略。

权威边界见 专业职责规范 和 独立审核规范。

美术、音频与视觉效果资源工作台

操作手册

工作台是项目内可按需运行的 Godot 开发场景，提供单项查看/试听和事件组合预览。 它随框架复制，但不会初始化环境、设置主场景、生成 Product/Feature 或替代人工体验。

按当前任务进入

实际游戏项目须先满足 GDD 前提，并完成 环境配置，再打开所需场景按 F6。各入口独立运行，不必按顺序遍历。

现在要做什么 从这里开始 完成检查
查看候选、独立试听 查看与独立试听 知道选中了什么，当前对象绑定未改变
检查图像或音频源文件 源资源分析 结果对应正确文件，失败或未知值有说明
比较对象的素材、声音与效果 组合预览与试调 当前对象、A/B、播放与修改范围清楚
把选定参数用于实际场景 保存后验证 明确保存目标，并在消费场景查看已保存效果

四个工作台及对应消费入口集中在 示例操作导航。example_ 前缀只标识示例，不表示素材已适合当前游戏。

查看与独立试听

  1. 打开 asset_workbench/examples/single/example_workbench.tscn，按 F6。
  2. 在左侧“资源候选”筛选并选择文件，查看摘要；音频可独立试听或停止试听。
  3. 确定要使用该候选时，才点击“应用到对象 A/B”，继续在当前入口 预览与试调。

影响范围：

  • 浏览、元数据与独立试听不会修改对象资源。
  • Inspector 的“资源绑定”显示对象实际使用的文件，左侧高亮只代表候选。
  • 浏览器尺寸与时长来自 Godot 导入资源；独立试听条件不等于 Cue 的播放参数。

完成检查： 能区分候选文件与对象绑定；未点击应用或编辑参数时，草稿保持原值。首次 Cue 读取失败仍可浏览、试听和分析候选；修正文件后从“对象更多”重载恢复对象操作。

窗口与外观

  • 宽窗口为可拖动三栏，左侧列表和右侧属性各自滚动；对象信息、播放、停止与保存保留在固定区域。
  • 窄窗口通过“资源候选 / 组合预览 / 对象属性”切换。真实组合布局不重排，容不下时在预览内部滚动；布局不持久化。
  • 默认白底黑字，可切深色或在适用图像预览启用透明棋盘格。外观设置不改变素材颜色、草稿或保存结果。

项目默认视口和工作台/分析窗口均为 1600×900。编辑器嵌入时服从宿主区域，显式命令行尺寸可覆盖默认值。

分析图像与音频源文件

前置： 按 Analyzer 说明 准备依赖和项目 python_executable。创建器不安装依赖。缺少分析依赖不妨碍预览和播放。

  1. 选择候选，点击“分析候选源文件”；在独立窗口中使用“分析对比 A/B”。
  2. 先核对两侧文件名、类型和状态，再查看问题摘要、指标及图表。更换候选不会给旧结果换名。
  3. 按需查看音频峰值/RMS 包络、颜色与 Alpha 分布；滚轮缩放图表，或滚动查看详细指标。

影响范围： 分析 A/B 不改变对象 A/B、播放或保存目标。结果针对原始图像/音频，不包含导入后变化、Cue 增益、最终混音或 Shader/粒子画面，也不生成审美分数。

结果不完整或过期时：

  • 结果缺口： 短音频、静音、未支持指标和失败分别说明，不用零值代替未知。
  • 过期或不可比较： 修改分析参数后旧结果标为 STALE；版本、后端、参数或单位不兼容时停止叠图，可按当前参数同时重算两侧。
  • 重算与取消： “重分析”强制重算；关闭窗口取消其后台任务。

非文件资源、不支持格式、解码失败、超时或损坏输出会显示原因，不阻断原工作台。大图有限采样与音频预算以实际状态为准；缓存、Adapter、Schema、扩展指标及上限由 Analyzer 技术说明 承接，版本与许可见 依赖记录。

批量分析与比较

  1. 用“候选更多 → 将筛选结果加入批量分析”收集候选；也可在集合菜单指定目录，或用对象/场景更多菜单收集对应当前方案的图片和音频。
  2. 核对实际新增、已有和跳过项。原集合成员保留；间接纹理或音频 Resource 显示跳过原因，不自动展开内部依赖，也不收集 Shader。
  3. 运行批量分析，查看逐项状态和同类统计；Ctrl 选择两项同类结果送回分析 A/B 图表。

可取消运行、保存分组/规则，或显式保存结果历史。明确阈值和相对中位数偏差只提示数值差异；不据此推断语义风格。完整操作、容量限制和失败处理见 分组批量说明。

组合预览与试调

选择入口： 已打开工作台时继续当前入口；需要三对象示例时，打开 asset_workbench/examples/composition/example_workbench.tscn 按 F6。不同入口各自持有配置，不能靠切换入口转移草稿。

  1. 多对象入口先在中央点击目标，这会选中并触发它；单对象入口直接使用当前对象。
  2. 确认 Inspector 顶部对象名称和当前 A/B，再应用候选或修改右侧参数。对象之间保留各自草稿。
  3. 使用预览下方的触发、连续或快速触发检查效果；需所有对象一起播放时使用预览上方“触发全部”。

作用范围：

  • 方案切换： 对象 A/B 只切当前对象，场景 A/B 切全部对象；混用时显示“混合方案”。
  • 初始方案： 打开或重载后 A 使用已保存配置；原配置有声音且存在其他候选时，B 只换声音，静音配置保持静音。
  • 方案边界： 这些方案是效果参数试调，不切换完整 UI 布局。

停止与低频操作：

  • 停止： “停止全部”清除全部对象、延迟、循环与独立试听；“停止试听”只作用于候选。
  • 对象操作： 对象的分析、复制、恢复和重载在“对象更多”。
  • 场景操作： 场景分析、统一增益与逐文件保存在“全场景更多”。统一增益只改各对象当前方案。

完成检查： 当前对象、当前方案、资源绑定和未保存状态符合本次选择；随后按 保存后验证 检查实际消费。

Shader 与独立资源组合

打开 asset_workbench/examples/shader_composition/example_workbench.tscn，可试调外描边、溶解与无图片噪声三个预设。图片、声音与 Shader 分别替换或留空，全空配置也允许保存；单对象和普通组合入口同样支持可选绑定。

无图片时沿用白色矩形承载面，不补选图片。各对象保持独立材质和参数，源预设只读；“触发全部”从初态触发，再按各自声音/Shader 延迟播放。

目前支持 2D canvas_item 及既定强度、颜色、时序参数；没有任意参数编辑、3D、全屏后处理或多 Shader 堆叠。候选配置、参数适用性、契约与许可见 Shader 示例说明。

粒子与动画组合预览

打开 asset_workbench/examples/effects_composition/example_workbench.tscn，在 Inspector 选择粒子、Tween 或 AnimationPlayer 片段，仍只编辑当前对象当前草稿。两个组合实例展示六个对象；共用 Cue 的对象也独立持有 A/B。

图像、声音、Shader、粒子与片段分别可选；粒子可使用自己的贴图，运动目标为空时不补素材。运行实例和材质按对象隔离，动画不移动名称或选中边框。

粒子/运动重触发从头开始；声音与图标脉冲仍可重叠。持续粒子的发射时长与存活时间不同；停止全部立即隐藏并取消待播放内容，下次触发重置模拟。

预设、局部/场景坐标、组合变换和层级在原生 Godot 场景/Animation 资源中制作，工作台不提供任意轨道编辑。参数与素材来源见 粒子与动画说明。

局部管理与有限时间编排

在粒子动画入口点击“播放编排 / 循环编排”，使用各对象当前 A/B，依次播放 A 组、B 组，再让两组核心并行。播放不修改或保存 Cue；停止全部和方案切换取消后续编排与循环。

体验时注意：

  • 时间窗口： 片段截止会截断声音和粒子余尾；错过的窗口不会补播，尚未结束的窗口从效果开头触发。
  • 播放预算： 示例只允许三个受管对象同时播放，延迟音频也占预算；它不是 GPU、显存或全场景声部保证。

编排在原生 Godot Inspector 制作，工作台不提供时间轴编辑、暂停或跳转。消费场景可试验分组触发/取消和优先级。局部 Manager、句柄、时钟与 API 的实现说明集中在 管理与编排说明。

保存后验证消费场景

保存前： 看固定底栏中的目标文件与影响范围。保存当前方案只写当前 Cue，不修改源图片、声音或共享预设；所有引用同一 Cue 的消费场景会读到该保存结果。

  1. 点击“保存当前方案”，核对成功或冲突消息；需要完整路径时查看并复制保存目标。
  2. 用“对象更多 → 打开消费场景”，或按 入口导航 打开对应场景按 F6。
  3. 实际观看、操作和试听，确认消费场景读到已保存效果；未保存的 A/B 草稿不会传入。

保存全场景： 沿用逐文件保存，不是多文件事务。

  • 共用 Cue： 多个对象共用 Cue 且内容相同时只写一次。
  • 分歧或冲突： 内容分歧或磁盘冲突时跳过并说明，其他文件仍可能成功。
  • 内存草稿： 单对象保存不替换其他对象的内存草稿。

重载： 明确确认后丢弃当前对象两份草稿。需要保留试调时先保存选定方案，不能把重载当作撤销最后一步。

效果组合的消费入口为 effects_composition/example_consumer.tscn，可检查不同摆放、旋转和缩放。正式导出还应按 消费接入与导出 包含实际引用、运行脚本与许可，并从独立包验证；F6 成功不证明导出依赖完整。

工具与实际游戏的关系

完整界面方案由 Agent 在已授权 Feature 或实验中编写独立 .tscn；工作台只辅助资源与反馈试调，不提供自然语言场景生成、通用拖拽编辑或任意节点属性修改。示例布局不是项目已确认 UI，试调参数也不会自动写入专业规格。

  • 复用与写回： 实际对象优先复用已有表现组件、Scene/Resource 与音频服务，并有唯一明确写回目标。
  • 示例模型： FeedbackCue 是示例提供的可选媒体、粒子和有限动画模型，不要求游戏整体改造。
  • 预览隔离： 需要隔离掉落、存档、网络和业务 Autoload 副作用，仅选择场景文件不能证明它独立安全。

源资源、Godot 导入、工作台画面与正式消费场景各有验证边界；参数明确的普通替换无需完整试调链，工作台也不新增 Feature 阶段或完成状态。专业要求与制作边界见 专业来源与资源。

  • 理由与依据： 引用适用工程规则并解释用途，不复制整本规则。

需要实施指导时，implementation-guidance-godot 也使用这份 docs/features/F0XX-design.md。首版只支持已有 Feature，包括工程 Feature；不额外生成带模型名、日期或“guide”后缀的副本。内容说明关键约束如何影响设计、接口与生命周期、必要依赖顺序及验证理由，不预先规定每个函数怎么写。引用相对于设计稿所在目录，例如 ../../agent-rules/00-core/change-scope-and-ownership.md。

实施任务在 Stage 1 提出方案和未决选择，在 Stage 2 取得有效批准后保存；已有设计就更新原文件。若仅授权交付指导文档，只沿用批准后的设计保存契约，不启动完整 Stage 2、不推进实施状态或测试计划。明确委派顾问时，顾问只可写获准的设计稿，Feature notes 链接和 Progress 等记录由原负责人按本次授权维护。设计属于解释材料，不替代需求、规则、AC 或 Registry；其修改照常参与当前证据指纹，不能把旧验证自动当成新设计已通过。

架构地图在源码难以表达模块关系时才有价值。总览区分实际直接协作与允许的依赖方向，说明谁创建/释放状态、谁有权修改及关键入口。模块 README 已能导航时链接即可，不预设 Bootstrap 或 Autoload。运行说明可按需包含触发、状态变化、Godot 生命周期和失败路径。

对照 逻辑与表现职责，架构记录真实协作而非再次定义玩法。例如 GDD 保存购买条件，UI 保存商店操作，表现文档保存获得反馈；架构说明哪个对象处理购买、谁维护余额和背包、界面如何读取状态及响应结果。一次任务改变这些连接时，可在局部设计展开必要理由；简单调用清楚可见时，不为两层模型另建架构文档。

图中的箭头要分清代码依赖、装配、继承、消息或时序；静态引用搜索不证明动态加载、运行时 Signal 和真实状态归属。观察、推断、建议和已实现行为分别表述。地图更新职责、路径、入口和理由，旧设计正确记录过去时保留历史，不改成一直如此。

设计新核心对象或调整结构时，实际判断来自已确认行为、状态与生命周期、调用方负担及真实依赖。比较复用、不改、局部修正、删除/合并与必要新增；API 更短、文件更少或采用模式本身都不是收益。枚举状态、Command、序列化或新管理层只服务实际用途，不为假想未来预建体系。具体方法见 架构规范。

ADR 的阈值

ADR 使用 docs/architecture/adr-NNNN-<slug>.md，同时考虑：

  • 撤销是否有实质成本。
  • 仅靠源码和当前结构是否难以恢复原因。
  • 是否确有候选与重要取舍。

普通局部选择留在设计或 notes；独立架构讨论可以保存已获准 ADR，不必虚构 Feature。

记录问题、约束、候选、决定、收益、成本、依据和有用的重新考虑条件。Proposed、Accepted、Superseded 是普通文档状态，后者保留旧理由并链接替代决定；Accepted 说明决定已确认，不证明代码运行通过。已有具体授权直接沿用，不加额外批准。

探索结果与工作目录

wayfinder-godot 沿用本页的文档分工：一次性讨论可以留在对话；需要获准续接记录时，在 Progress 保存当前问题、未决项、下一步与材料链接，局部决定进入 Feature notes 或设计。外部结论归研究资料，真实运行归现有报告位置；重要技术决定仍须满足 ADR 阈值，采纳的游戏规则与交付边界回到各自 GDD/Product，不另建探索台账或默认报告。

使用 worktree 后，需要续接的信息还包括实际工作目录和当前版本，让下一次工作能找到正确现场。目录中的源码、被忽略的本机材料和运行证据仍各有归属；仅有代码提交不能证明另一目录拥有相同数据或证据。记录结论不等于批准采用某套实现，采用成果也不自动授权清理其目录，具体准备与整合由对应 Skill负责。

项目规则与领域规则

  • 根 AGENTS： 规则入口。
  • docs/project-rules.md： 开发约束、协作与工程原则；需要游戏设计边界时引用 GDD 所属正文。
  • agent-rules/： 按领域提供工程语义。
  • methodology/： 流程和验证。

领域可叠加，例如测试 .gd 同时遵循脚本与测试规则。按当前修改读取领域 README 的相关路由，不每轮通读全部目录。

领域 规则目录
通用、GDScript 00-core/、10-gdscript/
Scene、Resource、Shader 20-scenes/、21-resources/、30-shaders/
项目配置、导出 40-project-config/、41-export-config/
数据、资产、测试 50-data-files/、60-assets/、70-tests/

规则可能过时或范围过宽。怀疑错误时说明具体条款、事实与影响，将代码符合性和规则正确性分别判断；合理的 PREFER 偏离不必自动改规则。不能因个人偏好暗中豁免约束，也不把每个 Bug 教训升级为硬规则。

增改删规则的写前自检保留在对话；一批可合并说明但各项可对应：

  • 变化与依据： 说明原文和变化、真实依据、长期价值与归属。
  • 范围与影响： 说明强度/范围、重复或冲突、下游影响。
  • 判断与授权： 说明结论及已有授权。
  • 特定修改： 删除解释承接位置或不再需要的原因，措辞/链接修订说明语义和强度不变。

没有规则变化不生成报告，不新建规则台账。

规则变化先处理当前任务的实际影响，沿用具体授权；新决定才等待用户。原 Feature 内辅助文档不另起“必须清空工作区”的任务。适用记录在最终验证前定稿，较晚采纳也检查失效依据。唯一细则见 规则增量维护。

调研与项目知识

调研按问题需要进行，可直接查询或委派 researcher，不是每个 Feature 必经阶段。涉及引擎/API 写明实际版本，核对所读页面；stable/latest 不代替版本号。一手来源事实、项目推断、本地实测分别说明，损坏抽取或遗漏代码保留原文链接及限制。

有长期价值时写 docs/research/<明确主题>.md，同主题优先维护已有报告，重要结论变化保留日期、原因与被引用历史。最低信息为问题与范围、日期和适用环境、结论、依据、建议、未知；角色文件维护详细报告约定。采纳的游戏设计回到 GDD，交付安排回到 Product，其他决定回到专业来源、设计或 ADR，不让研究建议自动变成要求。

知识目录初始有 godot-runtime/、gdscript/、debugging-testing/、tools-pipeline/ 主题索引。

  • 保存与索引： 每条独立经验保存一个 Markdown，索引链接和简述；按真实内容扩展，不每个 Feature 建目录，不多处复制。

  • 查阅与续接： 规划、调试、实现或审核按问题定位相关已有经验并核对版本条件；空索引不阻塞，续接复用有效已读内容。

  • 经验内容： 说明场景、有效做法或根因、适用范围与真实依据；成功经验不必编造根因。Feature notes 保存原事件，知识提炼方法并链接原件。

  • 落盘授权： 只读请求不因此获得落盘权限，有价值的已授权知识在收尾提交前保存。

  • 验证影响： 纯知识/调研 Markdown 不使业务测试指纹失效，可执行文件、规则和契约仍按实际范围检查。

报告与历史

工具原件使用固定路径，自定义结果按 目录说明 放置；正式证据和临时输入分开。直接引用 gdUnit 原件，额外控制台日志只补原件没有的信息，不新建报告总索引或用文件名 final 代替有效结果。

  • 临时材料： 需要跨任务保留时，在现有 notes/Progress 说明用途和结束保留条件。
  • 证据保留： 当前验收、未解决失败、后续工作、历史与知识引用需要的证据继续保留。
  • 归组与迁移： 核对生成命令、读取脚本和引用，不能只移动文件；工具原件不随意迁移。
  • 清理范围： 清理是需明确范围的维护动作，旧、未跟踪、后有成功或目录名 scratch 都不等于可删除。

Progress 保存真实停点和必要链接，不能由“下一步实施”推断批准。正式完成的执行历史归档一份到 docs/progress/<key>.md，已有记录先读，保留原文和证据；未解决事项仍留当前交接，不每阶段重复复制报告。代码提交不保证默认忽略的报告存在于另一目录或机器。

任务续接的信息契约

交接正文按以下主题保留信息：

  • 当前现场： 真实项目路径、分支和现有差异。
  • 任务与决定： 目标与最新要求、有效决定/授权、实际阶段。
  • 验证与后续： 已做和未做的验证、证据及下一步。

未知保持未知，未结束命令说明已知状态。原对话交接后停止实施，接收方在该任务的目标工作目录核对实际文件再继续；普通同目录续接沿用原目录，已有明确 worktree 目标时以该目标为准。

会话摘要帮助定位，不替代权威文件；不要求为换对话清空现场、提交半成品、另开分支、建 worktree 或重跑全部检查。具体交接步骤的临时只读/输出限制不永久覆盖接收方后续已授权任务。这里不建立 Handoff 文件、CONTEXT.md 或平行任务状态表。

权威依据：产物生命周期、项目术语、架构规范。

需求、任务与执行主体

术语 本框架中的含义与边界
GDD Game Design Document，游戏设计正文；在 docs/gdd/ 持续维护定位、体验与反馈目标、核心循环、系统规则、内容与版本设计范围，是项目开发前提
Product 依据 GDD 划定的可验收交付单元，可覆盖一个系统、其中一部分或跨系统体验；不重复定义游戏规则

Feature 具有范围、验收条件和状态的开发任务；工程 Bug、重构和维护也可按规范建为 Feature
AC 验收条件（Acceptance Criteria），说明目标行为如何被客观判断；不等于一条测试用例
Bug 实现偏离仍有效的已确认要求或契约；用户改变要求不自动归为 Bug
工程变更 修复、重构或维护已有系统的任务类型；具体分类由工程变更规范决定
Stage Feature 执行规范中的阶段定位，不是新增的逐阶段审批或自动状态机
Goal 承载持续授权工作的目标；Goal 停止或预算耗尽不证明 Feature 完成

Skill 围绕一个明确职责组织的专项方法及按需资料；多个场景可以使用同一方法
researcher 按问题收集外部资料并区分事实、推断和未知的调研角色
independent-reviewer 在指定范围独立形成审核结论的角色；角色配置存在不证明实际独立实例已运行
提示词 / Prompt 用户发送给 Agent 的当前任务输入；集中库中的每条入口只对应一个具体场景
公开接口 / API 调用方依赖的参数、返回值、行为及失败约定；影响消费者时须核对实际契约

游戏职责与协作

术语 本框架中的含义与边界
游戏逻辑层 负责游戏规则、业务状态与有效结果；可使用真实 Godot 能力，不要求所有逻辑脱离引擎
游戏表现层 负责玩家感知与交互反馈，包括界面、动画、特效、声音和镜头；可以维护显示过渡等自身状态
游戏表现文档 记录一次具体表现的过程、标准要求、候选方案、采用关系及实现与验收入口；不等于表现层全部资料
行为请求 对游戏操作表达意图，由负责该规则的逻辑判断是否允许及实际结果
游戏状态 当前游戏事实，如余额、生命值、库存；有明确所有者，区别于悬停或动画进度等表现状态
一次性事件 某次已发生变化的通知或结果，如本次购买成功；读取当前状态不代表需要重放历史反馈
跨层功能 同时涉及游戏逻辑、表现及双方接入的功能范围；不新增任务类型、阶段或强制拆分方式

来源：游戏组织指南、架构规范、专业来源约定。两层用于理解游戏职责；工具、环境、测试与构建仍按共同工程支持说明。

Git 提交 对选定文件状态的本地版本记录；提交不等于测试通过、人工接受或正式交付

Scene / 场景资源 Godot 的场景文件及其节点结构；文档中的“使用场景”则指用户情境，必要时写全称区分
Resource / 资源对象 Godot 可被引用、共享和保存的数据对象；“素材”更侧重外部图像、音频等输入文件
Shader 本项目使用的着色器程序；工作台当前支持范围以实际工具契约为准
Signal / 信号 Godot 对象间的事件通知机制；不能仅凭静态文本搜索推定所有连接关系
Autoload 通过项目配置自动加载的对象；不是所有共享能力都必须采用的组织方式
UID Godot 资源身份标识；与文件路径相关但不应当作同一字段随意替换
导入元数据 / 导入缓存 .import 保存源资源的导入配置，.godot/ 保存生成缓存；两者不能一并当作可删除垃圾
Cue 工作台及消费示例用于保存所选资源与表现参数的配置资源；不等于源素材本身
工作台 编辑期查看、试调、比较和保存资源组合的工具；临时草稿与已保存 Cue 分开
Analyzer / 源资源分析器 对图像、音频源文件进行分析的工具；结果不替代渲染效果、听感或运行性能测量
消费入口 读取已保存 Cue 并在运行时使用它的场景或代码；区别于工作台编辑入口
A/B 比较 在规定条件下对照两份候选或参数；具体比较对象需写明

来源：工程领域规则、工作台与消费示例。这里只解释项目用语，不代替 Godot API 文档。

动词性术语

动作 应表达的结果与边界
创建 产生新的项目或对象；创建器完成复制不代表环境已就绪
初始化 / 配置 建立或调整所需初始状态、工具路径等；就绪仍以对应实际检查为准
预拆分 在 Product 总览检查约定交付范围、粗略边界、来源与依赖；不提前生成后续 Product 正文或 Feature
细化当前 Product 轮到该交付单元时，依据最新 GDD 和已完成工作写明本次交付边界与衔接
规划 Feature 一次覆盖当前 Product 的完整必要范围，确定任务、依赖、AC 和验证方式；规划完成不等于实现完成
实施 / 实现 在有效授权内改变代码、资源或配置，达到当前目标
诊断 / 定位 用证据确认问题及其原因；尚未证明的解释称为假设，不自动扩大为修复
修复 使偏离既有要求的行为恢复预期；不通过降低 AC 或改历史验收结果达成
重构 在保持约定行为的前提下改善结构；有具体收益与相应回归依据
优化 必须说明优化对象与比较依据，例如性能预算或查找成本；“优化了”本身不是可验证结果
迁移 / 替换 按明确方案改变承载位置或实现并核对消费者、引用及保留的数据；不是自动升级承诺
接入 / 消费 将已确认素材、资源或能力接到实际使用位置；收到文件不等于接入完成
同步 更新明确受影响的直接来源与引用；框架不因此自动更新已有游戏项目
验证 用适用检查判断某项要求是否成立；需要说明对象、范围与结果
复验 对修复或内容变化后的对象再次执行必要检查；不能用旧版本结果替代
审核 / 审查 根据证据评价内容、实现或职责并形成结论；不自动获得修改权限
验收 按约定条件接受当前交付物；人工验收须有实际用户结果
完成 / 正式交付 满足所属流程的出口；Feature 以规定状态及完成记录为准，不只看测试、提交或试玩
提交 创建 Git 版本记录；“提交到远端”应明确称为推送，不能混用
暂停 / 续接 保存真实停点 / 从已有文件、有效授权和记录继续；不重新推定旧验证仍有效
归档 / 清理 保存历史 / 移除已获准且不再需要的对象；未跟踪或暂存目录名称不授予删除权限

动作的授权与完成条件仍按维护约定、项目执行规范及所属场景执行；本表只统一表达。

状态、形容词与副词

只记录会影响执行判断或经常产生误解的词，不建立普通形容词词典。

用语 使用要求
已确认 / 已批准 写清被确认的是需求、方案、范围还是验收结果，不能互相代替
已通过 / 有效 指明检查对象、对应内容和范围；工具退出码为零不等于整个流程完成
待定 / 待验收 / 阻塞 分别表示尚缺决定、尚缺适用人工结果、存在不能继续的前置；不要统称“未完成”而隐藏原因
失效 / 过期 当前内容、版本或条件已使旧依据不再适用；日期较早本身不能证明失效
最小完整 完整解决本次目标所需的最小影响范围；不是文件最少或行数最少
自动 / 人工 表明谁实际完成动作；“可自动完成”不证明已经运行。Agent 不得编造人工观察或代替用户作出接受决定，可以如实记录用户的实际结果
正常 / 成功 / 没问题 不单独作为完成标准；改为具体可观察的状态或检查结果

新增或改义时先核对现有权威来源、别名和实际消费者，再更新本页及必要引用。具体玩法词汇、场景完整步骤、字段枚举和工具参数仍保留在各自所属文件，不复制进词表。
