# 已有模块的玩法要求变了，需要更新需求

[返回场景索引](../../scenario-index.md) · [执行步骤](#执行步骤) · [完成标准](#完成状态与验证标准)

## 触发场景与使用时机

已有模块的玩法要求变了，需要更新需求。

需要的材料：

- 模块与原要求：所属模块、原要求。
- 变更与影响：新决定、影响范围。

## 前置条件与适用范围

项目已有真实 GDD，需要修改已确认的玩家行为，并核对相关交付范围。

## 执行步骤

使用[集中提示词库](<../../../prompts/godot-development-prompts.json>)中的“Godot 项目开发 → 需求设计 → 已有模块的玩法要求变了，需要更新需求”。填入上述材料；已有对话直接补齐输入，不必重发入口。当前 Agent 使用 [design-gdd](../../../../../project-source/skills/design-gdd/SKILL.md) 处理玩法，使用 [product-author](../../../../../project-source/skills/product-author/SKILL.md) 处理交付影响。

**S1｜核对行为差异**

当前 Agent 使用 design-gdd 只补问实质未决的玩法差异，区分新需求与对既有要求的 Bug；交付取舍才使用 product-spec-elicitor。

**S2｜更新所属来源**

design-gdd 将确认的整体设计变化写回 GDD，数值主题由 [design-balance](../../../../../project-source/skills/design-balance/SKILL.md) 在授权内直接维护；product-author 维护相关 Product 交付范围与引用。其他专业细节由所属方法补足，GDD 已有细节直接引用，未轮到的 Product 只更新预拆分。

**S3｜交接计划影响**

列受影响已有 Feature 与尚未规划范围，来源按项目规则提交后交 feature-sync。

## 步骤产出与状态变化

| 步骤 | 可继续的依据 |
| --- | --- |
| S1 | 旧新意图和范围明确 |
| S2 | 正式来源准确表达新决定 |
| S3 | 来源变更与计划同步职责分开 |

## 资源与文件影响

GDD、Product 交付范围、必要专业来源与链接修改；历史 Feature 验收不重写。

## 阻塞、异常与范围变化

未确认的新想法不自动进入需求；明确旧要求的 Bug 走修复。

## 完成状态与验证标准

新要求已成为可核实的正式来源，影响范围和后续同步入口明确。
