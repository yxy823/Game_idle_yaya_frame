# 只审核 GDD、专业文档、Product 与 Feature 的衔接

[返回场景索引](../../scenario-index.md#只读专项审核) · [通用模板](专项审核通用模板.md)

## 触发场景与使用时机

GDD、Product 和 Feature 重复保存同一设计，或讨论过的范围限制没有进入后续规划；或者起草 GDD 时，不知道还没建模的数值、游戏语言和文本键、数字显示这类内容先写在哪里、写成什么。

## 前置条件与适用范围

本专题回答的问题：一项游戏需求从 GDD 到 Product、再到 Feature 时，设计内容、范围边界和来源能否完整、无歧义地传递，且每类信息只在一处维护；起草 GDD 时就要用到的数值、本地化和表现内容，是否写明了默认值、占位写法和归属。

具体范围、必读来源和检查要点都写在提示词里，无需填写参数。审核只读，不修改任何文件。

## 执行步骤

**S1｜拼接并发送提示词**

1. 打开一个新对话；这个对话不能参与过被审内容的修改。
2. 复制[Yaya 框架维护提示词库](../../../prompts/yaya-maintenance-prompts.json)中的「只读专项审核 → 专项审核通用模板」。
3. 把「只读专项审核 → 只审核 GDD、专业文档、Product 与 Feature 的衔接」的内容粘贴到模板末尾的「本次专题」下方。
4. 发送。

**S2｜等待审核报告**

审核 Agent 按专题范围只读核对，在对话中交付报告。需要留存时，明确要求保存到 `tmp/reports/<任务>/`。

## 完成状态与验证标准

收到按通用模板结构交付的报告：先逐步写出 2–3 个具体任务的推演，问题清单分为已确认问题、有依据的风险和可选改进，每项都能定位到原文；没有问题时列出核查过的入口。报告包含两个推演：一个简单需求从 GDD 条目追到 Product 范围、Feature 字段和修订记录；一个起草 GDD 时就涉及数值、玩家可见文字和数字显示的需求，写明每项内容写在哪个文件、之后由哪个 Skill 接手。每一步附依据原文。报告只给建议，不包含修复。

## 流程关联与衔接关系

不确定该从哪里查起时，先用[框架好像有问题，先判断从哪里查起](<框架好像有问题，先判断从哪里查起.md>)。拿到报告后，需要判断哪些意见值得改时，使用[收到外部审核意见，先核实哪些值得修改](<../改完检查/收到外部审核意见，先核实哪些值得修改.md>)；确定修复范围后，使用[框架出现可复现问题，需要修复](<../出了问题/框架出现可复现问题，需要修复.md>)。
