# 想检查本地框架是否自洽，先做静态审核

[返回场景索引](../../scenario-index.md) · [执行步骤](#执行步骤) · [完成标准](#完成状态与验证标准)

## 触发场景与使用时机

框架积累了一批修改，或准备拿它创建新项目之前，想由独立审核确认规则、Skill、工具、手册和空白项目源材料之间没有互相矛盾或断开的地方。需要的材料（都可选）：

- **检查范围**：不填时整体审核整个框架与全部空白项目源材料；要限定时写模块、路径、提交区间或关注点。
- **对照基线**：旧提交或旧报告路径，用来区分新出现、仍存在和已解决的问题；没有就填“无”。
- **具体任务**：2–3 个要走一遍的任务。不填时由审核者按[审核的判断方法](../../../../maintenance/design-guidelines/reviews-and-reports.md#审核的判断方法)挑选。
- **报告位置**：默认在对话中交付；要保存时写 `tmp/reports/<任务>/` 内的文件路径。

## 前置条件与适用范围

本次只读审核，不实施修复；被审文件、配置和已有游戏都不修改，也不生成项目、运行测试或启动 Godot。

## 执行步骤

使用[集中提示词库](<../../../prompts/yaya-maintenance-prompts.json>)中的“Yaya 框架维护 → 整体体检与整理 → 想检查本地框架是否自洽，先做静态审核”，按上面的材料填写 `${1}` 到 `${4}`。当前 Agent 作为主 Agent，把审核委派给独立新上下文的子智能体，只负责明确范围、提供材料、核对报告覆盖和归档，见[正式审核的独立性](../../../../maintenance/design-guidelines/reviews-and-reports.md#正式审核的独立性)。

**S1｜固定检查基线**

独立审核 Agent 核对当前提交和真实差异，按范围建立生产入口、规范与调用者清单。

**S2｜走查具体任务并追查实际契约**

独立审核 Agent 按[审核的判断方法](../../../../maintenance/design-guidelines/reviews-and-reports.md#审核的判断方法)把每个具体任务逐步走一遍：读哪个提示词或文档、调用哪个 Skill 或工具、写哪个文件或产出什么、在哪一步卡住或要猜。已确认的取舍也可以质疑，但要用具体任务说明在哪一步造成什么代价。

再逐对象读取正文与实现，补查任务没走到的部分，检查读写方、完成语义、复制边界和说明关系；不能用目录枚举代替审查。AGENTS.md、Skill、任务提示词与条件规则按[规则与提示词文件](../../../../maintenance/design-guidelines/instruction-files.md)核对，脚本和其他材料按各自依据审查。

整体审核按[审核覆盖与结论](../../../../maintenance/design-guidelines/reviews-and-reports.md#审核覆盖与结论)分五类给出结论：文档职责、文本编写、Skill 职责、脚本职责、提示词与场景。有限抽查只能给出相应范围的结论。

**S3｜交付独立结论**

独立审核 Agent 以任务走查为报告主体，区分已确认问题、静态推断与待运行验证，列最小调整及复验建议；被审范围有还没实际用过的新机制或新工具时，按审核的判断方法列出需要的试用：每项写明任务、目标项目、被测文件和要观察的结果。五类分别写明覆盖、依据和结论，未发现问题、证据不足与未涉及明确区分；详情只展开一次。默认在对话中交付，给了路径时只写这一份报告。

## 步骤产出与状态变化

| 步骤 | 可继续的依据 |
| --- | --- |
| S1 | 被审提交、未提交差异和覆盖范围已写明 |
| S2 | 每个具体任务都有逐步走查；每项发现有文件与行号或符号 |
| S3 | 报告含任务走查、五类结论、未验证项、需要的试用和证据限制 |

## 资源与文件影响

被审源与原始证据只读；只在指定路径写这一份报告，不提交。

## 阻塞、异常与范围变化

证据不可用时收窄结论；不把静态推演写成真实运行，静态审核结论也不能代替新机制或新工具的实际试用。不能实际委派时说明独立审核未完成，不以主 Agent 的自查替代。

## 完成状态与验证标准

有当前文件依据、以具体任务走查为主体的独立审核报告已交付，未修改被审源。
