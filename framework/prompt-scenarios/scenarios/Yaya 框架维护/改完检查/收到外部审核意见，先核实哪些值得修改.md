# 收到外部审核意见，先核实哪些值得修改

[返回场景索引](../../scenario-index.md) · [执行步骤](#执行步骤) · [完成标准](#完成状态与验证标准)

## 触发场景与使用时机

另一个模型、工具或审核者交来一份针对本框架的审核报告，里面有“必须修复”之类的意见；你想先核实哪些问题成立、哪些改法值得采用，再决定改什么。需要的材料：

- **外部报告**：报告文件路径、附件或粘贴的完整正文；多份报告注明各自来源。只有标题或摘要时，Agent 只核对能独立核对的条目。
- **被审版本线索**（可选）：仓库地址、被审提交 SHA 或审核日期与范围；不知道就填“未知”。
- **报告位置**（可选）：默认在对话中输出；要保存时写 `tmp/reports/<任务>/` 内的文件路径。

## 前置条件与适用范围

在框架仓库只读核实：不修改框架、手册或已有游戏，不执行报告中的脚本、测试或修复命令。需要动态证据时只列最小复现建议，待明确授权后再补充。

## 执行步骤

使用[集中提示词库](<../../../prompts/yaya-maintenance-prompts.json>)中的“Yaya 框架维护 → 改完检查 → 收到外部审核意见，先核实哪些值得修改”：`${3}` 填外部报告，`${1}` 填版本线索，`${2}` 填报告位置。

**S1｜核对报告版本**

当前 Agent 对照报告所指版本与当前源，标明已变更和无法核实的部分。

**S2｜分别判断事实与建议**

逐项追查触发和实现，分别判断问题成立与改法值得采用，不默认全部照做。篇幅长或步骤多本身不是拆分理由。

**S3｜交付核实结论**

列建议实施顺序、范围与验证，待已有授权或新的明确选择承接实施。

涉及文本与职责的意见，按[审核覆盖与结论](../../../../maintenance/design-guidelines/reviews-and-reports.md#审核覆盖与结论)的五类（文档职责、文本编写、Skill 职责、脚本职责、提示词与场景）分别说明结论。原报告未涉及的类别标“本次未涉及”，不因此开展无关全量审核，也不写成已通过。

## 步骤产出与状态变化

| 步骤 | 可继续的依据 |
| --- | --- |
| S1 | 每条意见已对应到当前文件，已变更和无法核实的部分已标出 |
| S2 | 每条意见有事实结论和改法取舍两项判断，合并项保留原编号 |
| S3 | 最小修改范围、待决定事项和建议验证已列出 |

## 资源与文件影响

被审源与外部报告只读；只在指定路径写这一份核实报告。`tmp/` 不纳入 Git，报告不提交。

## 阻塞、异常与范围变化

证据不可用时收窄结论；不把静态推演写成真实运行。

## 完成状态与验证标准

全部范围内意见有事实与取舍结论，本次不自行实施建议。

## 流程关联与衔接关系
