# 想查哪些反复出现的问题和操作值得做成脚本

[返回场景索引](../../scenario-index.md) · [执行步骤](#执行步骤) · [完成标准](#完成状态与验证标准)

## 触发场景与使用时机

同一类错误或人工核对在提交、试用或子智能体派活中一再出现，例如多次补交同类文件、多次纠正同一种措辞、子智能体多次越过派活约束；想先弄清现有脚本拦住了哪些、漏了哪些，再决定要不要新增或删除脚本。

需要的材料：

- **关注线索**：想重点核对的问题类型或时间范围；不提供时覆盖全部证据来源。问题类型只决定重点核对什么，不缩小证据范围；给了时间范围时，git log 和会话记录按这个范围取，否则取全部历史。

## 前置条件与适用范围

- 本次只交付审核报告，不修改、不新增或删除脚本，不运行仓库中的脚本或测试，不做 git 写操作。
- 问题只取自有记录的证据：git log、`tmp/` 下的试用日志与审核报告、Agent 记忆目录、本仓库与试用项目的会话记录，以及 Codex 会话记录。记忆目录与本仓库会话记录在作者本机的 `C:/Users/89523/.claude/projects/D--A-Games-Game-idle-yaya-frame/` 下；试用项目的会话记录在同一上级目录中与项目路径对应的目录，试用项目按用户指定或 `tmp/` 下试用日志确定；Codex 会话记录在 `~/.codex/sessions`。读不到时报告缺口。
- 是否值得做成脚本，按[何时把临时脚本做成工具](../../../../maintenance/design-guidelines/skills-and-scripts.md#何时把临时脚本做成工具)判断。
- 只想为一类工作设计处理方法、不涉及脚本覆盖时，改用[同类工作会反复出现，先设计处理方法](同类工作会反复出现，先设计处理方法.md)；只复盘一次任务的返工原因时，改用[当前任务反复返工，先复盘原因](当前任务反复返工，先复盘原因.md)。

## 参与角色与职责边界

- **审核 Agent**：在没有参与过被审脚本或规则修改的新对话中执行，读取证据、枚举脚本并形成结论。用户要求正式独立审核时，交给独立子智能体，见[正式审核的独立性](../../../../maintenance/design-guidelines/reviews-and-reports.md#正式审核的独立性)。
- **用户**：报告交付后选择要实施的候选；报告建议本身不是实施授权。

## 执行步骤

使用[集中提示词库](../../../prompts/yaya-maintenance-prompts.json)中的“Yaya 框架维护 → 改进做事方法 → 想查哪些反复出现的问题和操作值得做成脚本”，填入关注线索。当前 Agent 使用框架维护规则执行，不启动生成项目的执行 Skill。

**S1｜枚举现有脚本**

审核 Agent 按实际目录列出框架维护侧（`framework/` 下各 `tools/`、`.githooks/`、`.claude/settings.json` 中的钩子）和分发侧（`project-source/tools/`、`project-source/defaults/` 下的开发工具、框架自己维护的插件）的脚本，从 README、钩子配置和测试说明确认每个脚本的触发时机。入口脚本每个一行，共享模块、测试夹具和调试台按目录各写一行。第三方插件按[编辑器插件版本与兼容性记录](../../../../maintenance/dependencies/editor-plugin-versions.md)的登记只列名称，带 Yaya 补丁的注明补丁，不评价插件本身。

**S2｜从证据整理反复出现的问题**

审核 Agent 检索 git log 中的 fix 与「修正」类提交、`tmp/` 下的试用日志与审核报告、记忆目录和会话记录，整理用户纠正、子智能体违反派活约束、提交钩子拒绝等记录。同一类问题第二次出现即算反复出现，与[何时把临时脚本做成工具](../../../../maintenance/design-guidelines/skills-and-scripts.md#何时把临时脚本做成工具)的触发条件一致；同一事件出现在提交、记忆、会话多处时只算一次。子智能体是否违反派活约束，拿首条派活消息与它的工具调用对照：派活本身互相矛盾的记为派活问题，不算子智能体违反；主 Agent 自己的违反同样记录，Codex 拿提示词与执行的命令对照。每条问题写出现次数和证据位置；会话记录按关键词检索时写明检索词和覆盖范围。

**S3｜对照覆盖并提出候选**

审核 Agent 把问题与脚本逐一对照，标出已覆盖、部分覆盖（漏在哪一步或哪类输入）和没有覆盖。只对反复出现、判断规则确定、人工核对容易漏的问题提出候选脚本，按「出现次数 × 漏过代价」排序并写理由，写明检查内容、所在 `tools/` 目录、触发方式，以及为什么改规则文字或扩展现有脚本不够。PreToolUse 拦截、权限 deny 规则、记录或统计 Agent 动作的方案属于「不监督 Agent 的每个动作」排除的做法，不提出；检查提交内容或在用户输入时给出提示的钩子不在此列。需要判断力的问题单列为不适合脚本化。同时列出没有调用方、与规则重复或可以删除的现有脚本。

**S4｜走查并交付报告**

审核 Agent 至少拿 2 个具体问题走一遍：有对应脚本时它在哪一步拦住问题，没有它时问题在哪一步漏过。覆盖表和走查中，静态推演与实际运行确认的内容分开写。然后在对话中交付报告；用户明确要求保存时写到 `tmp/reports/script-candidates/`，文件名带日期后缀。

## 步骤产出与状态变化

| 步骤 | 可继续的依据 |
| --- | --- |
| S1 | 每个脚本有作用和触发时机，触发方式能回到配置或调用方原文 |
| S2 | 每条问题有次数和可定位的证据；读不到的来源已记为缺口 |
| S3 | 覆盖表、候选脚本、不适合脚本化的问题和可删除的脚本都有依据 |
| S4 | 至少 2 个走查已写出，报告已交付 |

## 资源与文件影响

- **只读**：仓库中的脚本、钩子配置、README、测试说明、`tmp/` 下的日志与报告、只读 git 查询（如 log、show、diff、config --get），以及仓库外的记忆目录、本仓库与试用项目的会话记录和 Codex 会话记录。
- **输出**：对话中的审核报告；用户要求保存时才写入 `tmp/reports/script-candidates/`。检索会话记录用的一次性脚本放在系统临时目录，不进仓库。

## 阻塞、异常与范围变化

记忆目录或会话记录读不到时，说明缺口，继续用 git log 和 `tmp/` 完成能独立判断的部分。需要运行脚本才能确认的触发行为或检查结果，列为证据缺口，不在本入口运行。

## 完成状态与验证标准

报告包含脚本清单、反复问题清单、覆盖表、候选脚本与不适合脚本化的问题、可删除的现有脚本、至少 2 个走查和证据缺口；每条结论能回到具体证据。仓库文件未被修改，候选脚本没有实施。
