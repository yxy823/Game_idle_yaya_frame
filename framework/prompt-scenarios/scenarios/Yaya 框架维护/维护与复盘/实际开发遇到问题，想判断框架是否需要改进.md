# 实际开发遇到问题，想判断框架是否需要改进

[返回场景索引](../../scenario-index.md) · [执行步骤](#执行步骤) · [完成标准](#完成状态与验证标准)

## 触发场景与使用时机

在某个游戏项目里，Codex 等 Agent 卡住、反复重试、做了不该做的事，或提出“框架应该改”；你把它的输出转到框架维护对话，想先判断问题出在框架、项目、环境还是 Agent 执行。需要的材料：

- **开发输出**：粘贴原 Agent 的输出和相关原始日志，或给出附件、文件路径。没有正文时 Agent 会请你补充，不凭标题分析。
- **背景线索**（可选）：原任务与授权摘要、项目路径、版本或提交；只填已知的，项目文件和 Git 中能读到的不必另外整理。
- **关注点**（可选）：想判断的具体疑问；不填时围绕反馈反映的实际问题分析。

## 前置条件与适用范围

在框架维护仓库只读、静态归因：不重跑原项目开发，不修改框架或游戏文件，结论在对话中交付。需要动态证据时只提出最小复现和所需环境，按另行明确的运行授权执行。

## 执行步骤

使用[Yaya 框架维护提示词库](<../../../prompts/yaya-maintenance-prompts.json>)中的“Yaya 框架维护 → 维护与复盘 → 实际开发遇到问题，想判断框架是否需要改进”：`${3}` 填开发输出，`${1}` 填背景线索，`${2}` 填关注点。

**S1｜还原反馈现场**

当前 Agent 完整读取实际提供的输出和日志，区分原用户目标与授权、可核对的操作和结果、原 Agent 的解释和修改建议；只有摘要时标明可读范围。

**S2｜核对框架责任**

对照项目实际文件与框架当前源材料（规则、Skill、模板、工具、复制映射和提示词），把每条观察归为框架通用问题、项目局部问题、环境或外部工具问题、Agent 执行偏差、共同因素或证据不足，并写出支持与反对的证据。

**S3｜提出最小改进与下一步**

分别判断问题是否成立、改法是否值得，给出最小修正。需要后续动作时，说明发回原项目线程还是留在框架维护线程，并附可直接复制的完整指令：原项目后续参考 [Godot 开发提示词库](../../../prompts/godot-development-prompts.json)，框架修正参考 [Yaya 框架维护提示词库](../../../prompts/yaya-maintenance-prompts.json)；没有适用条目时直接起草，不强套模板。

## 步骤产出与状态变化

| 步骤 | 可继续的依据 |
| --- | --- |
| S1 | 每条反馈有来源和编号，原目标、操作结果与原 Agent 解释已分开 |
| S2 | 每条观察有归属判断和证据，未确认的部分标为待核实 |
| S3 | 改法取舍与最小修正已列出；有后续动作时附接收线程和可复制指令 |

## 资源与文件影响

框架维护仓库、游戏项目和原始日志只读；不创建报告、Feature 或审核记录文件。

## 阻塞、异常与范围变化

证据不可用时收窄结论，没有亲自复现的结果标为转述；不把静态推演写成真实运行。

## 完成状态与验证标准

实际反馈已逐项归因并评价改法，后续建议和必要的可复制指令已交付；没有修改文件，也没有自动给原项目线程发送任务。

## 流程关联与衔接关系

依据：根 AGENTS.md 的[维护边界与查阅](../../../../../AGENTS.md#维护边界与查阅)（分别判断问题与改法，用户选定范围后才修改）与[先判断修改属于哪里](../../../../maintenance/maintenance-and-sync.md#先判断修改属于哪里)。用户选定框架修复范围后，转到[框架出现可复现问题，需要修复](框架出现可复现问题，需要修复.md)。
