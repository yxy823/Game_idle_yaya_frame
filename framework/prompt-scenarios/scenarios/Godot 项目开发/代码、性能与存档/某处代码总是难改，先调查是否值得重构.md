# 某处代码总是难改，先调查是否值得重构

[返回场景索引](../../scenario-index.md) · [执行步骤](#执行步骤) · [完成标准](#完成状态与验证标准)

## 触发场景与使用时机

同一个模块每次加功能都要连带改好几处，或者一处小改动总引出别处的问题，想先弄清是结构问题还是正常复杂度。

需要的材料：

- **关注范围与痛点**：模块、调用链或反复修改的位置，以及具体难在哪里；没指定时 Agent 从近期 Git 历史找常改的区域作为线索。
- **下一项相关变化**：已确定要做的需求或工程任务；没有就填“无”。

## 前置条件与适用范围

需要从实际源码发现重构候选，本次不实施。

## 执行步骤

使用[预设提示词库](<../../../prompts/godot-development-prompts.json>)中的“Godot 项目开发 → 代码、性能与存档 → 某处代码总是难改，先调查是否值得重构”。填入上述材料。

**S1｜追查修改阻力**

当前 Agent 阅读实际模块、调用关系与必要历史，找到重复变化和不清晰责任。

**S2｜比较最小调整**

比较不改、局部整理和结构重构的收益与成本，明确保持的行为和验证建议。

## 资源与文件影响

只读：不修改文件、不改任务状态，结果在对话中交付。

## 阻塞、异常与范围变化

只有风格偏好或未来假设时不强行提出架构层。

## 完成状态与验证标准

重构机会、依据和最小候选已交付，不自动开始重构。
