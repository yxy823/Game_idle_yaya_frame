# 已经实际体验，记录验收结果

[返回场景索引](../../scenario-index.md) · [执行步骤](#执行步骤) · [完成标准](#完成状态与验证标准)

## 触发场景与使用时机

你按清单体验完 F012，需要 Agent 把结果记录进完成证据。结果可以用两种方式给出，不需要另选入口：

- 已经直接在清单 JSON 里把每项的 status 改成 passed 或 failed 并写了备注。
- 不想自己编辑清单，在对话里说“背包全部通过，只有排序那项不对”。

需要的材料：

- 在对话中给结论时：你的结论原话，接受或拒绝了哪些检查项，不通过的具体表现。已经填好清单时不需要。
- Feature ID 与清单路径（可空）：不提供时用当前对话中正在验收的 Feature，由 Agent 在 `reports/manual-acceptance/F0XX/` 查找已绑定的清单。

## 前置条件与适用范围

用户已实际体验，并在已绑定的清单中填写了结果，或在对话中明确给出结论。

## 执行步骤

使用[预设提示词库](<../../../prompts/godot-development-prompts.json>)中的“Godot 项目开发 → 审核与人工验收 → 已经实际体验，记录验收结果”。填入上述材料。本页由当前 Agent 使用项目自己的 [$manual-acceptance](<../../../../../project-source/skills/manual-acceptance/SKILL.md>)，链接指向框架中的源文件，仅供核对。

**S1｜判断结果来源并核对**

当前 Agent 读取已绑定的清单，确认检查项定义未被改动，再按结果来源核对：

- 清单已填写：确认结果确由用户填写；备注与状态矛盾时只就具体问题澄清。
- 对话结论：确认结论对应当前内容和清单中的哪些检查项，区分建议、继续请求与实际接受；没有覆盖全部检查项时先补问。

清单已填写、对话里又给了相矛盾的结论时，先问以哪一处为准。

**S2｜记录结果**

对话结论先写进清单对应项的 status，comment 写明“来自对话”和原话；清单已填写时不改用户填写的状态和备注。然后使用 yaya/tools/features/record-feature-completion.py record-acceptance --feature <ID> --checklist <清单路径>。工具列出绑定后可能变化的文件时，逐个核对：先确认是否真的改过（绑定时未提交、之后原样提交的不算），真正改过的都不涉及本 Feature 才加 --confirm-unrelated-changes 重新记录，否则重新准备清单。

**S3｜报告接受范围并交回完成检查**

核对记录结果；全部 passed 即为明确接受，不再重复确认；failed/pending 保留给对应处理。说明已接受与待修复内容，继续原授权剩余事项；用户不需要再填一次清单。

项目工具命令的使用要求：

- 工作目录：实际游戏项目根目录。
- Python 与调用形式：使用 `docs/methodology-config.json` 中的 `python_executable`，按 `& $projectPython -B <脚本路径> <参数>` 调用，每次立即检查 `$LASTEXITCODE`。
- 参数：尖括号参数替换为实际值。
- 结果边界：命令成功只证明该操作完成。

## 步骤产出与状态变化

| 步骤 | 可继续的依据 |
| --- | --- |
| S1 | 结果来源已确定；检查项定义未被改动；需要澄清或补问的具体项已列出或为零 |
| S2 | 对话结论已写进清单（comment 写有“来自对话”和原话）；`record-acceptance` 退出码为 0，输出的状态为 `accepted`、`rejected` 或 `pending` |
| S3 | 报告列出通过、失败、pending 的检查项 ID |

## 资源与文件影响

用户自己填写的状态和备注保持原样；对话结论写进已绑定清单的状态和备注，不另建结果文件。该 Feature 的完成证据 `docs/features/F0XX-evidence.json` 中的人工结果会更新。

## 阻塞、异常与范围变化

清单缺失、检查项定义被改、绑定后变化涉及本 Feature、状态与备注冲突，或对话结论范围不全、含义矛盾时，保留失败，只澄清具体缺口；自动测试不代替用户的结论。

## 完成状态与验证标准

用户的验收结果已写进清单并按真实来源记录，实际接受或失败范围明确，没有重复验收或伪造材料；尚需其他完成检查不跳过。
