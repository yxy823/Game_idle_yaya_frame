# 我手动改过项目，想确认是否仍符合要求

[返回场景索引](../../scenario-index.md) · [执行步骤](#执行步骤) · [完成标准](#完成状态与验证标准)

## 触发场景与使用时机

你没经过 Agent，直接在编辑器里改了某个场景的参数，或手改了 GDD 的一条规则，想知道这些修改和 GDD、Product、Feature 的验收条件是否还一致。

需要的材料：

- 修改范围（可空）：哪些文件、模块或提交；不提供时检查当前未提交的修改。
- 修改意图：想达到的效果、是否是已确认的新决定或临时实验；不确定就说不确定。
- 比较基线（可空）：修改前的提交或要检查的提交范围；不提供时与 HEAD 比较。

GDD、Product、Feature 和实际差异由审核实例直接读取。

## 前置条件与适用范围

需要独立静态核对手改内容与有效要求，本次不修复。

## 执行步骤

使用[预设提示词库](<../../../prompts/godot-development-prompts.json>)中的“Godot 项目开发 → 审核与人工验收 → 我手动改过项目，想确认是否仍符合要求”。填入上述材料。本页由新的 `independent-reviewer` 实例按修改对象组合方法：代码、场景、资源用 [$review-code](<../../../../../project-source/skills/review-code/SKILL.md>)，GDD、Product、Feature 文件用 [$plan-review](<../../../../../project-source/skills/plan-review/SKILL.md>)。

**S1｜确定实际检查版本**

独立审核 Agent 核对未提交或指定提交差异；工作区干净不代表没有历史修改。

**S2｜对照需求与实现**

审核实例对手改的代码、场景、资源用 review-code 核对 Feature/AC 与实际行为；对手改的 GDD、Product、Feature 文件用 plan-review 检查设计矛盾、交付范围与来源的对应。区分已确认的新决定和未批准的冲突。

**S3｜建议所属处理入口**

交付一致、冲突和未知部分及最小后续动作；不改来源或放宽 AC 消除冲突。

## 步骤产出与状态变化

| 步骤 | 可继续的依据 |
| --- | --- |
| S1 | 实际检查的提交或差异范围已写明 |
| S2 | 每条发现都引用文件位置和对应的 GDD 条目、Product 范围或 AC |
| S3 | 报告分出一致、冲突、证据不足三类，并为每类冲突写明所属处理入口 |

## 资源与文件影响

被审文件、原证据与验收历史只读；对话报告不运行测试。

## 阻塞、异常与范围变化

历史基线不可还原时核对当前一致性并说明变化未知，不猜测旧状态。

## 完成状态与验证标准

独立静态一致性报告已交付，未替用户批准需求或修复。
