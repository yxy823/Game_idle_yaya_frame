# 功能已经写出来，需要补齐需求和任务记录

[返回场景索引](../../scenario-index.md) · [执行步骤](#执行步骤) · [完成标准](#完成状态与验证标准)

## 触发场景与使用时机

背包整理已经在代码里能用，但 `docs/product/` 和 `docs/feature-list.json` 里都没有它的记录，后续改动和验收找不到依据。

需要的材料：

- 实现范围：功能名或代码路径，例如 `scenes/inventory/`；只给功能名时，Agent 搜索后列出它认为属于该功能的文件，请你确认。
- 原始意图和已确认要求：你当初想要的效果和后来确认过的改动，原话即可；不提供时，Agent 只列出代码现状并逐项问你，不把代码行为当作已批准的设计。

GDD、Product、已有 Feature 记录和代码由 Agent 直接读取。

## 前置条件与适用范围

项目已有真实 GDD，已有代码但缺少当前交付范围或任务记录，本次只补文档；缺少 GDD 时说明缺口并停止。

## 执行步骤

使用[集中提示词库](<../../../prompts/godot-development-prompts.json>)中的“Godot 项目开发 → 规划 Product 与 Feature → 功能已经写出来，需要补齐需求和任务记录”。填入上述材料。本页使用 [$product-author](<../../../../../project-source/skills/product-author/SKILL.md>)、[$feature-plan](<../../../../../project-source/skills/feature-plan/SKILL.md>)。

**S1｜核对意图与实现**

当前 Agent 对照 GDD 和有效决定，区分实际代码行为与已批准设计，对实质冲突补问，不从代码倒推用户接受。

**S2｜补齐正式来源**

通过 [design-gdd](../../../../../project-source/skills/design-gdd/SKILL.md) 在已有 GDD 中保存确认的设计补充，再由 product-author 补齐当前 Product 交付范围与来源映射；专业细节交所属方法，保持原实现不动。

**S3｜对齐当前任务**

没有计划时，feature-plan 先在对话中给出拆分预览，经你确认后再写入（你已明确授权自主拆分的除外）；新记录以 `pending` 开始，notes 写明实现早于记录、已核实的文件和剩余缺口。已有计划时由 feature-sync 对齐。保留原 ID 和真实历史。

## 步骤产出与状态变化

| 步骤 | 可继续的依据 |
| --- | --- |
| S1 | 代码行为与已确认意图的对照已列出，冲突项已向你提问 |
| S2 | GDD 补充与当前 Product 交付范围已保存并提交 |
| S3 | 拆分预览已确认；Feature 记录写入后 `check-feature-list.py` 通过，notes 列出剩余实现和验证缺口 |

## 资源与文件影响

GDD、当前 Product、必要专业来源和任务文档修改；代码、运行证据、历史接受只读。

## 阻塞、异常与范围变化

来源意图未确认时保留差异；不能以补录时间代替未知完成时间。

## 完成状态与验证标准

当前需求与任务能解释已有实现和真实缺口，没有制造交付或测试通过。
