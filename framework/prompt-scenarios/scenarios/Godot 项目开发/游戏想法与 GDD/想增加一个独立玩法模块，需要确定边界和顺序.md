# 想增加一个独立玩法模块，需要确定边界和顺序

[返回场景索引](../../scenario-index.md) · [执行步骤](#执行步骤) · [完成标准](#完成状态与验证标准)

## 触发场景与使用时机

已有核心循环和背包，想加一个“钓鱼”玩法：要先确定它和采集、背包怎么衔接，再决定排在哪个 Product、什么时候做。

需要的材料：

- 新模块的目标：想让玩家做什么、为什么要加，用原话写。
- 已知的衔接（可选）：例如“钓到的鱼进背包，可以卖给商店”。
- 交付规划范围（可选）：是否纳入本次交付规划、要不要排在某个 Product 之前；不写时，Agent 只给出建议顺序，请你确认。

现有 GDD、`docs/product.md` 和实现情况由 Agent 直接读取。

## 前置条件与适用范围

项目已有真实 GDD，新增玩法影响设计和交付范围；本次确定设计边界与交付预拆分，不提前细化未来 Product。

## 执行步骤

使用[预设提示词库](<../../../prompts/godot-development-prompts.json>)中的“Godot 项目开发 → 游戏想法与 GDD → 想增加一个独立玩法模块，需要确定边界和顺序”。填入上述材料。当前 Agent 使用 [design-gdd](../../../../../project-source/skills/design-gdd/SKILL.md) 处理新增玩法，再用 [product-author](../../../../../project-source/skills/product-author/SKILL.md) 安排交付；交付取舍按需使用 product-spec-elicitor。

**S1｜确定独立边界**

当前 Agent 用 design-gdd 对照已有 GDD 确认新增设计与既有玩法的关系，区分游戏系统和 Product 交付单元，避免重复设计。

**S2｜更新设计与交付轮廓**

design-gdd 把确认玩法写入 GDD，数值模型按需由 design-balance 直接维护，其他专业细节交所属方法；product-author 更新 docs/product.md 中的交付边界、来源映射、依赖和建议顺序。

**S3｜安排后续时机**

核对当前 Product 尚未完成范围，新增交付单元未轮到时只保留预拆分，不创建详细 Product 或 Feature。

## 步骤产出与状态变化

| 步骤 | 可继续的依据 |
| --- | --- |
| S1 | 新模块与已有系统的重叠和依赖已列出，已确认独立成模块或并入现有模块 |
| S2 | GDD 新章节和 `docs/product.md` 中的预拆分条目已保存，条目链接到 GDD 章节 |
| S3 | 新交付单元的前提和建议顺序已写入 `docs/product.md` 的依赖与建议顺序 |

## 资源与文件影响

GDD、Product 总览及必要专业引用修改；不预建未来 Product 详细文档、Feature、AC 或测试登记。

## 阻塞、异常与范围变化

边界与现有模块重叠时先合并需求，而非为名字新增独立模块。

## 完成状态与验证标准

新增设计及交付边界、依赖和建议顺序已确认保存，详细规划等待实际轮到。
