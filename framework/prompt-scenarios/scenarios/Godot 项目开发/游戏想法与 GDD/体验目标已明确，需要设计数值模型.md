# 体验目标已明确，需要设计数值模型

[返回场景索引](../../scenario-index.md) · [执行步骤](#执行步骤) · [完成标准](#完成状态与验证标准)

## 触发场景与使用时机

已经能说清想让玩家经历怎样的节奏和取舍，也有相关玩法规则，但缺少支撑它们的公式、参数和计算依据。例如希望首次升级等待较短、后续选择有取舍，却还没有成本和产出的关系模型。

需要的材料：用原话写的目标体验（例如“首次升级等 30 秒左右”）、允许探索的机制、关心的时间尺度，以及已有的试玩或计算样本（路径或数据）。没有样本时 Agent 用标明的假设建模；GDD 中已有的规则与数值由 Agent 直接读取。

## 前置条件与适用范围

相关规则可以仍是 GDD 草稿；不要求完整 GDD、Product 或 Feature。此页建立当前范围的模型，已有模型需要调参时使用[已有数值需要调整，更新模型与参数](<../要求变了/已有数值需要调整，更新模型与参数.md>)。

## 参与角色与职责边界

[design-balance](../../../../../project-source/skills/design-balance/SKILL.md) 负责数值模型、参数和计算说明，可在授权内直接维护 GDD 数值主题。[design-gdd](../../../../../project-source/skills/design-gdd/SKILL.md) 负责整体玩法与体验目标的设计决定；不要求它代替数值入口保存正文。[review-balance](../../../../../project-source/skills/review-balance/SKILL.md) 承担按需正式独立审核，不由设计者的自查代替。

## 执行步骤

使用[集中提示词库](../../../prompts/godot-development-prompts.json)中的“Godot 项目开发 → 游戏想法与 GDD → 体验目标已明确，需要设计数值模型”。

**S1｜把目标转成可计算的约束**

当前 Agent 核对机制、单位、时间尺度、边界和已有样本，区分已采用规则、设计目标、实测数据与假设。只补问影响模型的关键决定，不因为某个游戏类型常见就加入离线、转生或无限成长机制。

**S2｜构建模型并复算样本**

使用 design-balance 的建模参考，选择能解释当前目标的最小模型。定义公式、参数、舍入和更新条件，对典型阶段、边界输入及合理策略进行可复算比较，检查重要参数变化对结果的影响。

**S3｜按决定保存数值正文**

本入口请求按[GDD 文件名](../../../../../project-source/methodology/01-product-doc-structure.md#gdd-文件名)保存模型与计算说明：单系统使用 `docs/gdd/balance/<system-key>.md`，跨系统模型使用 `docs/gdd/balance/cross-system.md`，不按模型复杂程度另选位置。用户只讨论时不写文件。已有明确采用决定直接沿用；新候选标明状态，不能静默替换现行采用值。写明模型适用范围、依据和仍需体验验证的假设。

## 资源与文件影响

维护当前 GDD 数值主题及必要计算说明和引用，不另建平行数值规格。本入口不修改游戏代码、运行参数文件或资源，不为建模创建 Product、Feature 或测试登记。

## 阻塞、异常与范围变化

必要目标、机制或数据缺失时，说明受影响的结论，能使用的有界假设明确标注。模型若需要新增玩法或超出授权的体验目标变化，交回整体设计决策；不能通过写一个公式偷偷决定玩法。

## 完成状态与验证标准

当前模型已有依据、公式、参数和适用范围，完成与模型相称的计算并按授权保存。交付实际输入、方法、结果及局限，分别标明候选或采用状态。数学自洽不等于体验平衡，未执行的模拟、运行或试玩不能写成通过。

## 流程关联与衔接关系

后续需要调整既有模型时使用[已有数值需要调整，更新模型与参数](<../要求变了/已有数值需要调整，更新模型与参数.md>)。已有样本且明确要求正式审核时，使用[独立审核：已有样本的数值方案平衡](<../审核与人工验收/独立审核：已有样本的数值方案平衡.md>)，按项目规范交给非作者的独立审核实例。
