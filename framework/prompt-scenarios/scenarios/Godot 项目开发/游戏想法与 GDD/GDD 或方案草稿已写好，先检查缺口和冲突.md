# GDD 或方案草稿已写好，先检查缺口和冲突

[返回场景索引](../../scenario-index.md) · [执行步骤](#执行步骤) · [完成标准](#完成状态与验证标准)

## 触发场景与使用时机

例如 Agent 刚整合出一版 GDD 草稿，你想在预拆分 Product 之前，先看看规则之间有没有矛盾、哪些体验目标还没落到机制上；或者 Feature 方案已经写好，想在开工前确认拆分和验收条件是否合理。

需要的材料：

- 要检查的材料，例如 `docs/gdd/systems/shop.md`、Product 01 或 F01-005。
- 这次检查要支持什么决定，或想重点看的方面（可空），例如“能不能开始预拆分 Product”。
- 其余（引用的 GDD 主题、Product 边界、项目规则和已采纳的决定）由 Agent 直接读取。

## 前置条件与适用范围

材料已经写出。检查 GDD 不需要先有 Product 或 Feature。要正式的独立审核时，改用[我手动改过项目，想确认是否仍符合要求](<../审核与人工验收/我手动改过项目，想确认是否仍符合要求.md>)或对应的独立审核入口；要检查代码和资源时，改用[独立审核：已准备好变更的代码](<../审核与人工验收/独立审核：已准备好变更的代码.md>)。

## 执行步骤

使用[预设提示词库](<../../../prompts/godot-development-prompts.json>)中的“Godot 项目开发 → 游戏想法与 GDD → GDD 或方案草稿已写好，先检查缺口和冲突”。填入上述材料。本页使用 [$plan-review](../../../../../project-source/skills/plan-review/SKILL.md)。

**S1｜确定检查的问题**

当前 Agent 确认要检查哪份材料、它要支持什么决定，读取它引用的来源；检查 GDD 时还读取 GDD 审查要点。

**S2｜检查并交付结论**

检查 Product 或 Feature 方案时，当前 Agent 先从本项目的 Feature 或 GDD 场景中挑 2–3 个具体任务逐步走一遍，其中至少一个是“中途发现以前做完的东西有问题”；再按目标和边界、假设和选择、拆分和依赖、验证、Godot 实现约束中相关的方面补查，交付每个问题的位置、影响和最小修改建议，并说明交给哪个 Skill 修改。

## 步骤产出与状态变化

| 步骤 | 可继续的依据 |
| --- | --- |
| S1 | 已说明检查的材料、要支持的决定和读取的来源 |
| S2 | 结论已交付：问题、依据、建议和负责的 Skill；没有问题时列出检查过的内容 |

## 资源与文件影响

只读，不修改任何文件。

## 阻塞、异常与范围变化

- 材料引用的来源不存在：作为证据缺口写进结论，不替你补写设计。
- 你决定按建议修改：用对应的入口修改，例如 GDD 用[已有模块的玩法要求变了，需要更新需求](<../要求变了/已有模块的玩法要求变了，需要更新需求.md>)，Product 用[Product 已预拆分，准备细化当前交付范围](<../规划 Product 与 Feature/Product 已预拆分，准备细化当前交付范围.md>)。

## 完成状态与验证标准

指定材料已检查完，结论、依据和建议已交付，被检查的文档没有被修改。
