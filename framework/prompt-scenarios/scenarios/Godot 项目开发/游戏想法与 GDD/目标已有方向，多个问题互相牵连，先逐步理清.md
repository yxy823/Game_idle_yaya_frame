# 目标已有方向，多个问题互相牵连，先逐步理清

[返回场景索引](../../scenario-index.md) · [执行步骤](#执行步骤) · [完成标准](#完成状态与验证标准)

## 触发场景与使用时机

目标已有方向，但多个问题相互影响：例如先确定背包规模，才知道需要验证哪种布局和性能方案。用户希望先理清当前能判断什么、还缺什么，以及应按什么依赖推进。

## 前置条件与适用范围

读取相关已确认决定与现有材料，按当前问题判断所需设计依据。从零形成游戏设计由 design-gdd 承接；缺失规则不当作已确认事实，不据此开始依赖它的实现。只有一个具体问题时可直接使用普通讨论入口；询问项目现状或下一入口时由 advisor 处理。

## 参与角色与职责边界

当前 Agent 使用 [wayfinder](../../../../../project-source/skills/wayfinder/SKILL.md) 推进当前目标的探索。能直接查明的事实由 Agent 调查；影响业务目标或重要取舍的选择由用户回答。专业方法保留自己的输出与正式写入责任。

## 执行步骤

使用[预设提示词库](../../../prompts/godot-development-prompts.json)中的“Godot 项目开发 → 游戏想法与 GDD → 目标已有方向，多个问题互相牵连，先逐步理清”。补充目标、已知决定、现有疑问与本次允许的调查或试验范围。

**S1｜找出目前真正影响下一步的问题**

从现有事实、GDD/Product/Feature 和相关记录恢复当前目标。区分已确认、待查事实、待选取舍与尚不能具体化的后续问题；不把已经排除的范围重新塞入计划。

**S2｜按依赖取得需要的答案**

需要讨论时使用 [grill-me](../../../../../project-source/skills/grill-me/SKILL.md)；需要外部事实时调研；需要运行证据时在具体授权内使用 [in-game-tuning](../../../../../project-source/skills/in-game-tuning/SKILL.md)（在调试台比较候选）或 [technical-validation](../../../../../project-source/skills/technical-validation/SKILL.md)（技术验证）。只有确需保留多套实现时才使用创建 worktree 入口。答案改变后只重查依赖它的判断，不强制穷尽所有分支。

**S3｜返回足以推进的结论**

给出结论和依据、仍缺的实质决定及下一步。只讨论时在对话交付；需要且获准保存时，使用既有记录归属。

## 资源与文件影响

该提示词默认讨论与必要只读调查；创建原型、运行工具和修改正式文档须有覆盖对应动作的授权。Progress 保存当前状态及链接，具体结论归原有 GDD/Product、Feature、调研或适用 ADR，不新建 wayfinder 记录文件或逐题文件。

## 条件分支与路径规则

已有方案需要找漏洞，使用 plan-review；设计反复出现的一类工作，使用 loop-me；总结实际经过，使用 retro。wayfinder 不成为这些入口的统一前置，也不要求固定输出多个 worktree。

## 阻塞、异常与范围变化

缺少用户取舍、资料或实验权限时，说明哪一项判断受阻以及怎样取得答案；继续能够独立推进的获准调查。不能用假设代替用户的实际回答，或以未验证推断宣称可行。

## 完成状态与验证标准

本次探索目标得到有依据、足以支持下一步的结论。未解决问题与证据局限如实保留；保存停点不等于全部探索完成。

## 流程关联与衔接关系

普通单个问题使用[只有一个项目问题没想清楚，先讨论](<只有一个项目问题没想清楚，先讨论.md>)，续接使用[项目问题还没讨论清楚，继续原来的讨论](<../现状、暂停与续接/项目问题还没讨论清楚，继续原来的讨论.md>)。方法选择与产物归属分别依据[任务路由表](../../../../../project-source/methodology/00-overview.md#任务路由表)和 [Progress](../../../../../project-source/methodology/09-records-reports-and-handoff.md#progress)。
