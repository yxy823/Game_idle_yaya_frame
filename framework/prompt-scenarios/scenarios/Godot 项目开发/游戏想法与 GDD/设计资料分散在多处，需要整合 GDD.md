# 设计资料分散在多处，需要整合 GDD

[返回场景索引](../../scenario-index.md) · [执行步骤](#执行步骤) · [完成标准](#完成状态与验证标准)

## 触发场景与使用时机

玩法已经在笔记、对话记录或几份文档里讨论过，但正文分散、同一规则出现多个版本，难以判断目前采用哪一个。希望整合为项目内可查找、可维护的 GDD。也适用于手上已有一份或多份成形的外部设计资料，例如一份完整的 GDD 草稿，需要直接整理进项目的 GDD。

需要的材料：资料的位置或内容（路径、链接或粘贴原文）、这次要整合的主题（不写时整合全部指定资料）、你已确认的决定和已知冲突。现有 GDD 和存放位置由 Agent 读取并按固定文件名确定。

## 前置条件与适用范围

可以尚未有完整 GDD，也不要求 Product 或 Feature。此处处理已有资料的整合；只有一个游戏想法时使用[只有游戏想法，先形成 GDD 草稿](<只有游戏想法，先形成 GDD 草稿.md>)，只希望阅读外部需求并返回改写建议时使用[拿到一份外部需求，先整理成项目可用的草稿](<拿到一份外部需求，先整理成项目可用的草稿.md>)。

## 执行步骤

使用[预设提示词库](../../../prompts/godot-development-prompts.json)中的“Godot 项目开发 → 游戏想法与 GDD → 设计资料分散在多处，需要整合 GDD”。当前 Agent 使用 [design-gdd](../../../../../project-source/skills/design-gdd/SKILL.md)，按需读取其整合参考。

**S1｜核对来源与有效决定**

对照现有 GDD《设计范围与边界》及相关主题，把当前范围内的重复、互补和冲突内容分清，核对哪些决定已采用。较新、较长的文档或已经存在的实现都不能自动压过有效设计决定；涉及玩法取舍的冲突只向用户补问必要问题。

同时核对 `docs/gdd/open-questions.md` 中相关问题，复用已有决定，避免再次提出已经解决的选择。

**S2｜整合唯一正文**

将可确定的内容放入所属 GDD 主题。新建整合结果或获准标准化时，按[GDD 文件名](../../../../../project-source/methodology/01-product-doc-structure.md#gdd-文件名)使用固定名称与多实例命名模式，入口为 `docs/gdd/README.md`；系统规则与数值模型按作用域进入固定文件，不按游戏规模、篇幅或复杂程度选择位置。相同职责不另取名，迁移时同步实际文件与章节引用。涉及整体范围时按[设计范围与边界](../../../../../project-source/methodology/01-product-doc-structure.md#设计范围与边界)归入 `design-scope-and-boundaries.md`，局部限制留在所属主题，其他位置引用正文。导入 GDD 的已有主题在获准迁移前沿用原位置，新增主题或系统使用标准路径并从原入口链接；不重排无关内容或预建空章节。保留原始输入资料，不能静默删除未采用材料或把候选改为确定规则。

按[开放问题](../../../../../project-source/methodology/01-product-doc-structure.md#开放问题)把尚未解决的设计冲突归入固定文件，保留来源、影响和所需决定，主题只保留必要上下文与引用。后续讨论和规划据此处理依赖；已解决项的结果写回所属主题并更新引用。

按[备选方案与未采纳想法](../../../../../project-source/methodology/01-product-doc-structure.md#备选方案与未采纳想法)归位：当前比较进入开放问题，已采纳规则的备选值随所属规则或模型，没有当前待决问题依赖的设想保存到 `docs/unadopted-ideas.md`。保留原始资料作为来源，现行正文不重复保存。

本次资料中已确定的专业规格按[留在 GDD 中的内容](../../../../../project-source/methodology/11-specialist-workflows.md#留在-gdd-中的内容)迁入对应固定正文，GDD 保留整体目标、玩法规则与引用；首次写在哪里不改变职责。

按[项目术语文件](../../../../../project-source/methodology/14-project-terminology.md#项目术语文件)，使用 `project-terminology` 将本次资料中已确认的定义与别名统一保存到 `docs/terminology.md`，当前仅用于一个主题的术语也使用该文件。GDD 中的重复定义改为引用，详细玩法规则留在所属主题；要求留存的原始输入继续作为来源保存。

**S3｜核对覆盖和后续影响**

说明约定资料归到哪里、哪些内容未纳入以及原因，标明未解决的冲突。已有专业来源、Product 或 Feature 确受影响时指出消费者和所属同步入口；本次没有这些记录也不需要为整合补建一套。

## 资源与文件影响

本入口请求维护 `docs/gdd/` 的正文、`docs/unadopted-ideas.md` 中本次保留的设想、本次已确定的专业规格、`docs/terminology.md` 中本次已确认的术语与必要导航；用户只要求讨论时，不写文件。引用原始资料不改变其文件，未经额外授权不删除或覆盖原件，不开始实现或重写历史验收。

## 阻塞、异常与范围变化

不能确定采用哪份设计时，保留冲突及其依据，只停止依赖该决定的部分。新的玩法决定回到设计讨论，不能把资料整理当作全款游戏的设计授权。

## 完成状态与验证标准

约定范围内可确定的资料已整合，原意、采用状态、正文归属和引用已核对；已确认的术语统一保存到项目词表，GDD 不留另一份定义。影响当前整合的关键冲突尚未解决时，明确未完成部分；文件保存不能代替这些决定，也不证明游戏已运行或体验已通过。

## 流程关联与衔接关系

数值主题需要建模时使用[体验目标已明确，需要设计数值模型](<体验目标已明确，需要设计数值模型.md>)；已有模型需要调整时使用[已有数值需要调整，更新模型与参数](<../要求变了/已有数值需要调整，更新模型与参数.md>)。当前设计已采用且明确、且获准安排交付后，才进入 [已有 GDD，需要预拆分 Product 交付范围](<../规划 Product 与 Feature/已有 GDD，需要预拆分 Product 交付范围.md>)。
