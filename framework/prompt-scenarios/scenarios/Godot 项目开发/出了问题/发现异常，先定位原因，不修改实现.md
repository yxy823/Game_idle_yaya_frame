# 发现异常，先定位原因，不修改实现

[返回场景索引](../../scenario-index.md) · [执行步骤](#执行步骤) · [完成标准](#完成状态与验证标准)

## 触发场景与使用时机

发现规则、表现或二者接入的异常，本次先定位原因，不修改实现。例如生命值计算错误、Shader 画面异常，或购买失败却播放成功反馈，都可从本入口调查，不必先判断属于哪一层。

需要的材料：

- 问题表现：预期与实际、触发条件。
- 已有证据：按问题提供日志、画面或运行条件，无须凑齐所有材料。
- 允许的诊断运行：是否允许启动 Godot、跑已有测试或加临时诊断代码。不写时只做静态追查（读日志和源码），不运行、不加代码。

## 前置条件与适用范围

当前只需要原因与处理建议，不授权修复实现。“预期”本身是否成立还不确定时（例如不确定这是 Bug 还是想要新行为），先用[已有内容表现不对，先判断是 Bug、要改要求还是只需调值](<已有内容表现不对，先判断是 Bug、要改要求还是只需调值.md>)核实。

## 执行步骤

使用[预设提示词库](<../../../prompts/godot-development-prompts.json>)中的“Godot 项目开发 → 出了问题 → 发现异常，先定位原因，不修改实现”。填入上述材料。

**S1｜整理可核实表现**

当前 Agent 使用 [bug-diagnosis](../../../../../project-source/skills/bug-diagnosis/SKILL.md)，读取已有证据、有效要求和实际代码，按问题追查规则结果、表现或接入，区分明确事实与假设；方法调用不改变本次只诊断、禁止修改实现的范围。

**S2｜定位原因**

在获准范围复现或静态追查调用链，必要查询证据，不增加持久埋点。

**S3｜交付修复建议**

说明最小修改位置、验证方式，以及修复入口[发现 Bug，需要修复](<发现 Bug，需要修复.md>)（说明所属 Feature 是否已交付），不代执行。

## 步骤产出与状态变化

| 步骤 | 可继续的依据 |
| --- | --- |
| S1 | 预期行为及其来源、实际症状和触发条件已写明 |
| S2 | 从触发到症状的因果链有证据支撑，或已列出已排除项和缺少的证据 |
| S3 | 最小修复位置、验证方式和所属修复入口已给出 |

## 资源与文件影响

实现和任务状态只读；诊断运行只产生获准日志。

## 阻塞、异常与范围变化

运行无权限或证据不足时给受限结论；不把仅怀疑原因写成已确认根因。

## 完成状态与验证标准

已交付原因证据、限制和最小建议，没有实施修复。

## 流程关联与衔接关系

依据：[因果诊断](<../../../../../project-source/methodology/07-engineering-change.md#因果诊断>)。本入口结束于原因与建议；本次明确的只诊断限制优先于旧实施授权，修复需用户后续明确续接或更新范围。
