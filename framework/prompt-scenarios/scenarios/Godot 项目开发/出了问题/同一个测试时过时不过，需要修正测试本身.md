# 同一个测试时过时不过，需要修正测试本身

[返回场景索引](../../scenario-index.md) · [执行步骤](#执行步骤) · [完成标准](#完成状态与验证标准)

## 触发场景与使用时机

同一份代码上，某个测试有时通过、有时失败，游戏行为本身符合要求。例如全量运行时偶尔失败、单独运行总是通过。

需要的材料：

- 不稳定的测试：测试文件路径与用例名，例如 `tests/combat/test_damage.gd` 的 `test_crit_roll`。
- 失败证据：失败与通过运行的报告路径或原始输出，并说明失败出现在全量还是单独运行；没有现成记录时，Agent 先按下方命令复现。

测试代码、对应的 AC、测试登记和被测实现由 Agent 直接读取。

## 前置条件与适用范围

游戏行为符合要求，问题出在测试本身。游戏行为确实有误时，使用 [发现 Bug，需要修复](<发现 Bug，需要修复.md>)；还不确定原因时，先用[发现异常，先定位原因，不修改实现](<发现异常，先定位原因，不修改实现.md>)。

## 执行步骤

使用[集中提示词库](<../../../prompts/godot-development-prompts.json>)中的“Godot 项目开发 → 出了问题 → 同一个测试时过时不过，需要修正测试本身”。填入上述材料。本页使用 [$engineering-change-plan](<../../../../../project-source/skills/engineering-change-plan/SKILL.md>)、[$feature-execute](<../../../../../project-source/skills/feature-execute/SKILL.md>)。

**S1｜查明不稳定的来源**

当前 Agent 读取失败运行的原始报告、测试代码和被测实现，写明已证实的原因，例如依赖真实时间、测试之间共享状态、随机数没有固定种子或依赖执行顺序。然后用 engineering-change-plan 的 maintenance 模式提出维护 Feature，取得用户批准后写入；当前请求已明确批准具体方案及其执行时沿用。

**S2｜按原因修正测试**

当前 Agent 使用 feature-execute 修改测试和必要的辅助代码，让测试自己控制时间、状态或随机数；不放宽断言、不加长等待、不重试、不跳过，也不改变游戏行为。

**S3｜验证稳定且仍然有效**

当前 Agent 在项目根目录按原来失败的方式重复运行，报告实际运行次数和每次结果；再临时制造测试本应抓住的问题，确认测试会失败后恢复。有可复用的教训时写进项目知识。

- 单独运行：`& $projectPython -B yaya/tools/testing/run-gdunit-tests.py --target <测试文件路径>`
- 全量运行：`& $projectPython -B yaya/tools/testing/run-gdunit-tests.py --feature <维护 Feature ID> --scope full`

`$projectPython` 换成 `docs/methodology-config.json` 中的 `python_executable`，参数见 [run-gdunit-tests.py](<../../../../../project-source/tools/README.md#run-gdunit-testspy>)。每次立即检查 `$LASTEXITCODE`；项目关闭了 gdUnit 的失败重试，不要打开它来掩盖不稳定。

## 步骤产出与状态变化

| 步骤 | 可继续的依据 |
| --- | --- |
| S1 | 不稳定原因及其证据已写明；维护 Feature 已获批写入（`check-feature-list` PASS） |
| S2 | 差异只涉及测试与测试辅助代码，断言和等待没有放宽 |
| S3 | 重复运行的次数与结果；临时制造问题时测试失败的输出；恢复后差异只含修正 |

## 资源与文件影响

测试与测试辅助代码、维护 Feature 记录和必要的项目知识条目修改；游戏代码和已验收参数不变。

## 阻塞、异常与范围变化

查明是游戏行为有误时停下，转到 Bug 场景；需要在生产代码中为测试增加控制入口时，先说明理由。

## 完成状态与验证标准

测试在原来失败的环境中稳定通过，仍能抓住它要证明的问题，工程任务完成条件满足。
