# Feature 交付后发现 Bug

[返回场景索引](../../scenario-index.md) · [执行步骤](#执行步骤) · [完成标准](#完成状态与验证标准)

## 触发场景与使用时机

某个 Feature 已经正式完成，之后发现它的行为偏离当时确认的要求。例如数值计算错误、效果显示异常，或操作失败却播放成功反馈，都可使用本入口，不必先判断问题属于规则、表现还是二者接入。

需要的材料：

- 所属 Feature ID，例如 `F003`；不确定时说明问题出现在哪个功能，由 Agent 对照 Feature 记录确认。
- 问题证据：预期与实际、触发条件的原话，以及已有日志或截图的路径；无须凑齐。

已交付契约、完成记录和当前实现由 Agent 直接读取。

## 前置条件与适用范围

正式交付以项目规定的 Feature 完成状态和完成记录为准，不以测试通过、代码提交或用户试玩作为单独依据。本页限定已交付行为出现缺陷。

## 执行步骤

使用[集中提示词库](<../../../prompts/godot-development-prompts.json>)中的“Godot 项目开发 → 修复与改进 → Feature 交付后发现 Bug”。填入上述材料。本页使用 [$engineering-change-plan](<../../../../../project-source/skills/engineering-change-plan/SKILL.md>)、[$feature-execute](<../../../../../project-source/skills/feature-execute/SKILL.md>)。

**S1｜记录问题与现场**

当前 Agent 核对仍有效要求、实际失败和交付状态，保留触发条件与已有证据。需要定位原因时使用 [bug-diagnosis-godot](../../../../../project-source/skills/bug-diagnosis-godot/SKILL.md)，按实际问题追查规则结果、表现或接入，复用已有证据并检查当前实现、已交付契约与直接消费者；分别记录已证实根因和假设，简述独立修复范围及旧行为回归，再返回独立 Bug 任务的规划或执行。

**S2｜规划并修复**

当前 Agent 先使用 `engineering-change-plan` 的 bug 模式提出独立 Bug Feature：ID、AC、`bug_diagnosis`，验收模式默认规划为 manual，用户另行批准时按批准的模式。方案取得用户批准后写入，再使用 `feature-execute` 修复；当前请求已明确批准具体方案及其执行时沿用。原 Feature 历史保持真实。

- 按[共用变更规则](../../../../../project-source/Project_AGENTS.md#任务范围)控制影响，保持无需变化的 API、依赖和代码风格。
- 为实际缺陷补必要回归；无法自动覆盖时保留原因与可重复的人工路径。
- 本专用入口在适用验证完成（已批准验收模式为 manual 时包括用户明确的实际验收）且用户明确允许本次提交前，不创建任何本地提交，包括计划和阶段性 checkpoint。修复授权、验收通过或普通“继续”不单独构成提交许可；已有明确许可沿用。

**S3｜完成复验**

当前 Agent 完成受影响自动测试与项目支持的适用解析、lint 或类型检查。按已批准的验收模式：manual 时向用户提供实际体验入口并记录明确结果；automated 时以自动 AC 与回归验证为准，不记录未发生的人工决定。未通过继续在授权内修复。

**S4｜返回完成检查**

当前 Agent 核对测试原件、适用的人工接受，以及用户指定的评审结果；检查最终差异没有无关改动，说明关键文件、修复理由及具体剩余风险。取得本次提交许可后，按本次的提交约束，对独立 Bug 任务进行完成检查；尚缺许可时保留差异并报告待提交。

## 步骤产出与状态变化

| 步骤 | 可继续的依据 |
| --- | --- |
| S1 | 预期与实际、触发条件和所属 Feature 已写明；根因或待验证假设已标明 |
| S2 | Bug Feature 方案已获批写入（`check-feature-list` PASS）；修复差异已完成，原 Feature 的 AC 未改动 |
| S3 | 受影响测试与解析、lint 的实际结果；manual 时有用户的明确结论 |
| S4 | 最终差异已核对；有提交哈希，或待提交的差异说明 |

## 资源与文件影响

实现、回归测试和所属任务记录修改；原 Feature 的 AC、完成状态与验收历史只读，不为新缺陷重写。

## 阻塞、异常与范围变化

- 要求实质改变：改用[Feature 已交付，后来确认要改变要求](<../任务规划/Feature 已交付，后来确认要改变要求.md>)。
- 无关功能缺陷：另按所属场景处理。
- 只要求诊断：改用[发现异常，先定位原因，不修改实现](<发现异常，先定位原因，不修改实现.md>)。
- 无法复现：保留证据缺口，不宣称修复。
- 缺少方案批准、适用的人工接受或本次提交许可：保留真实停点和差异，不提交，不把该停点写成正式完成。

## 完成状态与验证标准

独立 Bug 任务满足其适用验证（manual 时含实际人工接受），并在用户明确允许后完成提交与收尾，原交付历史保持真实。
