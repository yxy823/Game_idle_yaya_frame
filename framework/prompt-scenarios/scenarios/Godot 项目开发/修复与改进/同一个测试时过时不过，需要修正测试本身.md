# 同一个测试时过时不过，需要修正测试本身

[返回场景索引](../../scenario-index.md) · [执行步骤](#执行步骤) · [完成标准](#完成状态与验证标准)

## 触发场景与使用时机

同一个测试时过时不过，需要修正测试本身：同一份代码上，某个测试有时通过、有时失败，游戏行为本身符合要求。

需要的材料：

- 不稳定的测试：测试文件与用例。
- 失败证据：失败与通过的运行记录，以及出现失败的环境（项目目录、全量或单独运行）。

## 前置条件与适用范围

游戏行为符合要求，问题出在测试本身。游戏行为确实有误时，使用 [Feature 交付前发现 Bug](<Feature 交付前发现 Bug.md>) 或 [Feature 交付后发现 Bug](<Feature 交付后发现 Bug.md>)；还不确定原因时，先用[发现异常，先定位原因，不修改实现](<发现异常，先定位原因，不修改实现.md>)。

## 执行步骤

使用[集中提示词库](<../../../prompts/godot-development-prompts.json>)中的“Godot 项目开发 → 修复与改进 → 同一个测试时过时不过，需要修正测试本身”。填入上述材料。本页使用 [$engineering-change-plan](<../../../../../project-source/skills/engineering-change-plan/SKILL.md>)、[$feature-execute](<../../../../../project-source/skills/feature-execute/SKILL.md>)。

**S1｜查明不稳定的来源**

当前 Agent 读取失败运行的原始报告、测试代码和被测实现，用 engineering-change-plan maintenance 建立任务，写明已证实的原因，例如依赖真实时间、测试之间共享状态、随机数没有固定种子或依赖执行顺序。

**S2｜按原因修正测试**

当前 Agent 使用 feature-execute 修改测试和必要的辅助代码，让测试自己控制时间、状态或随机数；不放宽断言、不加长等待、不重试、不跳过，也不改变游戏行为。

**S3｜验证稳定且仍然有效**

当前 Agent 在原来失败的环境中反复运行全部通过，再临时制造测试本应抓住的问题，确认测试会失败后恢复，并把可复用的教训写进项目知识。

## 步骤产出与状态变化

| 步骤 | 可继续的依据 |
| --- | --- |
| S1 | 不稳定的原因有证据 |
| S2 | 修改针对已证实的原因 |
| S3 | 稳定通过且仍能抓住问题 |

## 资源与文件影响

测试与测试辅助代码、维护 Feature 记录、项目知识条目修改；游戏代码和已验收参数不变。

## 阻塞、异常与范围变化

查明是游戏行为有误时停下，转到 Bug 场景；需要在生产代码中为测试增加控制入口时，先说明理由。

## 完成状态与验证标准

测试在原来失败的环境中稳定通过，仍能抓住它要证明的问题，工程任务完成条件满足。
