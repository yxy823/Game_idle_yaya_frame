# Feature 交付前发现 Bug

[返回场景索引](../../scenario-index.md) · [执行步骤](#执行步骤) · [完成标准](#完成状态与验证标准)

## 触发场景与使用时机

Feature 交付前发现规则、表现或二者接入的 Bug。例如数值计算错误、效果显示异常，或操作失败却播放成功反馈，都可使用本入口，不必先判断属于哪一层。

需要的材料：

- 任务与要求：所属 Feature、仍有效要求。
- 问题证据：预期与实际、触发条件，以及与当前问题有关的已有日志、画面或运行条件；无须凑齐所有材料。

## 前置条件与适用范围

正式交付以项目规定的 Feature 完成状态和完成记录为准，不以测试通过、代码提交或用户试玩作为单独依据。本页限定当前未交付 Feature 内出现缺陷。

## 执行步骤

使用[集中提示词库](<../../../prompts/godot-development-prompts.json>)中的“Godot 项目开发 → 修复与改进 → Feature 交付前发现 Bug”。填入上述材料。本页使用 [$feature-execute](<../../../../../project-source/skills/feature-execute/SKILL.md>)。

**S1｜记录问题与现场**

当前 Agent 核对仍有效要求、实际失败和交付状态，保留触发条件与已有证据。需要定位原因时使用 [bug-diagnosis-godot](../../../../../project-source/skills/bug-diagnosis-godot/SKILL.md)，按实际问题追查规则结果、表现或接入，复用已有证据并检查实现及直接消费者；区分已证实根因与假设，简述修复位置、受影响模块和复验范围，然后返回原 Feature。

**S2｜修复既有要求**

当前 Agent 使用 `feature-execute` 留在原 Feature 修复，不为当前未完成范围再建独立 Bug 任务。

- 按[共用变更规则](../../../../../project-source/methodology/15-task-scope-git-and-reporting.md#任务范围)控制影响，保持无需变化的 API、依赖和代码风格。
- 为实际缺陷补必要回归；无法自动覆盖时保留原因与可重复的人工路径。
- 本专用入口在适用验证完成、用户明确实际验收通过且明确允许本次提交前，不创建任何本地提交，包括计划和阶段性 checkpoint。修复授权、验收通过或普通“继续”不单独构成提交许可；已有明确许可沿用。

**S3｜取得实际复验**

当前 Agent 完成受影响自动测试与项目支持的适用解析、lint 或类型检查，向用户提供实际体验入口并记录明确结果；未通过继续在授权内修复。

**S4｜返回完成检查**

当前 Agent 核对测试原件、当前内容上的人工接受，以及用户指定的评审结果；检查最终差异没有无关改动，说明关键文件、修复理由及具体剩余风险。取得本次提交许可后，按本次提交约束返回原 Feature 的完成检查；尚缺许可时保留差异并报告待提交。

## 步骤产出与状态变化

| 步骤 | 可继续的依据 |
| --- | --- |
| S1 | 缺陷事实和任务归属明确 |
| S2 | 修复没有放宽原验收要求 |
| S3 | 最终内容有真实复验结果 |
| S4 | 本页出口与原任务收尾衔接 |

## 资源与文件影响

实现、回归测试和所属任务记录修改；原 Feature 继续承担范围和验收，既有自动通过不覆盖新的失败。

## 阻塞、异常与范围变化

- 要求实质改变：转需求变更。
- 无关功能缺陷：另按所属场景处理。
- 只诊断请求：使用只读定位。
- 无法复现：保留证据缺口，不宣称修复。
- 缺少实际人工接受或本次提交许可：保留真实停点和差异，不提交，不把该停点写成正式完成。

## 完成状态与验证标准

原 Feature 的新增实际失败已消除，必要复验与用户实际接受已取得，获准提交后返回原任务完成检查。
