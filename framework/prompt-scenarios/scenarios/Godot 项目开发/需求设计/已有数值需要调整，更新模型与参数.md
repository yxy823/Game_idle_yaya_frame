# 已有数值需要调整，更新模型与参数

[返回场景索引](../../scenario-index.md) · [执行步骤](#执行步骤) · [完成标准](#完成状态与验证标准)

## 触发场景与使用时机

已有数值模型和采用参数，需要根据体验问题、计算样本或新目标进行调整。例如实际升级等待与目标不符，或某种策略在已知条件下始终占优。问题表现本身还不能证明是哪一个参数导致的。

需要的材料：具体问题或新目标（原话，例如“第 3 级等待超过 5 分钟”）、相关样本或计算结果（路径或数据）、允许调整的参数范围，以及已经作出的采用决定。未限定调整范围时，Agent 只提出候选、不替换现行采用值；现有模型与采用值由 Agent 从 GDD 数值文件读取。

## 前置条件与适用范围

已有可核对的模型或参数来源；相关 GDD 可以仍在完善，不要求额外建立 Product 或 Feature。首次建立模型使用[数值模型设计](<体验目标已明确，需要设计数值模型.md>)，仅要求正式审核而不修改则使用[独立检查平衡](<../验证与收尾/数值方案已有样本，需要独立检查平衡.md>)。

## 执行步骤

使用[集中提示词库](../../../prompts/godot-development-prompts.json)中的“Godot 项目开发 → 需求设计 → 已有数值需要调整，更新模型与参数”。当前 Agent 使用 [design-balance](../../../../../project-source/skills/design-balance/SKILL.md)。

**S1｜核对当前差异和原因依据**

对照现行模型、目标与证据，区分观察到的症状、模型假设、已核实原因和待验证推测。已有审核结论也要对照当前版本，不能直接把所有意见当成调参依据；实现偏离既有规则时应交回相应工程排错入口。

**S2｜比较可解释的调整**

根据证据修改必要公式或参数，用可对照的输入复算调整前后结果。说明旧值、新值、适用条件、预期效果和代价，检查相关边界、敏感参数及合理策略；缺少数据时限定结论，不编造实测结果。

**S3｜按采用决定写回所属来源**

已有明确的采用决定与写入授权直接沿用，可完成对应模型和计算说明修改。尚待选择的方案保留为候选，同时保留现行采用值；用户只讨论时不写文件。按[固定 GDD 归属](../../../../../project-source/methodology/01-product-doc-structure.md#gdd-文件名)由数值入口直接维护：单系统模型在 `docs/gdd/balance/<system-key>.md`，跨系统模型在 `docs/gdd/balance/cross-system.md`，不按模型复杂程度另选位置。不需要再让 design-gdd 代写，也不把每次调整一律停在草案。

**S4｜核对实际消费者影响**

检查真正使用这些规则的专业来源、实现和已有 Product、Feature，说明受影响范围与所属同步入口。沿用项目的来源影响和计划同步约定，不重写历史验收，也不为一次调参另建记录文件。

## 资源与文件影响

本入口请求修改所属 GDD 数值主题、计算说明及必要引用；游戏代码、运行参数文件、资源和存档不随之获得修改权限。模型设计完成不代表运行实现已同步。

## 阻塞、异常与范围变化

原因尚不明确时，先说明当前证据能支持哪种调整以及仍不能下的结论。新增玩法或超出授权的体验目标变化交回 [design-gdd](../../../../../project-source/skills/design-gdd/SKILL.md) 处理整体设计决定，不能由参数变化暗中代替。已有具体授权不重复索取，未决选择只阻塞依赖它的写回。

## 完成状态与验证标准

本次授权的调整已完成适用计算并按决定保存，候选和采用状态清楚，影响及剩余证据缺口明确。交付可对照的前后结果与实际计算方法；预测、自查和计算通过分别陈述，不冒充实际运行、体验验收或正式独立审核。

## 流程关联与衔接关系

仅数值范围内的调整继续由 design-balance 负责。已确认玩法要求也要改变时，衔接[玩法需求更新](<已有模块的玩法要求变了，需要更新需求.md>)；已有样本且明确要求正式数值审核时，衔接[独立检查平衡](<../验证与收尾/数值方案已有样本，需要独立检查平衡.md>)。
