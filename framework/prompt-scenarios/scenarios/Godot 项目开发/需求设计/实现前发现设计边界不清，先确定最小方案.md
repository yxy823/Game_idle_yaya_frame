# 实现前发现设计边界不清，先确定最小方案

[返回场景索引](../../scenario-index.md) · [执行步骤](#执行步骤) · [完成标准](#完成状态与验证标准)

## 触发场景与使用时机

实现前发现设计边界不清，先确定最小方案。

准备材料：

- 设计对象与需求：准备新增的核心对象或待简化设计、实际需求。
- 运行责任：状态、消费者与生命周期。

## 前置条件与适用范围

尚未实施，设计中存在职责边界不清或不必要复杂度；本次只确定最小设计。

## 执行步骤

使用[集中提示词库](../../../prompts/godot-development-prompts.json)中的“Godot 项目开发 → 需求设计 → 实现前发现设计边界不清，先确定最小方案”。

**S1｜列明必须承担的职责**

当前 Agent 从实际需求和使用方整理对象状态、输入输出、消费者、创建与释放时机，不从现有类名推导必须保留的架构。

**S2｜比较更小方案**

逐项比较复用现有对象、合并重复职责、删除无必要层与最小新增；说明公开契约和不应承担的工作。

**S3｜交付设计边界**

给出推荐方案、职责分界、必要数据流和相称验证建议；仅讨论时留在对话，已有具体保存授权时按架构规范的固定归属保存：符合条件的决定进入 ADR，Feature 内局部决定进入其设计文件，无 Feature 的已采用决定使用“独立技术决定”契约。

## 步骤产出与状态变化

| 步骤 | 继续条件 |
| --- | --- |
| S1 | 真实职责与设计包装可分离 |
| S2 | 选择依据是需求及维护成本 |
| S3 | 实施者知道该新增什么和保留什么 |

## 资源与文件影响

需求、现有设计与代码只读；默认在对话交付设计结论，不自动新建类、脚本、ADR 或 Feature。

## 阻塞、异常与范围变化

缺少关键行为决定时只澄清该缺口；已有实现需要重构时交独立重构场景，不借设计分析改代码。

## 完成状态与验证标准

一个最小可实施的职责方案及取舍依据已明确，未开始实现或重构。
