# 实现前发现设计边界不清，先确定最小方案

[返回场景索引](../../scenario-index.md) · [执行步骤](#执行步骤) · [完成标准](#完成状态与验证标准)

## 触发场景与使用时机

准备新增一个核心对象（例如“背包管理器”），或手上的方案层次过多，但说不清它到底该负责哪些状态、谁会调用它，想在动手前先定下最小的职责边界。

需要的材料：要新增的对象或待简化的方案（名称、草稿路径或原话），以及它要满足的需求（原话，或 GDD、Feature 的位置）。实际调用方、状态和生命周期由 Agent 从现有代码和设计文件读取；尚无代码时按需求推导并标明假设。

## 前置条件与适用范围

尚未实施，设计中存在职责边界不清或不必要复杂度；本次只确定最小设计。

## 执行步骤

使用[集中提示词库](../../../prompts/godot-development-prompts.json)中的“Godot 项目开发 → 需求设计 → 实现前发现设计边界不清，先确定最小方案”。

**S1｜列明必须承担的职责**

当前 Agent 从实际需求和使用方整理对象状态、输入输出、消费者、创建与释放时机，不从现有类名推导必须保留的架构。

**S2｜比较更小方案**

逐项比较复用现有对象、合并重复职责、删除无必要层与最小新增；说明公开契约和不应承担的工作。

**S3｜交付设计边界**

给出推荐方案、职责分界、必要数据流和相称验证建议；仅讨论时留在对话，已有具体保存授权时按[架构与决定记录在哪里](<../../../../../project-source/methodology/10-architecture-overview.md#架构与决定记录在哪里>)保存：符合条件的决定进入 ADR，Feature 内局部决定进入其设计文件，无 Feature 的已采用决定写入[独立技术决定](<../../../../../project-source/methodology/10-architecture-overview.md#独立技术决定>)一节。

## 步骤产出与状态变化

| 步骤 | 继续条件 |
| --- | --- |
| S1 | 职责清单已列出，每项写明状态、调用方和生命周期的依据 |
| S2 | 每个备选方案对调用方的要求和维护成本已对比 |
| S3 | 推荐方案写明要新增、复用和删除的对象及公开契约 |

## 资源与文件影响

需求、现有设计与代码只读；默认在对话交付设计结论，不自动新建类、脚本、ADR 或 Feature。

## 阻塞、异常与范围变化

缺少关键行为决定时只澄清该缺口；已有实现需要重构时交给[重构调查](<../修复与改进/某处代码总是难改，先调查是否值得重构.md>)，不借设计分析改代码。

## 完成状态与验证标准

一个最小可实施的职责方案及取舍依据已明确，未开始实现或重构。
