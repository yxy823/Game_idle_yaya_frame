# 技术方案是否可行还不确定，先做验证

[返回场景索引](../../scenario-index.md) · [执行步骤](#执行步骤) · [完成标准](#完成状态与验证标准)

## 触发场景与使用时机

想用 GPU 粒子同时显示 2000 个掉落物，但不确定在项目使用的 Godot 版本和目标设备上能否保持 60 FPS，想在决定方案前先跑一个最小探针。

需要的材料：

- 技术假设和通过标准：一句话写明要验证什么、达到什么算可行，例如“2000 个掉落物时帧率不低于 60 FPS”。
- 目标环境（可选）：Godot 版本、显卡或驱动；不写时使用项目配置的 Godot 版本和当前机器，结论只适用于这个环境。
- 预算（可选）：最多花多少时间、允许改动到什么程度；不写时 Agent 先提出预算，请你确认后再构建。

覆盖本问题的 GDD 章节、已有实验记录和项目 Godot 配置由 Agent 直接读取。

## 前置条件与适用范围

项目有覆盖本问题的实质 GDD；缺少时，说明缺的是哪部分设计和 [design-gdd](../../../../../project-source/skills/design-gdd/SKILL.md) 路由，然后停止。你已要求做这次独立的技术实验。本页回答一个技术可行性问题，不修改生产架构，也不进入正式实现。

## 执行步骤

使用[集中提示词库](<../../../prompts/godot-development-prompts.json>)中的“Godot 项目开发 → 需求设计 → 技术方案是否可行还不确定，先做验证”。填入上述材料。当前 Agent 使用 [$technical-validation-godot](../../../../../project-source/skills/technical-validation-godot/SKILL.md)，按[技术验证](../../../../../project-source/methodology/13-debug-console-and-validation.md#技术验证)执行。

**S1｜固定技术判断**

写明问题、相关的已确认 GDD 规则、能回答问题的测量结果和实验边界。Progress 中已有实验仍能回答这个问题时，直接复用。

**S2｜执行最小探针**

在独立的场景和脚本中只实现回答问题所需的部分。问题涉及真实的信号、生命周期或持久化时，运行真实引擎路径并保护实时数据；模拟的转换不能证明集成可用。保留实际命令、版本、参数和原始输出。

**S3｜交付技术结论**

说明可行、受限（写明限制条件）、不可行或未验证，以及适用环境、失败原因、未测内容和后续成本。按[技术验证](../../../../../project-source/methodology/13-debug-console-and-validation.md#技术验证)把入口场景、问题、观察结果和探针代码的处置记在 Progress：作为后续实现参考的保留并说明用途，其余删除。

## 步骤产出与状态变化

| 步骤 | 可继续的依据 |
| --- | --- |
| S1 | 假设、通过标准、预算和相关 GDD 规则已写明；已核对能否复用已有实验 |
| S2 | 探针场景可独立运行；命令、版本、参数和原始输出已保留 |
| S3 | 结论、适用环境、未测内容和探针文件去向已记在 Progress |

## 资源与文件影响

只新增或修改获准的探针场景和脚本；实验记录写在 Progress，不另建报告。GDD、Product 和 Feature 记录不修改；已确认要采纳的决定交回所属来源。

## 阻塞、异常与范围变化

达到预算时停止扩展探针，报告已测部分和缺口。目标版本的 Godot 或测试设备不可用时，不换成其他环境得出结论；保留已有的原始输出，未运行的部分标为未验证。

## 完成状态与验证标准

技术假设有版本和环境明确的真实测量结果，结论与局限已记在 Progress。
