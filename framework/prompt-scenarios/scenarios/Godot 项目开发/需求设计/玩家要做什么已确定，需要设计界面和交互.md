# 玩家要做什么已确定，需要设计界面和交互

## 触发场景与使用时机

玩家要做什么已确定，需要设计界面和交互。

需要的材料：

- 流程与页面范围：玩家流程、页面范围。
- 显示要求：目标分辨率、已确定视觉方向。

## 前置条件与适用范围

项目已有真实 GDD，行为已确认，本次补足当前界面规格。

## 执行步骤

使用[集中提示词库](<../../../prompts/godot-development-prompts.json>)中的“Godot 项目开发 → 需求设计 → 玩家要做什么已确定，需要设计界面和交互”。填入上述材料。本页使用 [$design-ui-spec](<../../../../../project-source/skills/design-ui-spec/SKILL.md>)。

**S1｜拆解交互状态**

当前 Agent 用 design-ui-spec 先读取 GDD 已有设计，再核对入口、动作、可见反馈、错误和空状态。

**S2｜确定页面规格**

按[界面文档边界](../../../../../project-source/methodology/11-specialist-workflows.md#ui-文档边界)确定独立屏幕/弹层与宿主内的从属部件，再说明布局、信息层级、输入方式和状态转换；必要视觉未知由获准实验处理。

**S3｜保存规格引用**

独立界面使用 `docs/ui/<interface>-design.md`，从属部件在宿主分节。第二个界面使用相同控件或对话框行为时，将共用正文迁入 `docs/ui/components/<component-key>-design.md`，消费者改为引用并更新 UI 导航。按实际归属补足布局、状态和专用资源章节；完整表现引用 `docs/presentation/` 中的正文，在交互使用处与末尾“关联游戏表现”导航保留链接。界面规格固定归 UI 文档，原先写在 GDD 的本次规格迁入该文件并更新引用；GDD 保留玩法规则与整体目标，Product 保留交付范围和来源。

## 步骤产出与状态变化

| 步骤 | 可继续的依据 |
| --- | --- |
| S1 | 界面职责服务既定行为 |
| S2 | 关键状态有可观察预期 |
| S3 | 规格可被规划和原型采用 |

## 资源与文件影响

界面/共享组件规格、UI 导航、所属资源章节与必要的 GDD、表现、Product 引用修改；不实现场景、不代做 UX 审核。

## 阻塞、异常与范围变化

玩家行为未定时先澄清并维护 GDD，不用布局设计反向批准玩法。

## 完成状态与验证标准

界面规格覆盖当前流程、状态和输入反馈，关键决定已明确，关联表现的使用位置及导航可定位。
