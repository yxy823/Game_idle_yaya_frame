# 人工验收清单已填好，需要记录结果

[返回场景索引](../../scenario-index.md) · [执行步骤](#执行步骤) · [完成标准](#完成状态与验证标准)

## 触发场景与使用时机

你按清单体验完 F012，已经直接在清单 JSON 里把每项的 status 改成 passed 或 failed 并写了备注，需要 Agent 把结果记录进完成依据。

需要的材料：

- Feature ID（可空）：不提供时用当前对话中正在验收的 Feature。
- 清单路径（可空）：不提供时由 Agent 在 `reports/manual-acceptance/F0XX/` 查找已绑定的清单。

## 前置条件与适用范围

用户已实际体验，并直接在已绑定的清单中填写了各项结果。

## 执行步骤

使用[集中提示词库](<../../../prompts/godot-development-prompts.json>)中的“Godot 项目开发 → 验证与收尾 → 人工验收清单已填好，需要记录结果”。填入上述材料。本页由当前 Agent 使用项目自己的 `manual-acceptance-godot` Skill；[源码入口](<../../../../../project-source/skills/manual-acceptance-godot/SKILL.md>)仅供核对。

**S1｜核对清单**

当前 Agent 读取清单的状态和备注，确认检查项定义未被改动、结果确由用户填写；备注与状态矛盾时只就具体问题澄清。

**S2｜记录结果**

使用 yaya/tools/features/record-feature-completion.py record-acceptance --feature <ID> --checklist <清单路径>。工具列出绑定后变化的文件时，逐个核对；都不涉及本 Feature 才加 --confirm-unrelated-changes 重新记录，否则重新准备清单。

**S3｜报告接受范围**

核对记录结果；全部 passed 即为明确接受，不再重复确认；failed/pending 保留给对应处理。

项目工具命令的使用要求：

- 工作目录：实际游戏项目根目录。
- Python 与调用形式：使用 `docs/methodology-config.json` 中的 `python_executable`，按 `& $projectPython -B <脚本路径> <参数>` 调用，每次立即检查 `$LASTEXITCODE`。
- 参数：尖括号参数替换为实际值。
- 结果边界：命令成功只证明该操作完成。

## 步骤产出与状态变化

| 步骤 | 可继续的依据 |
| --- | --- |
| S1 | 检查项定义未被改动，需要澄清的具体项已列出或为零 |
| S2 | `record-acceptance` 退出码为 0，输出的状态为 `accepted`、`rejected` 或 `pending` |
| S3 | 报告列出通过、失败、pending 的检查项 ID |

## 资源与文件影响

清单的状态和备注保持用户填写的原样；该 Feature 的完成依据 `docs/features/F0XX-evidence.json` 中的人工结果会更新。

## 阻塞、异常与范围变化

清单缺失、检查项定义被改、绑定后变化涉及本 Feature，或状态与备注冲突时保留失败，只澄清具体缺口。

## 完成状态与验证标准

结果已记录，实际接受或失败范围明确；尚需其他完成检查不跳过。

## 流程关联与衔接关系

依据：[记录用户的结论](<../../../../../project-source/methodology/contracts/manual-acceptance-files.md#记录用户的结论>)、[绑定之后内容又有变化](<../../../../../project-source/methodology/contracts/manual-acceptance-files.md#绑定之后内容又有变化>)。

验收记录后 Feature 仍待收尾：记录本身不推进 Stage。只单独发了本提示词（例如在新对话里），或你要求暂停时，再发续接提示词：仍在原对话时用[仍在原对话，想继续暂停的 Feature](<../项目恢复与交接/仍在原对话，想继续暂停的 Feature.md>)，换了对话时用[换了一个对话，想继续上次没做完的 Feature](<../项目恢复与交接/换了一个对话，想继续上次没做完的 Feature.md>)。
