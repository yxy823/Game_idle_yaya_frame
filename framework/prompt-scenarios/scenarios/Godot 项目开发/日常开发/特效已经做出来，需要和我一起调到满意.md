# 特效已经做出来，需要和我一起调到满意

[返回场景索引](../../scenario-index.md) · [执行步骤](#执行步骤) · [完成标准](#完成状态与验证标准)

## 触发场景与使用时机

例如消除的爆炸特效已经接进游戏，你看了觉得连续消除时闪得刺眼、整体节奏拖沓，想一边看一边改，直到满意为止。人工验收时说“这里还要再调一下”，也从这里开始。

需要的材料：

- 要调的效果和你的感受：哪个效果、在什么情况下哪里不对，用自己的话说就行，例如“连续消除三次以上时太闪”。
- 想保持不变的地方（可空），例如“颜色不要动”。
- 其余（所属 Feature、效果的实现方式、当前参数）由 Agent 直接读取。

## 前置条件与适用范围

效果已经实现、能在 Godot 中运行，参数放在 Cue、资源或场景中。调整属于一个已授权的 Feature 或你要求的限定范围实验；没有这类授权时，Agent 只给调整建议，不改文件。效果还没有规划时，先用[有游戏表现想法，需要拆解需求并选择实现方案](<../需求设计/有游戏表现想法，需要拆解需求并选择实现方案.md>)。

## 执行步骤

使用[集中提示词库](<../../../prompts/godot-development-prompts.json>)中的“Godot 项目开发 → 日常开发 → 特效已经做出来，需要和我一起调到满意”。填入上述材料。本页使用 [$feel-tuning-godot](../../../../../project-source/skills/feel-tuning-godot/SKILL.md)。

**S1｜准备对比入口**

当前 Agent 确认效果的参数位置。效果用表现反馈组件（`FeedbackCue`）实现时，在 `dev/` 中准备一个只含这些效果的工作台入口；否则准备可以快速重新运行的场景。

**S2｜一轮轮对比**

每一轮 Agent 说明要改哪一两个参数、改多少、为什么，保留当前版本作为 A；你在同样的情况下对比 A 和 B，说出选哪个、还差什么。Agent 在 Feature notes 中记下这一轮。

**S3｜写回采用的值**

你满意后，Agent 把值保存到 Cue 或参数资源；时长、节奏这类在表现文档中写着的参数，在 Stage 4 之前同步进文档，再继续 Feature 的验证。

## 步骤产出与状态变化

| 步骤 | 可继续的依据 |
| --- | --- |
| S1 | 工作台入口或测试场景的路径已告诉你，你能打开并看到要调的效果 |
| S2 | notes 中每一轮有改动的参数和你的选择 |
| S3 | Cue 或参数资源中是采用的值，消费场景能正确加载；需要时表现文档已更新 |

## 资源与文件影响

修改效果的 Cue、参数资源或场景，以及 `dev/` 中的工作台入口；必要时修改表现或 UI 文档中玩家可感知的参数。不新建调整记录文件。

## 阻塞、异常与范围变化

- 两三轮下来仍然没有接近你想要的效果时，Agent 停下来说明可能的原因：方案本身不合适时转[有游戏表现想法，需要拆解需求并选择实现方案](<../需求设计/有游戏表现想法，需要拆解需求并选择实现方案.md>)；缺合适的图像或声音时标出资源缺口；帧率下降时转[运行出现卡顿，先测量并定位瓶颈](<../资源、性能与数据/运行出现卡顿，先测量并定位瓶颈.md>)。
- 要换一种技术或新增组成部分，属于表现设计的变化，不在调参中悄悄完成。

## 完成状态与验证标准

你对效果满意，采用的值已写回，相关自动测试仍然通过。调参中说的“这个好”不是人工验收；需要验收的 Feature 仍在 Stage 5 正式验收。
