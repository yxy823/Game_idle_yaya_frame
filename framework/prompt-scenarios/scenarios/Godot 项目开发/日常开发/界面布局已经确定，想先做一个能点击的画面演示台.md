# 界面布局已经确定，想先做一个能点击的画面演示台

[返回场景索引](../../scenario-index.md) · [执行步骤](#执行步骤) · [完成标准](#完成状态与验证标准)

## 触发场景与使用时机

例如 UI 规格已写好背包界面的布局和按钮尺寸，在实现依赖它的逻辑之前，要在 Godot 中按目标视口实际看一看、点一遍，确认布局、尺寸与交互可读性成立。

需要的材料：

- 演示台承载：当前 Feature 内的局部检查点，或已规划的视觉基础 Feature ID。不提供时由 Agent 按计划判断并说明。
- 代表性素材：图片、字体等文件的路径。缺少时对应检查保持未验证。
- 演示台要回答的问题（可选）：例如“长物品名在 1280×720 下是否被截断”。不提供时由 Agent 从 UI 规格整理。

已确认的 UI 规格和 Feature 计划由 Agent 直接读取。

## 前置条件与适用范围

UI 规格已确认，需要在 Godot 中按目标视口验证布局、尺寸与交互可读性；本次不重新设计方向，只验证一个方案。画面演示台要回答：目标视口下的空间关系、资源尺寸与裁切、文字可读性、按钮可用性，以及相关的空状态、密集状态和长文本状态是否成立。

## 执行步骤

使用[集中提示词库](<../../../prompts/godot-development-prompts.json>)中的“Godot 项目开发 → 日常开发 → 界面布局已经确定，想先做一个能点击的画面演示台”。填入上述材料。本页使用 [$feature-execute](<../../../../../project-source/skills/feature-execute/SKILL.md>)。

**S1｜固定演示台范围**

当前 Agent 由 feature-execute 调用 [prototype-godot](../../../../../project-source/skills/prototype-godot/SKILL.md)，核对规格和演示台承载位置，明确当前 Feature 内检查点或独立的视觉基础 Feature，写出要回答的问题、目标视口与缩放条件；后续在 `dev/showcase/visual/<主题>/` 中用真实 Godot 场景制作和检查。

**S2｜接入真实交互**

用已确认素材搭建可独立运行的目标界面与必要点击、切换和反馈，不提前铺无关业务。

**S3｜提供体验入口**

完成适用解析和运行检查，在目标视口下实际操作。之后按承载方式分开处理：

- 独立的视觉基础 Feature：按 Stage 4–5 由 [manual-acceptance-godot](<../../../../../project-source/skills/manual-acceptance-godot/SKILL.md>) 准备当前版本的 pending 清单，交用户验收。
- 当前 Feature 内的局部检查点：交用户确认可观察行为，把入口场景、问题和观察结果记在当前 Feature notes，再返回原任务。

## 步骤产出与状态变化

| 步骤 | 可继续的依据 |
| --- | --- |
| S1 | 演示台问题、目标视口和承载方式（局部检查点或视觉基础 Feature ID） |
| S2 | 可独立运行的画面演示台场景路径 |
| S3 | 解析与运行检查结果；独立的视觉基础 Feature 的 pending 清单路径，或当前 Feature notes 中的结论 |

## 资源与文件影响

画面演示台场景、脚本、实际资源引用和当前任务记录修改。UI 规格按[验证与采纳](<../../../../../project-source/methodology/13-prototypes.md#验证与采纳>)只写入演示台实际使用的参数，其他内容只读。

## 阻塞、异常与范围变化

关键规格未定时退出既定的演示台实施，不在本页混入设计探索。缺少代表性素材时，对应检查标为未验证，并取得合适的样本或用户接受的替代品。

## 完成状态与验证标准

画面演示台可运行可点击，目标反馈可观察，实际体验结论与后续依赖明确。
