# 项目约束已确认要改，现在维护规则文档

[返回场景索引](../../scenario-index.md) · [执行步骤](#执行步骤) · [完成标准](#完成状态与验证标准)

## 触发场景与使用时机

已经和 Agent 商定一条开发约束，例如“存档格式变更必须带版本迁移”或“不引入第三方插件”，现在要把它写进项目规则。

需要的材料：

- 已确认的约束：原话或对话中的决定，以及适用范围（哪些模块、哪类任务）。
- 写入位置：知道就写（如 `docs/project-rules.md` 某一节）；不写时由 Agent 按规则职责判断。

## 前置条件与适用范围

变更只涉及项目规则或所属工程规则中的开发约束、协作或工程原则，已有明确写入授权。游戏设计范围与排除项由 [design-gdd](../../../../../project-source/skills/design-gdd/SKILL.md) 按 GDD 正文归属维护，不在本入口重复保存。

## 执行步骤

使用[预设提示词库](<../../../prompts/godot-development-prompts.json>)中的“Godot 项目开发 → 要求变了 → 项目约束已确认要改，现在维护规则文档”。填入上述材料。没有专用 Skill，由当前 Agent 按[规则的增量维护](<../../../../../project-source/methodology/04-project-rules.md#规则的增量维护>)执行。

**S1｜判断规则归属**

当前 Agent 按[职责划分](<../../../../../project-source/methodology/04-project-rules.md#职责划分>)核对现有项目规则、`yaya/agent-rules/` 模块、Skill、工具和 README，确认这条约束应保留在哪里、是否已有覆盖。

**S2｜输出自检报告**

写入前在对话中按[自检报告](<../../../../../project-source/methodology/04-project-rules.md#自检报告>)逐条说明修改前后、归属、重复与冲突、受影响的 Feature 和检查方式。只写下已商定的约束不需要再次批准；报告中出现新增限制或含义、范围变化时，等待你明确决定。

**S3｜修改最小条款**

合并同义要求，说明适用条件与边界，修复直接引用，不扩展所有任务的前置检查。

**S4｜核对冲突并交付**

把实际差异与自检报告对比，静态检查新旧优先关系、链接与授权语义，遵循该入口当前的提交约束提交。规则影响已计划或已完成 Feature 的契约时，指出需要用 `feature-sync` 评估的范围。

## 步骤产出与状态变化

| 步骤 | 可继续的依据 |
| --- | --- |
| S1 | 目标文件与章节已确定，已有覆盖或冲突条目已列出 |
| S2 | 自检报告已在对话中给出，需要你决定的变化已得到答复 |
| S3 | 规则条款已写入，同义条目已合并 |
| S4 | 差异与报告一致、链接有效，提交哈希和需 `feature-sync` 的范围已报告 |

## 资源与文件影响

获准规则文档和必要链接修改；不创建虚构 Feature、不运行业务测试。

## 阻塞、异常与范围变化

归属或行为含义尚不明确时只澄清具体缺口；不能用措辞整理扩大权限。

## 完成状态与验证标准

确认约束已在正确位置保存，没有重复或相冲突的规则正文。
