# 已确认的界面要求要变，需要更新规格并明确影响

[返回场景索引](../../scenario-index.md) · [执行步骤](#执行步骤) · [完成标准](#完成状态与验证标准)

## 触发场景与使用时机

`docs/ui/shop-design.md` 规定购买按钮在列表底部，现在决定改成每个物品行内各有一个购买按钮，而 F005 已按旧规格实现。

需要的材料：

- 确认的变更：哪个界面、改成什么，用原话写；有草图或截图时附上路径。
- 是否同时同步计划（可选）：写明“改完后同步 Feature 计划”时，提交规格后直接运行 feature-sync；不写时只列出受影响的 Feature 和同步入口。

现有规格、GDD、Product、实现和使用这份规格的 Feature 由 Agent 直接读取。

## 前置条件与适用范围

原规格已存在，当前决定会改变界面要求。

## 执行步骤

使用[集中提示词库](<../../../prompts/godot-development-prompts.json>)中的“Godot 项目开发 → 要求变了 → 已确认的界面要求要变，需要更新规格并明确影响”。填入上述材料。本页使用 [$design-ui-spec](<../../../../../project-source/skills/design-ui-spec/SKILL.md>)。

**S1｜定位规格差异**

当前 Agent 比较原决定与新要求，并核对 Product 交付范围。新要求改变玩家行为（例如能买的东西或购买条件）时，先经 [design-gdd](../../../../../project-source/skills/design-gdd/SKILL.md) 更新 GDD，再改界面规格。

**S2｜修改所属规格**

design-ui-spec 更新受影响状态、布局、界面专用资源章节和相关表现引用，核对实际使用处与末尾导航。需要改变表现正文时，由 design-game-presentation 承接同一授权，保留其他有效要求。

**S3｜追查消费者**

核对直接引用和共享设计使用者，包括同一表现的其他界面及各自采用方案，列出受影响的 Feature。在项目根目录运行 `python -B yaya/tools/checks/check-markdown-links.py`，确认受影响的链接和锚点有效，再按项目 `AGENTS.md` 的「Git 与提交」提交规格修改。你已授权同步计划时，提交后使用 [feature-sync](../../../../../project-source/skills/feature-sync/SKILL.md)；否则只交付受影响 Feature 清单和同步入口。

## 步骤产出与状态变化

| 步骤 | 可继续的依据 |
| --- | --- |
| S1 | 新旧要求差异已列出；涉及玩家行为的部分已由 GDD 承接 |
| S2 | UI 规格、界面专用资源章节和表现引用已更新 |
| S3 | 链接检查通过、规格修改的提交哈希、受影响界面与 Feature 清单；已授权时 feature-sync 的结果 |

## 资源与文件影响

既有 UI 规格和必要链接修改；原完成历史不改，当前实现不在此页修改。

## 阻塞、异常与范围变化

新要求与 GDD 设计冲突时先明确所属来源；不能用改规格掩盖 Bug。

## 完成状态与验证标准

新规格已保存并提交，受影响的界面、表现和 Feature 已列出；已授权同步时计划已对齐。

## 流程关联与衔接关系

依据：[编写与采纳](<../../../../../project-source/methodology/11-specialist-workflows.md#编写与采纳>)、[源同步前先提交来源修改](<../../../../../project-source/methodology/11-specialist-workflows.md#源同步前先提交来源修改>)。之后单独同步计划时，使用[要求已经改好，同步受影响的 Feature](<要求已经改好，同步受影响的 Feature.md>)，由它按受影响 Feature 的状态分别处理。
