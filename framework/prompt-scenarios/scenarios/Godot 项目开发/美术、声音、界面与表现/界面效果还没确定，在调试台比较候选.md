# 界面效果还没确定，在调试台比较候选

[返回场景索引](../../scenario-index.md) · [执行步骤](#执行步骤) · [完成标准](#完成状态与验证标准)

## 触发场景与使用时机

商店界面已经有了能点的骨架，购买按钮按下去的反馈拿不准：缩放弹跳、闪光，还是只换一个音效。你想在真实游戏里来回切换着看，选定后让游戏以后就用它。背包格子用 64px 还是 96px 的图标、最长的物品名放不放得下，也从这里开始。

需要的材料：

- 要定的效果：哪个界面的哪一处、拿不准什么，例如“购买按钮按下的反馈”。
- 候选来源（可空）：真实素材路径（例如 `assets/sfx/buy/`），或想试的几种做法；不写时 Agent 按 UI 规格和表现文档提出候选，请你确认。
- 所属 Feature ID（可空）：Agent 从上下文和 Progress 确认归属。只有你明确要求独立试验，或核对后没有所属 Feature 时，才走限定范围比较。
- 预算（限定范围比较时可选）：最多花多少时间、准备几个候选；不写时 Agent 先提出预算，请你确认后再准备。

覆盖本界面的 GDD、UI 规格、Art Bible、项目的调试台说明 `dev/debug/README.md` 和 Godot 配置由 Agent 直接读取。

## 前置条件与适用范围

项目有覆盖本界面用途的实质 GDD；缺少时，说明缺的是哪部分设计和 [design-gdd](../../../../../project-source/skills/design-gdd/SKILL.md) 路由，然后停止。

游戏里已经有这个界面的骨架：`game/<对象>/` 中的最小真实状态和调参资源。还没有骨架时，不在 `dev/` 搭假界面，按[界面的开发顺序](../../../../../project-source/methodology/13-debug-console-and-validation.md#界面的开发顺序)先规划骨架 Feature。界面方向本身还没定时，先用[玩家要做什么已确定，需要设计界面和交互](<玩家要做什么已确定，需要设计界面和交互.md>)写规格。

## 执行步骤

使用[预设提示词库](<../../../prompts/godot-development-prompts.json>)中的“Godot 项目开发 → 美术、声音、界面与表现 → 界面效果还没确定，在调试台比较候选”。填入上述材料。当前 Agent 使用 [$debug-console-godot](../../../../../project-source/skills/debug-console-godot/SKILL.md)，按[调试台](../../../../../project-source/methodology/13-debug-console-and-validation.md#调试台)执行；插槽、候选、预设和采纳的具体机制见[调试台共享代码](../../../../../project-source/defaults/dev/debug/_shared/README.md)。

**S1｜把效果接到调参资源**

当前 Agent 找到这个效果在游戏里的位置。参数还写死在代码或场景里时，在当前授权内提到 `game/<对象>/tuning/` 下的调参资源；每份调参资源在调试台里就是一个插槽。

**S2｜放入候选与固定局面**

当前 Agent 在 `dev/debug/<对象>/slots/<插槽>/<候选>/` 放入候选，素材附来源与许可说明，并给插槽和参数起中文名。需要反复看同一过程时，登记固定局面或试播动作。然后更新 `dev/debug/README.md` 中的登记，告诉你启动命令和要看的地方。

**S3｜在调试台比较并采纳**

你在项目根目录用 `dev/debug/README.md` 中的启动命令打开调试台：选候选、拖参数，按 ` 键在“当前改动”和“游戏原值”之间切换比较；满意后点“采纳到游戏”并确认一次。各操作的路径见[调试台使用场景](../../../../../project-source/defaults/dev/debug/_shared/usage-scenarios.md)。

**S4｜收尾并提交**

当前 Agent 按[收尾步骤](../../../../../project-source/defaults/dev/debug/_shared/README.md#收尾步骤)让采纳的文件成为正式资源：补回 UID，运行资源格式检查和所选测试（至少包括写入资源所属组件的测试和依赖方向测试），然后提交。UI 规格或表现文档链接被写入的调参资源，不抄数值；比较与采纳在 Feature notes 中记一两行，限定范围比较记在 Progress。

## 步骤产出与状态变化

| 步骤 | 可继续的依据 |
| --- | --- |
| S1 | 要比较的效果已由调参资源承载，你知道它对应哪个插槽 |
| S2 | 候选和固定局面在调试台中可见；你已拿到启动命令 |
| S3 | 调试台提示“已采纳”；`dev/debug/adoption-log.md` 有待收尾的记录 |
| S4 | 收尾提交哈希和测试结果；文档链接与记录已写好 |

## 资源与文件影响

- 修改：`game/<对象>/tuning/` 下的调参资源，被采纳的候选移入 `game/<对象>/` 后的文件，`dev/debug/<对象>/` 下的候选、插槽登记与固定局面，`dev/debug/README.md` 的登记，以及链接调参资源的规格位置。
- 保留：落选的候选留在 `dev/`（正式导出不包含），你要求时才删除；被替换的实现留在游戏目录，仍可在调试台选回，发布前由你决定删除或排除。

## 阻塞、异常与范围变化

- **还没有这个界面的骨架**：Agent 停下并说明，按 [feature-plan](../../../../../project-source/skills/feature-plan/SKILL.md) 规划骨架 Feature，对应提示词在“规划 Product 与 Feature”分组，例如[当前模块的需求已确认，准备做项目的第一份 Feature 计划](<../规划 Product 与 Feature/当前模块的需求已确认，准备做项目的第一份 Feature 计划.md>)。
- **视觉决策 Feature 已规划但还没开工**：先用 [feature-execute](../../../../../project-source/skills/feature-execute/SKILL.md) 走完 Stage 0–2（见[Feature 已规划并可开始，现在实施这一项](<../实施与调参/Feature 已规划并可开始，现在实施这一项.md>)），在 Stage 3 中从本页 S1 开始。
- **缺代表性素材**：对应候选标为未验证；用方块或占位文件名比较不算数。
- **达到预算**：限定范围比较停止增加候选，用已有候选取得你的比较。
- **你还没比较**：本页停在 S3 等待。
- **编辑器开着或采纳要等下次启动**：按调试台状态栏的提示做；收尾需要关闭编辑器时，Agent 会先请你保存并关闭。
- **采纳的资源属于已完成的 Feature**：被写入的调参资源被已完成 Feature 的文档或 AC 链接时，Agent 收尾提交后报告，按[完成后再调值](../../../../../project-source/methodology/13-debug-console-and-validation.md#完成后再调值)转到[要求已经改好，同步受影响的 Feature](<../要求变了/要求已经改好，同步受影响的 Feature.md>)。

## 完成状态与验证标准

你已在调试台采纳到游戏，收尾已提交，所选测试通过；或你决定这次不采纳，决定已记录。采纳到游戏不是人工验收：属于 Feature 时，该 Feature 继续 Stage 4 的自动验证和按界面任务试用，再由你在 Stage 5 验收游戏原值。
