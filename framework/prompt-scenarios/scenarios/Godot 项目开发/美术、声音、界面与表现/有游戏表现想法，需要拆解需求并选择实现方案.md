# 有游戏表现想法，需要拆解需求并选择实现方案

[返回场景索引](../../scenario-index.md) · [执行步骤](#执行步骤) · [完成标准](#完成状态与验证标准)

## 触发场景与使用时机

知道想让玩家感受到什么，或已有“领取时图标飞过去、按钮亮一下”这样的描述，需要整理成可实现的表现要求并比较技术方案。

提供体验目标或口语描述（原话即可）、在哪里触发，以及已确定的约束。已有实现时可以给出场景或脚本路径；GDD、UI 和已有表现文档由 Agent 直接读取。材料不齐时从现有信息开始，不要求先选 Shader 或粒子。

## 前置条件与适用范围

本页负责表现规划，可支持从体验目标形成初期 GDD 设计；运行实验和正式实现仍需相关范围的真实设计。本页不编写运行代码，不制作图片或音频，不检索本地资源库。

## 执行步骤

使用[集中提示词库](../../../prompts/godot-development-prompts.json)中的“Godot 项目开发 → 美术、声音、界面与表现 → 有游戏表现想法，需要拆解需求并选择实现方案”。填入上述材料。当前 Agent 使用 [$design-game-presentation](../../../../../project-source/skills/design-game-presentation/SKILL.md)，执行时采用游戏项目自己的 Skill 副本。

**S1｜描述一次完整表现**

读取相关设计和已有表现导航，从触发、玩家看到或听到的过程到结束状态说明目标。按[表现文档边界](../../../../../project-source/methodology/11-specialist-workflows.md#游戏表现文档)，同一触发时刻与感知结果的不同来源共用一份正文，例如商店和奖励的入包反馈共用 `item-added.md`；独立奖励揭晓过程可单独成文，结尾引用已有入包正文。例如“背包物品入包”先明确玩家如何识别到达，再决定是否需要飞行、闪光或数值变化。

**S2｜拆分要求并比较方案**

按独立行为或控制需要拆分组成部分，按需引用 Shader、粒子等语义参考，形成标准需求。比较已有实现、序列帧、Shader、粒子、Tween 或 AnimationPlayer 的适用性；整体和组成部分都可以保留候选。候选不要求全部制作，具体算法、节点与源码留给实现。

**S3｜保存采用关系和资源规格**

在 `docs/presentation/<scope>.md` 保存过程、组件要求、候选及当前采用组合。比如“奖励入包采用图标飞行 B＋目标位置反馈 A”，分别引用两部分，避免为每种组合复制全文。方案所需纹理的规格、准备状态、源与目标位置写入该方案；已有共享资源按[资源规格归属](../../../../../project-source/methodology/11-specialist-workflows.md#资源需求与交接)引用组件正文或 Bible 的“共享资源规格”章节。尚未确认的选择保持待定，不写成已采用。

组件被第二份独立表现采用或明确纳入候选时，按表现文档约定将其共同要求、候选与资源规格迁入 `docs/presentation/components/<component-key>.md`，各父表现改为引用并保留自己的使用上下文。多个界面消费同一份表现时，组件仍在该表现正文中；已建立的共享组件只要仍有消费者就保留固定路径。

**S4｜连接设计、实现与验收入口**

UI 在实际交互位置及末尾“相关游戏表现”导航引用正文；角色死亡等非 UI 表现由对应 GDD 章节承接。维护表现总览，已有实现时记录真实实现及消费位置；尚未实现时说明缺口。验收章节链接原任务的条件、运行入口及已有报告或完成证据，不另存结果记录文件。

## 步骤产出与状态变化

| 步骤 | 可继续的依据 |
| --- | --- |
| S1 | 触发、玩家看到或听到的过程和结束状态已写出 |
| S2 | 各组成部分有标准要求及适用候选 |
| S3 | `docs/presentation/<scope>.md` 已保存，当前采用组合与候选分开列出，资源规格写在所属方案或已有共享章节 |
| S4 | 能从相关 GDD/界面找到采用方案及已有实现、验收入口 |

## 资源与文件影响

新增或更新所属表现文档、实际共享组件及其导航；UI/GDD 引用或对应资源规格章节受本次修改影响时，一并更新。原实现、资源文件和历史验收证据保持原状；多个界面共用表现时引用同一正文并保留各自使用信息。

## 条件分支与路径规则

具体可行性未知时，原任务可使用 `technical-validation-godot` 做获准的技术验证；几种做法要在真实游戏里比较时，用 `debug-console-godot` 把它们放进调试台；正式实现沿用已有开发任务，表现与 Feature 不要求一一对应。只有已采纳要求和当前获准方案进入实施。实现任务可在保留既定表现要求的前提下调整手段，并在最终验证前同步实际采用、文件与接入变化；目标改变按设计变更处理。

## 阻塞、异常与范围变化

缺少某方案的纹理时，继续描述运动、数量感觉、持续时间和触发方式，把纹理规格及缺失事实保留在方案内。仅暂停依赖缺失决定或文件的工作。没有真实运行或人工反馈时，不能把规划完成或实现可用写成体验已接受。

## 完成状态与验证标准

本次可确定的表现要求、候选、采用关系及资源依赖已保存，未决选择明确，引用可定位。用当前场景走一遍设计、方案、实际实现及验收入口；不存在的实现或验收记录如实留为缺口。
