# 想试做一个还不确定要不要的玩法

[返回场景索引](../../scenario-index.md) · [执行步骤](#执行步骤) · [完成标准](#完成状态与验证标准)

## 触发场景与使用时机

游戏已经能玩，你想加一个玩法或功能，但不确定它好不好玩、值不值得做，想先做出来玩一玩，不要就整个丢掉。例如给卡牌战斗加一个连击系统，改动会碰到主线代码。游戏已有骨架、只需比较几种规则候选时，用调试台的逻辑候选，不用这个入口。

## 前置条件与适用范围

在实际游戏仓库执行，`docs/gdd/` 有覆盖相关系统的实质设计。你能说出要试的东西和要回答的问题，例如“连击会不会让战斗太快”。做法的正文是 13 号规范的[试做玩法](../../../../../project-source/methodology/13-debug-console-and-validation.md#试做玩法)。

## 参与角色与职责边界

当前 Agent 用 [worktree-create](../../../../../project-source/skills/worktree-create/SKILL.md) 开实验分支并在里面试做。你试玩后决定留下还是丢掉；Agent 的试玩和截图不能代替这个决定。这个入口不改 GDD、Product 或 Feature 记录，不合并分支，也不删除分支或目录。

## 执行步骤

使用[预设提示词库](../../../prompts/godot-development-prompts.json)中的“Godot 项目开发 → 实施与调参 → 想试做一个还不确定要不要的玩法”。补充要试的东西、要回答的问题、怎样算值得留下，以及预算。

**S1｜开分支并记下问题**

Agent 从主线开实验分支，在主目录的 Progress 记一条独立实验：问题、留下的标准、分支和目录、预算。

**S2｜做最小可玩版本**

只做能回答问题的部分，不补完整测试。运行游戏前保护主线的 `user://` 存档和设置，因为 worktree 不隔离这些数据。

**S3｜交给你试玩并记下结论**

Agent 给出试玩入口和要观察的点。你决定后，Agent 在 Progress 的实验条目写明结论。

## 资源与文件影响

新增一个实验分支和目录，主目录 Progress 多一条实验记录。实验分支里的代码不进 Feature 列表、测试登记表和完成证据。

## 阻塞、异常与范围变化

超出预算、需要改动问题之外的系统，或主线数据可能被改到时，Agent 停下问你。试做中发现要先定下的设计规则时，回到 GDD 讨论，不在实验里替你决定。

## 完成状态与验证标准

试做版本能从给出的入口启动，并能回答写下的问题；你已试玩并给出决定，Progress 写明了结论。只做出版本、还没试玩时，停在等你试玩。

## 流程关联与衔接关系

决定留下时，用[已有模块的玩法要求变了，需要更新需求](<../要求变了/已有模块的玩法要求变了，需要更新需求.md>)把设计写回 GDD，再按需求变化的路线拆成 Feature；实现这些 Feature 时可以用[已选定 worktree 中的成果，带回目标分支](<已选定 worktree 中的成果，带回目标分支.md>)把实验代码带进来作为起点。决定丢掉时，放弃的理由可以由 `design-gdd` 记进 `docs/unadopted-ideas.md`；分支和目录先保留，删除要你明确同意。
