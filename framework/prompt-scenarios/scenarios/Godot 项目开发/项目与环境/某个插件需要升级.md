# 某个插件需要升级

[返回场景索引](../../scenario-index.md) · [执行步骤](#执行步骤) · [完成标准](#完成状态与验证标准)

## 触发场景与使用时机

`addons/` 里的某个插件有了新版本，例如 gdUnit4 上游修掉了你遇到的运行器问题，或 lint 插件新增了想用的检查，想把它换成新版本，同时保留本地补丁和插件里保存的个人数据。

需要的材料：

- **插件名**：`addons/` 下的目录名，例如 `gdUnit4`。一次只升级一个；想升级多个时，每个插件分别使用一次本场景。
- **目标版本或上游提交**：发布版本号或提交哈希。不提供时，Agent 查出上游最新的正式发布版本，写进 S1 的方案，由你批准方案时一并确认。

插件的上游地址、本地补丁说明和启用状态由 Agent 从插件目录和 `project.godot` 读取。

## 前置条件与适用范围

升级开始时工作区要干净。本场景只替换一个插件的版本；升级 Godot 本身用[想把 Godot 升级到新的补丁版本](<想把 Godot 升级到新的补丁版本.md>)。

## 执行步骤

使用[预设提示词库](<../../../prompts/godot-development-prompts.json>)中的“Godot 项目开发 → 项目与环境 → 某个插件需要升级”。填入上述材料。本页先由当前 Agent 使用 [$engineering-change-plan](<../../../../../project-source/skills/engineering-change-plan/SKILL.md>) 建立维护 Feature，再用 [$feature-execute](<../../../../../project-source/skills/feature-execute/SKILL.md>) 实施；具体做法按 07 的[升级插件](<../../../../../project-source/methodology/07-engineering-change.md#升级插件>)执行。

**S1｜建立升级的维护 Feature**

当前 Agent 用 engineering-change-plan 的 maintenance 模式，按[维护 Feature 契约](<../../../../../project-source/methodology/07-engineering-change.md#维护-feature-契约>)写明插件名、旧版本、目标版本和上游来源，要保持成立的行为（全量测试，lint 插件还有升级前的 lint 结果），以及回滚方式：撤销替换插件目录的提交。展示方案，取得你的批准后写入；当前请求已明确批准具体方案时沿用。

**S2｜确定来源，找出本地修改和用户数据**

对应 07 的第 1、2 步。当前 Agent 从上游取固定的版本或提交，记下来源地址和版本号；逐项判断 `YAYA_PATCH.md` 等本地补丁说明中的补丁是否已在新版本修复，列出需要重新应用的补丁；备份插件目录中保存的用户数据或偏好（例如看板数据）。升级的是 lint 插件时，此时先对全部脚本运行一次 lint，保留结果用于 S5 对比，方法见 `yaya/methodology/contracts/gdscript-lint.md` 的「直接运行」。

**S3｜替换插件目录**

对应 07 的第 3 步。当前 Agent 用新版本替换整个插件目录，再恢复 S2 保留的补丁和数据，不手工合并新旧文件。

**S4｜扫描与稳定性检查**

对应 07 的第 4 步。当前 Agent 在项目根目录运行两次编辑器扫描（`$projectGodot` 的取法见[首次 Godot 扫描](<../../../../../project-source/tools/README.md#首次-godot-扫描>)）：

```powershell
& $projectGodot --headless --editor --path . --quit 2>&1 | Tee-Object -FilePath <日志路径> | Out-Host
$LASTEXITCODE
git status --short
```

第一次扫描为新插件文件生成的 `.uid`、`.import` 随插件目录一起提交；出现其他变化时先查原因。第二次与运行前相比没有新增或改写的文件，不要求整个工作区干净。同时核对 `project.godot` 中该插件的启用状态和注册的 Autoload 没有意外变化。日志路径按[报告与清理](<../../../../../project-source/methodology/09-records-reports-and-handoff.md#报告与清理>)放在该 Feature 的报告目录。

**S5｜验证并交付**

对应 07 的第 5 步。当前 Agent 检查 S4 日志中没有该插件的新错误，运行全量测试（`run-gdunit-tests.py --feature F0XX --scope full`，参数见 [run-gdunit-tests.py](<../../../../../project-source/tools/README.md#run-gdunit-testspy>)）。升级的是 gdUnit4 时，再按 `yaya/agent-rules/70-tests/gdunit4-profile.md` 的「运行器版本变更」逐项核对；升级的是 lint 插件时，对全部脚本运行 lint，与 S2 的结果对比。全部通过后在 Feature notes 写明来源地址、新旧版本和重新应用的补丁，按 feature-execute 的完成条件交付。

## 步骤产出与状态变化

| 步骤 | 可继续的依据 |
| --- | --- |
| S1 | 维护 Feature（插件、新旧版本、来源、要保持的行为、回滚方式）已获批写入，`check-feature-list` PASS |
| S2 | 来源地址和固定版本；需要重新应用的补丁清单；用户数据的备份位置；lint 插件的升级前 lint 结果 |
| S3 | 插件目录已整体替换，补丁和用户数据已恢复 |
| S4 | 扫描生成的文件已随插件提交或已查明原因；第二次扫描没有新的文件变化；插件启用状态和 Autoload 未变 |
| S5 | 编辑器日志、全量测试和对应的专项核对结果；Feature notes 中的版本与补丁记录；提交哈希 |

## 资源与文件影响

- 被升级插件在 `addons/` 下的目录：整体替换；本地补丁和用户数据要恢复，不能丢失。
- 扫描为新插件文件生成的 `.uid`、`.import`，随插件目录一起提交。
- 维护 Feature 记录和验证报告。
- 其他插件不改动。

## 阻塞、异常与范围变化

- **本地补丁无法应用到新版本**：停下说明冲突的补丁和原因，不手工拼接新旧文件。
- **验证出现新错误或新失败**：属于项目代码需要适配新版本的，在本 Feature 内修复；无法解决时撤销替换插件目录的提交（新建提交，不改写历史），Feature 保持未完成。

## 完成状态与验证标准

插件已换成确认的版本，本地补丁和用户数据保留，第二次扫描没有新的文件变化，没有该插件的新错误，全量测试和对应的专项核对通过，维护 Feature 按完成条件交付。
