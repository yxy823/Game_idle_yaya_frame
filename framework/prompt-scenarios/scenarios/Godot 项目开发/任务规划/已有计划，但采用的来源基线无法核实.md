# 已有计划，但采用的来源基线无法核实

[返回场景索引](../../scenario-index.md) · [执行步骤](#执行步骤) · [完成标准](#完成状态与验证标准)

## 触发场景与使用时机

例如修订记录的最后一条没有可用的 `synced_at_commit`，或者新纳入了一份 `docs/ui/` 规格，却查不出旧锚点当时是否覆盖过它；这时不能再按锚点差异同步。

需要的材料：

- 对齐范围：要重新对齐的 Product 或 Feature ID。不提供时，Agent 先提出当前文档对齐的范围，等你确认。
- 已知的历史缺口（可选）：例如“早期规划提交被合并过”。不提供时由 Agent 从 Git 和修订记录核对。

现有计划、修订记录和当前来源由 Agent 直接读取。

## 前置条件与适用范围

不能证明旧锚点或新专业来源的历史覆盖，本次恢复可解释的当前对齐。

## 执行步骤

使用[集中提示词库](<../../../prompts/godot-development-prompts.json>)中的“Godot 项目开发 → 任务规划 → 已有计划，但采用的来源基线无法核实”。填入上述材料。本页使用 [$feature-sync](<../../../../../project-source/skills/feature-sync/SKILL.md>)。

**S1｜尝试恢复锚点**

当前 Agent 先按[从历史中恢复锚点](<../../../../../project-source/skills/feature-sync/references/anchor-and-fallback.md#从历史中恢复锚点>)核对规划提交和计划内容；恢复不了时，说明缺失的历史证据，区分不存在与未读到，不猜补旧差异。

**S2｜对照当前要求**

按[提出当前文档对齐](<../../../../../project-source/skills/feature-sync/references/anchor-and-fallback.md#提出当前文档对齐>)，在对齐范围内阅读完整的当前来源并与计划比较，报告对齐缺口和未知历史，注明检查的 HEAD。

**S3｜确认并修订计划**

按[阶段 3：用户审阅与决定](<../../../../../project-source/skills/feature-sync/SKILL.md#阶段-3用户审阅与决定>)只就尚未批准的实质选择询问；然后修订计划，并按[记录修订](<../../../../../project-source/skills/feature-sync/references/anchor-and-fallback.md#记录修订>)写明历史未知。

**S4｜检查并提交**

在游戏项目根目录运行：

```powershell
$projectConfig = Get-Content -LiteralPath 'docs/methodology-config.json' -Raw | ConvertFrom-Json
$projectPython = $projectConfig.python_executable
& $projectPython -B yaya/tools/checks/check-feature-list.py
$LASTEXITCODE
```

打印 `FEATURE LIST CHECK: PASS` 且退出码为 0，只证明 Feature 记录的结构、引用和依赖一致，不证明需求覆盖或实现完成。检查通过后按 feature-sync 的提交约定提交计划。

## 步骤产出与状态变化

| 步骤 | 可继续的依据 |
| --- | --- |
| S1 | 恢复出的锚点，或缺失历史证据的说明 |
| S2 | 当前文档对齐报告：检查的 HEAD、对齐缺口、未知历史 |
| S3 | 未批准动作已有用户决定；修订记录写明历史未知 |
| S4 | `FEATURE LIST CHECK: PASS` 和计划提交哈希 |

## 资源与文件影响

现有计划及本次修订记录修改；不制造来源收据、旧提交或虚构 R000。

## 阻塞、异常与范围变化

关键来源本身未确认时保留待定，不把恢复任务当批准所有当前文字。

## 完成状态与验证标准

获准范围已按当前有效来源对齐，无法恢复的历史明确记录，检查通过并已提交。
