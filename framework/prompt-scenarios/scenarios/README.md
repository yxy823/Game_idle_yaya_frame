# 场景速查手册的编写与维护

本页面向场景页的编写者，约定收录范围、文件位置、标题、内容栏目和核对方法。使用者从[场景索引](scenario-index.md)进入。新增场景或实质改变职责时，先按[职责设计准则](../../maintenance/design-guidelines/README.md)评价。

## 收录什么

场景速查手册收录项目开发和框架维护中的具体情境：正常推进、要求变化、问题处理和中断续接。常见的流程中断、环境故障和证据恢复也在范围内，收录边界遵循[使用范围](../../README.md#使用范围)。与 Godot 项目手册的分工见[两本手册的分工](../../README.md#两本手册的分工)。

每篇场景页：

- 交付**一个**可验证的结果。
- 按 Project 区分在哪个仓库执行，不把框架维护的操作带进游戏项目。
- 对应一条同名的专用提示词，规则见[提示词与场景准则](../../maintenance/design-guidelines/prompts-and-scenarios.md)。唯一的例外是「只读专项审核」：专题条目要与「专项审核通用模板」拼接使用，专题页只说明拼接方法和完成标准。

用户能辨认的入口不同时才拆成两页，判断方法见[入口按用户能否辨认划分](../../maintenance/design-guidelines/prompts-and-scenarios.md#一条提示词对应一篇场景)和[入口的情境分层](../../maintenance/design-guidelines/prompts-and-scenarios.md#入口的情境分层)。具体的错误码写在对应页内。

当前各领域的覆盖范围如下。具体有哪些场景、各自的前提和出口，以[场景索引](scenario-index.md)为准，这里不登记名称、数量或路径。

| 领域 | 覆盖内容 |
| --- | --- |
| 框架维护 | 评估、借鉴、修复、删减、目录整理、静态与动态审核各有入口；维护源与外部验证项目分开 |
| 创建与环境 | 创建项目；环境的配置、更新、路径恢复和首次扫描各自分开 |
| 需求与专业来源 | `design-gdd` 从零形成或维护 GDD，整体范围归《设计范围与边界》，未决设计归《开放问题》；`design-balance` 维护数值主题，`product-author` 只维护交付范围；专业文档引用已有细节；术语由 `project-terminology` 维护，开发约束归项目规则 |
| 任务规划 | 先预拆分，再逐个细化 Product 并拆分 Feature；首次基线 R000、后续追加分开处理，来源变化和基线无法核实合并为同步 Feature 一个入口，由 Agent 判断后分流；保留 ID 和真实完成历史 |
| 实现与修复 | 新任务执行、调试台调参与采纳、完成后再调值、Bug 修复（交付前后由 Agent 按完成证据分流）、反馈分诊、重构和明确目标的维护；`feature-execute` 负责完整交付，专业方法不另设 Stage |
| 素材与诊断 | 资源的准备、接收、技术审核、新增与替换分开；方向已定的变化要追查使用方；临时观测与持久指标分开，测量诊断与优化分开 |
| 验证与人工验收 | 解析与 lint、自动测试、实际场景、独立审核、清单准备和人工结果登记分开，结果写在清单里还是对话里由 Agent 判断；不属于 Feature 的组件测试用 `--target` |
| 恢复与交接 | 测试证据不可用时，由 Agent 判断是报告路径错误、原件缺失、内容过期还是运行中断；同目录暂停、切换、换对话续接都保留真实停点，当前工作有无 Feature 由 Agent 判断 |
| 知识 | 只读总结、写入知识和实现脚本各有入口；先查已有覆盖，复盘不自动新增规则 |

## 目录与单篇范围

路径是 `framework/prompt-scenarios/scenarios/<Project>/<分类>/<提示词名称>.md`，各层使用提示词库中的准确名称：

- **Project 文件夹**：区分项目开发与框架维护。
- **分类文件夹**：按[入口的情境分层](../../maintenance/design-guidelines/prompts-and-scenarios.md#入口的情境分层)混合组织：出错、要求变了、回来与离开这类转折情境单独成组，正常推进的工作按处理对象成组；不另设状态目录或英文别名。
- **场景文件**：文件名就是提示词名称，影响处理方式的状态写进名称；正文一级标题与文件名（去掉 `.md`）一致。
- **README 与索引**：放在 Project 目录之外，只提供编写约定、选择提示和链接。

一篇场景要有明确的入口、一个处理目标和一个可验证的出口。多个步骤可以共同完成一个目标；出现用户能辨认的不同入口或不同的任务归属时，就拆页。区分条件只有 Agent 查得到时，两套处理路径合并在一页，由 Agent 在第一步判断后分流，规则见[提示词与场景准则](../../maintenance/design-guidelines/prompts-and-scenarios.md#一条提示词对应一篇场景)。不要按单个命令拆成碎片。

新写一篇之前先查已有场景：同义的场景和提示词合并，保留最容易识别的标题。导航可以从多处链接到同一页，但一页只对应一条提示词。

## 标题与措辞

- **标题先写状态，再写事情**：例如“Feature 已规划并可开始，现在实施这一项”“素材文件已经收到，先登记来源并核对是否齐全”。标题要在目录里能独立看懂，不能只写“Bug 修复”“验证恢复”。具体的测试、试玩等情境写进“触发场景”。
- **状态要写准**：区分“代码写完”“测试通过”“待人工验收”“完成交付”，口语化不能导致状态模糊。依赖“是否已正式交付”分流时，写清要核对哪个完成状态和记录，不靠标题、测试结果或某次提交来推断。
- **名称与术语**：保留 Feature、Product 等准确名称，必要的术语在首次出现时简短解释。术语的统一写法见[框架术语](../../terminology.md)。
- **路径与示例**：说明路径属于哪个项目、示例 ID 要替换成什么。
- **同类场景保持一致**：采用相同的入口判断依据和例外分类；只有任务归属确实不同时才保留差异。

排版遵循[框架写作指南](../../../.agents/skills/technical-documentation-writing-yaya/references/writing-guide.md#表达与排版)，操作内容按[流程文档参考](../../../.agents/skills/technical-documentation-writing-yaya/references/procedure-writing.md)组织。

## 栏目怎样使用

栏目采用[11 类信息及其边界](../../../.agents/skills/technical-documentation-writing-yaya/references/procedure-writing.md#11-类信息及其边界)中的名称、边界和顺序：

- 只写有内容的栏目，空栏目直接省略，不写“无”或“不适用”。会影响执行的未知信息要写明缺口，不能当作空栏目省略。
- 标题不带栏目编号，以免省略栏目后出现编号空缺。
- 默认只写一条正常路径；没有分支就省略分支栏目。需要在两套方法之间选择时：用户能分辨的，先收窄入口或拆页；只有 Agent 查得到的，在第一步写明判断依据，后续步骤按判断结果分别写出。正常等待用户体验属于当前步骤的待完成状态，不写成异常。
- 执行步骤用 `S1｜动作名称` 编号，标题与说明分段，S 步骤本身不再加 `1.` 这样的数字序号；一个 S 步骤内部有先后顺序的几个小操作，可以用编号列表写。“步骤产出”表使用同样的 S 编号。编号只帮助阅读，不新增 Stage 或项目状态。
- 短场景没有导航价值时省略流程概览，避免几个栏目重复同一段话。

## 写到什么程度

读者读完一篇场景页，必须能知道：第一步做什么、要提供哪些材料、由谁操作、会改动什么、什么时候结束。

### 不要在页内重复的内容

以下约定统一写在[场景索引的「怎样使用场景页」](scenario-index.md#怎样使用场景页)，场景页不再逐篇重复：已有对话直接补齐材料、默认由当前 Agent 执行、授权在场景之间延续、出口之后转入所属场景、出口不等于 Feature 交付、人工接受要真实取得。只有某篇场景的做法与这些约定不同时，才在页内说明。

### 执行步骤

- **开头**：写出提示词在库中的完整位置（Project → 分类 → 名称）、需要填写的输入，以及实际负责的 Agent 和 Skill。生成项目使用自己的 `.agents/skills/<名称>/SKILL.md`，源码链接只供核对。
- **每个 S 步骤**：写明执行者、操作对象和使用的入口。一个 Skill 贯穿全篇时在开头说明一次，只在切换方法或角色时就近标明，例如独立 Bug 先由 `engineering-change-plan` 规划，再由 `feature-execute` 实施。
- **执行者**：区分当前 Agent 和已配置的专用角色。没有专用 Agent 或 Skill 时，直接写“当前 Agent 使用已有方法”，不编造“Bug Agent”“原型 Skill”之类的名称，也不把切换 Skill 写成自动委派。独立审核只在有实际授权时启用。
- **命令**：写出实际脚本和必要参数，不能只写“运行相关检查”；命令前写明工作目录、必要准备、需要替换的参数和覆盖等副作用。解释结果的具体含义，不把退出码为 0 说成整个任务完成。
- **授权**：保留用户已明确的授权和限制，不因拆页而重新索取同一确认。

### 与提示词的关系

提示词正文分别维护在 [Godot 开发提示词库](../prompts/godot-development-prompts.json)和 [Yaya 框架维护提示词库](../prompts/yaya-maintenance-prompts.json)。场景页链接到所属的库，面向使用者写清入口名称、用途、所需输入、实际命令和必要的约束提醒。

- 入口条件和完成条件可以用使用者的话在页内重述，方便不打开 JSON 也能判断是否适用、何时结束。
- 提示词中的授权、约束和执行原则不整段复制到页内，也不复述详细的 Git 提交规则；需要时写“遵循该入口当前的提交约束”。
- 提示词的字段要求见[字段与审核原则](../../maintenance/design-guidelines/prompts-and-scenarios.md#提示词字段与审核原则)。同步修改时，核对场景页与提示词在输入、授权、验证和出口上的含义一致。
- “完成状态”只写目标达成的情况；受阻和待决定写在对应的停点说明里。

### 资源与文件影响

按实际的项目对象列出读写影响。要保护的核心约束（例如原验收条件、完成历史）写在对应对象的那一行。场景页只提供执行信息，尚未完成的编写工作记在[框架待办](../../progress.md)中。

## 写完怎样核对

- 从标题、前提、步骤到出口，是否始终围绕同一个目标；读者不必在页内重新选择另一套流程。
- Project、分类和文件路径与提示词名称一致；正文一级标题与文件名一致。路径核对用[提示词与场景路径检查](../tools/README.md#提示词与场景路径检查)，它不读正文，标题、输入、步骤和出口由作者自查，也不为此增加元数据或手工登记。
- 文章解释的是现有的规则、文件和工具，没有新增流程、状态、验收门槛或自动同步。
- 步骤与产出的编号对应，内部链接和来源锚点有效；只链接已有完整正文的页面，未扩展的能力写在范围说明里，不建空壳页面。
- 两本手册没有互相引用，读者必需的动作没有藏在另一本手册里。
- 没有按模板凑出来的空话。常见的三种：“触发场景”第一句照抄标题，改写成具体情境或删掉；材料行写成“验证权限：验证权限”这样的标签复述，改写成用户要提供的具体东西和不提供时的默认，Agent 能读到的不列；依据只链接整个文件，改为链接起决定作用的那一节。
- 修改场景入口后，同步 JSON、同名路径、[场景索引](scenario-index.md)和受影响的引用，不新建流程记录文件。

阅读时还要检查：读者能否找到自己的情况、能否明确何时开始和结束、步骤与产出是否便于对照，以及是否还有需要拆开的内容。链接检查通过不代表阅读体验良好。
