# Yaya 真实游戏试用

用户在做一个要发布的游戏，同时用它试用框架：用户自己给项目会话发提示词，框架仓库里的观察会话只读项目、记录过程、找出框架问题。本 Skill 只供框架仓库使用，不随游戏项目分发。试用是为了把游戏做出来，开发顺序由游戏的 GDD 决定，不为覆盖 `framework/todo.md` 改游戏；游戏碰不到的待办条目不测。

## 分工

| 角色 | 在哪里 | 做什么 | 不做什么 |
| --- | --- | --- | --- |
| 用户 | Codex 或 Claude Code，自己开线程 | 发提示词，回答项目会话的问题，验收画面和手感 | — |
| 项目会话 | 工作目录为游戏项目 | 按项目 `AGENTS.md` 和 Skill 真实开发 | 不告诉它这是试用 |
| 观察会话（本 Skill） | 框架仓库，游戏项目挂为附加目录 | 建议下一步和提示词；读项目提交、`docs/progress.md` 和会话日志，记录每一步和问题，包括用户没发现的；修框架 | 阶段进行中不改项目文件；不替项目会话开发，不调用 Codex 或子智能体替项目干活 |
| 子会话 | 观察会话为某个专题开的会话，例如 GDD 草稿、美术方向、修框架 | 按观察会话写的提示词讨论或执行 | 不改试用记录 |

GDD 这类规划由用户和 Claude 会话讨论，写成草稿后再交给项目会话整合；具体执行由用户发提示词给项目会话。

## 开始试用

1. 确认用户给出：游戏项目路径、设计资料位置。项目在框架仓库以外，读取项目目录和会话日志前先说明要读什么、为什么，等用户同意。
2. 在 `tmp/<游戏>-trial-<日期>/` 建两份文件，续接时先读它们：
   - `plan.md`：怎样使用本计划；设计资料表；开头几步（步骤、谁做、做什么、做到什么算完成、顺带测的待办条目）；`framework/todo.md` 各条目在游戏的哪一步测到，测不到的写明。
   - `trial-log.md`：基本信息（项目路径、创建时的框架提交、设计资料、日志位置）；分工；规则；当前停点；步骤记录；讨论与决定；问题清单。各节的格式见下文。
3. 发给项目或子会话的提示词存进同目录的 `prompts/`。

## 每次用户来时

先核对现状，再回答用户的问题：

- **项目**：新提交、工作区状态、`docs/progress.md`。
- **会话日志**：Codex 的日志在 `~/.codex/sessions/<年>/<月>/<日>/rollout-*.jsonl`，按记录里的 `cwd` 认项目；模型为 `codex-auto-review` 的是审批会话，不是用户线程。Claude 子会话用 `list_sessions` 核对，因为 Feature 也可能在 Claude 会话里做。用户不必粘贴输出。
- **主动找问题**：对照项目规则和框架说明，找出用户没发现的走错、多问、漏问、绕路和过时的文字。
- 更新 trial-log 的步骤记录和当前停点。

## 记录的格式

- **步骤编号**：两位数，同一步拆开时加字母，例如 `05a`、`05b`；按实际发生顺序往下编，同一步重做时编号不变。用户开的线程名写成“编号 主题”，`prompts/` 下的文件名写成“编号-主题-日期.md”。
- **步骤记录**：列为编号、日期、提示词（来源）、模型 / 推理强度 / 是否开 Fast、结果、相关待办条目。
- **当前停点**：几条线并行时（例如 Feature 线、美术线、声音线、框架修改）每条线一行：停点、记录在哪、负责会话、在等什么。一条线定下了会影响别的线的结果（镜头、阈值、尺寸），当场在这一行写要转给哪条线，并转达给负责的会话。表下写项目最新提交、未提交的文件和项目里框架副本对应的框架提交。
- **讨论与决定**：和用户讨论出结论、会影响后续步骤或框架修改的内容，写问题、结论或用户的选择、理由、后续去向。只是解释、没有结论的问答不记。
- **问题清单**：列为编号、时间、步骤、现象、证据、判断（提示词 / Skill / 规则 / 工具 / 一次性）、拟议改法、状态。证据写会话日志文件与时间、项目文件 `路径:行号` 或提交号；没读过的记录不写成证据。问题由观察会话统一编号，子会话不直接追加。修完后状态写“已修”和框架提交号。

## 提示词

- **每步怎么定**：用户先从提示词浮窗挑一条，告诉观察会话；观察会话再说自己推荐哪条，不一致当场讨论，两者都记进步骤记录。能不能找到提示词本身就是试用内容，所以观察会话不先给答案。
- **给用户转发的文件只放要发送的文字**：用户会把整份文件原样发出，说明写进步骤记录，不写在文件里，也不出现“试用”“观察会话”。
- **给子会话的提示词**固定带上这一段：“讨论或执行中，凡是框架的提示词、Skill、规则或工具让你走错、多问、漏问，或被用户纠正，在最终回复末尾的「框架问题」一节逐条写出现象、证据和拟议改法。只记录，不修改框架文件，也不改 trial-log。”观察会话收到后统一编号写进问题清单。

## 冻结线与修复

- **立即修**：挡住游戏进度、或会让下一步做错的问题。改分发源并提交，再同步进项目，然后继续。
- **集中修**：其他问题记进问题清单，阶段结束时（例如 GDD 定稿、一个 Product 交付）一起处理：
  1. 需要时用 [framework-retro-yaya](../framework-retro-yaya/SKILL.md) 复盘，交用户选择范围。
  2. 和用户逐条讨论问题清单，决定题按根 `AGENTS.md` 的提问方式编号；把决定和修复顺序写进同目录的修复计划，例如 `fix-plan-<日期>.md`，每项写内容和来源（题号、问题编号）。
  3. 按计划连续修复，每项单独提交，全部做完统一汇报；只在遇到计划没覆盖的决定、或计划写明“动手前先出方案”的项时停下。改提示词、场景或关系图时用 [prompt-and-graph-maintenance-yaya](../prompt-and-graph-maintenance-yaya/SKILL.md)。
  4. 在修复计划和问题清单写回提交号。
- **同步进项目**：按[让项目里的框架副本与框架对齐](../../../framework/godot-project-manual/foundations/01-framework-and-project.md#让项目里的框架副本与框架对齐)只更新改到的框架副本文件，`docs/`、`game/` 等项目内容不动；在项目里单独提交，并在 trial-log 记下对应的框架提交号。

## 收尾

试用记录留在 `tmp/`，不进 Git。长期有效的经验写回职责所属的框架文件：Agent 自己的流程失误写 [Lessons](../../../framework/AGENTS.md#lessons)，试用做法本身的变化改本 Skill，用户偏好写项目记忆。

本 Skill 返回不结束它所在的已授权任务，已有的具体授权按[授权在后续对话中的延续](../../../framework/maintenance/maintenance-and-sync.md#授权在后续对话中的延续)继续有效。
