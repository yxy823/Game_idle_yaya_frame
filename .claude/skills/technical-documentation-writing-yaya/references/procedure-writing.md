# 框架流程与场景文档

用于框架的操作指南、维护流程和场景页（包括场景速查手册中的游戏开发场景）。围绕一个明确处理目标说明入口、动作和可验证出口；多个步骤可以共同完成同一目标，不按步骤数量判断是否需要拆页。本参考不规定实际游戏项目中 GDD、Product 或 Feature 设计的章节。

## 11 类信息及其边界

下表维护流程信息的分类名称、边界和顺序。框架场景手册的编写规范决定何时采用这套分类以及具体标题、编号和提示词对应方式。按读者需要只展示有内容、有查阅价值的栏目；空项省略，未知但影响执行的内容须明确缺口。概念页、工具参考、设计依据和审核报告不必套用此结构。

| 分类 | 核心问题与边界 |
| --- | --- |
| 触发场景与使用时机 | 为什么现在考虑本流程；触发不等于已经满足执行条件 |
| 前置条件与适用范围 | 现在能否开始，适用与不适用什么情况；缺少条件后的处理另写在路径或阻塞中 |
| 参与角色与职责边界 | 谁提供输入、决定、执行与验证；不在这里重复详细步骤 |
| 流程概览 | 经历哪些主要阶段和判断节点；不展开命令或点击细节 |
| 执行步骤 | 谁对什么对象采取什么动作；保留动作所需的条件、入口与参数 |
| 步骤产出与状态变化 | 这一步得到什么可核实结果，何时可以继续；按执行顺序观察 |
| 资源与文件影响 | 哪些对象被读取、新增、修改、删除或替换；按对象汇总，不重放全部步骤 |
| 条件分支与路径规则 | 预期的合法路径如何分流、汇合或转入其他流程 |
| 阻塞、异常与范围变化 | 为什么无法继续，必须保留什么，补齐什么后从哪里恢复或转入哪个流程 |
| 完成状态与验证标准 | 如何证明整篇流程的目标达到；不把中间产出当成最终完成 |
| 流程关联与衔接关系 | 哪些上游、下游、依赖或替代流程与本页相关；选择条件只在相应路径中展开 |

分类区分信息职责，不要求重复写同一件事。短流程的步骤若已清楚表达出口，无需再造一张同义表；复杂流程可以用相同步骤编号对照产出，缩短动作段中的重复说明。

## 写清入口和单篇目标

- 标题写出会改变处理方式的状态和要处理的事情，具体测试、操作或发现过程放在触发场景中。
- 如果入口依赖“已发布”“已验收”等状态，写明实际执行仓库的判定证据；不靠一次测试、文件存在或一次提交推定。
- 同类场景采用一致的判定依据和例外分类；实际处理不同则保留差异，不能只为表面对称复制步骤。
- 正常分支仍服务于本页目标；若需要在两套独立目标和处理方法之间选择，必须调整入口或拆页。正常等待输入或人工验收可以是待完成状态，不伪装为异常。

## 步骤、工具与产出

每步围绕一个可判断完成的目标。说明执行者、操作对象和真实入口；一步的说明含多个动作或约束时，按动作与约束分段；因果解释可保留短段落，不把整步塞进一个表格单元。

- **实际入口**：涉及 Skill、Agent、提示词或命令时，核对真实名称与位置。一个工具贯穿全篇时统一说明，切换执行者或方法时再就近注明，不逐步机械重复。
- **职责归属**：没有专用角色或工具就描述实际执行者与方法。不要编造名称、把 Skill 调用写成自动委派，或将用户负责的验收改成 Agent 代替判断。
- **可执行命令**：就近交代工作目录、必要准备、替换参数和覆盖、清除等副作用。共用准备可以链接到准确小节，关键输入不能要求读者凭记忆补齐。
- **结果含义**：写出预期看到的输出及其支持的结论。退出码为零可能只代表工具执行完成，不能自动等同于整项任务或人工验收完成。
- **编号**：同一流程采用一套步骤编号。若采用 `S1｜记录问题与现场`，S 步骤本身就不再加 `1.`；一个 S 步骤内部有先后顺序的小操作，可以用编号列表。产出表沿用相同的 S 编号，不额外定义业务状态。

例如，动作写“按维护说明核对受影响的 Markdown 正文、链接、锚点与导航”，出口写“修改涉及的事实与示例和源材料一致，已检查的链接、锚点与导航有效”。不能把这个出口写成“用户已经确认阅读体验”。介绍项目工具回归的页面则必须明确被测的是哪个实际项目版本，不把框架源文件存在当成外部项目已更新。

## 阻塞与完成

阻塞说明提供可采取的下一步，区分原因、需要保留的现场或材料、恢复条件与恢复位置。无法验证就如实保留验证缺口，不调整验收标准使流程看似结束。

完成条件以已确认目标为依据，用文件、可观察状态或真实检查结果表达。不要为了“客观”而自行新增测试、人工审批、提交要求或完成门槛；局部步骤或页面目标达成，也不取消尚未完成的更大范围授权。

例如，一篇用日志解释异常行为的诊断指南，结尾只写“复制日志并关闭工具”，交代的是保存和清理，还没有说明诊断得到什么：

- 目标是解释行为或缩小范围时，写明记录支持的判断、与预期行为的差异，以及仍未排除的可能性。
- 证据不足时，说明缺少什么、下一步从哪里补充；若原目标要求确认根因，保留“尚未定位”的状态，不能把保存日志当作已经完成。

这些结论可以直接写在结束步骤中，不必新增报告模板或固定栏目，也不要求所有诊断都以修复代码结束。

核心保护要求必须落在受影响对象上。例如要求保留既有验收记录时，在资源影响中注明该记录保持原有事实，并说明新结果的实际记录位置，不能只在结尾笼统提醒。

## 来源和阅读检查

流程页提供开始操作所需的信息，详细工具契约和方法规则引用其权威来源。框架场景指向集中维护的提示词入口，不复制一份提示词正文；具体对应关系遵循场景手册规范。维护进度、待迁移范围与历史解释放在已有维护位置，不混入稳定操作正文。

从读者当前情境检查标题、前提、动作和出口是否一致。确认步骤与产出对应，分支不会把另一套任务隐藏在页内，阻塞时仍能找到恢复位置。只核对本次变化，不因为整理文案而要求读者重走未变化的业务流程。
